Found by coord PR-236 (lethal-code, 2026-11-19), red check R6. Related: [[R814]], [[R859]].

**What happens** (`scripts/al-runner-v3-update.ts`):
- `readReceipt` compares the receipt's `pinDigest` with this checkout's hand pin only when this checkout HAS that pin
  (`hand !== undefined`). A receipt naming a pin this checkout does not know skips the digest check entirely.
- `gateOne`'s default pass path then writes no `gated-builds` ledger row (only the log line "no gated-builds row: this
  script's checkout has no pin …"). It still returns `pass`, and still moves `current` when `movesCurrent` holds.
- The build's `.gated` names that unknown pin in `readingsFrom`.

**Why it is not a silent wrong answer.** Every reader refuses an unknown pin loudly:
- `checkGated` calls `adoptV3Pin`, which throws `al-runner-v3-unknown-readings: "<id>" is no pin in this checkout`;
- `parseGatedBuilds` refuses a ledger row whose `readingsFrom` is no hand pin.

So nothing judges by it unchecked. The harm is AVAILABILITY: `current` can move to a build that every v3 session then
refuses. "Merge master" cannot fix that when the pin was removed on purpose (for example a fork's pin, such as
perf-combined's, after PERF-10).

**When it can happen.** The gate runs at `.gated`'s LethAL commit, the update script at its own checkout. A pin present at
the first and gone at the second gives exactly this.

**Fix to decide.** A pass whose receipt names a pin this checkout does not know becomes infra-fail by name (or `held`)
BEFORE any copy, ledger or `current` move. It needs one red test in each direction: an unknown pin refuses; a known one
passes as today. The refresh and private paths already require `pinApplied === pinRootOf(gated)`, but `pinRootOf` can
itself name a pin this checkout lacks; the same rule should cover them.
