**What happened.** The al-runner gate was run to re-record its baseline for [[R193]]/[[R197]] and
refused AFTER recording: *"no execution context carries a `platformAppsDir`"*. Its first line named
the build: **al-runner v2.10.0.0**, three minors past the 2.7.0.0 the gate last saw. The per-mutant
table was unchanged (3/16/0, the relabelling proof passed); only the pin was gone.

**Why.** Invoked exactly as the backend invokes it, with `--auto-provision` and a warm cache, 2.10
prints no `[provision]` line at all: neither `Downloaded <N> app(s) ... to <dir>` (2.1.2.0) nor
`platform apps already complete at <dir>` (2.7.0.0). R147's refusal text had named this case from
the start ("the cache was already complete and the runner said nothing"); 2.7 made it speak, 2.10
made it silent again. This is R123's class, the runner rewording between days, and the gate caught
it the same way it caught the 2.7 change.

**The fix, and why it is not a guess.** The runner still prints
`[bc] selected BC 28.1.49838.54169 (C:\...\artifacts\28.1.49838.54169)`, naming the artifact
directory it chose. Both earlier sentences named the platform apps at `<that directory>\platform-apps`,
verbatim, so the location is measured layout rather than an assumption, and the backend keeps its
own check: the derived directory must be readable and hold at least one `.app`, exactly the
already-complete rule. A directory that is not there is a refusal naming the derivation, never a
silent fall-back to `--auto-provision`.

**What is still owed.** The measured al-runner contract in `docs/measurements/README.md` §"al-runner
v2" should record 2.10's silence beside 2.7's sentence, and [[R123]] (probe the contract per
session) remains the row that would have found this before the gate did.
