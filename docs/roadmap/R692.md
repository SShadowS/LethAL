## Traced and fixed (R-699, 2026-10-24)

Traced by reading the code (no server call).
- **Fail-closed today.** A 500 from `RunMutant` scores nothing: the transport returns `error` / `in-flight-unknown` with
  its fence. The answer read-back accepts only a committed answer for this exact attempt and op, so a 500 never becomes
  killed or survived. The marker stays set, `LeaseSession.finish` does not release the lease, and the server refuses
  every later acquire: `operation-busy`, then `operation-orphaned` after expiry plus 15 s, then
  `container-needs-recycle`. The match between the give-up time and `expiresAt` was a coincidence. bc1 needs a restart
  and `ForceResetLease`.
- **No `StopHungRun` after a 5xx.** The request is closed, so no 408 can arrive to prove the stop; and its tombstone
  would let the next session in on our word alone, which R665 ruled against.
- **What this fix adds** (diagnostic only; verdict, operation and fence unchanged): BC's error text, the first 400
  characters, is kept in the failure message for `RunMutant` (read with a time bound, R191; an unreadable body adds
  "(body unread: ...)") and for `RunMutantMany`. The stranded note and the quarantine detail advise "raise the floor
  with --mutant-timeout-ms" only when the run reached its budget; a fast HTTP status names itself instead.
- **Still unknown:** what made BC answer 500 (a BC fault, the mutant escaping `Runner.Run()`, or an error in the
  finish phase), and whether it repeats. The next occurrence will carry BC's text.
