Found by coord task R-915 (BC.History E-Document Core and Subscription Billing on al-runner v3, `"transport": "serve-entries"`, 2026-11-11). Evidence: `/coord/handoff/R-915/{edoc,sb}.sample.serve-entries.stderr.txt`. Related: [[R916]], [[R786]], [[R612]], [[R761]].

**What happened.** Both runs named the transport explicitly, so no fallback applies (R761), and both failed by name:
- E-Document Core: `al-runner-v3-entries-batch-refused` (its install code reads a resource file, al-runner #5635), after 1,160 s.
- Subscription Billing: `al-runner-v3-entries-warmup-dirty` (a warm-up row R612 does not keep: XmlPort VariableText with TextEncoding = WINDOWS), after 1,876 s.
In both, the time went on the whole baseline first. The refusal was known from the first warm-up request.

**Invented repro.** A test app with one test that al-runner refuses by name at the serve warm-up (for example, an XmlPort import it does not pin) and many slow passing tests. `lethal run --backend al-runner-v3` with `"transport": "serve-entries"` runs every baseline test, then fails `al-runner-v3-entries-warmup-dirty`.

**Wanted.** With an explicit serve-entries transport, the warm-up's refusal fails the run before the rest of the baseline. The message names the row and says the default (no `transport` key) would fall back to one-shot. This is a different fix from R916, which asks the default to keep serve for the other tests.

**Fixed (coord R-922), in two parts.**
- **A whole-batch refusal (E-Document Core).** An explicit serve-entries run, and only that, now sends one probe request after
  deploy and before the baseline: one NONE entry for the test codeunit with the fewest tests, on a daemon closed right after. It
  judges only `entries-batch-refused`. Live check on E-Document Core (R-915's sample, sources rebuilt from BC.History, edge-42af5d384):
  the run failed by name 63 s after it started, at the probe of codeunit 133501 (34 s, most of it the daemon's start), with no
  baseline call. R-915 reached the same refusal after 1,160 s: about 1,097 s saved. Upstream: al-runner issue 5635 (already filed).
  No invented app reproduced the refusal: six variants of resource-reading install code (in the target or the test app,
  `GetResourceAsText` or `ListResources` + `GetResource`, resource folders on both apps) all ran green on serve.
- **A warm-up row R612 does not keep (Subscription Billing).** Under auto, [[R921]]'s tie rule usually moves such a codeunit to
  `method`, where the row is never sent. Where it cannot (an explicit `isolation: "test"`, or `method` loses a test), failing at the
  baseline row could refuse a run that would pass: whether the codeunit enters the warm-up union depends on coverage, known only after
  the baseline. So that failure stays after the baseline, and its message now says the default would re-run the session one-shot when
  every unkept row is a by-name refusal.
