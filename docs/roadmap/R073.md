**`RemoveCommit` ships proven on its refusals and unproven on its claims.** Registering it changed no fixture's mutant set — both `Commit` sites in `fixtures/sandbox-data` are the shadowed negatives (`Data Shadow` declares `Commit`; `Data Ops.ShadowedBuiltins` calls it qualified) and both are correctly refused, verified offline at 93/16 specs. So no gate has ever generated, let alone killed, a `remove-commit` mutant. Adding a positive is not free: a `Commit()` in an object declaring no `Commit` lands `no-coverage`, not `survived`, unless a covering test comes with it, and the honest fixture shape is a transaction-boundary test — write, `Commit`, raise, then assert the write survived. That also settles what R33 left unmeasured: whether a committed write survives a later uncaught error under the platform runner's isolation, which is the operator's actual kill mechanism. (`Commit()` itself is measured to EXECUTE in the fenced run.)
