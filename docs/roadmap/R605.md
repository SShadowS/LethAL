**Filed 2026-10-21 by R-604** (lethal-preproc; orchestrator ruling). Linked from [[R599]].

**What.** On bc3, `scripts/bc-republish.ts` uninstalled `LethAL Sandbox App` 1.0.20747.27757 (a version a gate
run minted) and called the automation API's bound `Microsoft.NAV.unpublish` action. Both answered HTTP 204 and the
extension row was gone. Publishing the app.json build, 1.0.0.2, over the dev endpoint was then refused:

> HTTP 422 `{"Message":"Publishing failed due to 'Cannot install the extension LethAL Sandbox App by LethAL 1.0.0.2
> because a newer version 1.0.20747.27757 was already installed.'. The original extensions have been restored.",
> "ErrorType":"InvalidOperation"}`

The message's last sentence was not true here: the restore run that followed found all six removed apps absent
(`republish-bc3-restore.log`, "absent ... nothing to remove"), so nothing had been restored.

So BC keeps an installed-version record after uninstall plus unpublish. Only a publish over the dev endpoint
(`dev/apps`) was measured; the automation API's own `upload`/install path was not tried. On a Windows container `Sync-NAVApp -Mode
Clean` clears it; nothing measured clears it on the Linux servers. `uninstallAndDeleteExtensionData` is offered by
the API but is NOT measured, deletes data, and was ruled out on bc3 (it carries the R594 Continia oracle).

**Consequence.** R599's second way to close ("unpublish and republish through the automation API") cannot bring a
target back to its app.json version once a gate has minted one. It can replace a TEST app (its record is at its
app.json version, and a same-version publish is accepted) and a target at a NEW minted version. The bc3 restore did
exactly that: targets at versions from `reserveAppVersion`, test apps at app.json versions, each read back by
version and sha256.

**Evidence.** `/coord/handoff/R-604/republish-bc3.log` (the refusal), `/coord/handoff/R-604/republish-bc3-restore.log`
(the restore with `--mint`).

**To close.** Measure what clears the record on a Linux bc server (an owner-side step, or an API call), or rule
that a target's resident version does not matter (every gate publishes its own instrumented target at a minted
version) and say so in R599 and `docs/gates/servers.md`.
