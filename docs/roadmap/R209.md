title: "`resolveVarRef`'s `VarSymbol` reference identity holds for procedure locals, parameters and object globals, but NOT for trigger-locals, and nothing in its contract says so"
status: "open, filed 2026-09-06 while building [[R196]]'s `classifyHangCapable`, which needed to compare two resolved variables for sameness"
section: "correctness-risks"
order: 921
---

**Measured, not inferred.** `resolveVarRef(node, ctx)` (`packages/engine/src/semantic/resolve-var-ref.ts`)
is a thin adapter over `receiver.ts`'s `lookupVar`. Calling it twice for two identifiers that both
refer to the very same declaration:

- **Procedure-local** (`var I: Integer` on a `procedure`): three identifiers reading `I`, resolved
  three times, all three results pairwise `===`. One object.
- **Trigger-local** (`var N: Integer` inside a `trigger`): three identifiers reading `N`, resolved
  three times, all three results pairwise `!==`, despite identical `name`/`typeText`. Three
  different objects for one declaration.

**Cause.** `lookupVar` checks `triggerScopeVar` first (`receiver.ts`), and that function calls
`collectVarDeclarations(varSection)` fresh on every invocation. `symbol-table.ts`'s own module doc
explains why: trigger names repeat per object (every field can declare its own `OnValidate`), so
trigger-local scope is deliberately **not** indexed in `buildSymbolTable`'s `globals`/`procedures`
maps the way object globals and procedure locals/parameters are: there is no name-keyed slot to
cache into, so `triggerScopeVar` re-parses the `var_section` on every call instead. `globalsOf`,
`localsOf` and `resolveProcedure` all read from those cached maps and return the SAME stored
object on repeat lookups; `triggerScopeVar` does not, because it is not backed by one.

**Why it is a live hazard, not a curiosity.** Nothing about `resolveVarRef`'s type signature
(`ALSyntaxNode, SemanticContext -> VarSymbol | null`) hints that identity is conditional on which
scope the answer came from. A caller who writes `resolveVarRef(a, ctx) === resolveVarRef(b, ctx)` to
ask "same declaration?" gets a correct answer for every object global and every procedure
local/parameter, and a silently wrong `false` the moment either `a` or `b` sits inside a trigger.
[[R196]]'s Task 2 brief was written against exactly this assumption (measured earlier in the same
plan, over the non-trigger paths only) and its own test suite includes a trigger fixture that would
have failed had the code shipped as specified.

**Current workaround, in the one caller that has hit this** (`packages/builtin-tier1/src/loop-hazard.ts`,
`sameDeclaration`): compare `.node.startIndex` of the two declarations instead of the `VarSymbol`
objects themselves. Two distinct declarations can never start at the same byte offset **within one
file**, so this is exactly as precise as reference identity where reference identity happens to
hold, and correct where it does not. This is a per-caller workaround, not a fix to `resolveVarRef`
or `lookupVar`: every future consumer that wants "same declaration?" has to know to do this instead
of the obvious `===`.

**The precondition that makes the positional workaround itself safe, and why it does not generalise
for free:** `startIndex` is a byte offset *within its own file*. Two declarations in *different*
files can share one. `loop-hazard.ts`'s comparison is sound only because both sides are always
resolved from identifiers inside the same procedure of the same object (an assignment's target and
an enclosing loop's condition), so both candidates are necessarily in the same file. A caller that
compared symbols resolved from two different files by `startIndex` alone would be silently wrong.

**Why a source-level fix is not obviously available.** The natural fix is to make `triggerScopeVar`
cache its result the way the object-level maps do, keyed on the trigger's own `var_section` node.
That needs a stable key: `ALSyntaxNode` (`syntax-node.ts`) wraps each `web-tree-sitter` node in a
fresh `WrappedNode` on every access to `.children`/`.namedChildren`/`.childForFieldName`/`.parent`,
so the wrapper itself is not a usable cache key (two accesses of the "same" node are two different
JS objects). A cache would have to key on something else stable per node, such as
`(sourceFile, node.startIndex)`, which is available but is not free of its own coordination (the
cache would need to be attached to, or threaded alongside, the `SymbolTable`/`SemanticContext`
already in scope, and invalidated correctly if either is ever reused across a re-parse). Nobody has
scoped that change; this row exists so the next consumer of `resolveVarRef` does not rediscover the
same landmine by tripping on it.

**To close:** either (a) give `triggerScopeVar` a stable per-`var_section` cache so `VarSymbol`
identity holds everywhere `resolveVarRef` can answer, and update every existing "same declaration"
comparison (currently just `loop-hazard.ts`'s `sameDeclaration`) to drop its positional workaround
once identity is trustworthy again, or (b) leave the object-identity contract as "holds outside
triggers only" and document it directly on `resolveVarRef`'s own doc comment (not just here), so a
future caller reads the caveat at the point of use rather than discovering it by testing.
