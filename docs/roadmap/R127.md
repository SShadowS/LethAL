**`--only <glob>` selects FILES. There is no way to say "only this operator".** `MutationSetOptions`
carries exactly one scope field, `only`, matched against project-relative paths; the CLI exposes it
as `--only` and nothing else narrows what a run deploys. `--tests-only` narrows the SUITE, not the
mutant set, and it can change a verdict, so it is not a substitute.

**The cost is measured, not hypothetical.** R85's first rung wanted the rate at which Continia
Document Output's suite notices an argument swap. It could only ask for FILES, so it deployed
**894 mutants to score 3 swaps** (`docs/campaign/2026-08-07-r85-swap-rate/rung1.result.md`) — every
`empty-block`, `void-method-call`, `negate-conditional`, `return-value` and `conditional-boundary`
site in the chosen files came along, and 80% of the whole scope turned out to have no covering test.
The run then 502'd and quarantined at M0487 with roughly 142 mutants never run.

**With an operator filter the same question is cheaper AND better designed.** The whole
`swap-call-arguments` population on that project is **437 sites across 91 files**. Deploying exactly
those is FEWER mutants than the truncated run already spent, covers the entire population rather
than a sample, and needs no sampling rule at all — so there is nothing to pre-commit a seed for and
no selecting-on-a-correlated-variable hazard. The coverage split would be decided by the run instead
of guessed in advance, which is precisely what R85's next rung is required to have.

**It also unblocks a requirement that is currently UNSATISFIABLE.** R85 says a second rung needs "a
coverage-aware selection rule, decided from a prior run's coverage split". Measured against the only
prior run that exists: it touched **11 files**, and just **3** of them had any covered mutant. Those
3 files hold **10** of the 437 swap sites, and 3 of those 10 were already scored. So the strictly
coverage-aware frame derivable today has a ceiling of about 7 fresh observations against a
requirement of 30. The frame cannot come from that run; it has to come from a cheaper way of
reaching the whole population.

**Shape, not prescription.** The obvious spelling is a repeatable `--operator <name>` filtering
`generateMutationSet`'s output by `operatorName`, mirroring `--only`'s "a pattern matching nothing
throws" rule so a typo cannot silently deploy zero mutants and report a clean run — this project's
signature bug, and the reason `only` already refuses an empty match. Whether it belongs beside
`only` in `MutationSetOptions` or as a separate field is a design question, not a settled one.

**What it must NOT become:** a knob that changes a VERDICT. Narrowing which mutants are deployed
narrows what a run measured and must show up in `validity` the way `--only` does (`narrowed`), so a
reader cannot quote an operator-scoped score as a project score. R41 already built that machinery
for files; this would reuse it, not reinvent it.

A second, larger mechanism would also solve R85 — a coverage-only pass that records the project's
baseline coverage map without deploying any mutant, so a coverage-aware frame can be built for any
question. That is strictly more work than the filter and is not needed to unblock this one.

Filed 2026-08-08 while planning R85's second rung, which is deferred on it.

**BUILT 2026-08-08.** `--operator <name>` (repeatable) on `lethal run` and `lethal run --dry-run`;
`MutationSetOptions.operators` / `SessionConfig.operators` underneath. What the row got right, and
the two things it did not.

**Right about the shape.** A repeatable flag filtering `generateMutationSet`'s output by
`operatorName`, mirroring `--only`'s "matching nothing throws" rule, is what shipped.
`resolveOperatorNames` is the `admittedByOnly` analogue: it resolves before any file is read, so a
typo fails at once, and it accepts a bare `swap-call-arguments` because every builtin is
`lethal.`-prefixed and requiring the prefix would buy nothing.

**Right about the two hard constraints, and both are now tested.** The narrowing surfaces as a new
`operator-narrowed` caveat rather than reusing `narrowed`: the two narrow different axes, and
`CAVEAT_INTERPRETATIONS.narrowed`'s own prose says "the run was scoped by `--only`", which would have
become false. `reliability` degrades to `narrowed` on the operator axis alone. `renderConsole` prints
a `NARROWED (--operator)` line beside the score.

**WRONG, or at least incomplete, about where the filter goes.** The row says "filtering
`generateMutationSet`'s output by `operatorName`" and stops there. Filtering the raw spec list is
UNSAFE, and the failure is exactly the class this row forbids. `dedupeSpecs` drops a Tier-1 spec when
a Tier-2 operator emits byte-identical AL at the same node (design §3.2). Measured on a four-statement
fixture: `SetRange`, `CalcFields` and `TestField` each produce a `void-method-call` spec that LOSES to
its Tier-2 claimant, and only `Modify(true)` keeps one. Filter before dedup and
`--operator void-method-call` deploys FOUR mutants where an unfiltered run deploys ONE — three of them
mutants the project's real mutant set does not contain. The filter therefore runs AFTER per-file
dedup, joined by reference identity the way `cli.ts`'s dry-run summary already does, and the
operator-scoped set is a strict subset of the unfiltered deployed set. Red-checked: reverting that one
line turns three tests red, including a general one that unions every single-operator run and compares
it against the unfiltered set.

**The exclusion count is a SITE count, not a file count, and that asymmetry with `--only` is
deliberate.** `--only` skips files before their specs exist, so their site count is genuinely
unmeasured and the report says "N files were not considered". Every operator still runs over every
admitted file here and the filter drops specs afterwards, so `excludedSiteCount` is a number the run
actually measured — reporting a file count would throw away a fact in hand.

**The barren-operator refusal needed a second message.** A registered operator with sites ONLY in a
file no selector var can be injected into (an `xmlport`, a `query`) deploys nothing, and refusing it
with the same words as "no sites at all" sends the reader hunting for code that is right in front of
them. The refusal names that case separately.

**Not done, and filed rather than silently left:** the campaign fence (`campaign-fence.ts`) still
requires BOTH `--only` and `--tests-only` and does not recognise `--operator` as a narrowing. An agent
under that fence cannot use operator scope alone. Deliberate: `--operator empty-block` on Document
Output is still thousands of sites, so treating it as sufficient narrowing would weaken the fence. The
product's own pre-flight refusal (`LARGE_RUN_MUTANT_THRESHOLD`) does count it, and names both levers.

**Found while doing this, and fixed here:** the skipped-file warning told users "only a codeunit or a
table can carry the injected `var MutationSelector` declaration". That has been false since R40 added
`page`/`report` and R30 added `pageextension`/`tableextension` — six carrier kinds today. `CARRIER_KINDS`
is now exported from `@lethal/schemata` and the warning derives the list instead of restating it. Two
doc comments claiming the same stale thing are corrected in place.
