title: "The only scope knob is a FILE glob, so measuring one operator on a real project costs every other operator's mutants in those files"

**`--only <glob>` selects FILES. There is no way to say "only this operator".** `MutationSetOptions`
carries exactly one scope field, `only`, matched against project-relative paths; the CLI exposes it
as `--only` and nothing else narrows what a run deploys. `--tests-only` narrows the SUITE, not the
mutant set, and it can change a verdict, so it is not a substitute.

**The cost is measured, not hypothetical.** R85's first rung wanted the rate at which Continia
Document Output's suite notices an argument swap. It could only ask for FILES, so it deployed
**894 mutants to score 3 swaps** (`docs/campaign/2026-08-07-r85-swap-rate/rung1.result.md`) — every
`empty-block`, `void-method-call`, `negate-conditional`, `return-value` and `conditional-boundary`
site in the chosen files came along, and 80% of the whole scope turned out to have no covering test.
The run then 502'd and quarantined at M0487 with roughly 142 mutants never run.

**With an operator filter the same question is cheaper AND better designed.** The whole
`swap-call-arguments` population on that project is **437 sites across 91 files**. Deploying exactly
those is FEWER mutants than the truncated run already spent, covers the entire population rather
than a sample, and needs no sampling rule at all — so there is nothing to pre-commit a seed for and
no selecting-on-a-correlated-variable hazard. The coverage split would be decided by the run instead
of guessed in advance, which is precisely what R85's next rung is required to have.

**It also unblocks a requirement that is currently UNSATISFIABLE.** R85 says a second rung needs "a
coverage-aware selection rule, decided from a prior run's coverage split". Measured against the only
prior run that exists: it touched **11 files**, and just **3** of them had any covered mutant. Those
3 files hold **10** of the 437 swap sites, and 3 of those 10 were already scored. So the strictly
coverage-aware frame derivable today has a ceiling of about 7 fresh observations against a
requirement of 30. The frame cannot come from that run; it has to come from a cheaper way of
reaching the whole population.

**Shape, not prescription.** The obvious spelling is a repeatable `--operator <name>` filtering
`generateMutationSet`'s output by `operatorName`, mirroring `--only`'s "a pattern matching nothing
throws" rule so a typo cannot silently deploy zero mutants and report a clean run — this project's
signature bug, and the reason `only` already refuses an empty match. Whether it belongs beside
`only` in `MutationSetOptions` or as a separate field is a design question, not a settled one.

**What it must NOT become:** a knob that changes a VERDICT. Narrowing which mutants are deployed
narrows what a run measured and must show up in `validity` the way `--only` does (`narrowed`), so a
reader cannot quote an operator-scoped score as a project score. R41 already built that machinery
for files; this would reuse it, not reinvent it.

A second, larger mechanism would also solve R85 — a coverage-only pass that records the project's
baseline coverage map without deploying any mutant, so a coverage-aware frame can be built for any
question. That is strictly more work than the filter and is not needed to unblock this one.

Filed 2026-08-08 while planning R85's second rung, which is deferred on it.
