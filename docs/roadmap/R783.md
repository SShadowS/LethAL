**Filed 2026-10-25 by lethal-preproc, from coord task R-783.** Related: [[R589]], [[R658]], [[R669]].

**What.** The owner set up docker1 (192.168.2.77), a copy of server1's three BC on Linux servers:
- the same compose, image digests, ports per name and logins;
- the same builds: bc1 28.4.53241.56590, bc2 and bc3 .56646;
- a fresh CRONUS on every restart, with no LethAL Control and no Continia stack;
- 4 vCPU, against server1's 22 cores.

Server1 goes off at 04:00 CET on 2026-10-26. This spike measures whether the BC gates run on docker1. It is not a
switch: master and the normal configs keep naming server1.

**Steps.**
- On the spike branch only, make `HOST` (`scripts/bc-app-content.ts`) overridable by `LETHAL_BC_HOST`, with
  server1 as the default.
- Set up docker1's bc3 with Continia, under the bc3 lease.
- Run `itest:bcdev`, then `itest:hang`, on it, and compare the timings with server1's.
- Report what passes, what fails, and the config a switch would need.

**What a switch to docker1 needs.**
1. `HOST` in `scripts/bc-app-content.ts`: change its default, or set `LETHAL_BC_HOST` (this spike).
2. `MARKER_HOST` in `packages/runner/itest/out-of-use.ts`, hard-coded to server1. It must move with `HOST`. On any
   other host, `markedServerFor` matches nothing, so out-of-use markers are silently NOT checked. Nothing refuses.
   `bc-linux-setup.test.ts` pins the two equal.
3. `scripts/r658-hang-gate.sh`: `WANT="server=192.168.2.157:7149|7249"` is hard-coded for bc2 and bc3. The wrapper
   refuses any other host's target line.
4. The gitignored configs and launch files. Rerun `bc-linux-setup.ts` per server; bc3 adds
   `--with-continia --accept-build 28.4.53241.56646`.
   - It writes `lethal.config.bcN.json` in `sandbox-app`, `-data`, `-hang` and `-harden`, and the
     `.vscode/launch.bcN.json` files.
   - Every worktree that copied those files (lane-code, lane-bugs, task worktrees) needs fresh copies.
5. `docs/gates/servers.md`: the host and the proof table. Proof is per server, so every gate must be proven on
   docker1's bcN before it runs there.
6. `scripts/testdata/bc-demo-kraken-pin.json` and the bc-demo config, if bc-demo moves too.
7. docker1 also starts from a fresh CRONUS after every restart. Rerun setup each time: about 100 s on a fresh server.
8. Prose and frozen specs that quote 192.168.2.157: `fixtures/README.md`, `docs/talk-laptop.md`, the autonomy
   README, and 4 specs under `docs/superpowers/specs/`. Update the prose; the frozen specs stay as history.

**Proposal: a switch by one setting.**
- One source: a small module in `packages/runner/src` exports `BC_LINUX_HOST`, the host name with no scheme. It
  reads `LETHAL_BC_HOST` (validated as `http://<host>`, as the spike's `hostFrom` does). The default is a committed
  constant, so a switch is a one-line commit, not an environment variable that every process must carry.
- `HOST` in `scripts/bc-app-content.ts` becomes `http://${BC_LINUX_HOST}`. Scripts may import packages.
- `MARKER_HOST` in `out-of-use.ts` becomes `BC_LINUX_HOST`. Then `bc-linux-setup.test.ts`'s mirror test checks the
  derivation instead of two copies.
- `r658-hang-gate.sh` computes `WANT` from the same module: `bun packages/runner/src/bc-host.ts` prints the host.
  It does not get its own default, so the shell copy cannot drift. Its test would check the printed host.
- A guard against the silent case in item 2: `printItestTarget` refuses a config whose host is a known BC on Linux
  host other than `BC_LINUX_HOST` (server1 or docker1), by name. A config left over from the old host then refuses
  before any lease or call, instead of running unmarked.
