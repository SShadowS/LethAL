**Filed 2026-10-25 by lethal-preproc, from coord task R-783.** Related: [[R589]], [[R658]], [[R669]].

**What.** The owner set up docker1 (192.168.2.77), a copy of server1's three BC on Linux servers:
- the same compose, image digests, ports per name and logins;
- the same builds: bc1 28.4.53241.56590, bc2 and bc3 .56646;
- a fresh CRONUS on every restart, with no LethAL Control and no Continia stack;
- 4 vCPU, against server1's 22 cores.

Server1 goes off at 04:00 CET on 2026-10-26. This spike measures whether the BC gates run on docker1. It is not a
switch: master and the normal configs keep naming server1.

**Steps.**
- On the spike branch only, make `HOST` (`scripts/bc-app-content.ts`) overridable by `LETHAL_BC_HOST`, with
  server1 as the default.
- Set up docker1's bc3 with Continia, under the bc3 lease.
- Run `itest:bcdev`, then `itest:hang`, on it, and compare the timings with server1's.
- Report what passes, what fails, and the config a switch would need.

**What a switch to docker1 needs.**
1. `HOST` in `scripts/bc-app-content.ts`: change its default, or set `LETHAL_BC_HOST` (this spike).
2. `MARKER_HOST` in `packages/runner/itest/out-of-use.ts`, hard-coded to server1. It must move with `HOST`. On any
   other host, `markedServerFor` matches nothing, so out-of-use markers are silently NOT checked. Nothing refuses.
   `bc-linux-setup.test.ts` pins the two equal.
3. `scripts/r658-hang-gate.sh`: `WANT="server=192.168.2.157:7149|7249"` is hard-coded for bc2 and bc3. The wrapper
   refuses any other host's target line.
4. The gitignored configs and launch files. Rerun `bc-linux-setup.ts` per server; bc3 adds
   `--with-continia --accept-build 28.4.53241.56646`.
   - It writes `lethal.config.bcN.json` in `sandbox-app`, `-data`, `-hang` and `-harden`, and the
     `.vscode/launch.bcN.json` files.
   - Every worktree that copied those files (lane-code, lane-bugs, task worktrees) needs fresh copies.
5. `docs/gates/servers.md`: the host and the proof table. Proof is per server, so every gate must be proven on
   docker1's bcN before it runs there.
6. `scripts/testdata/bc-demo-kraken-pin.json` and the bc-demo config, if bc-demo moves too.
7. docker1 also starts from a fresh CRONUS after every restart. Rerun setup each time: about 100 s on a fresh server.
8. Prose and frozen specs that quote 192.168.2.157: `fixtures/README.md`, `docs/talk-laptop.md`, the autonomy
   README, and 4 specs under `docs/superpowers/specs/`. Update the prose; the frozen specs stay as history.

**Built: the host from one setting (branch `lethal/r783-switch-ready`, default still server1).**
- `packages/runner/src/bc-host.ts`:
  - `bcLinuxHost(env)` returns `LETHAL_BC_HOST` when it is set, refusing anything but `http://<host>` by name;
    otherwise `DEFAULT_BC_HOST`, server1.
  - `BC_HOSTS` names both known hosts.
  - Run as a script, it prints the host.
- Every consumer derives from it:
  - `HOST` in `scripts/bc-app-content.ts`, and so the configs and launch files the setup script writes;
  - `MARKER_HOST` and `markedServerFor` in `out-of-use.ts`, so out-of-use markers are checked on the host in use;
  - `WANT` in `scripts/r658-hang-gate.sh`, which runs the module and has no default of its own.
- `printItestTarget` throws `BcHostMismatchError` for a config naming the OTHER known host, before any marker read,
  lease or line. A config left on the old host after a switch cannot run unmarked. A host that is not a known BC on
  Linux host (Cronus28, an envtool environment) is not refused.
- Red tests, each red with its consumer's derivation undone:
  - `r783-bc-host.test.ts`;
  - `out-of-use.test.ts`: the marker check follows the setting; a config on the other host refuses, in each
    direction;
  - `bc-linux-setup.test.ts`: `HOST`, `MARKER_HOST` and the launch file follow the setting;
  - `r658-hang-gate.test.ts`: `WANT` follows the setting in each direction; a malformed value refuses.
- **The flip** (branch `lethal/r783-flip`, one commit on top): `DEFAULT_BC_HOST` becomes `BC_HOSTS.docker1`, plus
  `docs/gates/servers.md` and the other live-host prose.

**Runbook: the switch to docker1 (owner ruling, 2026-10-25; flip at 03:00 UTC, after server1 goes off at 04:00 CET).**
1. Before 03:00 UTC, the orchestrator merges `lethal/r783-switch-ready`. It changes nothing on its own: the default is
   still server1.
2. At 03:00 UTC, the orchestrator merges `lethal/r783-flip`. From then on, every process on master defaults to docker1.
3. The owner's host session confirms that docker1's bc1, bc2 and bc3 are up. Their databases start fresh after any
   restart, and the setup script fixes that.
4. **Each lane, in its own worktree, after merging master** (about 03:05 UTC), for each server it uses:
   - check the lease is free (`kraken coord holder bcN`); setup takes the lease itself, so do not hold one;
   - `bun scripts/bc-linux-setup.ts --server bcN --lane <lane>`. For bc3, add
     `--with-continia --accept-build 28.4.53241.56646`. This publishes LethAL Control, the fixtures and, for bc3,
     Continia when they are missing. It rewrites the gitignored `lethal.config.bcN.json` in `sandbox-app`, `-data`,
     `-hang` and `-harden`, and `.vscode/launch.bcN.json`, all naming docker1, then runs `lethal doctor`.
   - `--write-config-only` rewrites the configs with NO server call and no lease, once the server has been set up by
     someone today. One lane does the full setup per server; the rest may use `--write-config-only`.
   - Check: a gate's first line, `[itest target] ...`, must name `server=192.168.2.77:<port>`. A config still naming
     server1 now refuses by name (`BcHostMismatchError`); rerun step 4 for that worktree.
5. Copied configs: a worktree that holds COPIES of another lane's configs (`cp` from lane-code) must copy them again
   after step 4, or run step 4 itself.
6. Fixture `.alpackages` that are symlinks into another lane's worktree: replace them with real copies (`cp -rL`)
   before any gate. See [[R787]].
7. Only the proven pairings run. On docker1, `docs/gates/servers.md` lists:
   - bc3: setup, bcdev, hang, bcdev-names, bcdev-wrapped, tables, chunked, harden, lend, lease, verify, testapp,
     agreement, verify-scale;
   - bc1 and bc2: setup and bcdev only. Prove a gate there before running it.
   - stale-publish and the R-759b proof leg: unproven on any docker1 server.
8. Back to server1, if needed: revert the flip commit, or set `LETHAL_BC_HOST=http://192.168.2.157` for every
   process, then do step 4 again.
