**Filed 2026-10-22 by lethal-bugs during R-601** (the R-601 plan review's I1 and its Q1 advice,
`/coord/handoff/R-601/review-plan-opus.md`; orchestrator ruling Q1).

**What.** Since [[R601]] a resume carries the verdicts of a crashed closed-world run when this
session's guard gives the same closed answer now and the run's recorded server key
(`runs.resource_key`) equals this session's. Two equal answers bracket the window only if nothing
on the server changed in between and came back. Two cases are not seen:

- **A server restart inside the gap.** The `bc1`-`bc3` servers keep their databases in memory, so a
  restart loses every app. A dependent of the test app could exist before the crash and be gone
  after the restart, and the resume's "0 dependents now" says nothing about "then". A restart is
  also a likely cause of the crash.
- **A dependent published and removed again inside the gap** (0 -> 1 -> 0). This is R389's stated
  limit, widened to the length of the crash gap.

The key also omits the tenant (`quarantineResourceKey` excludes it by design).

**To measure (a probe, not a fix).**
1. Is there a readable server start time or boot id (an OData or dev-endpoint read, or a
   LethAL Control field) that a session could record at its first guard ask and compare on resume?
2. Do dev-endpoint publishes and unpublishes appear in BC's install or operation history
   (`NAV App Installed App`, the extension deployment status), with a time a session could compare
   with the crashed run's window?

Either answer, if real, would let the resume refuse a gap it cannot bracket. Use `/al-probe` on a
leased `bc1`-`bc3` server.

**Evidence.** `resumableTestApp` (`packages/runner/src/closed-world.ts`), `quarantineResourceKey`
(`packages/runner/src/resource-key.ts`), the R601 stated limit in `docs/roadmap/R601.md`.

**Still open (2026-10-22, lethal-bugs during R-614).** The probe is designed only; no code and no server call yet
(design: `/coord/handoff/R-614/build-progress.md`, Part 2). The strongest candidate for question 1 is
`serverGeneration` in LethAL Control's `HarnessInfo`: it is seeded on a fresh lease row, which an in-memory
restart forces. But `HarnessInfo` is an OData ACTION, so reading it needs a POST, and the designed probe is
GET-only. It stays open until a probe that may make that one POST (or an owner-run restart) is pre-committed.

**Measured 2026-10-23 on bc1 (coord task R-632b, lethal-code; pre-commitment master 6eb6e37a).** Raw output and the
probe are in `/coord/handoff/R-632b/`. No restart was requested.

- **Q1, `serverGeneration`: a usable restart marker, apart from the restart itself.** The probe read it through
  `HarnessVerifier.verify()` (the `HarnessInfo` POST, which only reads).
  - It stayed `60ccc92ee1aa45de8ad47bacb7d17bca` across two reads 5 s apart, across a coord-lease release and
    re-take, and across a publish and an uninstall of a throwaway app.
  - By the code, it changes only when the "LC Lease" row is created (`EnsureLeaseSeeded`, at install into an
    empty database) or by `ForceResetLease`. bc1-bc3 keep their databases in memory, so a restart, followed by the
    setup's republish, mints a new one.
  - **Not yet confirmed: the restart itself (1c).** It needs one owner-run restart of a bc server in a quiet window.
    Read the generation before; restart; re-run `bun scripts/bc-linux-setup.ts --server bcN`; read it after. The
    prediction is that the value changes. The probe's `gen` step does the reads.
- **Q2, publish history: NOT readable, so a publish inside the gap cannot be bracketed.**
  - The automation API's `extensions` rows have no time field at all (packageId, id, displayName, publisher, the
    version parts, isInstalled, publishedAs).
  - `extensionDeploymentStatus` answered HTTP 200 with NO rows before the publish, after a dev-endpoint publish
    of the throwaway app, and after its uninstall (`Microsoft.NAV.uninstall`, HTTP 204). Dev-scope publishes and
    uninstalls leave no record there.
  - The publish and uninstall did not change `serverGeneration`.
  - So R389's 0 → 1 → 0 case stays a stated limit: neither the history nor the generation sees it.
- **Left on bc1:** the probe app "R632 Probe" (publisher LethAL R632, ids 91500-91510, no dependents) is published
  and uninstalled. BC on Linux here has no unpublish path, so it stays until the next restart, which empties the
  database.

A resume guard on `serverGeneration` is now buildable for the restart case: [[R680]]. This item stays open for
the restart confirmation (1c).

**1c confirmed 2026-10-23 on bc2 (coord task R-632c, lethal-code). Closed.** Evidence in `/coord/handoff/R-632b/`.
- **Before:** after the owner's first bc2 restart that day and a clean `bc-linux-setup.ts --server bc2`, the
  generation read `2b8971cb88584ba486dcf6c453a2d76c` (two equal reads at 08:13:14Z and 08:13:19Z;
  `bc2-gen-baseline.txt`, which predicted a different value after the next restart).
- **Restart:** the owner restarted bc2 again. `bun scripts/bc-linux-setup.ts --server bc2 --lane code` then ran clean
  (no Continia; doctor ok on all four fixtures; `bc2-setup-after-restart2.log`).
- **After:** the probe's `gen` step, under a coord lease, read `fed2d48811de43878ee6c9bacf3f26a9` twice (15:21:43Z and
  15:21:48Z; `gen-after-restart2.log`). The value changed, as predicted.
- So a restart of these in-memory servers, followed by the setup, mints a new `serverGeneration`, and [[R680]]'s
  resume guard covers the restart case. A publish or uninstall inside the gap still changes nothing LethAL can read
  (Q2): that stays a stated limit, not open work.
