**Filed 2026-10-22 by lethal-bugs during R-601** (the R-601 plan review's I1 and its Q1 advice,
`/coord/handoff/R-601/review-plan-opus.md`; orchestrator ruling Q1).

**What.** Since [[R601]] a resume carries the verdicts of a crashed closed-world run when this
session's guard gives the same closed answer now and the run's recorded server key
(`runs.resource_key`) equals this session's. Two equal answers bracket the window only if nothing
on the server changed in between and came back. Two cases are not seen:

- **A server restart inside the gap.** The `bc1`-`bc3` servers keep their databases in memory, so a
  restart loses every app. A dependent of the test app could exist before the crash and be gone
  after the restart, and the resume's "0 dependents now" says nothing about "then". A restart is
  also a likely cause of the crash.
- **A dependent published and removed again inside the gap** (0 -> 1 -> 0). This is R389's stated
  limit, widened to the length of the crash gap.

The key also omits the tenant (`quarantineResourceKey` excludes it by design).

**To measure (a probe, not a fix).**
1. Is there a readable server start time or boot id (an OData or dev-endpoint read, or a
   LethAL Control field) that a session could record at its first guard ask and compare on resume?
2. Do dev-endpoint publishes and unpublishes appear in BC's install or operation history
   (`NAV App Installed App`, the extension deployment status), with a time a session could compare
   with the crashed run's window?

Either answer, if real, would let the resume refuse a gap it cannot bracket. Use `/al-probe` on a
leased `bc1`-`bc3` server.

**Evidence.** `resumableTestApp` (`packages/runner/src/closed-world.ts`), `quarantineResourceKey`
(`packages/runner/src/resource-key.ts`), the R601 stated limit in `docs/roadmap/R601.md`.

**Still open (2026-10-22, lethal-bugs during R-614).** The probe is designed only; no code and no server call yet
(design: `/coord/handoff/R-614/build-progress.md`, Part 2). The strongest candidate for question 1 is
`serverGeneration` in LethAL Control's `HarnessInfo`: it is seeded on a fresh lease row, which an in-memory
restart forces. But `HarnessInfo` is an OData ACTION, so reading it needs a POST, and the designed probe is
GET-only. It stays open until a probe that may make that one POST (or an owner-run restart) is pre-committed.
