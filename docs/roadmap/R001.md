~~Fenced-path writes fail~~ — **REFUTED 2026-07-26, twice over.** The entry first blamed a missing user permission (wrong: the OData user is SUPER), then Microsoft's Permissions Mock on the fenced path (also wrong). Measured by A/B on one property — two probe codeunits identical except `TestPermissions`, same app, same tables, same server, mock running in both: **omitted (→ Restrictive) = writes refused; `TestPermissions = Disabled` = writes succeed.** It is not the invocation path either — `continia test run` reaches `Test Runner - Mgt` 130454 with the mock started exactly as `RunMutant` does, and a restrictive codeunit is refused there too. The real rule: **a test codeunit that does not declare `TestPermissions = Disabled` cannot write, on any runner.** Real suites declare it (Continia Document Output: **76 of 76** test codeunits, and `InherentPermissions` on zero tables — this row said "77 of 77" until R13 recounted: the 77th object matching `Subtype = Test` is a `TestRunner`, which declares no `TestPermissions` at all). Our fixture did not, and the `InherentPermissions = RIMD` workaround was hiding that. Fixed in `769f667`: property declared, workaround removed from both tables, `itest:tables` passes per-mutant at the frozen 3/2/2 with the `OnInsert` mutant scoring. **Nothing blocks Tier-2 trigger operators.** Credit: the user challenged this from their own suite.
