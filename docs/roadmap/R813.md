## The owner's rulings (2026-11-05), which replace the recommendation below

- **Users:** a shipped gate manifest of gated numbered releases ([[R814]], option A, after `/coord/handoff/R-814/edge-fetch.md`
  showed an old edge binary cannot be fetched). Users run a sibling build of the commit we track.
- **A release only joins the manifest,** with its own gate run. It never touches `current`.
- **The licence question** in §3 is the owner's, and stays with the owner.
- Built by R-814. What was recommended below is kept as the record of the facts.

## The recommendation

**Do neither as the default.** Keep `current` on numbered releases, because that is what upstream tells users to install.
Gate edge every day as an early warning that never moves `current`. Add a mechanical pin, so a build whose readings
equal the committed pin moves with no person. Build from main only on demand, to bisect a regression. Before all of that,
restart the daily gate: it last ran on 2026-10-27, so alpha.8 to alpha.11 were never gated, and a tool that tracks nothing
gains nothing from a better choice of what to track.

## 1. How often it moved, and what each move cost

Window: 2026-10-22 to 11-05.

| Measure | Figure |
|---|---|
| Commits on upstream `main` | 3,596 |
| Numbered alphas published | 10 (alpha.4 to alpha.13) |
| Edge build runs | 14 (12 passed, 1 failed, 1 cancelled) |
| Distinct edge commits we gated | 8 |
| Pins in `V3_BUILD_PINS` | 9, of which 6 share one set of readings (`READINGS_8078BCF49`) |
| Commits touching the pin file | 16 |
| One full v3 gate on this machine | about 7 min (18:56 to 19:03 on R-796c) |

- **Edge moves less often now.** Since 2026-11-04 it is built nightly, and only from a commit whose nightly CI passed,
  including upstream's slow comparisons. Upstream's `main` runs ahead of that.
- **The cost of one move is mostly people.** An unpinned candidate fails by design: it is judged against the default
  tables, and each of the last six read C, N1E and X `held`, T `gate-fail`, and O1 `gate-fail` (`infra-fail` on alpha.12).
  Then someone reads the logs, a pin is committed and merged, `current` is re-gated, and the candidate is gated again.
  Spare estimated its alpha.7 switch at about 20 min of machine time, plus the pin's own review and CI.
- **5 of the 8 pins since alpha.5 changed no reading:** `edge-dcdf9e821`, `edge-db0296678`, `alpha.6`, `alpha.7` and `edge-2c63a382e`. Each
  differed only in its version line, the core number in `timeout-is-cpu`'s text, or O1's request count. The other three
  moved something real: `edge-a157b2d34` (N1E, #5798 fixed), `edge-8078bcf49` (eight defects gone) and `alpha.12` (O1's
  CDO set lists 18 package apps, and the run seed).

**Can an identical pin be mechanical? Yes, without weakening the pre-commitment rule.** The rule is that a prediction is
committed before the run. `current`'s pin already is one: "this build reads the same". So:
- Judge a candidate against `current`'s committed pin, not the default tables.
- Mask only a fixed, tested list of fields that may differ: the version line, the core number in `timeout-is-cpu`, and O1's
  request count. Every other field stays compared. A new mask is a code change, so it gets a review.
- On a pass, record `readingsFrom: <pin id>` in `.gated`, with the receipt and `gate.log` beside it (R805).

**What still needs a person:** any `held` row, any moved verdict, killing test or count, a new refusal or warning code, a
new contract fact, any `infra-fail`, and K failing. All of those take today's path. Replayed over those 8 pins, this
stops at exactly the three that moved something, which is the right answer. That replay is by reading the pin comments,
not by a run.

## 2. Which al-runner do LethAL's users get?

**Today, none: the supported path refuses a user's binary.** This is by reading the code, not a run.
- LethAL has no published release: the README says "build it yourself", and `v0.1.0-alpha.3` is still a draft. Its
  Installation section does not mention al-runner, and nothing bundles it.
- `alRunnerV3.path` defaults to `/work/tools/al-runner-v3/current/al-runner`, which exists only in this container.
- `checkGated` refuses any binary with no `.gated` beside it (`al-runner-v3-ungated-build`), and `lethal doctor` reports the
  same.
- Only `al-runner-v3-update.ts` writes `.gated`. It hard-codes `/work/tools`, `/coord` and `/work/lethal-wt`, and its gate
  needs the private CDO checkout. So a user cannot produce one, short of writing the file by hand.
- v3 refuses on Windows, and upstream's Windows zip takes a real share of downloads (alpha.7: 11 Windows, 14 Linux x64).

**What they would install.** Upstream's README sends users to the newest numbered alpha (`mise use`, `mise up`); edge is
opt-in. mise lists only numbered releases. Download counts cannot settle it: edge's assets are replaced nightly, so
they read 0, and our own gate downloads are in the alpha counts.

**Edge and a release are never the same binary**, even at one commit: alpha.6 and `edge-db0296678`, and alpha.7 and
`edge-2c63a382e`, each have the same commit and readings but two sha256s, because the version line is compiled in. Pins match on version
AND sha256. So if `current` is edge and LethAL ships, what was gated is not what a user runs, and the user's build has
no pin. That is the strongest reason not to make edge the default.

## 3. Building from main

- **Toolchain.** Edition 2024, `rust-version` 1.85. Upstream's package build pins Rust 1.98.1. This machine has 1.99.1.
- **Targets.** Upstream ships `x86_64-unknown-linux-musl`, which needs the musl target and `musl-gcc` (for mimalloc). This
  machine has only the gnu target and no `musl-gcc`.
- **The build.** `cargo build --release --locked -p alrunner-cli --target <t>`, with `CARGO_PROFILE_RELEASE_LTO=thin` and
  `CARGO_PROFILE_RELEASE_STRIP=symbols`.
- **Wall time.** Not measured here. Upstream's own x86_64 musl build step took 3 min 4 s on a GitHub runner, with its cargo
  cache. A cold build will take longer.
- **The version line.** Crate version, plus `ALRUNNER_VERSION_SUFFIX`, plus `ALRUNNER_COMMIT`. A local build prints the same
  shape as a numbered release, so only the sha256 tells them apart. `findV3Pin` needs both, so a local build cannot pass as a
  release.
- **Beyond `cargo build`.** Smoke tests, the archive, `SHA256SUMS` and a build provenance attestation, plus signing on
  Windows. A local build has none of these.
- **Reproducible enough to pin by sha?** Not measured, and unnecessary: a pin would name the sha of the binary we built.
- **Licence.** Business Source License 1.1 (not open source), changing to Apache 2.0 four years after each version.
  Building, modifying and commercial use on your own machines are allowed. Offering it, modified or not, to third parties
  for a fee, or as a substantial part of a paid or bundled product, is not. LethAL is MIT, so bundling al-runner needs
  care before any paid offering. This is a reading, not legal advice: the owner should decide.

**The trial build was not run.** The session's permission check denied it, because it runs code downloaded from outside the
repo (`[Code from External]`). I did not work around that, and the task made it optional ("if it is cheap"). If the owner
wants the wall-time and reproducibility figures, the script is `/coord/handoff/R-811/r811-build.sh`: it needs that
permission from the owner, and it builds alpha.12's commit twice, in a scratch folder with its own cargo home.

## 4. What building from main gives, and what it costs

**Gives:** a chosen commit, a fix the same day it merges, and bisecting a regression across upstream's commits.

**Costs:**
- `main` has not passed upstream's nightly comparisons, which is why upstream moved edge to nightly on 2026-11-04.
- Each build is a new sha, so a new pin. The mechanical pin makes that cheap, but it is still a gate run.
- No user can get that binary, so it widens the gap in section 2 further than edge does.
- We take on a toolchain, a musl setup and the provenance upstream already provides.

So its value is real but occasional: bisecting. That needs a build on demand, not a policy.

## 5. The smallest change to `scripts/al-runner-v3-update.ts`

Not built; this is the shape to size it.
1. `gateOne` passes `LETHAL_V3_PIN_FROM=<current's pin id>` to a candidate's gate. The itest's pin lookup uses that pin's
   readings, with the fixed masks, when `findV3Pin` finds no exact pin.
2. On a pass, `.gated` records `readingsFrom`, and the session's pin lookup follows it. Without this, a session on that
   build would read as unpinned.
3. `edgeLocked` passes a new option so a pass records the build but never moves `current`. Today `--edge` moves it.
4. Something must run the update daily again. The last log is 2026-10-27. lethal-spare ran it, and that session is gone
   from `.kraken/project.yaml`. This is a schedule, not a code change.

The user path in section 2 is a separate item, needed before any LethAL release that offers v3.

**The choice for the owner:**
- (a) This recommendation.
- (b) `current` follows edge, accepting that users run something else. Then only step 1 and 2 and the schedule are needed.
- (c) Build from main. Then the trial build must be allowed first.
