**Measured.** A run scoped to four files published two batches: batch 0 (25 guards, one table) and
batch 1 (633 guards, one codeunit). Batch 0 was fully scored on the first pass. The run then needed
`--resume` twelve times in two hours (hangs and socket drops, see [[R194]] and [[R196]]), and every
resume did the same thing, read from `events.ndjson`:

| step | elapsed |
| --- | ---: |
| deploy batch 0 (25 guards) | 38 to 45 s |
| baseline batch 0, 407 tests | 205 to 242 s |
| mutants batch 0 | 1 ms, 25 carried, nothing to run |
| deploy batch 1 (633 guards) | 42 to 46 s |
| baseline batch 1, 407 tests | 197 to 223 s |

About 8.5 minutes per resume before the first uncarried mutant, roughly half of it on a batch that
had no work left. Twelve resumes is about 1.7 hours of a 4-hour session.

**Why it is this way, and what is legitimately owed.** Each batch is a fresh artifact with a random
id, and the baseline against it does two jobs: it proves the instrumented build with every guard off
behaves like the original (green tests), and it collects the coverage index the fenced path
attributes mutants with. Neither result is persisted across runs, and `resume-reusing-run` says so:
*"Deploy and baseline still run; coverage attribution and covering-test lists come from THIS run."*

**Two fixes, in order of safety.**

1. **Skip a batch with no remaining work.** If every mutant of a batch is carried by the resume
   (and none is a colliding key, see [[R193]]), do not deploy it and do not baseline it. Nothing
   about a carried verdict depends on the batch being republished. This halves the cost above and
   changes no verdict.
2. **Reuse the coverage index for an unchanged batch.** The instrumented source of a batch is a
   function of the mutant set, and the baseline's coverage is a function of that source plus the
   published test app. Persist the index in the store keyed by the batch's content hash and the
   published test app's package hash, and on `--resume` reuse it when both match, running the
   green check only. This is the bigger saving and needs a pre-commitment: the risk is a stale
   index attributing mutants against tests that changed, which is R56's shape.

**Evidence.** The session's `events.attempt*.ndjson` and `run.attempt*.log` (scratchpad, not
committed); the `resume-reusing-run` warning text in `orchestrator.ts`.

## OUTCOME, half 1, 2026-09-02

**Landed.** Before deploy, `batchCarriesEntirely` asks whether every mutant of the batch is either
a stranded skip or a carried verdict that has its coverage facts; if so `replayCarriedBatch`
records them all from the prior run, emits `resume-batch-carried` naming the run and the counts,
emits the batch's `coverage-split` rebuilt from the persisted rows (so `untargetedTriggerCount` and
R175's `unplaceableCount` stay consistent with the verdicts beside them), and the loop moves on.

**What makes it possible.** `ResultsStore` persists `covering_tests` (JSON), `coverage_attribution`
and `unplaceable` per mutant row, written by every `record()` call (`[]` is explicit: no test ran
this; NULL is a pre-R192 row: unknown). `CarriedVerdict` carries them. A batch with one carried row
from before the columns existed takes the old path, so an upgraded database never skips on
invented facts.

**Proof.** `resume.test.ts`: the two-batch scenario now asserts ONE deploy on resume (batch 1's),
no `batch-published` for batch 0, one `resume-batch-carried` warning, and every batch-0 mutant
carried with the same verdict, covering list and attribution it had; red with the skip disabled
(deploys 2, expected 1). A migration test builds the pre-R192 table by hand, opens it, reads the
old row back without facts, and inserts a new row with them. Full suite 2644 pass; bcdev gate
3/12/4 unchanged, both determinism passes identical.

**What it saves.** On the measured run, the 40 s deploy and 215 s baseline of batch 0 on each of
twelve resumes: about 51 minutes of a 4-hour session. Batch 1 still costs its deploy and baseline
on every resume until half 2.

## OUTCOME, half 2, 2026-09-02

**Landed.** Every completed baseline is stored (`baseline_snapshots`: run, batch, the two hashes,
and the observations verbatim, coverage included). On `--resume`, after a batch is deployed, the
orchestrator hashes the artifact's `.al` tree (control files excluded, since the selector embeds
the random artifact id) and the test app (published package bytes on bcdev; the test source tree
where the backend has no package concept; `undefined`, never reuse, when a package read fails),
and if a snapshot matches both, its observations stand in for the baseline: the same
`baseline-batch-finished`, the same coverage split, the same durations for budgets, and a
`resume-baseline-reused` warning naming the run and the batch. A baseline that stopped short (a
lease or in-flight `break`) is never recorded, so a partial one cannot be reused as a whole one.

**Proof.** `resume.test.ts`: first run aborts on batch 1's first mutant, having completed batch 1's
baseline; the resume deploys batch 1 and runs ZERO baseline tests, and every verdict except the
R53 stranded skip equals a fresh run's; red with the reuse decision disabled (one baseline test
ran). A second test edits the test project and shows the baseline re-run with no reuse warning.
`baseline-snapshot.test.ts` pins the hash properties (control files and non-`.al` invisible, a
one-byte change visible, a failed package read is not a fall-back). Full suite green; bcdev gate
3/12/4 unchanged.

**What this does not re-check, stated on the caveat itself** (`CAVEAT_INTERPRETATIONS.resumed`):
the environment's data. A test green at the stored baseline that would be red now is not
re-detected. That exposure exists inside every run between its baseline and its last mutant; a
resume within one lineage does not add a new kind of it.

**Saving.** On the measured run, batch 1's 215 s baseline on each of twelve resumes: with half 1's
batch-0 saving, a resume there now costs one 45 s deploy instead of 8.5 minutes.

## MEASURED, 2026-09-03: both halves live on the hosted path

Run 2 of the Templates slice resumed eleven times (one hang per resume, [[R201]]). On every
resume half 1 fired (`resume-batch-carried`: batch 0 recorded from the store, no deploy, no
baseline) and half 2 fired (`resume-baseline-reused`: batch 1's 407-test baseline "done in
0.7s" against 211 to 237 s when actually run). Baseline time over the whole run was 669 s for
three real baselines, against 1,620 s for the seven the morning run paid; deploy stayed at ~40 s
per resume because batch 1 had work left. Eleven resumes at ~230 s each is 42 minutes this run
did not spend.
