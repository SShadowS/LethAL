**Found by** coord PR-437 (lethal-preproc, 2026-11-25), while finding why the laned-baseline tests ran 2-4 s per fill instead
of ~60 ms. It is not in PR-437's code.
- **Where:** `refuseDaemonDependencySkip` (R590, `al-runner-v3-backend.ts`) yields one event-loop turn with
  `await new Promise((r) => setImmediate(r))` after every serve answer, on the one-worker path too.
- **What was measured (PR-437's test rig, in-process fakes with no real I/O):**
  - The wait took 734-794 ms each time. One fill paused about 0.9 s several times, and nothing was pending but that
    `setImmediate`.
  - With a no-op 5 ms interval running, the same fill took 57-69 ms (3 runs), against 1.9-4.0 s without it (3 runs).
  - So in a quiet loop, a pending `setImmediate` waited for the next timer: a 2 s worker idle timer, or a close's 500 ms
    or 1 s wait. With no timer due at all it could wait for good, which likely explains one test run killed at 280 s.
- **Not shown:** that a real run stalls. Real daemons keep producing pipe I/O, which wakes the loop. But the wait's cost
  then depends on unrelated scheduling, and every serve answer pays it.
- **Levers (not chosen here):**
  - yield with `await Promise.resolve()` or a zero-delay `setTimeout`, whose wake-up does not depend on other timers;
  - or read stderr after the pump's own flush;
  - or measure first: per-request time on a real serve run, with and without.
- **PR-437's handling:** its test rig keeps the loop awake while a fill runs (`awake` in
  `pr437-baseline-spread.test.ts`). That decides no order.
- **Related:** R590, R885, PR-437.

**Done by PR-448 (lethal-preproc, 2026-11-25).** Evidence: `/coord/handoff/PR-448/` (`measure.md`, `m1/`,
`redchecks.md`).
- **Why R590 yields:** the stderr pump is its own async loop. One event-loop turn lets pipe data that has ALREADY ARRIVED
  be read before the check. A microtask is not enough, because it runs before any I/O is read.
- **Measured:**
  - **A real serve run** (scoped DO on edge-e5176a9fd, 2 workers): 315 yields, sum 18.7 ms, max 8.2 ms. The stall does
    not occur there, because live pipes keep the loop polling.
  - **PR-437's pure-promise rig:** up to 895 ms per yield with the CPU idle (1.3 ms of CPU).
  - **Not reproduced in isolation:** no stall in eight isolated shapes (timers, a pending pipe or stream read, Workers,
    nested immediates, under `bun test`).
- **The fix:**
  - `yieldTurn()` ends on `setImmediate` OR a 0 ms timer, whichever fires first, and clears the other.
  - On a real run `setImmediate` wins at ~0 ms, so nothing changes.
  - On a quiet loop the timer bounds the wait at ~1 ms, whatever other timers are scheduled.
- **Red tests both ways** (`pr448-yield-turn.test.ts`, and the R1224 test in `al-runner-v3-entries.test.ts`):
  - a skip line arriving one turn after the answer still stops the session (red with no turn);
  - a starved `setImmediate` no longer stalls the yield (red with today's setImmediate-only yield);
  - a starved timer does not either;
  - the losing primitive is cleared.
- **Not changed:** PR-437's parked rig keeps its `awake` helper (that branch is not landed). The bound-print pool's own
  `setImmediate` (`baseline-snapshot.ts`, the R653 P7 fix) settles a worker answer, not a wait, and is left as it is.
