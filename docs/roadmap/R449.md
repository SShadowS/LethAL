**Found by lethal-preproc, 2026-10-05,** reading branch CI for R-294 (branch `lethal/r294`). R448 lists none of these tests.

**What happened.** On two Windows `check` runs, a different SQLite-heavy test timed out each time, and nothing else failed. Each passed on the other runs of the same branch, and the Linux `unit-linux` job passed every time:

| Run (commit) | Test | Time |
|---|---|---|
| 37239963279 (435c7d55) | `scripts/store-query.test.ts`: "latest run is the highest FINISHED id; a newer unfinished one is reported, not chosen" | 8290 ms |
| 37243906848 (02ac898e) | `packages/runner/tests/cli-envtool.test.ts`: "an environment deleted at teardown takes its stored bundles with it (R360 I-1) > two runs that each created and deleted their own environment leave no bundle" | 7431 ms |
| 37243906848 (02ac898e) | `packages/runner/tests/store.test.ts`: "ResultsStore > migrates a pre-5A runs table that lacks the provenance columns" | 6757 ms |

The runs between and after them were green on both jobs: 37241383676 on 462cfdbf, and 37243966820 on 26e6fff2. The code changes between these commits do not touch any of the three tests. So these are timing failures, not failures caused by the code.

**Why it matters.** It is the same family as R226, R335, R428 and R439: unit tests with no headroom against bun's 5 s default, which turn a CI run red at random. Here it happens on Windows only, where the kraken container cannot reproduce or time it. All three tests open real `bun:sqlite` stores, which suggests that Windows file I/O on the CI runner is the slow part.

**What would close it.** For each test, find what it spends its time on (store creation, migrations, a spawned process). Remove that cost, or give the test a file-local timeout with the measured reason, as R439 did. Measuring it needs Windows timings, for example the CI log's per-test times over several runs. Unmeasured so far.

**Closed 2026-10-05 (lethal-preproc).** The cause was the disk the tests wrote to, not the tests, and not a lock. Measured from the CI logs:

- **Not a lock wait.** Each of the three tests holds one connection at a time (the store-query test is the first in its file, and its store is closed before the read-only handle opens), so no `busy_timeout` wait was possible. The stalls were not 5 s-shaped either: 8290, 7431 and 6757 ms, and in the same windows the neighbouring store tests ran 3 to 15 times slower (538 to 964 ms for store-query's other tests, 1518 ms and 2790 ms for the tests after the other two).
- **The same stall hit tests with no SQLite file at all.** In master run 37245027545 three tests of `orchestrator.test.ts`'s "runSession — Task 7: only a typed AlcCompileError may be bisected" ("never bisects a publish-style failure", "a worker's ArtifactPrepareError aborts the whole session", "a non-compiler failure mid-bisection aborts the search"), which normally take 15 to 30 ms with an in-memory store and a few small temp writes, timed out back to back at 5000 ms, and the next test took 2204 ms: one stall of about 17 s on async file I/O. Git-spawning tests in the slow windows were up to 3 times slower too (5366 ms against a usual 1848 ms).
- **Every one of them wrote to the temp folder, which on GitHub's Windows runner is on C:, the OS disk. The checkout is on D:, the runner's local disk.**

Two fixes:

1. `ci.yml`'s Windows "Unit tests" step sets `TEMP` and `TMP` to `runner.temp`, which is on D:. The test preload takes its temp root from there (the logs now show `D:\a\_temp\lethal-unit-run-...`). This is the one that removed the stalls: the three store tests went from 100 to 500 ms to 7 to 34 ms, and the three orchestrator tests from 15 to 240 ms to 9 to 26 ms.
2. `ResultsStore`'s constructor sets `PRAGMA synchronous = NORMAL` after switching to WAL. Under SQLite's default (FULL) every commit fsynced the WAL, and opening a new store alone is about 16 commits. An fsync waits for the disk, so it is where a slow disk hurts most. Measured on Linux ext4, a new store plus one run: median 238 ms under FULL, 54 ms under NORMAL. NORMAL is SQLite's recommended setting for WAL: a crashed or killed process loses nothing, and an OS crash or power cut can lose the last commits but cannot corrupt the file. A lost verdict row is a mutant that resume runs again. Pinned by the store test "R449: a file store commits without an fsync per commit (WAL, synchronous NORMAL)", red-checked: with the pragma removed it fails on `synchronous` (received 2, expected 1).

No timeout was raised, nothing is skipped on win32, and `STORE_BUSY_TIMEOUT_MS` is unchanged. Evidence: five consecutive green runs of both jobs on `f224fa0d` (which includes master 91000496): run 37249045895, attempts 1 to 5. Windows times per attempt (store-query / cli-envtool / store pre-5A; orchestrator publish-style / ArtifactPrepareError / mid-bisection), in ms: 16, 34, 13; 11, 21, 14 — 15, 28, 12; 14, 26, 13 — 10, 20, 7; 18, 15, 11 — 15, 27, 12; 11, 19, 15 — 14, 25, 10; 9, 17, 12.
