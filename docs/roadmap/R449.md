**Found by lethal-preproc, 2026-10-05,** reading branch CI for R-294 (branch `lethal/r294`). R448 lists none of these tests.

**What happened.** On two Windows `check` runs, a different SQLite-heavy test timed out each time, and nothing else failed. Each passed on the other runs of the same branch, and the Linux `unit-linux` job passed every time:

| Run (commit) | Test | Time |
|---|---|---|
| 37239963279 (435c7d55) | `scripts/store-query.test.ts`: "latest run is the highest FINISHED id; a newer unfinished one is reported, not chosen" | 8290 ms |
| 37243906848 (02ac898e) | `packages/runner/tests/cli-envtool.test.ts`: "an environment deleted at teardown takes its stored bundles with it (R360 I-1) > two runs that each created and deleted their own environment leave no bundle" | 7431 ms |
| 37243906848 (02ac898e) | `packages/runner/tests/store.test.ts`: "ResultsStore > migrates a pre-5A runs table that lacks the provenance columns" | 6757 ms |

The runs between and after them were green on both jobs: 37241383676 on 462cfdbf, and 37243966820 on 26e6fff2. The code changes between these commits do not touch any of the three tests. So these are timing failures, not failures caused by the code.

**Why it matters.** It is the same family as R226, R335, R428 and R439: unit tests with no headroom against bun's 5 s default, which turn a CI run red at random. Here it happens on Windows only, where the kraken container cannot reproduce or time it. All three tests open real `bun:sqlite` stores, which suggests that Windows file I/O on the CI runner is the slow part.

**What would close it.** For each test, find what it spends its time on (store creation, migrations, a spawned process). Remove that cost, or give the test a file-local timeout with the measured reason, as R439 did. Measuring it needs Windows timings, for example the CI log's per-test times over several runs. Unmeasured so far.
