**Filed 2026-11-23 by lethal-bugs (coord task PR-376), from PR-375's note.** PR-375's zip-blob family was refused in every cell as
`dotnet-unavailable` until its run passed `--bc-version 28.4.53241.56646` with `--dotnet-sidecar` and `--dotnet-assembly-dir`. The
question was whether DO's own runs lose cells the same way. Read-only, from c3's and c3off's stores (PR-357), LethAL's code and a
live serve process's arguments; no config file was read.

**1. How many of c3's runs are dotnet-unavailable: none.**
- `test_results` rows whose message says `dotnet-unavailable`: **0** in c3 and 0 in c3off. Mutants with it in a note or a killing
  failure: 0.
- Rows that name DotNet at all: **351** in each run, all of them the helper's own answers:
  - Newtonsoft `JsonTextWriter` exceptions under a mutant: 311 (`CDO Mail Msg Builder Tests`);
  - ZipArchive exceptions and the PR-375 `ZipArchive.Dispose` refusal: about 25 (`CDO Open Documents Tests`, `CDO Doc Attachment
    Event Tests`, `CDO PDF Merge Tests`);
  - and their cascades.
- A .NET exception text needs the helper to have loaded the type and run it, so **the helper ran**.

**2. What LethAL passes on DO's path.**
- `--bc-version`: the config's four-part `bcVersion` (`al-runner-v3-backend.ts`, the argument builder; doc "v3 `--bc-version`
  (four numbers)"). A live serve process showed `--bc-version 28.4.53241.56646`.
- `--dotnet-sidecar`: by default the pinned build's own sidecar, when its `.gated` names one with an unchanged sha256 (R886,
  `alRunnerV3.dotnetSidecar`). The live process showed `/work/tools/al-runner-v3/main-bf3a3e863/dotnet-sidecar/AlDotNetSidecar.dll`.
- `--dotnet-assembly-dir`: one per `assemblyProbingPaths` folder (R941/R943). The live process showed
  `/coord/cache/bc28-service-windows`, the cached BC 28 service tier (388 entries).
- So DO's path gets exactly the three things zip-blob needed.

**3. Whether BC 29 is a build the helper supports here.** al-runner models the config's 28.4 build; bc4's BC 29 is only the oracle
for the refusal-family differentials. **No BC 29 service tier is cached** (`/coord/cache/` holds `bc28-service` and
`bc28-service-windows` only). A run that named a 29 build would need one before the helper could load its types, but no DO run names
29 today.

**Why PR-375 failed:** `scripts/refusal-family.ts` calls al-runner with a fixed `--bc-version 28` and no helper flags. `28` resolves
to build 28.4.53241.53758, whose service-tier runtime al-runner then tries to download (and cannot, offline). Families whose .NET
types need no service tier were never affected: no stored family run (PR-32, PR-93, ...) contains `dotnet-unavailable`. zip-blob
now passes its own flags (`ZIP_BLOB.args`, a `ponytail:` comment records the box paths).

**Lever: none for LethAL's product path.** The only ceiling is the script's: a future family whose .NET types need the service
tier must pass the same three flags in its `args`, as zip-blob does.
