**Filed 2026-10-05 by the orchestrator, owner-approved, as the follow-up to R-196** (plan
`docs/superpowers/plans/2026-10-05-R-196-refuse-hang-capable-sites.md`; refusal in `hangCapableForMutatedNode`,
`packages/builtin-tier1/src/loop-hazard.ts`).

**What breaks, for whom.** R-196 stops value operators from mutating a write to a variable that the
enclosing loop's own condition reads, because such a mutant can hang the server. That is right. But
the refusal leaves no trace: no mutant, no `excludedSites` row, no count. A reader judging how well
tested the code is (a person, `lethal explain`, an agent deciding where to write tests) sees a score
that looks complete while every loop step in the project went unmeasured. Measured in R-196's census:
about 0.3% of mutants (1,463 in BaseApp, 136 in CDO), all on loop steps, so the gap is concentrated
exactly where a reader would assume loop logic is covered. Same wrong-confidence class as R399.

**To close.** Record the refused sites in the existing `excludedSites` mechanism
(`packages/runner/src/excluded-sites.ts`) under one new reason, for example `hang-capable`, with a
per-file site count, and let a non-zero count narrow the report's reliability the way R399's rows
do. Not per-site detail: nothing can be killed there. This touches the report format, so follow the
`SessionReport` ripple list in `CLAUDE.md` and say whether the report schema version moves. Pin both
directions, red-checked: a refused site appears with its reason and count, and a run with no refused
site adds no row and does not narrow reliability. Blocked on R-196 landing (same operator code).

**Closed 2026-10-04 by R-447 (`bb4a0c46`).** Plan: `docs/superpowers/plans/2026-10-05-R-447-hang-refused-excluded-row.md`.
- **The row.** New `excludedSites` reason `hang-refused`, one row per file with a `sites` count (one
  site = one operator refusing one node), no per-site detail. A row with sites > 0 narrows
  `reliability` (R399's rule) and adds a `scoreDescribes` clause and a console line. The count comes
  from the operators' own decision: each of the four splits its claim check into "every check except
  the hang check" plus the hang check, and an optional `refusesHangCapable` uses the same split, so
  the count cannot include a site the operator would never have claimed. Plug-in operators without
  that method are not counted. Inactive `#if` arms, `--operator` and `--lines` are honoured.
- **Explain.** `unobservedBlock` is withheld for gaps in a file with a `hang-refused` row, since the
  loop's own step was never measured there.
- **Schema.** `report-v3` gains one reason value in place (v3 stays); `stream-v1` gains one optional
  event property. No IDENTITY_SCHEME or explain version change; no sample report regenerated.
- **Effect on real projects:** `full` reliability becomes rare (BaseApp 1,463 refused sites, CDO Cloud
  136), which the owner approved.
- **Live:** `itest:hang` on Cronus28, branch HEAD `e2e8fb62`, 2026-10-04, PASS exactly as
  pre-committed in `docs/superpowers/specs/2026-10-05-r447-hang-row-precommitment.md`: both legs carry
  `{src/HangLogic.Codeunit.al, hang-refused, sites 2}` and read `narrowed`; per-mutant figures
  unchanged (ON 24 / 5 / 9, OFF 1 / 0 / 2 with 1 error). Every other fixture and example gets no row.
- **Not counted, by scope:** loop-condition literal refusals (for example shift-integer's
  `until X.Next() = 0`) stay silent.
