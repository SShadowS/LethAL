**Filed 2026-10-22 by lethal-preproc** during the R-654 inventory (`/coord/handoff/R-654/inventory.md`), and
confirmed by reading the code. Related: [[R553]], [[R654]], [[R586]].

**What.** `report.ts` picks the screen's message rule from the backend kind:
`screenBackend = caps.kind === "al-runner" ? "al-runner" : "bcdev"`. An `al-runner-v3` run therefore takes
bcdev's rule. `screenMessageOf` strips no leading `<Type>: ` prefix, and the `vacuous` note's al-runner check is
skipped.

**Why it matters.** R553 measured that v2 writes every failure as `{Type.Name}: {Message}`. Read unstripped, that
form made the screen flag 51 of 51 kills as `vacuous`, where bcdev flagged 3. Nobody has measured v3's (Rust)
failure-message shape. If v3 also prefixes its messages, its assertion-screen figures are skewed the same way.
These are report figures only: verdicts are not touched.

**To close.**
- Measure v3's `killingTestFailure` text on the sandbox fixture (a plain `Error()`, an `Assert` failure, a
  runtime error).
- Then either give v3 its own `screenMessageOf` branch or record that bcdev's rule fits it.
- A test per backend kind.
- Fold this into [[R654]] if that change touches the screen.

**Closed 2026-10-22: bcdev's rule fits v3 (option (a), comments and tests only).** Measured in
`/coord/handoff/R-657/measure.md` with an invented probe app, on al-runner v3 alpha.2 (91253f2d6) and edge
(57f1e4f98), each one-shot and serve:
- The seven failure shapes (plain `Error()`, `Assert.AreEqual`, `Assert.IsTrue`, `TestField`, an
  `Assert.ExpectedError` mismatch, `asserterror` with no error, divide by zero) are byte-identical across both
  builds and all modes. None carries a `<Type>: ` prefix; the stack is a separate field, never in the message.
- Across 47 stored v3 reports, 0 kills carry a prefix.
- On the CDO `CDO Recipient Mgt.` slice, v3's message equals bcdev's message half on 51 of 51 kills, and the
  screen flags the same 3 (M0044, M0045, M0051).
- No upstream issue was needed: no v3 message differs from BC's.

The code already routes `al-runner-v3` to bcdev's rule. Comments at `screenBackend` (`buildReport`) and
`screenMessageOf` now say this is on purpose. Tests in `assertion-screen.test.ts`: "R657: v3's measured message
shapes, read with bcdev's rule" (same flagged set and `partial` under v3 and bcdev), and the R586 test retagged
R586/R657 (v3 is not stripped and gets no al-runner `vacuous` note). The R553 tests remain the v2 and bcdev pins.
No kill's screening changed.

**RESIDUAL: the TestField, divide-by-zero and `asserterror`-with-no-error texts were not compared against a live
BC** (no lease was used). `Error()`, the `Assert.*` family and duplicate-key errors are covered by the CDO
comparison against bc3. A future v3 build that adds a `<Type>: ` prefix would not be caught by these unit tests,
because they use fixed strings: [[R667]].
