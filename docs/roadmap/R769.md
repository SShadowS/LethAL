**Filed 2026-10-25 by lethal-spare (coord task R-769, owner speed work).** Question: v3 compiles every batch and the
test app with alc first (about 19 s on D1), because al-runner ran code that does not compile (#5602). The pinned build
reports #5602 fixed. Can the proof be skipped on such builds?

**Answer: no.** Measured on `al-runner 3.0.0-alpha.5+edge.20261024 (dcdf9e821)`, the pinned `current`, with invented
AL only. There were 31 shapes (two of them isolating checks, u11 and u11b), each one edit on scratch copies of `scripts/r586-probe/probe-app` and `probe-tests`.
Each shape was run three ways: alc as the control, v3 one-shot with `v3CallArgv`'s argv, and a fresh `serve` daemon
(plain `runTests` and LethAL's `entries` shape). One-shot and serve agree on every shape. Raw evidence:
`/coord/handoff/R-769/out/report.md`; the driver is `/coord/handoff/R-769/shapes.ts`.

| what v3 does with AL alc rejects | shapes |
|---|---|
| refuses: exit 3, `compilationErrors` | AL0118 (unknown proc, undefined var: leg X (b)'s shape), AL0132 unknown field, AL0440 duplicate procedure, AL0161 tests call a now-local proc, AL0118 in a test codeunit the call does not select, AL0122 Text to Integer (called, uncalled, in a branch never taken, in the second object of a two-object file) |
| panics, no rows | a duplicate object id (one-shot exit 2; serve `{"error":"the run panicked"}`) |
| the affected tests come back NotRun, the rest RUN | syntax errors (target and selected test codeunit), AL0135 wrong argument count (called), AL0118 missing object (called), AL0135 in a compiled-in `#if` arm (called), a test calling a procedure the target lacks |
| RUNS, tests pass | AL0135 in an uncalled routine; AL0118 `Codeunit::"No Such Codeunit"` (uncalled); AL0122 an Integer returned from a procedure declared `: Text` (uncalled); AL0139 `exit(5)` in a procedure with no return type, **also on the path the test calls** |

`#if` arms are not a separate gap. The first run listed "AL0122 in a compiled-in `#if` arm" as a RUNS shape (s11).
Two isolating shapes showed the cause is the return type instead:
- `1 + 'x'` outside any `#if` compiles under alc (u11);
- s11's arm sat in a `: Text` procedure, and returning an Integer from one is what alc rejects;
- an error in a compiled-in arm on a called path behaves like plain code (t11).

**Why the proof stays.**
1. A mutant whose AL alc rejects (so BC would never compile it) can still run on v3 and fail a test. That would read
   as a kill. AL0139 on a called path is a concrete mechanism.
2. Even a build that refused every shape would not be enough on its own. Bisection reads only `AlcCompileError`, so
   without alc a non-compiling mutant stays in the batch. v3 then refuses the whole batch or partly runs it, and the
   R461/bisection path loses its signal.

**Probe notes.**
- `'x'` is a Char literal and converts to Integer, so the first type-error shapes compiled under alc. They are kept in
  the report as invalid shapes and redone with `'xy'`.
- The probe's `ProbePermissions.Codeunit.al` (`TestPermissions = Restricted`) is not valid AL on BC 28 (alc AL0169),
  so it is left out of every copy.
