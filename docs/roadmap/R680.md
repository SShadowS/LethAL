**Filed 2026-10-23 by lethal-code**, from R632's probe (coord task R-632b, `/coord/handoff/R-632b/`). Related:
[[R632]], [[R601]], [[R389]].

**What.** Since R601, a resume carries a crashed closed-world run's verdicts when the guard gives the same closed
answer now and the server key matches. It cannot see a server restart inside the crash gap, and on bc1-bc3 a
restart loses every app. R632 measured a usable marker: `serverGeneration` from LethAL Control's `HarnessInfo`.
- It stayed constant across reads, a lease release and re-take, and a publish and an uninstall.
- By the code, it is re-minted only when the lease row is created (an install into an empty database, as after a
  restart of these in-memory servers) or by `ForceResetLease`.

**To close.**
- Record `serverGeneration` in the run row at the session's first guard ask. `HarnessVerifier.verify()` already
  returns it.
- On resume, refuse by name when the current value differs, or when the stored run has none. Never carry the
  verdicts.
- Add a red test in each direction.
- Wait for R632's restart confirmation (1c) before relying on it for the restart case. A `ForceResetLease` also
  changes the value, which is the safe direction: an extra refusal.
- It does NOT cover a dependent published and removed inside the gap (0 → 1 → 0). R632 measured that dev-endpoint
  publishes leave no readable history, so that stays R389's stated limit.

## Built 2026-10-23 (R-680, lethal-bugs)

Plan `docs/superpowers/plans/2026-10-23-r680-resume-server-generation.md` r2 (the plan review's fixes applied).

**The change** (`orchestrator.ts`, `store.ts`, `test-membership.ts`):
- **The read.** A bcdev session (one with a lease config) reads `serverGeneration` ONCE, before `testAppIdentity`,
  where the closed-world guard is first asked. It records the value on the run row (`runs.server_generation`). An
  empty answer refuses.
- **The resume rule.** `--resume` and `--resume-run` refuse with `ServerGenerationChangedError` (code
  `server-generation-changed`, naming both values) when the run recorded another generation, or none.
  - A run recorded before R680 has none: no back-compat.
  - The check runs first, for an env-tool session too, so nothing is carried and no run row is written.
  - A session with no lease (al-runner-v3) has no server; the rule does not apply.
- **The lease** is asked at the recorded generation, never at a second read. The server grants only at the
  generation it holds, so a restart after the read is refused `generation-changed` before any deploy, for a fresh
  session as for a resume.
- **The R192 baseline snapshot** (the plan review's Important 1) is reused only from a run on the same generation.
  Before, a baseline recorded before a restart could be lent to a resumed run after it, and a test red on the
  restarted data would score a false kill.

**Tests** (`orchestrator.test.ts`, the R680 describe, on `envRun`; `store.test.ts`):
- refusals, asserted as `ServerGenerationChangedError`: `--resume-run` and bare `--resume` across a changed
  generation, and a run with none recorded;
- the control: the same generation resumes and carries;
- the lease is asked at the one read, and the row records it;
- a restart between the read and the lease stops a fresh and a resumed session before any deploy;
- the snapshot is not reused across generations, and is reused (control) on the same one;
- a bcdev session without the env-tool hook refuses the same way (build review M3);
- the store round-trips the column, and reads it null on a row from before it.

**The build review's critical finding, fixed:** `itest:lend`'s `seedRunFrom` (`packages/runner/itest/lend-seed.ts`)
cloned a run without its generation, so every seeded run would have been refused by the new rule and the lend gate
would have BLOCKED. It now copies the generation. Its unit test `lend-seed.test.ts` had passed for the wrong reason,
because its source run recorded none; the source now records one. Red-checked: without the copy, 7 of its tests go
red (`red-unit/6-*`).

**Red-checked, each restored** (`/coord/handoff/R-680/red-unit/`):
- without the differing-value check, tests 1 and 2 go red;
- without the missing-value check, test 3;
- with the rule applied without a lease, 193 lease-less resume tests;
- with a second read at acquire, the three window tests;
- without the snapshot filter, the snapshot test.

**Not covered, and why that is safe:** `--skip-known-survivors` (history lending) still lends across a restart. It
skips survivors only, so a restart can hide a kill (an under-report), never make one. The agent guide says so.

**The restart case is measured (R632 1c, coord task R-632c, 2026-10-23).** A real restart of bc2, followed by the
setup, changed `serverGeneration` from `2b8971cb88584ba486dcf6c453a2d76c` to `fed2d48811de43878ee6c9bacf3f26a9`, as
the control app's code says (`/coord/handoff/R-632b/bc2-gen-baseline.txt`, `gen-after-restart2.log`). So the
resume rule refuses a crash gap that spans a restart on real servers, not only by the code.
