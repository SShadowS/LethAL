**What happened.** The R175 re-run of `do rung1` deployed an artifact `alc` refused (R189). Every one
of its 155 mutants was recorded `error`, `mutationScore` was `null`, and the process **exited 0**.
`validity.reliability` was `narrowed` (for `--only`, `--operator` and `--tests-only`), `authoritative`
was `true`, and `caveats` held exactly the three narrowing caveats and nothing about the errors.

So a consumer that branches on the exit code, or reads `authoritative`/`reliability` the way
`docs/using-lethal-from-an-agent.md` tells it to, sees a run that completed normally and measured a
narrowed scope. It measured nothing.

**Why the exit code is 0.** `main()` in `cli.ts` returns `QUARANTINED_EXIT_CODE` when the session
was quarantined and 0 otherwise; the report is the answer and the exit code is not a verdict. That is
a defensible design for an ordinary run with a few errors, and it is not obviously right for a run
where the error count equals the mutant count and the score is `null`.

**Why there is no caveat.** `Caveat` has no member for "errors dominate". `platform-artifact-kills`,
`attribution-unplaceable` and the narrowing caveats all describe a run that produced verdicts.
`errors: 155` sits in `counts` where a reader who does not look for it will not see it, and
`renderConsole` prints it in the score line (`error 155`) after a `score: n/a` that reads as "no
mutants in scope".

**Bisection's message compounds it.** With three independent culprits the single-culprit search
cannot confirm any of them, so it reported *"deploy failed for a reason that is not attributable to
any mutant (failure reproduces even with the candidate excluded) — likely environmental (e.g.
app-version monotonicity, transport, licence)"*. The observation is correct and the "likely
environmental" gloss pointed away from the actual cause, which was three mutants. The message
should list "more than one mutant breaks the compile" beside the environmental candidates.

**What would close it.** Any one of, in order of usefulness:
1. A `Caveat` (say `all-errors` or `errors-dominate`) with a `CAVEAT_INTERPRETATIONS` entry, set
   when `errors` equals the recorded count, or exceeds some stated fraction; `reliability` then
   says so rather than `narrowed`. This ripples the way any new caveat does (`interpretation.test.ts`,
   `report.test.ts` counts, the schema).
2. A distinct exit code for it, documented next to `QUARANTINED_EXIT_CODE` in the agent contract.
3. The bisection detail naming multiple culprits as a candidate cause.

**Not done now** because the run that found it was in the middle of measuring R175, and a new caveat
is a `SessionReport` change with the full ripple listed in `CLAUDE.md`.
