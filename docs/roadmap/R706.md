**Filed 2026-10-24 by R-586b (lethal-bugs)**, evidence the r15 pre-commitment draft
(`/coord/handoff/R-586b/precommit-r11.md`), upstream issue
[#5700](https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5700) and `docs/measurements/r639/`.

**What.** al-runner v3 alpha.4, edge and alpha.5 fail an unhandled `HttpClient.Get('http://localhost:1/x')` with "There
was an error while executing the HTTP request, the connecting endpoint violates security requirements…"
(`HttpRequest:Security`). bc1 fails the same test with `BC_HTTP_INTERNAL_TEXT`, "The request was blocked by the runtime
to prevent accidental use of production services.", in a web-service session under runner 130450. So leg C reads
`refusal-row-shape = unlike-bc` and gate-fails every such build, and a normal session refuses it by name.

Upstream (#5700) reproduces the "security" text on Windows BC 28.5 and 29.0 and on their BC-on-Linux CI through the test
runner hub, and suspects our web-service session under runner 130450. They have not confirmed it. The pre-commitment
keeps the ruling "stays a refusal of the build" until this is measured.

**To close.** On a leased bc server (one gate per server, under a coord lease; a heavy slot free first), run the SAME
probe test in a client session or through the test runner hub, and in the web-service path, and compare the texts.

Conditions, all required:
- the same BC build as `docs/measurements/r639/` (BC 28.4, Base and System Application 28.4.53241.56590);
- the same probe app (the r639 probe), with `TestHttpRequestPolicy` ABSENT;
- both paths measured in the same session of work, on the same server, with the server's go;
- both probe apps removed and read back absent afterwards, as r639 did;
- the raw texts and `GetLastErrorCode` of both paths saved under `/coord/handoff/`, and a README that names the
  server, the build, the harness and the runner.

**What each result means.**
- Client path reads the "security" text, web-service path reads "blocked by the runtime": v3's text is what a user's CI
  sees and `BC_HTTP_INTERNAL_TEXT` is an artefact of our harness. Then (a) of the ruling is met: the pin gains the
  "security" text as a second `gone` text (a delta with its own tests). Lifting also needs the bcdev harness question
  decided (the authoritative backend runs tests in a session whose error texts differ from a user's CI): a separate
  roadmap item.
- Both paths read "blocked by the runtime": v3 is wrong; `unlike-bc` stays and upstream is told.
- If upstream first closes #5700 as a BC-on-Linux image difference: that does NOT lift the ruling, because our oracles
  bc1-bc3 are BC on Linux. It becomes an owner ruling plus a roadmap item.
- If a later build writes `BC_HTTP_INTERNAL_TEXT`, the fact reads `gone` (held): a normal re-pre-commitment.
  (Superseded by the ruling below: a build that writes it now reads `unlike-bc`.)
