**Filed 2026-11-06 by lethal-code.** Related: [[R824]], [[R238]], [[R264]].

**What happened.** Master CI run 42142390734 failed on `unit-linux`: two teardown tests in `cli-envtool.test.ts` expected
`quarantined: false` and read `true`. The same tests passed on the next head.

**Cause: a test of mine, from [[R824]].** `issue #29: an explicit --server/--instance pair wins over --config` in `cli.test.ts`
left a record for `https://host|env-4711` in `defaultQuarantineDir()`, on purpose. That is the tier `cli-envtool.test.ts` uses. Under
`--parallel` a reused worker keeps its fake home, so when `cli.test.ts` ran before `cli-envtool.test.ts` on one worker, the second
file saw the record. Which worker runs which file varies, which is why it looked flaky. Running a copy of `cli-envtool.test.ts`
after `cli.test.ts` fails the same two tests, every time.

**Can a real run hit it? No: this was the tests' sharing, and the product behaved as designed.** `quarantined` in teardown is not a
process-wide flag. `withEnvTeardown` reads it from the run's report and from `tierHasQuarantineRecord`, a durable record on disk for
that exact server and instance ([[R238]]). A plain body failure reads `true` only if that tier really has a record, or the store
cannot be read. Then keeping the environment is the right answer: it does not delete a tier a record names.

**Fixed.** `clearQuarantineFromCli` takes the folder as an argument, as `withEnvTeardown` does, and its tests use a private folder.
A test pins that nothing is left for that tier in the default store, and that with no folder given the command reads the default.

**Not done.** A reused worker still shares one fake home across files, so another test that writes the default store could do this
again. A grep finds no other test writing this tier there; other tiers in that store were not checked.
