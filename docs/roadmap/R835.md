**Filed 2026-11-06 by lethal-code.** Related: [[R824]], [[R238]], [[R264]].

**What happened.** Master CI run 42142390734 failed on `unit-linux`: two teardown tests in `cli-envtool.test.ts` expected
`quarantined: false` and read `true`. The same tests passed on the next head.

**Cause: a test of mine, from [[R824]].** `issue #29: an explicit --server/--instance pair wins over --config` in `cli.test.ts`
left a record for `https://host|env-4711` in `defaultQuarantineDir()`, on purpose. That is the tier `cli-envtool.test.ts` uses. It
only bites in a SERIAL run, where one fake home serves every file. `unit-linux` runs serial (its log says so; `cli.test.ts` was file
166 of 473 and `cli-envtool.test.ts` file 298). Under `--parallel` each file gets a new fake home (measured by the build review), so
the Windows job and a default local verify cannot show this. It failed on one head and not on the next, so the file order seems to
vary between runs; that part is inferred from one log. In a serial run, a copy of `cli-envtool.test.ts` run after `cli.test.ts`
fails the same two tests every time. The zero `could not read the quarantine store` lines in the log rule out the "on any doubt" path.

**Can a real run hit it? No: this was the tests' sharing, and the product behaved as designed.** `quarantined` in teardown is not a
process-wide flag. `withEnvTeardown` reads it from the run's report and from `tierHasQuarantineRecord`, a durable record on disk for
that exact server and instance ([[R238]]). A plain body failure reads `true` only if that tier really has a record, or the store
cannot be read. Then keeping the environment is the right answer: it does not delete a tier a record names.

**Fixed.** `clearQuarantineFromCli` takes the folder as an argument, as `withEnvTeardown` does, and its tests use a private folder.
A test pins that nothing is left for that tier in the default store, and that with no folder given the command reads the default.
The first test had also left `http://other|BC` there; that is gone too.

**A general guard, for the same class.** `scripts/test-preload.ts` now fails the run and names the file when a test file leaves a
record in the fake home's quarantine store, and clears it, so the file that leaks is blamed and not the file that reads it. It runs
per file in both serial and `--parallel` runs, so a local verify catches a leak that only `unit-linux` could show before.

**Still exposed, by reading only.** `orchestrator.test.ts` and `schemas.test.ts` read the default store on their own tiers
(`http://cronus281|BC`, `http://schema-fixture|BC`). They write nothing there on the paths read, and the guard would name any
writer.
