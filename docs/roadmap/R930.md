Found by lethal-bugs, 2026-11-11 (coord R-921). Related: [[R851]], [[R905]].

**What happened.** At 17:05 UTC, `al-runner-v3-update.ts --regate` skipped itself with "3 heavy jobs are running (limit: 2 others)".
Only one heavy slot was held, by a BaseApp corpus diff. Two minutes later the same command ran.

**What it was not.** The first guess was that corpus-snapshot's outer process and its `--in-slot` child count as two jobs. Measured,
that is false: all four of that job's processes (outer, `flock`, `--in-slot` child, its worker) are in one process group, and
`countHeavyJobs` counts groups. Its process snapshot just before the run that started shows one matching group. The second group at
17:05 was short-lived and is not known.

**The flaw found, and measured.** `countHeavyJobs` matches `HEAVY_JOB` against every process's whole command line.
- A shell's command line names the command it runs. GNU `timeout` moves itself into a new process group. So
  `bash scripts/heavy-slot.sh other timeout 9 bun ... cli.ts run ...` matches in the shell's group AND in the `timeout` group: one job
  read as two. A harness's own `bash -c` wrapper is a third group (measured with an invented command, 2026-11-11).
- A reader such as `grep -E "cli.ts run"` (a status check) matched as a job.
- With a BaseApp-class slot held, two counted jobs become three, and the update skips for the day.

**Fixed.** A reader is never a job. A shell is skipped when a process below it is a job of its own, since that process stands for the job.
A shell with no job below it still counts, as corpus-snapshot's guard rules for a shell-wrapped census whose child names no corpus
(review r2). So a retry loop between attempts still reads as a job: the safe direction, a skipped update. `corpus-snapshot.ts`'s own
guard (`isHeavy`) is unchanged.
