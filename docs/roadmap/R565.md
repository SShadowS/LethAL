**Filed 2026-10-10 by R-561 (orchestrator's ruling).** This is the mechanism [[R561]] is blocked on. LethAL reads a
project's own `.al` files. Of a dependency it reads only symbols (`app-package.ts` reads `SymbolReference.json`). So
a rule that must know what a dependency's procedure DOES cannot be evaluated. The case that needs it is R561: a
call from the project to a dependency report's preset writer, such as Quality Management calling BaseApp's
`Whse.-Source - Create Document`.SetWhseWkshLine.

## What can be known, measured on `Microsoft_Base Application_28.5.54151.55132.app` (al-runner's platform-apps cache; output in `/coord/handoff/R-561/scratch/symbols-vs-source.txt`)
- **Symbols alone** (`SymbolReference.json`). Each report entry carries `Methods` (Name and Parameters only, no
  body), `Variables` (the report's globals), `DataItems` (each with `RelatedTable`, `Properties` and nested items),
  `RequestPage`, `Layouts` and `ReferenceSourceFileName`.
  - So it gives a dependency report's procedure names, its globals, and which table each data item walks.
  - It does NOT give which procedure writes which global, nor what an open item's exit guard reads. A "preset
    writer" (R500 and R555) cannot be derived from symbols.
- **Source.** Microsoft's package ships it: the `.app` inside the ReadyToRun wrapper holds 8,096 `.al` files next to
  `SymbolReference.json`.
  - So for a Microsoft dependency, a real user's machine has the report bodies: in the platform apps al-runner
    provisions, and in any `.app` exported from a BC container.
  - For a third-party dependency, the source is there only if its publisher includes it (`resourceExposurePolicy`).
    Otherwise there are symbols only, and the rule cannot answer.

**To build:** for each `Report X` receiver whose X is outside the project, find X in the dependency packages
(`.alpackages`, or al-runner's platform apps), read that report's `.al` when the package carries source, and run
R555's `presetWriters` on it. When no source is available, say so by name and do not guess. Out of scope: any rule
that would need a dependency's source and can do without it.

## Built (branch `lethal/r565`; plan `/coord/reviews/R-565-plan/plan.r1.md` as amended by `plan.r2.md`)
**The rule.** A call through a `Report X` receiver, X a report the project does not declare (by name or by id), to a
preset writer of X is hang-refused exactly as R555 refuses one for a project report. X's writers come from X's own
source, read from the dependency packages (`packages/runner/src/dependency-report-source.ts`), plus the writers of
every dependency reportextension of X in the selected packages. Those files are parsed into a context of their own,
in which every `#if` arm is active and every report counts as extended (R487): the project, or any app installed on
the server, may extend it, and the packages cannot say. The reader reaches `crossWriters` (`loop-hazard.ts`) through
`SemanticContext.dependencyReport`, built per generation; there is no module state.

**Packages searched, per backend** (`MutationSetOptions.dependencyPackageDirs`, passed by `runSession`):
- al-runner: the platform-apps folder provisioning reported, then `alRunner.packagesDir`.
- bcdev and envtool: `bcdev.packageCachePath` (default `<project>/.alpackages`), as alc reads it.
- `--dry-run`: the same config folders, without al-runner's provisioned folder. The compile-only driver: its
  `--package-cache`.

Per app id the first folder holding the app wins, then its highest version in that folder; only those packages are
read, extensions included. Two app ids declaring X is `ambiguous`, and nothing is read. A ReadyToRun wrapper is
read only in the measured shape: a top-level `readytorunappmanifest.json`, exactly one top-level `.app` named exactly
`EmbeddedAppFileName`, whose `NavxManifest.xml` id, name, publisher and version equal the `Embedded*` values and
which carries `SymbolReference.json`. Anything else is `unwrap-failed`; there is no file-name fallback. The first
folder still wins when its copy is refused (`unwrap-failed`, or `no-symbols` with a readable manifest): a later
folder's copy of the same app id is not read, and is recorded with that refusal's reason. An `unreadable` package
has no readable app id, so it cannot block a later copy. The reader only reads: entries are read by exact name and
nothing is extracted or written.

**No source.** Nothing is refused for lack of source: the call is checked against what was read, as before. Each
lookup that is not `ok` gives one `dependency-report-source-unavailable` warning naming the report (or package) and
the reason: `not-found`, `no-source`, `ambiguous`, `parse-damaged` (read, and R555's `damagedProcs` applies),
`unwrap-failed`, `no-symbols` (a runtime package), `unreadable` (a corrupt package, one holding an entry name
twice, or a listed source entry that cannot be read; generation continues), `base-not-found` (the entry declares
no report of the name the symbols give, so nothing is used). `SessionReport.dependencyReportSources` lists every record (report, extension and
package), and the banner prints those that are not `ok`.

**Fingerprint.** `dependencySourceSha256` is SHA-256 over every record (kind, report, outcome, package, app id,
version, entry and the entry's SHA-256). It is written to the run row after generation and before any mutant row
(`setDependencySourceSha256`, like `setCarryHidden`), and to the report. `carryRecord` rule 1 now needs the
generation source hash AND this digest equal, where a null on either side is never equal (null against null
included); rule 2 is unchanged. Verify copies its source run's digest. `IDENTITY_SCHEME` is 40.

**Stated limits.**
- `--dry-run` on al-runner has no provisioned platform folder, so Microsoft reports are read only from
  `alRunner.packagesDir`, and its refused set can differ from a real run's. It warns.
- On bcdev the BaseApp in `packageCachePath` can be older than the server's after a server update. Accepted; the
  report records the version read.
- A third-party package that ships no source is `no-source`: its preset writers are not known.
- The bcdev and envtool wiring (`packageCachePath` into `runSession`) is proven by unit tests only:
  `itest:bcdev`, `itest:tables` and `itest:chunked` call `runSession` directly with no `dependencyPackageDirs`,
  and no fixture calls a `Report X` outside its project, so no live gate reads a dependency report.
