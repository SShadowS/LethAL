**Found 2026-10-05 by the post-merge gpt-6.1-sol review of R-196 and R-447**
(`/coord/reviews/postmerge-2026-10-05/sol-R-196-R-447.md`; static review, not run). No critical
finding, and R-447's count/refusal wiring was found consistent. Each gap below emits a mutant that can
hang the server and is neither refused nor hang-tagged:

1. **`shift-integer` in an active `#if` condition tail.** `inLoopCondition` (in `shift-integer.ts`)
   looks only inside the loop's `condition` field and misses a sibling
   `preproc_conditional_expression_tail`. Example: `while false #if X or (Cust.Next() <> 0) #endif do`,
   whose `0 -> 1` is claimed. Use the tail-aware containment already used elsewhere.
2. **`flip-boolean-literal` on a literal inside a comparison in a loop condition.**
   `isLoopCondition` and `CONDITION_WRAPPERS` (in `flip-boolean-literal.ts`) exclude
   `comparison_expression`, so a literal in `repeat ... until Done = true` (or an exit guard in a body,
   `if X = true then exit`) is flipped untagged.
3. **Member-target writes.** `assignmentTargetOf` (in `loop-hazard.ts`) rejects member targets, so
   in `repeat Rec.Done := true; until Rec.Done;` removing or flipping the write hangs untagged. Writes
   through `with` are the same unresolved case. (A loop whose only exit is a body guard is [[R446]].)
4. Lower: `swap-additive` mutating the bound in a loop condition (`while I < N - 1` to `N + 1`), which
   hangs only with a body that does not advance `I`; it was there before R-196.

Two test gaps from the same review: `loop-hazard.test.ts` "CLAIMS through an OUTER loop, not only the
nearest one" writes the outer variable after the inner loop, so a nearest-loop-only classifier passes
(move the write inside the inner body); `orchestrator.test.ts` "built-in operators REFUSE the loop's
step…" asserts only that `Remaining := Remaining - 1` is absent, so dropping only swap-additive's
refusal (which emits `Remaining - 1`) passes (assert that too).

**To close.** Measure each shape on BaseApp and CDO first. Refuse 1-3 with a red test per direction;
rule on 4 with its count. Fix both tests and red-check them.

**Closed 2026-10-05 (`f023b8a2`, `IDENTITY_SCHEME` 14).** Plan:
`docs/superpowers/plans/2026-10-05-R-454-untagged-hang-shapes.md` (r2, adopted).

- **Shape 1 refused, silently.** `shift-integer`'s loop-condition refusal now reads the condition's
  `#if` tails through `loopConditionParts` (in `loop-hazard.ts`), the same parts
  `conditionIdentifiers` reads. 0 sites on any measured corpus.
- **Shape 2 refused, silently** (R239's scope). `flip-boolean-literal`'s `CONDITION_WRAPPERS` gains
  `comparison_expression`, so loop conditions and in-loop `if` guards both. Honest classification
  of the 28 loop-condition sites on BaseApp: **no established hang**. 15 end on any data (a counter
  bound, a `Next() = 0` arm, a queue read or write, an array index); 13 are data-dependent (a body
  that only counts, ending only on Integer overflow on a one-row page; no progress on a one-row
  page; one outer fixpoint loop). The refusal rests on the conservative rule, not a measured hang.
- **Shape 3 refused AND counted** into R447's `hang-refused` row. `classifyHangCapable` sees an
  `R.Field` write whose receiver resolves, keyed by the receiver's declaration and the member name
  compared SEPARATELY (so `"A.B".C` is not `A."B.C"`), against every enclosing loop's condition.
  An unresolved receiver still declines: filed as [[R458]].
- **Tests.** Shapes 1-2 in `loop-exit-refusal.test.ts` (with same-loop controls and a pin that
  neither is counted); shape 3 in `loop-hazard.test.ts` (other member, other receiver, the
  collision control, the outer-loop member write, an unresolved receiver) and
  `refuses-hang-capable.test.ts` (all four operators: refused and counted, sibling emitted, no

  reverting its fix.

- **Point 4, closed 2026-10-05 by ruling:** `swap-additive` keeps loop-condition bounds. Corpus
  evidence, not a general rule: the 7 such sites on BaseApp (6 Source, 1 Test; 0 on CDO, 0 on
  fixtures) were each read and none can loop forever: `RecordMatchMgt` `GetLongestCommonSubstring`
  x2 (inner loop, `j += 1`), `UserTask` `CreateRecurrence` (`Counter := Counter + 1`) and the Test
  site (`SCMItemAttributes`, `I += 1`) advance their counter unconditionally on every pass;
  `ServiceCalcDiscount` `GetNewServiceLineNoBias` has a halving second conjunct that ends it;
  `PhysInvtCountManagement` `CalcPeriod` errors on an array index past its bound (its `repeat`
  steps `i` unconditionally); `OpenXMLManagement` `CopyDataToExcelTable` (the one equality bound,
  `until ColumnsCount = DataTableColumnsCount - 1`) steps by 1 from 0, so the `+ 1` mutant reads
  `DataTable.Columns.Item(<column count>)` and ends on a .NET index error before it reaches its new
  target. **Remaining risk, accepted:** a bound mutation can add iterations on which the body does
  not advance (a conditional step), so on another codebase such a site can hang. The review's
  (gpt-6.1-sol) counterexample: `I := 0; N := 3; while I < N - 1 do if I < 2 then I += 1;` ends,
  but its `N + 1` mutant runs at `I = 2`, where the body no longer advances, and never ends. The
  run's existing hang handling (timeout, strand, quarantine) is what catches it. Revisit if a hang
  from this operator is ever measured.
