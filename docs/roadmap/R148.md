Every `itest:alrunner` invocation prints this to stderr, and nothing reads it:

```
[dep] LethAL/LethAL Sandbox App v1.0.0.999 resolved to a package with NO IMPLEMENTATION (no publishedartifacts DLL,
      no src/*.al) and no other copy was found in the package caches:
      winner: U:\Git\LethAL\fixtures\sandbox-tests\.alpackages\LethAL_LethAL Sandbox App_1.0.0.999.app
      Calls into this app will fail with "The object with ID 0 does not
      have a member with that ID". Provision a package that carries an
      implementation - `al-runner provision`, or re-run with --auto-provision;
```

`fixtures/sandbox-tests/.alpackages` holds TWO copies of the mutation target: a
`LethAL_Sandbox App_1.0.0.0.app` and a `LethAL_LethAL Sandbox App_1.0.0.999.app`. The `999` build is
symbol-only, it is the one al-runner names as the WINNER of dependency resolution, and al-runner says
in as many words that calls into it will fail.

**The tests pass anyway**, which is why this has never been noticed. The run also compiles the source
bundle `fixtures/sandbox-app`, and the line above it, `[layered] cache HIT LethAL Sandbox App 1.0.0.0
... (src .app + sidecar symbols)`, shows an implementation package built in-process from source
winning at execution time. So resolution names one package and execution uses another.

**Why it is worth a row rather than a shrug.** The gate exists to notice when al-runner starts
answering differently. If a future release ever let the declared `[dep]` winner reach execution, the
sandbox target's procedure bodies would be gone, and the failure would arrive as a change in verdicts
rather than as a message anyone read. It is also a live example of a warning stream this repo does
not inspect: the line has been printed on every al-runner gate run for months.

Two things worth deciding when this is picked up, and they are separable:

1. Whether the stale `1.0.0.999` copy should simply be removed from
   `fixtures/sandbox-tests/.alpackages`, and what re-publishes it. The version does not match the
   test app's declared dependency (`1.0.0.0`), so something wrote it out of band.
2. Whether `AlRunnerBackend` should surface `[dep] ... NO IMPLEMENTATION` as a warning event at all,
   for any project. On a real project that line means the run is measuring an app whose bodies are
   absent, which is a whole-session correctness problem, not a fixture quirk.

Evidence: the stderr above, captured 2026-08-15 under both the `--auto-provision` and the
`--package-cache` argv while measuring R147, identical in both. `ls
fixtures/sandbox-tests/.alpackages` shows both copies.

---

**Decision 2 BUILT 2026-08-19; decision 1 deliberately left alone.**

`parseAlRunnerMissingImplementation` reads the runner's `[dep] … resolved to a package with NO
IMPLEMENTATION` line, the transport records the FIRST occurrence (the runner repeats it identically
per invocation), and `runSession` emits it as a `warning` with code
`al-runner-missing-implementation`, so it lands in the report and the NDJSON stream instead of the
terminal scrollback.

Built exactly like R129's `parseAlRunnerBcBuild`, which is the precedent for reading al-runner's
stderr rather than ignoring it: anchored at line start so a test's own failure text cannot forge it,
`undefined` meaning "the runner did not say it" and never "there is no problem", and surfaced through
an optional method the orchestrator asks for structurally rather than widening `ExecutionBackend`,
because no other backend has the concept.

Four unit tests cover the parser, including the forgery case and the repeat case. The line the tests
use is the verbatim one captured from a real 2.1.2.0 run.

**Three more cover the EMISSION, and they exist because the live gate cannot answer this.** LethAL
CAPTURES al-runner's stderr rather than inheriting it, so `itest:alrunner`'s own transcript contains
no `[dep]` line at all and a green gate says nothing about whether the warning was emitted. The
emission is therefore driven offline through `runSession` with a stub backend: one test asserts the
warning names the app and quotes the runner, one CONTROL asserts a backend that saw nothing emits no
warning, and one asserts a backend without the method at all neither throws nor warns — which is
every non-al-runner backend. Red-checked: neutering the read fails exactly the first.

**Why the warning matters even though the fixture is fine.** On this fixture the run also compiles
the target from source, an implementation package wins at execution time, and the gate is green
either way. On a real project the identical line means every mutant in that app was scored against a
program whose procedure bodies are absent. Nothing in the line distinguishes the two, which is the
whole argument for putting it in the report.

**Decision 1 stays open**, and not from neglect: `fixtures/sandbox-tests/.alpackages` is GITIGNORED,
so deleting the stale `1.0.0.999` copy fixes one machine and no other, and the row's own question —
what wrote it out of band, given the test app declares a dependency on `1.0.0.0` — is unanswered.
Removing the file without answering that would make the warning stop appearing here while leaving
whatever produces it in place, which is the worse outcome now that the warning is wired up.

---

**Decision 1 ANSWERED and acted on 2026-08-19.** The row's blocking question was "what wrote it out
of band, given the test app declares a dependency on `1.0.0.0`". Answered by opening both packages:

| file | zip entries | `src/*.al` | manifest version |
| --- | ---: | --- | --- |
| `LethAL_Sandbox App_1.0.0.0.app` | 8 | **yes** | 1.0.0.0 |
| `LethAL_LethAL Sandbox App_1.0.0.999.app` | 3 | no | 1.0.0.999 |

Same app id, same app name, different FILE names — the second spelling is what a symbol download
produces (`<publisher>_<name>_<version>`), the first predates a rename. **Nothing in LethAL writes a
`999`**: `reserveAppVersion` mints `<major>.<minor>.<daysSinceEpoch>.<secondsOfDay/2>`, which is
never a round number, and both files carry the fixture's creation date. So it was placed by hand when
the fixture was built and simply outlived its reason.

That makes it safe to remove, which the row could not previously conclude: the `1.0.0.0` package
satisfies the declared dependency AND carries the implementation, so the `999` stub was pure
resolution noise that al-runner correctly complained about. **Removed, and `itest:alrunner` passes
3 / 14 / 0** — the gate is green without it.

`.alpackages` is gitignored, so the removal fixes one machine. What lands in the repo is the note in
`fixtures/README.md` §symbol-staging, so the next person to repopulate symbols does not recreate it.

**One honest consequence:** with the stub gone, the `al-runner-missing-implementation` warning built
by decision 2 now has nothing to fire on in this repository. It stays covered by unit tests for the
parser and by three orchestrator tests for the emission, and it exists for a REAL project, where the
same line means every mutant in that app was scored against a program whose bodies are absent.
