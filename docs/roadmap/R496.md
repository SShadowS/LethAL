**Found 2026-10-06 by R-492's plan review** (`/coord/handoff/R-492/review-r1.md`, Q1). Pre-existing;
R492 did not change it.

**What.** A run's test-app identity (`test_app_hash`) is the hash of the test app package alone.
Resume, `--skip-known-survivors` and R192 baseline-snapshot reuse match on it. When an env-tool hook
also publishes a DEPENDENCY of the test app (`publishApps`) and that dependency changes between two
runs while the test app does not, both runs are proven and match, so verdicts and a baseline carry
across a changed dependency. Only the digests' dependency fingerprint (R-371) records the change.

**To close.** Include the dependency fingerprint (or the hook-published apps' hashes) in the identity
the three consumers compare, or refuse when the recorded digests' dependency parts differ. Measure
first how often a hook republishes a dependency without the test app.

**Measured (R-496, `/coord/handoff/R-496/measure.md`).** A session WITHOUT a hook has the same hole,
and it is the common case: any republish of a library the tests depend on, between two runs, left
both runs proven with equal hashes. An offline reproduction on fakes carried through all three
consumers, in both session kinds.

**Closed (R-496, plan r3 at `/coord/handoff/R-496/plan.md`).** `runs.test_app_deps` (additive column;
NULL on older rows) holds R-371's `dependencyFingerprint`, written in the same update as the hash
and the proven flag; proven implies a fingerprint. Resume (both kinds), `priorSurvivorKeys` and
`findBaselineSnapshot` compare it, and NULL never matches. A session without a hook takes it UNDER
THE LEASE, before the batch loop, from the served test app's manifest (so a package without `.al`
fingerprints too); a hook session takes it from the read-back after the hook; al-runner from its
`app.json` and package folders, before its run row. When a non-hook run's pre-lease digests recorded
another dependency part than the value under the lease, the run's identity and digests are cleared
before any identity is published (one `test-digests-unavailable` warning); a fresh run then runs
unproven and a requested resume refuses. In bytes mode EVERY extension the walk hashes, partner and
transitive ones included, must have exactly one installed row at the served version, read by the
per-app `$filter=id eq <GUID>` read only (an unfiltered read is refused before it is sent and
propagates as `UnfilteredExtensionsQueryError`). Side effect: `lethal verify` now refuses a run
whose closure holds a staged partner dependency. Limits: apps outside the closure; symbols-only
packages; binary-only platform updates; al-runner's Microsoft apps by declared version; R192's data
caveat; a dependency changed during the batches; the control app's own bytes (only its version and
its dependencies count); no exclusion without a lease. Tests in `orchestrator.test.ts` "R496: the
dependency fingerprint is part of the proven test-app identity" and "R496 T11", in `store.test.ts`,
`baseline-snapshot.test.ts` and `extensions-query-refusal.test.ts`; each fix red-checked
(`/coord/handoff/R-496/redchecks.md`). Follow-up: [[R498]] (a source-less hook read-back never
proves).
