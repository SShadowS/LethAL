**Part 1, PR-88 (2026-11-16): the sensor, not the estimator.** R987's estimator stays max-only: two spec-adversary passes showed
that lowering a cost from a reading can run the container out of memory. PR-88 reads each request's true peak (VmHWM after a
verified `clear_refs` reset, max with the sampler; a probe showed the 200 ms sampler read a 300 MB burst as 91-165 MB). It also
adds per-codeunit cap lines and a `serve-request-sized` event in `--progress-out`. The order dependence this item describes is
NOT fixed. Its follow-up is [[R1091]] (calibration requests per codeunit, probed first from those events).

Found by R-984's t6 BLOCK analysis (lethal-bugs, 2026-11-16; `/coord/handoff/R-984/t6-block.md`), confirmed by lethal-code
against t6's events.

**Measured.** [[R987]] lowers the number of test entries a serve request carries when a request grows its daemon too much per
entry (`al-runner-v3-entries-cap-lowered`, "requests of its tests carry about N test entries (not 256)"). On the same DO project
and config, the six windows printed N = 119 (t1), 41 (t2b), 208 (t3), 230 (t4), 201 (t5) and 38 (t6). In t6 the warning came at
event seq 30352, right after mutants of CDOeDocPrePostValid: the value is taken once, from the first large prefetch the window meets,
so it reflects whichever codeunit comes first, not the project.

**Why it matters.**
- Request packing varies from window to window. With a timeout cut (R895) that is one of the two inputs that move a timeout-killed
  verdict between windows ([[R1057]]).
- One heavy codeunit early in a window sets a low cap for the whole window: 38 in t6 is about 5x more prefetch requests than t5's
  201 for the same tests. Not the cause of t6's slowdown (that was a refused test sent once per mutant, PR-47), but a cost of its own.

**Possible fix** (not designed): measure per codeunit (or per entry group) and keep a running figure, rather than one value per
window from the first large request.

**To close.** The cap follows the codeunits a request carries, with a test that two requests of different codeunits in one window
get different caps, and a DO window whose log shows it.

**Closed by measurement (coord PR-168, 2026-11-18; orchestrator ruling: build only for a saving of about 3% or more).**
Evidence: `/coord/handoff/PR-168/result.md`, from DO y1's events (`/coord/handoff/R-984/y1/y1.run.events.ndjson`,
edge-4ebfe7913, 3 lanes).
- **The first half is already true.** Since PR-88 the cap follows the codeunit. y1's 106 `al-runner-v3-entries-cap-lowered`
  warnings each name one codeunit, with caps from 10 to 254 (median 164).
- **What it costs.**
  - The mutant phase took 24,881 s wall. It sent 5,066 prefetch requests over 110 codeunits, with a median of 12
    entries per request.
  - 829 requests (16%) sat at a lowered cap, carrying 57,175 entries.
- **The upper bound.** With no cap at all, those entries would pack into 605 fewer requests. That saves 184-421 s wall,
  0.74-1.69% of the phase, depending on whether a saved request is charged its fixed timings (0.915 s), a fit's intercept
  (1.06 s) or a whole 1-3 entry request (2.09 s). A per-codeunit cap that keeps a memory bound can save no more.
- **y2's figure** is appended to the result file when that run ends.
- **The remaining order dependence** (max-only costs, raised by co-packing) is not worth a change at this size. See
  [[R1091]].
