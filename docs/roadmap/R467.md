**Found 2026-10-05, closing R244 (R-244).** `lethal.empty-block` listed `repeat_statement` as a
body parent and matched nothing: a `repeat` body is a `statement_block`, and a `begin ... end`
inside it is a `code_block` whose parent is that `statement_block`. R244 deleted the dead entry
and pinned that no `repeat` body is claimed (`packages/builtin-tier1/tests/empty-block.test.ts`,
"claims no repeat body, Next-terminated or not, plain or begin...end"). This item is the part R244
did not build: whether `repeat` bodies should get an `empty-block` mutant at all.

## The population (measured 2026-10-05, `/coord/handoff/R-244/measurement.md`)

| corpus | `repeat` loops | `until` calls `Next(` | `until` does not |
|---|---|---|---|
| BaseApp history (`/work/src/BC.History`) | 12,041 | 11,504 | 537 |
| CDO | 303 | 290 | 13 |
| fixtures | 7 | 4 (`sandbox-coverage-probe`) | 3 (`sandbox-hang`) |

None of the 12,363 is written `repeat begin ... end until`; every body is a plain statement list
(17 BaseApp bodies mix in a `begin ... end`, 8 are empty). The `Next(` class is by TEXT
(`X.Next(` or a bare `Next(`), so a cursor advanced through a helper (`NextRec`, `NextDate`, a
`NextRow()` like `sandbox-hang`'s `WalkOneRow`) is counted with the hang class.

## The shape a build would take

Claim the repeat's `statement_block` ONLY when its `until` is a cursor advance, and refuse the
rest positionally, as R179 cedes `while` bodies to `loop-skip`. Emptying a body whose `until` the
body advances freezes the condition and HANGS the session (all three `sandbox-hang` repeats), and
`empty-block` is not one of the hang check's callers (`hangCapableForMutatedNode`). Emptying a
cursor loop's body terminates: the loop still walks every row, doing nothing on each.

## The question to answer BEFORE building (R159 point 2)

The statements inside these bodies already carry their own fine-grained mutants (removed calls,
removed assignments, swapped operators, flipped literals). An emptied body is a COARSE mutant on
top of them, and R159 point 2 is the argument that a coarse mutant a single weak assertion kills
adds reach only where the fine ones cannot go. This item must say what the coarse mutant adds that
they do not before anyone builds it, by measuring it, not by assuming it. R159's own live run on
`sandbox-data` is the precedent for each answer being possible: there `empty-block` KILLED
procedures where the fine-grained flip SURVIVED. A useful measurement is the R159 one at repeat
bodies: on a fixture with cursor loops, how often the emptied body and the fine mutants inside it
disagree.

## Cost if built

About 11,500 new BaseApp mutants and 290 CDO ones, 4 on `sandbox-coverage-probe`. It needs an
`IDENTITY_SCHEME` bump (added mutants move same-tuple ordinals), a pre-commitment for any gate
fixture that moves, and a refused-site count for the non-`Next` loops (in the excludedSites
report, like `hang-refused`).
