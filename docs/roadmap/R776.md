**Filed 2026-10-25 by lethal-preproc, from coord task R-773.** Related: [[R765]], [[R774]].
Evidence: `/coord/handoff/R-773/de5f5ace/` (`runs/gc-1`, probe fresh) and `/coord/handoff/R-773/de5f5ace/gc2/`
(probe from cache).

**What.** `packagesFingerprint` (`al-runner-v3-probe-cache.ts`) puts each `.app`'s name, size and mtime into the
contract-probe cache key. The code gives no reason for mtime over content. Any new copy of the same files gets a
new key, so its first run reruns the probe:
- a fresh checkout or a new worktree;
- a CI runner;
- an `.alpackages` the AL extension downloaded again;
- a folder copied without its timestamps.

The miss is the safe direction, never a wrong hit. But it costs a whole probe.

**Measured on the gift card at de5f5ace, through `lethal run`.** Both runs had 3 other heavy jobs running.
- Probe ran fresh (a new key): wall 16.1 s, of which the probe was 9.9 s.
- Probe from cache, same folder: wall 6.2 s.

**What a content hash would cost.** Hashing the folders' bytes took about 0.09 s each, with the files already in
the page cache:
- the gift card's packages: 64 MB, 5 apps;
- CDO's `Test/.alpackages`: 72 MB, 17 apps.

**To close.** Decide whether the key should hash file contents instead of mtimes. It is about 0.1 s per run with a
warm page cache; measure a cold read too. If so, change `packagesFingerprint` and its tests. Size alone is not
enough: two builds of an app can have the same size.

**Done (2026-10-25; owner approved the content hash via the orchestrator).**
- `packagesFingerprint` now hashes each `.app`'s bytes on its own, streamed, and feeds `name\0<sha256 hex>\n` per file
  into the key. Size and mtime are out.
  - Per-file hashes, not one shared stream: the build review showed that with one stream, a file holding
    `abc\0B.app\0def` fingerprinted the same as `abc` plus a `B.app` holding `def`. That is a wrong hit, the dangerous
    direction.
- Each of these throws, and `probeKey` turns it into "key unavailable": the probe runs, and nothing is written.
  - a file it cannot read;
  - an `.app` that is not a regular file. A FIFO would block, and a device could be read forever.

  A session already blocks earlier on a FIFO, though: `assertBcVersionMatchesPackages`, v3 and alc all read every
  `.app` in the folder.
- Cost of `packagesFingerprint` itself, under a load average of about 16:
  - 0.14 s per call with a warm page cache, on both folders above;
  - 0.18 s (gift card) and 0.26 s (CDO) for a cold read through `O_DIRECT` (`dd iflag=direct`), which bypasses
    the page cache.
  - A probe costs about 10 to 14 s.
- Tests in `r762-probe-cache.test.ts`:
  - a changed byte, with the same name, size and mtime, misses;
  - the same bytes rewritten and touched hit;
  - a copied folder with the same bytes hits;
  - an `.app` that cannot be read (a directory) reruns the probe each time and writes no entry;
  - one file's bytes cannot pose as a file boundary;
  - a FIFO `.app` makes the fingerprint throw instead of block. This test is skipped on Windows, which has no
    `mkfifo`.
- Red-checked:
  - with the old size-and-mtime fingerprint back, the first four go red;
  - with one shared hash stream, the boundary test goes red;
  - without the regular-file check, the FIFO test hangs to its timeout.
- The `bcVersion` key-part test now holds the fingerprint still with a spy. The backend requires the System
  Application to equal bcVersion, so that test must change the app's bytes, which now also moves the fingerprint.
