**Found by** lethal-bugs on PR-504's branch (2026-11-28). The branch did not touch the file. Evidence: CI run 46139921525,
job `unit-linux`, first attempt.

- **What failed** (4 of 16,390 tests): each expects the update to be SKIPPED (a held gate lock, or heavy load) and read
  `pass`, so the gate would have run.
  - R639 the gate lock (L1-L6), "L1: a live holder: skipped, exit 2, the gate never runs": `["pass"]` where
    `["skipped"]` was expected;
  - R639 --edge-rejudge (R1-R9), "R1: skipped with 3 other heavy jobs, under 10 GB, or a live lock: exit 2 and no gate";
  - PR-255: --main, "the lock: a held .gate.lock skips the run, gates nothing";
  - R859: refreshRows, "a skipped run (heavy load, or the lock held by a live update) writes nothing and gates nothing".
- **Not reproduced:** the same commit passed `bun scripts/verify.ts` locally (16,378 pass, 0 fail), and the CI re-run of
  the same job passed. The same tests pass in master's CI.
- **Ruled out:** a real pid on the runner. `takeGateLock` decides a holder is live from `deps.procCmdline`, the test's
  own fake process list, not from the host's processes.
- **Suspicion, not a finding:** shared state in the file's setup. All four are skip paths that read a lock or a heavy-job
  count, so one test seeing another test's lock root, lock file or fakes would give exactly "the skip condition was not
  seen". It needs a read of how the tests build `deps.root` and the fakes, and whether any of them share a directory or
  a module-level value.
- **Why it matters:** these tests guard the update gate's refusal to run beside a live update or under heavy load. A test
  that fails or passes by shared state cannot be trusted to show that guard.
- **Related:** R639, R859, PR-255, PR-504.
