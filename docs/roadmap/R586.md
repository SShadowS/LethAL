**Owner request, 2026-10-20:** "migrate from AL Runner to https://github.com/StefanMaron/al-runtime-rs".

**What al-runtime-rs is,** per its README on 2026-10-20 (not yet measured):
- A Rust rewrite of the ideas behind BusinessCentral.AL.Runner, by the same author. The repo was created
  2026-10-13.
- It parses, checks and runs AL source itself, in its own VM against an in-memory database: no BC service tier,
  no Microsoft DLLs, no .NET. DotNet-typed AL calls go to an optional .NET helper.
- CLI: `alrunner test <app> <testapp>`.
- Releases: numbered alphas (`3.0.0-alpha.N`) plus a nightly `edge`, for Linux x64, Windows x64 and macOS arm64.
- As an alpha it refuses many tests as "not run" (exit 7). Exit 6 means a selection matched nothing.

**Why it is not a drop-in.** LethAL's al-runner backend depends on a measured contract, and each part must be
re-measured on the new runtime as supported, different or missing:
- exact-name selection and AL names (R551, [[R557]]);
- JSON rows and statuses;
- per-test timeouts and the hang shape (R516, R518);
- coverage (R220, R407);
- a warm daemon (`--server`);
- switching the active mutant without recompiling (the resource selector, R222);
- `--define` symbol sets (R319, R321);
- platform-app provisioning and pinning (R147);
- compile-error reporting (R583);
- test data and company setup;
- "not run" refusals. LethAL must score those as neither killed nor survived.

**To close.**
1. Measure the contract (coord task R-586).
2. Run LethAL's fixtures and the R546 CDO slice, comparing per mutant with BC.
3. Recommend: (a) a new backend beside al-runner, (b) a replacement, or (c) wait.
4. File the missing capabilities upstream at al-runtime-rs.

Planning and building come only after the owner chooses.

Measured on alpha.2 and NOT needed upstream (evidence: the orchestrator workflow of 2026-10-21, its `alr-proposals`
scratch, which is not copied into the repo):

- `perTestCoverage` in `--coverage-json` gives correct PER-TEST hit counts, one-shot and on `serve`. It is the
  equivalent of BC's `ObservedActive`, and it is what the §6 Sleep rule reads.
- `serve` survives a CPU-timeout test (notRun, "Test exceeded 3s timeout.", exit 7) and answers the next request from
  the same warm workspace.

No tagged release contains these fixes yet: the latest are `v3.0.0-alpha.3` (09:07Z) and `edge` c893e3633 (05:57Z),
both from before the closures. When a release with them is tagged, it goes through the update gate
(`scripts/al-runner-v3-update.ts`) and is measured against the pre-commitment (dcdd1489); the pin is NOT moved by
hand. #5602, #5603 and #5604 are three of the four verdict-changing defects, so their fix is expected to move rows
toward BC: that is the gate's `held` case, never a blacklisting.

TestPage runs on v3, where LethAL's fenced BC session refuses it. That is a BC-side limit, not an al-runner bug, so
no issue was filed.
