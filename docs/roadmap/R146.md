`buildDoctorDeps` (cli.ts) THROWS when a config has neither an `envTool` nor a `bcdev` section, with
a message that is accurate about today's checks:

> `lethal doctor` only checks a bcdev-configured project — environment, quarantine, control-app
> version and alc/altool are all live-BC concerns. This config has no "bcdev" section; if this is an
> al-runner project (`--backend al-runner`), there is nothing here for doctor to check today.

That sentence stopped being true on 2026-08-14. [R131](R131.md) added `al-runner-cache`, a check that
reads a local directory, needs no environment, and is ABOUT al-runner. It runs in create mode for
exactly that reason. But a project configured for al-runner alone — no `bcdev` section, which is a
legal config `lethal run --backend al-runner` accepts — never reaches any check at all, because the
throw fires first. So the one check written for al-runner users is unreachable by the users who only
use al-runner.

Not fixed inside R131 deliberately: R131 asked for a REPORT and got one, and widening what
`lethal doctor` accepts is a change to that command's contract rather than a detail of the report.
Doing it inside R131 would have been the "smuggled scope" mistake this repo keeps a rule against.

What closing this needs, and the order matters:

1. Decide what an al-runner-only `lethal doctor` should CHECK, not just what it can print. Candidates
   that need no BC container: the al-runner binary's presence and version (`--version`, the same
   read [R123](R123.md) would formalise), the artifact cache (built), `alc` (needed for the target
   compile on both backends). The environment/lease/quarantine/control-version checks genuinely have
   no meaning there and must stay absent rather than pass vacuously — the R110 lesson.
2. Keep the throw for a config that is neither, which is a real mistake worth refusing.
3. Print a caveat naming what was NOT checked, the way `DOCTOR_CREATE_MODE_CAVEAT` already does for a
   create-mode envTool config, so a green al-runner doctor cannot read as a green bcdev doctor.

Evidence: the throw in `buildDoctorDeps`, and the `al-runner-cache` check in `doctor.ts` that it
prevents an al-runner-only project from ever reaching.

# CLOSED 2026-08-15

## What an al-runner-only `lethal doctor` now prints

Real output, this machine, against a config whose only section is `alRunner`:

```
ok: every check passed
  [ok] al-runner: al-runner v2.1.2.0
  [ok] al-runner-cache: 1.3 GB across 9 BC build(s) in ...\al-runner\artifacts; 7 superseded (875.2 MB): ...

Not checked: the per-file publish ceiling (needs a generated mutation manifest) and baseline test
health (needs an actual run). ...
this config declares "alRunner" and neither "bcdev" nor "envTool", so it is an al-runner-only
project and only the two checks that mean something without a BC server were run. NOT CHECKED, and
absent rather than passing: environment status, the lease, the quarantine record, the
control-version of the deployed LethAL Control app ... and alc/altool ... A green report here says
nothing about whether a bcdev run would work.
```

## The `alc` candidate in this row's own step 1 was WRONG, and that is the finding

The row lists `alc` among the things an al-runner doctor should check, "needed for the target compile
on both backends". Checked against the code rather than assumed: `buildBackend`'s al-runner branch
RETURNS before `defaultAlToolPaths`/`resolveAlToolPaths` are reached, and `ArtifactCompiler` — the
only thing in LethAL that invokes `alc` during a run — is constructed solely on the bcdev branch.
al-runner compiles the bundle with its own compiler.

So a `tool-paths` check here would have failed configs that `lethal run --backend al-runner` accepts,
which is the doctor-stricter-than-`run` drift R21 and R34 each caught once already. `toolPaths` is
therefore ABSENT on this path, and the caveat says so alongside the four live-BC checks.

`DoctorDeps.toolPaths` became optional to allow that. The check itself is unchanged.

## What was kept absent, and why that is the whole design

`environment`, `lease`, `quarantine` and `control-version` are not reported as passing, not reported
as failing, and not reported at all. R110 is the reason and it is written into the module: the lease
check shipped once returning `"clear"` unconditionally, rendered `[ok]`, and was confidently green in
exactly the stranded-lease scenario the recovery tooling exists for. A check that cannot fail is not a
weak check, it is a false one.

The `al-runner` check earns its place by the opposite test: it CAN fail. A missing binary fails it,
and so does a v1 binary — which matters more, because this adapter's v2-only argv pointed at v1
produces wrong verdicts rather than an error. It calls `AlRunnerBackend.status()`, the same probe
`runSession` makes, rather than a second `--version` parse that could drift from it.

## Two defects found on the way, both fixed here

1. **`doctorFromCli` dropped `alRunnerCacheDir`.** R131 added the injection point to `buildDoctorDeps`
   and declared it again on `doctorFromCli`, but the spread in the middle never passed it on. So the
   seam worked in a direct `buildDoctorDeps` test and did nothing through the CLI, where a unit test
   would walk whatever multi-GB artifact cache the machine happened to hold.
2. **`runDoctor` would have reported an empty deps object as green.** `checks.every(...)` on an empty
   array is `true`, so `ok: every check passed` would print having checked nothing. Harmless while one
   dep was mandatory; reachable the moment R146 made every dep optional. It now throws. Empty-vs-empty
   agreement is this project's signature bug and this is the one command whose entire job is to say
   whether things are healthy.

## Scope note

The `al-runner` check follows the CONFIG, not a backend flag doctor does not have: a bcdev project
that ALSO declares an `alRunner` section gets it alongside the live-BC checks. A config that never
mentions al-runner gets no dep and therefore no check.

`buildDoctorDeps`'s returned `createModeCaveat` was renamed to `caveat`, because the two shapes that
produce one are mutually exclusive (a create-mode config HAS an `envTool` section; an al-runner-only
config has neither) and a field named for create mode while carrying something else would be a lie in
the name.
