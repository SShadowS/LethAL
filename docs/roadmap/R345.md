**Seen 2026-09-29 by the orchestrator**, re-running `itest:alrunner` on master after merging R-242
(al-runner v2.12.0). The `--server` leg of the `[LETHALA]` symbol set refused to start: the R149
re-probe under the session's platform-app pin reported `qualified-test-name` UNMEASURABLE,
"no readable --output-json envelope (exit 82)", and `runSession` refused. Log:
`H:/lethal-coord/tasks/R-242/orch-itest-alrunner.log`.

At the same time another session was running its own al-runner probes (two `--server` daemons,
one with `--define R318A`), sharing the same al-runner cache (`~/.cache/al-runner`, the
`ncl-shadow` engine variant) and package directories. An immediate re-run on the same tree PASSED
every leg (`orch-itest-alrunner-2.log`), and the lane's own two runs of the same branch passed.

**Not known:** what exit 82 means in al-runner 2.12.0, and whether concurrent al-runner processes
(a shared cache lock, a variant rebuild, or a port) caused it. Until measured, this is a suspected
flake, not a LethAL defect: the refusal itself was correct (the probe could not read the contract,
so the run did not guess).

**To close.** Reproduce with two concurrent al-runner sessions on this machine, read al-runner's
exit code 82, and decide: document "one al-runner session at a time" for the lanes, retry the
probe once on this exit code, or report it upstream. Until then, lanes should not run
`itest:alrunner` while another session runs al-runner.

**Second sighting, same evening.** The code lane's R-318 probe batch hit the same exit 82 at 21:16
on its `[R318A]` leg, while the orchestrator's `itest:alrunner` re-run was running. So both
failures happened with two sessions running al-runner at once, and neither side failed when running
alone. Still not measured directly.

**Record, 2026-09-30.** Exit 82 is the low byte of 0xE0434352, the .NET unhandled-exception code, as
Bun reports it (measured). The Windows event log showed 4 identical al-runner crashes on 2026-09-29
(`FileNotFoundException` for `Microsoft.Dynamics.Nav.Ncl` at `BcRuntime.EnsureApplied`, before any
test ran), two of them the sightings above. The cause, read from al-runner v2.12.0's source, is the
ncl-shadow rewrite replacing `Microsoft.Dynamics.Nav.Ncl.dll` with `File.Replace` (Win32
`ReplaceFile`) in the shared `~/.cache/al-runner/ncl-shadow` directory on every start, which briefly
leaves the name absent. Offline, a `File.Replace` loop against a concurrent opener gave 743
`FileNotFoundException` in 339 replaces. Live on 2026-09-30 from a cleaned cache: 0 failures in 90
processes over five two-process shapes. The same rewrite leaked 2,127 `~RF*.TMP` files (22.2 GB,
deleted 2026-09-30). Reported upstream as
https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/5018 and /5019. Lanes run one
al-runner session at a time (runbook). LethAL now keeps a stderr tail and names the likely cause in
the probe's unmeasurable fact (this commit). No retry and no per-session cache, by ruling.

**What closes it:** the upstream fix, then a re-run of the five shapes.

**Closed 2026-10-02 on a pinned source build (owner decision).** The fix (PR #5026, merge
`90e4fcc7`) is on upstream main but unreleased, so al-runner was built from main at `c39ad5de`
(`v2.12.0-main.c39ad5de`, `H:/al-runner-builds/c39ad5de/al-runner.exe`). The five shapes were NOT
re-run: they failed 0 times in 90 even on v2.12.0, so passing them proves nothing. The fix itself
was measured instead. The crash came from replacing `Ncl.dll` on every start, and a replace gives
the file a new NTFS file id. Over a full `itest:alrunner` on the source build (09:08:05 to
09:17:35, dozens of al-runner starts), the variant's `Ncl.dll` was written once at 09:08:25, when
the cache was built, and its file id never changed. No `~RF*.TMP` file was left. The same gate
passed with every frozen figure identical (3/12/4 on all four legs, layout 7/3/0, both symbol sets
5/4/0, CLI-default 3/16/0), on BC runtime 28.5.54151.55132 instead of 28.1. The lanes moved to
this build and the one-session-at-a-time rule is dropped (runbook). The global v2.12.0 still has
the defect.
