**Publish cost scales with INJECTED GUARD COUNT, because BC recompiles the extension server-side — and a fully instrumented real app exceeds the hosting proxy's timeout.** Measured 2026-07-27 against a hosted Continia BC 28 environment, same app, same source, same publish path, only the guard count differing: **163 guards → HTTP 200 in 28 s**; **11,777 guards → nginx `504 Gateway Time-out` at 362 s**; Continia's own uninstrumented build publishes fine. The proxy cap is real and unraisable from the client (`curl --max-time 1800` still 504s; the CLI's `--request-timeout 1800000` has no effect, and its own cut-off shows as a 301 s `The operation timed out.`), but the cap is the *constraint*, not the cost — the cost is BC recompiling every injected guard. **Three earlier framings of this entry were wrong and are corrected here**: not app SIZE (8.9 MB transfers in 2.3 s, `time_starttransfer=0.11s`), not SCHEMA work (a schema-identical ForceSync republish hit the same wall), and not the proxy alone. This makes `--only` (R41) load-bearing rather than a convenience: on a hosted environment it is what makes publishing an instrumented real app possible at all, and it caps how large a single batch may be. LethAL should size batches by guard count against a configurable publish budget, not put every mutant in one artifact. Operationally: BC keeps publishing after the proxy severs the connection, holding a tenant-wide lock (~15 s to reject while held); each failed attempt rolls the extension back; repeated interrupted attempts drove the tenant to `503 The tenant 'default' is not accessible`. So the env-tool publish path must poll for the installed version on a timeout, never blindly retry. **The cap also quarantines RUNS, not just publishes** (measured 2026-07-27): a third trial run latched `quarantined: baseline test in-flight-unknown running ContainerUniqueness_Check_FiresDuringAuthReconfiguration` and scored 0 of 138 mutants. A fenced call that outlives the proxy window returns unreadable, which is indistinguishable from "the server may still be executing it" — so the session correctly latched unsafe, refused to score anything, and wrote a durable tier quarantine needing an operator `clear-quarantine`. Two earlier runs of the identical configuration completed, so hosted DO runs are FLAKY rather than merely slow, and the exposure scales with baseline duration (1,246 tests, ~750 s of a ~1,000 s run). Narrowing the TEST set — not just the mutant set — is the lever that reduces both cost and this risk.
