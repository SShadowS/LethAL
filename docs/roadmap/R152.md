LethAL versions three machine surfaces and publishes a schema for none:

| Surface | Version constant | Where |
|---|---|---|
| The JSON report (`--out`) | `REPORT_SCHEMA_VERSION` = 2 | `report.ts` |
| The `explain` projection | `EXPLAIN_SCHEMA_VERSION` = 4 | `explain.ts` |
| The NDJSON event stream (`--progress-out`) | `STREAM_SCHEMA_VERSION` = 1 | `events.ts` |

The versioning is real and carefully reasoned: `EXPLAIN_SCHEMA_VERSION`'s own doc comment argues
which changes bump it and which do not, and `explain.test.ts` pins the leaf-path set against the
TYPE declaration so an unversioned schema change cannot ship. All of that lives inside this
repository. A consumer outside it has a version number and no artifact to check against, so it
cannot validate a file, cannot generate types, and discovers a shape change by crashing on it.

The pin makes this cheap in a way it would not be in most projects: `EXPLAIN_LEAF_PATHS` is already
asserted equal to the leaves walked out of `ExplainOutput`'s declaration, so a generated JSON Schema
has an existing mechanism to be checked against rather than needing a new one.

**Half done 2026-08-16.** `schemas/explain-v4.schema.json` and `schemas/doctor-v1.schema.json` are
published, with `schemas/README.md` stating what is covered and what is not.

The generate-or-hand-write question was decided in favour of **hand-written and pinned**, which is
the opposite of what this row first guessed. A generator makes drift impossible by construction and
is also a new piece of machinery to maintain for two documents; pinning the artifact against the
DECLARATION buys the same guarantee with a test this repository already knows how to write.
`packages/runner/tests/schemas.test.ts` asserts it three ways: schema leaf paths equal the leaves
walked out of `ExplainOutput`/`DoctorJsonOutput` in BOTH directions, every published `enum` equals
the runtime constant it copies, and a committed campaign report's projection validates against the
schema capped and uncapped. Red-checked: deleting one property from the schema reddens both the
declaration walk and the real-data check.

The validator in that test is deliberately small — type, const, enum, required, properties,
additionalProperties, items, minItems, local `$ref`. If a schema here ever needs a keyword it does
not support, add a real validator as a dependency rather than growing that function.

**Closed 2026-08-18 for the other two, by GENERATING them.** `SessionReport` walks out to 130 leaves
and the stream is a union of 20 event shapes; at that size a hand-written file is not a guarantee, it
is a second copy of the type that someone forgets. So `scripts/generate-schemas.ts` emits both from
the declarations, refusing loudly on any construct it cannot read rather than emitting an open object
that would validate anything. `--check` fails when a committed schema no longer matches the type,
which is the guarantee a generated artifact needs.

Two findings came out of doing it, both now pinned by tests:

- The small validator in `schemas.test.ts` did not implement `anyOf`, so it returned "valid" for
  EVERY document against the stream schema — this repository's signature bug, living inside the test
  that exists to prevent it. Caught because the NDJSON header line failed to fail.
- Required fields were added to the report without bumping `schemaVersion`, so the published v2
  schema rejects genuine older v2 reports. Filed as [[R157]] rather than papered over by loosening
  the schema until it agreed with everything.

Evidence: the two schema files, `schemas/README.md`, `packages/runner/tests/schemas.test.ts`.
