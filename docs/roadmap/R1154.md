Found by coord PR-251 (lethal-code, 2026-11-20). Evidence: `/coord/handoff/PR-251/` (`result.md`, `gap.txt`,
`gap-split.txt`, `overlap.txt`). Source: perf10c (`/coord/handoff/PR-217/perf10c.run.events.ndjson`).

**What misled.** Prefetch wall minus every al-runner timer summed to 6,972 lane-s, read as about 1.08 s of unexplained
work per request. Split:
- **About 5,900 lane-s is overlap.**
  - One prefetch request per lane was open about 1,990 s, from about 13.06M to 15.06M ms. Its al-runner timers explain
    only 20-32 s.
  - While it was open, the same lane finished 377-464 other requests (1,835-1,910 s of wall).
  - Each lane's summed request wall (17,287-17,972 s) exceeds the whole mutant phase (16,458 s), which is impossible for
    one-at-a-time work.
- **1,515 lane-s are requests cut at a timeout:** no timings, about 60 s each. That is real time, R1147's lever.
- **About 18 lane-s are left** (median per-request gap 1 ms).

**The rule to adopt.** Any figure that adds request walls per lane (busy lanes, gaps, "lane-s" totals in TIMING, ad hoc
sums like PR-231's and the orchestrator's) must merge each lane's request intervals (`atMs - wallMs` to `atMs`) before
adding, or report the overlap separately. Otherwise concurrent requests on one lane (two daemons of different modes)
inflate it.

**The open question (a time-boxed look in PR-251, not settled).**
- **The request's shape:** each long request went to a SECOND, rarely used daemon of its lane (`daemonRequest` 22,
  `daemonProved` 109; the lane's main daemon was at about 1,216). It held 110 whole-codeunit calls, one entry each,
  about 1,980 tests, and its sizing peak was about 2.5 GB.
- **A fixed wait:** its untimed part was IDENTICAL on all three lanes, 1,967.19 s, though the requests started at
  different times and did different work. That is a fixed-length wait, not work.
- **Ruled out:** PR-119's overlapped baseline samples (baseline fill only) and lazy proofs (`proveOnDaemon`, sent as
  `warmup`).
- **No lane time was lost,** since the lane kept scoring. But the request held that daemon's memory for about 33 minutes,
  and no window or kill-ledger order was seen held.
- **Next step:** a measure-only log of which code path sends a prefetch to a non-main daemon, and what its untimed
  1,967 s is. Then decide whether it is a lever (memory) or harmless.

**Resolved (coord PR-267, lethal-preproc, 2026-11-20).**
- **The 1,967.19 s was server1's SUSPEND,** not a wait (PR-252: kraken read the journal, 06:46:03Z-07:18:59Z).
  - perf10c's `wallMs` was then wall time, so the three requests in flight across the sleep each carried it; `atMs`
    is monotonic.
  - Their computed start (`atMs - wallMs`) moved back 1,967 s, onto hundreds of the lane's other requests. That
    explains the identical gap on all three lanes, and why the timers explained only 20-32 s.
- **There is no real overlap** (`/coord/handoff/PR-267/overlap.py`, `overlap.txt`). With those three walls reduced by
  the measured step, every lane has 0 requests starting before the previous one ended. Summed walls equal the union
  exactly: lane 0 16,603 s, lane 1 15,384 s, lane 2 15,320 s (raw: 1,839-1,912 s of "overlap" per lane).
  - So no second-daemon request stayed open, and there is no memory lever.
- **The cause is fixed at the source:** PR-252 put `wallMs` on the monotonic clock, so a sleep can no longer stretch a
  request.
- **LethAL's TIMING lane line already merges a lane's intervals** (`timing-summary.ts`, `reach`). It is now pinned by a
  red-checked test: overlapping requests on one lane count once (a plain sum turns it red). No repo script sums
  request walls per lane (`v3-timing.ts` and `simulate-lanes.ts` do not), so there is nothing else to clip.
- **The rule still stands for ad-hoc analyses:** merge each lane's intervals before adding (PR-259's `idle.py` does).
