**Why.** R778 batches many kill pairs into one entries request, so M_k runs after M_{k-1} in the same request. That
needs "each entry starts from a fresh database" to hold. It was measured per TEST for four kinds (the R-653 order
probe, edge 57f1e4f98, a tiny app) and per entry on probe apps (R-635), not on `dcdf9e821`, not on a 17-app install,
and not for non-transactional state (NumberSequence, static caches, temp files, isolated storage). The cost model
(0.5 s per request against 10 ms per entry) hints that the step between requests is heavier than the one between
entries. Evidence: `/coord/handoff/R-778/design-review.md` finding 3.

**Work.**
- Add the order probe as a gated leg of the al-runner-v3 update gate, run for every pin, so a build that stops
  isolating entries cannot become `current`.
- Extend it with a non-transactional kind (NumberSequence, a static cache, a temp file, isolated storage) and a
  SingleInstance codeunit in a dependency app.
- Ask upstream to document the per-entry reset (aldevtools/BusinessCentral.AL.Runner).
- The live check stays D1 per-mutant equality (`report-diff` IDENTICAL against the current serve report).
