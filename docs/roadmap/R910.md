Found by coord task R-908 (2026-11-10). Evidence: `/coord/handoff/R-882/S3.events.ndjson`, `/coord/handoff/R-908/`. Related: [[R69]], [[R908]], [[R909]].

**What.** The reader (`scanTestPageModel`, `testpage-scan.ts`) follows calls through the test app's own source. A test that reaches a page through dependency code is not refused and is sent to the fenced session. R-882's 3 ServiceDeclaration failures, "cause not found" there, are this:
`Sales Line.ShowItemChargeAssgnt` and `Purchase Line.ShowItemChargeAssgnt` (Base Application), and `No. Series - Impl..LookupRelatedNoSeries` (Business Foundation). Each failed with a CLR `NotSupportedException`.

**Why it matters.** On Linux BC such a test fails fast. On a Windows server, R69 measured that a page open with a realistic page can hang the fenced session, so a test the reader misses is a wedge risk there.

**To decide (coord R-910).** Whether the reader can see dependency symbols or source well enough to follow these calls, or whether the limit is named instead.

**Decided (coord R-941, 2026-11-12): a named limit, not built** (`/coord/handoff/R-941/p3/r910-decision.md`).
- **How many tests it touches.** No census can say: R-906's census counts only tests the reader refuses, and a test whose only page open
  is in dependency code is not refused. Live data: R-882's baselines (Payment Practices 36, Service Declaration 61) show 0 and 3 tests
  whose CLR `NotSupportedException` comes from a dependency page open, all three in Service Declaration
  (`SalesDocWithItemChargeApplicableForServDeclBasicPosting`, `PurchDocWithItemChargeApplicableForServDeclBasicPosting`,
  `CannotSetServDeclManuallyIfItThisNumberAlreadyExists`). R908's correction also names 3 such failures in BankDeposits' 75 tests;
  their event file is not on record, so that half is unconfirmed: 3 to 6 of 172 measured tests (1.7% to 3.5%). R-908's 95 unrefused
  control tests showed none.
- **What building it would cost.** Microsoft's packages carry their `.al` source (Base Application 8,096 files), but `scanTestPageModel`
  reads only the test app's own source by design. Following calls means parsing about 8,000 more files per run plus cross-app name
  resolution; one hop is not enough (the opens sit behind triggers and helper chains); and a transitive walk over-refuses, since the
  reader does not evaluate conditions (BankDeposits would be refused wholesale through a lookup reached from an `OnInsert`).
- **Why the stake is low now.** R911 measured `Page.RunModal` in dependency code on Windows BC 28.4: it fails fast both ways (whole
  baselines 1,745 ms and 306 ms), no hang. So a missed open costs a fast failure at baseline and the coverage of the mutants only that
  test covers, on either OS; it does not wedge a server.
- **If it is ever wanted:** the smallest useful scope is source-bearing dependencies, one hop from test code, matched against a list of
  known page-opening procedures, not a walk.
