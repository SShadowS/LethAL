title: "Schemata inserts the `MutationSelector` variable into an object's FIRST var section, which may be `protected var`, so the instrumented object exposes it to extensions"
section: "correctness-risks"

**Found 2026-10-05 under R-468** (gpt-6.1-sol's plan review, `sol-review-r1.md` and
`sol-review-r2.md` in the coord handoff `R-468`: "document and track, not dismiss").

**What.** `compile-plan.ts` adds `MutationSelector: Codeunit "Mutation Selector"` to an instrumented
codeunit or table by reusing its first existing object-level `var_section` (`existingVar`, the
first `var_section` among `declarationMembers`). It does not look at whether that section is
`protected var`. When it is, the instrumented object declares `MutationSelector` as a PROTECTED
global, which a `tableextension` (or, for a codeunit, nothing today) can see. The original object
did not declare it at all.

**How common.** R-468's census: 621 of the 704 extra object-level var sections in the BaseApp
history corpus are `protected var`, and the usual shape is `protected var` FIRST, then `var`.
Tables carry 74 of the 690 multi-section objects; how many tables have a `protected var` as their
FIRST section was not counted.

**What it could cost.** Unmeasured. An extension that already declares a member named
`MutationSelector`, or reads the base table's protected globals by name, could fail to compile or
bind differently against the instrumented build. A real project will almost never use that name,
so the realistic cost is small, but it is a change to the extension-visible surface of the
instrumented object, which instrumentation should not make. It compiles today on every fixture.

**To close.** Measure first: on BaseApp and CDO, count instrumented tables and codeunits whose
first var section is `protected var`. Then either insert into the first NON-protected section (a
fresh `var` section if there is none) or rule that the exposure is acceptable, with an `alc` probe
of a tableextension against such a table either way.
