## What breaks, and for whom

LethAL emits `report-v2`, `explain-v4`, `doctor-v1` and `stream-v1`, all of its own design, and
**nothing any CI system can render**. A user who runs it in a pipeline gets a JSON file and a console
score. There is no build tab, no trend, and no way for a reviewer to click a survivor and see the
mutated line, which is how mutation testing is actually read.

## Azure DevOps specifically, since that is where the question came from

There is **no native mutation-testing result type**. Two routes exist and only one of them is honest:

1. **The report tab.** The Stryker team maintain [`PublishMutationReport@1`](https://marketplace.visualstudio.com/items?itemName=stryker-mutator.mutation-report-publisher),
   which adds a tab to the build result rendering an HTML mutation report, and can break the build
   below a minimum score. It is FRAMEWORK-AGNOSTIC: it renders whatever HTML it is pointed at.
2. **The Tests tab.** `PublishTestResults@2` takes JUnit/NUnit/VSTest/xUnit, and a mutant can be
   forced into a `<testcase>` with killed=pass and survived=failure. **Do not do this.** A survivor
   is a FINDING, not a broken build; the tab adds flakiness tracking, ownership and duration history
   that mean nothing for a mutant; and mutation scores move for honest reasons, so it would redden
   builds when the code improved. It renders, which is not the same as being right.

Route 1 needs the `mutation-testing-report-schema` JSON, which `mutation-testing-elements` turns into
the HTML. The same file feeds the Stryker dashboard and the GitLab/GitHub renderers, so one exporter
buys every ecosystem at once.

## The spike, and what it proved

`scripts/export-mutation-elements.ts <report.json> --project <dir> [--out] [--html]`.

Run against the real `itest:tables` report, 345 mutants over 26 files:

- **VALID** against the official `mutation-testing-report-schema@3.9.0`, checked with the schema
  shipped in that package rather than a transcription of it.
- Statuses round-trip exactly: **267 Killed / 63 Survived / 15 NoCoverage**, which is the frozen gate.
- Every mutant's `location` lands inside its file, computed from `startIndex`/`endIndex` against the
  source rather than from the report's `line` alone (the schema needs start AND end, line AND column).
- `--html` writes a **self-contained** 433 KB report with the renderer INLINED. A CDN reference was
  rejected deliberately: a build agent may have no egress, and a report that renders blank on a
  locked-down agent is worse than one never produced.

All six LethAL verdicts map: `killed`/`survived`/`no-coverage`/`timeout-killed`/`error` go to
`Killed`/`Survived`/`NoCoverage`/`Timeout`/`RuntimeError`, and an unmapped verdict THROWS rather than
landing on `Pending`, which would read as "not yet run".

## Why it is not a CLI reporter yet: the projection is lossy in the one way that matters

The schema carries one `status` per mutant and has no room for the qualifications this project spent
months earning. Measured on that same report, the exporter printed:

- **2 mutants that R175 reports as attribution-unplaceable flatten into `NoCoverage`.** That is
  precisely the conflation R175 exists to prevent: `NoCoverage` reads as "your tests do not reach
  this code", and for those two it is a statement about LethAL's attribution instead.
- 2 kills screened as platform artifacts ([[R138]]) become ordinary kills.
- R121's assertion-screen discrimination (`partial` here) has no equivalent.
- 330 mutants carry a `coverageAttribution` (`exact` / `object` / `all-green`) the schema cannot
  express, so an APPROXIMATE covering set renders as an exact one.
- [[R172]]'s likely-equivalent survivors lose their flag.

The exporter prints all of this on every run rather than projecting silently, because a silent
projection is how a qualified verdict becomes an unqualified one, which is exactly what R175 was.

## The decision this needs before shipping

Not "should we export" but **what a lossy export is allowed to claim**. Options, none chosen:

1. **Export and warn**, as the spike does. Cheapest, and the warning is on the console where CI eats
   it.
2. **Carry the qualifications into the HTML.** The schema has no field, but `MutantResult` has an
   optional `description`, and R175's unplaceable mutants and R172's flagged survivors could say so
   there. It survives into the rendered tab, which is where a reader actually looks.
3. **Refuse to export an unplaceable mutant as `NoCoverage`** and emit `Ignored` instead, which at
   least does not blame the suite. It also under-reports, and `Ignored` means something else.

Option 2 looks right and is not much more work. It should be measured against a rendered report
rather than reasoned about, which needs the browser step the spike could not run.

## Also unresolved

**Source is embedded.** `FileResult.source` is REQUIRED, because the HTML highlights the mutated
span. Against a project's own code in its own pipeline that is fine and necessary; it is also exactly
what the 2026-08-09 redaction ruling forbids publishing for a third party. A shipped reporter needs
the same guard `scripts/redact-campaign-report.ts` applies, or a loud refusal, before anyone points
it at a report bound for a public repository.

**`thresholds` is required and is not a LethAL concept.** Nothing in `lethal.config.json` sets a
mutation-score threshold. The spike writes the ecosystem's conventional 80/60 and says so; a shipped
reporter should make it configurable rather than inherit a number nobody chose.
