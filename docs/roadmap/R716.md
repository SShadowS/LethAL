**Filed 2026-10-24 by lethal-code (coord task R-714).** A recurring verify flake: "R565: a NULL dependency digest
(a row from before R565), same source, twins: history carries nothing" timed out at 5 s on full verifies, and was
green on re-run each time: 2026-10-23 15:27Z (6,640 ms, `/work/lethal`) and 2026-10-24 09:38Z (6,350 ms, the R-317
merge verify).

**Why it took 6 s.** Not the test's own work: the whole file runs in about 1 s alone (17 tests, 1,058 ms; the
test itself is two small `runSession`s). The cause is where its database lived. `project()` in the test file set
`dbPath` to `join(root, "lethal.sqlite")`, a folder on the real disk, and the NULL-digest test and the
"NULL columns" test open a file-backed `ResultsStore` there (they need a second connection to null a column).
R616 moved every other file-backed test store to the tmpfs folder (`testDbPath`), because `fsync` waits on the
shared disk took seconds under other jobs' writes; this file was missed. The verify ledger
(`/coord/locks/verify-ledger.tsv`) shows disk pressure at both failures (io "full" avg60 6.23 and 2.05) and CPU
pressure near zero ("full" 0.00, "some" avg60 0.16 and 0.81).

**Fix.** `project()` takes `dbPath` from `testDbPath("lethal.sqlite")` (the preload's per-worker tmpfs folder).
The other test files that name a `lethal.sqlite` only build path strings and open nothing. No timeout was raised.

**R616's pressure gate and CPU.** Not changed. CPU pressure was near zero at both failures, so a CPU term would not
have raised the timeout; the disk term already in the gate (io "full" avg10 at least 5) reads the right resource,
and the failures here sat below it because the test's own `fsync` was the bottleneck, which this fix removes.

**Red check.** None: no logic changed (a test fixture's path). The file passes (17 of 17) from the tmpfs path.
