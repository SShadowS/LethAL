**Seen once, 2026-09-26, on Cronus28 the day it was set up.** The first `itest:tables` run on
`lethal/lane-code` (`da35dd8`) scored nothing: 0 killed, 0 survived, 0 no-coverage, with
`quarantined: "baseline test in-flight-unknown running PageActionComputesNonZero"`. That test opens
a `TestPage`, which the fenced session normally refuses at once, so the gate expects exactly ONE
named baseline FAILURE there. Straight after, master (`5420201`) passed on the same container, and
a rerun of the same branch passed too, both at the frozen 299 / 63 / 15. The quarantine went to
the gate's scratch directory, so no durable quarantine was left behind.

What is not known: whether a cold container (the first TestPage open after setup) makes that
call outlast its baseline budget, or something else stranded it. One occurrence is not a rate.
If it recurs, capture the `--progress-out` stream and the control app's op log for that call.
The cost when it happens is high: an in-flight-unknown baseline quarantines the whole session,
which looks like a total regression in a gate.

**Superseded hypothesis (review r1).** The cold-container/budget account above, that the call runs
long enough to lose to its own timer, is contradicted by stored evidence: run 339 died at 29.5 s on
a socket close, far under the 120 s baseline budget (`BASELINE_TIMEOUT_DEFAULT`), so the timer is not
a universal explanation. It is not ruled out either: every hit recorded since fails AFTER headers
arrive, and six of the Cronus284 hits then ended at the 120 s client timeout while the body read
stalled. What is superseded is "the call is simply slow on a cold container"; timer expiry after a
stalled body remains part of what was observed. Kept for history.

**Recurred 2026-09-26, three times in one afternoon, on control app 1.0.0.19 (merged GH-24 tree `5b9e12a`).**
Same quarantine reason each time. (1) `itest:chunked`'s control leg scored 0 / 0 / 0 while its chunked leg,
straight after, passed at 17 / 7 / 2. (2) After an NST restart (`/recover-tier`), `itest:hang` passed, then
`itest:chunked`'s control leg quarantined again. (3) `itest:tables` straight after that chunked run quarantined
too, although the chunked leg in between had opened the same TestPage without trouble. So it is NOT only the
first TestPage open after a cold start. The GH-24 lane saw it twice more on the same build, each passing on
retry. The failure existed before GH-24: R225 measured it on 1.0.0.18. Whether GH-24 changed its rate remains unresolved (see below). Each occurrence is a real cost for
acceptance gates regardless of its rate: it throws away a full gate run. Whether the RATE itself has changed
is narrower than that: the only contrast this cycle measured, the client at HEAD against the client at
`7b7fff3` (A vs B', both on control app 1.0.0.19), does not show an increase (one-sided Fisher p = 0.6646; see
the Phase A read-out below). The app-only contrast (control app 1.0.0.18 vs 1.0.0.19, client held fixed) and
the combined contrast were not measured this cycle, so neither is ruled in or out as a cause of a rate change.

**Measured 2026-09-26 (Phase A read-out, Cronus284, control app 1.0.0.19).** Pre-commitment and full
read-out: `docs/superpowers/specs/2026-09-26-r236-rate-precommitment.md`, section OUTCOME. Status stays open.
- Rate: the HEAD client (A) hit **3 of 30** counted sessions, the client at `7b7fff3` (B') **3 of 30**. One-sided
  Fisher p = 0.6646: this measurement does not show an increase from the client commits since `7b7fff3`. No
  drift (A1 vs A2 p = 1.0, B'1 vs B'2 p = 0.2241), no short arm. The app-only and combined contrasts (arm B, on
  1.0.0.18) were not run.
- Warm-up sessions (the first two on the container, and the first after a restart) hit **2 of 3**, against
  6 of 60 counted. The pre-arm smokes on Cronus28 hit 6 of 7. Why the two containers differ is not known.
- Where it breaks: all 8 broken calls (6 counted, 2 warm-up) are the TestPage call `PageActionComputesNonZero`,
  and no other call errored. Each is a truncated reply: status 200, chunked, no `Content-Length`, most of the
  body, then either the client's 120 s timer (6) or a socket close near 28 to 31 s (2). Every hit's headers came
  after 600 ms; every clean answer's by 543 ms. In 7 of 8 the server's own op record says the fence finished
  (`done`); the 8th could not be read (both status reads timed out while BC logged OData throttling, event 705).
- The missing part is the END of the answer: 73 to 116 bytes in the timer cases, one byte (the envelope's final
  `}`) in the socket-close cases. None of the cuts falls inside the CLR callstack text.
- The pre-committed truncation decision (D6) did not hold: two offsets (6616 and 6642) are not below the
  smallest clean answer (6616), and clean answers differ from one another outside the mask (`artifactId`,
  `startTime`, `finishTime`). So it does not show on which side the bytes were lost.
- Mechanism: inconclusive. Cronus284's session control was `not determinable`, so no hit's whole-action end is
  proven, and no fix is licensed by this cycle.
- Wedges: 1 of 8 hits followed by a preflight left the container unable to answer `HarnessInfo` and needed a
  restart.

**R-236b fix landed 2026-09-27 (kept-answer readback), acceptance MEASURED-PARTIAL; this item stays
open.** Commits `3abee88..43f8e01` (interleaved with an unrelated GH-06 merge): the mechanism is
control app 1.0.0.20 saving each answer that ran, committed as the action's last statement; a new
read-only `GetOpAnswer` action returns it only to the exact caller identity (`attemptId`, `opSeq`,
`epoch`, `generation`); the client, on any `in-flight-unknown` exit, reads it back once, bounded, and
accepts only an identity-checked `pass`/`fail` with no `operation`. Everything else, a refusal,
`lease-lost`, malformed, partial, `found: false`, keeps today's path unchanged. The grouped path
(`RunMutantMany`) got the same treatment. Full mechanism, every ruling and the acceptance rules:
`docs/superpowers/specs/2026-09-27-r236b-reply-fix-precommitment.md`.
