Coverage attribution has two paths, and they disagree about what to do when an object's only covering
tests fail at baseline.

The member-level path DECLINES. A mutant whose covering tests are all non-green is recorded
`no-coverage` (or `error` with a note naming the red test), which is honest: we cannot know.

The trigger path does not decline. When a table trigger mutant cannot be coverage-matched, FALLBACK 2
runs it against every green test instead, and whatever comes back is scored. If the object's only
covering test is the red one, the green set by construction excludes every test that could kill the
mutant, so the mutant reliably comes back `survived`.

**Measured 2026-08-13.** One root cause (a stale primary key in a fixture loop, see the measurements
index) made a single test red at baseline. That one failure produced two different reporting outcomes
from the same underlying ignorance:

- five mutants in a PROCEDURE recorded `error`, each with the note `unsupported test type: mutant
  covered only by test(s) that did not pass at baseline`, naming the red test. Correct and legible.
- two mutants in that table's `OnInsert` TRIGGER recorded `survived`, via FALLBACK 2, against a green
  set that excluded the only test able to kill them. Both had been pre-committed `killed`, and the
  pre-commitment was right; the observation simply did not test it.

Why this matters more than an ordinary attribution gap: **`survived` is a finding, not a neutral
result.** A user reads it as "your suite executes this line and does not catch this mutation", which is
exactly the claim a campaign is bought to make. A false `survived` therefore does not merely lose
information the way `no-coverage` does, it manufactures a defect report against the user's tests. It
is also silent: nothing in the record distinguishes a `survived` earned against a covering test from
one scored against a set that could never kill the mutant.

What this row asks for:

1. FALLBACK 2 should DECLINE, the way member-level attribution already does, when every test that
   covers the mutant's object is non-green. `no-coverage` under the existing `baseline-red` caveat is
   the honest answer.
2. If declining is judged too blunt, then at minimum the verdict must carry a caveat naming the
   condition, so a `survived` produced this way is never readable as an ordinary survivor.
3. Either way, `untargetedTriggerCount` already counts the mutants that took this path. It was 2 on
   the measured run. The tally exists; the verdicts it covers are what need the treatment.

Related: R55 records the general rule that tests failing at baseline are dropped from the green set and
mutants covered only by them become non-findings. This row is the narrower case where the same
condition produces a WRONG finding rather than a lost one.

## Decision (2026-08-14): fallback 2 DECLINES

Option 1, the row's own preference, and after reading the code the second option is worse than the
row allowed for. A caveat attached to a `survived` verdict leaves the mutant counted as a survivor in
`mutationScore`, so the headline number keeps the false finding and only the prose disowns it. The
whole reason `error` and `no-coverage` exist is that a mutant nobody could have killed does not
belong in the score at all. Declining also adds no new concept: it is the answer the member-level
path already gives to the identical question, which is what made the disagreement a defect rather
than a design.

How it is wired:

- `coverageFilter` takes an optional fourth argument, the coverage index built from the baseline
  tests that did NOT pass. It is consulted at exactly one place, fallback 2, and only to distinguish
  "nobody has ever seen this object execute" from "the only test that sees it is the red one". The
  lookup is `byObject` on the (objectType, objectId) PAIR, the same key fallback 1 uses, so a red
  test covering `codeunit 99999` can never decline a `table 99999` trigger (R70's collision shape).
- The orchestrator now builds that index BEFORE the split rather than after, and hands the same
  object to both consumers, so the split and `unsupportedCoverage` cannot end up reasoning from
  different evidence.
- A declined mutant falls into `uncovered` and takes the pre-existing path from there. In practice
  that path always resolves it: we declined precisely because the non-green index holds its object
  key, so `unsupportedCoverage`'s fallback 1 finds it, and the mutant is recorded `error` with the
  note naming the red test. That is strictly better than the bare `no-coverage` this row asked for
  as a floor — the reader is told which test could not run, not merely that something could not be
  measured.
- `untargetedTriggerCount` now counts only mutants actually RUN untargeted. A declined mutant was
  not run, so claiming it under that tally would have been a second small lie.

Evidence, red-checked: with the decline disabled, `orchestrator.test.ts`'s R140 case fails with
`Expected: "error" / Received: "survived"` — the manufactured finding, reproduced on demand. The
unit case in `selection.test.ts` fails alongside it. Four sibling unit cases pass with the fix
disabled AND enabled, deliberately: they hold the genuine fallback-2 path, the object-type
discrimination, the precise-attribution path and the omitted-argument path unchanged, so the fix
cannot pass by simply switching fallback 2 off.

Live, 2026-08-14: `itest:tables` PASS at killed **191** / survived **31** / no-coverage **10** over
232 deployed, score 0.8603603603603603, `untargetedTriggerCount` **0**, and the per-mutant baseline
file was not touched by the run. Unchanged in every figure, which is what this gate was asked to
prove. It was expected to be UNCHANGED — 191/31/10, `untargetedTriggerCount` 0 — because
that fixture takes fallback 2 for nobody. The gate's job here was to prove the change is a no-op on
healthy attribution, not to demonstrate the fix. Deliberately NOT demonstrated live: the tables gate
asserts exactly one permitted baseline failure by name, and making a second fixture test red to show
the fixed behaviour would gut that assertion. A live demonstration is possible but needs its own
fixture and its own gate; it is not worth a second permitted red test on this one.
