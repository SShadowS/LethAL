Found by coord task PR-15 ([[R1032]], `docs/campaign/2026-11-15-pr15-1753-dates/`). Evidence:
`/coord/handoff/PR-15/rerun/18*` and `cfg/v3.18*.json`. Related: [[R1008]], upstream aldevtools/BusinessCentral.AL.Runner#8002.

**What was measured.** Sustainability (R-925 `sus`, 526 tests), the whole baseline by `scripts/triage-baseline.ts`, configs pinned:

| build | cacheDir | green | refused | "changed number sequence" refusals |
|---|---|---|---|---|
| edge-a184cfc79 | unknown (PR-05) | 356 | 156 | 41 |
| edge-a184cfc79 | warm | 393 | 119 | 0 |
| edge-5a58a0f16 | new (first use) | 318 | 194 | 89 |
| edge-5a58a0f16 | warm | 393 | 119 | 0 |
| edge-5a58a0f16 | new, empty | 273 | 246 | 148 |

The two warm runs, one per build, are identical test by test. The refusal is al-runner's "an earlier test of this codeunit, <test>,
changed number sequence <x> that existed before it" (#8002, open in the refusal ledger). Every run on a cold cache cascaded, and
every run on a warm one did not. That is a correlation over four runs whose cache state is known, not a mechanism.

**Why it matters.** A project's first window on a new cacheDir measures a smaller green set. Mutants that only the lost tests cover
become `no-coverage`, and a comparison with a warm run shows moves that no code change caused. PR-15 first read 38 of these tests as a
5a58a0f16 change. It is also a case where one build gives two different baselines on the same inputs ([[R1008]]'s successor PR-21
re-checks a reused baseline for this reason).

**To close:**
- find which part of the cold cache matters (the install baseline, the compiled packages, or timing);
- reduce it to an invented repro and comment on #8002, or file a new issue;
- until then, warn when a session starts on an empty cacheDir, or warm the cache before the baseline.
