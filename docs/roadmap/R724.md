**Found in coord task R-327b (2026-10-24).** `scripts/corpus-snapshot.ts` maps every `RefusedError` to exit 2
(`process.exit(e instanceof RefusedError ? 2 : 1)`). That covers two different kinds of refusal:
- **Transient:** the heavy-job guard ("at most three heavy jobs container-wide", R642). Retrying later is right.
- **Permanent until the caller acts:** "no master entry for <merge-base> with dumper <key> … Run `snapshot <set>
  --master` first", an unknown set, error projects, "zero keys on both sides", and a non-legacy entry. Retrying never
  helps.

**What it cost.** R-327b's retry loop (`until rc != 2`) waited for a heavy slot correctly. Then master moved under the
branch (R-586c touched a generation-path file), the diff's master side had no entry, and the loop retried that
refusal every two minutes for about three hours. It appended the same "no master entry" line each time, until the
orchestrator noticed. Any lane that writes the obvious loop has the same trap.

**To fix.** Give the heavy-guard refusal its own exit code (for example 75, which the tool already passes to
`flock -n -E 75` internally), or print a fixed machine-readable prefix on it. Then pin, in
`scripts/corpus-snapshot.test.ts`, that the guard refusal and a missing master entry exit differently. Update the
header's "Exit codes" line, and the `repo-scripts` skill if it shows a retry loop.
