**LethAL could supply its OWN test runner, which would move mutant activation and attestation INSIDE the test session — the thing that currently makes the hub unable to carry a verdict at all.** Today `LC Run Method` calls `Test Suite Mgt.RunAllTests`, driving Microsoft's DEFAULT runner, so activation must happen OUTSIDE the test session. Three consequences, all verified in code 2026-08-01: `runOnHub` (`bcdev-backend.ts:771`) never reads `pendingMutantId`, so routing mutants to `coverageMode: "procedure"` today would run UNMUTATED code and report **100% silent false survivors** with no error; `WriteActive` is `local` by construction so any hybrid needs a new persistent-activate action whose committed row outlives the session with no clear path; and attestation (`ObservedAny`/`ObservedIdentityMismatch`) lives in a SingleInstance codeunit — session-local memory — so a hub session's `Expected*` is blank and an OData readback lands on a different pooled session. Nothing compared to nothing. **A custom `Subtype = TestRunner` codeunit runs INSIDE the test session**, so it could activate in `OnBeforeTestRun` and read attestation in `OnAfterTestRun`, in the same session as the test, on ANY transport — which would make the fence's same-session co-location a property LethAL owns rather than a property of one OData action. **FEASIBILITY MEASURED 2026-08-01 (`docs/measurements/r77-custom-testrunner-probe.al`), offline alc against the EXISTING symbol set (sole dependency Microsoft `Test Runner`): COMPILES CLEAN.** `Subtype = TestRunner` with `OnBeforeTestRun`/`OnAfterTestRun` is accepted, and `Record "AL Test Suite"."Test Runner Id"` is settable — note the guessed name `"Test Runner Codeunit ID"` does NOT exist and alc rejected it; the real field came out of the Test Runner symbol package, which also exposes `Test Suite Mgt.ChangeTestRunner`/`GetDefaultTestRunner`/`GetCodeIsolationTestRunner`/`GetIsolationDisabledTestRunner`. **NOT established, and each can still kill it:** (1) whether `bcdev_test_run` runs a suite LethAL controls or builds its own — if the hub never uses our suite, our runner never loads and none of this reaches the hub, which is the whole point; (2) whether `OnBeforeTestRun` runs inside per-test isolation and what that does to a write (in-memory SingleInstance state is not transactional and should survive, and the in-memory half is the half activation needs — but "should" is reasoning, not measurement); (3) whether replacing the runner changes isolation semantics, which would MOVE VERDICTS and must be gated on a per-mutant join against all four frozen gates; (4) `TestPermissions` interaction. **Why this outranks wiring R69's routed path:** it attacks the root constraint rather than routing around it, and it is transport-agnostic — it would serve fenced, hub and client-services alike. Entry criterion: answer (1) first, because it is cheap and it gates everything else.
