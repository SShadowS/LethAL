## Decided 2026-08-08 — refused, and this is the whole reasoning

R77's own research is excellent and none of it is disputed here. What changed is that the two
surviving deliverables were re-read against what LethAL actually does, and both turn out to buy
nothing.

### 1. `TestIsolation = Function` is unobservable to LethAL

The stated prize, from `design.md` §6.2: "a test codeunit whose methods share intra-codeunit DB
state could, under Codeunit isolation, let one method's writes reach the next". True of the platform
in general. **It cannot happen here, because LethAL never runs two test methods in one suite
execution.**

- `LC Run Method.RunOneMethod` builds a fresh `AL Test Suite`, selects EXACTLY the one named method,
  and fails closed unless exactly one matches. Its own doc comment says so and the code does it.
- `run-mutant-transport.ts` sends a single `testMethod` on every `RunMutant` call. There is no call
  shape that names two.
- That is true of the BASELINE as well as of mutants: the baseline is a loop of one-method calls,
  which is why a 1,311-test baseline costs 742 s rather than one suite run.
- Corroborated live on 2026-08-08 by an unrelated probe's callstack:
  `Test Suite Mgt.RunAllTests` sits directly under `LC Run Method.RunOneMethod`, for one method.

With one method per suite execution the codeunit-isolation boundary and the method boundary are the
same boundary. Function isolation would change nothing that LethAL can observe, so building a custom
runner to obtain it is work with no measurable effect.

**And if it were applied anyway it would be actively harmful.** Function isolation is STRICTER than
the platform default. A target project whose suite passes in VS Code but happens to carry an
order-dependent test would go RED at baseline under LethAL's runner and green everywhere else.
R55 measured what baseline-red then does: those tests drop out of the green set and every mutant
covered only by them is recorded `no-coverage` rather than `survived` — real survivors converted
into non-findings. LethAL's job is to measure the user's suite as the user runs it, and a knob that
manufactures baseline failures degrades the measurement on exactly the suites that have the problem
it claims to fix.

The al-runner backend does not rescue the idea either: it has no `AL Test Suite` and no
`Test Runner Id`, so the mechanism does not exist there at all.

### 2. Moving activation and attestation into `OnBeforeTestRun`/`OnAfterTestRun` has lost its
beneficiary

The row's case was that a subscriber "fires inside the same session as the test on ANY stack-1
transport (fenced OData and the client-services batch loop alike)", and that it "may simplify R74's
fix rather than merely enabling it".

Both of those are about a path that no longer exists. R69 closed with the recovery measured at 2.30%
of a real app's mutants, and `batch-transport.ts`, `testpage-router.ts` and the routed orchestrator
helpers were DELETED (`c1da575`). R74 is MOOT for the same reason. What remains is the fenced path,
where activation and attestation already happen in the same session as the test — that co-location
is what the fence is, and it is what every verdict this tool issues already rests on.

So the change would move working, gated, same-session wiring into a different mechanism with the
same guarantee, and the gate for it would be a per-mutant join across all four frozen gates because
changing the runner can move verdicts. Cost with a real downside, benefit of zero.

### What would reopen this

One fact, and it is checkable rather than a matter of taste: **LethAL running more than one test
method per session.** If a future cost optimisation batches several methods into one suite execution
— which is plausible, since the baseline's 742 s is a loop of 1,311 single-method calls — then
intra-codeunit leakage becomes reachable, Function isolation becomes observable, and this decision
must be retaken. Note the trade in that direction is not free either: batching is exactly what would
introduce the leakage the custom runner would then be needed to prevent.

Nothing else here is superseded. The hub findings, the two-execution-stack architecture read, and
the BCApps source pointer (`U:/Git/DO.Support-SlowDOSetup/BC`, `w1-28.0.46665.48549`, the same build
as our containers) are all still true and still worth keeping.
