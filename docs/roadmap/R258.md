---
id: "R258"
title: "lethal verify cannot see an edited test that did not cover the mutant, because a test is new only by identity against the source run's baseline"
section: "product-gaps"
status: "open"
order: 962
---

**What.** `planVerify` decides which tests are new by comparing against `sourceBaseline`, the
covering set `baselineTests` recorded for the source run. That comparison is by test identity
(codeunit and method), not by test body. If someone edits an EXISTING covering test's assertions
so it would now actually exercise a survivor's mutated line, `lethal verify` still classifies it as
an old covering test, never a new one, so its stronger new-test checks (the double freshness-checked
unmutated run, the flakiness gate) never run against it.

**Why it is not simply widened.** `alc`'s own output is not deterministic enough to diff test bodies
reliably; C02-05 Task 0 measured this (see `docs/measurements/README.md`). A hash-of-source check
for "did this test change" would need the same non-determinism worked around that source hashing
already works around for the target project, and nothing here does that for individual test methods
yet.

**Evidence.** `planVerify`, `baselineTests` (`packages/runner/src/verify.ts`), and C02-05 Task 0's
`alc` non-determinism measurement in `docs/measurements/README.md`.

**What would close it.** A per-test identity that also changes when the test body changes (a hash of
the test method's own source, computed the same tolerant way source hashing is), recorded alongside
the source baseline and compared at verify time.
