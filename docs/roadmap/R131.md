**`--auto-provision` resolves the project's BC version by PREFIX to the latest matching Microsoft
build, so the cache gains a directory rather than reusing one.** Measured 2026-08-09 on al-runner
2.1.1.0; the runner's own line is `[provision] Resolving BC version prefix '28.0'... Resolved:
28.0 -> 28.0.46665.53508`.

This machine's cache, after a handful of gate runs over a few days:

```
~/.local/share/al-runner/artifacts/28.0.46665.53459/   platform-apps + test-apps   ~137 MB
~/.local/share/al-runner/artifacts/28.0.46665.53492/   platform-apps + test-apps   ~137 MB
~/.local/share/al-runner/artifacts/28.0.46665.53508/   platform-apps + test-apps   ~137 MB
~/.local/share/al-runner/artifacts/28.1.49838.50794/   engine DLLs + test-apps     ~358 MB
```

Three directories for one project. Only the newest is ever selected again, because the prefix always
resolves forward. Microsoft publishes 28.0 builds regularly, so this grows without bound on any
machine that keeps running al-runner gates.

**Two consequences, and the second is the one that matters.**

1. **Disk.** ~137 MB per upstream publish, forever, on every developer and CI machine that uses the
   al-runner backend.
2. **Every "warm cache" claim in this repo has a shelf life.** R125's and R128's measurements, and
   the frozen `itest:alrunner` timings, were all taken on a cache that was warm FOR THE BUILD CURRENT
   AT THE TIME. The first run after an upstream publish is a cold run again. R128's one-time
   provisioning step is what keeps that cost off a mutant's clock; nothing keeps it off the wall
   clock.

**Not fixed, and the reason is that it is not obviously ours.** Deleting artifact directories LethAL
did not create, out of a cache al-runner owns, is a destructive operation on shared state — another
tool on the machine may be pinned to one of them with `--bc-version`. The honest options are (a) ask
upstream for a retention policy or a `--prune`, (b) have `lethal doctor` REPORT the size and the
stale directories without touching them, or (c) do nothing and let the operator decide. (b) is cheap
and is the only one of the three that cannot be wrong.

Filed 2026-08-09 out of R128's measurement, so the growth is tracked rather than discovered again by
someone wondering where their disk went.
