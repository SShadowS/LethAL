Found by coord task R-902 (Intrastat Core on v3, 2026-11-10). Evidence: `/coord/handoff/R-902/ist.stderr.txt`,
`ist.events.ndjson`, `run.log` (exit 124 at the 6 h cap). Related: [[R890]] (why a mutant runs whole codeunits), [[R897]] (the cut at
a streamed timeout).

**Measured.** 3,301 mutants; baseline 97 of 111 green in 104 s; coverage split 2,308 covered and 993 no-coverage. The 993 were
recorded at 12:26. Then nothing: no line on stdout or stderr, no event, for 6.3 hours. al-runner's serve daemon ran at 80-99% CPU and
grew to 10 GB resident. The run hit the 6 h cap with no report, so even the 993 recorded verdicts reached no report.

**Why, from the code (not measured inside al-runner).**
- All 111 tests are in one codeunit. On serve-entries a mutant runs each covering codeunit WHOLE, by design (codeunit-level setup
  must behave as on BC, R890). So each covered mutant costs about the baseline's 104 s.
- A prefetch request holds up to `ENTRIES_CHUNK_CAP` (256) units: about 128 one-codeunit mutants here, so about 3.7 h or more per
  request, and about 67 h or more for the 2,308.
- Its outer bound, `v3CallDeadlineMs`, is 10 x stop seconds x every test in the request + 90 s, capped at `MAX_TIMER_MS` (about 25
  days). R897's cut fires only on a streamed timeout row. So nothing bounds a request that is simply long.
- A prefetched answer is used only when the whole request returns, so no mutant past the coverage split is scored while it runs.

Whether al-runner was slow or stuck is not known: the daemon's stderr is not kept. The first request had not returned after 6.3 h,
against about 3.7 h predicted from the baseline.

**To do (cheap first).**
1. Before the mutant phase, print an estimate from the baseline: covered mutants x covering codeunits' baseline time, and say when it
   is above some hours.
2. Show progress while a prefetch request runs: rows stream (R897), so count them.
3. Size prefetch requests by estimated time, not only by units, so a long request cannot hold the run for hours.
4. On a cap or a stop, write the report with what is known.

**Built (a6cbc276, review fixes 6d73834f).** Cause correction: auto isolation chose `method` for Intrastat's test codeunit, so one mutant costs at most about
36 s. What lost the run was the loop awaiting one prefetch for ALL 2,308 covered mutants before scoring any. Now both mutant loops
prefetch and score in windows of at most 600 s of estimated covering-test time (and the entry cap; a mutant over it goes alone), so a stop
loses one window. `--time-budget <seconds>` stops scheduling before each window and each live mutant (`--workers`: between windows only),
leaves unreached mutants out of the report with the `time-budget-reached` caveat and `timeBudget` field, keeps the run unfinished so
`--resume` continues it, and clamps only prefetch deadlines. The estimate is in the mutants phase `detail`, with a warning over 2 h.
Step 4 (a smaller per-mutant test set, such as `method` on a tie) can change verdicts and needs a ruling and a pre-commitment.
Review fixes: a prefetch's batch refusal is decided with the batch's group count and the 256-entry chunk its requests fill (request
make-up already decided it at the 256-entry cap before windows), so windows decide it as one whole-batch prefetch does; the one
remaining difference is a window that is wholly refused while a later window of the same chunk would have run, which stops the
session where one chunk would not. The section-G gate counts only covered mutants that ran when the budget stopped the session, so a
planned stop is no quarantine (a mutant that ran un-attested still trips it). The budget is rechecked after a window's prefetch. The
stop is reported only when something is left out, with `batchesNotStarted`. A budget stop exits 7. Named limit: under `--workers` the
budget is checked between windows only.
