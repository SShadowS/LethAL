**Measured 2026-09-03, al-runner v2.10.0.0.** `al-runner provision fixtures/sandbox-tests` reported
`BC 28.1.49838.54169 engine artifacts already complete` and then fetched the Microsoft test toolkit
INTO `artifacts/28.1.49838.54169/test-apps`, the binary's own build. The same day `itest:alrunner`
(3 / 16 / 0, all 19 verdicts identical, PASS) pinned `platformAppsDir` at
`artifacts/28.1.49838.54169/platform-apps`, the SAME build. On 2.7.0.0 those were different
directories (`test toolkit already present at .../28.1.49838.50794/test-apps` from the subcommand
while the run resolved the platform apps to `28.0.46665.53952`), and that difference is the whole
reason `provisionOnce` (`packages/runner/src/al-runner-backend.ts`, R128) runs the test bundle
through `--auto-provision` instead of calling `provision`.

**What is and is not established.** The subcommand now fills the directory the run reads from, on
THIS fixture (which declares no `application` version in `app.json`, so both paths may simply be
falling back to the binary's build). Not measured: a project that declares `"application": "28.0"`,
where the run's platform-app resolution followed the project prefix on 2.1.1.0 and 2.7.0.0. Until
that shape is measured on 2.10.0.0, the note in `provisionOnce` is historically accurate and
present-tense wrong, and the code keeps working either way because `--auto-provision` is on by
default. `docs/measurements/README.md` §"al-runner v2" records the 2.10.0.0 re-verification.

**To close:** measure `provision` against a bundle that declares a 28.0 application version; if the
run and the subcommand agree there too, replace `provisionOnce`'s `--auto-provision` warm-up with
`al-runner provision <testDir>` (bounded exactly as today) and re-freeze nothing, since no verdict
depends on it. If they still disagree, update the comment to name 2.10.0.0 as re-checked and leave
the code.
