R138 gave `lethal.swap-modify-flag`'s `Insert` mutants a `PlatformKillMechanism`, so the report's
platform-artifact screen finally groups them. The tag is applied to EVERY `Insert` mutant, with no
detector behind it, and that is over-broad by construction.

The mechanism needs a specific shape: the target table's `OnInsert` must assign the primary key.
Skipping the trigger then leaves the key blank, the first blank-key insert succeeds and a second
raises a duplicate primary key. Where `OnInsert` does something else — set a Boolean, stamp a
timestamp — `Insert(false)` cannot raise anything the unmutated program did not, so a kill there is
assertion-earned and screening it is noise.

**Measured on the table fixture, 2026-08-14.** The screen fires on two `Insert` kills and exactly one
of them is a platform artifact:

- arm K (`DataFlagOps`, `InsertTwiceWithKeyTrigger`) IS one. Its covering test asserts nothing at
  all, and the kill is a duplicate primary key. This is the case R138 was filed on.
- arm A (`DataFlagOps`, `InsertRunTriggerSetsTheTriggerField`) is NOT one. `Data Trigger Probe`'s
  `OnInsert` sets a Boolean and never touches the primary key, so no duplicate-key error is
  available at that site; the test asserts the Boolean and fails honestly.

One of two. That is a two-kill sample and no rate should be read off it, but the direction is real,
and on a real project it is the difference between a screen a reader acts on and a screen a reader
learns to skip. The 658-file Document Output snapshot holds 91 `Insert(true)` sites (2026-08-12
census), so the population that would carry the tag is large.

What would close this: resolve the receiver's table (`receiver.ts` already resolves it internally —
`resolveReceiver` returns a `tableRef`, it is simply not exported), look up that table through
`SymbolTable.resolveObject`, find its `OnInsert` trigger, read the table's primary key (the FIRST
entry in its `keys` section) and tag only when `OnInsert` assigns a field in that key.

Two limits the narrowing must state rather than hide:

1. A base-app record cannot be resolved at all — the semantic layer is source-derived and cannot see
   base-app triggers — so those `Insert` mutants would go untagged. For a SCREEN the unsafe direction
   is under-tagging (a platform kill credited to the suite), which is the opposite of the direction
   every other Tier-2 guard resolves toward. That trade needs stating, not assuming.
2. A table's `OnInsert` may assign the key indirectly (a No. Series call, a helper procedure), so a
   literal "assigns a primary-key field" test will miss real cases. Measure how many before choosing
   the predicate.

Until this closes, an `Insert` kill carrying the tag means "read this", not "this was the platform" —
which is what the tag's own explanation says, and why R138 was still worth landing without it.
