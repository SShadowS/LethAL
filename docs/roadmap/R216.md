**Found by the issue #6 cross-check's context probe**, the dimension added specifically because a
node-kind comparison cannot see what an operator's `targets()` predicate depends on. This is the
first thing that probe found on its own.

**The measurement.** On `U:/Git/BC.History/BusinessFoundation` the probe reports:

```text
call in statement position    tree-sitter 1534    compiler 1569    <-- differs
```

35 calls the AL compiler treats as statement-position (an `InvocationExpression` whose parent is
`ExpressionStatement`) that `isStatementSlot` answers false for. Zero in the other direction, so it
is a clean one-way gap rather than two definitions disagreeing in both directions.

**The cause, traced to one node.** Every one is a call inside an `asserterror`:

```al
asserterror NoSeriesBatch.GetNextNo(NoSeriesCode);
```

The ancestor chain puts the `call_expression` in the `body` field of an `asserterror_statement`, and
`SINGLE_STATEMENT_SLOTS` (`packages/engine/src/ast/tree-walks.ts`) does not list
`asserterror_statement.body`. It lists the two `if` branches, a `case_branch` body, and the `while`,
`for` and `foreach` bodies. Nothing in the engine or in any operator mentions `asserterror` at all,
so this reads as an omission rather than a decision: the set's own doc comment names what it
deliberately excludes (a `case_else_branch`, a `repeat` body) and why, and this is not among them.

**It would be safe to claim.** `asserterror ;` compiles, verified with `alc` 18.0.2668733, so
deleting the call yields valid AL. The mutant would also be meaningful rather than trivial: it
tests whether the `asserterror` actually asserts anything, which is exactly the weakness a mutation
tester should surface. [Qualified 2026-09-27: that holds for asserterror in TEST code, which LethAL
does not mutate. In product code a deletion there mostly reports reach (killed whenever reached if
the body raises, equivalent if it does not); validate-to-assign's rewrite is the exception, since
skipping OnValidate can change whether the body raises. See the census section below.]

**And it costs nothing today, which is why this is LOW and not a correctness row.** Across the whole
16,898-file corpus of Microsoft's published Business Central source:

| | files containing `asserterror` |
| --- | ---: |
| non-test code | **0** |
| test code | 1,063 |

`asserterror` is test-only by file count in this corpus [2026-09-27: replaced by an object-role
count, see the census section.], and LethAL mutates the target app rather than its tests. So
the missed sites are in code no run would touch. All 35 in the measurement are in `*Tests.Codeunit.al`,
which follows from the corpus-wide count rather than from inspecting each one.

**What would change that.** An app that uses `asserterror` in non-test code, which this corpus says
is not a thing Microsoft does but which nothing forbids. If one ever appears, this row is the reason
its sites go missing, and the fix is one entry in `SINGLE_STATEMENT_SLOTS` plus the R161-style
measurement of what it admits.

**The call-slot omission is not a grammar bug.** For a CALL under `asserterror`, `tree-sitter-al`
shapes the construct correctly. The two parsers simply draw "statement position" differently around
`asserterror`, and LethAL's line is the narrower one. (This applies to the call-slot finding measured
2026-09-09 only; the assignment shape widened below IS an upstream grammar issue, tree-sitter-al #28.)

**Why this widens this row instead of filing a new one.** The pre-commitment for the cross-check
says "one item per container". The container here is this row's, `asserterror_statement.body`, and a
second row would split one fix across two places. This is a deliberate departure from "new item",
stated in the findings.

**The new fact: the kind name differs.** In `asserterror Outcome := Compute(7);` tree-sitter-al
4.3.0 builds `asserterror_statement > assignment_expression`, not the `assignment_statement` it
builds for the same line without `asserterror`. That IS an upstream grammar issue as well as a
LethAL one; see "Upstream: U3" below. For LethAL it matters for the fix:
- `remove-assignment` targets `assignment_statement` only
  (`packages/builtin-tier1/src/remove-assignment.ts`), so adding `asserterror_statement.body` to
  `SINGLE_STATEMENT_SLOTS` would admit the CALLS above and still miss every assignment.
- The cross-check's rule R3 (a compiler-only context delta at a tree-sitter node of the probe's kind
  whose parent is `asserterror_statement` is this row) matches the probe's kind,
  `assignment_statement`, so it cannot fire for these. That is why they came out UNEXPLAINED rather
  than explained.

**Minimal reproduction** (hand-written, not corpus source), `scripts/lib/al-kind-mapping-asserterror-assign.al`:
```al
codeunit 50004 "Assert Assign Probe"
{
    procedure Check()
    var
        Outcome: Integer;
    begin
        asserterror Outcome := Compute(7);
        asserterror Compute(8);
        Outcome := Compute(9);
    end;

    local procedure Compute(Seed: Integer): Integer
    begin
        exit(Seed);
    end;
}
```
Harness output: assignment probe compiler-only UNEXPLAINED at 125; call probe compiler-only
explained-asserterror 1 (the call beside it, as R3 expects).

## Upstream: U3, the grammar gives `asserterror` an expression where AL has a statement (2026-09-27)

Re-assessed at review (GH-06 run 002). The paragraph above once called the kind difference "not a
grammar defect". That was wrong. In tree-sitter-al 4.3.0 (`f7af22a`) the rule is
`asserterror_statement: seq(asserterror_keyword, optional(field('body', choice($._expression,
$.code_block))))`, and `node-types.json` lists no `*_statement` kind for that field. The AL
compiler's `AssertErrorStatementSyntax` holds a statement. So an assignment there can only be
`assignment_expression`, and a statement that is not an expression is not attached at all: in a
hand-written repro, `asserterror if Outcome = 2 then Error('two');` and `asserterror exit;` each parse as
an `asserterror_statement` with no body followed by a SIBLING `if_statement` / `exit_statement`,
with no ERROR node, while the compiler's parser builds `AssertErrorStatement > IfStatement` and
`> ExitStatement` with no error. The second symptom has zero occurrences in the 16,898-file
BC.History corpus (no `asserterror` is followed by `if`, `exit`, `case`, `repeat`, `while`, `for`,
`foreach`, `with` or `begin`), so only the assignment symptom is measured.

Filed as **SShadowS/tree-sitter-al#28** (U3). This row stays open for
the LethAL side either way: even a fixed grammar needs `asserterror_statement.body` in
`SINGLE_STATEMENT_SLOTS` before any operator sees the site.

## 4.4.1 (2026-09-27): the grammar half is fixed; the LethAL half is unchanged and separate

tree-sitter-al 4.4.1 (#28, upstream `209d038`, vendored at `50e98d1`) fixes U3: an assignment
inside `asserterror` is now `assignment_statement`, matching what the AL compiler always built.

The kind fact the "WIDENED" section above relied on, that "tree-sitter names that body
`assignment_expression`, which is ALSO an upstream grammar issue", no longer holds under 4.4.1:
the same construct now builds `assignment_statement`. `remove-assignment` targets
`assignment_statement` only (`packages/builtin-tier1/src/remove-assignment.ts`), gated on
`isStatementSlot`, so once `asserterror_statement.body` is added to `SINGLE_STATEMENT_SLOTS`, that
one operator gains these sites for free; before 4.4.1 it never could have, no matter what the slot
list said, because the node it targets did not exist there.

`packages/engine/tests/ast/grammar-shapes.test.ts` (TSAL-441 Task 5) pins the current state as
still `false`: its R216 case builds only `asserterror Compute(8);`, a call, and asserts
`isStatementSlot(body)` is still `false`. `isStatementSlot` is decided by the parent's kind and the
field name (`asserterror_statement.body`), not by the body's own kind, so a call is enough to pin
it: one pass on both g430 and g441. The slot fix itself is not part of this bump.

Measured (`docs/measurements/2026-09-27-gh06-grammar-crosscheck.md` section 10, run 003, cluster
C4): the 80 records (sysapp 8, baseapp 72) that were UNEXPLAINED under 4.3.0 (the grammar and the
compiler disagreed on the kind, so the cross-check's rule R3 could not match) are now EXPLAINED
under 4.4.1 (the grammar agrees with the compiler, R3 matches, and the record is recognised as an
`asserterror` assignment). `remove-assignment`, gated on `isStatementSlot`, still does not CLAIM any
of them, because the slot is still missing. `toggle-blank-string` is not gated on the statement
slot, and does claim a subset: eight of the 72 baseapp records, at bodies that assign a blank
string literal to a page field's `Value` (the TSAL-441 pre-commitment's AMENDMENT 1). The rest, and
all eight sysapp records, stay unclaimed. The records did not disappear, and no run changes.

[[R283]]'s residue now lives here: even with 4.4.1's call-shape fix (#26), a call inside asserterror
is still not a site for the seven slot-gated operators, for the same missing-slot reason as the
assignment case above. [Corrected 2026-09-27: non-slot-gated operators (swap-call-arguments,
swap-modify-flag, swap-find-direction, flip-boolean-literal, swap-additive) already plant mutants
on and inside such a call.] The one remaining fix, adding `asserterror_statement.body` to
`SINGLE_STATEMENT_SLOTS` plus its own census, covers both the call and the assignment shape, and is
a separate follow-on (orchestrator ruling Q2, TSAL-441 plan), not part of TSAL-441 itself.

**Who reads the predicate this changes.** `isStatementSlot` is consumed by: the operators that gate
on it (`lethal.void-method-call`, `lethal.remove-assignment` in `packages/builtin-tier1/src`, and
`lethal.remove-calcfields`, `lethal.remove-commit`, `lethal.remove-setrange`,
`lethal.remove-testfield`, `lethal.validate-to-assign` in `packages/builtin-tier2/src`, six
deletions plus `validate-to-assign`'s rewrite of `Rec.Validate(F, V)` to `Rec.F := V`); the emission
side, `placeReach` and `emptiedSlotFiller` in `packages/schemata/src/dispatch.ts`; and the grouping
side, `gapBlockOf` in `tree-walks.ts`, which reads `SINGLE_STATEMENT_SLOTS` directly so an existing
mutant inside an `asserterror` body would move to a smaller gap block (no identity key reads the gap
block, so this changes no verdict). Not consumers: `swap-call-arguments`, `swap-find-direction`,
`swap-modify-flag`, `swap-enum-member`, `flip-filter-literal` only compute `parentContext` from
`isStatementPosition`; `write-txn-codeunit-run` and schemata's `wrapIfSingleStatementSlot` read
`isStatementPosition`, not `isStatementSlot`. None of those change behaviour under this predicate.

**Ruling.** STOP (b): 0 deployable product sites on every one of the fourteen inputs above. The
7,846 gained sites are all in test code, which LethAL does not mutate, so admitting the slot buys
nothing today; the pre-commitment's stop rule closes the row on that measured absence, not on a
belief that the sites carry no information. Pre-commitment:
`docs/superpowers/specs/2026-09-27-r216-asserterror-slot-precommitment.md`.
