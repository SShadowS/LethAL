Two separate id problems, reported by the user 2026-08-20, neither of which any test could have
caught: nothing in this repo publishes two of these apps into one service instance.

**1. `LethAL Control` sat at 71000-71010.** It is published at GLOBAL scope, it is resident on both
benched containers (Cronus281 and Cronus283), and a real product in the same environment,
CentralGauge, owns `CG-AL-X011` at codeunit 71000 and `CG-AL-X012` at table 71010. Those are exactly
LethAL's `LC Mutation Active` (table 71000) and `LC Permission Canary` (codeunit 71010). They
coexisted only because the object TYPES happen to be opposite at both points. Nobody designed that
and nothing protects it: one new CentralGauge table at 71000, or one type change here, and
publishing fails on a server LethAL does not own. A tool that installs itself into someone else's
environment does not get to rely on a coincidence.

Moved to 91000-91010, `idRanges` 91000-91099, 43 ids across 20 files. The web service survives the
move without hand-repair because `Install.Codeunit.al`'s `ReconcileWebService` resolves
`Codeunit::"LC Control API"` SYMBOLICALLY and self-corrects a stale row.

**2. `LethAL Sandbox Data` declared codeunits 79197/79198/79199** with the same ids, the same type
and the same names (`Mutation Upgrade` / `Mutation Register` / `Mutation Selector`) as `LethAL
Sandbox App`. Both fixtures took LethAL's built-in `DEFAULT_SELECTOR_IDS`, which live in App's
block; Data made that legal by grafting a three-id island `{79197..79199}` onto its own `idRanges`,
the signature of a fixture cloned from App whose selector triple was never renumbered. The two apps
publish to different containers, so nothing ever failed. Co-install them and publishing does.

Data's triple moved to 79397-79399, the top of its own 79300-79399 block, and the island is gone.
NOT to 79297-79299 as first proposed: `LethAL Sandbox Probes` declares 79200-79299, so that would
have swapped one collision for another.

**Verification.** All five live gates re-run after the move and every one is verdict-identical:
`itest:tables` 201/34/11 over 246 deployed, `itest:bcdev` 3/10/4, `itest:alrunner` 3/14/0 (against
al-runner 2.3.1.0), `itest:hang` 3 killed + 2 timeout-killed, and the
gift-card demo, which `lethal campaign compare` reports as all 43 mutants matching the frozen
baseline. `itest:envtool` also passes at 3/10/4; its baseline had to be re-recorded because it
predated [[R166]] and [[R159]] and the environment had been unreachable since, and the re-recorded
file is IDENTICAL to `itest:bcdev`'s mutant for mutant, which is the property that gate exists to
show.

**Historical ids were deliberately NOT swept.** `docs/campaign/*.report.json` carry measured
callstacks naming `LC Run Method(CodeUnit 71007)`; the dated plans and specs under
`docs/superpowers/`, the closed rows [[R061]] [[R063]] [[R069]] [[R077]], and the R61 record in
`docs/measurements/README.md` describe what was observed at the time. Rewriting an id inside a
measurement makes it a record of something that never happened. Read them with the mapping above:
`710nn` -> `910nn`. (`scripts/r72-probe/src/R72Probe.Codeunit.al` also matches `710nn` and is a false
positive: those are ROW KEYS passed to `WriteHere`, not object ids.)

**What this row does not fix:** the fixture id convention is still inconsistent, which is
[[R170]].

One process note worth keeping. The first pass of gates ran against a STALE
`extensions/lethal-control/lethal-control.app` — the control-app skill's `cp` staging step was
skipped, so the symbol package the targets compiled against still declared the 71000 ids while the
server ran the 91000 ones. Every gate passed anyway, which is itself the finding: a cross-app
`Codeunit "LC Control State"` reference binds by NAME through the app dependency, not by an id
baked at compile time. Had it bound by id, `Active(MutantId)` would have failed for every mutant
and the whole suite would have come back survived rather than erroring, which is the quiet failure
shape this project keeps having to design against. The file was restaged and `itest:bcdev` and
`itest:tables` re-run against it, unchanged.
