`Rec.Modify()` means `RunTrigger = false`. The shipped operator only rewrites an EXPLICIT `true` to
`false`, so the argument-less form, which is the overwhelmingly common way BC code is written, is
invisible to it.

**Measured on `do-rel2/Cloud`**, statement-position calls only:

| shape | sites | claimed today |
| --- | ---: | --- |
| `Modify` (no args) | 181 | no |
| `Insert` (no args) | 126 | no |
| `DeleteAll` (no args) | 74 | no |
| `Delete` (no args) | 38 | no |
| **total, the missing direction** | **419** | |
| `Insert(true)` | 44 | yes |
| `Delete(true)` | 10 | yes |
| `Modify(true)` | 8 | yes |
| **total, what ships** | **62** | |

The missing direction is **6.8x** the footprint of the one we have. It is the same bug class in
mirror image: a developer adds a trigger flag that should not be there, and the `OnInsert` or
`OnModify` chain runs when the code meant it not to.

**Note for anyone reading Fable's proposal of this row (2026-08-19), which asked for
`DeleteAll(true)` to `DeleteAll(false)`:** that direction measures **one** site on this corpus
(`DeleteAll` carries an explicit flag once, and it is already `false`). The valuable direction is
the opposite one, and the measurement is why.

**Why it is not a free version bump.** Turning a trigger ON adds behaviour, and the added behaviour
can raise: a number series that allocates twice, a `TestField` in `OnInsert`, a duplicate primary
key. Every one of those is a kill with no test asserting anything. The reverse direction already
needed this treatment: R138 added `run-trigger-skipped-insert` and R143 narrowed it by reading the
receiver's `OnInsert` and dropping the tag where the trigger provably does not assign the primary
key. The forward direction needs its own analysis, and it is harder, because it must reason about
what a trigger DOES rather than about what skipping it avoids.

Overlap: every one of the 419 already carries a `void-method-call` deletion, so by the letter of
R13's marginality rule they are non-marginal. `swap-modify-flag` shipped anyway under the same
condition, because running a call without its trigger is a different program from not running it at
all, and R82's fixture measured four sites carrying BOTH mutants. The same argument applies here and
should be made explicitly rather than assumed.

**PROBED 2026-08-19, and the headline number in this row is the CEILING, not the footprint.**

`scripts/r165-probe/census.ts` asks what a forward operator could honestly claim rather than how
many argument-less calls exist. The difference is large enough to change this row's priority.

The forward mutant `Modify()` -> `Modify(true)` RUNS the table's `OnModify`. Two facts follow:

- If the receiver's table declares no such trigger, the mutant is close to equivalent, and a wave of
  near-universal survivors is exactly what `RemoveSetLoadFields` was refused for. "Close to" rather
  than "provably": running triggers also raises the platform's integration events, which a
  subscriber elsewhere can observe. So scoping these out is a COST, recorded as one, not an
  equivalence proof.
- If the receiver is a base-app record, this project cannot see the trigger at all, so no screen can
  classify a kill there. R143's ruling for the SKIP direction was to tag when unresolvable; here the
  same choice would tag everything, which separates nothing.

So the operator can only be honest where the table is this project's AND declares the trigger.
Measured on `do-rel2/Cloud` (554 files, 93 project tables):

| | sites |
| --- | ---: |
| argument-less `Insert`/`Modify`/`Delete` on a proven record | **394** |
| implicit `Rec` receiver, no table to reason about | 93 |
| receiver's table not declared by this project | 81 |
| table declared but declares no matching trigger | 171 |
| **CLAIMABLE** | **49** (Insert 37, Delete 10, Modify 2) |

The 419 in the table above counted statement-position calls across four methods including
`DeleteAll`; 394 is the same population under the operator's own receiver proof. Either way the
claimable figure is **49**.

**49 still clears R13's bar of 13**, and it is comparable to what the SKIP direction actually claims
here (62). So this is not refused. But it is no longer the largest item on the list, and the row's
"6.8x the footprint" claim is wrong: measured, it is smaller than the direction we already ship.

**The hazard is also worse than the row implies.** R138 ruled that `Delete` and `Modify` need no
mechanism in the SKIP direction because skipping writes LESS and can add no error. Forcing a trigger
writes MORE, so all three methods can add one, and a naive implementation would tag every mutant it
emits, which is a screen that separates nothing (the `vacuous` state R132 exists to distinguish).

The narrowing that makes it honest is available precisely because the operator is scoped to tables
this project declares: tag only where the trigger's body can provably raise (`Error`, `TestField`,
`FieldError`, an insert of another record, a number-series call), and drop the tag where it provably
cannot. That is R143's shape applied to the opposite direction, and it is the design to build from.

**Revised ranking after this probe:** [[R163]] (1,093 sites) and [[R162]] (2,355 sites) both rank
ahead of this row now. Neither carries a hazard that would tag its whole output.

**BUILT AND LIVE-VERIFIED 2026-08-19.**

`lethal.swap-modify-flag` 1.2.0 (MINOR: it gains sites and moves no existing mutant, so §5.1's
history reset must not fire) now also claims the ARGUMENT-LESS form. `Rec.Modify()` means
`RunTrigger = false`, so the mutant is `Rec.Modify(true)`, which makes the table's `OnModify` run.

**Scoped exactly as the probe said it had to be**: claimed only where the receiver's table is one
this project declares AND that declares the matching trigger. 49 sites on `do-rel2/Cloud`. Both
refusals are costs with reasons, not oversights — a base-app trigger is invisible here so no screen
could classify a kill at such a site, and forcing a trigger that does not exist is close enough to
equivalent to be a survivor factory.

**New mechanism `run-trigger-forced`, and it is STRONGER than its mirror.** Forcing a trigger writes
MORE than the unmutated program, so unlike skipping one it can add an error — which is why R138 gave
`Delete` and `Modify` no mechanism in the skip direction and this direction needs one for all three.
Unlike `run-trigger-skipped-insert`, a blanket tag on every `Insert` mutant, this one is emitted only
where `forcedTriggerCanRaise` finds a raise-capable statement in the trigger body. That precision is
possible precisely because the scoping above guarantees the trigger is in front of the detector. It
under-tags for a raise reached through a project procedure, which is the honest direction for a
screen whose value is that a tag means something.

**Live:** `itest:tables` 201/34/10 over 245 -> **201/34/11 over 246**, the single new mutant
`no-coverage` exactly as pre-committed, baseline diff 1 added 0 removed, then re-run to prove it
compares. `itest:bcdev`, `itest:envtool`, `itest:alrunner`, `itest:hang` and the demo campaign were
measured at zero new sites and did not move.

**The one mutant is worth reading.** It sits in `pageextension Data Main List Ext`'s `OnOpenPage`,
where the fixture had already written, long before this operator existed:

> `Modify()` (i.e. RunTrigger = false) on purpose: running OnModify would add 1 to the very field
> being asserted.

So the mutation is exactly the bug that comment guards against — and it is **not killed**, because
the test that would catch it (`PageExtCountsMatchingRelated`) was removed after being measured twice
to wedge the fenced session. The operator found the right site; the fixture cannot score it. It
carries no tag either, correctly: `Data Main`'s `OnModify` holds one assignment and no raise-capable
call, so `platformArtifactKills.killedCount` stays 2.

**What this row's earlier estimate got wrong, kept visible above:** the "419 sites, 6.8x" figure was
a ceiling. The honest footprint is 49, which is SMALLER than the 62 the skip direction claims.
