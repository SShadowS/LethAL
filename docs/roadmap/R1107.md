Filed by coord PR-113 (lethal-code, 2026-11-17), at the orchestrator's ruling.
- **Why it would help.** In `fillDaemonBaseline`, each R948 cross-check sample (`baselineSampleIds`: index 1, the last, and
  every 10th) runs one-shot while the daemon idles, because `check()` is awaited in the loop. On DO's 735fb42 PR run that was 9
  samples, 33.3 s of a 142.7 s baseline (`/coord/handoff/PR-113/trace/split.md`).
- **The idea.** Start each sample's one-shot and continue with the next daemon request.

**The spec-adversary found no false-kill path.** Nothing is served before the fill ends, and the daemon's answer is fixed
before its sample starts. But a sound build needs these five fixes:
1. **Outcome precedence.**
   - The problem: an in-flight sample's non-ok outcome must win over every later loop event, at every exit (4 returns, 2
     throws, the `finally`, the R1001 uniform check). Otherwise a sample's late "dropped" can let R1001 stop the run as
     "uniformly refused" when the real cause was a daemon-vs-fresh difference. A run that would have succeeded is lost.
   - The fix:
     - wrap each started sample as a promise that never rejects;
     - inspect it at every boundary;
     - rethrow the original error object on a throw;
     - count R1001's "one compared sample" from clean compares, not attempts;
     - never let a sample outlive the fill (as R866 does).
2. **Memory.**
   - The problem: `memoryGate` has no fall-back. An over-bound poll closes the fill's daemon and stops the session.
     Concurrency holds two estimates at once.
   - The fix: a side-effect-free, one-read admission check, under which the sample runs sequentially when it says no;
     `watchMemory()` while a sample is in flight (R970); and an RSS time-series probe (daemon idle vs in a request, and a
     one-shot's ramp) on DO and on a larger corpus BEFORE the build.
3. **R951's replacement.** `replace()` must pick from the loop's current position, not the sample's, or replacements are lost
   and "too few clean samples" drops follow.
4. **Durations.** A sample's kept durations come from its one-shot, which would now run under contention. That is the safe
   direction, since it only lengthens budgets. The spec must say so, and R790's too-slow re-run must await the in-flight sample.
5. **No lane-gate charge.** No lane daemon lives during a fill: `deploy` closes them, and the lanes start after the baseline.

**Measured with PR-113's events** (the 735fb42 arm on a4497f3d): 9 cross-check one-shots, 36.0 s of a 152.4 s baseline.
[[R1106]]'s per-request fixed cost is about 52 s on the same run, so the two levers are of similar size.

**Decide after** PR-113's baseline timing events show the per-request split. [[R1106]] (batching baseline requests) may be the
larger lever on the same phase.

**The gating probe (coord PR-118, lethal-preproc, 2026-11-17, measure only; `/coord/handoff/PR-118/`).**
- **Setup.** PR-113's arm (DO at 735fb42, `--changed-since 735fb42^`, `--workers 1`, config `PR-67/v3.json`, build
  edge-4ebfe7913), re-run on master 9a9af99f, which has [[R1106]]'s batched baseline (PR-115).
  - An RSS time series of each al-runner process of the run, every 200 ms (`sampler.ts`, `rss.tsv`, `analyse.ts`).
  - The sampler also saw other lanes' al-runner processes; the analysis keeps only children of the run's CLI.

| baseline | PR-113 (before batching) | PR-118 (batched) |
|---|---|---|
| wall | 142.7 s | 67.0 s (the baseline phase: 68.9 s) |
| the daemon's own part | about 108 s | about 32 s |
| 9 cross-check one-shots | 33.3 s (23%) | 35.2 s (**53%**) |
| the baseline daemon's peak | 1.82 GiB | 1.78 GiB |
| a one-shot's peak | 1.42-1.70 GiB | 1.22-1.42 GiB |

- **Batching does not shrink the samples.** It cut the daemon's part by about 70%, so the samples are now more than half of
  DO's baseline. Overlapping them with the daemon's work could save up to about 30 of the 67 s.
- **Memory (DO).**
  - The daemon holds 1.45-1.74 GiB while it idles during a sample, and at most 1.78 GiB in a request: a request barely
    grows it.
  - A one-shot ramps to about 1.0 GiB within 1.2 s and peaks at 1.22-1.42 GiB.
  - So a concurrent sample would make the fill's peak about 3.2 GiB, against 1.78 GiB today.
- **A larger corpus is not measured here.** A one-shot loads the same program as the daemon, so on a BaseApp-size corpus a
  concurrent sample about doubles the fill's peak.
- **Recommendation: build**, with the five fixes above. Fix 2's side-effect-free admission check is mandatory, so a
  sample runs sequentially when memory says no. The larger-corpus RSS series belongs in the build's pre-commitment.
