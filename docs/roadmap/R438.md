**Found 2026-10-04 by the orchestrator's merge review of R-385** (merge ac9d9d0c). R433 (done) made
`fetchApiRows` in `packages/runner/src/harness.ts` refuse, before any request, an automation-API path
naming `extensions` unless it is filtered to one app id, because the unfiltered list hung BC 28.4 and
took Cronus28 down. The review found two narrow ways past that run-time check:

- `refuseUnfilteredExtensionsQuery` tests only the PATH. A call such as
  `fetchApiRows("…automation/v2.0/companies", …, { $expand: "extensions" })` asks BC for every
  company's extensions through the query string, and is not refused.
- `decodePercentEscapes` stops after 16 decoding rounds and returns text that may still be encoded,
  without refusing, so a deeply nested escape is checked in encoded form.

Only code inside `harness.ts` can reach either, because the source scan
(`scripts/automation-api-guard.test.ts`) reports the automation API text anywhere else. No code issues
either form today. The scan cannot see a path built from pieces either; that is accepted, as for any
text scan.

**To close.** Run the same refusal over the query's keys and values (`$expand`, `$filter` and any
other), and refuse when a `%XX` escape is still left after the last decoding round. One red-going test
for each, red-checked by removing each clause.

**Closed (9c58e352).** The decoder now reports whether any `%XX` escape is left after its 16th round,
and the guard refuses that for the path and for every query key and value. The "names extensions"
check now runs over the path, the keys and the values, each decoded the same way, so an `$expand` of
`extensions` (plain or encoded) on the companies path is refused before any request. The allowed
form (extensions path plus one GUID filter) and the companies calls still send. Each new clause was
red-checked by deleting it: removing the leftover refusal turned the three deep-escape tests red,
and removing the key and value check turned the four query tests red.
