**An env-tool publish that EXITS 0 while reporting failure in its body is invisible to us — and that is R90's measured mode.** `env-tool.ts`'s only post-spawn failure gates are a spawn throw, LethAL's own timeout abort, and `exitCode !== 0`; on exit 0 the sole processing is `reads`-path extraction, and `READS_KEYS` cannot even NAME a `success` field, so no config can express the check today. `deployment-verifier.ts`'s `decidePublishOutcome` therefore maps such a publish to `indeterminate` (never `failed`), which means `PublishFailedError` is unreachable **by construction** for a tool that exits 0 — R90's documented reproduction is `continia publish` exiting 0 with `{"success": false, "message": "The operation timed out."}`. Consequence: R90's per-tier publish ceiling records an `indeterminate` row rather than a `failed` one for the hosted tier — the exact tier the ceiling exists for — so it never learns that ceiling. The other failure modes DO reach it (exit-non-zero, hang past `envTool.timeoutSeconds`, spawn failure, container-path altool failures); the empty slice is precisely exit-0-with-a-failure-body. Fix: a **config-declared publish success predicate** on env-tool blocks. Three constraints the design must hold. (1) **Vocabulary-neutral** — `env-tool.ts`'s `EnvToolStatusExpectation` doc comment states LethAL hardcodes no vendor's status vocabulary, so no hardcoded `success` field name; the config declares path and value, with `requireStatus`/`readyWhen` as the precedents. (2) **Positive-evidence polarity** — a `successWhen` (declared ⇒ absence of the marker is FAILURE) fails closed; a `failWhen` fails open the moment the tool's output shape drifts, which is this project's signature bug wearing a new hat. (3) The thrown error must **carry the tool's stdout verbatim**, because R23's version-conflict recovery parses BC's rejection text out of publish output (`env-tool.ts`'s `publishCredKeys` check). Acceptance is measurable without a live tier: a stub env-tool exiting 0 and printing a failure body must move its `publish_outcomes` row from `indeterminate` to `failed`; that flip in the store IS the close. Scope: `env-tool.ts` validation + `run()`, `fixtures/README.md`, and a rerun of `itest:envtool`. Filed 2026-08-05 from subsystem C's Task 2 review; one link is inferred rather than recorded — no campaign doc captures the exit code, but `docs/campaign/2026-08-03-do/rung2.result.md` shows the failure surfacing with no cause text, which an exit-non-zero path would have carried verbatim.

**Closed 2026-08-07. Shipped as `successWhen`, and every constraint the row named is held.**

```jsonc
"publish": {
  "command": ["publish", "{envId}", "{appFile}", "--json"],
  "successWhen": { "path": "success", "equals": "true" }
}
```

- **(1) Vocabulary-neutral** — no built-in field name and no built-in value; the config names both,
  the same rule `requireStatus` and `readyWhen.equals` already follow. Deliberately NOT expressed by
  adding `success` to `READS_KEYS`: that list is values LethAL CARRIES FORWARD (endpoint,
  credentials, status), and a success marker is consumed and discarded.
- **(2) Positive-evidence polarity** — declared means "success looks like THIS". A different value,
  a missing path, a path resolving to an object, or output that is not JSON at all are all
  FAILURES. Both halves are required and must be non-empty, refused at validation time before any
  spawn, because an empty half makes the check unfalsifiable while reading in the config as though
  the project were protected.
- **(3) The error carries the tool's stdout VERBATIM** (redacted), so R23's one-shot
  version-conflict recovery can still parse BC's rejection text out of it. The non-JSON branch also
  widens from its usual 200-character opening to the whole body when `successWhen` is declared —
  and the test for it puts the rejection text PAST character 200 on purpose, since a short body
  would be kept by the truncating branch too and the test would pass without measuring anything.

**Widened past the row's ask, on purpose: `successWhen` is allowed on ANY block, not only
`publish`.** Exit-0-while-reporting-failure is not publish-specific, and the credential-withholding
rule composes unchanged (a block that reads credentials gets the same "(output withheld)" it
already gets on a non-zero exit). Undeclared behaves exactly as before, so this cannot turn a
working project's publish into a refusal.

**The close is the store flip the row asked for.** `env-tool-publisher.test.ts` runs the SAME stub —
exit 0, body `{"success": false, "message": "The operation timed out."}` — twice through the publish
path, differing only in whether `successWhen` is declared, and asserts the `publish_outcomes` row is
`indeterminate` without it and `failed` with it. `failed` is the only outcome R90's per-tier ceiling
learns from, so before this the hosted tier could never learn its own ceiling.

**Live-gated, and the gate measured something a unit test could not.**
`LETHAL_ITEST_ENVTOOL=1 bun run itest:envtool` with `successWhen` declared in the fixture config is
**3 killed / 10 survived / 3 no-coverage**, matching the frozen figures. Because the predicate fails
CLOSED, that green run is also positive proof that `continia publish --json` really does emit
`success: true` on the success path — a wrong field name would have refused every publish rather
than passing quietly. The fixture config (`fixtures/sandbox-app/lethal.config.envtool.json`) is
gitignored, so a future session must add the `successWhen` block back to exercise this;
`fixtures/README.md` documents the shape.

**Red-checked twice, both at the call site rather than at the function:** neutering the comparison
reddens three tests; reverting the whole-output branch to the 200-character truncation reddens the
version-conflict one.
