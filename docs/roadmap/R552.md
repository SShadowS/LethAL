**Found 2026-10-09 by R546** (`docs/measurements/2026-10-09-r546-alrunner-bc-agreement.md`,
"Deviations").

**What.** Before compiling, the bcdev backend copies the control app's symbol package into
`bcdev.packageCachePath` as `lethal-control.app` (`BcDevMcpBackend`, the `cp` of
`controlSymbolPath` beside its `mkdir`). It is never removed. R546 pointed `packageCachePath` at a
project's `Test/.alpackages`, which is also the al-runner `packagesDir`: after one bcdev run that
folder held an 18th package that no one put there, and anything that pins the folder by hash or by
count (R396's addendum, R546's slice gate) sees it change. Whether al-runner loads an undeclared app
found there was NOT measured: its verbose log resolves packages by declared dependency (`[dep]`), and
`stageForCompile`'s own comment calls an unused symbol harmless.

**Who hits it.** A user who reuses the project's own `.alpackages` as the bcdev cache, which is the
obvious choice when compiling a real project. Not a verdict risk on its own.

**To close.** Stage the control symbol in a LethAL-owned directory passed to `alc` as a second
package-cache path (alc accepts several), or document that `packageCachePath` must be a dedicated
folder and warn when it holds an `app.json`'s sibling `.alpackages`.

## Fixed (R-553): fallback built, no two-path form

**Owner ruling 2026-10-21:** drop the two-path `/packagecachepath:A;B` form, whose behaviour on the
Windows host's alc (18.0.2668733) was never measured, and build the fallback planned in
`/coord/handoff/R-553/fallback-plan.md`. The first build (2026-10-09, `0197b811`) sent alc the
user's cache plus a `.lethal-symbols` directory as two paths; that form is gone.

- **One path to alc.** `buildPackageCacheCopy` (`packages/runner/src/artifact.ts`) makes a
  LethAL-owned directory `<temp>/lethal-pkgcache-<random>` holding every `*.app` of the user's
  `packageCachePath`, subfolders included at the same relative path (alc searches subfolders of a
  package cache, measured on Linux alc in the delta review), plus `controlSymbolPath` as
  `lethal-control.app`.
  `CompileInput.packageCacheCopyPath` carries it, and `ArtifactCompiler.compile` sends it as the ONE
  `/packagecachepath:`, in place of the configured cache. Without it the argv is unchanged;
  `compileProject` (the test-app compile, the R461 plain check) is unchanged.
- **Hard links, copy fallback.** Each file goes in by `link`, which shares the user's file and never
  writes it. On `EXDEV` (another volume) or `EPERM` (no hard links there) it is copied instead. Any
  other error is an `ArtifactPrepareError` naming the file, and the partial directory is removed.
- **The leftover `lethal-control.app` is left out.** A `lethal-control.app` an older LethAL left in
  the user's cache (any case, any depth) is skipped by file name, so it cannot compete with
  LethAL's own copy. The skip is by file name only: a control package under another file name
  (`LethAL_LethAL Control_<ver>.app`, say) still goes in, and alc picks the highest version as
  before; a user project does not declare that dependency, so Download Symbols does not fetch it.
  The leftover gets ONE warning per backend (safe to delete), matched by the same name test, and
  is never deleted or overwritten.
- **Lifetime.** `BcDevMcpBackend` builds the copy on its first compile and reuses it for every
  compile of the session; a failed build is retried by the next compile. `close()` removes it, also
  when the MCP client's close throws, and `cli.ts` calls `close()` in its session `finally`.
  `scripts/campaign/compile-only.ts` builds its own and removes it in its `finally`; the
  `stale-publish` itest builds one under its scratch root, which its `finally` removes.
- **Fail loudly.** A `;` or `,` in the copy's path is refused with `ArtifactPrepareError` before any
  spawn (alc splits on both, silently). Never `AlcCompileError`: alc did not run. The user's cache
  path is no longer passed to alc at all, so a `;` in it no longer matters.
- **Costs.** A full copy is the USUAL case, not the exception: inside kraken `/tmp` and `/work` are
  on different filesystems, so `link` fails with EXDEV and every session copies the cache (64 MB
  for sandbox-app's `.alpackages`, about 70 MB for a full BaseApp set); the same holds on Windows
  whenever the cache is not on C:. The copy is made once per session, not per compile. Hard links
  (milliseconds) apply only where the cache and the temp directory share a volume. A package added
  to the user's cache mid-session is not seen until the next session.

**Unit evidence.** Kept, unchanged in what they assert: the user's cache listing (name, size,
sha256, mtimeMs) is identical after `deploy()`, `compileCheck()` and a failed compile, and a stale
leftover keeps its bytes and mtime (`bcdev-backend.test.ts`, `compile-only.test.ts`). Added: alc gets
EXACTLY ONE package-cache path (artifact, bcdev and compile-only tests); the copy holds every user
package by hard link plus the symbol; packages in subfolders are copied at their relative path;
the leftover is skipped by name, any case, at any depth; the leftover warning matches it the same
way (`Lethal-Control.app` warns on Linux); the EXDEV and EPERM copy fallback; any other link or
copy error is an `ArtifactPrepareError` naming the file, and the partial copy is removed; `close()` removes the copy;
a throwing session's `finally` removes it; compile-only's `finally` removes it after a failed alc.
Each was red-checked in its own direction (`/coord/handoff/R-553/red-checks-fallback.md`).
