Found by PR-34 (lethal-bugs, 2026-11-15; `/coord/handoff/PR-34/bc/`), the mutant-level al-runner v3 vs bcdev differential on a
copy of System Application's Secrets module (68 mutants, 6 tests) on bc2 (BC 28.4 W1 on Linux).

**Measured.** Under the default coverage mode ("procedure"), the bcdev run's baseline was green (6 of 6 pass), yet all 68 mutants
read `no-coverage`. Every procedure of the module carries `[NonDebuggable]`. The stored baseline coverage of each test holds one
entry only: the generated selector codeunit's `Active`. The instrumented guards inside the target call `Active`, so the target
code did run, but BC recorded no Code Coverage line for any of the target's four codeunits. al-runner v3 on the same copy covers
all 68 (47 killed, 20 survived, 1 error). The one-line cause: BC records no Code Coverage line for a `[NonDebuggable]` procedure.
Not measured separately: a module that mixes `[NonDebuggable]` and plain procedures. The reading here comes from a module where
every procedure has the attribute and only the selector shows.

**Why it matters.** It is the R175 class: an attribution loss that reads as untested code. A real project with secret-handling or
licensing code under `[NonDebuggable]` would see those mutants as no-coverage on bcdev. The report gives no caveat, so a user
reads it as missing tests.

**Possible fix** (not designed): name the cause. The emitter can see `[NonDebuggable]` on a procedure, so a mutant site inside one
could carry a note or a caveat ("BC records no coverage here; run with coverageMode none for a verdict"). Or LethAL could run those
mutants against every green test, as mode "none" does.

**To close.** A bcdev run over a `[NonDebuggable]` site either scores it (killed or survived, as v3 does) or names why it cannot,
with a test that fails if the note is dropped.
