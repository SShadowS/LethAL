`SessionReport.platformArtifactKills` tags exactly one mechanism today, `write-txn-codeunit-run`, and
only `lethal.remove-commit` declares it. Extending `lethal.swap-modify-flag` to `Insert(true)` adds a
second, larger population of kills that are platform artifacts rather than earned kills, and the
screen is blind to all of them.

The shape, on ordinary BC code: a table whose `OnInsert` assigns the primary key from a No. Series.

```al
for i := 1 to Count do begin
    Line.Init();
    Line.Insert(true);   // mutant: Insert(false)
end;
```

With `Insert(false)` the trigger never runs, so `"No."` stays blank. The first iteration inserts a
blank-key row and succeeds, because blank is a legal `Code[20]`. The second iteration raises a
duplicate primary key error. The test dies on the platform error before evaluating any assertion, and
the mutant is scored `killed`. The suite did not earn that kill. A quieter single-row variant is just
as real: the blank key makes a following `Rec.Get(ExpectedNo)` or `Rec.Modify()` raise "the record
does not exist".

Measured population for context: 91 `Insert(true)` sites in the 658-file Document Output snapshot
(2026-08-12 census), against 43 `Modify(true)` sites the operator covers today.

Why this is not R86: R86 is that no kill records why it died (`failure_note` is NULL for every killed
mutant). This row is narrower and actionable without R86 — the operator KNOWS which mechanism its
mutant can trigger, the way `remove-commit` does, so it can declare a `PlatformKillMechanism` and the
screen can group it. Candidate mechanism name: `run-trigger-skipped-key-assignment`, or the broader
`run-trigger-skipped`.

Work this row asks for:

1. A second `PlatformKillMechanism` value declared by `swap-modify-flag`'s `Insert` mutants (and a
   ruling on whether `Delete(false)` needs one; skipping `OnDelete` removes errors rather than adding
   them, so probably not).
2. A screen that separates such kills in the report without moving the verdict, the R72 discipline:
   a diagnosis never moves a verdict.
3. A fixture arm that measures the class live rather than arguing it. The R136 trio's spec adds one
   (a table whose `OnInsert` assigns the key, an arm that inserts twice, a test that asserts nothing),
   pre-committed `killed` and recorded as a platform artifact the screen does not tag. That arm is the
   evidence this row closes against.

Until it closes, no `Insert` kill on a real project supports any claim about that test's assertion
quality. The R136 trio spec says so in its "what the live run may not conclude" section.

## Closed 2026-08-14

`PlatformKillMechanism` gained a second value, `run-trigger-skipped-insert`, declared by
`lethal.swap-modify-flag` on its `Insert` mutants only. Pre-committed in
`docs/superpowers/specs/2026-08-14-r138-insert-mechanism-precommitment.md` before the operator change
was written and before any container touched it. `itest:tables` PASS, and every prediction matched.

**The ruling on `Delete` and `Modify`: no mechanism, and that is a decision rather than an omission.**
Skipping `OnDelete` or `OnModify` writes LESS than the unmutated program, never more, and the row is
still located by the same key, so there is no error the mutation can ADD. Only `Insert` can: with
`OnInsert` skipped, a table whose `OnInsert` assigns the primary key leaves it blank, the first
blank-key insert succeeds and a second raises a duplicate primary key.

**The verdicts did not move**, which is the R72 discipline this row inherited. killed **191**,
survived **31**, no-coverage **10** over 232 deployed, score 0.8603603603603603,
`untargetedTriggerCount` 0, and the per-mutant baseline file was not re-recorded.

**`platformArtifactKills.killedCount` went 1 -> 3, not 1 -> 4.** The session brief expected 4 on the
premise that all three of arm K's untagged kills were this operator's. They are not. Only one of them
is a `swap-modify-flag` mutant; the other two reach the same duplicate-key error through Tier-1
operators mutating the trigger itself — an `empty-block` on `Data Key Probe`'s `OnInsert` body and a
`negate-conditional` on its blank-key guard. Those two remain untagged, so the screen's blind spot
shrank rather than closed, and `platform-artifact-kills.ts` now says so in its "what it cannot see"
list. The +2 is the fixture's two KILLED `Insert` sites (arm A and arm K); arm B's `Insert` mutant
carries the tag too but survives, and a survivor at such a site is just a survivor.

**The cost, stated rather than discovered.** The tag is syntactic and applies to every `Insert`
mutant, because whether the target table's `OnInsert` touches the primary key is not visible at the
call site and, for a base-app record, is not visible at all. So of the two kills it screens here,
exactly one is a platform artifact: arm K's (whose covering test asserts nothing, killed by a
duplicate key) and NOT arm A's (an honest assertion kill on a table whose `OnInsert` sets a Boolean).
One of two, on a two-kill sample. Narrowing it is [R143](R143.md).

Because the two mechanisms are not equally evidenced, `PLATFORM_ARTIFACT_KILL_DIAGNOSIS` — shared
across mechanisms — no longer says every screened mutant sits at a site BC is "MEASURED to refuse".
That was true of the write-transaction detector and false of every `Insert` site. Each mechanism's
own explanation now states its own evidence strength, and the write-transaction claim is unchanged:
it still names Cronus281 and the 2x2x2.

The gate pins both mechanisms BY NAME and the Insert group BY MUTANT (arm A and arm K, by procedure
name), not by a count — a count of two is satisfied by the wrong two, and the ruling silently
widening to `Delete`/`Modify` is exactly what that assertion catches.
