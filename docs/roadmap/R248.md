title: "A test-app publish whose pre-fence read fails still goes ahead, and then can only end indeterminate: one wrong read credential leaves a container needing a recycle"
section: "correctness-risks"

**Found in C02-05's final review (2026-09-26), confirmed by reading.** `publishTestApp` reads the
resident test-app package before it claims the lease's publication fence, to refuse a downgrade.
`fetchPublishedAppPackage` answers `null` alike for a 404 (never published), a 401 (bad read
credentials) and a timeout. C02-05's decision 3 lets a `null` pass to the in-fence backstop, which
is right for "never published".

For the other two it is not. If the dev-endpoint read credentials (`BC_DEV_USER` /
`BC_DEV_PASSWORD`) are wrong while altool's own are right, the pre-fence read returns `null`, the
publish goes ahead, and the read-back is `null` again. Decision 2 then calls the outcome
`publish-indeterminate`: the marker stays set and `container-needs-recycle` is recorded. So one
configuration mistake turns every `lethal verify` (C02-06) into a container an operator must clear
by hand. In C02-06's flow the test app is nearly always already published, so a pre-fence `null`
almost always means "could not read", not "never published".

A possible fix: make the read tell a 404 apart from every other failure, and refuse a pre-fence
unreadable answer as a typed pre-server refusal (terminal, no marker claimed) before the fence.
Not measured live. C02-06 should decide this before it ships.
