## What breaks, and for whom

A mutant reported `no-coverage` is excluded from the mutation score and read by every downstream
consumer as "your tests do not reach this code". For a mutant in a PUBLIC procedure, LethAL can emit
that verdict without ever running the mutant, on an INFERENCE rather than an observation, and the
inference can be wrong. The user then reads "your tests don't reach this" where the truth is "LethAL
did not try".

This is R29's error class (a confident, non-empty, wrong coverage answer) pointing the other way:
R29 and R63 manufactured false SURVIVORS, and this manufactures false NO-COVERAGE.

## The code

`packages/runner/src/selection.ts`, `coverageFilter`. When a mutant's member key misses `byMember`,
the unnamed-member fallback to object level is gated:

```ts
if ((testKeys === undefined || testKeys.size === 0) && !isTrigger && m.procedureScope === "local") {
  testKeys = index.byObjectUnnamed.get(objectKeyOf(m.objectType, m.codeunitId, context));
}
```

The comment above it states the premise in capitals: *"a PUBLIC procedure whose member key misses
DID NOT EXECUTE (a public execution always resolves by name)"*.

**That premise is the whole load-bearing claim and it carries no measurement.** Its neighbours in the
same comment do: locals are absent from `SymbolReference.json` ("verified 2026-07-18"), and R63's
expansion produced 77 false survivors on Document Output (measured). The converse — that a public
execution ALWAYS resolves — is asserted. It is the step that turns "we cannot name this member" into
"this member did not run", and it is the only step in the chain nobody measured.

## The evidence that it is false

Reported by a downstream user, verified by them from report data, and it is a logical contradiction
inside ONE report rather than a statistical argument:

- `SetFieldFromJsonToken`'s mutants M0027/M0030 were **killed** by `TestDeserializeFromJson_ValidData`.
- `DeserializeFromJson`, its **only caller**, is `no-coverage` with zero covering tests.

A callee cannot execute unless its caller does. So the caller executed, its member key missed, and it
was reported `no-coverage` anyway. Corroborating: all 94 of that task's `no-coverage` mutants carry
`durationMs == 0`, which is consistent with never having been run.

**Scope as reported: 223 of 2058 mutants (10.8%) across 17 reports.** Four tasks are affected
wholesale (51/51, 19/19, 14/14, 94/114), which is the shape of an object-wide or task-wide cause
rather than a scattering.

## CORRECTION, same day: the default path is FENCED, not the methodId path

The reported mechanism (and this row's first draft) described `AppMethodIndex.lookup` resolving a
numeric `methodId` against `SymbolReference.json`. That is `coverageMode: "procedure"`, the HUB path.
`DEFAULT_COVERAGE_MODE` is **`"fenced"`** (bcdev-backend.ts), which resolves a LINE NUMBER through
`line-map.ts` instead. Both paths feed the same `selection.ts` gate, so the defect below is common to
them, but anyone hunting the naming failure must know which resolver was actually in play.

`buildCoverageMap` (hub) and the fenced builder both do the RIGHT thing with an unresolved member:
they emit an object-level entry rather than dropping it. The defect is entirely in the consumer.

## Two candidate mechanisms, both MEASURED DEAD 2026-08-26

Recorded so nobody spends the afternoon on them again.

1. **"`internal` procedures are missing from `SymbolReference.json`, so they resolve as unnameable
   while `procedureScopeOf` calls them public."** FALSE. Compiled a probe carrying all AL
   visibilities: `local` is absent (as documented), but `internal` IS present, and so is a public
   method inside an `Access = Internal` object. Object-level `Access` is not even recorded.
2. **"`procedureScopeOf`'s regex mislabels a local as public when an attribute contains a `]`"**
   (`[EventSubscriber(..., Codeunit::"Item[Ledger] Mgt", ...)]`). FALSE, and the regex's attribute
   handling turns out to be dead code: the parser does not include attributes in the `procedure`
   node's text, so `proc.text` starts at `local`. Verified against five realistic attribute shapes
   through the real parser.

## What is still unknown, and what would settle it

The mechanism. What must be true, from the contradiction itself: the affected object IS in
`declaredObjects()` and its method index DOES work, because a sibling procedure in the same object
resolved by name and was killed. So the failure is specific to particular METHODS, not to the object
or the artifact.

Remaining candidates, untested:

- The `methodId` BC reports in `Code Coverage` does not equal `Methods[].Id` in
  `SymbolReference.json` for some method kinds (overloads, interface implementations, event
  publishers). The ids are hashes, not ordinals: the probe read `Id=1373418902` for a three-line
  procedure.
- `procedureScope` absent from the manifest entry for those mutants. The field is OPTIONAL
  (`project.ts`), and `m.procedureScope === "local"` is false for `undefined` just as it is for
  `"public"`, so an artifact that did not emit it would send EVERY ordinary mutant down the public
  branch. This would explain the wholesale tasks better than anything else and is the first thing to
  check.

**The cheap discriminator, on report data already in hand:** for a `no-coverage` mutant in a
procedure known to have executed, read its manifest `procedureScope`. `"public"` on a procedure that
is `local` in source means the classifier; absent means the manifest; `"local"` means the gate was
never the problem and `byObjectUnnamed` was empty for that object.

## A third hypothesis, WEAKENED by an existing measurement rather than by me

The line map's base-line frame. `fileLineMapEntries` bases the FIRST object in a file at line 1, so a
leading licence header counts as part of that object's numbering, and no gated fixture tests it:
**every fixture file a live gate scores holds exactly ONE object**, and the only multi-object file in
the repository is in `sandbox-coverage-probe`. The measured table in `LineMapEntry.baseLine` lists
only SECOND and THIRD objects, where "previous end + 1" and "own keyword line" differ; for a FIRST
object with a header they differ by the header length and nothing in that table discriminates them.

Against that: `docs/measurements/README.md` records the frame being checked on a real commercial
file. Document Output's instrumented `Codeunit 6175297` is 3,177 lines, BC's rows carry `lineNo`
30..3171, and bucketing 410 real rows against the instrumented procedure ranges named exactly the
five procedures the run attributed. So the frame was right there. Not proof for every file shape, but
enough that this is no longer the leading candidate.

## The detection gap, which is the reason 17 reports went by

`warnOnThinFencedCoverage` fires only when a test resolves **zero** members. Partial degradation, some
procedures in an object naming correctly and others not, is exactly the reported shape and is
**silent**. The warning's own doc comment records a measured 92-vs-15 no-coverage blowup on Document
Output with this shape, and says "nothing in the verdicts, the counts or the exit code said anything
was wrong". That is still true for the partial case.

## The ground truth already exists and the skill does not mention it

`scripts/probe-r58-differential.ts` accepts `--mode none` as well as `procedure` and `fenced`, and
`coverageMode: "none"` runs every mutant against every green test, so it is attribution-free ground
truth. Any mutant that `none` kills and `fenced` reports `no-coverage` is a PROVEN attribution
failure, per mutant, by name.

The `coverage-differential` skill documents only `procedure` vs `fenced`. The one comparison that can
prove attribution wrong is the one nobody is told to run.

## The workaround is real and is not a fix

`coverageMode: "none"` bypasses this entirely: `orchestrator.ts` skips `buildCoverageIndex` and
`coverageFilter` and runs every mutant against every green test, so no verdict can come from
attribution. Confirmed in code. It costs a full cross-product of run time and it does not make the
default path safe.

## Until it is fixed

`no-coverage` from the default path cannot be quoted as "the tests do not reach this" without a
`coverageMode: "none"` re-run. That caveat belongs in `lethal explain`'s survivor projection and in
`docs/using-lethal-from-an-agent.md`, neither of which says it today.

## MECHANISM FOUND, 2026-08-26, and it is a resolver mismatch

The gate reasons about the WRONG RESOLVER. Its comment justifies itself with
`SymbolReference.json`, which lists no local procedures, so on the HUB path a local's member key
must miss however thoroughly it executed. `DEFAULT_COVERAGE_MODE` is **`fenced`**, which resolves
lines through `line-map.ts` — and that file parses the source and **never looks at scope**. The word
`local` does not appear in it.

**MEASURED, `fixtures/sandbox-app`, fenced:** all five mutants of the local `LogAudit`, the exact
procedure the gate's comment cites as its reason to exist, come back `coverageAttribution: "exact"`.
The premise for the local half is false on the default path, and the premise for the public half
("a public execution always resolves by name") is the same claim about the same wrong resolver.

**MEASURED, 424 mutants across three fixtures:** the local widening fires for a non-trigger mutant
**zero** times on fenced. Every `attribution: "object"` is a trigger taking FALLBACK 1.

## What shipped

1. **`line-map.ts` now indexes TRIGGER spans, for classification only.** `lookup` still refuses to
   name a trigger, so rule 4 is untouched; what is new is being able to tell the two kinds of
   `undefined` apart. A line inside a trigger is a member we decline to name. A line inside NOTHING
   is the resolver failing on source LethAL itself emitted, which is the R175 defect made visible.
2. **`CoverageMap.namingGaps`**, populated by the fenced builder only. The hub cannot compute it: an
   unresolved `methodId` there could be a local (expected) or a public whose id did not match, and
   it cannot tell which, so it reports none rather than guess.
3. **`unplaceableCount` / `unplaceableMutants` on `SessionReport`**, an `attribution-unplaceable`
   caveat with a reader interpretation, and a CLI banner. Verdicts and score are UNCHANGED: these
   stay excluded, because "we do not know" is still honest. What changes is that a reader can see
   which part of a no-coverage total is ours, and which mutants to re-run under `coverageMode:
   "none"`.
4. **The local widening is gated on the resolver.** On fenced it no longer fires, so a local whose
   member key misses there is reported honestly instead of being widened into confident
   object-level coverage — which was R63's manufactured-coverage shape reached from the other side.

## The wrong first attempt, kept on the record

The first detector asked "did anything unnameable execute in this object?" and **over-flagged**. In
a table whose triggers fire constantly the answer is always yes. MEASURED on `fixtures/sandbox-data`:
it flagged both mutants of `Data Main.TouchCount`, which that fixture's own comment documents as
genuinely uncovered. A signal that fires on every uncovered procedure of every trigger-carrying
table would have retired the word `no-coverage` without replacing it. The corrected signal reports
**0** on the same fixture.

## What is still NOT fixed

- **The hub path is unchanged**, deliberately. Its resolver genuinely cannot name locals, so the
  widening is correct there and there is no naming-gap signal to be had.
- **The downstream 17 reports are not explained by this alone.** This build makes the failure
  VISIBLE and stops the fenced path manufacturing coverage; whether their runs were fenced or hub,
  and whether a naming gap is what their reports would now show, needs `unplaceableCount` on a
  re-run. The `--mode none` differential remains the ground truth.
- **No gated fixture reproduces a naming gap.** All three gates report 0, which is the right answer
  for them and means the new signal's non-zero branch is proven only by unit tests. A fixture that
  provokes a real gap is worth having and does not exist.
