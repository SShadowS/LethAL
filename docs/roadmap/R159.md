**The question this answers.** Every operator LethAL ships was justified one at a time, and every
operator it REFUSED has its reason written down, `RemoveSetLoadFields` on cost after a live
measurement, the three Tier-3 candidates in `docs/superpowers/specs/2026-08-02-r13-tier3-decision.md`.
What was never written down is the complement: the AL constructs no operator inspects **at all**,
which no refusal covers because nobody ever proposed them. A brainstormed list of "operators we
could add" is unfalsifiable. A histogram of the grammar's own node kinds over a real corpus, marked
with which kinds an operator's `targets()` claims, is not.

`scripts/census-node-kind-coverage.ts` is that instrument. It reads RAW tree-sitter node types, never
`ALNodeKind`: the curated enum is a subset chosen by us, so censusing it could only ever report that
the kinds we named are the kinds we handle, the blind spot would be invisible in exactly the shape
it takes.

**Measured 2026-08-19 on `do-rel2/Cloud`** (Continia Document Output, 554 `.al` files), counting only
nodes with a `procedure` or `trigger_declaration` ancestor:

| | |
| --- | --- |
| distinct node kinds inside procedure/trigger bodies | 115 |
| behaviour-carrying kinds (name ends `_statement` / `_expression`, or a literal) | 31 |
| of those, claimed by at least one operator | **5** |
| of those, never claimed by any operator | **26**, 26,865 occurrences |

The narrowing to 31 is mechanical, on the grammar's own naming convention, rather than a

**Three things this number is NOT, stated so nobody quotes it as a coverage score.**

1. **Node-kind coverage is not mutation adequacy.** Two operators at different kinds can be killed
   by the same test, and this project has already refused an operator on exactly that ground:
   `IsolationLevelSwap` was refused because 25 of its 36 sites already carried a shipped
   `void-method-call` mutant. Overlap has to be measured per candidate, not assumed away.
2. **`empty-block` destroys the contents of 6,100 blocks**, so the code inside an unclaimed
   `assignment_statement` is not untested, it is untested *individually*. A whole-block deletion is
   a coarse mutant that a single weak assertion kills; the fine-grained one is what separates suites.
   The gap is real but it is a gap in DISCRIMINATION, not in reach.
3. **One corpus, one vendor.** A different app's mix will differ; `ternary_expression` at 6 here may
   be common elsewhere.

**The one entry with no recorded reason at all is arithmetic.** `additive_expression` (1,087) and
`multiplicative_expression` (34) are 1,121 sites of a construct that Arithmetic Operator Replacement
`+`↔`-`, `*`↔`/`, is the single most standard operator for in the mutation-testing literature, and
it is a staple of every comparable tool. `design.md` §4 does not list it in Tier 1, Tier 2 or Tier 3;
no roadmap row refuses it. That is an omission rather than a decision, which is the specific thing
this row exists to correct.

The runners-up worth a decision, all AL-flavoured rather than generic: `qualified_enum_value` (2,355,
outside the behavioural filter because of its name), swapping an enum member is the kind of change
BC code branches on constantly; `case_branch` (1,004), deleting an arm; `unary_expression` (1,124),
removing a `not`, which `negate-conditional` reaches only when the negation is a comparison.

**Next step is a decision, not a build.** Each candidate needs the same treatment the shipped ones
got: a site census, an overlap check against the mutants already emitted there, and a live
pre-committed arm in `fixtures/sandbox-data`. Shipping AOR because the literature likes it, without
measuring how many of its 1,121 sites already carry a `void-method-call` or `empty-block` mutant,
would repeat the mistake `IsolationLevelSwap` was refused for.

**Multiplicative: attempted 2026-08-20, REFUTED live, and the hold now has a measured reason.**

The spike held this half because `x * y` -> `x / y` divides by zero when `y` is zero. That hazard IS
avoidable by construction — claim only where the mutant is `*` (no division at all) or divides by a
non-zero LITERAL — which measured 25 of 27 numeric sites on `do-rel2/Cloud`, comfortably over R13's
bar. The operator was built on exactly that scope.

`itest:tables` refuted it. All four verdicts matched the pre-commitment, and R132's twin-pair check
failed instead:

```
Overflow under conversion of ... Decimal18 value 12.5 to System.Int32.
Data Assert Ops(CodeUnit 79318).DoubledLevel line 10
```

`DoubledLevel(25)` mutated to `25 / 2` is 12.5, and returning a Decimal from an `Integer` procedure
RAISES in AL rather than rounding. The mutant died on the platform, not on an assertion — the same
false-kill class, through a mechanism the design never considered. The additive half's `alc` proof
had already compiled `Level * 2` -> `Level / 2` on this fixture, which is the trap in one line:
**compiling is not running.**

Re-measured with the real hazard: `/` -> `*` is 7 sites, `*` -> `/` with a Decimal operand is 0, and
`*` -> `/` all-Integer is 18 and unsafe. The safe scope is **7, below the bar of 13**, so the
operator is reverted and this half stays HELD.

What would unhold it: a way to know the CONTEXT a multiplicative expression's value flows into (a
Decimal variable, field or return type), at which point the all-Integer sites become claimable where
the destination can hold a fraction. That needs the type table to answer about assignment targets and
return types, which is [[R160]]'s neighbourhood rather than this operator's.

Full record, including the unedited prediction:
`docs/superpowers/specs/2026-08-20-r159-swap-multiplicative-precommitment.md`.

**Third candidate built, 2026-08-26: `lethal.remove-assignment`.**

`assignment_statement` was the largest unclaimed kind at 6,850 corpus occurrences with zero
exact-span overlap. It is the direct analogue of `void-method-call` — AL has two statement forms and
this row's census showed LethAL deleted only one of them.

Spike and build: `docs/superpowers/specs/2026-08-26-r159-remove-assignment-spike.md` and its
build pre-commitment. **74 of 75 verdicts matched.** It moved every gate, the largest landing this row
has produced: `itest:tables` 219/41/12 over 272 -> **252/57/15 over 324**, bcdev 3/10/4 -> 3/11/4,
al-runner 3/14/0 -> 3/15/0, `itest:hang` 5 mutants -> 7 with a third non-terminating one, and both
demos.

Two things learned that the next candidate should carry:

1. **Predict the THREE-way split, never kill-versus-survive.** The spike's aggregate prediction said
   0 no-coverage on both fixtures and both produced 3, because it reasoned about whether a suite
   would CATCH a deleted assignment and forgot the assignment might sit in a procedure no test calls.
   Both fixtures say so in their own READMEs.
2. **A fixture generator that hardcodes an operator's yield breaks when the set changes.**
   `publish-ceiling.test.ts` built a file of exactly N deployed guards from the constants "3 per
   `exit(A > B)` procedure, 1 per `G := n` procedure". This operator made the second yield 2 and three
   tests failed at once. It now MEASURES both yields against the real pipeline and solves the mix, so
   the next operator changes a number rather than a result.

**`string_literal` was called a refusal candidate here, and the measurement says otherwise.**

That claim — most are labels, messages and error text, so mutating them is noise — was made from
intuition about AL, before anything was counted. `scripts/census-literal-contexts.ts` counts it, by
the ENCLOSING CONSTRUCT rather than in aggregate, because a literal's context is what decides whether
mutating it changes behaviour, changes a message, or touches a surface no operator may touch.

**Measured on `do-rel2/Cloud`**: 12,835 string literals, 4,892 of them inside procedure or trigger
bodies, **0 already claimed at the same span** by any shipped operator.

| context | count | share |
| --- | ---: | ---: |
| property (declarative: Caption, ToolTip, …) | 6,953 | 54.2% |
| other call argument | 2,147 | 16.7% |
| **comparison operand** | **823** | 6.4% |
| string concatenation | 749 | 5.8% |
| variable declaration | 593 | 4.6% |
| attribute argument | 368 | 2.9% |
| **assigned value** | **306** | 2.4% |
| message / error argument | 263 | 2.0% |
| filter argument (`flip-filter-literal`'s) | 261 | 2.0% |
| everything else | 372 | 2.9% |

The intuition was right about the AGGREGATE and wrong about the DECISION. 54% really are declarative
properties and R135 already refuses those. But the slice that is provably behavioural by context —
a value the program compares against or stores — is **1,129 sites, 87x R13's bar of 13**, and a
further 2,147 call arguments whose meaning depends on a callee this layer would have to resolve.
"Most of them are noise" does not refuse an operator whose non-noise slice is that large.

**So the honest verdict is BUILD, on a narrow slice**: comparison operands and assigned values, the
1,129, leaving properties to R135, filters to `flip-filter-literal`, and message text alone. The
mutation is well defined and compile-safe by construction in a way `flip-boolean-literal`'s was not —
the empty string is assignable wherever a string literal is legal, whatever the target's length.

Two things a spike must settle before it lands, neither of them a refusal:

1. **Equivalence.** `if X = 'FOO'` becoming `if X = ''` changes the branch only when a test drives X
   to one of those values. Expect survivors, and expect them to be honest ones.
2. **A platform-kill hazard with a precedent.** Assigning `''` into a primary key produces a
   duplicate-key error with no test asserting anything — the shape R138 tagged for
   `swap-modify-flag`'s `Insert`. It needs the same treatment, decided before the operator ships
   rather than after a live run surprises someone.

On this repository's own fixtures the behavioural slice is 7 sites (3 comparison, 4 assigned), so a
live half would need a fixture arm.

**`for_statement` is a refusal and nothing needs building.** Every one of the 46 in the corpus has an
integer literal bound, so `shift-integer` already claims the site. The operator that looked most like
a control-flow gap turns out to be fully covered by one already shipped.

**`parenthesized_expression` was mis-called here, and the correction is the useful part.** Of 763,
**529 would not compile** and **202 are pure no-ops**, leaving 32. The refusals are not a hunch:

- AL is Pascal-family, so `and`/`or` bind TIGHTER than comparison. `(A = B) and (C = D)` without its
  parens is `A = (B and C) = D`, which `alc` rejects with `AL0175`. Same for `not (A = B)`, `AL0173`.
- A paren whose inner operator already binds at least as tight is decoration; removing it is an
  equivalent mutant by construction, unkillable, and 202 are that.
- The 32 that remain both compile AND change meaning, and they are **entirely boolean regrouping**.
  Broken down by shape, which is what an operator would have to target:

  | sites | shape | mutant |
  | ---: | --- | --- |
  | 15 | `(X or Y) and Z` | `X or (Y and Z)` |
  | 11 | `not (X and Y)` | `(not X) and Y` |
  | 6 | `not (X or Y)` | `(not X) or Y` |

  **Zero arithmetic candidates**, which is worth stating because it is the shape one expects: the 8
  additive and 4 multiplicative parents in the corpus all wrap an operand that already binds tighter,
  so their parens are decoration. A `parenthesized_expression` operator here is a De Morgan probe,
  not an arithmetic one.

Every shape was VERIFIED against real `alc.exe` in `scripts/r159-paren-probe.py`, **each with its own
control**, rather than argued from a precedence table. That mattered twice: the first probe version
was itself malformed AL and its CONTROL failed to compile, which would have read as "the mutant does
not compile" had only the mutant row been read.

**The date/datetime/time literals are ONE candidate, not three.** 12 alone is under the bar; a single
temporal-shift operator over all three is 125 sites and comfortably over it.

**Three counting errors were made and corrected while producing this table, all the same shape**, and
they are recorded because the instrument is now the evidence:

1. `and`/`or` given C precedence, which reported ZERO claimable parens out of 763.
2. `opText` reading a childless token, which returned null for EVERY `comparison_expression` (the
   grammar wraps the operator in a `comparison_operator` node that has a child) and misfiled 529
   parens as "redundant".
3. `integer_literal` tested against a RAW kind. The grammar emits `integer`; `integer_literal` is the
   curated `ALNodeKind` name. This is [[R120]] exactly, and it made `subscript_expression` and
   `for_statement` report every site as claimable.

Each one produced a clean, plausible number. Only the compile probe and the cross-check against this
row's own earlier census caught them.

**Marginal footprint checked, and the numbers above are already marginal.** [[R171]] records that
R13's bar applies to the count of mutants an operator ADDS, not the raw sites, so every candidate was
re-measured against the spans the 20 shipped operators already claim on the same corpus. **Exact-span
overlap is 0 for all six**: no shipped operator claims a `parenthesized_expression`, a temporal
literal, a `subscript_expression` or a `foreach_statement` span. The claimable column IS the marginal
column.

One measurement was attempted and discarded rather than reported, because it looked meaningful and
is not: "is this candidate ENCLOSED by an already-claimed span" answers 100% for every candidate,
since `empty-block` claims whole procedure bodies and those contain everything. Enclosure is not
overlap, and a table showing "32 of 32 already covered" would have been a false refusal.

The one place the distinction bites is `subscript_expression`: `shift-integer` does not claim the
subscript span, but at the 90 sites whose index IS an integer literal it already claims the literal
INSIDE it and produces the same effect (`arr[1]` -> `arr[2]`). Those 90 are excluded above on effect
rather than on span, which is why the column reads 53 and not 143.

**CORRECTION, same day: the marginal check above used the WRONG definition, and the corrected one
refuses every remaining candidate.** The section above measured overlap at EXACT SPAN and concluded
"the claimable column IS the marginal column". That is not the test this row's own AOR spike used.
The spike's definition is "no fine-grained mutant already on the same STATEMENT", and R13's bar
applies to that. Re-measured properly:

| candidate | sites | marginal (statement) | |
| --- | ---: | ---: | --- |
| `parenthesized_expression` | 32 | **0** | all 32 already carry a `negate-conditional` mutant on the inner expression |
| temporal (`date`+`datetime`+`time`) | 125 | **7** | |
| `subscript_expression` | 53 | **2** | |
| `foreach_statement` | 13 | **0** | |
| `for_statement` | 46 | 0 claimable | unchanged, and for a sound independent reason |

So the answer to "which of these do we build next" is **none of them**, on the bar as written.

**But a clean sweep of refusals is the result that should be distrusted, and it did not survive a
control.** The same measurement applied to `lethal.swap-additive`, which this row BUILT and which the
project values, returns **3** marginal sites today against a bar of 13. Its own spike published 61,
and re-measured against the operator set as it stood on 2026-08-19 it returns 77. Nothing about the
operator changed; nine operators shipped in between, and each one makes the next candidate look
already-covered.

**That is a finding about the METHOD, not about these candidates, and it is filed as [[R181]].** The
bar tightens itself every time an operator lands, with nobody deciding that it should, and applied
today it would refuse work this project is glad it did. The remaining candidates' marginal counts
really are low and none of them is hereby recommended; what is no longer safe is reading "refuses" as
"measured and settled" when the same test refuses a shipped operator.

**Practical consequence for this row:** its remaining candidates are DEFERRED rather than refused,
pending R181. The one genuine refusal that stands on its own is `for_statement`, whose sites are
claimed by `shift-integer` outright rather than by a statement-granularity argument.
