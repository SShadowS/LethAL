**The code:**
- `readCgroupMemory` in `packages/runner/src/al-runner-v3-baseline-check.ts` reads `used = memory.current −
  inactive_file`.
- `scripts/heavy-slot-class.ts` (`readContainerMemory`) and `scripts/heavy-slot-guard.ts` use it for admission:
  `used + peak + reserve ≤ memory.max`.
- `active_file` stays in `used`. That is the page cache the kernel has recently touched, which it still reclaims under
  pressure before it kills anything.

**Measured** (lethal-code, 2026-11-22 01:52Z, `/sys/fs/cgroup/memory.stat`, three samples 5 s apart; only small jobs
running, no heavy slot held):

| part | MiB |
|---|---|
| memory.current | 8,551-8,561 |
| anon | 2,043-2,054 |
| active_file | 5,188 |
| inactive_file | 900 |
| shmem | 0 |
| **the guard's `used`** (current − inactive_file) | **7,650-7,660** |
| current − all file cache | 2,462-2,472 |

**The effect:** PR-303's A/B warm-up (`--peak 22`) was refused 659 times from 00:57Z.
- With a slot held, the refusal read "held slots' peaks 19.2 (1)".
- With NO slot held, it read "used 7.5 + peak 22 + reserve 4 = 33.5 > 32".
- With only `anon` counted, it would have been 2.4 + 22 + 4 = 28.4, which is admitted.
- The same 5.1 GiB of idle `active_file` made PR-302's own watchdog stop t1 at 01:48:48Z (preproc found that).

**The trade-off for kraken and the owner** (not decided here):
- Counting all file cache as free over-admits when the cache is the running jobs' own mapped binaries and corpora:
  reclaiming those makes the jobs thrash.
- Counting it all as used, as now, under-admits by the size of the idle cache.
- Options:
  - subtract `active_file` above a floor;
  - subtract all file cache, but keep the reserve;
  - or use `memory.stat`'s `workingset_*`, or PSI memory pressure, as the second check.
- Any change is a heavy-slot rule change, so it is kraken's and the owner's.
