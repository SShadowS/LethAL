**al-runner announces which BC artifact build it selected, and LethAL throws the line away.** Every
invocation prints to stderr:

```
[bc] no --bc-version given - selecting BC 28.1.49838.50794, the exact build this binary was
     compiled against. Override with --bc-version.
[bc] selected BC 28.1.49838.50794 (~/.local/share/al-runner/artifacts/28.1.49838.50794)
```

Nothing in `al-runner-transport.ts` reads either line, and no field of `SessionReport` carries the
answer. So a report says which al-runner BINARY ran (R123's contract probe pins five wire facts per
session, and the gate prints the version as its first line) but not which BC RUNTIME that binary
executed the tests against, which is the thing the verdicts actually depend on.

**Why this is provenance rather than correctness.** R101(a) originally called the default a
correctness hole — "the runner picks the latest artifact in the cache and does not print the
selection" — and that was CORRECTED by measurement: it does print it, and it pins to the build the
binary was compiled against rather than to whatever is on disk. Measured again on 2.1.1 with three
artifact versions present, the announcement is unchanged. So the selection is deterministic given
the binary, and the residual is only that the report cannot be read later to find out what it was.

**One thing makes it more than bookkeeping.** 2.1.1's own `--help` documents a DIFFERENT rule from
the one its runtime announces: "Default: the latest version present in
`~/.local/share/al-runner/artifacts`". If a future release ever makes the help text true, the
selection becomes machine-state-dependent, and a run that never recorded its BC build would give no
way to tell two differing runs apart after the fact. Capturing the line costs nothing now and is
the only thing that would make that transition detectable.

**Shape, not prescription.** Parse `[bc] selected BC <version>` off the stderr the transport already
captures and record it beside the al-runner version, most likely on
`ReportValidity.executionContexts` where the al-runner entry's `basis` already describes how that
runner executes. Passing `--bc-version` explicitly is a separate, weaker idea: it would make the
choice ours, but it would also mean a project whose symbols do not match our pin fails loudly for a
reason we introduced. R125 measured the version-mismatch failure mode already, and `--auto-provision`
resolving the version FROM THE PROJECT is what fixed it — pinning would work against that.

Filed 2026-08-08 out of R101(a), which is closed.

# CLOSED 2026-08-09

## What shipped

`parseAlRunnerBcBuild` (al-runner-transport.ts) reads the announcement; `OneShotTransport` records
the latest one it has seen and exposes it; `AlRunnerBackend.observedBcBuild()` forwards it;
`runSession` emits an `al-runner-bc-build` event after the mutant phase, which the fold carries onto
`ReportValidity.executionContexts[].bcBuild` and `.bcBuildAnnouncement`. `renderConsole` prints one
`BC RUNTIME:` line quoting the runner verbatim.

Three properties are asserted rather than described, each red-checked by breaking it:

- **`selected` beats `selecting`.** What was used, not what was intended.
- **The `[bc] ` line-start anchor is load-bearing.** Without it a test asserting on a version string
  in its own failure text is read as the runner's selection.
- **Never stamped on an authoritative (bcdev) context, nor on a CARRIED verdict.** bcdev's runtime is
  the container the config names, which the report already identifies; a carried verdict's BC build
  belongs to the run it came from.

## What this row got right, and the one thing it did not

Right: the lines are on stderr, the selection is deterministic given the binary, and `--bc-version`
is the wrong fix. Not right, and corrected in the source: `al-runner-transport.ts`'s
`parseAlRunnerPayload` doc comment described `[r2r]`/`[bc]` as part of a STDOUT banner. Measured
2026-08-09 on 2.1.1.0 they are on stderr. The parser scans both streams regardless, so a future
release moving its banner cannot silently stop the recording.

## Note on how this landed

Part of the plumbing (the transport parse, the event type, the fold field) was swept into R72's
commit by a `git add -A`, so this row's work spans two commits rather than one. Recorded here rather
than rewritten out of history.
