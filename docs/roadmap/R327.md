id: "R327"
title: "A split-header procedure placed after an object-level `var` section parses INSIDE that section's `var_body`, so it is not a member of its object"
section: "correctness-risks"
status: "open, filed 2026-09-29"
order: 1019
---

**Found while writing R-302's Task 1 tests (2026-09-29).** A hand-written codeunit with a global
`var` section first, then a `preproc_split_procedure` (`#if CLEAN27` header, `#else` header,
`#endif`, shared body), parses with the split node as a child of `var_section > var_body`, after the
variable declarations. The same codeunit with a PLAIN procedure in that position parses the
procedure as a sibling of the `var_section`, a direct member of `declaration_body`. Measured with
the native parser at `1280c6cc`; the repro is invented:

```al
codeunit 50100 "Repro T"
{
    var
        Y: Integer;

#if CLEAN27
    procedure Pick(X: Integer): Integer
#else
    procedure Pick(X: Integer): Integer
#endif
    begin
        exit(X);
    end;
}
```

**What it costs.** `declarationMembers` does not see such a member, so R302's symbol-table entry
for it is never built: its locals, parameters and return type do not resolve, and Tier-2 rule 3
cannot see it as a declared procedure. What the schemata and runner walks do with it (they walk
ancestors, not members) is NOT measured.

**How often.** Every one of the 22 split members in DC/Cloud (11) and BaseApp (11) is a direct
child of `declaration_body` (measured, a scratch walk over both corpora), so no pre-committed R-302
row is affected. BC code usually puts the global `var` section last, which is why none was seen.

**Closing.** Report it upstream on SShadowS/tree-sitter-al with the repro above (a grammar item, so
the fix is there), then pin a split member after a global `var` section in
`packages/engine/tests/ast/tree-walks.test.ts` as a direct member of its object.
