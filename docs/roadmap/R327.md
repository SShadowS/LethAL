**Found while writing R-302's Task 1 tests (2026-09-29); the risk was restated by the Task 1
review (I1).** A split-header procedure of R301's shape (`preproc_split_procedure`, one shared
`var` section) that follows the object's global `var` section parses as a child of that section's `var_body`, after the variable
declarations. A PLAIN procedure in the same place is a direct member of `declaration_body`. So
`declarationMembers` does not list the split member, and `buildSymbolTable` does not index it.

**What it cost, measured at `271c584b` (the version of this row before the rewrite said "its
names do not resolve", which was wrong: they resolved to the wrong thing).**

- **A false site that breaks the build.** `resolveProcedureAt` missed the unindexed member, the
  name fallback found nothing, and `resolveIdentifierType` and `lookupVar` fell through to the
  object's GLOBALS. Repro `r327-swallow` (hand-written): globals `X, Y: Integer`, then the split
  member `Pick(X: Integer; Y: Text)` calling `Show(X, Y)`. `swap-call-arguments` was emitted at the
  call and the instrumented project FAILED `alc` with AL0133 in both builds (`[]` and `[CLEAN27]`).
- **R324's shape through the back door.** A swallowed overload `Foo(T: Text): Text` did not count,
  so the plain `Foo(X: Integer): Integer` was "unique" and typed the call `Foo('x') + Foo('y')` as
  `Integer`. `swap-additive` was emitted and `alc` FAILED with AL0175 in both builds (repro
  `r327-overload`).
- **A wrong Tier-2 claim.** A table whose `SetRange` is a swallowed split member did not stop the
  claim on `R.SetRange(...)`: a mislabelled `remove-setrange` displaced the Tier-1
  `void-method-call` (repro `r327-setrange`; this one compiles, the label is what is wrong).

R316's preamble shape in the same position parses correctly (measured, a hand-written repro), so
it is not affected.

**How often.** Zero corpus members: all 22 split members in DC/Cloud (11) and BaseApp (11), the 26
in the R-302 repros and the 2 in the gate target are direct members of `declaration_body`
(measured with a scratch walk). System Application, BusinessFoundation and every fixture have none.

**Engine guard (R-302 fix round).** `swallowedSplitMembers` (`packages/engine/src/ast/tree-walks.ts`)
lists them. `declaresProcedure` counts them, `uniqueProcedure` counts their names (so a name one
of them declares is never unique), and `resolveIdentifierType` / `lookupVar` return `null` inside
a split member the table did not index, with no name fallback and no global fall-through. The three
repros are pinned through the real pipeline in
`packages/runner/tests/preproc-instrumentation.test.ts`, and `alc` of each instrumented project
passes under `[]` and `[CLEAN27]`. What remains: sites inside a swallowed member that need a type
are refused (under-generation, the safe direction), and the member is still not a member to any
other walk that uses `declarationMembers`.

**Known loss under the guard (R-302 review round 2, M8).** Inside a swallowed member,
`resolveVarRef` returns `null`, so the hang classifier cannot match a loop condition's variable.
Measured on a hand-written repro: `I += 1` inside `while I < 5` gives `remove-assignment` and
`shift-integer` mutants tagged `loop-condition-target` in the plain twin and UNTAGGED in the
swallowed member. The effect is fewer tagged mutants and a missing hang warning for that loop. The
tag drives only a warning and a report column, never a verdict. The same guard also drops the sites
that need a type (`r327-swallow` loses the `swap-additive` on `X + 1`).
**Fix:** index swallowed members the same way as direct split members, by passing
`swallowedSplitMembers(objectNode)` through `parseSplitProcedure` in `buildSymbolTable`. Types, the
hang tag, `uniqueProcedure` and the twin site set then behave as for a direct member. Ruled out of
R-302's scope.

**Closing.** The grammar fix upstream, then a pin that such a member is a direct member of its
object, then drop the guard's special case.

**Ruling, 2026-10-06 (R-339, one census with R339, R336 and R483).** Closed as a stated limit.
0 split members inside a `var_body` in 20,598 files (BC.History 17,451, DC 1,656, DO 814, CDO 677,
every fixture and example; `/coord/handoff/R-339/tools/census.ts`). A repro with a plain procedure
after the swallowed one, run through the real pipeline: every emitted mutant and the instrumented
project compile with `alc`; the swallowed member keeps its untyped sites (`empty-block`,
`return-value`) and loses the typed one (`swap-additive` on `X + 1`), as the guard intends
(`/coord/handoff/R-339/tools/probe.ts`, `out/probe.txt`). The guard stays; the indexing fix and the
grammar fix wait for a project that hits the shape.

## Draft upstream issue (not filed; SShadowS/tree-sitter-al)

> **A `#if`-split procedure after an object-level `var` section is parsed inside the `var_body`**
>
> Input (valid AL, compiles with `alc` with and without `CLEAN27`):
>
> ```al
> codeunit 50100 "Repro"
> {
>     var
>         X: Integer;
>
> #if CLEAN27
>     procedure Pick(X: Integer): Integer
> #else
>     procedure Pick(X: Integer): Integer
> #endif
>     begin
>         exit(X);
>     end;
> }
> ```
>
> Actual: `declaration_body > var_section > var_body > [variable_declaration,
> preproc_split_procedure]`.
>
> Expected: `declaration_body > [var_section, preproc_split_procedure]`, as for a plain
> `procedure` in the same position, which is already a sibling of the `var_section`.
>
> `preproc_split_procedure_preamble` (a per-arm `var` section after each header) in the same
> position parses correctly, as a sibling of the `var_section`. So does the plain case with the
> global `var` section placed after the procedure.
