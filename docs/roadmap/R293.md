title: "The cross-check's directive guard (R2) recognises only `preproc_conditional*`, so directive code under `preproc_split_*`, `preproc_fragmented_*` and 4.4.1's six new `preproc_*` kinds reads as UNEXPLAINED instead of guarded"

**Found by the issue #6 cross-check itself**, recorded rather than fixed
(`docs/measurements/2026-09-27-gh06-grammar-crosscheck.md`, section 6, and section 10.6 for the
4.4.1 widening).

**What happens.** The cross-check's own "guarded" column (rule R2) means "this compiler-only or
tree-sitter-only record sits inside a directive span, so the disagreement is expected, not a
finding." R2 tests for a tree-sitter `preproc_conditional*` span only — the container [[R214]]
names. But tree-sitter-al 4.x also builds other directive containers over the same kind of
retired-code shape: `preproc_split_*` and `preproc_fragmented_*` (clusters C2, C5, C6, C7 in run
002 and run 003). A record inside one of those is just as much "expected disagreement inside a
directive" as one inside a `preproc_conditional*` span, but R2 does not recognise the container, so
the record reads as UNEXPLAINED rather than guarded.

**Why it was not widened when it was found.** R2 was defined by `preproc_conditional*` before the
run (the pre-commitment's rule, fixed ahead of time). Section 6 of the measurement doc states the
gap explicitly at the point it was seen, and does not change the rule after reading the output:
"R2 was defined by `preproc_conditional*` before the run, and changing it after reading the output
would be editing the rule to fit the data. A future run should widen it under a new
pre-commitment." Every record C2, C5, C6 and C7 touch already has its own roadmap item — [[R285]]
for C2, [[R287]] for C5/C6/C7 — so nothing about the underlying LethAL gaps was left unfiled; only
the cross-check's own accounting of "guarded" undercounts.

**4.4.1 widens the gap to six more kinds.** tree-sitter-al 4.4.1's step A (upstream #24, #25) adds
six new named `preproc_*` kinds that R2 also does not recognise: `preproc_operand_prefix`,
`preproc_split_case_end_branch`, `preproc_split_case_statement_end`,
`preproc_split_report_brace_close`, `preproc_split_report_dataitem_header`,
`preproc_split_report_dataitem_open_over_endif` (TSAL-441 run 003, measurement doc section 10.6).
Any future disagreement sitting inside one of these six will read as UNEXPLAINED for the same
reason C2/C5/C6/C7 already do, on top of the existing gap.

**Why this needs its own pre-commitment rather than a quick edit.** Widening R2 changes the
cross-check harness's own rule, not just a roadmap row: every corpus's "guarded" and "UNEXPLAINED"
counts would move, and a rule change made without predicting its effect first is exactly the
mistake the pre-commitment discipline exists to prevent (`docs/superpowers/specs/`). Closing this
item means writing a pre-commitment naming the new R2 definition and the predicted effect on each
of the seven corpora, then re-running the cross-check on all seven and comparing against that
prediction, the same shape as [[R214]]'s own two-part discovery (over-claim, then the missed
under-claim half).

**Cost today.** None of these records change any verdict: every one is already routed to a filed
item by its cluster (C2 -> R285, C5/C6/C7 -> R287, C3 -> R286, C4 -> R216), so this is purely a
measurement-accounting gap in the harness's own summary, not a missed defect. The risk is only that
a future reader trusts the "guarded" column's count as complete.

**What would close it.** A new pre-commitment for `probe-grammar-crosscheck.ts`'s R2 rule that adds
`preproc_split_*`, `preproc_fragmented_*` and the six new 4.4.1 kinds to what "guarded" recognises,
with a predicted per-corpus effect, followed by a re-run of all seven corpora and a comparison
against that prediction.

See [[R214]], [[R285]] and [[R287]] for the LethAL-side gaps this guard's blind spot sits next to,
and `docs/measurements/2026-09-27-gh06-grammar-crosscheck.md` sections 6 and 10.6 for the
measurements above.
