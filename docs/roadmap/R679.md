**Filed and closed 2026-10-23 by lethal-bugs during R-658** (orchestrator ruling: fold it into R-658 if it is a
one-line message change with a test).

**What happened.** After the owner restarted bc3 on 23 Oct, `bc-linux-setup.ts --server bc3 --with-continia`
stopped with "the Microsoft apps are not all 28.4.53241.53758: no Continia app published". bc3's Microsoft apps read
28.4.53241.56646.
- The lane read that as "the pinned Continia stack no longer fits bc3", and reported it to the orchestrator as a
  re-pin problem.
- That was wrong. The setup header documents `--accept-build <v>`, and R594 ruled bc3 at `.56646` a new oracle: the
  R594 reports `bc3-A`/`bc3-B` were measured at that build. One flag reproduces the oracle's state.
- The stop message named neither the server's build nor the flag.

**Fix.** The P1 stop now names the server's Base Application build and says: "If this server's build (…) is a
deliberate new oracle, rerun with --accept-build <that build> (R594)". This is in `decideContinia`.
- Test: `decideContinia (R679)` in `scripts/bc-linux-setup.test.ts`, with Microsoft on another build. It stops, names
  that build and `--accept-build`, and publishes nothing.
- It goes red when the old message is put back (`/coord/handoff/R-658/red-r679.txt`).

**Builds on record (22-23 Oct, from existing logs, no new call):**
- bc1: Base and System Application 28.4.53241.56590 (`docs/measurements/r639/bc1-probe.json`).
- bc2: 28.4.53241.56646 (R-649's probe).
- bc3: 28.4.53241.56646 (R-658's probe, and its P1 read after the restart).

After the 23 Oct restart, bc3's Continia stack was republished with
`--with-continia --accept-build 28.4.53241.56646`. All 5 pinned apps were read back by sha256.
