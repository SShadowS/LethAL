## What broke, and for whom

[[R147]] exists to stop paying `--auto-provision` on every per-mutant al-runner invocation. Measured
2026-08-15: `--auto-provision` costs 17.1 s per invocation on a fully warm cache and re-downloads
2 x 115 MB of platform apps already on disk; pinning `--package-cache <dir>` instead costs 6.8 s and
downloads nothing. LethAL invokes the CLI once per (mutant x covering test), so that is paid on
every one.

The pin is established by parsing al-runner's own completion sentence:

```
[provision] Downloaded 6 app(s) (115 MB total) to C:\...\28.0.46665.53671\platform-apps
```

**That sentence is only printed when a download actually happens.** On a warm cache al-runner says
something else entirely, so `parseAlRunnerPlatformAppsDir` returned `no-completion-line`, the pin was
refused, and every invocation kept `--auto-provision`.

So the optimisation engaged **only on the runs that had just paid the download anyway**, and
disengaged on every run where it would have helped. That is close to the exact inverse of the
intended behaviour.

## How it was found, and what it says about the gate

Not by reading the code. `itest:alrunner` was run against **al-runner 2.7.0.0** (a four-minor jump
from the pinned 2.3.1.0) and failed its R147 assertion:

```
no execution context carries a `platformAppsDir` — this session did not pin al-runner's
platform-app directory, so every invocation paid --auto-provision again (R147).
```

The first hypothesis, and the obvious one for a four-version jump, was that al-runner had reworded
the sentence. **It had not**: the `Downloaded` line is byte-identical and still parses. Running the
provisioning invocation by hand is what showed the real cause — a warm cache prints

```
[provision] platform apps already complete at C:\Users\...\artifacts\28.0.46665.53952\platform-apps.
```

**The refusal message had named this possibility from the day it was written** — *"Either the cache
was already complete and the runner said nothing, or the wording moved"* — and nothing had ever acted
on it. The branch was documented, plausible, and dead.

## Why the gate had been green

`itest:alrunner`'s own doc records why this hid for so long: `--auto-provision` resolves the platform
apps at the PROJECT's version prefix, and that prefix resolves to whatever Microsoft published most
recently. A cache that was warm yesterday is cold the moment a new 28.0 build lands, so on many days
the gate ran cold, saw the `Downloaded` sentence, pinned, and passed. It was green for a reason that
had nothing to do with the code being right.

## The fix

`PLATFORM_APPS_ALREADY_COMPLETE` is read alongside the download sentence, and the parse result now
carries `basis: "downloaded" | "already-complete"` so the CALLER can tell the two apart:

- `"downloaded"` — the runner stated a count, so the directory must hold at least that many `.app`
  files. Unchanged; this is what catches a provisioning that stopped part-way.
- `"already-complete"` — the runner stated NO count. Inventing one would be the guess this parser
  exists to refuse, so `appCount` stays 0 and the caller applies the strongest honest check
  available: the directory must be non-empty. Weaker, and recorded in the type rather than hidden.

**Two sibling sentences in the same output are the traps**, and both are pinned by test as things
that must NOT match:

| line | why it must be rejected |
| --- | --- |
| `[provision] BC <build> engine artifacts already complete at <dir>.` | identical phrasing for the ENGINE directory, which must never be pinned as a package cache |
| `[provision] test toolkit already present at <dir>/test-apps.` | different noun phrase AND a different directory |

The trailing full stop belongs to the sentence, not the path, and is consumed outside the capture
group — asserted directly, because a pinned directory ending in `.` would be a plausible-looking
wrong answer.

A cold run prints BOTH sentences (`--auto-provision` provisions twice, [[R130]]), so both are scanned
into one set: agreeing spellings are one answer, and two DIFFERENT directories still return
`conflicting` and pin nothing.

## Evidence

- Red-checked: removing the new scan reds exactly the four new warm-cache tests and leaves the other
  28 in that file green.
- `itest:alrunner` **PASSES** on 2.7.0.0 with a warm cache and now prints
  `platform apps pinned at: C:\Users\...\artifacts\28.0.46665.53952\platform-apps`.
- All 19 per-mutant verdicts unchanged across the 2.3.1.0 -> 2.7.0.0 jump: **3 / 16 / 0**.
- The 2.7.0 contract measurement, including `--auto-provision` becoming the default and the new
  `provision` subcommand, is in `docs/measurements/README.md` §"al-runner v2".
