Found in lane-preproc's CI (attempt 1 red, green on re-run), 2026-11-13; coord task R-963. Related: [[R972]] (R960: six slot
files, memory-only admission), [[R967]] (a different queue test's race), [[R952]] (the queue).

**Cause (measured).** The test held slots 1-3 so that both `--wait` waiters had to queue, then freed slot 1 and expected A before
B. Since R960 there are six slot files, so three stayed free: a waiter could take one at once, before the test had both tickets
in place, and the order the test checks was never set up. Reproduced on master: 2 failures in 12 runs. My own change (R-960)
introduced it: the tests that hold "all" slots were not all moved to six.

**Fixed (coord R-963).** The test holds every slot (`SLOTS`) and frees only slot 1. It also gets a roomy fake cgroup (1 of 64
GiB), so the memory rule decides, as in the container: with no cgroup limit the count fallback would refuse beside five held
slots, and no waiter would ever run. 12 runs in a row pass. Red: a queue that serves the newest ticket first fails it (B, A).
The other heavy-slot tests were checked for a hard-coded slot count: "all slots held: exit 75" held three and passed only
because the count fallback refused; it now holds `SLOTS` and asserts the "all heavy slots held" message, which `heavy-slot.sh`
now prints apart from a guard refusal (red with three slots held). The loops over six slots in `corpus-snapshot.test.ts` use
`SLOTS`. Every other fixed slot number in the tests is deliberate (a count-fallback case, or a stated number of held slots).
