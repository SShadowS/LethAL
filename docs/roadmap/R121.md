**A false kill is now visible in the record but nothing classifies it.** R86 closed the READ: every
killed mutant carries `MutantOutcome.killingTestFailure`, the failing run's own text, so a reader who
looks can tell BC's *"The length of the string is 18, but it must be less than or equal to 10
characters"* apart from `Assert.AreEqual failed`. What LethAL still does not do is say which is which,
so nothing counts them, nothing warns, and R85's kill-rate split (a real kill rate versus a
platform-artifact one) has no input.

**The obvious rule is measured WRONG and must not be revived.** R86 first proposed that a top
callstack frame inside the TARGET app identifies a platform artifact. Classified over all 109
mutant-attributed failing rows in run 148: **4 rows matched, and only ONE was arm E.** The other
three (M0059, M0062, M0066) are ordinary kills where the target's own `TestField`/`Get` raised —
*"Category must have a value in Data Main"*, *"The Data Main does not exist"* — which R82's spec §4
insists must read as REAL kills, because production validation catching a bad state is exactly what a
test suite is entitled to credit. **75% false-positive rate on the only run the rule has ever been
checked against.** Shipping it as a `cause` would have been worse than the silence it replaced.

**The candidate that the data does support, and which is not yet measured:** the failing frame's
statement is not the MUTATED statement, AND the message is a platform-class error. Both halves need
their own measurement before either is written down as fact. The first half needs the mutated
statement's location compared against the top frame, which the record now has on both sides; the
second half needs a closed list of platform-raised message shapes, and that is where the trouble is.

**Two structural obstacles, both measured elsewhere:**

- **The message is PROSE and it localises.** R66 measured that class. An English-sentence detector is
  an English-only detector, and BC ships in dozens of languages. Anything keyed on message TEXT has
  that ceiling by construction; anything keyed on structure (which frame, which statement) does not.
- **The fixture cannot stand in for a real suite.** All 22 tests in `fixtures/sandbox-data-tests`
  raise via bare `Error(...)`. Continia Document Output's suite uses Microsoft's Library Assert
  ~1,886 times, which puts a THIRD app on top of the callstack — a shape no gate here has ever seen.
  A rule tuned on the fixture would be tuned on the wrong stack shape.

**`lethal explain` still projects no kills at all**, and deliberately so: it lists survivors and
`error` outcomes because "nothing keys a kill beyond the verdict word itself". A classifier would be
the first thing that does key one, so the explain surface belongs with the rule and not before it —
adding a kills section now would mean projecting free text the contract forbids consumers to parse.

Per R72's discipline a diagnosis must NOT move a verdict, whatever the rule turns out to be: a killed
mutant stays killed, this is a `cause`-shaped annotation, never a re-scoring. Changing that would
invalidate every frozen gate figure in `CLAUDE.md` and every committed baseline under
`docs/campaign/`.

Evidence: `docs/roadmap/R086.md` (the falsification, re-measured independently by an adversarial
review of the landed work); `docs/measurements/README.md` §"R82 live". Filed 2026-08-07 when R86
landed the record without the classifier.

Two things that matter for building the classifier:

- **All three have the TARGET app on top of the callstack** — `CDO Essential Module License` raising

  top-frame-in-target rule, on top of the four already measured, and they fail it in the opposite
  direction from M0059/M0062/M0066: those were real kills the rule called artifacts, these are
  artifacts the rule would also call artifacts, for the wrong reason.
- **The candidate rule this row proposes looks right on them.** The failing frame's statement
  (`RegisterModuleFeatures line 42`) is not the mutated statement, and the message is a platform

The suite's own assertion in all three cases is unrelated — the killing test is about feature-enabled
messaging and asserts nothing about names or descriptions — which is exactly the reader judgement the
classifier would have to automate.

# MEASURED 2026-08-08 against a real 73-kill corpus

The corpus this row was blocked on now exists and is committed:
`docs/campaign/2026-08-08-r85-swap-population/` deployed the whole `swap-call-arguments` population
on Continia Document Output and produced **73 kills, every one carrying its `killingTestFailure`**.
Each was classified BY HAND for the campaign's own false-kill obligation, before any rule was
written, so the labels are not something invented to make a rule look good: **6 FALSE (the arm-E
field-length shape), 67 real** (50 where a test's own `Assert.*` failed, 17 where the mutated
program errored on its own wrong behaviour).

`scripts/r121-classify-eval.ts` scores rules against it and is re-runnable against any report.
Output committed at `docs/campaign/2026-08-08-r85-swap-population/rung2.r121-eval.txt`.

## This row's candidate rule is wrong, and here is exactly why

**Half 1 is backwards.** The row says the failing frame's statement "is not the MUTATED statement",
citing `RegisterModuleFeatures line 42` against a mutation this report places at file line 62. Those
are different units: **an AL callstack line number is PROCEDURE-RELATIVE**, and the mutant's `line`
is a FILE line. Comparing them at all requires the procedure's start line, which no field of the
report carries — so the half the row calls ready ("the record now has it on both sides") is the one
the record cannot express.

At the finest granularity the record DOES support, procedure name, the measurement is unambiguous
and points the other way: **all 6 false kills raise inside the mutated procedure.** Of course they
do — a field-width rejection happens at the assignment the swap corrupted. B1 therefore flags 61 of
73 and catches none of the 6.

That is the second time a rule was written from an example rather than from a corpus, and the second
time the corpus reversed it. The pattern is worth naming: both failures came from comparing things
that are not comparable (an app name against a role; a procedure-relative line against a file line).

## What the corpus DOES support, and what it does not

- **No structural rule reaches usable precision.** The best is B1-inverted at 50% — a coin flip.
  Shipping it as a `cause` would mislabel 6 real kills as artifacts on this project alone.
- **The only 100%-precision rule is the message TEXT**, and it is 100% by construction, because the
  field-length shape IS the ground-truth definition. It is also English-only (R66), so its ceiling
  is a property of the approach, not of the tuning.
- **B2 is not a classifier but it is a perfect SCREEN.** "The message does not begin with `Assert.`"
  flags 23 of 73 with **100% recall** — it never misses a false kill. That is enough to say
  *"23 of your 73 kills were not produced by a test assertion; read them"* without claiming any one
  of them is false, which is a `cause`-shaped annotation that cannot move a verdict.

**The screen's limitation is measured, not assumed, and it is why this is not shipped yet.** B2
depends on the target suite's assertion style. Document Output uses Microsoft's Library Assert
~1,886 times, so the prefix is meaningful there. All 22 tests in `fixtures/sandbox-data-tests` raise
via bare `Error(...)`, so on the tables gate B2 would flag **every** kill and screen nothing. A
screen that is informative on one suite and vacuous on another must say which it is doing, and
deciding that needs the second real project this row has never had.

## What is now settled, and what a next step would be

Settled: the corpus exists, is committed, and is re-scorable; three rules are refuted with numbers
rather than argument; the arm-E shape's structural signature is the opposite of what was assumed.

A next step, in order:

1. **Ship B2 as a SCREEN, not a classifier**, with wording that says only "no test assertion
   produced this failure" and a count. Needs a gate, and needs an answer to the bare-`Error()` suite
   above, most likely by reporting the screen's own coverage ("23 of 73 kills, of which the screen
   distinguishes nothing when a suite asserts via `Error`").
2. **A second real project.** Everything above is one suite's assertion style and one operator's
   kills. R101(f) measured a discriminator on the al-runner path that does NOT localise (an
   `out-of-scope: ` message prefix emitted by the runner itself, not by BC), which is the first
   non-English-only signal anyone has found for this problem — but it is al-runner-only and the
   authoritative backend is bcdev.

Per R72's discipline this stays a `cause`-shaped annotation whatever it becomes. Re-scoring would
invalidate every frozen gate figure and every committed campaign baseline, including the one this
measurement is built on.
