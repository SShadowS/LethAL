**What.** `swap-modify-flag` turns `Delete(true)` into `Delete(false)`. R138 tags only the skipped
`Insert` trigger as a platform-kill mechanism (`run-trigger-skipped-insert`, narrowed by R143), on
the reasoning that a skipped `OnDelete` or `OnModify` only writes less and so cannot make a later
statement raise. That reasoning is wrong in one real shape: an `OnDelete` that deletes child rows.
With the trigger skipped the children stay, and a later insert of a child with the same key fails
with a duplicate-key error that no test asserted. That kill is a platform artifact of the same class
as `Insert(false)`'s duplicate key, and today it would be scored `killed` with no tag.

**Not yet shown.** No measured kill is known to be this. A program can also raise on genuinely wrong
behaviour without an assertion (R121), so an untagged `Delete(false)` kill is a lead, not a false
kill.

**What would close it.** A live, pre-committed fixture arm on `sandbox-data`: a parent table whose
`OnDelete` deletes children, a test that deletes the parent and re-inserts a child with the same key,
and a test that asserts the children are gone. Pre-commit which kills are assertion-earned and which
are platform-only. Then decide whether a `run-trigger-skipped-delete` mechanism and an R143-style,
receiver- and trigger-aware detector are warranted (resolve the receiver's table, read its
`OnDelete`, keep the tag where the table cannot be resolved or a subscriber may act). Verdicts do not
change; only the screen does.

**Ruling (2026-10-05, R-281).** Closed by a ruling, with no new fixture arm. Plan:
`docs/superpowers/plans/2026-10-05-R-281-run-trigger-skipped-delete.md`.

- `lethal.swap-modify-flag`'s `Delete(true) -> Delete(false)` mutants now declare a new mechanism,
  `run-trigger-skipped-delete`. The tag is syntactic and never moves a verdict. `Insert` keeps its
  R143 tagging unchanged; `Modify` stays untagged.
- The tag is dropped only when `deleteSkipCanRaise` (`forced-trigger-raise.ts`) PROVES the skip
  harmless: the table resolves, its file arm is decided, no same-project delete-event subscriber or
  `tableextension` `OnBeforeDelete`/`OnAfterDelete` exists (an event name quoted or not), and its
  `OnDelete` is absent or calls only what the exported helper `isHarmlessTriggerCall` proves
  harmless (non-writing Record methods claimed by `claimsRecordMethod`, `Modify`/`Delete` on
  `Rec`/`xRec` outside any `with`, unqualified `Error`/`Message`/`Confirm`). The own-row list is per
  trigger, so for R-213's `OnModify` a `Rec.Delete()` is not harmless. Everything else keeps the
  tag: an unresolved table, a write to another record, a call inside `with`, any project or codeunit
  call, a shadowed name. Calls written without parentheses keep it too: a statement call
  (`CleanUp;`), a qualified call that is not a project field read (`Kid.DeleteAll;`), and any name
  of a procedure on the table or its project tableextensions (`if CleanUpChildren then`).
- **Limits of that reading.** A parenthesis-less call used as a value is recognised only by name
  against the table's own and project-extension procedures, so one declared in another app's
  tableextension is unseen. Subscribers are found by the `EventSubscriber` attribute in this
  project only.
- Measured before building (survey, scratch scripts, not committed): in Base Application, 139 of 286
  `Delete(true)` sites have an `OnDelete` that deletes other rows; in Continia Document Output, 3 of
  the 13 sites whose table resolves. Most sites do not resolve and keep the tag (BC.History 1484 of
  1797, CDO 76 of 89, mostly test apps). Sites that lose the tag: BC.History 81, CDO 10, fixtures 0;
  almost all have no `OnDelete`. 4 BC.History sites keep it only because of a same-project
  subscriber; no table that loses the tag has a delete subscriber or extension trigger in another
  app of either corpus.
- Only `itest:tables` moves: `Data Flag Ops.DeleteWithTrigger`'s killed `Delete(true)` mutant gains
  the tag (its `OnDelete` inserts a tombstone row), so `platformArtifactKills.killedCount` 2 -> 3.
  That is an OVER-TAG: the kill is earned by the test's own `Error`. The gate change is
  pre-committed and run separately.
- **Not measured, stated plainly.** The duplicate-key route itself stays UNMEASURED live for
  `Delete`: no gate kills a mutant that way. Whether `RunTrigger` changes how BC deletes record
  links, notes or media is unmeasured. A delete subscriber or `tableextension` in ANOTHER app (the
  test app, say) is invisible to the detector; that limit is in the report's explanation.
