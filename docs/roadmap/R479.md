**Found 2026-10-05 by the post-merge gpt-6.1-sol review of R-473** (`/coord/reviews/postmerge-R-473/sol.md`;
static review, not run). R-473 itself is clean: no regression, no key move.

`receiverUnresolved` (`packages/engine/src/semantic/receiver.ts`) rejects every receiverless call, and
`claimsRecordMethod` refuses implicit calls inside a `pageextension` by design (R30/R67: the extended
page's `SourceTable` is usually in another app). So a bare `Insert(true)`, `Modify(true)` or
`Delete(true)` in a pageextension stays with `flip-boolean-literal` and its true -> false flip carries
NO `run-trigger-skipped-*` tag, while `Rec.Insert(true)` there gets the tag through R-473. That is
the under-tag direction, and `runTriggerTag` in `flip-boolean-literal.ts` inherits it.

**To close.** Measure the bare shape in pageextensions (and anywhere else an implicit receiver is
refused) on BaseApp and CDO. Then treat a receiverless RunTrigger call whose implicit record is
refused as unresolved FOR TAGGING ONLY (keep the tag; the claiming refusal stays), the same rule
R-364, R-460 and R-473 apply. Tag-only, so no key should move; prove it with an exact site diff. Pin
both directions, red-checked. Check the overlap with [[R464]] (the implicit-record resolver) first.

Also noted, minor, no action: a parenthesised literal (`X.Modify((true))`) is untagged by design and
pinned by "does NOT tag a parenthesised (true) RunTrigger".

**Done (2026-10-05, 9d34135a; review fix 2026-10-06, f2153aac).** Evidence: the coord handoff `R-479` (`survey.md`, `plan.md`,
`build.md`).

*Cause.* `receiverUnresolved` returned `false` at its first check for any call with no receiver.
A bare call whose implicit record could not be proven was therefore "not claimed" but never
"unresolved", and `runTriggerTag` dropped the tag. `Rec.Insert(true)` in the same pageextension
reaches the qualified resolver, finds the pageextension scope with no table, counts as unresolved
and keeps it.

*Fix.* `receiverUnresolved` sends a bare call to `implicitRecordUnresolved`, which reads the same
`recordScopesAt` that R464 built. Claiming is unchanged, so `swap-modify-flag` still does not claim
these calls. Both directions: `true` keeps the skip tag of its kind, `false` gets
`run-trigger-forced` (R460's branch). The rule applies to every RunTrigger argument `runTriggerTag`
knows, so a bare `ModifyAll(..., true)`, `DeleteAll(true)` or `Insert(true, X)` (and their
`false` forms) is tagged in the same places; that is intended.

Tagged (a bare call, the innermost record scope exists, none of the exclusions below applies):
a pageextension's `Rec`; a reportextension's `modify(X)` trigger, request page and added dataitem
(every bare record call in a reportextension, which Tier 2 never claims); a `with` whose subject
has no table this project can prove, including one with no declaration the index can see.

Not tagged, checked in this order before the reportextension case:
- no record scope at all (a page without `SourceTable`, a codeunit outside a TableNo `OnRun`, a
  plain report body): the call is not a record method;
- a name the enclosing object (or the reportextension) declares as its own procedure;
- a name the project declares on the scope's KNOWN table or a tableextension of it (rule 3), for
  example a reportextension dataitem on a project table with its own `Modify(Boolean)`;
- a `with` whose subject is DECLARED as a non-record (a codeunit variable), read through the
  extension's own variable scope inside a reportextension.
Contexts R464 already resolves (table, tableextension, page with `SourceTable`, TableNo `OnRun`,
report dataitems, `with` on a known record) behave as before: claimed calls are ceded or judged by
proof. A project procedure reached some other way (for example through a `with` on a record whose
table this project cannot see) is not excluded and is tagged; that is the over-tag direction R143
accepts for a screen.

*Review fix (sol final r1, f2153aac).* The first build checked "in a reportextension" before the
exclusions, so a project table's own `Modify` on an added dataitem and a codeunit `with` inside a
reportextension were tagged. Both are now excluded first.

*Measured* (complete spec dumps, every operator at every node, master 2bced9a6 against the branch,
by identity key): 0 added, 0 removed, 0 changed, so 0 keys moved, on the fixtures (17 projects,
1,612 rows), examples (4, 177), CDO (6, 57,755), DC (14, 193,011), DO (7, 81,503) and BC.History
(519, 2,298,868). No corpus has the shape: a text search finds no bare RunTrigger call in any
pageextension or reportextension there. A scratch probe project shows the change, 10 rows retagged
(pageextension 7, reportextension 3), with no other difference and 0 keys moved. No fixture row
moves, so no gate pin (`itest:tables`' `platformArtifactKills` included) changes, and no identity
scheme or operator version changes. Re-measured after the review fix, same sets, same method:
again 0 added, 0 removed, 0 changed everywhere; the probe's same 10 rows.

*Why build it with an empty diff.* A bare `Modify(true)` in a pageextension trigger is ordinary
customer code; these corpora simply lack it. And this is the under-tag direction: an untagged flip
whose kill came from a skipped trigger would be counted as an honest kill.

*Tests* in `flip-boolean-literal.test.ts`: "tags a bare RunTrigger call on a pageextension's
implicit Rec, both directions" (also: no claim, and a reportextension `modify` trigger) and "keeps a
bare call untagged where its binding is known". RED-CHECKED, each revert red then restored green:
bare branch back to `false` (the first test); drop the unknown-table check, the own-procedure
guard, or the non-record `with` check (the second test, one assertion each); stop ceding a claimed
sole `true` (the second test, plus R473's test and "still cedes a sole Insert(true)"). The second
test's own-procedure and codeunit-`with` controls cover `true` and `false`. "keeps a
reportextension's bare project procedure and codeunit `with` untagged" pins the review fix, both
directions, with a tagged dataitem control; red under: drop the known-table rule-3 check (the
project-procedure case), drop the non-record `with` check (this test and the second), and drop
only the reportextension variable lookup (this test alone).
