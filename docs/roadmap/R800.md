**Evidence:** `/coord/handoff/R-798/measure.md` (sections 3 and 4), `/coord/handoff/R-798/ab2.out`, `ab3.out`,
`r790-ab.out`. Related: [[R790]], [[R798]], [[R586]].

**What.** The same alc batch compile of D1 takes 6.5 s alone and 8.1-9.4 s with one al-runner call running beside it
(three runs each, same commands outside LethAL, load 5-6). With alc pinned to cores 0-15 and the call to 16-31, alc was
still 1.1-1.5 s slower. The CPU time (user + sys) is the same alone and beside the call (31-35 s against 30-39 s): alc
does not do more work, it waits. `nice -n 19` on the call did not relieve it (R-798 A/B, ab2 and ab3). So the cost is
not CPU scheduling. It looks like memory bandwidth or cache contention: both processes are heavy on memory (alc is a
.NET server GC; the call compiles the same AL).

**Why it matters.** It is the main reason R790's speculative baseline does not pay (it saves a 2.6 s baseline and
costs 1.5-2 s of alc wall plus about 1 s of extra prep). R790 is therefore opt-in (`LETHAL_V3_SPECULATE_BASELINE=1`).

**Re-measured 2026-11-08 (coord task R-880), and not reproduced.** Same D1 batch (copied from a v3-timing d1 run), alc
18.1.2842859, al-runner `current` = 3.0.0-alpha.13+edge.20261108 (897b441eb). One `al-runner test` call started first,
alc 0.65 s later, exactly as R-798. 7 pairs, alone and beside interleaved, one heavy slot per run, runs started only
when the 1-minute load was under 10 (or after 240 s of waiting). Logs: `/coord/handoff/R-880/base2.out`, scripts
`ab.sh`, `alc1.sh`, `call1.sh` in the same folder.

| alc, D1 batch | median wall | wall range | median CPU (user + sys) | load at start |
| --- | --- | --- | --- | --- |
| alone | 9.50 s | 8.09-10.18 | 26.46 s | 7.7-15.1 |
| beside one call | 8.74 s | 8.55-9.71 | 26.58 s | 7.7-9.8 (first run: 244, a spike from other jobs) |

Beside is not slower: the median is 0.76 s lower and inside the spread of the alone runs (2.1 s). The call's own wall
was 3.0-3.5 s (median 3.20 s, CPU about 7 s). An earlier batch of 7 pairs at load 20-90 (other lanes' jobs, `base.out`)
was too noisy to read (alone 11.3-19.7 s, beside 11.9-20.2 s) and is not used. alc alone is now 9.5 s, not 6.5 s: the
machine is busier than in R-798 and the alc build differs, so the absolute figure is not comparable. What is
comparable is that the 1.5-2 s beside-penalty is gone. R-798's runs were at load 5-6, this one at 8-12. So the
penalty was either fixed by a newer al-runner build or alc, or never a memory effect. No fix was tried: nothing to fix.
R790's opt-in ruling rested on this penalty, so a fresh `r790-ab.sh`-style on/off timing of the whole D1 run (R-798's
method) is the next step if the owner wants to revisit it; this item does not change the default.

**Ideas (not built; no longer needed).**
- Start the speculative call after alc's front end, when alc's memory use is steadier, so the two overlap less.
- Speculate only on a machine that measures a gain (a one-time calibration, cached like the probe).
- Cut the extra prep first (the `alc-src` copy of 0.54 s, the sync `boundKey` of 0.26 s): measure.md section 5, E and F.
- Check whether `DOTNET_GCHeapCount` or `DOTNET_GCgen0size` for alc changes the contention.
