**Evidence:** `/coord/handoff/R-798/measure.md` (sections 3 and 4), `/coord/handoff/R-798/ab2.out`, `ab3.out`,
`r790-ab.out`. Related: [[R790]], [[R798]], [[R586]].

**What.** The same alc batch compile of D1 takes 6.5 s alone and 8.1-9.4 s with one al-runner call running beside it
(three runs each, same commands outside LethAL, load 5-6). With alc pinned to cores 0-15 and the call to 16-31, alc was
still 1.1-1.5 s slower. The CPU time (user + sys) is the same alone and beside the call (31-35 s against 30-39 s): alc
does not do more work, it waits. `nice -n 19` on the call did not relieve it (R-798 A/B, ab2 and ab3). So the cost is
not CPU scheduling. It looks like memory bandwidth or cache contention: both processes are heavy on memory (alc is a
.NET server GC; the call compiles the same AL).

**Why it matters.** It is the main reason R790's speculative baseline does not pay (it saves a 2.6 s baseline and
costs 1.5-2 s of alc wall plus about 1 s of extra prep). R790 is therefore opt-in (`LETHAL_V3_SPECULATE_BASELINE=1`).

**Ideas (none built).**
- Start the speculative call after alc's front end, when alc's memory use is steadier, so the two overlap less.
- Speculate only on a machine that measures a gain (a one-time calibration, cached like the probe).
- Cut the extra prep first (the `alc-src` copy of 0.54 s, the sync `boundKey` of 0.26 s): measure.md section 5, E and F.
- Check whether `DOTNET_GCHeapCount` or `DOTNET_GCgen0size` for alc changes the contention.
