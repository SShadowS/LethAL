**Filed 2026-10-22 by lethal-bugs during R-647** (orchestrator ruling; R-647's pre-commitment r10 names this item).

**What.** The al-runner v3 update gate's leg X (d) is the only live check that LethAL's §6 Sleep rule fires. Its probe's
only covering test, `SleeperDoubles`, starts with `Sleep(600000)`. Upstream edge builds now count a virtual Sleep
toward the test time limit (leg C's `sleep-is-noop` reads `gone`), so on edge that test exceeds the 120 s baseline
timeout, is not green at baseline, and every X (d) mutant reads no-coverage. r10 keeps X (d) a gate-fail with
diagnostics only, so every such edge build is `gate-fail` on X, and `current` stays on alpha.2. That is the correct
outcome until BC's own behaviour is measured; it is not to be worked around.

**To measure (an al-probe on one leased bc server, apps removed and read back absent afterwards).**
1. Does BC's `Sleep(600000)` really wait 600 s in a test codeunit run through LethAL's harness?
2. Does it hit the harness's test timeout (LethAL Control's budget, or the session's), and with what row or text?
3. A short `Sleep` (for example 100 ms) control: waits, passes.

**To close.** Re-cast X (d) from that measurement in a pre-commitment delta (for example a shorter Sleep that still
proves the rule, or the timeout row as BC's own reading), run `itest:alrunner-v3`, then `--edge-rejudge` at the new
commit.

Evidence: R-647's diagnosis (`/coord/handoff/R-647/diagnosis.md`); the edge rejudge's kept log
(`/work/tools/al-runner-v3/rejudge/edge-57f1e4f98@711c94d9…/gate.log`); r10.
