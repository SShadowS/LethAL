**Nothing lets a user predict the DEPLOYED mutant count, and the two available numbers differ by enough to break a plan.** `--dry-run` reports mutation **sites** (raw specs); `SessionReport.mutants[]` holds **deployed** mutants after §3.2 dedup drops a Tier-1 mutant wherever a Tier-2 operator claims the same site. Measured on DO: **176 sites → 148 deployed** (-16%), **991 → 973**, **476 → 473**. The gap is not a constant and depends on the operator mix of the specific file. This is not cosmetic: the campaign's own rung-1 gate pre-committed the site count as the expected mutant count and `assertCardinality` correctly refused every anchor until it was corrected — the tool was right and the plan was wrong, but nothing in the tool's output would have prevented the mistake. Capacity planning, cost estimation and any pre-committed cardinality all need the deployed figure BEFORE the run. Cheapest fix: have `--dry-run` report both, since it already runs `generateMutationSet` and dedup is pure. Evidence: `docs/campaign/2026-08-03-do/rung0.precommit.md`, `rung1.result.md`.
