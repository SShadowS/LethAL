**Measured.** The config template named `CRONUS Danmark A/S`; the hosted sandbox has
`CRONUS UK Ltd.` and `My Company`. `doctor` reported `control-version` and `lease` both FAILED with
BC's *"The company "CRONUS Danmark A/S" does not exist"*, which is right but was the third failure
the operator read that morning, after `envId` and the control app, each found one run at a time.

**Fix.** A `company` check that lists `/api/v2.0/companies` (the operator did exactly this by hand)
and fails with the configured name and the names that exist, placed before the checks that need a
company. It joins the pinned check list in `doctor`'s tests and the agent contract.

## OUTCOME, 2026-09-02

`HarnessVerifier.fetchCompanies` GETs `api/v2.0/companies` with the tenant and basic auth and
never the company (a company that does not exist would fail the call meant to say so); a 401 is a
`HarnessAuthError` as for HarnessInfo, and a body without a `value` array or a row without a string
`name` is refused rather than read as "no companies". The doctor dep returns the RESOLVED company
beside the names from one lazy call, so on an env-tool config a tool failure stays a failing check
instead of aborting the report (the first version resolved eagerly in `buildDoctorDeps` and broke
exactly that test). The check is listed before `control-version`.

Live on Cronus283: `[ok] company: "CRONUS Danmark A/S" exists`; with the company set to
`CRONUS Sverige AB`: `[FAIL] company: ... the server has: "CRONUS Danmark A/S", "My Company"`,
with environment, control-version and lease all failing beside it on BC's 404, which is the
before-picture the row was filed on. Tests: six on the check, four on the read. Full suite 2662.
