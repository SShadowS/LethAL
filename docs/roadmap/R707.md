**Filed 2026-10-24 by lethal-preproc during R-623**, from its build review.

**What.** R-623 measured an in-place same-version publish of a target under an installed dependent on bc2
(`/coord/handoff/R-623/measure.md`, step 2). It replaced the target's bytes in one installed row, and the dependent
stayed installed. But only a procedure BODY changed, and the dependent was never run. Not measured:
- whether BC recompiles an installed dependent when its target's public procedures change their signatures;
- whether the dependent's code then runs against the new target, errors, or is refused.

The same is true of an ordinary upgrade (setup's row 5), which never checked dependents either, so this predates
R-623.

**Why it is not a false-kill risk.** `StaleTestAppError` (R56) fires only when a test method is missing, never on a
symbol change. If a dependent's compiled code breaks against the new target, its tests error at baseline and leave
the green set, so their mutants read `no-coverage`. That is under-reporting, never a test passing against code it was
not built for while also killing a mutant. Setup also compiles every tests app against the new local target before
it publishes anything, so a change that breaks a tests app's SOURCE stops setup with nothing published. And every gate
republishes its own instrumented target at a minted, higher version under the installed tests app.

**One related gap.** `bc-republish.ts republish <target>` compiles only the requested apps, so it does not run that
source check for the target's dependents.

**To close.** Measure it once on a lane's own server: a target republished with a changed public procedure signature
under an installed dependent that calls it, then the dependent run (a web-service probe, the al-probe skill's
topology). If useful, add the dependents' compile check to `bc-republish.ts`.

## Measured and closed (R-707, 2026-10-24)

Run on bc2 by `scripts/r707-probe/drive.ts --all` (08:01Z, pre-commitment `4e310924`); full record in
`/coord/handoff/R-707/measure.md`. Target A, dependent B, B's web service called to prove it runs.

| step | result |
|---|---|
| 1 | A1 and B published (200), one installed row each |
| 2 (control) | B's web service call answers 200, value 1 |
| 3 | A1s (same version, `Answer(X)`) in place under installed B: refused 422, `AL0135` on B; "The original extensions have been restored."; A is still A1, B installed, B's call still 1 |
| 4 | A2r (1.0.0.2, `Answer` removed), an upgrade under installed B: refused 422, `AL0132` on B; "The original extensions could not be restored"; afterwards A is 1.0.0.1 uninstalled, B has no row, B's call 404 |
| 5 | not run (the state after step 4 was not as expected) |
| cleanup | A's uninstalled row unpublished (204); both absent |

So BC recompiles every installed dependent from its own source at publish and refuses a breaking change, for a
same-version publish and for an upgrade. No stale dependent can be measured; the "dangerous" row did not happen.
The new finding, a refused upgrade that cannot restore, is filed as [[R709]]. The gap in `bc-republish.ts` is
closed: it compiles each unrequested fixture dependent against the new target build and refuses
`dependent-breaks` before anything is sent.
