Found by PR-209's spec-adversary (lethal-preproc, 2026-11-19) before the build that makes `condition-true` default-on.
Probed on `conditionTrue.generate` over parsed, invented AL. Related: [[R868]], [[R164]], [[R834]], PR-187.

**The shape.**
```al
local procedure NextRow(): Integer
begin
    if Walked < Rows then
        exit(1);
    exit(0);
end;
...
repeat
    Walked += 1;
until NextRow() = 0;
```
- `condition-true` makes `Walked < Rows` true. `NextRow` then always returns 1, and the loop never ends.
- R868 (`optin-hang.ts`) refuses by NAME where the mutated guard writes or reads a loop's own variables. Here the loop's exit
  value comes from a helper's `exit(...)`, behind an `if` the helper owns. Its header's list of blind spots does not name
  this case.
- The fixture `sandbox-hang`'s `NextRow` has the opposite polarity (`if Walked >= Rows then exit(0)`), so the mutant ends
  the loop there. No gate meets the endless polarity.

**Why it matters.**
- Today it costs only users who name `--operator condition-true`.
- Once PR-209 makes the operator default-on, every default run carries it.
- On BC a hung mutant strands its tier, unless `--stop-hung-sessions` is set.
- PR-187's "0 timeouts in 4,444 mutants" covers DO and two BC.History apps on al-runner v3 only.

**To close.**
- R868 refuses `condition-true` on an `if` whose then-arm `exit(...)`s from a procedure that is called inside a loop's exit
  test (`until`, `while`) of the same object. Also cover `blank-argument`'s analogue, if it has one.
- A name rule cannot tell the polarities apart, so it refuses BOTH (the safe direction, R829). Parsed red tests: the endless
  polarity is refused, and the terminating one (sandbox-hang's `NextRow`, line 63) is refused too. A helper guard NOT used in
  a loop's exit test is still made. In itest:hang, the line-63 site then shows as a `hangRefused` row (PR-209 spec §0b).
- The header's blind-spot list is updated.
- **A prerequisite of PR-209's default flip.**
