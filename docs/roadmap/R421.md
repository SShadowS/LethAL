**Found 2026-10-03, running R307's unit suite in the kraken (Linux) container for the first time.**
The test `R307: sandbox-data is byte-identical with the trial in place` in
`packages/runner/tests/per-file-refusal.test.ts` pins two sha256 hashes of
`writeInstrumentedProject`'s output for `fixtures/sandbox-data`. Both were recorded on the Windows
host, where the test passes. On Linux both differ:

| | Windows (pinned) | Linux (measured) |
|---|---|---|
| `mutant-manifest.json` | `b03f52f2d9b2442098380746c8b4c6a8eb8dde17e49e5229cb5c66b31bcfa20f` | `b754095f8aebddf35074c5d032bdac8692076e3e9c1b015d6810bc0ec0ff588e` |
| all files, sorted by name | `e889a463…` | `9abd8f06e020d8f0fa0113b1534f70927664f1c0383540fd958dec19b7fa73c6` |

Linux gives the SAME manifest hash at `d1438ade` (the commit the pin names as its base, before R307's
trial existed), at `297a30f6` (the last commit whose full suite passed on Windows) and at the R307
branch head. So no R307 commit changed the output. The pin has never matched Linux.

**Ruled out, measured:** locale (`en_US`, `da_DK`, `C.UTF-8` all give `b754…`), line endings (all 32
fixture files are LF, `.gitattributes` forces `eol=lf`), and ICU collation: on sandbox-data's real
keys (29 files, 23 operators, 387 mutant ids) `localeCompare` and plain code-unit order disagree on 0
pairs under ICU 78.3.

**Cause, found the same day (Linux side, read-only).** The only difference is the path separator in
the manifest's `file` field. Proof: in the Linux manifest, replacing `"file": "src/` with
`"file": "src\\` in all 387 entries gives exactly the Windows pin `b03f52f2…`, and doing that with the
`.al` files unchanged gives the pinned all-files prefix `e889a463…`. So for this fixture every
instrumented file, mutant id, order, `astHash`, `gapId` and identity ordinal is already the same on
both platforms. (The first version of this item listed path separators as ruled out; that looked at
the Linux output only, and was wrong.)

Where it leaks: `generateMutationSet` (`packages/runner/src/orchestrator.ts`) keeps the raw relative
paths from its recursive `readdir`, which on Windows contain `\`, and `writeInstrumentedProject`
writes them as the manifest's `file`. Glob matching and `gapIdOf` already convert `\` to `/`
(`normalizeRelPath` in `packages/runner/src/line-filter.ts` exists for this); the discovered path
itself is never converted. Windows-made reports in the repo show it, for example
`examples/credit-limit/demo.report.json` (`"file": "src\\CreditLimitMgt.Codeunit.al"`).

**Why it matters beyond the pin.** Discovery sorts the paths, and later sorts order by file. `\`
(0x5C) sorts AFTER uppercase letters while `/` (0x2F) sorts BEFORE them, so in a project with
subfolders `src/Foo/A.al` and `src/FooBar.al` swap places between Windows and Linux. That changes
mutant numbering and identity-ordinal order across platforms, so a baseline, a `--resume` store or a
`--skip-known-survivors` list recorded on one platform can be wrong on the other. sandbox-data has no
subfolders, which is why only the `file` text differs there. (This paragraph was first argued from
the byte values; the fix below measured it.)

**Consequences now (orchestrator ruling, 2026-10-03).** The pin is NOT changed. R307 cannot merge
while the Linux CI job would fail on it, so this item blocks R307's merge until the cause is known and
ruled on. R307's option-3 amendment records its O1 reference hashes on Linux, labelled as Linux;
whether pins are carried per platform is decided here.

**Closed by R-421 (plan `docs/superpowers/plans/2026-10-03-R-421-normalise-discovered-paths.md`,
measurements in the coord handoff `R-421/measurements.md`).** Windows was simulated on Linux by
feeding `\`-keyed snapshots into the real functions with `platform: "win32"`; the simulation
reproduces the Windows pin `b03f52f2…` exactly.

- **Measured moves.** Plain `.sort()` disagrees between the two forms on subfolder paths
  (`src/Foo/A.al` vs `src/FooBar.al`), which moved discovery order, mutant ids and batch membership.
  `localeCompare` never disagreed (0 of 87,990 path pairs), so the identity-ordinal and report sorts
  did not move on their own. The identity key holds no path, but ordinals are numbered per batch, so
  a moved batch moved a key: with identity twins in two files and `maxGuardsPerBatch` 6, one key
  ended `|1` on Linux and had no suffix on the Windows form.
- **The fix.** `discoveredRelPaths` (in `packages/runner/src/line-filter.ts`) turns every discovered
  name into its `/` form ONCE and sorts in that form; reads go through the raw name, so a
  `\`-keyed snapshot still resolves. Test discovery (`TestMethodRef.file`, the report's `testFiles`)
  does the same; a test's file is in no identity key. Off win32 a literal `\` in a file name is
  refused by name (`DiscoveredPathError`), including a name whose part after the `\` would look
  like a generated `Mutation*` file. `clear-ceiling --file` matches a stored row in either form.
- **`IDENTITY_SCHEME` 7** (orchestrator ruling), with every literal moved in one commit, because a
  key can move on Windows. No explain version change: it versions shape, not values. Old Windows
  stores and lists with a moved key are refused or warned by name under `--resume`,
  `--skip-known-survivors` and equivalence marks; no committed campaign key moves, and no fixture
  has a subfolder.
- **Pins and sample reports.** The five `fixture-emission` manifest pins are now in the one `/`
  form (the R411 shim that rewrote them for Linux is gone), each checked from both path forms. No
  test pins a sample report's bytes, so the committed Windows-made reports (for example
  `examples/credit-limit/demo.report.json`, still showing `src\\…`) are not regenerated.
- **Left for R307.** R307's sandbox-data pin in `per-file-refusal.test.ts` lives on the R307 branch.
  It is re-recorded there once, to the Linux value (manifest `b754095f…`, all files `9abd8f06…`),
  after master with this fix is merged in; R307 then takes `IDENTITY_SCHEME` 8.
