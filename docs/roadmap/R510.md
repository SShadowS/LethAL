**Found by** the opus review of the [[R502]] plan (M2). Pre-existing, unchanged by R502.

`SymbolTable.resolveObject` (`packages/engine/src/semantic/symbol-table.ts`) runs `Number.parseInt(idOrName, 10)`
on every reference and matches an object by that id before comparing names. `parseInt` reads a leading number
and ignores the rest. A reference to a quoted name that starts with digits (`Record "50000 Foo"`, which reaches
here unquoted as `50000 Foo`) therefore resolves to whatever object has id 50000, when one exists.

**Effect.** The receiver binds to the wrong table. It is the same class as [[R502]]'s C1: the wrong table's
triggers are read, and a trigger-skip tag can drop. It needs a project with both an object named like that and an
object with that id, which is rare.

**To close.** Treat the reference as an id only when it is all digits (`/^\d+$/`). Add a test with the
`"50000 Foo"` / id-50000 pair.

## Fixed (R-509, 2026-10-08)
`resolveObject` matches by id only when the reference is all digits (after trimming); any other reference matches
by name only.

**Measured first** (`census509.ts`):
- fixtures, examples, CDO, DC and DO have no object whose name starts with digits;
- BC.History has one codeunit named so, and no object of that kind has its leading number as an id.

So nothing resolved wrong in any corpus. The fix prevents the case, and the spec diff above shows it moved nothing.

**Tests** (`r509-temporary-and-ids.test.ts`) cover both directions:
- `"50000 Foo"` resolves to the table named so, and `50000` and `50100` still resolve by id;
- through a receiver and a tag, `Record "50000 Foo"` binds to itself (no `OnDelete`) and no longer to table 50000.

Red-checked:
- `parseInt` restored: 2 red;
- id matching disabled: 1 red.
