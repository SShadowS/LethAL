id: "R261"
title: "The store does not record a run's --selector-id overrides, so lethal verify fails when it re-validates the config's defaults against app.json instead"
section: "product-gaps"
status: "done (dc5d2e4f)"
order: 965
---

**What.** `verifyFromCli` re-validates selector ids before building a backend, but it has no
recorded selector ids to validate: the store never kept the `--selector-id`/`--control-id`/
`--table-id` overrides a source run was given, so verify resolves them from the config file's
defaults instead and calls `validateSelectorIdsForProject` on those. A run that needed the CLI
overrides in the first place, because the target app's `idRanges` excluded the config's default
ids, has an installed build made with the override ids, but a `lethal verify` on it recomputes the
default ids from the config, fails `validateSelectorIdsForProject` against `app.json`, and exits 1
before touching the backend at all.

**Evidence.** `verifyFromCli`, `validateSelectorIdsForProject` (`packages/runner/src/cli.ts`), and
the `ponytail:` comment at the `verifyFromCli` call site owning the gap: "the config's selector ids,
never the source run's CLI overrides (the store keeps none)."

**What would close it.** Recording the resolved `SelectorConfig` on the run row alongside the other
session-fingerprint data, and having `verifyFromCli` validate and reuse those instead of re-resolving
from the current config file.
