**Filed 2026-10-23 by lethal-bugs at R-434's close**, by the orchestrator's ruling. [[R434]] part 1 is a stated
limit until then.

**The gap.** `lethal verify` cannot see an installed app outside the test app's dependency closure. Installing or
upgrading one (a global subscriber, a setup change, a test-runner extension) leaves every test old. A real case:
ALDirectCompile's "Test Runner Extension" 3.2.0.0 is on bc1, bc2 and bc3, outside every closure. An app that depends
on the test app, including its event subscribers, is in no digest under either world answer (R-600).

**Measured source** (`docs/measurements/r434/`): AL's `NAV App Installed App`, read by a web-service codeunit. The
whole list is 117 to 122 rows, takes 1-6 ms in AL and 60-160 ms over HTTP, and is the same rows on every read. The
automation `extensions` list must never be used (R433).

**To close.**
1. **A LethAL Control procedure** that returns the installed list (id and version) from AL. That is a control
   version bump: `CONTROL_APP` and `CONTROL_SHA256` updated, published to every gate server, every gate re-proved per
   server (R604), and `MIN_CONTROL_VERSION` raised only if verify cannot do without it.
2. **Leave out what LethAL itself changes:** the app under test, its test app, and every target with a registered
   artifact (the control app's registry knows LethAL's instrumented targets). Every gate run mints a new version for
   its target (bc1 held 8 such versions), so without this, verify would see every test as new on a shared server.
3. **Fold the remaining `id version` list** into every test's digest. Any other install, upgrade or removal then
   makes every test new: coarse, but the safe direction.
4. **Pre-commit and measure** on bc1-bc3: how often the folded list changes across a day of gates. **Red tests:** an
   install or a version change moves every digest; a publish of an instrumented target does not.
