**al-runner's `asserterror` never fails a test** — `asserterror I := 1;` is reported `pass`, so any mutant killable only by an `asserterror` assertion comes back SURVIVED there while bcdev kills it (measured: 0/7 vs 3/2/2 on the table fixture; re-confirmed 2026-07-26 against a fresh `AsserterrorNeverRaises` probe). Under-reporting only, never a false kill. Loud-warn, not hard-refuse (see `packages/runner/src/al-runner-canary.ts`'s doc comment): the backend already declares `authoritative: false`, under-reporting is safe-direction, and refusing outright would block legitimate offline smoke-testing for a third-party-binary defect that a future al-runner build could fix on its own. The CLI now runs a startup canary — a known-failing `asserterror` executed against the ACTUAL configured binary every `--backend al-runner` session (`runFromCli`'s `announceAlRunnerCanary`) — and prints a measured, this-build verdict instead of a static 2026-07-25 claim; if a future al-runner build fixes it, the canary says so instead of continuing to warn about a defect that's gone. Evidence: `fixtures/README.md` §Tier-2 Phase 0, `scripts/probe-alrunner-tables.ts`, `packages/runner/tests/al-runner-canary.test.ts`.
