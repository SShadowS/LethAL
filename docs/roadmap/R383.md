**Found 2026-10-01 by the orchestrator, reading upstream; not yet measured.** StefanMaron/BusinessCentral.AL.Runner#3713
was closed by PR #3787 (`c1a47da1`, merged 2026-09-10), and GitHub's compare shows that commit is an
ancestor of the `v2.12.0` tag (`d9ac3170`). LethAL still treats the defect as live:
`packages/runner/src/al-runner-coverage.ts` (header, "MEASURED against al-runner 2.11.0") refuses
coverage for the WHOLE run when any file declares more than one object, and `CLAUDE.md`
(`itest:alrunner` paragraph), `README.md` (around line 695), `docs/roadmap/R220.md` and
`docs/roadmap/R255.md` all say so.

The header says the defect was measured on 2.11.0, after the upstream fix date. So either the
fix is not in 2.11.0, or it does not cover LethAL's shape (two codeunits in one file, a test that
calls only the second). Reading cannot settle which.

**What to do:**
1. Re-run the header's two-codeunit probe on al-runner 2.12.0. Only one al-runner session may run
   on this machine at a time (R345), so get the orchestrator's go-ahead first.
2. If the second object's executed line is now reported, admitting multi-object files is NOT a
   one-line change. The header notes that Cobertura's line numbers are file-relative while BC's are
   object-relative, so each object's base line must be applied (`line-map.ts`). That needs its own
   plan and a pre-commitment, since it changes which mutants are scored `no-coverage`.
3. Either way, sweep the prose: `CLAUDE.md`'s "a capability flag that depends on the project's
   file layout" reasoning for `authoritative: false` rests on this defect.

Prevalence is low (1 of 553 files on Continia Document Output, 0 on the fixtures), so this is
about stating the truth, not about measured cost.
