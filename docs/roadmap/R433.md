**Found 2026-10-04 by the R-385 lane (lethal-code), measuring how to read the Microsoft apps a server
has installed.**

## What happens

BC's automation API lists installed apps at
`{baseUrl}/api/microsoft/automation/v2.0/companies(<company id>)/extensions`. Asked for ALL rows (no
`$filter`) on Cronus28, BC 28.4.53241.53758, it never answered:

| request | result |
|---|---|
| no `$filter`, 3 runs | the server closed the socket after about 166 s each time |
| `$filter=publisher eq 'Microsoft'` | the same, about 166 s |
| `$top=5` | 200, 1,863 bytes, 52 ms |
| `$filter=id eq <Library Assert id>` (`HarnessVerifier.fetchExtensionInstalled`), 3 runs | 49, 40, 39 ms |

So a filter on the app id is fast, and a filter on publisher is NOT a safe narrowing: BC appears to
build the whole list before it filters.

## The incident

After those calls Cronus28's service tier stopped answering: `GET http://cronus28:7048/BC/` returned
503, `api/v2.0/companies` hung, and `lethal doctor` failed its HarnessInfo and companies reads with
`AbortError`, while the auth layer (401 on `api/v2.0`) and the dev endpoint still answered. A host
restart is needed (coord question q-20261004T044641-657876a8). That the hung list calls CAUSED it is
not proven, but the timing fits, and no one should repeat the experiment to find out. Every gate that
uses Cronus28 was blocked until the restart.

## Who issues it today: nobody

Searched 2026-10-04 (master 260767d8) for `automation/v2.0`, `/extensions`, `fetchExtensionInstalled`
and `fetchApiRows` in `packages/*/src` and `scripts`, tests excluded:
- The ONLY builder of the `extensions` path is `HarnessVerifier.fetchExtensionInstalled(appId)` in
  `packages/runner/src/harness.ts`, and it always sends `$filter=id eq <appId>`.
- Its callers: `lethal doctor`'s test-app presence check (in `cli.ts`; the id comes from the tests
  project's `app.json` and is refused before the call if it is not a non-empty string) and five
  itests (`BASE_APPLICATION_ID`).
- `scripts/probe-continia-env.ts` reads `automation/v2.0/companies` only, not `extensions`.

Nothing PREVENTS a new caller from issuing it: the private `fetchApiRows` accepts any query, the id
is not checked to be a GUID, and no test refuses an unfiltered `extensions` URL. R-385's first plan
proposed exactly such a call before it was measured; the next idea of this kind will look just as
reasonable.

## To close

1. One private function in `harness.ts` is the only code that builds the `extensions` path. It
   refuses (`HarnessVerificationError`) any `appId` that is not a GUID, before any request, and
   always sends `$filter=id eq <guid>`.
2. A unit test: every `extensions` URL a fake fetch sees carries that id filter, and `""` or a
   non-GUID id throws with zero fetches.
3. A source guard test (like `real-home-guard`) that scans `packages/*/src` and `scripts/` (not
   tests) and fails if `automation` with `/extensions` appears anywhere outside `harness.ts`.
4. Red-check each: drop the GUID check (the `""` test goes red); add a scratch unfiltered call in a
   `src` file (the guard goes red); restore.
5. A sentence in `docs/measurements/README.md` with the table above, and in the `al-probe` and
   `measurement-campaign` skills: "never list all extensions; read by id".

R-385's plan (r2) does this as its task T0; if T0 lands, close this item with that commit.
