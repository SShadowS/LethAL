**Found 2026-10-21** by the Opus build review of [[R586]] (`/coord/handoff/R-586/review-build-opus.md`, Minor 11).

**What.** When v3 refuses a test at baseline (a notRun row, not a timeout), the test leaves the suite as
unsupported. A mutant whose ONLY covering test was that one then reads `no-coverage`. The
`[v3-refused-test-nearby]` note (I3) is written on survivors only, so this `no-coverage` has none.

**Effect.** A reader is told to write a test that already exists: the gap is v3's refusal, not the suite.

**To close.** Tag such a `no-coverage` with the refused test's name (a note, or a refusal cause the report
groups), and pin both directions in a unit test: a mutant covered only by a refused test carries the note, and
one with no covering test at all does not.

**Checked 2026-10-23 (coord task R-608): no link exists yet, so nothing was built.** The orchestrator names a
`no-coverage` mutant that a non-passing baseline test covers (`unsupportedCoverage`, built by `coverageFilter` over
`unsupportedIndex`). That index comes from each test's recorded `coverage`. The v3 backend records coverage only for a
passing, not-`notRun` row (`run`, the `coverage` constant), so a test v3 refused has none, and the index cannot place
any mutant on it. The one place that knows which tests v3 refused is the backend's private `baselineRefused` map, read
only by `survivorNote` through a covering test's codeunit. A `no-coverage` mutant has no covering test, so that join
has nothing to start from. Tagging every `no-coverage` while any test was refused would put the note on mutants no
refused test can reach. To close this, something must say which code a refused test reaches (for example a static
walk of its calls); that is new work and is not filed here.
