**A COMMENT containing `codeunit <id> "Name"` silently truncates test discovery — every `[Test]` after it in the file is dropped, and the mutants those tests covered are reported `no-coverage` with no warning anywhere.** `discoverTests` (`packages/runner/src/discovery.ts`) is static and regex-based: `CODEUNIT_HEADER_GLOBAL = /codeunit\s+(\d+)\s+("([^"]+)"|(\w+))/gi` splits the file into codeunit SECTIONS, and a section is skipped entirely unless `SUBTYPE_TEST` matches inside it. The regex does not skip comments, so **prose** matching that shape opens a bogus section; the remainder of the file falls into it; it contains no `Subtype = Test;`; and every test from that point on vanishes. **FOUND BY ACCIDENT 2026-08-02, which is the alarming part** — while building the R78 fixture I wrote a doc comment reading ``codeunit 79308 "Data Value Source".GetValue`` above a new `[Test]`. Source had 22 `[Test]` methods; `discoverTests` returned **21**; the new test was simply absent. Rewording the comment to `` `"Data Value Source"` (object 79308) `` restored 22. Nothing in the pipeline noticed: the live run reported `baselineGreen=true`, `baselineTests {total: 21, failing: 0}`, an empty `unsupportedTests`, no caveats — and the three mutants that test exclusively covers came back `no-coverage`. A dropped test is INDISTINGUISHABLE from a test that never existed. **Why this is worse than a normal bug:** the direction is silent under-reporting of coverage, which this project's whole design is built to make impossible to do quietly (cf. R31's stale-test-app, R35's permissions refusal — both of which are NAMED in the report). A real suite is far likelier to hit this than a fixture: referring to `codeunit 50100 "Sales Post"` in a comment above a test is ordinary AL commenting. Every test below it disappears from the green set, and its mutants read `no-coverage`, which a reader interprets as 'nobody tests this'. **Fix candidates, in order:** (a) strip comments before sectioning (`//` to EOL and `/* */`), which is a small, testable change and the obviously correct one; (b) require the header match to be at line start with only whitespace before it; (c) at minimum, WARN when a file yields a section with no `Subtype = Test` yet contains `[Test]` — a loud approximation that catches the class even if the parse stays naive. Also worth asserting: total discovered `[Test]` count equals a naive whole-file `[Test]` count, and refuse loudly on mismatch. Needs a red-check: a fixture file with a `codeunit N "X"` comment above a test must go RED before the fix.
