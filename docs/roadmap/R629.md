**Filed 2026-10-22 by coord task R-572** (lethal-code), on the orchestrator's ruling after the R-572 BC.History
re-price STOP (`/coord/handoff/R-572/reprice/investigation.md`). A plausible hang that is NOT refused, on master
and on lethal/r572 alike. (First filed on the branch as R619; renumbered at the merge, because master had given
R619 to another item in the meantime. The R-572 re-price r2 pre-commitment says "R619" for this item.)

**What.** Every hang refusal is decided inside ONE project. BC.History holds a module as its own nested project
(`BaseApp/Source/Base Application/Modules/System/FileOperations`, one file) that is ALSO compiled into the
BaseApp project. The loop that can hang (`Custom Layout Reporting.GenerateFileName` in the BaseApp project: a
`while` loop whose exit tests whether a temporary record filtered on a generated file name is empty) calls
`File Management.AppendFileNameWithIndex`. In the BaseApp project that callee is refused (6 of 6 keys). In the
nested FileOperations project the same object, file and spans deploy all 6 keys: that project has no loop that
calls it (its census reports 0 loops), so no rule fires. A mutant that drops the index returns the same name on
every pass, so a test in a dependent app that reaches the loop hangs.

**Price.** 6 deployed keys in BC.History (the FileOperations copy), on master and on the branch. Not counted on
any other corpus.

**To close.** Decide the unit a refusal is decided over when a project's source is also a module of another
measured project: refuse a nested project's site when the parent project refuses the same object, file and span
(a cross-project join on the identity key's file and span), or state it as a limit of running a module alone.
Find how many nested-module projects exist per corpus first.

## Closed by ruling (2026-10-22, R-629)

Plan: `docs/superpowers/plans/2026-10-22-r629-nested-project-hang-copies.md`. Evidence: `/coord/handoff/R-629/`.

**The real price was larger than 6.** Nested projects: bch 297 of 519, dc 2 of 14, do 0, cdo 0. Deployed keys in a
nested copy whose parent hang-refuses the same procedure: **bch 229, dc 6, do 0, cdo 0**. The figure of 6 above
counted only R572's rule; the older hang rules bring bch to 229. A by-name join over every pair of projects finds
hits only between nested pairs. (`measure.md`)

**Where the refusing loop lives** (step 0, `measure.md`):
- **Parent's own code: bch 157, dc 6.** All 157 bch keys are in Base Application, File Management's 113 among them.
- **A sibling System Application module that depends on the key's module: bch 72.** For example Azure AD Graph <-
  Azure AD User Management (28), and Azure AD Plan <- Azure AD Licensing (14). 13 of the 72 run the reverse
  direction (the loop is in a module the key's module depends on) and are UNVERIFIED.

**Why the parent's loops cannot hang a run of the module.** Measured on bc1 (BC 28.4.53241.56590,
`docs/measurements/README.md`, section "R629"): BC refuses to publish a second app that declares an object ID
already declared by an installed app (HTTP 422, "is defined in multiple apps"). It does so whether the names match
or not. A shared NAME with different ids is accepted, which does not apply here: a nested copy compiles its
parent's source, so it shares every id. The parent therefore cannot be installed beside the mutated module, and
its loops never run against the mutant.

**The sibling-module keys (72)** can hang a run only on a MODULAR install: each System Application module as its
own app, and no System Application app. LethAL's users mutate their own apps, and Microsoft ships System
Application as one app, so these are closed as "modular System Application install only" (orchestrator ruling).

**What stays open:** the same shape in an ISV app suite, where an installed app depends on the target and calls it
from a loop, is filed as [[R634]].

**Shipped:** a `nested-project` warning. A session whose `projectDir` sits under an enclosing directory with its
own `app.json` says so once, naming both paths, and says that loops in the parent or in a dependent app are not
seen. It refuses nothing and changes no deployed mutant.
