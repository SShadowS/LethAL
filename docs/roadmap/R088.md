**A released `lethal` binary carries no evidence of which commit built it, and the filename cannot tell a stale one from a fresh one.** `build/` is gitignored (`.gitignore:4`), so the artifact is untracked and git records nothing about its provenance; the name carries only the package version (`lethal-0.1.0-alpha.1-windows-x64.exe`), which does not move when `packages/` does. **Measured 2026-08-04** while preparing the DO campaign: the local binary was built 2026-07-27 20:49 and is **56 package-commits stale** — `grep -c` against it returns **0** for both `swap-call-arguments` and `remove-commit`, two operators that ship today, while `negate-conditional` returns 3. A run driven by that binary silently measures a smaller operator set than the same source would, and nothing in the report, the filename, or `--version` says so. It surfaced because the campaign's rung 3 hands an agent the binary while rungs 0–2 run from source — the two would have disagreed by 13 of ~176 mutants on one codeunit. **Mitigated for the campaign, not fixed for users:** plan Task 8 step 1b rebuilds from the pinned commit, greps each depended-on operator (zero ⇒ abort) and records commit + sha256 + build time in the run manifest. The product fix is for `--version` to report the build commit and the registered operator set, so a downloader can tell what they are holding. Evidence: `docs/superpowers/plans/2026-08-03-do-live-campaign.md` Task 8 step 1b; `scripts/build-binary.ts`.

**Closed 2026-08-07. Verified against a real compiled binary, which is the only way this row could
be closed honestly — the defect it describes is invisible from source.**

```
$ ./build/lethal-0.1.0-alpha.1-windows-x64.exe --version
0.1.0-alpha.1
build: 9b879396b58eb31faec15d098542d2ca34f8d95d (DIRTY working tree — the commit does not describe this build) built 2026-08-07T19:44:27.927Z
operators (12): lethal.conditional-boundary, lethal.empty-block, lethal.negate-conditional,
lethal.remove-calcfields, lethal.remove-commit, lethal.remove-setrange, lethal.remove-testfield,
lethal.return-value, lethal.swap-call-arguments, lethal.swap-modify-flag, lethal.swap-rec-xrec,
lethal.void-method-call
```

**Both halves the row asked for, and the second is the one that answers the measured incident.**
The 2026-08-04 finding was not "which commit" in the abstract — it was that `grep -c` against a
stale binary returned 0 for `swap-call-arguments` and `remove-commit`. The operator line makes that
question askable without grep, and it is read at RUNTIME from `operatorTiers`, the SAME map
`generateMutationSet` walks. A hand-maintained list beside the real one could drift exactly the way
the binary drifted from its source.

**How the stamp gets in, and why not the obvious ways.** `bun build --define`, injected once per
invocation so every target of one `build:binaries` run carries an identical stamp. Not a runtime
file read: R50 already measured that a runtime-computed path resolves against Bun's virtual root
under `--compile` and fails, which is why the VERSION is a static import. Not a generated source
file either: that would have to be written before the build and cleaned up after, and a half-failed
build would leave a lying constant checked out in the tree. The `typeof __LETHAL_BUILD_COMMIT__ ===
"undefined"` guard is what lets the same source run un-stamped under `bun run` — `typeof` on an
undeclared identifier is the one expression that does not throw — so a developer build reports
"built from source; no commit stamp" instead of crashing.

**A dirty tree is reported, never refused.** Making a dirty build while developing is legitimate;
one that claims a commit describing something else is not. The build prints a warning and the
binary prints `DIRTY` in capitals. The run above IS dirty, which is why the flag shows — the R88
changes themselves were uncommitted at build time.

**The first line is exactly the version**, so `lethal --version | head -1` keeps working.

**Row correction, and a second one found on the way:** `docs/releasing.md` listed BOTH "No
`--help`" and "No `--version`" under known gaps. Both were false — R49 shipped them — and had been
for several releases. Corrected in place, with a note saying they were wrong rather than a silent
deletion.
