**A released `lethal` binary carries no evidence of which commit built it, and the filename cannot tell a stale one from a fresh one.** `build/` is gitignored (`.gitignore:4`), so the artifact is untracked and git records nothing about its provenance; the name carries only the package version (`lethal-0.1.0-alpha.1-windows-x64.exe`), which does not move when `packages/` does. **Measured 2026-08-04** while preparing the DO campaign: the local binary was built 2026-07-27 20:49 and is **56 package-commits stale** — `grep -c` against it returns **0** for both `swap-call-arguments` and `remove-commit`, two operators that ship today, while `negate-conditional` returns 3. A run driven by that binary silently measures a smaller operator set than the same source would, and nothing in the report, the filename, or `--version` says so. It surfaced because the campaign's rung 3 hands an agent the binary while rungs 0–2 run from source — the two would have disagreed by 13 of ~176 mutants on one codeunit. **Mitigated for the campaign, not fixed for users:** plan Task 8 step 1b rebuilds from the pinned commit, greps each depended-on operator (zero ⇒ abort) and records commit + sha256 + build time in the run manifest. The product fix is for `--version` to report the build commit and the registered operator set, so a downloader can tell what they are holding. Evidence: `docs/superpowers/plans/2026-08-03-do-live-campaign.md` Task 8 step 1b; `scripts/build-binary.ts`.
