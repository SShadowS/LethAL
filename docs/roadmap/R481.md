**Found 2026-10-05 while building R475** (coord handoff `R-475`, plan
`docs/superpowers/plans/2026-10-05-R-475-code-unit-identity-order.md`, open question 1, raised by the
gpt-6.1-sol r1 review). Pre-existing; R475 fixed only the identity comparators.

**What.** The function in `packages/runner/src/test-order.ts` that ranks a mutant's covering tests
(kills in this procedure, then fewest members covered, then the qualified test NAME) breaks the last
tie with `localeCompare`, which uses the host's DEFAULT collation. Two hosts with different
collations (Danish puts `Aa…` after `Z…`) can run the same covering tests in a different order.

**Why it matters (correctness, not display).** The order decides `killingTest`, `killPosition` and
warm-kill positions, and it can decide the VERDICT: `report.ts`'s `session-warm` contract admits that
an ordered warm prefix can hide a cold kill. So one project measured on two hosts can score a mutant
differently with nothing else changed.

**Measured.** 2 test-name pairs in `fixtures/sandbox-data-tests` order differently under code unit
than under the kraken default (`en`). The Windows host's default collation is not measured.

**To close.** Compare names by code unit (R475's `compareCodeUnits` in `packages/schemata/src/ids.ts`)
or a fixed collation. That can move `itest:tables` and `itest:chunked` `killingTest` /
`killPosition` / `warmKills` pins, so pre-commit the expected per-mutant moves first, then re-record
those baselines deliberately (R332).
