Found by lethal-code, 2026-11-12 (coord R-938, Base Application x Tests-Fixed Asset on al-runner v3). Related: [[R900]], [[R941]],
[[R943]].

**What happened.** With `assemblyProbingPaths: ["/coord/cache/bc28-service-windows"]` (the Windows BC service folder R900 names), alc
refused LethAL's plain build of Microsoft's Base Application with two errors: `AL0451: An assembly named
'Microsoft.AspNetCore.StaticFiles' could not be found in the assembly probing paths` (from Base Application's `dotnet.al`) and `AL0185:
DotNet 'FileExtensionContentTypeProvider' is missing` (File Management). That assembly is part of the ASP.NET Core shared framework, which
a BC service folder does not carry. Adding `/opt/dotnet/shared/Microsoft.AspNetCore.App/10.0.14` (the container's .NET 10 runtime) as a
second probing path, after the service folder, made the build compile. R-927 found Linux copies of BC's OWN assemblies cause
AL0133/AL0122, so the order matters: the service folder first, the framework folder only for what it lacks.

**Invented repro.** An app declaring `DotNet "Microsoft.AspNetCore.StaticFiles.FileExtensionContentTypeProvider"` compiles with a probing
path that includes an ASP.NET Core shared framework folder and fails with AL0451/AL0185 with only a BC service folder.

**Wanted.** R900's documentation (and README's probing-path note) name both: the BC service folder, and an ASP.NET Core shared framework
folder for apps that use ASP.NET types (Base Application does); say which version alc tolerates (measured: 10.0.14 compiles BC 28's
Base Application). Optionally `lethal doctor` checks a configured probing path set for the assemblies a project's `dotnet.al` names.
