**Filed 2026-10-23 by lethal-bugs during R-661**, from its build review.

**What.** `BcDevConfigSection.coverageMode` is typed `"procedure" | "none" | "fenced"` (`cli.ts`), but only the type
says so.
- `validateBcDevConfig` checks the required fields and ports, then returns the parsed JSON cast to the type.
  Nothing checks `coverageMode`.
- Whatever string the file holds reaches `BcDevMcpBackend`'s `cfg.coverageMode`, then `capabilities().coverage`, and
  every baseline's `RunOpts.coverage`.

**What a user sees, read from the code (not run):**
- `"line"`: `run`'s routing predicate sends the baseline to the hub with line coverage. That is a mode the docs
  never offer, and R661 measured that its overrun quarantines (`docs/measurements/r661/`).
- A typo such as `"Fenced"` or `"fenced "`: `run` sends the baseline through the fenced transport, but
  `collectCoverage` is false (it requires exactly `"fenced"`). `indexArtifact` builds no line map, and the run behaves
  as `none` (every mutant against every green test). That is slower and silent. Whether a report then states the
  typo as its `coverageMode` has not been checked.

**Who hits it.** Anyone who hand-edits `lethal.config.json`.

**To close.** Refuse an unknown `coverageMode` by name in `validateBcDevConfig`, listing the accepted values. Add one
red test per direction: an accepted value passes, and `"line"` or a typo is refused.

Evidence: R661 (`docs/roadmap/R661.md`); `validateBcDevConfig` and `BcDevConfigSection` in
`packages/runner/src/cli.ts`; `run` and `capabilities` in `packages/runner/src/bcdev-backend.ts`.
