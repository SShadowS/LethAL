title: "`itest:testapp` hard-codes the sandbox-tests version 1.0.0.2, so it fails since GH-09 bumped the fixture to 1.0.0.3"
section: "backends-and-tooling"
status: "open"
order: 969
---

**What.** `test-app-publish.itest.ts` (C02-05) pins `TEST_APP_VERSION = "1.0.0.2"` and asserts the
server's read-back version equals it after its marker publish (step 6) and after its restore
(step 7). GH-09's commit "namespace Sandbox Logic" bumped `fixtures/sandbox-tests/app.json` to
`1.0.0.3` and did not touch the gate, so the gate now fails both assertions with
`server version: expected '1.0.0.2', actual '1.0.0.3'`. Nothing else in the gate is wrong: steps 1
to 5 (full run per mutant equal to `bcdev.baseline.json`, artifact load, kill and survivor, the
compile refusal, `StaleTestAppError`) pass.

**Who hits it.** Anyone running `LETHAL_ITEST_TESTAPP=1 bun run itest:testapp`. Its restore step
also reports failure and asks for a manual restore, although the restore itself published the
committed suite (a following `itest:verify` restored and proved it; `itest:bcdev` passed).

**Found by.** C02-08, re-running the gates that share `compileTestApp` after the R268 fix, on
Cronus28, 2026-09-26.

**What would close it.** Read the expected version from `fixtures/sandbox-tests/app.json` instead
of a literal, so a fixture bump cannot silently break the gate again, then re-run it live.
