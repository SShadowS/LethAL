**Found while building R-236c's TestPage scanner**, whose own plan names this gap as one reason it
does not resolve variables through the engine's symbol table
(`docs/superpowers/plans/2026-09-27-R-236c-testpage-pre-refusal.md`, section D1, "C1 (multi-name
declarations)").

**What happens.** AL lets one `var` declaration name several variables at once, for example
`A, B: TestPage "My Page"`. `collectVarDeclarations` (`packages/engine/src/semantic/symbol-table.ts`)
builds one `VarSymbol` per `variable_declaration` node from `decl.childForFieldName("name")?.text`,
which reads only one name field. Every name after the first in a multi-name declaration is never
added to `globals`/`locals`, so no lookup through `lookupVar`, `resolveVarRef` or a Tier-2 receiver
can ever see it: it reads as "not declared" rather than as the type it actually has.

**Measured.** R-236c's own scanner test proves the gap by building around it:
`packages/runner/tests/testpage-scan.test.ts`, test "the SECOND name of a multi-name declaration
(review r2, C1)", declares `A, B: TestPage "X"`, calls `B.OpenView()`, and asserts the scanner
(which reads scope from the AST directly, not through this function) refuses the test correctly.
The engine's own `collectVarDeclarations` would answer that `B` is not declared at all.

**Consequence to measure before any fix.** Tier-2's receiver resolution and `resolveVarRef` both
refuse on any variable that is the second or later name of a multi-name declaration today, the safe
(conservative) direction. A fix can therefore ADD claimed Tier-2 sites and resolved `resolveVarRef`
answers wherever a real project uses this AL shape, moving `itest:tables` and any other gate that
counts claimed sites. R-236c's own scanner does not depend on this fix: it collects every name
itself and is unaffected either way.

**Why not fixed here.** R-236c's plan states plainly: do not change `collectVarDeclarations`
(loop-hazard and the operators depend on today's behaviour). The scanner keeps every name of every
declaration itself instead and files this gap.

**To close:** change `collectVarDeclarations` to push one `VarSymbol` per name rather than per
declaration node (iterating whatever set of name children the grammar exposes, not just the field
named "name"), then measure the effect on both reference corpora and on `itest:tables` before
landing, since a real project may declare multi-name TestPage-typed or ordinary variables this way
today without anyone noticing they were invisible to scope resolution.

**Closed 2026-10-05 by R-294 (6154426f, fixed together with [[R294]]).** Cause: the four readers of
a declaration (`collectVarDeclarations`, `triggerLocalNames`, `conditionallyDeclared`,
`parseSplitProcedure` in `symbol-table.ts`) read `childForFieldName("name")`, the first name only,
so a use of B in `A, B: T` resolved to a same-named global of another type. That made WRONG
mutants, not only lost sites: a `swap-call-arguments` swap that `alc` rejects (AL0133) and a
`remove-setrange` claim on a Codeunit receiver. Fix: one helper reads the declaration's DIRECT
`name` children (a Label's attributes carry `name` fields one level down) and all four readers use
it; every name gets the full shared type text and the shared declaration node. `loop-hazard.ts`'s
`sameDeclaration` now keys by that node's position AND the name, or `while A < 10 do B := B + 1`
would be a false hang. While building it, the review's `with` probe found that `types.ts` typed a
name inside `with R do` by the local even where R's field of that name wins; master already
emitted an `alc`-failing swap there with single-name locals (measured with `alc` 18.0, AL0133), so
a name inside a `with` body now types as nothing. A `#if` between two names of one declaration
does not parse as one declaration and its file stays excluded as undecided (pinned). A local named
like a parameter is AL0121 in AL, so it needs no test. `IDENTITY_SCHEME` 11. Combined census, both
fixes on the branch against master 776461b4 (R-196 merged): BaseApp (BC.History, 203 projects)
+1,169 sites in 54 projects and 166 removed; CDO at 5f2a71d +4 and 2 removed; fixtures, examples
and unit fixtures 0 and 0 (the gate capture diff is empty on all 25 project sets). Of the census's
wrong rows of the later-name class (BaseApp 30 `swap-call-arguments` and 99
`flip-boolean-literal`, CDO 1 `swap-call-arguments`), none is still emitted. The other removed
rows are the hang-capable sites the two fixes newly see, which R196 now refuses instead of tagging
(36 BaseApp, 1 CDO; measured against the pre-R196 base they were 36 and 1 new hang tags), plus one
`swap-additive`.

**Review addition: the implicit `with`.** The final review found one more door to a wrong swap:
some bodies run inside an implicit `with` over a record, and there a field of that record wins
over an object global of the same name (a local or parameter still wins over the field). `types.ts`
does not read those fields, so `implicitRecordShadowsGlobals` makes a bare name that would fall
through to the globals type as nothing in the places measured with `alc` 18.0: a page with a
`SourceTable`, every pageextension, a codeunit's `OnRun` when it has `TableNo`, report dataitem
triggers, a report request page with a `SourceTable`, and reportextension dataset and request
page triggers (the request page refused unmeasured). Table, tableextension and xmlport triggers
were measured safe. The synthetic case: on a page over a table with a Text field `Z`, two Integer
page globals `Q2` and `Z` were swapped, which `alc` rejects (AL0133); the tests are in
`r294-implicit-with.test.ts`. Census of this refusal alone (the commit before it against the commit
that adds it): BaseApp 1,961 rows removed (1,175 `swap-call-arguments`, 786 `swap-additive`), CDO 38
(32 and 6), nothing added. 12 of the BaseApp removals are swaps that moved to another argument pair
at the same call; each new pair is made of procedure locals, parameters or named returns of one
type, read in the source, so the field cannot win there. Fixture, example and unit-fixture capture
diff: empty. Wrong or safe, by a type-level check (no `alc` on the corpora): for each removed row,
the names whose type the refusal took away; for each name, the implicit record (the dataitem chain
innermost first, the page's or request page's `SourceTable`, the extended page's `SourceTable`,
the codeunit's `TableNo`); that record's fields from the corpus tables, their tableextensions and
the platform's `System.app` symbols; then the field's type against the global's. Result: 0 wrong.
BaseApp: 1,959 rows where the record has no field of that name (4 checked by hand: 3
pageextensions of Role Center pages with no `SourceTable`, 1 dataitem chain whose tables have no
such field), and 2 where one name has a same-typed field. CDO: 38, no such field. So the refusal
closes a real door, but these corpora had not used it; what it costs here is the lost sites.
