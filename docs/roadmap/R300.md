**Filed by R-297 Task 0 (2026-09-28), as the plan's ruling C.** Plan:
`docs/superpowers/plans/2026-09-28-R-297-instrumentation-real-corpora.md`.

**What this landing does and does not do.** R-297 makes the writer see through a
`preproc_conditional_object` wrapper, so a file whose object is wrapped in `#if ... #endif`
instruments instead of throwing (R298's writer half). It does NOT score such an object under fenced
coverage (the default) or al-runner: its coverage is REFUSED by name, per object, in both of those
paths (the bcdev line map and al-runner's `--coverage`), so every mutant in a wrapped object reads
`no-coverage`. No row of a refused object reaches attribution at any grain there, and unaffected
objects in the same run keep scoring (R-297 Task 4). A refusal is honest; a guessed line number would
attribute a hit to the wrong statement. In `coverageMode: "procedure"` (the bc-dev-mcp hub), the
backend attributes coverage by method id from the compiled app's own `SymbolReference.json` rather
than the line map, so this refusal does not apply there; this item owns deciding whether that path's
attribution is itself correct for a wrapped object.

**The open question.** A two-arm file (`#if X` object `#else` object `#endif`, the same type and id
in both arms) compiles only one arm. The line map needs to know where that arm's lines start as the
server numbers them:

- **H2 (predicted):** the base line is the previous COMPILED object's end + 1, because the inactive
  arm is disabled text the compiler never sees as an object.
- **H1:** the base line is the previous object TEXT's end + 1, counting the inactive arm.

Neither is measured. Reasoning about it is exactly what `/bc-measure` exists to replace.

**What the measurement needs.**

- A container: an al-probe on Cronus28 with LethAL Control **1.0.0.20** (`MIN_CONTROL_VERSION`,
  `packages/runner/src/harness.ts`).
- al-runner with the ELSE arm compiled (a preprocessor symbol set so the second arm is the live
  one), since the two backends may differ.
- The two-arm probe must name procedures DIFFERENTLY per arm (for example `AIf` and `AElse`), so a
  result can reject the inactive arm's name rather than match either.
- The bcdev hub path (`AppMethodIndex`, which takes procedure names from the server) needs the same
  decision, not only the line map.

**Size of the blind spot** (shape census, R-297 Task 0, 2026-09-28). The plan-time census said
two-arm was the dominant shape (System Application 22, BusinessFoundation 10, BaseApp 132). That
was a miscount: a wrapped file usually holds `namespace_declaration` AND its object inside the
`#if`, and the census counted the namespace as a second declaration. Recounted by object kind and
by `#else`/`#elif` arms, NO wrapped object in any measured corpus has two arms:

| corpus | files with a wrapped object, one arm | two arms | wrapper holding no object (`using` lines only) |
| --- | --- | --- | --- |
| DC/Cloud | 4 | 0 | 0 |
| System Application | 22 | 0 | 6 |
| BusinessFoundation | 10 | 0 | 0 |
| BaseApp | 141 (plus 1 nested) | 0 | 31 (one of them two-arm) |

So H1 against H2 above is a question about the repro shape, not about these corpora. The shape
that IS common, one arm with a namespace inside, still needs its own measurement: where the
server's object line numbers start when the `#if` line and the namespace sit inside the wrapper,
and what happens to every mutant in the object when the build's symbols compile the whole object
out (then nothing of it is compiled, so no mutant in it can run; see the inactive-arm item).

**Closing.** R298 stays OPEN until this item lands. This item closes when wrapped objects are
scored by a measured rule in both coverage paths and a live gate pins a verdict in one.
