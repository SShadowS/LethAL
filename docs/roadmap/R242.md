**Found 2026-09-26, while planning [[R235]].** Only the one-shot CLI path consumes the platform-app
pin ([[R147]]): `buildAlRunnerArgv` sends `--package-cache <pin>` in place of `--auto-provision`.
The `--server` path, which the server leg and the `selectorMode: "resource"` leg of
`itest:alrunner` both use, starts the daemon with the configured `packagesDir` alone and never with
the pin. But `runSession` still records `platformAppsDir` on those sessions' execution contexts.

**What is wrong.** A reader of a server-mode report sees `platformAppsDir` set and concludes the run
searched that directory. It did not: the field says what the one-time provisioning call FOUND, not
what the runner used, and on these legs nothing consumed it. The verdicts are unaffected; the
report field is misleading on its own terms.

**Since R235** the gate asserts the pin only on the two one-shot legs, so the gate no longer checks
a value that was recorded but not used. The report still records it.

**Options.** Either record `platformAppsDir` only where the transport consumes the pin (the
one-shot path), or wire the pin into the daemon's start-up so the field becomes true. The second
changes what a server-mode run resolves, so it would need the same per-mutant equality evidence as
R235.

Evidence: the R235 plan (`docs/superpowers/plans/2026-09-26-R-235-alrunner-provision-sentence.md`,
"What the pin is, and what it is not" and "Out of scope"); `assertPlatformAppsPinned` in
`packages/runner/itest/al-runner.itest.ts`.

**Closed 2026-09-29 (cd90b9e2, review fixes f7c46702), option 1.**
`AlRunnerBackend.usePlatformAppsDir` now returns whether its transport will send the pin. Only the
one-shot CLI path does, so under `serverMode` the backend declines it. `runSession` records
`platformAppsDir` (through the `al-runner-platform-apps` event) only when the pin was consumed. On
a `--server` session it emits nothing about the pin: declining it is normal operation there, and the
absent field is the statement. A setter that answers anything but a boolean refuses the session,
because reading it as "declined" would silently drop the provenance of a transport that still sends
the pin. A worker that declines a pin the session backend consumed fails the session.

Unit tests pin each path: one-shot consumes, server and resource decline, a `runSession` report
records the field only on the consuming path (the server test requires a context that scored
mutants), and a non-boolean answer refuses. Each was red-checked against a reverted fix
(`.superpowers/r242-redcheck.log` and `r242-redcheck-002.log` in the R242 worktree).
`itest:alrunner` now also asserts that the `--server` and resource legs LACK the field; the
one-shot assertion is unchanged. Measured on al-runner 2.12.0: PASS, 3/12/4 on every leg with
identical per-mutant verdicts, symbol sets 5/8/0 each.

**Why not option 2.** Wiring the pin into the daemon would change what a server-mode run resolves,
so it needs its own per-mutant equality evidence, as R235 did. Nothing here needed that change.
The pinned contract re-probe that `runSession` still runs on a server session is filed as [[R344]].
