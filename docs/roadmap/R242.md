title: "On the al-runner `--server` and resource legs, `executionContexts[].platformAppsDir` records a pin the daemon never receives"

**Found 2026-09-26, while planning [[R235]].** Only the one-shot CLI path consumes the platform-app
pin ([[R147]]): `buildAlRunnerArgv` sends `--package-cache <pin>` in place of `--auto-provision`.
The `--server` path, which the server leg and the `selectorMode: "resource"` leg of
`itest:alrunner` both use, starts the daemon with the configured `packagesDir` alone and never with
the pin. But `runSession` still records `platformAppsDir` on those sessions' execution contexts.

**What is wrong.** A reader of a server-mode report sees `platformAppsDir` set and concludes the run
searched that directory. It did not: the field says what the one-time provisioning call FOUND, not
what the runner used, and on these legs nothing consumed it. The verdicts are unaffected; the
report field is misleading on its own terms.

**Since R235** the gate asserts the pin only on the two one-shot legs, so the gate no longer checks
a value that was recorded but not used. The report still records it.

**Options.** Either record `platformAppsDir` only where the transport consumes the pin (the
one-shot path), or wire the pin into the daemon's start-up so the field becomes true. The second
changes what a server-mode run resolves, so it would need the same per-mutant equality evidence as
R235.

Evidence: the R235 plan (`docs/superpowers/plans/2026-09-26-R-235-alrunner-provision-sentence.md`,
"What the pin is, and what it is not" and "Out of scope"); `assertPlatformAppsPinned` in
`packages/runner/itest/al-runner.itest.ts`.
