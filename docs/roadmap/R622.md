**Filed 2026-10-22 by lethal-preproc during R-618** (orchestrator ruling: file it even though it did not reproduce).
Possibly a load effect like [[R616]], but the shape differs: R616's tests failed at the 5000 ms timeout, and this one
never failed at all.

**What happened.**
- **When and where:** `bun scripts/verify.ts` (FULL, `--parallel=8`) in `/work/lethal-wt/r618`, started about 01:55Z
  on 2026-10-22, before R-618's merge with master.
- **The hang:** after about 9200 tests had passed, one `bun test --test-worker` process sat at 100% CPU for over 10
  minutes. The other workers had finished. Bun's per-test `--timeout=5000` never fired, which points at work that does
  not yield (a synchronous loop) rather than a slow `await`.
- **How it ended:** I killed that worker (my own unit-test process, not a live gate). verify.ts then named the file:
  `✗ packages/runner/tests/real-home-guard.test.ts (worker crashed: SIGTERM)`, after `killed 1 dangling process`, and
  reported `FAIL 9200 pass / 8 skip / 1 fail` after 631.4 s.
- **The load at the time:** load average 2.41 / 2.86 / 3.77 at 02:05Z, 47 GB free (`free -g`). One other CPU-bound
  job was running, `scripts/prod-identity-keys.ts` from the r572 worktree, at 100% CPU. So this was far below R616's
  load of about 9.6.

**Not reproduced.**
- The file alone: 4 pass, 0 fail, in 58 ms.
- The full verify re-run straight after: PASS 9204 / 0 in 18.5 s, and again after the merge: 9224 / 0 in 19.4 s.

**Logs:** `/coord/handoff/R-618/hang/lethal-verify-test-1792634748570.log` (the test log; the file's section is
near its end) and `/coord/handoff/R-618/hang/verify.txt` (verify.ts's own output).

**Why it matters.** A verify that hangs costs ten minutes, and it can look like a slow run rather than a failure.
An unattended verify, or one in CI, would sit until an outer timeout.

**To close.**
- Find what in `real-home-guard.test.ts` can spin without yielding. Its source scan (the no-direct-homedir guard)
  walks directories with `readdirSync`, so a directory that changed while it walked is one candidate. That is a
  guess; it is not measured.
- Or give verify.ts a per-file wall-clock limit that turns a stuck worker into a named failure, the way it already
  names a crashed worker.

## Watchdog (R-622)

The second option landed; the item stays **open**, because the hang itself was not reproduced (20 full verifies,
500 runs of the file alone, about 6000 forced timeouts: `/coord/handoff/R-622/repro.md`). The likeliest cause is a
Bun 1.4.2 fault after a per-test timeout killed a child in the R359 test.

- **What now happens.** Under `bun scripts/verify.ts`, the preload (`scripts/test-preload.ts`) writes a heartbeat
  for each test file as it starts, and verify reads them every second (`execWatched` in `scripts/verify.ts`). When a
  file runs over the limit, verify prints `watchdog: FAIL, <file> ran over 180 s in worker <pid>. R622.` at once,
  then stops that one process: SIGTERM, then SIGKILL 3 s later if it is still running. Before each signal it checks
  with the OS that the process is still a child of the `bun test` it started (`isChildOf`: `/proc` on Linux, CIM on
  Windows). The backstop: if the process cannot be confirmed as ours, or outlives the SIGKILL, verify kills its own
  `bun test` child through the handle it holds, which ends the whole run. The run then fails, naming the file.
  A passing run prints `watchdog: ok, no test file ran over 180 s`. A plain `bun test` (CI's own step) has no
  watchdog.
- **The limit: 180 s per file.** The slowest file on the Windows CI job took up to 29.4 s in three green master
  runs, and the slowest on Linux took 17.6 s at P=8 under load 44. 180 s is at least 6 times either. The planned
  120 s was only 4.1 times the Windows figure. No test timeout changed. Two files give their `beforeAll` 300 s
  (`plan-emit-soundness.test.ts`, `plan-emit-golden.test.ts`), but each whole file took under 0.5 s on the
  Windows CI runs, so 300 s is a loose timeout, not a measured need.
- **Known limits.** Serial, a file stuck before its first test is named as the file before it. A hang in bun's
  coordinator after the files ran is not covered. On Windows the OS check runs about a second before the signal,
  and Windows reuses pids quickly, so a reused pid is unlikely but not impossible there (on Linux the gap is
  microseconds). After the backstop under `--parallel`, an unconfirmed worker may keep running; the run still ends.
- **Evidence.** Windows times: `/coord/handoff/R-622/windows-times.md`. Red checks (kill, file naming, descendant
  check both ways, parent rule, the SIGKILL step, the backstop, report-once): `/coord/handoff/R-622/redcheck.md`.
  Review I1 (a pipe filling up) cannot happen on Bun 1.4.2, which buffers an unread pipe itself (measured there),
  so its red check did not go red. Verify: `/coord/handoff/R-622/verify-fix.log`.

## Whole-run limit (R-616b)

The gap named under "Known limits" (a hang in bun's coordinator after every file ran, which no file heartbeat
sees) is closed: `execWatched` now also kills the child through its handle after `RUN_LIMIT_S` (900 s) and fails
with `watchdog: FAIL, this run went over 900 s (no file was over its limit)... R622.` The limit covers every child
that verify runs, the typecheck too. A full
verify takes 30 to 45 s; the slowest ever seen was 631 s, in this item's own hang. The census of 78 failed runs
since 2026-10-22 (`/coord/handoff/R-616b/census.md`) shows no watchdog line and no run over 44 s. The original hang
is still NOT reproduced and is explained as before (the likeliest cause is a Bun 1.4.2 fault after a per-test
timeout killed a child in the R359 test). Red check: `/coord/handoff/R-616b/redcheck.md`, item 11.
