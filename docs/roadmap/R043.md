**`alc 18` writes OPC part names with single-encoded spaces, producing a package BC 28 cannot load — and LethAL has no way to select a different compiler.** Root cause proven 2026-07-27 by compiling ONE directory with both binaries and the SAME flags, then diffing the packages: identical 614-part lists, but the zip entry names differ — `alc 17.0.29.44223` writes `src/Al/Codeunit/Codeunit%25206175272%2520CDO%2520...al` (space encoded to `%20`, then OPC-escaped to `%2520`), while `alc 18.0.38.8509` writes `Codeunit%206175272%20CDO%20...al`. BC then looks up the properly-escaped name, finds nothing, and reports the generic `Specified part does not exist in the package.` Reproduced minimally: a single-codeunit app publishes fine as `Probe.Codeunit.al` and fails once renamed to `Codeunit 79400 LP Probe With Spaces.al` — so the trigger is a SPACE in a source file name, nothing else. That is why LethAL Control and every fixture publish (no spaces) while Document Output cannot (`Codeunit 6175272 CDO ....al` throughout). **Both compilers exit 0** — this is a packaging defect, not a compile error, and it surfaces only at publish. Earlier hypotheses, each killed by direct test: the `logo` backslash (forward slashes failed, removing the field failed, and `logo/Logo.png` is byte-identical in both packages), translation files, flat-vs-mirrored source layout, missing dependencies, and app size. Fix shipped for the LethAL half: `bcdev.alcPath` config override, so a project can pin the compiler its server accepts. The encoding difference itself is upstream (Microsoft's `alc`).
