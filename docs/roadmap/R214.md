**Found by the issue #6 cross-check, on its first run against deliberately awkward AL.** That is
the audit working as intended: R159's census counts kinds tree-sitter reports, so it could never
have surfaced this.

**What happens.** `tree-sitter-al` parses BOTH arms of a `#if` / `#else` block. The AL compiler
evaluates the directive and parses only the arm that is active for the symbols it was given. So
LethAL enumerates mutation sites inside an INACTIVE branch, and the compiler does not agree those
are sites at all.

Measured with `scripts/probe-grammar-crosscheck.ts` on a fixture containing:

```al
#if CLEAN25
    procedure BehindDirective(A: Integer; B: Integer): Integer
    begin
        exit(A * B);      // <- tree-sitter reports a multiplicative_expression here
    end;
#else
    procedure BehindDirective(A: Integer; B: Integer): Integer
    begin
        exit(A - B);      // <- the compiler parses THIS arm
    end;
#endif
```

```text
multiplicative_expression   tree-sitter 3   compiler 2   <-- differs
sites only TREE-SITTER sees (possible over-claiming): 1
   multiplicative_expression   (the `exit(A * B)` above, inside the inactive arm)
```

Reproduce with `bun scripts/probe-grammar-crosscheck.ts scripts/lib/al-kind-mapping-stress.al`,
whose `#if CLEAN25` arm is the fixture shown above.

**Why it matters.** This is the over-claiming direction, which is the worse of the two the audit
looks for. A mutant planted in an inactive branch is deployed, but its code is not in the built app,
so no test can reach it. It cannot be killed. It is therefore reported as a SURVIVOR, and a survivor
is the output a user is meant to act on. The score is diluted by mutants that were never live, and
nothing in the report distinguishes them from a real survivor.

**Prevalence, measured, and it is the honest part of this row.** On the two reference corpora the
exposure is near zero:

| corpus | files using directives | `#if` blocks |
| --- | ---: | ---: |
| `do-rel2/Cloud` (554 files) | 1 | 1 |
| `do-lethal-53470/Cloud` (572 files) | 1 | 1 |

So this is not currently costing those measurements anything detectable. It is filed because the
mechanism is real and the exposure is a property of the CORPUS rather than of the tool: Microsoft's
own AL uses `CLEAN`-tagged directives heavily for deprecation, and any app carrying feature flags
would too. A user whose code looks like that gets false survivors and no warning.

**The input already exists.** `preprocessorSymbols` is read from configuration and threaded to the
compile step (`al-runner-backend.ts`, `ArtifactCompilerConfig`), so LethAL already knows which
symbols are defined. Nothing in `packages/engine` or `packages/schemata` consults them: site
enumeration has no reference to directives at all.

**What closing it would take**, roughly in order of cost: refuse to enumerate sites inside a
directive block at all (cheap, correct, loses sites in the ACTIVE arm too); or evaluate the
directives against the configured symbols during enumeration and skip only inactive arms (right, and
needs the grammar to expose the directive structure); or emit the sites and mark them, so the report
can say "not built under these symbols" rather than "survived". The third is the one that keeps
faith with the three-verdict model, since it makes the fact observable rather than silently absent.

## WIDENED 2026-09-09: it loses sites too, and that is the half this row got wrong

Running the same harness over Microsoft's BaseApp (7,889 files) confirmed the over-claim above on
real shipping code rather than a fixture: `Inventory/Location/LocationList.Page.al` has an entire
`trigger OnAction()` inside an inactive arm, and tree-sitter reports its five calls where the
compiler reports nothing at all in that region.

But the same run showed the mechanism ALSO runs in the opposite direction, which this row did not
anticipate. tree-sitter parses a statement-level directive into a `preproc_conditional_statement`
container:

```text
inside  #if   call_expression <- preproc_conditional_statement <- statement_block <- code_block
outside #if   call_expression <-                                  statement_block <- code_block
```

The parse is CORRECT and this is not a grammar defect: zero ERROR nodes, and the container is the
honest shape for the construct. The defect is ours. `isStatementPosition`
(in `packages/engine/src/ast/tree-walks.ts`) requires the parent to be `statement_block` or
`block`, and `preproc_conditional_statement` is neither that nor a member of
`SINGLE_STATEMENT_SLOTS`. So every statement DIRECTLY inside any `#if` block is invisible to every
operator that gates on statement position.

Verified with the real operator set rather than by reading the predicate, on two structurally
identical calls in `Assembly/Costing/CalculateAssemblyCost.Codeunit.al`:

```text
inside  #if  -> claimed by: []
outside #if  -> claimed by: ["lethal.void-method-call"]
```

Unlike [[R215]], no downstream filter can rescue this: the direction is under-claiming, and
`isMutableSite` only ever removes sites.

**So a `#if` block is over-claimed and under-claimed at the same time**, by different operators.
Expression operators (`negate-conditional`, `shift-integer`) gate on node kind, so they claim in
BOTH arms and over-claim in the inactive one. Statement-position operators (`void-method-call`,
`remove-assignment`) gate on `isStatementSlot`, so they claim in NEITHER arm and lose the active
one. Stating it as a single over-claiming bug, as this row originally did, was wrong.

Prevalence on BaseApp, and note it is much lower than "617 files contain `#if`" suggests, because
most of Microsoft's directives sit at DECLARATION level where no statement slot is at stake:

| | count |
| --- | ---: |
| files containing `#if` | 617 of 8,020 |
| statement-level `preproc_conditional_statement` blocks | 373 |
| `call_expression` direct children (lost statement slots) | 374 |
| `assignment_statement` direct children (lost) | 20 |
| `if_statement` direct children | 42 |

The loss is bounded to DIRECT children: an `if` inside a directive has its own `statement_block`,
so its inner statements are unaffected.

**What this changes about closing it.** The three options above all address the over-claim only.
Any fix must now answer both directions, and the cheapest option gets worse rather than better:
refusing to enumerate inside directive blocks fixes the over-claim and PERMANENTLY entrenches the
under-claim. Teaching `isStatementPosition` to treat `preproc_conditional_statement` as a statement
container is a small, separable change that fixes the under-claim on its own, and is worth doing
regardless of which route the over-claim takes.

See [[R159]] for the census this was invisible to, and the issue #6 harness
(`scripts/probe-grammar-crosscheck.ts`) for how to reproduce it.

## 4.4.1 (2026-09-27): directive code parses where it used to ERROR, so exposure can only grow

tree-sitter-al 4.4.1 step A (#24, #25; upstream commits `0791253`, `bc72141`, `028cbdd`,
`e0ab7a4`) fixes three more directive shapes: an operator dangling before `#if`, a `begin`/`end`
(or a `case`, or a report's braces) split across a `#if` branch boundary, and a binary operator
opening a `#if` continuation. Upstream's own measurement: BC.History's 15,358 trees byte-identical
after each commit; BC 28.1 Base Application (upstream's own snapshot, 8,073 files) goes from 5
files with an ERROR node to 0.

Locally: the exploratory `bc281` copy used by TSAL-441 (build `28.1.49838.50244`, not upstream's
own `28.1.49838.50268`) already had 0 files with an ERROR or MISSING node under the OLD grammar
(4.3.0), including all five files upstream names as fixed. So this build does not reproduce
upstream's 5 -> 0 result, and adds no local confirmation of it
(`docs/superpowers/specs/2026-09-27-tsal441-grammar-bump-precommitment.md`'s AMENDMENT 1;
`docs/measurements/2026-09-27-gh06-grammar-crosscheck.md` section 10.5). No other copy of BC 28.1
Base Application was found on this machine, so upstream's own BC.History/BC 28.1 count is the only
measurement of this fix; locally it is "not measured".

The fix makes MORE directive code parse cleanly, which is exactly what widens this row's exposure:
every shape that used to ERROR now produces a real tree that LethAL's site enumeration walks like
any other code, `#if` guard and all, with none of the special handling an ERROR node might have
forced.

**Six new named kinds, and `isStatementSlot` knows none of them:** `preproc_operand_prefix`,
`preproc_split_case_end_branch`, `preproc_split_case_statement_end`,
`preproc_split_report_brace_close`, `preproc_split_report_dataitem_header`,
`preproc_split_report_dataitem_open_over_endif`
(`docs/measurements/2026-09-27-gh06-grammar-crosscheck.md` section 10.6).

**Census result on LethAL's own corpora:** across do, dc, sentinel, bcf, sysapp and BaseApp (both
halves), zero moved census rows sit in directive code anywhere in the TSAL-441 bump (its
pre-commitment's P4 and AMENDMENT 1); every moved row's construct settled to #26, #27 or #28 on its
own, none to step A. Zero moved rows shows no OBSERVED census effect from step A on these corpora;
it does not show that none of them carry the step-A shapes, since a shape can sit there without
producing a moved row. Either way, this bump neither confirms nor refutes the exposure growth
locally; it is read off upstream's BC 28.1 figure alone.

See [[R293]] for the narrower, separate gap this surfaced in the cross-check's own directive
detector (`scripts/probe-grammar-crosscheck.ts`'s R2 guard), which is blind to the same six new
`preproc_*` kinds for a different reason: it recognises only `preproc_conditional*`, so it now
under-reports "guarded" the same way section 6 already showed for the pre-4.4.1 kinds it missed.
