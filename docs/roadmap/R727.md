**Filed 2026-10-24 by lethal-preproc during R-709.** Related: [[R709]], [[R707]], [[R711]].

**What.** Every `lethal run` publishes the instrumented target as an upgrade over whatever is installed. When an
installed app that depends on the target no longer compiles against the new build, BC refuses the upgrade, cannot
restore the old target, and REMOVES every installed dependent (R709, measured by R-707). Since R709 LethAL refuses by
name at that point and prints BC's list. But that is after the fact. On a customer's development server those
dependents can be the customer's own extensions, not only the tests app.

**The question.** Should LethAL warn, or refuse unless confirmed, BEFORE publishing over installed dependents other
than the tests app on a server that is not a LethAL fixture server? Two shapes:
- read the target's installed dependents at run start (by app id; never list all extensions, R433) and warn, naming
  them;
- check each dependent's resident source against the new build first, as `bc-linux-setup.ts` and `bc-republish.ts`
  do since R-707 (`guardResident`, `guardDependents`).

The second is costly per run, and it needs symbols for apps LethAL does not own.

**Not built.** Prevention, for later. Needs first: how a dependent list is read by id over the dev or API endpoint,
and what a run should do when the list cannot be read.
