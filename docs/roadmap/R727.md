**Filed 2026-10-24 by lethal-preproc during R-709.** Related: [[R709]], [[R707]], [[R711]].

**What.** Every `lethal run` publishes the instrumented target as an upgrade over whatever is installed. When an
installed app that depends on the target no longer compiles against the new build, BC refuses the upgrade, cannot
restore the old target, and REMOVES every installed dependent (R709, measured by R-707). Since R709 LethAL refuses by
name at that point and prints BC's list. But that is after the fact. On a customer's development server those
dependents can be the customer's own extensions, not only the tests app.

**The question.** Should LethAL warn, or refuse unless confirmed, BEFORE publishing over installed dependents other
than the tests app on a server that is not a LethAL fixture server? Two shapes:
- read the target's installed dependents at run start (by app id; never list all extensions, R433) and warn, naming
  them;
- check each dependent's resident source against the new build first, as `bc-linux-setup.ts` and `bc-republish.ts`
  do since R-707 (`guardResident`, `guardDependents`).

The second is costly per run, and it needs symbols for apps LethAL does not own.

**Not built.** Prevention, for later. Needs first: how a dependent list is read by id over the dev or API endpoint,
and what a run should do when the list cannot be read.

## Built 2026-10-24 (coord task R-727, lethal-code): shape 1, as a count (option (b))

- **Measured first (bc3, read-only):** no standard BC endpoint gives an app's dependents by id. The `$metadata` of
  the automation API v2.0, API v2.0 and OData v4 has no dependency entity or property, apart from LethAL's own
  `DependentCount` (control 1.0.0.23). That counts PUBLISHED packages, any version, that declare an app as a
  dependency. On bc3 it gave Sandbox App, Data and Hang 1 each, Harden 2 and Tests 0, in 150-250 ms per call.
- **The rule** (`packages/runner/src/dependents-warning.ts`, wired in `runSession` before the first `deployOnce`,
  once per run):
  - A bcdev run reads `dependentCount(<target id>)`. When N exceeds the dependents the run accounts for (K is 1 when
    the tests app.json declares the target), it warns with code `installed-dependents`, on stderr and as a progress
    `warning` event, naming N, K and the target, and citing R709.
  - A failed read warns that the check could not run, with the reason.
  - It never refuses. There is no SessionReport field. al-runner backends make no call.
- **Known limits:**
  - No names: that needs control 1.0.0.24, [[R733]], after the Directions talk.
  - The count includes every published version, installed or not, so old versions can inflate it.
- **Tests:** `packages/runner/tests/r727-dependents-warning.test.ts`, red-checked per direction: never warns, always
  warns, a swallowed read error, the check removed, and the check moved after the deploy.
- **Pre-commitment:** `docs/superpowers/specs/2026-10-24-r727-dependents-warning-precommitment.md` (master
  e604a764). Every gate figure is unchanged; only `itest:harden` prints the warning (2 vs 1, harden-answers).
