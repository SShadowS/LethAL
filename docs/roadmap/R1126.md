Found by coord PR-158 (lethal-bugs, 2026-11-18), the al-runner vs BC test-by-test hunt on BC.History pairs. Upstream:
https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8333. Evidence: `/coord/handoff/PR-158/result.md`, the invented
probe `probe-aa/` (BC's answers in `bc3.out.txt`, al-runner's in `v3.out.txt`), and the sizing in `sizing/`.

**The defect (a wrong answer, not a refusal).**
- BC removes a page control when its `ApplicationArea` is not enabled for the session. A TestPage then raises `The field with
  ID = <id> is not found on the page.` al-runner applies the same rule (upstream #4750, closed).
- A BC test session starts with the company's experience-tier areas. In bc3's Essential company, `ApplicationArea()` returns
  `#Basic,#Suite,...` (34 areas).
- al-runner reads the same company as Essential too (the tier, the `Application Area Setup` record and the custom area's field
  all agree), but its session starts with an EMPTY area string. Under #4750's rule an empty string finds every control.
- So a control whose areas are not enabled in Essential is found on al-runner and not on BC. The probe measured this on BC 28.4
  (bc3, dev-endpoint runner) against edge-4ebfe7913. The control was in a custom area enabled only by
  `OnGetPremiumExperienceAppAreas`. SetValue passes on v3 and fails on BC, and `Visible()` answers Yes on v3 and raises on BC.
- A control in area All, and one in a group hidden by a Visible expression, agree on both runners.
- Where it was met: Microsoft's Subcontracting tests (a scratch-id copy, run on bc3). All 7 WIP adjustment tests pass on v3 and
  fail on BC with this error. Their page's area `Subcontracting` is enabled only for Premium.

**The verdict risk.**
- A test that BC fails is green on v3. On BC it is left out of the green set; on v3 it scores mutants.
- So a mutant it kills on v3 has a kill that BC, in an Essential company, would not give: a **false kill**, unless another green
  test kills it too.
- Mutants that only this test covers are scored on v3 and are no-coverage on BC.
- A test that sets the session's areas first (any `Library - Application Area` call) is not affected: both runners then use the
  string it set.
- The risk depends on the company: a Premium company enables more areas.

**How many, by parse** (`/coord/handoff/PR-158/sizing/`, `summary.md`).
- The parse covers 86 projects: R-975's 83 BC.History projects, DO and DC.
- A control is at risk when none of its areas is enabled in Essential, counting custom areas that the app's own Basic or
  Essential subscriber assigns as enabled.
- **Tests:** 98 at-risk tests with no area setup. **87 pass in the stored v3 baseline**, 2 fail and 9 are refused.
- **Kills resting on them: 5, all in Subcontracting.**
- By project:
  - `sub`: 81 tests, 79 passing;
  - `sus`: 15 tests (area `Manufacturing`);
  - `pbi`: 2 tests.
- **DO: none.** Its areas CDOBasic and CDOEDocumentSetup are enabled by its own OnGetEssentialExperienceAppAreas subscriber, under
  a condition: 15 tests depend on that condition.
- **DC: none.**
- The counts are a floor: only same-codeunit helpers are followed, and a library helper that sets areas is missed.

**To close.** An al-runner build whose test session starts with the company's areas, so the probe's
`SetControlInPremiumOnlyArea` fails as BC's does. Add the probe as a regression entry when upstream answers.
