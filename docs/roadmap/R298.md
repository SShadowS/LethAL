**Found by RUST-01 Task 0 (2026-09-27), running the normal product pipeline
(`generateMutationSet` + `writeInstrumentedProject`) over whole real corpora.**

**What throws.** `injectMutationSelectorVar` (`packages/schemata/src/compile.ts`) throws when a
mutation guard's enclosing AL object (found by walking up from the spec's `before` node via
`enclosingObjectDeclaration`) is not one of `CARRIER_KINDS` (codeunit/table/page/report/the two
extension kinds). Two of the seven non-fixture corpora hit this, both naming the same node kind:

- **bcf** (`U:/Git/BC.History/BusinessFoundation`, 104 files): exit 1, on
  `Source\Business Foundation\NoSeries\src\Legacy\NoSeriesLinePurchase.Table.al` — "a mutation
  guard sits inside `preproc_conditional_object`, and ... Spec generation is supposed to have
  dropped this file already."
- **BaseApp whole-corpus capture** (`U:/Git/BC.History/BaseApp`, 9,620 files, RUST-01 Task 0
  Step 6): `compileSchemataForFile: cannot instrument
  Source\Base Application\CRM\Outlook\BookingItems.Page.al — a mutation guard sits inside
  preproc_conditional_object ...` — the same defect, reached only after spec generation for the
  whole corpus completed (a ~138 s, 8.75 GB run).

**Why it throws, read from the code.** `enclosingObjectDeclaration` (`compile.ts`) walks up from
a spec's `before` node and returns the first ancestor whose *parent* is `source_file` — it does
not unwrap preprocessor-conditional wrapper nodes. When an object declaration (a `table` or
`page` here) is itself wrapped in a `preproc_conditional_object` node (the whole object sits
inside `#if ... #endif`), that walk returns the WRAPPER, not the table/page inside it, and
`preproc_conditional_object` is not in `CARRIER_KINDS` — so the function's last-resort throw
fires. Meanwhile `canCarryMutationSelectorVar` (`compile.ts:217`), which decides whether
`generateMutationSet` keeps the file's specs at all, uses `findFirst` — a recursive search that
finds the table/page regardless of the preprocessor wrapper — so it answers "yes, injectable" and
the file's specs are generated and reach `injectMutationSelectorVar`, which then cannot honor
that answer. The file is never one `assertNoUnsupportedObjectMix` would refuse either (that check
is about *multiple* object headers in one file, not a wrapped single one). The throw's own message
("spec generation is supposed to have dropped this file already") states an invariant the code
does not actually enforce for this shape. Note `packages/runner/src/testpage-scan.ts:72` already
unwraps `preproc_conditional`/`preproc_conditional_var`/`preproc_conditional_object` nodes for its
own purpose, so the unwrapping logic has precedent elsewhere in the codebase; `compile.ts`'s
object-walking code does not use it.

**Why it matters.** A real target project containing even one preprocessor-conditional object
declaration of this shape cannot be instrumented — the whole run aborts with a thrown `Error`
instead of a narrowed or degraded result, even though the file's specs were already deemed
injectable by an earlier check in the same pipeline. It also blocks RUST-01's own whole-corpus
identity capture (Q2 of `docs/superpowers/sdd/2026-09-27-RUST-01-native-parser/`'s brief): there is
no WASM-pipeline identity listing for bcf or for the whole BaseApp corpus to compare the native
pipeline's capture against.

**What would close it.** Either (a) make `enclosingObjectDeclaration` unwrap
`preproc_conditional_object` (and any sibling preprocessor wrapper kinds) the way
`testpage-scan.ts` already does, so the guard is correctly attributed to the table/page inside it
and instrumented normally, or (b) make `canCarryMutationSelectorVar`/`generateMutationSet`'s
upstream filter recognize and drop this shape up front (matching the throw's own stated
invariant), if wrapped objects are not meant to be instrumented at all. Re-run RUST-01 Task 0's
Step 5 (bcf) and Step 6 (whole BaseApp) afterward to confirm both corpora reach an identity
listing.
