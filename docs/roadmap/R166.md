`packages/engine/src/ast/hash.ts` canonicalises **every** `identifier` node to a positional id:

```ts
if (node.kind === ALNodeKind.identifier) {
  if (!scope.has(text)) scope.set(text, scope.size);
  return `(identifier #${scope.get(text)})`;
}
```

`design.md` §5.1 describes this as "local variable names canonicalized to positional ids", and says
the hash "changes when the expression's structure or operators change". A METHOD name is neither a
local variable nor structure, and it is erased along with them.

**Measured, not argued.** Parsed under the vendored grammar:

```
0a4aa6ba624a968a  DataMain.Delete(false)
042be415edc59abb  DataMain.Init()
0a4aa6ba624a968a  DataMain.Insert(false)
0a4aa6ba624a968a  DataMain.Modify(false)
```

`Delete`, `Insert` and `Modify` are one hash. `Init()` differs only because it takes no argument.

The same collapse hits arguments. In the gift card demo the three guard clauses

```al
Error(CardBlockedErr, CardNo);
Error(CardExpiredErr, CardNo);
Error(InsufficientBalanceErr, CardNo);
```

all canonicalise to `(call (member (identifier #0)) ((identifier #1) (identifier #2)))`, so their
three `void-method-call` mutants share ONE identity key, `ad08668…|Gift Card Mgt|
lethal.void-method-call|1`, with multiplicity 3. The re-recorded campaign baseline shows exactly
that, and the three are killed by three DIFFERENT tests (`RedeemBlockedCardFails`,
`RedeemExpiredCardFails`, `RedeemMoreThanBalanceFails`).

**Why it matters.** The identity key
`(astSubtreeHash, enclosingObjectName, operatorName, operatorMajorVersion)` is what §5.1 uses for
**history filtering**: "a mutant surviving on main and still surviving on PR is noise; newly
surviving mutants are signal". Two genuinely different mutants under one key make that question
unanswerable for them. On the demo, if the blocked-card guard started surviving while the
expired-card guard kept being killed, history could not tell which of the three moved.

**What it does NOT break, measured:** nothing today. Mutant generation and dedup key on SPANS, not
on this hash, so no mutant is dropped or conflated during a run; both live gates pass with the
collisions present, and `baseline-guard.ts` compares as a MULTISET precisely because "a semantic
identity legitimately repeats". The exposure is history filtering, plus any future feature that
treats the key as unique.

**Not caused by R161.** R161 only made an existing group grow, which is how it surfaced: the
baseline diff reported "appears 1 time in before but 2 times in after (semantic-identity group size
changed)" for `Data Ops`, where the new `DataMain.Delete(false)` mutant landed in the same group as
the pre-existing `DataMain.Insert(false)` one.

**A fix has to be careful in one specific way.** The obvious change, hashing an identifier's text
when it is a call's method name, must NOT re-introduce sensitivity to local variable renames, which
is the property the canonicalisation exists to provide. The narrow version is: keep positional ids
for identifiers in variable position, and keep the TEXT for the identifier that is a
`call_expression`'s callee (and the member name inside it). Whoever does it should re-record both
per-mutant baselines and set-diff them, because every mutant's key changes and a re-record that is
not read is a re-record that proves nothing.

**HALF FIXED 2026-08-19, and the half that remains is the one this row was named for.**

`serializeCanonical` now keeps an identifier's TEXT when it sits in a NAME position — the `member`
field of a `member_expression`, or a `call_expression`'s `function` field — and keeps the positional
id everywhere else. So `DataMain.Delete(false)`, `.Insert(false)` and `.Modify(false)` are three
hashes where they were one, and `Rec.Amount` differs from `Rec.Qty`.

**Proven to be a pure relabelling, which is the thing that had to be shown.** Every mutant's key
changes, so a re-recorded baseline diff is unreadable by itself. Instead the fixture was run twice,
once with each version of the hash, and the per-mutant listings compared on
`(file:line, operator, verdict)`:

| | |
| --- | ---: |
| rows compared | 237 |
| added | **0** |
| removed | **0** |

Identical. The verdict multiset of both re-recorded baselines is unchanged too. No verdict moved;
only labels did.

**Measured payoff:**

| | tables fixture | gift card demo |
| --- | --- | --- |
| distinct keys | 188 -> **206** | 32 -> **35** |
| mutants sharing a key | 73 -> **49** | 17 -> **15** |

**What is NOT fixed, and it is this row's own example.** The three `Redeem` guard deletions

```al
Error(CardBlockedErr, CardNo);
Error(CardExpiredErr, CardNo);
Error(InsufficientBalanceErr, CardNo);
```

still share one key, and they are killed by three DIFFERENT tests. They differ only in which
identifier is passed as the first ARGUMENT, and argument identifiers are exactly what the
canonicalisation exists to make invariant: a local rename must not reset history. The three labels
are named constants rather than locals, but the hash layer is purely syntactic and cannot tell a
`Label` from a variable without asking the symbol table, which `astSubtreeHash` deliberately does
not do (it takes a node, not a context).

So closing this row completely means one of:

1. **Give the hash a scope oracle**, so a `Label` or global constant keeps its text while a local
   stays positional. **COSTED 2026-08-19, and it is cheaper than this row first said.**
   `astSubtreeHash` has exactly ONE production caller — `packages/schemata/src/project.ts`, building
   the manifest — plus tests. `writeInstrumentedProject` already takes an options object, so the
   oracle is an ADDITIVE optional field, and the orchestrator that calls it already builds a
   `SemanticContext` (`buildSemanticContext`, orchestrator.ts) which would have to be threaded to
   that call. "Changes its signature and every caller", as written above, was wrong.

   The real cost is not the plumbing: it is that every mutant's key moves again, so BOTH per-mutant
   baselines re-record and each needs the same before/after proof this row's first half already
   paid — running the fixture twice and diffing on `(file:line, operator, verdict)` — because a
   re-record nobody reads proves nothing.
2. **Keep argument identifiers positional and accept the collision**, recording that history cannot
   distinguish two calls differing only in a named constant. That is where it stands today.
3. **Include the ARGUMENT INDEX of a differing identifier**, which does not help: both calls have the
   identifier at index 0.

Option 1 is the only real fix and it is not a small change. The exposure is unchanged from what this
row already recorded: nothing today is wrong, because generation and dedup key on spans and the
baseline comparison is a multiset; the cost lands on history filtering, which cannot tell those three
apart.

**CLOSED 2026-08-20. The row's headline case is fixed, and the fix was not where this row looked.**

R166's first half made method and field NAMES hash distinctly. The headline case it left open was
"three guards differing only in an ARGUMENT identifier", and the status said doing better "needs a
semantic distinction the hash layer does not have". That is true and it was the wrong place to look:
the distinction does not have to live in the HASH, it has to live in the IDENTITY, and the identity
already had room for it.

**What was measured first.** On `fixtures/sandbox-data`, keyed the old way: 26 groups shared a key
covering 89 of 280 specs. In the committed `tables.baseline.json`: 259 mutants over **225** distinct
keys, 20 conflated groups, and **six of those groups held mutants with DIFFERING verdicts**.

**Why differing verdicts inside one group is the actual defect.** `diffMutants` compares each key's
group as a MULTISET, deliberately and with a documented reason: keying on a within-key ordinal
instead would reintroduce the report-order sensitivity that made a re-record differ as text while
being semantically equal. That decision is right. Its consequence is that a group holding
`['killed','survived']` stays `['killed','survived']` however the two are dealt, so a regression that
swapped WHICH of them is killed was invisible. `resume.ts` and `selection.ts` read the same identity
to carry a verdict into a resumed run and to skip known survivors, so there the same collision does
not merely hide a change, it applies a verdict to the wrong mutant.

**The fix.** `procedureName` joined `IdentityKey`, falling back to `triggerName` where there is no
enclosing procedure. It is a stable SEMANTIC property, not an ordinal, so it separates without
reintroducing order sensitivity.

| | before | after |
| --- | ---: | ---: |
| `itest:tables` distinct keys / 259 mutants | 225 | **258** |
| conflated groups | 20 | **1** |
| groups that could hide a verdict swap | **6** | **0** |
| gift-card demo, keys / 45 mutants | 37 | **43** |
| `itest:bcdev` / `alrunner` / `envtool` | 17 / 17 | unchanged, already 1:1 |

The single residual on each side is honest and cannot hide anything: two `swap-additive` mutants in
two different fields' `OnValidate` of one table (both `survived`), and three `void-method-call`
mutants in one procedure (all `killed`). Separating those needs a field name and a statement
ordinal respectively, and the ordinal is the thing this design refuses.

**Verification.** A red-first test asserts a swap between two same-subtree mutants in different
procedures is SEEN. Its first draft passed before the fix, because the two mutants differed by
`killingTest` and the swap was caught through that rather than through identity — the test named one
thing and proved another. It now holds every compared field equal except the exchanged verdict, which
is what makes it a test of the identity. A second test pins the trigger fallback, which no live gate
exercises: on this fixture trigger mutants already have distinct subtree hashes, so the key count is
the same either way.

All five baselines were re-recorded and each compared against its predecessor IGNORING the key: the
multiset of (verdict, killingTest, coverageFiltered, errorClass) is IDENTICAL on all five. Keys
changed, no verdict did.

**One real bug was introduced and caught during the work**, and it is worth recording because it
would have hit every existing user. The identity index named the new column inside `SCHEMA`, which
`new ResultsStore` runs BEFORE `migrate()` adds it, so opening any pre-R166 `lethal.sqlite` threw
`no such column: procedure_name` from the constructor — and because the constructor threw, its
database handle was never closed and the file stayed locked. It surfaced as an EBUSY in an unrelated
test's cleanup, which is exactly how a constructor-thrown error hides. The index now belongs to
`migrate()`, rebuilt once when the stored definition does not already cover the column, and a test
opens a pre-R166 database and asserts both the open and the index.

Pre-R166 rows read back with `procedure_name` NULL. Both readers DROP a null rather than coercing it
to `""`, because an empty scope is a REAL value for an object-level mutant: coercing would let an old
row match a genuine object-level mutant and either skip it as a known survivor or carry a stale
verdict onto it. Dropping costs one re-run, which is the cheap direction.
