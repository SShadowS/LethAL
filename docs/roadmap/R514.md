**Priority.** Filed 2026-10-08 by R-512's build, from open question (a) of the R-512 plan (r3), which the plan's
adversarial review asked to be filed with priority. A false-kill risk. Found by reading the code and one offline
measurement; not verified live. Not fixed by [[R512]], which closes only the case where the session had evidence
against the snapshot.

**What.** On `--resume`, a batch whose instrumented source and test app hash the same as an earlier run's batch
reuses that run's baseline snapshot (R192, `findBaselineSnapshot`): its verdicts, coverage and durations. A covered
run that answers `timeout` at group position 1 is scored `timeout-killed` with no unmutated confirm. Only a `fail`
gets the kill-confirmation rerun, and only a position greater than 1 gets `confirmWarm`'s replay. Its budget comes
from the reused snapshot's duration: `max(2 x baseline duration, minMutantBudgetMs)`. So any reused snapshot whose
test has gone slow or red since it was recorded can produce a false `timeout-killed`. The R192 warning
(`resume-baseline-reused`) already says that a test that has gone red since is not detected.

**Most likely live shape.** A fast duration reused on a slower day: the snapshot was recorded when the test ran in
a few hundred milliseconds, the environment is slower today, the test runs past twice that, and the mutant scores
a kill it did not cause. No wrong binary is needed.

**Second route (also named by the R-512 plan, r3).** Once [[R512]] marks a snapshot S_A suspect,
`findBaselineSnapshot` falls through to the NEXT-newest snapshot with the same two hashes. That one may have been
recorded in the same stale period, with no evidence against it. The suspect mark refuses one snapshot, not a
period.

**Evidence.** The R512 repro (`resume.test.ts`, describe "R512: an attestation-invalidated batch's baseline
snapshot, then --resume") measured the reused-snapshot route before R512's fix: a test that times out on the real
binary scored `M0001 timeout-killed` (killing test `OverBudgetDetected`) with zero baseline runs, because the reused
snapshot said the test was green. R512 stops that one route (a snapshot the session had unattested evidence
against). It does not touch the general one: the same shape with a snapshot that carries no mark still scores the
kill. The hang-at-batch-start case R192 keeps on purpose is included.

**Proposed fix.** When the batch's baseline was reused, confirm a position-1 `timeout` unmutated at the same
budget before scoring it, as `confirmWarm` does for a later position. A confirm that also times out makes the
verdict an `error` (the test is slow or red without the mutant), not a kill.

**To close.** Reproduce offline first (a reused snapshot with a short duration, a covered run that times out at
position 1, today scored `timeout-killed`). Then add the confirm on the reused-baseline path, pin both directions
(a reused baseline's position-1 timeout is confirmed; a freshly measured baseline's is scored as today, or also
confirmed if the ruling says so), red-checked. Decide separately whether a suspect mark should also refuse older
snapshots with the same two hashes.

**Fix (e461bc90, plan r2 `docs/superpowers/plans/2026-10-08-R-514-reused-baseline-confirm.md`).** On a batch that
reused a stored baseline, a position-1 `timeout` goes through the cold kill confirmation: one unmutated run at
`max(budget, baselineTimeoutMs)`, and the kill stands only if `2 x confirm.durationMs <= budget` (R53's margin, not
1x, after the review's C1). On bcdev that is a real 2x margin. On al-runner one-shot it is only about 1x: the in-run
test timeout is half the budget, and the confirm's wall clock includes the compile, so a test running just under
budget/2 unmutated can still be scored a kill (final build review I1; the same exposure exists on a fresh al-runner
batch, so it is filed under [[R516]], not fixed here). A slower confirm is `error` with the new cause `reused-budget-stale` (explain schema
v14); a confirm that fails or times out is `unstable`; an overrun confirm under the default floor strands and
quarantines, as a re-run baseline would. `confirmWarm`'s timeout grain uses the same 2x rule on a reused batch. A
fresh batch is unchanged. Offline evidence: the four repros flipped and every named check red-checked
(`packages/runner/tests/resume.test.ts`, describe "R514: a reused baseline's durations set today's budgets").
Decision (4): the suspect mark is unchanged; it still refuses one snapshot, and the confirm now covers the older
snapshot route (b2) too. Filed from this fix: [[R515]] (option C, feeding the confirm's duration back into later
budgets) and [[R516]] (a fresh baseline's position-1 timeout, and durations from one worker's tier). To close:
`itest:hang` and the R514 reuse probe pass against their pre-commitments
(`docs/superpowers/specs/2026-10-08-r514-hang-reused-confirm-precommitment.md`,
`docs/superpowers/specs/2026-10-08-r514-reuse-probe-precommitment.md`), then `done (<commit>)`.
