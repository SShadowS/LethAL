`parseArgs` runs in strict mode over ONE option set for every subcommand, so a flag belonging to
`campaign` parses happily on `run` and then does nothing.

**R151 already named this hazard and fixed it for one flag.** Its comment is explicit that `--json`
is *"REFUSED elsewhere rather than ignored"*, because a silently-dropped `--json` hands a caller the
prose rendering while they believe they asked for a machine surface. The principle was right. It was
applied to `--json` and to nothing else.

**MEASURED 2026-08-27**, by passing each shared flag to `lethal run --dry-run` and reading the exit
code: `--json` refused, and **`--report`, `--manifest`, `--stage`, `--expect-mutants`, `--top` and
`--force` all silently accepted**.

## The one that cost real time

`lethal run --out r.json` writes the JSON report. `--report` is `campaign compare`'s flag. A run
given `--report` **completes normally, prints its score, and writes nothing** — and a run that wrote
no report is indistinguishable from one that wrote a report somewhere else. That is empty-vs-empty,
this project's signature bug, in the argv layer. It was found by a session that then had to re-run a
live campaign to get the file.

## The fix

`FLAG_OWNERS` maps each shared flag to the subcommands that own it plus a sentence naming what to
use instead, and `refuseFlagsThisSubcommandDoesNotOwn` throws for anything else. `--report` on `run`
now says to use `--out`, which is the mistake the flag is actually made for. Flags that are shared on
purpose (`--project`, `--config`) are owned by nobody and are absent from the table.

A boolean counts as present only when TRUE: the shared table defaults `force`/`json` to `false`, so
"absent" and "explicitly false" are one value and refusing on falsiness would reject every ordinary
invocation. `cli.test.ts` red-checks exactly that.

Pinned as a TABLE in the test rather than a case per flag, so a flag added to the shared option set
without an owner surfaces as a gap here rather than as a silent acceptance a year later.
