Found by coord task R-882 (BC.History Payment Practices on `bc5` against R-881's v3 run `pp1`, 2026-11-09). Evidence:
`/coord/handoff/R-882/S2.report.json`, `S2.events.ndjson` (baseline), `pp-diff-r4.json`. Related: [[R060]] (every bcdev verdict
describes the non-GUI branch), [[R890]] and [[R857]] (other splits between the two backends).

**What.** `Payment Practice Header`'s `Header Type` and `Aggregation Type` `OnValidate` ask through
`ConfirmManagement.GetResponseOrDefault(..., true)`. That asks only when `GuiAllowed`; otherwise it returns the default silently.
- On BC (bcdev, fenced web-service session, non-GUI) no confirm is raised. `ConfirmToCleanUpOnTypeValidation` and
  `ConfirmToCleanUpOnAggrValidation_Yes` fail at baseline with "The following UI handlers were not executed: ConfirmHandlerYes";
  `_No` fails because the default (yes) cleared the lines.
- On al-runner v3 the confirm IS raised: `ConfirmToCleanUpOnTypeValidation` passed at baseline, with its handler run.

**Effect on verdicts.** 7 mutants in that `OnValidate` (`PaymentPracticeHeader.Table.al` lines 56-63) were killed on v3 by
`ConfirmToCleanUpOnTypeValidation` and `survived` on BC. 28 more are `error` on BC ("covered only by tests that did not pass at
baseline"). Neither backend is wrong about its own branch; they measure different branches of the same code, and the report does
not say which.

**To decide.** Make v3 non-GUI like BC (if al-runner can run with `GuiAllowed` false), or name the branch in the report for each
backend. Measure first: how many sites in a real suite sit behind `GuiAllowed` (R060 counted 0.3% on one app).

## Measured, and pre-committed before the change (coord task R-901, 2026-11-10)

**al-runner cannot run tests with `GuiAllowed` false.** Probe on edge-3096bf68f (`/coord/handoff/R-901/repro-gui/`, invented): a
test's `GuiAllowed()` answers Yes, and a `Confirm` behind `if not GuiAllowed() then exit(Default)` is raised and handled. `--help`
lists no option; `--list-assumptions` sets it false only while the Contoso company is built; an older source tree hard-codes `true`.
Requested upstream: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/7564.

**So LethAL names the branch.** Today the report claims the opposite for v3: `measuredExecutionContext` gives al-runner-v3
`guiAllowed: false` and "executes headlessly by construction", and the console prints `NON-GUI EXECUTION ... (GuiAllowed=No,
ClientType=al-runner v3 CLI)`. That is wrong.

**Pre-committed, before any code:**
- v3 runs: `validity.executionContexts[].guiAllowed` becomes **true**, with a basis naming this measurement.
- The console's `NON-GUI EXECUTION` line counts only contexts with `guiAllowed` false, so a v3-only run no longer prints it.
- A new line, `GUI EXECUTION (al-runner v3)`, names v3's branch, and says a mutant behind `GuiAllowed` or a confirm wrapper can reach
  a different verdict than on BC's fenced path (this item).
- bcdev runs are unchanged (`guiAllowed: false`, the same line).
- **No verdict moves** on any backend; the v3 gate's per-mutant figures are unchanged. Only report text and that one field move. The
  tests that pin v3's old claim (`non-gui-execution.test.ts`, `r586-backend-kind.test.ts`) change deliberately.
- Committed sample reports keep what they recorded at the time; none is regenerated.
