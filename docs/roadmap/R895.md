Found by coord task R-882 (BC.History Payment Practices on `bc5` against R-881's v3 run `pp1`, 2026-11-09). Evidence:
`/coord/handoff/R-882/S2.report.json`, `S2.events.ndjson` (baseline), `pp-diff-r4.json`. Related: [[R060]] (every bcdev verdict
describes the non-GUI branch), [[R890]] and [[R857]] (other splits between the two backends).

**What.** `Payment Practice Header`'s `Header Type` and `Aggregation Type` `OnValidate` ask through
`ConfirmManagement.GetResponseOrDefault(..., true)`. That asks only when `GuiAllowed`; otherwise it returns the default silently.
- On BC (bcdev, fenced web-service session, non-GUI) no confirm is raised. `ConfirmToCleanUpOnTypeValidation` and
  `ConfirmToCleanUpOnAggrValidation_Yes` fail at baseline with "The following UI handlers were not executed: ConfirmHandlerYes";
  `_No` fails because the default (yes) cleared the lines.
- On al-runner v3 the confirm IS raised: `ConfirmToCleanUpOnTypeValidation` passed at baseline, with its handler run.

**Effect on verdicts.** 7 mutants in that `OnValidate` (`PaymentPracticeHeader.Table.al` lines 56-63) were killed on v3 by
`ConfirmToCleanUpOnTypeValidation` and `survived` on BC. 28 more are `error` on BC ("covered only by tests that did not pass at
baseline"). Neither backend is wrong about its own branch; they measure different branches of the same code, and the report does
not say which.

**To decide.** Make v3 non-GUI like BC (if al-runner can run with `GuiAllowed` false), or name the branch in the report for each
backend. Measure first: how many sites in a real suite sit behind `GuiAllowed` (R060 counted 0.3% on one app).

## Measured, and pre-committed before the change (coord task R-901, 2026-11-10)

**al-runner cannot run tests with `GuiAllowed` false.** Probe on edge-3096bf68f (`/coord/handoff/R-901/repro-gui/`, invented): a
test's `GuiAllowed()` answers Yes, and a `Confirm` behind `if not GuiAllowed() then exit(Default)` is raised and handled. `--help`
lists no option; `--list-assumptions` sets it false only while the Contoso company is built; an older source tree hard-codes `true`.
Requested upstream: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/7564.

**So LethAL names the branch.** Today the report claims the opposite for v3: `measuredExecutionContext` gives al-runner-v3
`guiAllowed: false` and "executes headlessly by construction", and the console prints `NON-GUI EXECUTION ... (GuiAllowed=No,
ClientType=al-runner v3 CLI)`. That is wrong.

**Pre-committed, before any code:**
- v3 runs: `validity.executionContexts[].guiAllowed` becomes **true**, with a basis naming this measurement.
- The console's `NON-GUI EXECUTION` line counts only contexts with `guiAllowed` false, so a v3-only run no longer prints it.
- A new line, `GUI EXECUTION (al-runner v3)`, names v3's branch, and says a mutant behind `GuiAllowed` or a confirm wrapper can reach
  a different verdict than on BC's fenced path (this item).
- bcdev runs are unchanged (`guiAllowed: false`, the same line).
- **No verdict moves** on any backend; the v3 gate's per-mutant figures are unchanged. Only report text and that one field move. The
  tests that pin v3's old claim (`non-gui-execution.test.ts`, `r586-backend-kind.test.ts`) change deliberately.
- Committed sample reports keep what they recorded at the time; none is regenerated.

## Built (f85a6c52), and sized

- `measuredExecutionContext` gives al-runner-v3 `guiAllowed: true` on the measured basis. `summarizeRunnerContexts` takes a
  `guiAllowed` filter: the `NON-GUI EXECUTION` line counts only contexts without a client, and a new `GUI EXECUTION (al-runner v3)`
  line names v3's branch and the possible verdict difference against BC. README says the same. Tests in `non-gui-execution.test.ts`,
  red both ways. As pre-committed, only `non-gui-execution.test.ts` changed; `r586-backend-kind.test.ts` needed no change.
- **How much code reaches the branch directly**, by parse (`/coord/handoff/R-901/count-gui2.ts`; two invented probe apps as the
  positive control, both counted exactly). It counts `GuiAllowed` as an identifier anywhere (bare `if GuiAllowed then` too), direct
  `Confirm(...)` and `StrMenu(...)` calls, and `GetResponse` / `GetResponseOrDefault` called on a receiver whose name contains
  "confirm"; the last column is the union of files:

  | corpus | files | `GuiAllowed` (files) | `Confirm` / `StrMenu` (files) | confirm wrapper (files) | files with any |
  |---|---|---|---|---|---|
  | DO | 814 | 50 (21) | 77 (54) | 12 (6) | 77 (9.5%) |
  | DC | 878 | 67 (21) | 75 (34) | 3 (2) | 44 (5.0%) |
  | BC.History | 17,451 | 903 (353) | 1,174 (714) | 602 (311) | 1,159 (6.6%) |

  So 5% to 10% of files reach a client-dependent branch directly. A first count (`count-gui.ts`) missed the bare `GuiAllowed`
  form and direct `Confirm`, and reported 1% to 3%: it was wrong (build review, R-901).
  - **What is not counted:** code that reaches these through a call chain (as PaymentPractices does, through Base Application's
    `ConfirmManagement`), and a confirm wrapper reached through a variable whose name does not contain "confirm".
  - **What can be over-counted:** a mention that is never reached by a covering test.
  This is files that hold such a call, not mutants whose verdict would differ.
- **Not solved:** v3 still runs the client branch, so its verdicts there can differ from BC's. That needs the upstream option
  (aldevtools #7564); when it ships, make v3 non-GUI by default, pre-committed per mutant, and check PaymentPractices' 7 mutants
  against R-882.

## The option, without a client (coord task R-907, a4f2bad2)

Upstream shipped `--no-client` (edge c3a993e47, #7564; serve: the runTests field `noClient`). **Owner ruling (2026-11-10): an
OPTION, not the default.** `alRunnerV3.noClient: true` passes it. The report records it per run
(`validity.executionContexts[].noClient: true`, with `guiAllowed: false` and `clientType: "al-runner v3 CLI, no client"`, so the
console prints the NON-GUI line), the stored runner build and the resume fingerprint carry it, and `testMethods[].baselineFlagged`
marks a baseline pass al-runner flagged as resting on an unprobed assumption (for any assumption, not only the client).

**Why not the default (measured, direct al-runner, edge-3138effad, `/coord/handoff/R-907/noclient/`).** Without a client, al-runner
refuses calls it has not pinned for a session without a client: CurrentClientType, Page.Run with a record or a Page variable,
Notification.Recall, a request page with a handler. Statistical Accounts' green tests go from 5 to 1 of 18; VAT Group Management's
from 27 to 18 of 82. Revisit the default when upstream pins more of them.

**The evidence for that revisit (pre-committed per mutant, 277a4803; `/coord/handoff/R-907/pp-result.md`).** PaymentPractices'
`PaymentPracticeHeader.Table.al`, 97 mutants, joined with R-882's BC run by mutant identity:
- without a client, the three confirm tests fail at baseline with BC's own texts; with a client they pass;
- R-882's 7 GUI-branch mutants are killed with a client and survive without one, as on BC;
- without a client v3 agrees with BC on every kill (6 of 6) and every survivor (77 of 77). BC's 14 `error`s are 12 `survived` (covered
  by a TestPage test LethAL refuses on BC's fenced path, which v3 runs as a flagged pass) and 2 `no-coverage`;
- with a client v3 had 20 kills BC does not give; without one, none.
