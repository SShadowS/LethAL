**`ROADMAP.md` rows are read field-wise on `|`, and 115 of 166 rows contain INLINE pipes — so a field-wise read silently returns a fraction of the row and looks complete.** Measured 2026-08-06: R69's row is **35,395 characters** across **15** pipe-separated fields, because its own prose carries inline pipes (`GuiAllowed=Yes | ClientType=Web`). An `awk -F'|'`-style read taking field 3 gets **5,633 chars — 15.9% of the row** — and stops at what reads like a natural end. **This produced two successive WRONG versions of a shipped skill.** Subsystem D's `measurement-campaign` skill first asserted a TestPage hazard R69 retracts, then over-corrected to "it is not a hang" — and both were written from 16% of the row, because the 2026-08-01 Phase-2 entry that reproduces the hang *twice, deterministically*, and states the 87 ms refusal "does not generalise past a code-free page", sits near character 27,000. The controller's own verification of the second error used a whole-line `print $0` piped to `grep`, which is why it caught it; a field-wise check would have confirmed the wrong answer. Consequences beyond that one skill: any agent or human checking a claim against this file can read a truncated row, find no contradiction, and report the claim verified — a gate that measures 16% of its evidence and reports success, which is this project's signature bug pointed at the durable record itself. **The `roadmap-auditor` subagent may share the blind spot and should be checked.** Fix: read rows by character range or with a parser that respects the leading `| **R<n>** |` structure rather than splitting on every `|`; where a row must be summarised, state the character offset examined so a partial read is visible as partial. Consider also whether rows this long (R69 is the file's longest) should be split, though note the length is load-bearing — R69's later entries are what retract its earlier ones, and a shorter row would have lost the correction rather than buried it. Filed 2026-08-06 from subsystem D's Task 4.

**CLOSED 2026-08-06 — by deleting the table, not by parsing it better.** Every row is now its own file (`docs/roadmap/R<nnn>.md`, zero-padded, YAML frontmatter `id`/`title`/`status`/`section`/`order` + the row's prose as the body); repo-root `ROADMAP.md` is generated from them by `scripts/roadmap-index.ts` and pinned by `scripts/roadmap-index.test.ts`, which fails if the two disagree. A partial read is no longer possible to *mistake* for a whole one: reading a row is reading a file.

Three things the migration MEASURED that the row had not, all of them evidence the field-wise hazard was worse than filed:

1. **Splitting on `|` was ambiguous in exactly the direction that hides prose.** Taking the LAST ` | ` as the status boundary — the natural implementation — silently mis-split **R33** and **R81**, because their statuses contain inline pipes (`` `rec.No=R2 | xrec.No=R1 | differ=YES` ``). Both mis-splits RECONSTRUCT byte-identically, so a round-trip check alone would have passed them. The split that works is code-span-aware: a `|` inside a backtick span is prose. Under it, 110 rows have exactly 3 cells.
2. **Six rows had a FOURTH cell, and GitHub was dropping it.** R40, R58, R66, R68, R69 and R72 each carried a superseded status followed by the current one; a 3-column table renders 3 cells and discards the rest, so the CURRENT status of six rows — including R69's `done` and R72's `blocked` — was invisible in any rendered view. They are preserved as a `## Superseded status` section in each file.
3. **A stray blank line split the Backends table in two**, so R63 through R108 — 45 rows — were not table rows at all in rendered markdown, only literal text. Generated output cannot acquire that defect.

Evidence: byte-identical round-trip of the pre-split file (311,667 bytes rebuilt from `_template.md` + the 116 row files, exact match, including the one trailing space on R34's line and the stray blank line above); and 238 prose cells (307,414 bytes) each found verbatim in the parsed store. Reading cost: 311,667 bytes → 26,017 for the index, and one row is now a ~2 KB file rather than a 311 KB file plus a parse.
