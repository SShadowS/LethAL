**Found by lethal-preproc, 2026-10-05,** running `bun scripts/verify.ts` on `lethal/lane-preproc` (3c35287b, equal to master's content at 6f20bae9) right after a kraken container restart, while every agent was rebuilding at once (load average about 3.4 on 32 cores).

**What happens.** Two consecutive full runs each failed ONE test, a different one each time, and each passes when run alone:
- `packages/schemata/tests/manifest-stream.test.ts`, "short writes are completed, byte-identically": `this test timed out after 5000ms` (5000.33 ms). The R-403 lane had already measured this file at about 4.2 s on its own against the 5 s limit, so it has almost no headroom.
- `packages/runner/tests/orchestrator.test.ts`, "runSession — I7 second consecutive transport error aborts the session", the test "stub backend erroring on every active-mutant run throws, persists partial results": failed in the first run, `1 pass / 0 fail` alone.

**Why it matters.** A red `verify.ts` that turns green on a re-run teaches people to re-run instead of read. The same pattern was fixed test by test before (R226, R335, R428).

**What would close it.** For each test, find what makes it slow (R335 and R428 each had a specific cause, such as a real spawn or a temp-folder walk) and remove that cause, or give it an explicit timeout with a stated reason. Then check that a full `verify.ts` run under load, for example beside a typecheck of another worktree, passes.

**Closed by R-439 (8ef7ce7e), 2026-10-05.** Both tests get a file-local 30 s timeout with the reason in a comment. There is no suite-wide change and no assertion changed.
- **The short-writes test** writes a 2,500-mutant manifest seven bytes at a time, about 70,000 calls. That is its purpose, so it was not made cheaper. Measured on the kraken container: 3.9 to 6.9 s, alone and beside a full `verify.ts`. Alone it now exceeds the 5 s default too, so it was never just load.
- **The I7 test** takes about 0.16 s inside `orchestrator.test.ts` normally. It was measured at 6.04 s in a loaded `verify.ts`; the log says `timed out after 5000ms`.
- **Red-check** on the short-writes test: a forced 6 s delay passes with the 30 s timeout and fails without it (`timed out after 5000ms`).
- **Leak check:** a timed-out body left no `lethal-manifest-*` or `lethal-orch-i7-*` folder behind, so R428's late-work leak does not apply here.
- **Two `verify.ts` runs**, each beside a concurrent full `verify.ts` in another worktree (load average 3.4 to 4.9 on 32 cores): both 6243 pass / 8 skip / 0 fail.
