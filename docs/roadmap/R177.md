## What breaks, and for whom

`itest:envtool` proves that reaching bcdev through an external environment tool changes no verdict.
It shares `fixtures/sandbox-app` with `itest:bcdev`, so the two must report the same mutants with the
same verdicts, and a divergence is the whole reason the gate exists.

It has not run since **2026-08-26**, when its environment expired and was deleted. Its constants were
moved from PREDICTIONS twice since (R159's `remove-assignment`, then `shift-integer`), and R164 is a
third change it has not seen. So one of four gates publishes figures that read exactly like the
measured ones and are not.

## What is already right, and should not be "fixed"

- The gate **refuses** rather than degrading: `environment ... reports status "Deleted", not
  "Running" ... LethAL will not start an environment it does not own`. It cannot silently pass.
- The committed baseline is deliberately left STALE, so a successful run fails per-mutant and names
  the accumulated mutants instead of agreeing with itself.

## What was closed 2026-08-27

The documented remedy for a per-mutant mismatch is "delete the baseline and re-run to record a new
one". Here that would turn two unreviewed predictions into a committed measurement in one step, and
it is a reflex, not a decision. `refuseSelfRecordWhileUnverified` now blocks it: while
`UNVERIFIED_MOVES` is non-empty and the baseline file is absent, the gate throws and names each move
that must be confirmed against `itest:bcdev` on the same day. Clearing that list is a deliberate edit
in the same commit that records the baseline.

`CLAUDE.md` no longer lists this gate's figures beside the measured ones without saying so.

## What is left, and why it is not mine to do

Restoring it needs a new environment provisioned through the external tool (`continia.exe`), which is
an account-level, possibly billable action outside the repository. Until then:

- **Do not quote 3 / 12 / 4 as measured.** They are `itest:bcdev`'s figures, inferred.
- **Do not delete the baseline to make a run pass.** That is what the new guard exists to stop.
- Confirm on restoration, by name: `remove-assignment` and `shift-integer` at
  `Sandbox Logic.LogAudit`, both predicted `survived`, and that R164's `loop-truncate` adds NOTHING
  here (sandbox-app has no `repeat` loop, measured).

**Alternative if it stays unrestorable:** retire the gate rather than carry it. A gate nobody can run
is worse than no gate, because its frozen numbers still look authoritative. That is a product
decision, not a code one.
