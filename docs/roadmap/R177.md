## What breaks, and for whom

`itest:envtool` proves that reaching bcdev through an external environment tool changes no verdict.
It shares `fixtures/sandbox-app` with `itest:bcdev`, so the two must report the same mutants with the
same verdicts, and a divergence is the whole reason the gate exists.

It has not run since **2026-08-26**, when its environment expired and was deleted. Its constants were
moved from PREDICTIONS twice since (R159's `remove-assignment`, then `shift-integer`), and R164 is a
third change it has not seen. So one of four gates publishes figures that read exactly like the
measured ones and are not.

## What is already right, and should not be "fixed"

- The gate **refuses** rather than degrading: `environment ... reports status "Deleted", not
  "Running" ... LethAL will not start an environment it does not own`. It cannot silently pass.
- The committed baseline is deliberately left STALE, so a successful run fails per-mutant and names
  the accumulated mutants instead of agreeing with itself.

## What was closed 2026-08-27

The documented remedy for a per-mutant mismatch is "delete the baseline and re-run to record a new
one". Here that would turn two unreviewed predictions into a committed measurement in one step, and
it is a reflex, not a decision. `refuseSelfRecordWhileUnverified` now blocks it: while
`UNVERIFIED_MOVES` is non-empty and the baseline file is absent, the gate throws and names each move
that must be confirmed against `itest:bcdev` on the same day. Clearing that list is a deliberate edit
in the same commit that records the baseline.

`CLAUDE.md` no longer lists this gate's figures beside the measured ones without saying so.

## What is left, and why it is not mine to do

Restoring it needs a new environment provisioned through the external tool (`continia.exe`), which is
an account-level, possibly billable action outside the repository. Until then:

- **Do not quote 3 / 12 / 4 as measured.** They are `itest:bcdev`'s figures, inferred.
- **Do not delete the baseline to make a run pass.** That is what the new guard exists to stop.
- Confirm on restoration, by name: `remove-assignment` and `shift-integer` at
  `Sandbox Logic.LogAudit`, both predicted `survived`, and that R164's `loop-truncate` adds NOTHING
  here (sandbox-app has no `repeat` loop, measured).

**Alternative if it stays unrestorable:** retire the gate rather than carry it. A gate nobody can run
is worse than no gate, because its frozen numbers still look authoritative. That is a product
decision, not a code one.

## RESTORED 2026-08-28

A dedicated **DK Business Central 28.0** environment was provisioned
(`e77394cb-fd23-4abb-9f04-dd83f5f64909`, profile `c803cb93-...`, build `28.0.46665.48632`) and the
gate PASSES: 19 mutants, **killed 3 / survived 12 / no-coverage 4**.

**The check that closes this row is not the totals.** The 19-mutant table is IDENTICAL to
`itest:bcdev`'s on the same day, mutant for mutant, diffed mechanically. The whole risk this row
described was that a matching 3/12/4 looks the same whether the indirection preserved the verdicts or
quietly changed WHICH mutants they belong to, so the restoration was PRE-COMMITTED by identity key
before it ran, in `docs/superpowers/specs/2026-08-28-r177-envtool-restoration.md`. The comparison
against the stale 17-mutant baseline returned exactly the two predicted additions
(`shift-integer` and `remove-assignment`, both at `Sandbox Logic.LogAudit`, both `survived`), zero
removed and zero changed.

All three `UNVERIFIED_MOVES` were confirmed by name against `itest:bcdev` run the SAME DAY first,
including the negative one: `loop-truncate` adds nothing here because `sandbox-app` contains no
`repeat` and no `while`, grepped rather than assumed.

### Two hard requirements, found by hitting them, that were written down nowhere

Three environments were created before one worked, and both failures are worth more than the
inconvenience:

1. **BC 27 or newer.** `extensions/lethal-control` is runtime 16.0. BC 26 caps at 15.2 and refuses
   the publish outright: *"The runtime version must be set to '15.2' or earlier."*
2. **DK localization.** `lethal.config.envtool.json` and `lethal.config.local.json` both name the
   company `CRONUS Danmark A/S`. A W1/BASE environment does not have it, and the harness fails with
   `Internal_DataNotFoundFilter` after publishing the control app successfully, which is a confusing
   place to fail.

BC 28 was chosen over the minimum 27 deliberately: `itest:bcdev`'s container is BC 28.0.46665, so the
two gates now share a platform and the confounder the spec flagged (a verdict difference that could
be the platform rather than the indirection) is reduced to a build revision.

### A fresh environment needs the fixture bootstrapped once

LethAL publishes the instrumented TARGET on every run but treats the TEST app as the user's own
workflow, so on a brand-new environment the tests app cannot compile: `AL0185: Codeunit 'Sandbox
Logic' is missing`. Publish `fixtures/sandbox-app/LethAL_LethAL Sandbox App_1.0.0.0.app` once by
hand, then the tests app, then run the gate. This is the same trap `CLAUDE.md` records for containers,
reached from a different direction.

### What the guard did, and it was right

`refuseSelfRecordWhileUnverified` was added 2026-08-27 to stop a missing baseline being silently
re-recorded while moves were unconfirmed. It did not fire on this run, because the STALE baseline was
deliberately left in place, so the gate failed per-mutant and NAMED the two accumulated mutants
instead of agreeing with itself. Both mechanisms worked as designed and neither was exercised in
anger before today.

### Both requirements were latent in the repo, and neither was stated as a requirement

`packages/engine/vendor/README.md` records the deleted environment as **DK 28.1**, so "DK" and
"BC 28" were both sitting in the repository the whole time — as an incidental detail of a
grammar-bump note, not as a constraint on provisioning a replacement. That is why they had to be
rediscovered by two failed environments. They are now stated as requirements in `CLAUDE.md` and
above, which is the difference between a fact being present and being findable.
