**`--stop-hung-sessions` is only PARTIAL on a hosted environment, and a real DO codeunit still cannot complete a clean run.** R53 built the flag for the non-terminating-mutant class and its own caveat said the stop was unmeasured on the hosted topology. **Measured 2026-08-04** on Continia environment `f5f11bf2` against DO codeunit 6175297 (148 deployed mutants, pinned source `5f2a71d3`): with the flag ON, one mutant scored `timeout-killed` — the stop worked — while another stranded anyway and quarantined the tier. Three fresh attempts, three strands (run 1 at M0092, run 2 twice). `docs/measurements` says of 2026-07-28 that *"a clean, COMPLETE fenced DO run does not exist"*; that is STILL true, with the flag available. What has changed is that `--resume` can carry a run to completion — run 1 resumed correctly, carried 63 verdicts and skipped 2 stranded identities unscored (the safe direction), reaching 148. **ROOT CAUSE FOUND 2026-08-04: the strands were SLOW mutants, not hung ones.** Both stranding mutants are `void-method-call` deleting a `SetCurrentKey` — which does not hang, it makes the following filtered query pick a worse plan and scan. They exceeded R47's hardcoded 30 s floor, and on the fenced path a budget overrun is indistinguishable from a genuine strand, so the tier quarantined instead of scoring them. `--mutant-timeout-ms 180000` eliminated BOTH strands entirely (errors 2 -> 0, single-pass completion, twice) while M0013 — `negate-conditional` on `until ... Next() = 0`, the genuinely non-terminating one — still scored `timeout-killed` at 30172 ms. That contrast within one run is the control proving the distinction. So `--stop-hung-sessions` is NOT deficient for this class; the 30 s FLOOR is, and R47 already records that the floor has no config key reaching it. **Two clean verdict-identical runs now exist (148 mutants, 25/107/15/1/0), so `docs/measurements`'s "a clean, COMPLETE fenced DO run does not exist" is no longer true.** **Second defect, still unexplained and now sharper:** run 2's `--resume last` printed NO `RESUMED:` banner and produced 86 fresh verdicts instead of continuing the 113 already recorded, where run 1's engaged and said so. **The store DISPROVES the first hypothesis** — queried directly, run 3 was `finished_at` NULL with 113 verdicts recorded, i.e. a valid unfinished target, when `--resume` ran; it created run 4 fresh anyway and re-measured from scratch. A resume that cannot use its target must THROW, not silently start over (this project's own fail-loudly rule). Cause undiagnosed; reproduction precise. **Measured cost this imposes:** ~10 min recovery per strand (env stop/start ~3.5 min + `force-reset-lease` + `clear-quarantine` + the resumed run), which no plan budgets. Evidence: `docs/campaign/2026-08-03-do/rung1.result.md`, `rung1.baseline.json`.

**NARROWED 2026-08-07. Read this before re-investigating — three hypotheses are dead.**

The first half of this row is SUPERSEDED. It asked whether `--stop-hung-sessions` is deficient on a
hosted topology; the row's own root-cause paragraph already answered no — the 30 s floor was the
defect — and **R91 closed that** by raising `MIN_MUTANT_BUDGET_MS` to 180_000. Nothing further is
owed here on the stop flag.

The second half — `--resume last` producing a fresh run with **no `RESUMED:` banner and no error** —
is still unexplained. What has changed is that the obvious explanations are gone, each checked
against the code rather than argued:

1. **The CLI does not drop the flag.** `parseCliConfig(["run", "--resume", "last", ...])` yields
   `resume: "last"`. The stray word was ignored, not fatal.
2. **`resolveResume` cannot fail quietly.** It THROWS when `findResumableRun` returns null, naming
   the project, backend and scope it searched. There is no path where it returns `undefined` for a
   `--resume` that was actually requested.
3. **`resumedFrom` was never derived from carried mutants.** Checked against the pre-event-stream
   code (`987415c^`), whose own comment reads *"a `--resume` that turned out to carry nothing still
   describes a run assembled differently"*. So a resume that matched a target and carried ZERO
   verdicts would still have set `resumedFrom` and printed the banner. The later `resume-resolved`
   event did not fix this; it was already keyed on the request.

So the remaining live possibilities are that `cfg.resume` never reached `resolveResume` (a wrapper
script or config path that did not forward the flag), or something in the invocation nobody has
reconstructed. **Reproduction needs the actual argv, not more code reading.**

**A separate, live defect was found while ruling those out, and is fixed (`3239afd`):** `--resume`
is a boolean flag, so `lethal run --resume 3` — an operator asking for run 3 — parsed to
`resume: "last"` and would have carried verdicts from whichever run was most recent. Silently. That
is a plausible cause of the field report if the real invocation named a run id, and it is a serious
defect on its own terms whether or not it explains this row. Stray positionals are now refused, with
the message naming `--resume-run <id>` when the argument looks like one.
