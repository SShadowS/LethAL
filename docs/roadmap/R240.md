**Found by lethal-code while fixing R232 in C02-04 part A (2026-09-26); not measured live.**
After C02-04 part A, `LeaseSession.publish` can return normally with the session LATCHED: a
refused `EndPublish` notes lease loss without throwing, and an unreconciled lost `EndPublish` ack
now latches through `leaveStrandedPublish` (`packages/runner/src/orchestrator.ts`). For the
`afterLeaseAcquired` hook, `runSession` calls `safety.assertSafe` right after, so nothing else
runs. The TARGET publish in `deployOnce` has no such check at the same point.

**Consequence:** a target publish that returned latched is still recorded through
`recordPublishOutcome` as `accepted` (R90's publish-size history, which the ceiling reads), before
the first guarded call throws `SessionUnsafeError`. That writes a success into a history whose job
is to say what publishes. And on `--resume`, one `fetchPublishedAppPackage` read
(`testAppHashFor`, R192) can run against the server before the guard stops the session.

Direction is mostly safe (the session still stops before any verdict), but the history row is
wrong and the extra server read happens on a latched session.

**Fix shape:** `safety.assertSafe` directly after the target publish returns in `deployOnce`'s
caller, before `recordPublishOutcome`; a test with a refused `EndPublish` on the target publish
asserting no `accepted` row and no package read.

**Closed (8599054b).** `deployOnce` now calls `safety.assertSafe` once `LeaseSession.publish`
returns, as `runLeaseHook` does for a hook publish. That covers both target-publish call sites
(the first attempt and the version-conflict retry) and a THIRD latched-return path the item did
not name: the heartbeat answering `renewed:false` while the publish is in flight. The caller sees
`SessionUnsafeError` as the deploy error; `classifyDeployFailure` does not classify it, so R90's
history gets NO row for a latched publish. Not `failed`: the publish may well have landed, and a
`failed` row would lower the ceiling on a guard count that published. Not `indeterminate` either:
the fence has already recorded what it knows (a lease loss, or a recycle), and the history's job
is publish SIZE, which a lost lease says nothing about. The artifact row (`recordArtifact`) is
skipped too, the conservative direction for `loadInstalledArtifact`.

The `--resume` package read the item describes did NOT reproduce on this HEAD: `scoreBatch` calls
`activateOnce` (which asserts the latch) before `testAppHashFor`, and the new tests saw no backend
call after a latched publish even with the fix reverted. Only the `accepted` row was wrong. Tests
in `orchestrator.test.ts` (`R240`), each latched path red-checked.
