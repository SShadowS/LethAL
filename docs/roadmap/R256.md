id: "R256"
title: "A run recorded WITH preprocessor symbols before C02-06 can still be resumed by a run with NO symbols, so an old verdict or baseline can carry across a `#if` change"
section: "correctness-risks"
status: "open"
order: 953
---

**What.** C02-06 part a added the sorted `preprocessorSymbols` to `sessionFingerprint`, but only when the list is
non-empty, so every no-symbol digest stays byte-identical and existing stores keep resuming. That closes the case
"new run with symbols resumes an old run". It does not close the reverse: a run recorded before C02-06 WITH symbols
has the old, symbol-blind digest, and a new run with NO symbols computes the same digest. `findResumableRun` and
`resolveResume` both match on the digest alone and never read the prior run's symbols, and R192's baseline key hashes
AL bytes, not compile symbols. So removing the symbols from a config and resuming reuses verdicts and a baseline
measured under a different `#if` branch, and the run then records a source hash for the NEW symbols, which
`lethal verify` would trust.

**Found by** gpt-6-sol's round-2 review of C02-06 part a (`H:/lethal-coord/reviews/C02-06-002/review-r2.md`), accepted
by the orchestrator as narrower than before that task, when any symbol change resumed.

**How rare.** It needs a store with a symbol-bearing run recorded before C02-06, then a config change that removes
every symbol, then `--resume`. Before C02-06 the CLI passed no symbols into the session at all (R101(c)), so such runs
exist only where symbols were set in the config.

**What would close it.** A provenance check rather than the digest alone: record the symbols on the run row (or a
marker that the digest includes them) and refuse to resume a legacy row whose symbols cannot be established, with a
test that inserts a legacy symbol-bearing row and attempts a no-symbol resume.
