**What happened.** [[R196]] plan B1 Task 6 added `hangCapableCount` to `mutation-set-generated`
(`packages/runner/src/events.ts`), required rather than optional, for the same reason
`declarativeSiteFiles` and `untargetedTriggerCount` are required: an absent count and a measured
zero must not look alike. `docs/campaign/2026-08-16-gift-card/rehearsal.events.ndjson` is a real,
committed campaign artifact captured before this field existed, and its own `mutation-set-generated`
line (seq 5) is missing it.

**The precedent, and why this is not a new problem.** [[R157]] already ruled on exactly this shape
for the report schema: an added REQUIRED field is not backward compatible for a VALIDATOR even
when it is for a reader, because `schemaVersion`/`streamSchemaVersion` stay the same across the
addition (the field is additive by the versioning rule, but not additive for a strict validator).
R157's own fixture, `docs/campaign/2026-08-08-r85-swap-population/rung2.report.json`, was
deliberately left unpatched and pinned as a known non-validating document
(`packages/runner/tests/schemas.test.ts`, "OLDER reports are also v2 and do NOT validate"). This row
is that same ruling applied to the STREAM schema instead of the report schema, for the same field.

**Why the file was not hand-patched.** Backfilling `"hangCapableCount":0` into this line would write
a MEASUREMENT into a run from 2026-08-16 whose build could not measure it, which is exactly the
ambiguity the field is required to prevent, just committed into the one artifact where it matters
most. Making the field optional instead would reopen the same ambiguity from the other direction.
Neither is the honest fix.

**How it is pinned today.** `packages/runner/tests/schemas.test.ts` carries two tests for this: the
blanket "every line of the committed event stream validates" test now excepts this one line by
`seq`, and a dedicated test asserts that line's `mutation-set-generated` event fails validation on
exactly `$.hangCapableCount`, required but absent, validated against its own branch of the
`stream-v1.schema.json` union (the top-level `anyOf` collapses a failed match to one synthetic
violation at `$` and would not name the field, which is why the dedicated test resolves the specific
branch first rather than validating against the union root directly).

**To close.** A live re-run of the gift-card rehearsal campaign, re-frozen with `hangCapableCount`
actually measured by a build that has the field. This file has been re-frozen four times before,
always by a real live run and never by hand; this is a fifth. Out of [[R196]] plan B1's scope (no
live BC container available to the task that found this), and needs `bun run mutate`-style live
gate access, not a code change.

**Expected value for whoever does the re-freeze, read off the committed report rather than
measured:** `docs/campaign/2026-08-16-gift-card/rehearsal.report.json` carries 12
`lethal.remove-assignment` and 2 `lethal.flip-boolean-literal` mutants (the two operators among the
four `hangCapableForMutatedNode` callers that this run actually deployed; `lethal.shift-integer` and
`lethal.swap-additive` contributed none), and every one of those 14 mutants' `originalText` is a
plain record-field assignment (`GiftCard."No." := CardNo`, `GiftCardEntry.Amount := Amount`, and
similar), not a loop counter. So `hangCapableCount: 0` is almost certainly the correct re-measured
value, not merely the value this row happens to pin as a failure today. Confirmed directly against
the committed report's 60 mutants (`node` one-liner over `rehearsal.report.json`), not asserted on
faith.
