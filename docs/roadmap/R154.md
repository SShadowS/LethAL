Until 2026-08-16 the repository had no `.github/` directory at all: nothing ran `bun run typecheck`,
`bun test` or the roadmap-index check on a push, on a repository that is public and about to be
shown to strangers.

Two workflows now exist:

- `.github/workflows/ci.yml` — push and pull request. Typecheck, remove `packages/*/dist`, unit
  tests, in that order (the order is the one CLAUDE.md gives, and the clean sits between the two
  because `tsc --build` regenerates the stale compiled `*.test.js` that produce ~21 phantom
  failures).
- `.github/workflows/release.yml` — on a `v*` tag. Refuses a tag that disagrees with the root
  `package.json` version, runs the same gate, builds all five targets, smoke-tests the Windows
  binary with `--version`, and opens a DRAFT release with the binaries attached.

They were written from the local build loop rather than derived from a green run, so every claim in
them started untested. Half of that is now measured and half is not.

**`ci.yml` — VERIFIED 2026-08-16.** Run
[31961823874](https://github.com/SShadowS/LethAL/actions/runs/31961823874) on branch
`directions-emea-readiness`: one job, 1m27s, typecheck clean and **2430 pass / 0 fail / 1 skip
across 145 files in 24.8s** — the same figures as the local suite, read out of the run's own log
rather than off the badge, so the runner is not quietly skipping files. The `oven-sh/setup-bun@v2`
pin at Bun 1.3.14 works and the suite is green on a hosted `windows-latest`.

**The first push found a real defect in the file, immediately.** The trigger was
`push: branches: [master]` plus `pull_request`, so pushing the branch ran NOTHING: `gh run list`
and `gh workflow list` both came back empty. A gate that first fires after a merge reports a
problem already shipped, and one that waits for a pull request gives a feature branch no signal at
all. Fixed in `af0b056` — `on: push:` with no branch filter. That is the whole argument for filing
this row instead of assuming a written workflow is a working one.

**`release.yml` — VERIFIED 2026-08-17**, run
[32063692530](https://github.com/SShadowS/LethAL/actions/runs/32063692530) on tag `v0.1.0-alpha.2`:
one job, **1m44s**, all five targets cross-compiled and attached to a draft release (windows-x64
105 MiB, linux-x64 101, linux-arm64 100, darwin-x64 77, darwin-arm64 71), the `--version` smoke test
printing `0.1.0-alpha.2` off the built exe, and the release body taken from the CHANGELOG section
rather than hand-written. The Azure signing steps skipped cleanly, as designed, because the repo
variables that switch them on are not set yet.

What had been guesses until that run: whether the version guard's `bun --print` line behaves under Actions' bash,
whether `bun run build:binaries` can cross-compile five targets inside a runner's disk and time
budget (five binaries at roughly 70 to 105 MiB each), whether the `build/lethal-*` glob matches,
and whether `softprops/action-gh-release@v2` has the permissions it needs from the `contents: write`
grant. All four answered yes on the first tag.

One non-blocking annotation on every run: `actions/checkout@v4` targets Node 20, which GitHub has
deprecated and force-runs on Node 24. Bumping to `@v5` is a one-line change and changes nothing
today.

Three known limits, deliberate rather than overlooked:

- **windows-latest only.** This is a Windows-first tool and the unit suite has never been run on
  Linux. Adding `ubuntu-latest` is worth doing and will probably surface path assumptions; it is
  not a blocker for the binaries, which cross-compile from one machine.
- **No `biome check .`.** Repo-wide it fails on pre-existing organizeImports and format debt in
  `engine`/`builtin-tier1`, so adding it would fail every build and teach everyone to ignore the
  job. Cleaning that debt is the prerequisite.
- **`lethal-control.app` is not attached by CI.** Building it needs `alc` from the AL VS Code
  extension, which no hosted runner has, and `*.app` is gitignored so no committed copy exists to
  attach. This is why the release is a draft: a human attaches the control app and names its
  version before publishing.

**What is still unverified is the SIGNING path**, because it has never been switched on: the three
Azure repo variables are unset, so the guarded steps skipped. The first signed release is the test
of `azure/login`, the federated credential subject, and the `Get-AuthenticodeSignature` check. See
`.claude/skills/release/SKILL.md`.

half; `af0b056` for the trigger defect the first push exposed; and `docs/releasing.md`
