Found by coord PR-222 (PERF-15, lethal-bugs, 2026-11-19), for the alrunner tentacle. Evidence: `/coord/handoff/PR-222/result.md`.

**What LethAL does.** After a `--test-timeout` cut, the v3 backend closes the serve daemon (`serve-daemon-closed`, reason
timeout) and the next request warms a fresh one. DO's y3 did this 23 times: 1,107.6 s of after-timeout warm-up (y2: 23, about
1,305 s).

**What PERF-15 measured** (alrunner's build 49f8a3e05, NOT `current`). One kept DO daemon took y2's 8 timeout mutants (18
timed-out rows, every one cut), each followed by a no-mutant control. All 11 `ALRUNNER_DAEMON_CLEAN_CHECK=next` lines read 0
differences in answers, engines, session, language, clock, process and compile. The only difference, store 1 per check, is the
fresh twin's own first-login record (`login [LoginRecord ...]` against the kept daemon's `login []`): a check artifact. It reads
"differ" after kept refusals too. Upstream is asked to leave that record out of the compare (q-20261119T154821-fa2d7d67).

**Before any keep (the standing keep standard):**
1. a census of every cut kind DO meets (y2 and y3, the full site key);
2. a direct DO check on `current`, kept daemon vs fresh, in the run's own isolation mode (method), with y2's sidecar and flags,
   every cut exercised, and the planted-difference self-test;
3. whether `current` behaves after a cut as 49f8a3e05 does (the cut path may differ);
4. a spec-light with the saving and what could make a verdict differ, for the orchestrator's ruling.

**Done and parked (coord PR-228, 2026-11-20).** The measurement is in the spec
`docs/superpowers/specs/2026-11-19-pr228-keep-daemon-after-timeout-cut.md`: the census, 16/16 and 34/34 kept-vs-fresh, and the
self-test. `alRunnerV3.keepAfterTimeout` (default off) was built on branch `lethal/pr228` and kept off master by ruling (a).

**What a build needs to know.** LethAL itself kills the daemon at the first timeout row: `AlRunnerServer.runEntries` with
`stopAtTimeout`, set by the v3 backend's in-flight send. al-runner would go on running the request. So keeping the process
means draining the cut request's tail, and the review of that design found:
1. **HIGH:** a second cut in the re-sent request skips PR-56's drift check (partial answers skip it) and arms the daemon again,
   so rows are counted on a daemon nothing checked.
2. **HIGH:** the likeliest next request skips the drift check and uses up the arming: the same mutant's next test as an `alone`
   call (PR-41's cut elsewhere), and per-test calls in method mode (the recheck), where the covering test is at index 0.
3. **HIGH:** the drain runs inside the NEXT request's deadline. A tail holding further hangs makes an unrelated live mutant
   `deadline-exceeded` (a wrong verdict), and a kill pair a transport failure. With the option off, it gets a real verdict.
4. **MED:** the tail runs in full and is then re-sent, so every entry after the cut runs twice and each remaining hang costs the
   limit. The measured saving came from one-entry requests and never saw this.
5. **MED:** a lazy warm-up on a kept daemon drains the tail, and a drift there stops the session (`warmup-disagrees`) instead of
   closing the daemon.

**The clean shape (asked of alrunner):** a runTests field that ENDS the request at a timeout row and keeps the process. LethAL then
does not kill, does not drain, and runs the drift check on every kind of next request, partial answers included (fixes 1 and 2).
