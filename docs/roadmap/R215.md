**Read the correction first.** This row was filed claiming that `negate-conditional` emits an
invalid mutant and that the run dies during instrumentation. **That claim was wrong**, and the
error was in how it was tested rather than in the reasoning about the grammar. It is kept, with the
mistake intact, because the mistake is the more useful half.

## What is true

AL's interface pattern writes, inside an enum value:

```al
value(1; Sequence)
{
    Implementation = "No. Series - Single" = "No. Series - Sequence Impl.";
}
```

`tree-sitter-al` v4.0.1 shapes the right-hand side as a `comparison_expression`. The AL compiler's
own parser does not: it has no comparison there at all. Found by the issue #6 cross-check on
Microsoft's own Business Central source (`U:/Git/BC.History`, 16,898 `.al` files), where the
construct occurs **535 times across 137 files**.

`lethal.negate-conditional.targets()` does return true for that node, verified by running the real
operator set against the real file. And the mutation it would produce is not merely meaningless, it
is a syntax error: `alc` rejects `Implementation = "IFace" <> "Impl"` with
`AL0104: Syntax error, '=' expected`.

## What is NOT true, and how the error was made

The pipeline never reaches that point. `orchestrator.ts` filters every candidate through
`isMutableSite` before instrumentation, and its comment names this exact shape: a declarative
page/report property that parses as a comparison, which nothing can wrap, and which once aborted a
whole session at `buildComponents`. The site is dropped, TALLIED as `nonExecutableSites`, and
surfaced in the report as [[R144]]'s `declarativeSites`.

Running the real CLI over a minimal project holding one such enum:

```text
[lethal] dropped 1 matched site(s) that are not inside executable AL (declarative page/report
properties, which parse as the same expression shapes statements do). They cannot be wrapped and
are not mutants: src\Kind.Enum.al (enum_declaration, 1 site(s)).
dry run: 1 file(s), 2 mutant site(s), 2 deployed mutant(s), 1 batch(es)
```

The run completes. Nothing invalid ships. The drop is announced rather than silent.

**The mistake:** the "EMIT FAILED: resolveSite: no enclosing statement" result that produced the
original severity claim came from calling `writeInstrumentedProject` directly with raw operator
output, which is not the pipeline. It bypassed the one guard that exists for precisely this case.
A probe that skips a filter and then reports the filter's absence is measuring its own shortcut.
Caught by an adversarial review that read `orchestrator.ts` rather than the probe.

## What is worth keeping

1. **The grammar over-claim is real and is upstream.** `SShadowS/tree-sitter-al` shapes a
   declarative property as a comparison, on a construct that appears 535 times in Microsoft's own
   source. LethAL is defended against it; a grammar consumer that is not would inherit it. Worth
   reporting to that repository, which is where R215's remaining action lives.
2. **The defence sits in the orchestrator, not the operator, and the two operators differ.**
   `flip-boolean-literal` guards itself with `inExecutableBody`, an allow-list, after hitting this
   exact failure on `Clustered = true` ([[R135]], [[R144]]). `negate-conditional` carries no such
   guard and relies on the central filter. Both work today. Whether a central filter or a
   per-operator guard is the right home is a real design question, and the honest answer is that
   the central one is doing its job, so this is not urgent.
3. **The declarative-drop message is good, and this is evidence for it.** It names the file, the
   object kind and the count, which is why the correction here took one CLI run.

## What this cost, stated plainly

An hour, a wrong severity in a committed roadmap row, and a commit message asserting the run dies.
The reasoning chain was sound at every step except the one where it stopped consulting the real
pipeline, and no amount of care about the grammar comparison would have caught that. Only running
what a user runs did.
