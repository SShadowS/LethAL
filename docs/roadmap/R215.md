id: "R215"
title: "`negate-conditional` claims an enum's `Implementation` mapping, emitting `Implementation = \"IFace\" <> \"Impl\"`, which is not AL"
section: "correctness-risks"
status: "open, filed 2026-09-08, measured, BLOCKS any project using the interface pattern"
order: 927
---

**Found by the issue #6 grammar cross-check on its first real corpus, Microsoft's own Business
Central source.** That is the audit doing the job it was built for, in the direction that matters
most: over-claiming, where LethAL sees a mutation site the compiler does not agree is one.

**What happens.** AL's interface pattern maps an enum value to an implementation:

```al
value(1; Sequence)
{
    Caption = 'Sequence';
    Implementation = "No. Series - Single" = "No. Series - Sequence Impl.";
}
```

`tree-sitter-al` v4.0.1 shapes the right-hand side as a `comparison_expression`. The AL compiler's
own parser does not, and R135's declarative-surface refusal does not cover this shape. So
`negate-conditional` claims it, verified by running the real operator set against the real file:

```text
lethal.negate-conditional  [1213-1266]
  "No. Series - Single" =  "No. Series - Sequence Impl."
  ->  "No. Series - Single" <> "No. Series - Sequence Impl."
```

`Implementation = "IFace" <> "Impl"` is not valid AL. This is a declarative mapping, not a
comparison, and `<>` there means nothing.

**Prevalence, measured on `U:/Git/BC.History` (16,898 `.al` files of Microsoft BC source):** 535
occurrences across 137 files. The interface pattern is standard in modern BC, so any project using
it is exposed, not just Microsoft's.

**MEASURED 2026-09-08, and it is worse than either outcome first considered.** The run does not
reach `alc` at all.

Compiling the mutated property by hand confirms it is not merely meaningless, it is a SYNTAX error:

```text
Kind.Enum.al(8,40): error AL0104: Syntax error, '=' expected
Kind.Enum.al(8,40): error AL0107: Syntax error, identifier expected.
```

But LethAL never splices a mutant in directly, it emits every mutation behind a runtime guard, and
a declarative property has no statement to wrap a guard around. Running the real emit path over a
minimal project holding one such enum:

```text
2 file(s), 3 spec(s) generated
EMIT FAILED: resolveSite: no enclosing statement for node at 153..181
```

**So the whole instrumented artifact fails to build, and the run aborts before anything is
measured.** Not a bad mutant among good ones: a dead run, the same shape GitHub issue #8 produced
from a different cause. Any project containing an enum with an `Implementation` mapping cannot be
mutation tested at all.

This is the SAME failure `flip-boolean-literal` already hit and fixed. Its own doc comment records
it verbatim: the first draft named declarative parents as a deny-list, and the instrumented artifact
then failed to build with `resolveSite: no enclosing statement for node at 271..275`, which was
`Clustered = true` on a table key. That is why it guards with `inExecutableBody`, an ALLOW-list.
`negate-conditional` never got the same treatment, and this row is what that omission costs.

**Why the existing refusal does not catch it.** `flip-boolean-literal` guards with
`inExecutableBody`, an ALLOW-list of `procedure` and `trigger_declaration` ancestors, precisely
because a deny-list of declarative parents is only ever as complete as the last person's memory
(R135, R144). `negate-conditional` has no equivalent guard. The same argument that produced the
allow-list there applies here, and this row is the evidence that the lesson did not travel.

**Relationship to the grammar.** Two independent fixes are possible and they are not alternatives:
the grammar could stop shaping a declarative property as a comparison, and `negate-conditional`
could refuse a site outside an executable body. The second is LethAL's to make and does not depend
on anyone else's release; the first is upstream in `SShadowS/tree-sitter-al`. A tool that only
mutates what the compiler agrees is code should arguably do both.
