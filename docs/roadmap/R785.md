**Filed from [[R781]]'s measurement (2026-10-25, `/coord/handoff/R-781/`).** With `--workers N`, each extra serve lane
compiles and warms the project before it runs a mutant. On a 140-mutant CDO slice the four lanes' warm-ups summed to
about 62 s against 7 s for one, while the live work (39 covered mutants) was about 23 s, so N = 4 was slower than
N = 1 (75 s vs 65 s) with identical results. Large projects (CDO, DC: thousands of procedure scopes) are where lanes
pay.

**The idea (unmeasured).** Lanes already start lazily, but every lane that receives a scope warms up. Start lane k
only when the live work still queued (covered mutants not yet handed out, times a per-mutant cost measured on lane 0)
is longer than about one warm-up; otherwise leave the queue to the lanes already warm. Deterministic results are not
affected: the scope-affinity queue and the manifest-order commit are unchanged; only how many lanes start changes.

**Built (rule only; live timings still to measure).** `--workers N` is an upper bound. Lane 0 always runs. After
each finished unit (never at queue start, when no cost is known) the queue starts ONE more lane, up to N and up to
`affordableLanes`, if `queued live mutants x lane 0's wall ms per live mutant > lane 0's own warm-up`. The memory hold
(`laneMayStart`) is unchanged; if it says no, the run stays at the lanes it has. One notice,
`al-runner-v3-lanes-started`, says "K of N lanes started: why, after lane 0's warm-up of X s".
- *Why this rule.* A new lane can take at most all the queued work R. It repays its warm-up W only if R > W; at
  R <= W it cannot finish ahead of the lanes already warm. It is the smallest rule with no tuning constant: it uses
  only two numbers the run measures (the lane-0 warm-up timer, and lane 0's wall per live mutant). It is cautious on
  purpose: R is single-lane time, so a start that would repay only at R slightly over W is the break-even case.
- *Why lane 0 only measures cost.* Its daemon was warmed in the shared prefetch, so its units carry no warm-up; a
  later lane's first unit would, and would inflate the estimate. A project whose first unit is huge starts no extra
  lane until that unit ends (conservative).
- *Live work.* A mutant counts only if it has covering tests AND the shared prefetch holds no answer for it
  (`needsLiveCall`: not in `prefetched`). Prefetched and uncovered mutants cost about 0 here: the prefetch already
  paid for them on lane 0, so on a project the prefetch answers fully, extra lanes rarely start. That is correct, not a
  bug: there is nothing left to spread. Kill-pair reproductions stay on the lane that serves the kill and are not counted.
- *Results do not depend on N.* Unit order, scope affinity and the manifest-order commit are untouched; only WHEN a
  lane starts changes. An owner with no `laneWarmupMs`/`needsLiveCall` (a fake) still starts every lane.
- Tests: `packages/runner/tests/parallel-queue.test.ts`, "R785" block (fake clock, call counters).

**To close.** Measure lane 0's warm-up and per-mutant cost on D1, the 140-mutant slice and a whole-app run; add the
start rule behind `--workers`; show the small slice no slower than N = 1 and the whole app still spreading, with the
per-mutant table equal to N = 1.
