**BC's "cannot run codeunit in a write transaction" is not distinguished from a genuine kill.** Spec §5 requires it for `RemoveCommit`: deleting a `Commit()` before a `Codeunit.Run(...)` makes the platform refuse the call, which kills the mutant for a reason that says nothing about assertion quality and inflates the score with platform noise. Deliberately NOT built with R33: nothing in any fixture has ever produced that message, so the detector would match an ASSUMED string — the R31 shape, where a reworded literal silently stops a diagnosis firing — resting on an unmeasured platform claim. An adversarial review named a second hole it must survive: `if not Codeunit.Run(...) then Error(PostFailedErr, GetLastErrorText())` re-wraps the artifact in the caller's own message, so a text match sees nothing and the reader counts a platform artifact as test quality. Order of work: produce the artifact once live from `sandbox-probes`, pin its exact text per runner, THEN write the detector — and word it as best-effort, never as a classification. The verdict must stay `killed` (a diagnosis must not move a verdict; design §6.7's timeout precedent).

## Superseded status

**MEASURED 2026-08-02, detector NOT yet built — and the measurement changed what it must be.** `fixtures/sandbox-probes/src/WriteTxnProbe.Codeunit.al` produced the artifact live on Cronus281, three tests (A/B controls, because a single test reported an AL-callstack line that maps ambiguously onto the source). Results, IDENTICAL on the hub and on the fenced path — the per-runner pin this row asked for: write alone is fine; `Codeunit.Run` alone is fine; write-then-`Codeunit.Run` ABORTS with BC's generic **"An error occurred and the transaction is stopped. Contact your administrator or partner for further assistance."** Full method and reasoning: `docs/measurements/README.md` §"R72". **Two of the three findings change the design.** (a) The refusal is REAL — that half of the premise holds. (b) It is **NOT catchable**: `Ran := Codeunit.Run(...)` does not return false, the error escapes and the test dies, so the adversarial re-wrap hole this row was written to survive (`if not Codeunit.Run(...) then Error(PostFailedErr, GetLastErrorText())`) **cannot occur for this artifact** — the caller never regains control. (c) The text is BC's GENERIC transaction message, naming neither `Codeunit.Run` nor the rule, so a detector keyed on the string ALONE would fire on any platform-stopped transaction and mislabel genuine kills as platform noise — the unsafe direction. The detector must therefore condition on the OPERATOR (`lethal.remove-commit` at a site preceding a `Codeunit.Run`) with the text as corroboration, stay best-effort in wording, and leave the verdict `killed`. **Blocked on R73**, deliberately: no fixture has ever generated a `remove-commit` mutant, so the detector cannot be proven to fire against anything real, and a detector proven only against a constructed string is the R31 shape this row exists to avoid.

## The blocking measurement, done 2026-08-08

`scripts/r72-probe/` — 2 x 2 x 2 over prior `Commit()`, call frame, and `Codeunit.Run` form, on
Cronus281 (BC 28.0.46665.49944, `LethAL Control` 1.0.0.16), fenced path, plus two controls. Full
table in that directory's README and in `docs/measurements/README.md` §R72.

| | `Ran := Codeunit.Run(X)` | `Codeunit.Run(X);` |
| --- | --- | --- |
| write opened in the `[Test]` body | **ABORT** | survives |
| write opened in a callee called from the test | **ABORT** | survives |

Both rows hold with and without a prior `Commit()`. Controls: the value form with no write open
succeeds and returns `Yes`; the write alone succeeds.

**This row named the FRAME and the frame is not the variable.** Nor is call depth, nor the test
runner's own transaction, nor `TableNo` — all four were on this row's candidate list and the first
three are eliminated outright by A1-vs-A3 and A5-vs-A7. The one difference nobody had written down
is that every aborting measurement so far consumed the Boolean return value, and
`Data Commit Ops.CommitThenRun` calls `Codeunit.Run` as a bare statement. That is why the live gate
saw it survive: the fixture cannot produce the artifact, and the prediction, not the gate, was wrong.

There is a mechanism behind it rather than a coincidence: the Boolean form promises to roll the
callee back on failure, which is a promise the platform will not make inside a transaction it did
not open. Worth stating because it is the kind of rule that could change between BC versions, and a
detector resting on it should be re-measured when one does.

**What the detector must now be**, which is sharper than what this row settled for when the trigger
was unknown: fire when a `lethal.remove-commit` site is followed by a `Codeunit.Run` **whose return
value is consumed**. That is a syntactic property of the call site, visible before anything runs,
so the diagnosis no longer has to lean on BC's generic transaction text as corroboration. It still
must stay best-effort in wording and must leave the verdict `killed` — a diagnosis must never move a
verdict (design §6.7's timeout precedent), which is the discipline R121 also obeys.

**What is still missing, and it is the same gap in a new place.** No fixture generates a
`remove-commit` mutant at a value-form call, so the detector would again be proven only against a
constructed string. The remaining work is therefore two steps in order, not one:

1. Give `fixtures/sandbox-data` a `CommitThenRunValueForm` arm (`Ran := Codeunit.Run(...)`) and a
   test that covers it, so deleting the `Commit()` produces the artifact live. This GROWS the tables
   gate's frozen figures and needs the per-mutant re-freeze that goes with that.
2. Then build the diagnosis against it, and red-check that removing it makes the gate stop naming
   the artifact.

Deliberately not done in the same session as the measurement: step 1 changes a frozen gate, and the
measurement is worth landing on its own.

# CLOSED 2026-08-09 — what shipped, and what this row got wrong

## What shipped

1. **The fixture site.** `Data Commit Ops.CommitThenRunValueForm` — the same procedure shape as
   `CommitThenRun`, the same callee, with `Ran := Codeunit.Run(...)` instead of a bare statement, plus
   `Data Tests.CommitBeforeValueFormCodeunitRunSucceeds` covering it. Six raw specs, five deployed.
2. **The detector.** `detectWriteTxnCodeunitRun` (builtin-tier2) tags a `lethal.remove-commit` spec
   with `platformKillMechanism: "write-txn-codeunit-run"` when a `Codeunit.Run` whose return value is
   CONSUMED appears later in the same procedure or trigger body. The tag rides the manifest into
   `MutantOutcome.platformKillMechanism`.
3. **The screen.** `SessionReport.platformArtifactKills` counts the KILLED mutants carrying a tag,
   groups them by mechanism, and prints a `PLATFORM-ARTIFACT KILL SCREEN` line plus the
   `platform-artifact-kills` caveat. It says "read these", never "these are false".

## The live result, pre-committed before the run

Pre-commitment: `docs/superpowers/specs/2026-08-08-r72-value-form-arm-precommitment.md`. All five
new mutants matched, and the tables gate moved 109/17/10 over 136 -> **113/18/10 over 141**, raw
specs 148 -> 154. The `remove-commit` at the value-form `Commit()` came back **killed**, screened,
and its verdict did not move.

The per-mutant baseline was re-recorded and diffed: exactly 5 additions, 0 removals, 0 changes.

## Red-checks

- Five separate guards in the detector, each mutated and each reddening exactly the test written for
  it: the ordering guard, the return-value-consumption guard, the enclosing-body guard, the receiver
  check, and case-insensitivity.
- The LIVE path: disabling the tag in `removeCommit.generate` takes `fixtures/sandbox-data` from
  1 tagged spec to 0, which makes `platformArtifactKills` absent and fails the gate's
  `screen !== undefined` assertion. So "removing it makes the gate stop naming the artifact" is
  measured rather than argued.

## What this row got wrong

- **It named the CALL FRAME as the candidate.** Measured irrelevant (A1 vs A3, A5 vs A7). So were
  call depth, the test runner's own transaction, and `TableNo` — all four were on the candidate list.
- **It settled for operator-plus-corroborating-TEXT.** The shipped detector uses no text at all. BC's
  refusal message is generic and localises (R66), so a text rule would both over-claim and be
  English-only; the syntactic rule has neither ceiling. This is worth stating next to R121, which
  measured that on a real 73-kill corpus the only 100%-precision rule anyone found WAS a message
  text — the two rows reached opposite conclusions from the same constraint, and the difference is
  that this artifact has a syntactic signature and the field-length one does not.
- **It treated the re-wrap hole as unresolved.** `if not Codeunit.Run(...) then Error(Err,
  GetLastErrorText())` cannot hide the artifact: probe arm B1 measured that the caller never regains
  control, and no arm in either pass has ever reported `ranFalse=Yes`.

## What the screen deliberately does NOT do

It covers ONE operator. R82's arm E — a swap killed by a BC field-length overflow under a test that
asserts nothing — sits in the same fixture, in the same run, and is not screened, because
`lethal.swap-call-arguments` tags no sites. The report's own interpretation says so rather than
leaving a reader to infer that an unscreened kill was assertion-earned. Extending the tag to other
operators needs, for each one, the same thing this one needed: a measurement of what the platform
actually refuses, and a fixture site that produces it.
