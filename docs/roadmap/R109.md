**No single command answers "is this environment ready to measure?" — the pre-flight refusals exist but only fire one at a time, mid-run.** Every check a user needs already exists as a refusal somewhere: environment status (`env-tool-session.ts`'s `requireStatus`, R34), lease and op-marker state, the quarantine record, the control-app version (R28), resolved tool paths. But each one aborts the run at the moment it trips, so a user with three problems discovers them across three slow round-trips — the measured experience `lethal doctor` replaces. `doctor` composes those same refusals into one read-only report that runs EVERY check before reporting, never short-circuiting. Two honesty constraints are part of the feature, not polish. (1) It must state what it does NOT check — the per-file publish ceiling needs generation to have happened, and baseline health needs a run — so all-green reads as "every pre-flight refusal I can evaluate passes", never "run will succeed". (2) For env-tool configs it may spawn only `resolve` blocks; never `createEnv`, `startEnv`, `publish` or `downloadSymbols`, because a diagnostics command must not mutate or bill. The drift hazard to watch in review is a narrow `DoctorConfig` that decouples from what `run` actually requires, which would let doctor report green on a config `run` rejects — worse than no doctor at all; the defence is projecting the narrow type from the SAME load-and-validate path `run` uses, `Pick<>`-coupling the carried-over fields, and a pinned test per check that a fixture making `run` refuse also makes doctor non-green. Filed 2026-08-05 from subsystem C's Task 4, whose plan mis-described this as "move R34's late probe earlier" — measured false: `backend.status()` (`orchestrator.ts:2067`) already precedes `discoverTests` and `generateMutationSet`, and R34's own refusal completes before `runSession` is entered at all. R34 is closed and stays closed; this is the separate gap.
