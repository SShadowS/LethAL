**Found by gpt-6-sol reviewing the GH-07 plan (2026-09-25), from the source; not measured live.**
R193 numbers identical twins in SOURCE order within their identity tuple
(`assignIdentityOrdinals`, `packages/schemata/src/project.ts`), and the key carries the ordinal
(`serializeKey`, `packages/runner/src/selection.ts`). The key does not carry the operator's minor
version, and the resume fingerprint (`sessionFingerprint`, `packages/runner/src/resume.ts`) does not
include the emitted mutant set.

**Consequence:** when a build makes an operator stop emitting one twin (a cession, such as GH-07's
`flip-boolean-literal` refusing a loop condition), every later twin in that procedure moves down one
ordinal. A `--resume` from a run recorded by the older build then matches the prior ordinal-0 verdict
to what is now a DIFFERENT mutant, and carries it without executing it. Example: `while false do ...`
before `Done := false` in one procedure; both `false` flips share a key; after the cession the
assignment's flip becomes ordinal 0 and inherits the loop flip's old verdict.

`campaign compare` is not affected the same way: it checks cardinality and per-key differences
against a committed baseline, so a changed count shows up as a mismatch to re-freeze.

**Fix shape (not decided):** put the emitted mutant set's digest (or each operator's full version)
into the resume fingerprint, so a run recorded by a build with a different mutant set is not
resumable; or refuse to carry a twin whose ordinal is above 0 when the twin count changed. Every
past cession had the same exposure; this is the class, not GH-07's defect.
