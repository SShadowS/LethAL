Split from [[R969]] by coord task PR-04 (2026-11-14), which built and ran R969's positive leg (`itest:lend` RL). Related: [[R680]].

**What is missing.** The positive half is proven live: a lease reset with no restart keeps the database id, and RL carries the verdicts.
The other half is proven only offline (`orchestrator.test.ts` "R969: the database id decides ..."): when the database itself is new, as
after a server1 restart (bc1-bc3 hold their databases in memory), the id changes and the resume must refuse as R680 did.

**How to measure it.** At the next server1 restart, before re-running the setup script:
1. Keep a scratch store holding an unfinished `itest:lend`-style run recorded on a bc server, with its database id.
2. After the restart and setup, run `--resume-run` of it.
3. Expect the R680 refusal, saying the database id changed (not `resume-across-lease-reset`).

Pre-commit that expectation before the restart. The restart itself is the owner's; do not cause one for this.
