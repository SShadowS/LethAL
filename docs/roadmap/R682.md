**Filed 2026-10-23 by lethal-bugs during R-560c**, by the orchestrator's ruling. It is a different gap from
[[R560]], with the same cure.

**What.** Today's gate runs print, for example:
- `tables itest: identity scheme changed (38 -> 41): 394 mutant(s) checked by their mutated-text hash, 12 mutant(s)
  text-UNVERIFIED`;
- the same for `hang itest SINGLE leg` (36 checked, 2 unverified) and `al-runner-v3 itest leg T` (40 -> 41, 394 and 12).
- `bcdev` (38 -> 41) has 0 unverified.

Every row of those baselines carries a `mutatedTextSha256`: R-560 part B re-recorded tables and hang.single at
scheme 38, and leg T's baseline was recorded at scheme 40, after R556. So these rows are not
R560's case, a hash missing on one side. They are [[R556]]'s deliberate rule: across a scheme change, keys may have
been reassigned, so `compareMutants` text-checks a row only when its hash is unique within its tuple group on both
sides. Byte-identical twins share one hash while their ordinals can move, so they are counted text-UNVERIFIED.

**Why it recurs.** `IDENTITY_SCHEME` (`packages/schemata/src/project.ts`) is 41 today. The gate baselines were recorded
at 38 (and leg T at 40). Every scheme bump puts every baseline recorded before it back into the cross-scheme compare,
and its twins back into UNVERIFIED. The cure is a re-record at the current scheme: the compare is then same-scheme,
and every row's text is checked. But nothing asks for that re-record. A scheme bump passes every gate, and the
UNVERIFIED line is easy to read as noise.

**To close.** Make a scheme bump carry its re-record:
- the gate pages (`docs/gates/README.md`, and each gate page) state that a change raising `IDENTITY_SCHEME` must
  re-record, in the same change, every gate baseline whose run then prints a non-zero text-UNVERIFIED count, by the
  R332 procedure;
- optionally, a unit test that fails when `IDENTITY_SCHEME` is above the scheme a committed gate baseline records,
  unless that baseline is listed with a reason;
- then re-record today's lagging baselines (tables, hang.single, al-runner-v3 tables, and any other the next gate runs
  name).

Evidence: R-665's gate logs (`/coord/handoff/R-665/bc1-gates/tables.log`, `/coord/handoff/R-665/hang-bc3/hang.log`,
`/coord/handoff/R-665/alrunner-v3/alrunner-v3-all.log`); `compareMutants` and `sharedHashes` in
`packages/runner/itest/mutant-equality.ts`; `identityStatement` in `packages/runner/itest/baseline-guard.ts`.

**Done 2026-10-23 (R-253, lethal-bugs): the rule is on the gate pages and in a test.**
- **The page:** `docs/gates/README.md`, "A scheme bump re-records the baselines". A change that raises
  `IDENTITY_SCHEME` re-records every gate baseline in the same change (R332), or lists each one it leaves behind
  with the item that re-records it.
- **The check:** `gate-pages.test.ts`, the R682 describe.
  - Every committed `itest/*.baseline.json` must record the current scheme or sit in `LAGGING_SCHEME` with an item.
  - A listed file that has caught up fails too.
  - Its two direction tests use `schemeLag`: an unlisted baseline behind a bump fails, naming the file; a listed
    one that caught up fails; an unlisted current one passes.
- **Stricter than first filed:** it holds every lagging baseline, not only those that print a non-zero
  text-UNVERIFIED count. Any baseline behind the scheme is compared across a scheme change, so its twins can go
  unverified on the next run.
- **Today's lagging baselines** (eight) are listed. Seven wait on [[R690]], which runs once after R-604b decides
  whether the scheme moves to 42 (lethal-preproc: decided by measurement, not before tomorrow). `envtool.baseline.json`
  waits on [[R683]] (host only). Not re-recorded here, so that they are recorded once.
