Filed by coord PR-115 (lethal-code, 2026-11-17), from its spec's delta review r1 (H-A) and its build review (H1). Spec:
`docs/superpowers/specs/2026-11-17-pr115-baseline-batching.md`.

**Today.** `baselineBatchingFor` requires three things:
- the build's exact version and sha are in `V3_BASELINE_BATCHING_BUILDS` (al-runner-v3-pins.ts);
- this session's probe reads PR-114's 8 capability facts as `matches`;
- the §6 Sleep rule is retired.

**Why a list, not a pin field.** Pin readings travel between builds:
- a re-gate writes the applied pin into `.gated` `readingsFrom`;
- every later candidate adopts that root's readings.

A flag on a pin, a hand pin or the shared root edge-d72d3197d would therefore have spread to later builds with no decision. The
list sits outside every pin's readings, so the update gate never copies it.

**The gap.** A new `current` never batches until a person adds its version and sha to the list. That is safe, but the saving is
lost silently; the session's stats line and leg DBM name the reason.

**To close.** The update gate already requires the 8 capability facts to read `matches` for a pass (leg C). Record that in
`.gated` (as `warnFacts` already are), and let `baselineBatchingFor` accept a build whose own `.gated` record says the facts passed
at its own gate. It must never be inherited through `readingsFrom`. Add a red test for each direction, and pre-commit before the
change.
