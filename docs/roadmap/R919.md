Found by coord task R-913 (Enforced Digital Vouchers on v3, 2026-11-11). Evidence: `/coord/handoff/R-913/edv.sqlite` (`runs`),
`edv-r.stderr.txt`. Caused by R-907 (the R907 tag). Related: [[R786]], [[R897]], [[R912]].

**What.** The 1 h `--time-budget` stopped the run, which said "run --resume to continue". The resume refused: "--resume found no
unfinished run to resume ... and configuration". The store held two runs: run 1, the serve attempt that stopped at the warm-up (R786
falls back on a test R612 refuses), with runner build `... isolation-auto`; and run 2, the one-shot fallback that did the work, with
`... skip-after-timeout isolation-auto`. A `--resume` starts on serve again, so its backend's `skipAfterTimeout` is false (serve never
passes the flag) and its runner build has no tag: it matches only run 1, which holds nothing to carry.

**Workaround, used.** Resume with `"transport": "one-shot"` in the config: it found run 2 ("reusing run 2 — 402 mutant verdict(s) may be
carried").

**Fix.** The tag says whether the BUILD lists `--skip-after-timeout` (`ExecutionBackend.skipAfterTimeoutSupported`), whatever the
transport, so a serve session and its one-shot fallback store the same string. Two sessions on the same build differ only when its
help call failed, which still splits them, as R907 meant.

**Runs stored in the window.** Serve runs stored between R907's merge (43efd53b) and this fix carry no tag, so a resume or lend from
them is now refused. This is fail-safe: it refuses, it never mixes. A run stored by a one-shot session in that window still matches.
