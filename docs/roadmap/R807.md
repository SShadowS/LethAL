**Done 2026-11-05 (coord task R-807).** Pre-commitment: `docs/superpowers/specs/2026-11-05-r807-alpha12-run-seed-precommitment.md`
(master 94b3337d). Evidence: `/coord/handoff/R-807/probe.md`. Related: [[R804]], [[R784]], [[R590]].

**Why.** From alpha.11, al-runner draws a fresh seed for `Random`, `CreateGuid` and SystemIds in every one-shot run and every
`serve` request. Measured on alpha.12 with no pin: a test failing when `Random(2) = 1` failed in 6 of 12 separate requests.
LethAL compares a baseline, a prefetch, live requests and one-shot calls, which are separate requests or processes, so a
value-dependent test could fail in a mutant's run for a reason other than the mutant.

**What was built.**
- `packages/runner/src/al-runner-v3-seed.ts`: `V3_RUN_SEED = 1`, and `v3ChildEnv()`, the one helper that builds the
  environment of an al-runner process (`ALRUNNER_SEED=1`, set explicitly on top of the parent's environment, so an ambient
  value cannot win). Spawn sites covered: the backend's `--version`, one-shot calls (`spawnCodeunit`) and serve daemons
  (lanes); the predefined-symbols probe; the contract probe (its `spawn` wrapper, so `--version`, the bad-flag call and
  every `call()` incl. the timeout burns' taskset-wrapped runs, and `serve-keep-reasons`); `lethal doctor`'s `--version`;
  the gate's O1 daemons and its direct build-7 call. The `seed` field and `--seed` are not used (alpha.7 refuses both).
- **Read-back guard.** A serve summary or a one-shot envelope that reports `seed` must read seed 1 with `seedSource` `env`,
  else `AlRunnerV3SeedError` (extends `Error` directly) refuses the session. No `seed` is accepted. Guard sites:
  `AlRunnerServer` (both summary returns) and `decodeV3Rows`.
- **Report.** `ExecutionContext.runSeed` (optional number) on directly measured v3 entries, absent when the build reports
  none. Optional, so older reports and the committed gift-card sample stay valid with no live regeneration. Schema
  regenerated.
- **Pin `alpha.12-d4bc8d3a5`** on the shared `READINGS_8078BCF49`, plus the optional pin field `o1.cdoApps` (18 here, default
  17) read by O1 (`o1CdoApps`).
- **Leg O1 sub-check** (`judgeO1Seed`, `o1SeedCheck`; new test codeunit 77055 `Order Seed Reader` in
  `fixtures/sandbox-order-tests`). Own package set only: the seed does not depend on the package set, and a second daemon pair
  on the CDO set would cost minutes of cold start for no extra proof. Pinned daemon: two separate requests read identical
  values. Daemon with the variable removed (`v3UnpinnedEnv`): on a build that reports `seed` the two requests differ, on one
  that reports none they are identical. Read-back: pinned answers read seed 1 / `env`. Any failure is `gate-fail`.

**Live readings (O1 alone, at b94f31a8; logs `/coord/handoff/R-807/o1-alpha7.log`, `o1-alpha12.log`).**
- alpha.7 (`current`): own and CDO sets pass (17 apps); seed sub-check: identical values with and without the variable, no

- alpha.12 (by path): own and CDO sets pass (CDO 18 apps, WorkDate 2026-08-01, commit kind "runs"); pinned answers read seed 1,
  source `env`, identical values; without the variable the two requests differ (seeds `fresh`).

**What a constant seed costs (owner ruling, stated plainly).** Under seed 1 a test that depends on `Random`, `CreateGuid` or a
SystemId reads the same values every time, whichever way it goes. So v3 cannot report such a test as flaky, the way real BC
might. The baseline decides it. Finding that kind of flakiness is upstream's stability mode, not LethAL's job.
