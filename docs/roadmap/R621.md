**Filed 2026-10-22 by R-618** (lethal-preproc; the orchestrator's ruling after `itest:lend`'s first live run).

**What.** `--resume` treats a stored `no-coverage` verdict two ways:
- **Wholly carried batch:** `replayCarriedBatch` carries every stored verdict, `no-coverage` included.
- **Partly carried batch:** `scoreBatch` records the uncovered mutants from this session's own coverage selection,
  before any carry lookup. So a stored `no-coverage` is never carried; it is re-derived, and the report does not mark
  it `carried`.

`CARRYABLE_VERDICTS` (`resume.ts`) includes `no-coverage`, so the carry index offers it either way.

**Evidence.** `itest:lend`, live run 1 on bc1 (`/coord/handoff/R-618/live-run-1.md`). Leg R2 resumed a partly
carried clone and carried 7 of 9 KEPT rows; the two no-coverage rows came back fresh. Leg R1 resumed a whole clone
and carried all 19, no-coverage included.

**Which direction is safe.** Re-deriving is the safe one: nothing is lent where fresh coverage is at hand. The
risky path is the whole-batch carry. It lends a `no-coverage` from an earlier run that this session's coverage
might classify differently (for example after a test was added that now reaches the mutant), with no fresh
coverage behind it.

**To close.**
- Decide and write down one rule: carry `no-coverage` in both paths, or re-derive it in both.
- If re-derive: `replayCarriedBatch` needs fresh coverage, which means it runs a baseline, which is the cost a whole
  carry avoids today. If carry: say why a stored `no-coverage` stays valid without fresh coverage.
- Update `docs/gates/lend.md` and the gate's expectations to the chosen rule.
