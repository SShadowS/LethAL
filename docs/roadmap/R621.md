**Filed 2026-10-22 by R-618** (lethal-preproc; the orchestrator's ruling after `itest:lend`'s first live run;
wording corrected after R-618's build review, I-2).

**What.** `CARRYABLE_VERDICTS` (`resume.ts`) includes `no-coverage`, so the carry index offers a stored
`no-coverage` like any other verdict. What happens to it depends on the path:
- **Wholly carried batch:** `replayCarriedBatch` carries every stored verdict, `no-coverage` included. No fresh
  coverage exists in this path.
- **Partly carried batch:** `scoreBatch` first records the mutants that THIS session's coverage selection leaves
  uncovered as fresh `no-coverage`, before any carry lookup. Every other mutant goes to `carriedVerdictFor`. So:
  - a mutant uncovered now is re-derived, whatever its stored verdict (a stored kill or survival is not carried
    either);
  - a mutant covered now whose stored verdict is `no-coverage` IS carried, and fresh coverage that says otherwise
    is overruled.

So the rule in both paths is: carried = carryable rows minus rows uncovered in this session. The second partial
case is the risky one, and arguably worse than the whole-batch carry, because the contradicting coverage is at hand.

**Evidence.** `itest:lend`, live run 1 on bc1 (`/coord/handoff/R-618/live-run-1.md`). Leg R2 resumed a partly
carried clone and carried 7 of 9 KEPT rows; its two no-coverage rows are uncovered in this session too, so they came
back fresh. Leg R1 resumed a whole clone and carried all 19, no-coverage included. The fixture has no mutant that is
stored `no-coverage` and covered now, so no gate exercises the risky case.

**How likely.** A test-app change changes the test-app hash, and `assertSameTestApp` then refuses the whole resume,
so "a test was added" cannot produce it. What is left is coverage that differs between two sessions on the same
test app and target; no such case is known.

**To close.**
- Decide and write down one rule: when a stored `no-coverage` disagrees with, or lacks, this session's coverage,
  carry it or re-derive it.
- If re-derive: in the partial path, a covered-now mutant with a stored `no-coverage` must be run, not carried; in
  the whole path, `replayCarriedBatch` needs fresh coverage, which is the baseline cost a whole carry avoids today.
  If carry: say why a stored `no-coverage` stays valid.
- Update `docs/gates/lend.md` and the gate's expectations to the chosen rule.

**Done (R-585, plan `docs/superpowers/plans/2026-10-22-r585-r621-carry-scope.md` r2). Rule: re-derive.**
- `carriedVerdictFor` never returns a stored `no-coverage`. This generalises R318's narrower line,
  which is removed; R318's snapshot `allowReuse` guard stays.
- Partial path: a mutant covered now is run; a mutant uncovered now reads `no-coverage` fresh, as
  before.
- Whole path: a fully scored batch holding a `no-coverage` row is no longer carried whole. It is
  deployed, and its baseline is reused from a matching snapshot when one exists (R192). The cost is
  one deploy per such batch per resume, accepted by ruling. The cheaper snapshot-confirmed variant
  is R643.
- The `resume-reusing-run` text says so.
- A realistic cause was reproduced: a target edit that adds a call. A resume allows it, the uncovered
  procedure's keys do not move, and so its stored no-coverage carried.
