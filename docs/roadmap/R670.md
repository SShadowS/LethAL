**Filed 2026-10-22 by lethal-bugs during R-658** (preparing `compile:fixtures` in a fresh worktree, as the R-658 build
review advised).

**What was measured.**
- I extracted every `.alpackages` folder from `/work/lethal/.kraken-local/fixture-symbols.tar` into a fresh worktree.
  The tar's sha256 equals `FIXTURE_SYMBOLS_TAR_SHA256` (`bdf460e2…`).
- `bun run compile:fixtures` then fails `fixtures/sandbox-data-tests` with 3 errors:
  `DataTests.Codeunit.al(1445|1457|1477,14): error AL0185: Report 'Data Band Report' is missing`.
  The log is `/coord/handoff/R-658/compile-fixtures.log`.
- The cause: the tar's `fixtures/sandbox-data-tests/.alpackages/` holds `LethAL_LethAL Sandbox Data_1.0.0.10.app`. The
  report and its extension came with R-254 and R-463 (`sandbox-data` 1.0.0.11 and 1.0.0.12), and the fixture is now
  1.0.0.13.
- The lane-bugs worktree shows the same, from its own stale 1.0.0.10 copy.
- Every other project the tar covers compiles.

**Why it matters.** CLAUDE.md step 4 makes `compile:fixtures` the only offline compile of the fixtures (R56), and a
fresh worktree's only symbol source is this tar. So in any fresh worktree that step reads FAIL for a reason unrelated
to the change under test, and that invites "pre-existing, ignore".

The al-runner-v3 gate extracts this same folder (`GATE_ALPACKAGES`, R614). Its leg T compiles `sandbox-data` from
source, so it is not affected. Whether any other consumer reads that app from the tar is not checked.

**To close.**
1. Rebuild the tar with the current `sandbox-data` app in `sandbox-data-tests/.alpackages`, or drop that app from the
   tar so it is always built from source.
2. Re-pin `FIXTURE_SYMBOLS_TAR_SHA256`. This follows R614's re-pin procedure: the gate worktree refuses once and is
   re-extracted.
3. Add a test that every `LethAL_*` app in the tar matches its fixture's `app.json` version, so a fixture bump without
   a tar refresh fails ordinary CI. The tar is not in CI, so this may need to be a check run by
   `compile:fixtures` itself instead.

Evidence: `/coord/handoff/R-658/compile-fixtures.log`; R614 (`docs/roadmap/R614.md`); R56.

- **Owner step: retiring the old tar.** `/work/lethal/.kraken-local/fixture-symbols.tar` (`bdf460e2…`) is kraken's
  `secret_files` delivery, re-extracted into the main checkout by `scripts/kraken-setup.sh`, so deleting it in
  the container does not retire it: kraken puts it back. The OWNER replaces it in the host secrets folder (the one
  `scripts/kraken-secrets.ts` writes) with the current tar, or drops that `secret_files` entry.
  - `scripts/kraken-secrets.ts` used to REBUILD `fixture-symbols.tar` from the HOST repo's `.alpackages` on
    every run (`symbolTar`), so a refresh from stale host folders shipped stale copies again, and a packed build
    can never equal the pin anyway (GNU tar's default format, host mtimes and owners). That path is gone:
    without `--symbol-tar <pinned tar>` the run is refused by name. With it, the tar ships verbatim, only if
    its sha256 equals the pin, its listing is readable and non-empty, and it does not drift from `app.json`
    (`tarDrift`). The owner refreshes the host's `.alpackages` from the new tar (for the host's own compile)
    and runs kraken-secrets with `--symbol-tar` set to that same tar, or retires the entry.
  - `scripts/kraken-setup.sh` now keeps each delivered tar under `fixture-symbols-<sha12>.tar` too, in the main
    checkout only, the name the code reads, so after the swap the pinned tar is found on a fresh container as
    well. In a worktree with an R614 marker it leaves the two gate folders alone (no removal, no extract),
    so another tar's files never sit under a stale marker that `prepareFixtureSymbols` would read as
    `verified`. Master's `kraken-setup.sh` has no such guard, and the swap runs before the merge, so the
    owner-steps file has the orchestrator reset every marked worktree right after the swap.
  - Exact steps: `/coord/handoff/R-670/owner-steps.md`.

  folders and the marker only when the marker names another pin, and refuses everything else
  (`scripts/fixture-symbols-reset.test.ts`, each refusal red-checked).
