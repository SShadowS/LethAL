**Found by** the review of [[R219]] run 003 (minor M4).

al-runner can label coverage with a path other than the batch file it compiled. Measured on
`v2.12.0-main.c39ad5de`, 2026-10-07:
- With the test app beside the source project, it labels with the project's SOURCE path. It
  discovers that project as a workspace dependency and caches it under
  `~/.cache/al-runner/workspace-deps`.
- From a copy compiled elsewhere, it labelled with the FIRST batch's flat path, in a directory that
  was no longer in use.

LethAL resolves those labels exactly where a file name is shared, and refuses a label that names no
file or two different files ([[R219]]). What has NOT been measured is how al-runner picks the label:
- **An object moved between files during a run.** Does the label follow the object's new file, or
  stay with the file the cache last saw?
- **A stale workspace-deps cache.** For example, a project edited since the cache entry was written,
  or a cache entry from an earlier session at another path.

Either could credit coverage to the wrong file within a project, or drop it. These are coverage
risks only. A wrong label can make a covered mutant read `no-coverage`, or select the wrong covering
tests. It cannot make a mutant read `killed`, because a kill comes from a test's own result, not from
coverage.

**To close:** probe both cases on the pinned al-runner build, with the one-shot and `--server`
transports. Record the labels. Then either show that LethAL's resolution handles them or refuse the
shape by name.

## Measured, and guarded (R-505, 2026-10-08)

**Measured on `v2.12.0-main.c39ad5de`, both transports.** Every run used a scratch cache (`AL_RUNNER_CACHE_ROOT`
plus `--cache`); the gates' cache was checked untouched. The 11 probes and their outcomes are in
`/coord/handoff/R-505/plan.md`.
- **The label's path is the object's file in the source project al-runner finds BESIDE THE TEST APP, as it is on
  disk at that moment.** It is re-read at every invocation and every `--server` `runTests`. It follows the object,
  not the content or the basename: a move into a brand-new file is named.
- **The lines are always the compiled batch's.** An edit inside a single-object file moves nothing.
- **A stale cache is harmless.** The workspace-deps cache is content-addressed and pins no path, so a new
  directory per session labels its own path.

**The risk.** LethAL compiles the session snapshot. If the live project changes during a run:
- an object moved to another existing file has its coverage credited to that file's object;
- an object moved to a new file, or a renamed file, has its coverage dropped.

Covering tests, and so verdicts, change.

**Upstream already fixed the labelling.** #5249 (`3c350f65`, 2026-10-02 19:46, closing #5222) makes the compiled
bundle win over a same-app-id sibling. The pinned `c39ad5de` is 29 commits before it. The root fix, moving the pin,
is a follow-up task.

**Guard (ruled 2026-10-08: option B; a frozen sibling copy was refused).** The frozen copy needed links into the
user's real test folder inside a scratch tree that is deleted recursively, a data-loss risk.
- `watchProjectInputs` (`packages/runner/src/source-drift.ts`) compares the live project with the run's start:
  - every `.al` file and `app.json`, against the session snapshot;
  - every resource the batch copies (`isProjectResource`), against the bytes at the first check;
  - minus the run's own output files.
- It is stat-gated, so bytes are read only when size, mtime or ctime moved.
- `AlRunnerBackend` checks before and after every coverage-producing call: the one-shot `sendOneShot` with a
  coverage file, and the `--server` suite run.
- Any change throws `ProjectChangedDuringRunError`, naming the first five changes and saying `--resume` continues
  the run. It is never a verdict: one-shot it propagates out of `run()`, and on `--server` it goes through R-219c's
  `ServerCoverageRefusal`.
- `buildBackend` arms it only with coverage on and a session snapshot. The itests build none, and their fixtures do
  not change.

**Limit, stated.** An edit undone between two checks, starting and ending inside one al-runner call, is not seen.
A `git checkout` to another branch and back during a run is that case. The agent guide says not to.

**Tests:** `r505-source-drift.test.ts` covers an edit, an add, a delete, a rename (removed plus added), app.json, a
resource, the run's outputs and tool directories (never counted), the five-change message, and a no-change control.
`cli-al-runner-defaults.test.ts` covers both transports (an edited project stops the run; an unchanged one runs) and
that no snapshot means no watch.
