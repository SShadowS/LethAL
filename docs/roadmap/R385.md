id: "R385"
title: "lethal verify cannot see a Microsoft dependency rebuilt or upgraded on the server while the test app's declared minimum version stays the same"
section: "correctness-risks"
status: "done (e64bc53e)"
order: 1062
---

**What.** R-371's dependency fingerprint (`dependencyFingerprint` in
`packages/runner/src/digest-inputs.ts`) covers every non-Microsoft dependency, transitive ones too,
by the SHA-256 of its package. A Microsoft dependency (publisher `Microsoft`) is covered by id and
version only, and the version is the one the test app's manifest DECLARES (`MinVersion`, or app.json's
`version`), not the one the server holds.

**Why it matters.** Two changes are invisible to `lethal verify`, so a test that now behaves
differently is treated as old (the unsafe direction):
- a Microsoft library rebuilt at an unchanged version;
- a Microsoft library (Library Assert, the Base App, the test libraries) UPGRADED on the server while
  the test app still declares the same minimum. This is broader than "rebuilt at the same version":
  a container update does it.
The negative is pinned by test in `packages/runner/tests/digest-inputs.test.ts` (the Microsoft-limit
case).

**What would close it.** Read the RESIDENT version of each Microsoft dependency from the server (bcdev
`/packages` or the installed-apps list) and put that in the fingerprint, instead of the declared
minimum. Hashing Microsoft packages by bytes, as for the others, is the full fix but means
downloading the Base App per run; measure that before choosing it.

**Closed 2026-10-04** (plan `docs/superpowers/plans/2026-10-04-R-385-resident-microsoft-dependencies.md`).
Measured first: on BC 28.4 the 14 Microsoft packages a test run depends on total 68.9 MB and download
in about 3.2 s, byte-identical across downloads, and 12 of them hold real `.al` source. So the full fix
was affordable and was chosen: the dependency fingerprint now hashes every Microsoft package in the
closure by its bytes, the same as the others, plus the platform (System) package always, Application
when an app in the closure declares it, and the control app's dependencies (which reaches Microsoft's
Test Runner, which runs every test). A per-id check confirms each Microsoft extension is the installed
one; a mismatch, an unreadable package or a control-version mismatch is refused by name, never
replaced by the declared version. There is no cache, because a cache keyed on version would miss a
same-version rebuild; the measured cost is about 4.3 s per run and per verify. The digest scheme moved
from v2 to v3, so every recorded test looks new once. Stated limits: a symbols-only package
(Application, a wrapper app, and the control app have no `.al`) hides a rebuild that changes only
bodies, and a binary-only platform update may not change System's bytes. The first read path, one
unfiltered automation `extensions` query, hung BC 28.4 and needed a container restart; that query is
now refused at run time and in source (R433). Live: `itest:verify`, `itest:agreement` and
`itest:verify-scale` pass on Cronus28, with every frozen figure unchanged. Follow-ups: R434 and R435.
