---
id: "R385"
title: "lethal verify cannot see a Microsoft dependency rebuilt or upgraded on the server while the test app's declared minimum version stays the same"
section: "correctness-risks"
status: "open, filed 2026-10-01"
order: 1062
---

**What.** R-371's dependency fingerprint (`dependencyFingerprint` in
`packages/runner/src/digest-inputs.ts`) covers every non-Microsoft dependency, transitive ones too,
by the SHA-256 of its package. A Microsoft dependency (publisher `Microsoft`) is covered by id and
version only, and the version is the one the test app's manifest DECLARES (`MinVersion`, or app.json's
`version`), not the one the server holds.

**Why it matters.** Two changes are invisible to `lethal verify`, so a test that now behaves
differently is treated as old (the unsafe direction):
- a Microsoft library rebuilt at an unchanged version;
- a Microsoft library (Library Assert, the Base App, the test libraries) UPGRADED on the server while
  the test app still declares the same minimum. This is broader than "rebuilt at the same version":
  a container update does it.
The negative is pinned by test in `packages/runner/tests/digest-inputs.test.ts` (the Microsoft-limit
case).

**What would close it.** Read the RESIDENT version of each Microsoft dependency from the server (bcdev
`/packages` or the installed-apps list) and put that in the fingerprint, instead of the declared
minimum. Hashing Microsoft packages by bytes, as for the others, is the full fix but means
downloading the Base App per run; measure that before choosing it.
