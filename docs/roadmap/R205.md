`U:/Git/do-lethal-54483` at `4954a88a`, `--only` seven Azure/setup files (605 sites, 591 deployed,

```
run-1-batch-0-staged\CDOAzureBlobStorage.Codeunit.al(1079,14): error AL0104: Syntax error, 'end' expected
```

Bisection re-staged with the candidate excluded, failed again, and every batch-0 mutant was scored
`error` with the note "deploy failed for a reason that is not attributable to any SINGLE mutant —
either environmental (e.g. app-version monotonicity, transport, licence) or MORE THAN ONE mutant

**What the artifact shows.** The staged `CDOAzureBlobStorage.Codeunit.al` is 2,732 lines for a
234-line source (offline instrumentation of the committed file is 1,425 lines). Its last dispatch
chain groups 21 mutants (M0109–M0129) whose recorded `procedure_name` is all
`AssertNoDuplicateFolderTriple`, although M0112–M0129 sit in the four procedures that FOLLOW it
(`InitializeConfigForTest`, `JoinFolderAndFilename`, `GetAzureID`, ...). Every alternative in that
chain, and its final `else` branch, carries the 76-line tail of the file after the procedure —
that tail occurs 21 times. The `else` branch (line 2648 of the staged file) is LethAL's verbatim
copy of the ORIGINAL statement it wrapped, and it reads:

```
        if CDOAzureBlobFolderMgt.IsFolderTripleTaken(...) then
            Error(DuplicateFolderTripleErr, CompanyNameFound);

    /// <summary>
    /// Runs only the config-caching half of a blob operation (SetupAzureBlobMgt) ...
    internal procedure InitializeConfigForTest()
```

The procedure's `end;` is missing. tree-sitter recovered by letting the `code_block` run to the
end of the declaration body (no `ERROR` node is needed for that), `findEnclosingStatement`
resolved every later mutant to that block, `buildComponents` made it one component, and
`emitDispatch` did exactly what it is specified to do with a root that large. **The emitter is not
at fault; the input was.**

**Why LethAL is exposed, and what to change.**

1. `generateMutationSet` parses every file ONCE at session start and keeps the trees; each batch's
   `prepareBatchProject` then copies the project from disk again. Nothing checks that the bytes on
   disk still equal the bytes that were parsed. The documented promise ("LethAL copies the project
   to a scratch directory and mutates the copy") is true per batch but not per SESSION, so a file
   edited between the parse and a later staging is instrumented from one text and shipped with
   another, and a file edited before the parse is instrumented faithfully from a text nobody
   meant to measure. Snapshot the project once at session start (into the session's scratch dir),
   parse AND stage from the snapshot, and record each file's hash in the report.
2. A source that does not compile UNMUTATED should be named as such. Compiling the plain snapshot
   once before batch 0 (or checking `rootNode.hasError` per file, which would not have caught this
   recovery) turns "not attributable to any single mutant ... environmental" into "your project
   does not compile: <alc output>" and saves the bisection's second compile. R181 already
   compiles a candidate build; this is the zero-mutant case of the same check.
3. Secondary, same session: during batch 1's baseline the same second session (most likely)
   republished the target and its test app to the shared sandbox. Nine tests passed, the tenth
   failed with `The metadata object CodeUnit 68986 was not found. The application might be
   incompatible with the current compiler`, and every later method lookup answered `expected
   exactly one method X, found 0` — so R139's detector refused the session as `StaleTestAppError`
   ("the published test app is missing 50 test(s) this project's source declares"). The remedy it
   prints (republish the test app) was wrong in cause: the app was not older, it was being
   replaced. The refusal message should name the second possibility — the test app changed
   UNDER the baseline — and the transport could tell the two apart by reading the test app's
   installed version (or `TargetArtifactRegistry`) at baseline start and again on the first
   `found 0`.
4. `lethal doctor` could warn when `--project` is a git worktree with uncommitted changes or a
   checked-out branch (as opposed to a detached, pinned commit), since a worktree another session
   can `checkout` in is exactly the surface this cost a run on. Weak signal, cheap check.
