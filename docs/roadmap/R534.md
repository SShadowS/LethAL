**Priority.** Filed 2026-10-08 by the R518 build, from the adversarial review of its plan (I1, M5).
A policy question, not a measured defect: never a false kill, but a whole session lost to one
mutant.

**What.** `verdictFromRunnerTest` scores an al-runner row whose status is not `pass` or `fail`, and
whose message is not a timeout wording (`RUNNER_TIMEOUT_MESSAGE`), as `error` with
`AL_RUNNER_UNCLASSIFIED_ERROR` and `operation: "pre-dispatch-rejected"`. `runOnce` re-sends it once
(`isRetrySafe`). If the retry is the same `error`, `classifyNonVerdictStep` marks it a transport
error and `runMutantsOnBackend` throws `backend transport error: two consecutive run() failures for
mutant <id> (test <m>) — aborting session per spec §11`. No verdict for that mutant or any later one.

[[R518]] fixed the common case, a test that hits al-runner's in-run stop (exit 3, now read as a
`timeout`). It did NOT change this path. A hang in the test codeunit's `OnRun` trigger, or a
`RunnerOutOfScopeException`, can still give a TEST-TIMEOUT abort whose row message is not a timeout
wording: R518's transport accepts the envelope, the row scores `error`, the retry runs the hang a
second time, and the session aborts.

**The question.** Spec §11's rule exists for a TRANSPORT that failed twice (the backend cannot be
trusted to answer). An al-runner `error` row is an ANSWER: al-runner ran, reported, and exited.
Should such a row (a) keep aborting the session, (b) score the mutant `error` with its cause and let
the session continue, or (c) at least not be re-sent (it is not "pre-dispatch": the test ran)?
Option (c) alone halves the cost of a hang that is not classified; (b) also keeps the session.

**Evidence.** Plan `/coord/handoff/R-518/plan.md` §D2 last point; review
`/coord/handoff/R-518/review-r1-opus-adversary.md` I1 and M5. The offline test that pins today's
shape is `AlRunnerBackend one-shot: a test timeout exits 3 (R518)` > "an OnRun-trigger exit 3 is
accepted as rows but scored a fail-closed error, never timeout" in
`packages/runner/tests/al-runner-backend.test.ts`. The code is `verdictFromRunnerTest` in
`packages/runner/src/al-runner-backend.ts` and `classifyNonVerdictStep` in
`packages/runner/src/orchestrator.ts`. Not measured live: no fixture has an `OnRun` hang.

**To close.** A ruling on (a), (b) or (c). If (b) or (c): the change, red-checked both ways, and a
session-level offline test where the unclassified row no longer aborts the session.

**Premise corrected (measured 2026-10-09, `/coord/handoff/R-534/measure.md`).** A
`RunnerOutOfScopeException` in a test BODY is `fail`, not `error`, on both transports: it never
aborted a session, it was scored a KILL whose only evidence was al-runner's refusal. A refusal in an
`OnRun` is `error`. And the commonest aborting shape was not in this item at all: an unexecuted UI
handler (`The following UI handlers were not executed: <h>`), which every `[HandlerFunctions]` test
whose dialog a mutant skips produces. Both it and an OnRun hang aborted live sessions on both
transports.

**Ruling: (b), which includes (c), with two causes.** Spec §11 was written for a backend that
FAILED to answer. An al-runner row is an answer, so it is never re-sent and never a §11 abort. It is
a `timeout` when it provably is one; otherwise a per-mutant `error` with cause `runner-test-error`,
or `runner-refused` for an `out-of-scope: ` refusal. §11 keeps aborting for real transport failures:
a one-shot spawn, envelope or compile failure, a `--server` start or request failure, a missing row
with no hang, and R488/R491's merged or duplicate results.

**Fix (2629351e, causes and schema beba3d6c, plan `/coord/handoff/R-534/plan.md` r2).** `verdictFromRunnerTest`: the OnRun-trigger
timeout (`RUNNER_ONRUN_TIMEOUT_MESSAGE`) is a `timeout` with its reported stop; every al-runner
timeout records where it fired (`timeoutIn`), and the cold confirm uses the test's own figure only
for a body timeout, the wall clock otherwise (fail-closed, since no pass row reports the OnRun's
time). `RUNNER_TIMEOUT_MESSAGE` is anchored. A refusal at the type position (`RUNNER_REFUSAL`) is
`runner-refused`; every other non-verdict row, `skipped` included, is `runner-test-error`, both
`completed-accepted` and lifted into the covering step's cause. On `--server` a test with no row
after a hung one is `runner-test-error` (presumed after it). A row an exit-3 abort line proves was
stopped at the timeout, in unknown wording, warns once per session
(`alrunner-timeout-wording-unrecognised`). Explain schema 16. Offline tests T1-T7 and S1-S5 in
`al-runner-backend.test.ts`, `r534-runner-rows.test.ts` and `resume.test.ts`, every guard
red-checked in each direction. Live: pre-commitment
`docs/superpowers/specs/2026-10-09-r534-alrunner-precommitment.md`, Part A `itest:alrunner` and Part
B `scripts/r534-probe/run.ts`, run 2026-10-09 on the master-merged build (430eea1a, local
`al-runner v2.12.0-main.43f76177`, no BC): Part A PASS, every frozen figure unchanged, contract
`timeout-exit-readable=matches` on every probing leg. Part B MATCHES the pre-commitment on both
legs: all 20 verdicts, killed 8 / timeout-killed 3 / survived 6 / error 3 (`runner-refused` 1,
`runner-test-error` 2), no abort, N 60 one-shot and 120 `--server`, one mutated spawn then one
cold confirm per OnRun hang, no wording warning. Log `/coord/handoff/R-534/live-partA-partB.log`.
