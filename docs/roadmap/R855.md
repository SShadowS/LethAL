Found by [[R853]]. Three blocks in one `if` / `else if` / `else` chain, each holding an `if ... then begin` inside a `#if` arm with its `end` after `#endif`, parse with a lost procedure or a root ERROR. The text is valid AL: `alc` builds it.

**Cause, measured.** tree-sitter 0.25.10 keeps at most 6 parse versions (`MAX_VERSION_COUNT`). With that value set to 64 in a scratch build, the same files parse clean. So the grammar accepts the text and the parser drops the right version first. A chain of two blocks parses; three or more do not. Which conflict forks the versions is not traced.

**Why it reaches LethAL.** A chain copies the source, so a file that parses clean can emit this shape. 3 of 13,484 emitted files do, across DC, DO and all of BC.History (2,318,022 mutants). They are `CDCContiniaOnlineMgt.Codeunit.al` (246 mutants), `EDocIntegrationManagement.Codeunit.al` (314) and BaseApp's `ProdOrderComponent.Table.al` (1,098). 0 of 19,461 source files fail to parse. Detail in [[R853]].

**The cost.** Since [[R853]] a run with a mutant in such a file stops by name, so a file must be left out to run. A full BaseApp run gives up 1,098 mutants on a core table until this is fixed.

**Order (owner, 2026-11-06).** This goes after the operator batch: one grammar fix, one bump, one re-record then.

**The root fix** is in the grammar: fork fewer versions for this shape. It is a separate item because a grammar bump moved `IDENTITY_SCHEME` last time ([[R796]]). Do not raise the limit in a patched tree-sitter: that could change other parses, and so mutant identities. Do not add a new chain form for this one shape.

**Upstream:** https://github.com/SShadowS/tree-sitter-al/issues/40, with an invented repro.

**The first plan is BLOCKED (opus plan review, 2026-11-07).** `/coord/handoff/R855/plan.md` recommends a scanner edit, `cs`: the word `end`, where neither `end_keyword` nor `preproc_split_end` is valid, returns a token no rule holds. Do not build it as written. Its premise, "`end` is never a name", is false. `End` is valid AL in value positions: `OptionMembers = End,Start;`, `InitValue = End;`, `ValuesAllowed = End;`, and `const(End)` or `filter(End)` in table views, `TableRelation`, `CalcFormula` and page links. `alc` builds them, the stock parser reads them clean, and `cs` gives ERROR. No member is lost, so `isUnreadFile` does not stop the run: the tree changes silently, and `parseDamaged` turns true for the whole project. 0 corpus files hold the shape, which is why the plan's five-set diff missed it. That diff also never parsed emitted text, and `cs` read only 3 of 13,484 emitted files.

Also measured there: the limit is two limits, not one. `MAX_VERSION_COUNT` alone does not clear EDoc or ProdOrder; `MAX_LINK_COUNT` matters too. A second shape exists beside the issue's, an `if ... else begin` run inside `#if`, in 8 or more arms of a chain. The sentence above, "a chain of two blocks parses; three or more do not", is the first shape only.

**The candidate now: `csb`, in scratch only (2026-11-07). The plan stands at the top of `/coord/handoff/R855/plan.md`, and the release needs the owner.** `cs` plus one condition: `valid_symbols[BEGIN_KEYWORD]`, so `end` dies only where a statement could start. Source: `/coord/handoff/R855/csb/`.

## Fixed: tree-sitter-al 4.6.0 pinned (coord R-861, run 002)

The owner released 4.6.0 (tag 56949ce3). It holds csb's scanner check unchanged, and fixes #30 to #36, #39 to #42 and item 67. LethAL now pins it.

**Measured before pinning, on scratch copies.**
- Main at 971f6a25 parses as csb on 20,722 source files, the `End` value set, the repros and 13,484 emitted files (2,392,080 mutants), with 0 errors.
- It also reads shape C.
- The five-set diff of master against 971f6a25, edb6ea22 and the 4.6.0 pin is identical in all five sets, 575 projects: no spec, tuple, ordinal or tag moves. No `IDENTITY_SCHEME` bump. Evidence: `/coord/handoff/R855/up/`.

**What LethAL had to change, because 4.6.0 reads names and `#if` var sections correctly.**
- A dotted `extends`/`implements` name is one `qualified_name` node. `lastFieldChild` and `fieldSegments` read its segments, and every `base_object` reader uses the last segment. `hasQualifiedBase` accepts the new node. `extends My.Reports.P` stays refused (R487).
- `extends <number>` (#34) is now a clean `integer`. 4.5.0 left such an extension unparsed, and the R500 shape 7 and R331 fallbacks caught it. `resolveNumericBase` maps the id to the project object of that type. With no such object (a dependency's), the base is unresolved and every reader stays conservative: it extends every report (R487 holds), it matches any table for "may touch" readers and trigger-skip, and a claim on it is refused (R336's shape). A callee found only through such an extension counts as unresolved, so its refusal stays. Found by the build review, and fixed with resolved, unresolved and plain tests, red both ways.
- Two `#if` var blocks in a row, and a nested `#if` around a var section, now parse. R303's hoist blanks every block's `var` at any depth, or alc would give AL0104. alc proved all 14 hoist cases under symbol sets that turn every arm on, with 40 builds and 0 errors. A restored `var` gives AL0104.
- R853's and R331's tests use plainly invalid AL, so no later grammar fix can read their inputs.

**Named limits.**
- A dotted `interface ... extends Ns.IFoo` still parses as an ERROR plus its last segment: a grammar gap filed upstream. testpage-scan reads the last segment, as on 4.5.0, and loses a dotted parent listed before another.
- A split trigger header now parses, and a reach latch there refuses the file: [[R877]].
- `object-clash` with an unresolved numeric base (`extends 18`, a dependency table): the owner stays "18", and a member clash through it is missed. A dependent's side holds names only, and matching every table would refuse on any shared field id, so there is no conservative direction.
