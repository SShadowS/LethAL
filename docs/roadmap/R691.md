**Filed 2026-10-23 by coord task R-608** (lethal-code), from its Opus build review
(`/coord/handoff/R-608/review-build.md`, "older gap"). Not from R-608's diff.

**What.** `hashAlFiles` (`baseline-snapshot.ts`, used by `hashAlTree` and `hashTestDir`) leaves out every `.al` file
whose NAME is one of `CONTROL_FILES` (the selector, register and upgrade codeunit file names LethAL writes), at any
folder depth, in `active/` and in the user's test dir. LethAL's own control files sit at the root of `active/`. A
user file with the same name in a subfolder, or in the test dir, is then in neither the R192 snapshot key nor the v3
compile proof, while alc and v3 still compile it. A change to it would not move either hash.

**Effect.** None measured: no fixture has such a file. A residual.

**To close.** Leave out only the control files at the root of `active/` (the paths LethAL writes), and none in the
test dir; a red-going unit test per direction (a same-named file in a subfolder is hashed; LethAL's own root file is
not).

**Closed (R-691).** `hashAlTree` (the batch tree) now leaves out only the three control files at its root, and
`hashTestDir` (the user's test dir) leaves out nothing; both share one walk, `hashWalked`. Three tests in
`baseline-snapshot.test.ts` cover the directions: a same-named user file in a batch subfolder moves the hash, one in
the test dir (root or subfolder) moves the hash, and LethAL's own root control file does not. Each was seen red with
its fix reverted. LethAL writes the control files only at the root of the batch dir (`prepareArtifactDir`), for bcdev
and for v3's `active/`. No frozen figure moves, and stored R192 snapshot keys stay valid unless a project has such a
file.
