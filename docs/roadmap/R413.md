**Found by the first Linux run of the unit suite (kraken-move Task 6, 2026-10-03).**
`QuarantineStore.read` (`packages/runner/src/quarantine-store.ts`) treats `ENOENT` as "no record".
Opening `<file>/<hash>.json`, where `<file>` is a regular file, gives `ENOENT` on Windows and
`ENOTDIR` on Linux, so the same session reads "no record" on Windows and throws at
`consultQuarantine` on Linux, before it reaches the write that the test exists to fail.

Failing test: `runSession — Layer 5C-B1 Task 8: publish fence + op-gated release (design §6 steps 2/5) > a failed recycle write keeps the RecoverOp error primary and preserves the write failure (R361)` (`packages/runner/tests/orchestrator.test.ts`). Evidence line from the capture:

```
ENOTDIR: not a directory, open '/tmp/lethal-unit-run-VonAhF/tmp/lethal-orch-quarantine-3qJ9VL/blocker/9d38de8d0726fd6074b4feeaa76d358f.json'
```

**To close.** Read `ENOTDIR` as "no record" too, the behaviour Windows already has: no record can
exist under a path that is not a directory, and `record()` still fails loudly on such a path
(`mkdir` refuses it). Whether a non-directory quarantine path should instead refuse the session on
both platforms is left open here; nothing in the product creates one.

**Superseded by R417 (2026-10-03).** Review ruling: reading such a path as "no record" let `clear()`
answer "cleared" and the quarantine check report clean. Both platforms now refuse it with
`QuarantineStoreNotADirectoryError`; a missing store dir is still no record.
