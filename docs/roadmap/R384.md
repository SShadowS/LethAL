**What.** Since R-371 a test's digest covers everything it can reach in the test app, plus every
event-subscriber codeunit and what those reach. An edit to a shared helper, or to anything in the
subscriber closure, turns every test that reaches it "new", and verify runs each new test against
every survivor. Above `--max-new-tests` (default 50) verify refuses as `too-many-new-tests` and
names the number to pass.

**Why it matters.** Measured offline over every test-app procedure edited in turn (plan
`docs/superpowers/plans/2026-09-30-R-371-reachable-set-test-digest.md`, the r2 tables, and the build
measurement in `scripts/r371-reach-measure/product-measure.ts`):
- DC (1,301 tests) and DO (1,287): P(N>50) is about 11% for a procedure edit and about 22% for an
  object edit. The p90 is "all tests" on both, because about 10% of procedures sit in the subscriber
  closure.
- BaseApp Test (40,291 tests): the relaxed p50 is 1,571 new tests per edit, so every edit is over the
  cap. The most-shared helper gives about 5,734 new tests, about 585k executions at 100 survivors.

**What would close it.** Run a new test only against the survivors it can reach. That needs the new
tests' coverage, which verify does not have without an extra coverage run of the new tests. The
reachable-set walk (`Scanner.reach` in `packages/runner/src/testpage-scan.ts`) gives the test side;
the survivor side is its covering set. The filter must stay fail-closed: a test whose coverage cannot
be read joins every survivor, as today.

**Closed 2026-10-04** (plan `docs/superpowers/plans/2026-10-04-R-384-verify-reachability-filter.md`).
No extra coverage run was needed: in the default `fenced` mode verify's first unmutated run of every
new test already returns per-test coverage, which was discarded. A new test now joins a survivor only
when `coverageFilter`, with the source run's arguments, places it in that survivor's list (member
grain); the survivor's own covering tests are never removed. Fail-closed everywhere coverage cannot
place a kill: a test that is not fresh (`invalidBaselineReason`), did not pass or has empty or
missing coverage joins every survivor; a survivor with no site mapping, an `#if`-wrapped object, an
unplaceable line or an untouched table trigger takes every new test; the filter is off in hub modes,
in coverage mode `none` and under the new `--no-reach-filter` (verify only; other subcommands refuse
it). The state is printed on stderr (the verify report has no field for it; R425). A survivor no new
test reaches stays `survived` and is counted on stderr. `too-many-new-tests` is now a run budget
whose message states the budget and the counts before and after filtering. No report, identity,
fingerprint or explain input moved.

Measured: `itest:agreement` and `itest:verify` on Cronus28 matched a BLIND pre-commitment
(`docs/superpowers/specs/2026-10-04-r384-reach-precommitment.md`) in every pinned value, including
`LogAudit` surviving without the new test; with `--no-reach-filter` the new pins go red; on
`itest:agreement` the filter ran 4 mutant runs instead of 20. `itest:alrunner` unchanged. Offline on
Continia Document Output's r85 data the median edit plans 474 runs instead of 3,150 under the
fail-closed rule (an upper bound: the old report covers only part of the suite). Data Capture and
BaseApp Test can only be measured live. Follow-ups: R426 (the stated limit) and R427 (skip the rerun
of a test that reaches no survivor).
