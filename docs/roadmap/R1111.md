Filed by coord PR-124 (lethal-preproc, 2026-11-17), found while measuring R1092's baseline coverage seconds.
- **What happens:**
  - `callCodeunit` sets `noCoverage` only outside the baseline (`!this.inBaseline`). So under `alRunnerV3.coverage: "none"`
    every baseline call still asks al-runner for `coverage` + `perTestCoverage`;
  - batching (which needs coverage) stays on;
  - the config only skips the coverage index and the attribution.
- **Measured** (`/coord/handoff/PR-124/result.md`):
  - DO 735fb42's arm, A-off: 4.2 s of `coverageMs` in 12 requests;
  - its whole project, B-off: 53.1 s;
  - both as much as with coverage on.
  - About 5.3 µs per statement of the instrumented program per request.
- **For whom:** only a user who sets `"coverage": "none"`; the default is `"al-runner"`. Such a run already pays far more in
  its mutant phase (every mutant runs every test: 2,253 s against 44 s on the arm). So this is a small waste, not a
  verdict risk.
- **Before changing it:** check what else reads the baseline's coverage under `"none"`.
  - The Sleep rule's joins (`sleepJoinRefusal`, `sleepCallRefusal`) and R948's cross-check (`hitSet`) read the coverage
    document.
  - A baseline with no coverage must not turn either into an empty join that passes.
  - Batching would also go off (`batchingOn(coverage)`), and that may cost more than the coverage it saves.
