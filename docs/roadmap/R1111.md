Filed by coord PR-124 (lethal-preproc, 2026-11-17), found while measuring R1092's baseline coverage seconds.
- **What happens:**
  - `callCodeunit` sets `noCoverage` only outside the baseline (`!this.inBaseline`). So under `alRunnerV3.coverage: "none"`
    every baseline call still asks al-runner for `coverage` + `perTestCoverage`;
  - batching (which needs coverage) stays on;
  - the config only skips the coverage index and the attribution.
- **Measured** (`/coord/handoff/PR-124/result.md`):
  - DO 735fb42's arm, A-off: 4.2 s of `coverageMs` in 12 requests;
  - its whole project, B-off: 53.1 s;
  - both as much as with coverage on.
  - About 5.3 µs per statement of the instrumented program per request.
- **For whom:** only a user who sets `"coverage": "none"`; the default is `"al-runner"`. Such a run already pays far more in
  its mutant phase (every mutant runs every test: 2,253 s against 44 s on the arm). So this is a small waste, not a
  verdict risk.
- **Before changing it:** check what else reads the baseline's coverage under `"none"`.
  - The Sleep rule's joins (`sleepJoinRefusal`, `sleepCallRefusal`) and R948's cross-check (`hitSet`) read the coverage
    document.
  - A baseline with no coverage must not turn either into an empty join that passes.
  - Batching would also go off (`batchingOn(coverage)`), and that may cost more than the coverage it saves.
- Related: [[R1092]].

**Closed (coord PR-145, lethal-code, 2026-11-18), by ruling: the coverage stays.** The task was to stop asking only where nothing
reads the baseline's coverage. Under `"none"` (spec `docs/superpowers/specs/2026-11-18-pr145-drift-baseline-red-and-coverage-none.md`;
Opus build review):
1. **The daemon baseline's cross-check reads it** (`fillDaemonBaseline`, R948, R951). It runs whenever the transport is
   serve-entries, whatever the coverage mode. It compares each sampled codeunit's one-shot answer test by test, the raw coverage set
   (`hitSet`) included, and that set needs no coverage index. Without coverage the check would silently lose that part (both sides
   "unavailable") and still compare rows. So the coverage is evidence the daemon's state is clean.
2. **Baseline batching is gated on it** (PR-115, `batchingOn(coverage)`). Batching does not read coverage, but it runs only when
   coverage is asked. Without coverage the fill would send one request per codeunit, unless that gate were changed too.

- **Correction to the spec:** the reused-baseline re-check (PR-126) does NOT read it under `"none"`. No coverage index is built, so
  both sides are null and the comparison is empty. That is filed as [[R1123]].
- **The Sleep rule's joins** read the mutant calls' coverage, not the baseline's.
- **Who it affects:** besides a user who sets `"none"`, the CLI switches to `"none"` for files the coverage index has no rule for
  (R602, `al-runner-v3-coverage-off`).
- **Why it stays:** such a run's mutant phase dwarfs the 4.2-53.1 s measured here.
