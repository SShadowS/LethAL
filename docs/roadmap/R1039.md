Found by coord task PR-28 while checking whether family 5 covers the ledger's #7480 key. Evidence: `/coord/handoff/PR-28/`
(`causes.txt`, `nc/`, `repro/noclient/`, `issue-noclient-handlers.md`) and lethal-bugs' BC run
`/coord/handoff/PR-17/ws-run/result.md`. Related: [[R1024]] (family 5, no-client), [[R890]] (the Bank Deposits suite).

**What.** The ledger key "Business Central Server attempted to issue a client callback to show a confirmation dialog box" has
2,290 standing sightings in 6 stores (R1036's count), 2,080 of them from one store (R-911's Bank Deposits run).
- **What the sightings are:** mostly mutants that errored because their baseline had no green test, with this text as the first
  message.
- **The tests behind them:** 17 distinct tests raise it, all binding a `ConfirmHandler`, for example `PostBankDepositWithLink`,
  `[HandlerFunctions('GeneralJournalBatchesPageHandler,ConfirmHandler')]`.
- **Not all:** the same baselines hold other refusals too, so fixing this alone may not make them green.

**Measured on al-runner edge-5a58a0f16.** Family 5's no-client app, run with and without `--no-client`:
- **without `--no-client`:** a Confirm or StrMenu with its handler bound passes;
- **with `--no-client`:** both fail with BC's client-callback text.

So under `--no-client` al-runner never calls a bound handler.

**Measured on BC (lethal-bugs, bc2, BC 28.4 W1, 2026-11-15).** The 28 cells were run as the test project of a LethAL bcdev run
(the control app over OData, Test Runner - Mgt 130454): the web-service path, with no client.
- **BC calls the bound handler:** Confirm, StrMenu, Message, Notification and Hyperlink with a handler pass.
- **An unhandled Message or Hyperlink fails "Unhandled UI".**
- **A report run without a request-page handler passes.**

So al-runner under `--no-client` gives 9 wrong answers of 28 cells. It also answers four cells it refuses today (CurrentClientType
passes; Report.Run with a RequestPageHandler fails "handlers were not executed"; Report.RunRequestPage fails "cannot be used in
background or server sessions"; a ReportHandler passes).

**Corroborated.** R-908's BC run of the same Bank Deposits tests, on the bcdev path, failed at "Bank Deposit-Post (CodeUnit
1690)" line 109. Bank Deposit-Post (Yes/No) asks the Confirm before it runs 1690, so the bound handler had answered yes.

**Filed.** https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8154, with BC's table and an invented repro. Regression
entry `u8154-noclient-handlers` (run with `--no-client`): BC's measured answers; on edge-5a58a0f16 all four tests differ.
The ledger key now maps to #8154. #7480 upstream is a different shape (an unhandled Confirm in `OnClosePage`).

**For LethAL: keep `--no-client` (orchestrator's ruling, 2026-11-15).**
- **The fact:** without `--no-client`, al-runner already calls bound handlers and matches BC for these cells.
- **Why it stays:** R907 chose `--no-client` for fidelity to BC's web-service path, where LethAL runs tests on BC, and it is set
  per config, not globally.
- **The trade-off:** dropping it would fix these 9 known differences and bring back others that `--no-client` exists to avoid,
  which are not measured. So LethAL waits for #8154. Until then, a test that binds a Confirm, StrMenu, Message, Notification or
  Hyperlink handler fails on al-runner, and LethAL loses its coverage there.

**Impact on stored results (PR-38).** Pre-committed in `docs/superpowers/specs/2026-11-15-pr38-wrong-answer-impact-precommitment.md`;
evidence in `/coord/handoff/PR-38/` (`impact.tsv`, `impact-tests.tsv`).
- `noClient` is off by default. The stored runs that set it and hold any kill or green baseline are four: R-911's VAT Group,
  Bank Deposits and Payment Practices runs, and R-907's Payment Practices run. The others (PR-05's and PR-15's reruns 7 and 8,
  R-975's sweep and R-986's tail runs) hold only `error` mutants and no kill.
- In them, 43 tests bind a Confirm, StrMenu, Message, SendNotification, RecallNotification or Hyperlink handler: VAT Group 12,
  Bank Deposits 25, Payment Practices 3 in each run.
- **Every one of the 43 is red in its stored baseline** (fail or error), so no stored kill rests on them: 0 of 17, 0 of 0, 0 of 311
  and 0 of 6 kills. Not material in stored results, so no label is proposed. The pre-committed prediction (material in at least
  one run) was wrong.
- **It becomes material** if a `noClient` run's baseline goes green on such tests.

**To close:** #8154 fixed upstream (the regression entry flips).
