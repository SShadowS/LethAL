**What the key is.** `astSubtreeHash | codeunit | procedure | operator | major`. [[R166]] added the
procedure name because byte-identical shapes in different procedures collided. Inside one procedure
they still do, and on real code they do constantly: every `true` literal in a procedure hashes the
same, so every `flip-boolean-literal` mutant in it shares one key; the same for every `X := false`
that `remove-assignment` claims, and for repeated call shapes.

**Measured, one codeunit, one run.**

- `resume-reusing-run`: *"15 identity key(s) matched more than one prior mutant and will be
  re-executed (a colliding key cannot say which verdict was whose)"*. Those mutants were re-run on
  every one of twelve resumes, on top of [[R192]]'s fixed cost.
- `mutant-skipped-stranded`: two genuine hangs and one socket drop produced **12 stranded** mutants
  in the progress line, because a stranded key excludes every mutant that shares it. The operator
  read the source and confirmed the over-exclusion by hand (*"its key now also excludes the other
  boolean-literal flips in that procedure"*, *"like the AllMatch reset on line 79"*). Those are
  reported as unmeasured with no way to run them short of `--retry-stranded`, which re-runs the
  real hang too.

**Why it matters beyond cost.** A per-mutant baseline (`campaign freeze` / `compare`) is keyed the
same way. Two twins in one procedure whose verdicts differ collapse into one key, and a swap of
their verdicts is invisible to `diffMutants`. R166's proof that its change was a pure relabelling
does not cover this case because the fixtures have no in-procedure twins with different verdicts.

**The fix shape.** Add a discriminator that is stable under edits elsewhere: the ordinal of this
key within its procedure (first twin 0, second 1) is the obvious one, and it changes only when a
twin is inserted before it, which is the same edit that moves a line number. It must land as a
relabelling with the same proof R166 gave, and every committed baseline re-recorded in one commit.

## OUTCOME, 2026-09-02

Landed as pre-committed in `docs/superpowers/specs/2026-09-02-r193-r197-relabelling-precommitment.md`.
The ordinal is assigned over the whole manifest by `assignIdentityOrdinals` (schemata) in
(file, start offset, mutant id) order; `identityKeyOf` reads it; `serializeKey` appends `|n` only
for `n > 0`. R166's objection to an ordinal was to REPORT order, and this is source order, which
the key's own doc comment now says. Persisted as `identity_ordinal` (NULL on a pre-R193 row, read
as 0, so an old database's twins still collide and re-run, the cheap direction), carried by
`--resume`, present on the report as optional `identityOrdinal` (schema regenerated, no bump), and
appended by `mutant-equality.ts`'s gate key. `buildResumeIndex` on two twin rows now yields two
carryable keys and a strand on one excludes only that one, pinned by test.

Live: tables 299/63/15 with its 6 colliding keys split over 12 mutants and 0 verdict changes;
bcdev and al-runner byte-identical. Full suite 2683.
