**Found 2026-10-08 by R-508's adversarial plan review (I1), by reading the code and one offline measurement. Not
verified live.** A false-kill risk. Not fixed by [[R508]].

**What.** When design §G's attestation gate fires (`scoreBatch`: an authoritative batch that contributed work but
never earned a clean attestation), it calls `store.invalidateBatch` and latches. `invalidateBatch` rewrites the
batch's mutant rows to `error`, but it does not touch `baseline_snapshots`. The batch's baseline was recorded
(`recordBaselineSnapshot`) before the mutant phase, so a later `--resume` whose batch has the same `batch_hash` and
test-app hash reuses it through `findBaselineSnapshot` (R192), and skips re-running the baseline.

**Why it can be a false kill.** The gate fires because no covered run proved the deployed binary was the
instrumented one. The baseline was measured against that same unproven binary. A snapshot measured against the
wrong binary can record test T as green when T is red on the real one. On resume, T is then sent as a covering
test of a mutant, fails for a reason that has nothing to do with the mutant, and scores a kill.

**Why R508 did not fix it.** R508 drops the snapshot on the lease-lost path only, through a separate
`dropBaselineSnapshot`. Dropping it inside `invalidateBatch` (the attestation path too) was measured on 2026-10-08
by adding `dropBaselineSnapshot` beside the attestation gate's `invalidateBatch` call. Five existing tests go red
(the review counted four):

- `runSession --resume (R47) > R192 (second half): a batch with work left is deployed but its baseline is NOT re-run when nothing it measured changed`
- `C02-04 characterization > R192: the resumed run reuses batch 1's baseline snapshot`
- `C02-04 characterization > R272: a reused baseline's durations never reach the report's testMethods`
- `R354: no verdict crosses a coverage-mode change > a resumed procedure run never reuses a newer none run's baseline snapshot`
- `R354: no verdict crosses a coverage-mode change > a resumed none run never reuses a newer procedure run's baseline snapshot`

The cost is also R192's main case: a resume after a hang (or any latch) at the start of a batch, which is exactly
the run in which the attestation gate fires before any covered run attests, would re-run that batch's baseline.

**To close.** Decide whether an unattested batch's baseline is trustworthy enough to reuse. If not: drop the
snapshot beside the gate's `invalidateBatch` call, rewrite the five tests above so their fixtures attest (or so
they assert the re-run), and pin both directions (an unattested batch's snapshot is not reused; an attested one
still is), red-checked. If it is: write down why in `findBaselineSnapshot`'s doc comment and close with a ruling.

**Fixed by R-512 (plan r3, `/coord/handoff/R-512/plan.md`).** Neither of the two options above: the gate is
unchanged, and the snapshot is not dropped. The gate cannot tell two states apart. A hang at batch start (no covered
run answered) is no evidence about the binary, so R192 keeps reusing that snapshot and the five tests above are
unchanged. An answer with `attestation.observedAny === false` before any clean attestation IS evidence of a wrong or
stale binary. At that first answer the snapshot IN USE (the reused one, else the run's own) is marked in a new
`suspect_snapshots` table, synchronously, before the mutant's `record()`; `findBaselineSnapshot` never lends a
marked snapshot. All four places an answer is read feed it (`feedAttestation`: the covering run, the
kill-confirmation rerun, and both `confirmWarm` sites). Writing it at the answer, not at the gate, also covers a
batch that reused another run's snapshot (it records none of its own), a throw before the gate, and a crash or
Ctrl-C. The mark is cleared on the batch's first clean attestation, the same reading the gate already applies to a
batch with mixed answers (coverage over-approximation, not a wrong binary). The mark is owner-scoped: only the run
whose insert created it may clear it (`marked_by_run`), so two concurrent resumes of the same snapshot cannot clear
each other's mark.

- `identityMismatch` is not used as evidence. The transport maps a mismatch to an `error` outcome with NO
  attestation, and `RunMutantMany` hard-codes it false, so it never reaches the orchestrator as an attestation.
  `observedAny: false` is the only shape that does.
- Not handled: a container that changes from wrong to right mid-batch would clear the mark (nothing in LethAL
  detects a mid-run republish). And a multi-service-tier environment, where one tier answers clean and another
  unattested in the same batch: the clean answer clears the mark (and passes the gate today), although some
  answers came from a wrong binary.
- Not a false kill, and left open: after a crash or throw before the gate, the batch's `survived` rows recorded from
  unattested answers are still carried by `--resume`, because the gate never rewrote them. That hides kills.
- The wider risk, any reused snapshot whose test has gone slow or red since, is [[R514]].
