section: "correctness-risks"

What IS measured, and it is worth stating first because it is easy to over-read: test writes made
under LethAL's fenced runs **do roll back**. `fixtures/sandbox-data-tests/src/DataTests.Codeunit.al`
records the measurement (R32 verification, 2026-07-27) — four fixture tables held **0 rows in both
companies after 432 fenced runs** — and it was written to correct an earlier comment that had
claimed the opposite.

What is NOT measured is the **granularity**. "Nothing persisted after 432 runs" is equally
consistent with:

- **per TEST** — the runner rolls back after each `[Test]` procedure, so test 5 cannot see rows test
  1 inserted; and
- **per RUN** — every test in a codeunit shares one transaction that is rolled back at the end, so
  test 5 sees everything tests 1 through 4 wrote.

Every fixture in this repository is written to be correct either way: the seeding helpers are
idempotent by construction (`if Get then Delete` before `Insert`, `ClearRelated` before
`AddRelated`), and the arms that assert counts reseed deterministically first. That is good practice
and it is also why none of them can tell the two models apart. The one place the distinction is
argued about — `CommittedWriteSurvivesFailure`'s `Commit()` for a "durable clean start" — is about
rows left by an earlier RUN, not by an earlier test.

**Why it matters.** A future fixture that asserts a count over a shared table, or any test whose
meaning depends on being the only writer, would be correct under one model and quietly wrong under
the other — and "quietly" is the problem, because the failure looks like a mutant verdict rather
than a fixture defect.

It nearly bit immediately. The gift card demo (`examples/gift-card`) rests entirely on one mutant
surviving: deleting the `SetRange` in `GetBalance` is invisible **only while one card's entries are
the only entries in the table**. Under per-RUN rollback, four earlier tests' entries would still be
there when `RedeemReducesBalance` runs, the unfiltered sum would not equal 60, and the planted
survivor would be killed — on stage, at Directions EMEA, for a reason that has nothing to do with
the point being made.

That was handled by making the demo agnostic like everything else here: a `ClearAll()` at the top of
every test. The row stays open because the underlying question is still unanswered and the next
fixture author has no measurement to consult.

**What closes this:** a probe that inserts a row in one `[Test]` and reads for it in a later one on
the same fenced run, against a real container, recorded in `docs/measurements/README.md`. Cheap, and
it turns a habit into a fact. `scripts/` already has the shape for this kind of throwaway probe
(`r132-assert-probe`, `r141-filter-probe`).

Evidence: `fixtures/sandbox-data-tests/src/DataTests.Codeunit.al` lines 37-43 (the measurement) and
530-553 (the commit case), the idempotent helpers at the foot of that file, and
`docs/superpowers/specs/2026-08-16-gift-card-demo-precommitment.md` §Verification, which is where
the gap was noticed.
