**This row was wrong and is kept as a correction rather than deleted.**

## What it claimed

That the repository measures test writes rolling back
(`fixtures/sandbox-data-tests`, R32 verification: four tables held 0 rows in both companies after 432
fenced runs) but does not measure the GRANULARITY — per `[Test]` procedure, or per run — and that a
fixture depending on the difference would be silently wrong. The gift card demo was said to depend on
it, because deleting the `SetRange` in `GetBalance` is invisible only while one card's entries are
the only entries present.

## Why it is wrong

Three reasons, any one of which is sufficient. Two were already in this repository; the third is
Microsoft's own documentation.

**0. The transaction boundary is the TEST METHOD, by definition.** The
[TransactionModel attribute](https://learn.microsoft.com/en-us/dynamics365/business-central/dev-itpro/developer/attributes/devenv-transactionmodel-attribute)
applies to a **method**, and describes "whether transactions are rolled back **at the end of a test
method**". Under `AutoRollback`: "The test method starts a transaction ... After the test method is
completed, the transaction is rolled back and the database is returned to its initial state." The
demo's tests declare no `TransactionModel`, so they take the platform default, which is
`AutoRollback` — the behaviour this repository has already measured (0 rows after 432 runs) and the
one the control app names. There is no model in which one test method's writes are visible to the
next unless a test explicitly opts out with `AutoCommit` or `None`, or calls `Commit()` — and under
`AutoRollback` a `Commit()` is an error, not a leak.

**1. Isolation is defined at procedure level and enforced by the server.** The platform test runner
rolls back after each test method; that is the NST's behaviour, not a property of how a suite is
written. `extensions/lethal-control/src/RunMethod.Codeunit.al` states it in the doc comment that
explains why the fence uses `Codeunit.Run` instead of a `[TryFunction]`:

> `Test Suite Mgt.RunAllTests` drives the platform test runner, whose **per-test isolation** and
> result persistence commit between methods

**2. LethAL runs ONE method per invocation, so there is no multi-test run for a transaction to
span.** `RunOneMethod` builds a single-method `AL Test Suite` per call, and phase 2 wraps exactly
that. Even if per-run isolation were the model, a "run" here contains one test.

So the question this row asked cannot arise on this execution path. The measurement it asked for —
insert in one `[Test]`, read in a later one on the same fenced run — would be measuring a shape
LethAL never produces.

## What was done because of it, and undone

The demo's test suite briefly gained a `ClearAll()` at the top of every test as a hedge. That has
been reverted: it defended against a risk that does not exist, and its comment asserted a platform
uncertainty that is not real — which is precisely the failure mode
`fixtures/sandbox-data-tests` line 37 already documents ("a fixture comment asserting the wrong
platform behaviour is how the next person builds on a false premise"). The suite is back to eight
tests that each issue one card, which is also the more honest demo: an ordinary suite, not a
defensively-written one.

The prediction it was meant to protect — the `remove-setrange` mutant in `GetBalance` SURVIVES —
is unchanged, and now rests on per-test isolation being what the platform does, which is the
correct reason.
