**Filed 2026-10-25 from coord task R-798.** Related: [[R790]], [[R797]]. Measurement: `/coord/handoff/R-798/measure.md`.

**Problem.** D1's deploy grew from 7.6 s to about 10.9 s with R790. Ranked causes: (1) alc runs 1.5 to 2 s slower beside
the speculative al-runner call (they compete for CPU); (2) about 1 s more work before alc starts (the `alc-src` copy 0.54 s,
the sync `boundKey` 0.26 s).

**Built.**
- **A. The speculative call is niced.** Its argv gets a `nice -n 19` prefix (`Bun.which("nice")`; not on Windows; seam
  `seams.niceBinary`), so every thread and child of al-runner starts niced. The live calls' argv is unchanged. Without
  `nice`, the fallback is `os.setPriority(pid, 19)` right after the spawn (`SpawnFn` gained `opts.onStart(pid)`; seam
  `seams.setPriority`), best effort. A failure there is caught and noted once (`al-runner-v3-speculative-nice-failed`); it
  never fails the run. The lane-trace expected JSON records the speculative argv and was updated on purpose (its helper pins
  `niceBinary` to `nice`).
- **E. Reorder.** `deploy()` now: stage, cached alc writes, the `alc-src` copy, START alc (its spawn runs in the
  synchronous part of the call), then `boundKey` ("before"), then the speculative spawn. alc's inputs are complete before it
  starts; the copy and the `fileStates` list are taken first. No hardlinks (alc rewrites `Translations/*.g.xlf` in place);
  no hash reuse (it would weaken the deps guard).
- **Counters.** `entriesStats()` has `speculativeKept` and `speculativeDropped`. Dropped = timed out, crashed, undecodable,
  too slow, spawn failed, a failure inside the speculation (every codeunit), the bound keys differing (the whole set), or a
  kept call asked for at another stop or coverage flag (moved from kept to dropped). A kept call never asked for stays kept.
  A rising `speculativeDropped` after nice would show the saving shrinking. Both are in `close()`'s serve-entries line and
  in `scripts/v3-timing.ts`'s table ("spec kept / dropped").

**Guards, still true.**
- The "before" key is taken before any call reads the batch (the call is spawned after `boundKey`).
- alc compiles the copy, never the batch, so `boundKey` reading the batch while alc runs sees no alc write. A copy-back that
  lands between the "before" key and the end changes the "after" key or the proof, and nothing is served (R790 c).
- The error path is unchanged: a rejected or unstartable alc aborts the calls, waits for them, throws the same error.

**Can a niced call change a verdict? No.** The only decision that reads its speed is the "too slow, run live" rule. A slower
call can only be dropped (live run) or kept; the served rows are the same bytes either way.

**Do durations come from CPU time or wall clock? Wall clock.** A budget's `durationMs` is LethAL's wall time for the whole
call (`call.wallMs` in `v3RowVerdict`); al-runner's own per-test figure goes only to `measuredDurationMs`. So a niced call
can read longer. It cannot move a budget: a call is kept only when `2 x wallMs < floor` and `2 x row.durationMs < floor`
(floor default 180 s, so wall under 90 s), and a budget is `max(2 x duration, floor)`, which is then the floor either way.
Edge case: `recordBaselineSnapshot` stores the (possibly inflated, still under floor/2) durations; a later `--resume` under
a LOWER floor could derive a budget from them. Not measured; a niced call under a lowered floor is the only path.

**To close.** Full v3 gate on the head (per mutant), a timing A/B back to back (D1 and gc, repeat 3) with
`speculativeKept` / `speculativeDropped` printed, then set `status` to `done (<commit>)`. A `LETHAL_DEPLOY_TRACE` per-step
timer was not added.
