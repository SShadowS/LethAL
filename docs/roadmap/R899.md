**What.** On `bc2`, 2026-11-09 22:28Z, at `lethal/r894` d8445257 (R-894's final round), `itest:tables` failed with `GateWarningsMismatchError`: an extra `lost-ack-unreadable`. The message: `BandCountsFromLow: unreadable answer from RunMutant (RunMutant failed: HTTP 500 — BC's body:` followed by BC's error JSON (first read here as empty; the trace below quotes it). The gate was right to refuse: no mutant row was compared. Log: `/coord/handoff/R-894/final/bc2/tables.log`. Related: [[R852]] (the same family, `lease-renew-unanswered`), [[R194]].

**What followed.** The next four gates on the same server could not get a lease:
- chunked: `operation-busy`;
- harden: `operation-orphaned` (opAttemptId a123);
- lend and hang: `container-needs-recycle`, because the orphaned marker did not change between two tries.

So a RunMutant whose answer was lost left a server-side operation that never ended, and only a recycle cleared it. kraken recycled bc2 (SQL, then BC). Setup and `lethal doctor` then passed, with control 1.0.0.25.

**What was measured around it.**
- One hour earlier, on the same server and the same code, all six records and confirms passed, `tables` included (`/coord/handoff/R-894/bc2/`).
- After the failure, the same five gates passed on `bc3` at the same head (`/coord/handoff/R-894/final/bc3/`).
- R-894's change only alters which mutants are generated, and the fixtures' gate sets did not move. So the code under test is not a known cause.

**Not known.** Why BC answered 500 with an empty body. Whether the reconcile (`reconcileFencedLostAck`) could end the orphaned operation instead of leaving it. The R852 rule holds: if it recurs, read the server's event log for that minute.

**To close.** Explain it if it recurs. Or decide whether a lost ack that leaves an orphaned operation should stop the session with a named `container-needs-recycle` at once, instead of letting the next gate find it.

## Traced offline (coord task R-900, 2026-11-10)

**The body was not empty.** The full warning in the log reads: `RunMutant failed: HTTP 500 — BC's body:
"{"error":{"code":"Unknown","message":"Failed to compare two elements in the array. CorrelationId: eb49b2d3-..."}}"; answer
readback: the server holds no committed answer for a123/89480 (it holds a122/89479)`. So BC raised a .NET sort-comparer exception
("Failed to compare two elements in the array") while it handled RunMutant attempt `a123`, and no answer for it was committed. The
correlation id is the key to that minute's event log on bc2 (R852's rule).

**What the code did, step by step (`runFenced`, `LeaseSession.reconcileLostAck`).**
1. The answer was unreadable, so `lost-ack-unreadable` was emitted and the lost ack reconciled.
2. The marker named our own attempt (`opKind` run, `a123`, opSeq 89480): the control app's phase 1 had claimed it and committed before
   the exception, and phase 3, which ends the operation, never ran.
3. "Ours" means "it may still be executing AL", so the reconcile polled about 8 s (`OP_POLL_ATTEMPTS`) for it to clear. It did not,
   so the outcome was `unresolved`, and the session quarantined and stopped. That fits the timing: the operation started at 22:28:24
   and the gate ended at 22:28:33.
4. The next gates met the same marker at `AcquireLease` (`operation-busy`, then `operation-orphaned`, then `container-needs-recycle`
   after two unchanged reads), as designed.

**So the reconcile did not create the orphan, and behaved as designed.** BC's exception killed the request between the claim and
the end of the operation. By design, the reconcile never calls `RecoverOp`: an unreadable answer cannot prove that the AL code
stopped, and clearing a marker over a still-running operation is the overlap that design §5 closes.

**What could end it.** This answer was not unreadable in that sense: an HTTP 500 that carries BC's own error JSON is a terminal error
from the service tier. If that proves no AL of the attempt is still running, then for our own attempt only (kind, attempt id and seq
all ours), after the poll fails, `RecoverOp` could clear the marker. The mutant would be scored `error` (never killed), and the
session could go on instead of condemning the tier. That is a claim about BC, so it is not built.

**The measurement that would settle it.** On a leased bc server that can be recycled:
1. publish a probe whose RunMutant path raises an unhandled .NET exception after phase 1;
2. confirm the 500 with BC's error JSON, and that the marker stays "run, ours";
3. read whether any session of that attempt is still alive (the server's active sessions);
4. call `RecoverOp` for that attempt, then confirm that the next `RunMutant` runs clean and that `lethal doctor` passes.
If no session survives the 500 in every case, add the scoped `RecoverOp` with a fake-server test, red both ways, and a live leg.
Until then the quarantine stays the safe answer. Separately, the cause of the sort-comparer exception needs the event log for
correlation id eb49b2d3 (bc2, 2026-11-09 22:28Z); it is gone after the recycle, so it waits for a recurrence.
