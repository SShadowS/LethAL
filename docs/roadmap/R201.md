**Measured 2026-09-02, Document Output Templates slice, hosted DemoPortal sandbox.** Mutant M0023
is `remove-assignment` on `CriterionIndex += 1`, a loop counter, so it never terminates. Without
`--stop-hung-sessions` (opt-in) the run quarantines at the 180 s budget and the server keeps the
op marker; that part is R53 working as designed. On `--resume` the mutant is skipped and
re-recorded as `error` with `STRANDED_SKIP_NOTE` ("not re-run on resume: ..."). `resolveResume`
reads ONLY the latest run's rows, and that skip note did not start with `STRANDED_NOTE_PREFIX`
(`quarantined: `), so `buildResumeIndex` saw an ordinary retryable `error`, and the NEXT resume
re-ran the hang: another 180 s, another quarantine, another stranded lease.

The first field run (the Support session, morning of 2026-09-02) hit exactly this and wrote a
`fixup-stranded.py` that rewrote the note in the scratch database after every iteration, with
the comment "LethAL marks a mutant it skipped on resume with a note that does not start with its
own stranded prefix, so the NEXT resume re-runs it". That is a defect report written as a
workaround; nobody filed it. Run 2 of the same slice (this session, evening) reproduced it with
no workaround in place: iteration 1 stranded on M0023, and a loop without the fixup would have
re-run it on iteration 3.

**Fix.** The skip note now lives in `resume.ts` beside `STRANDED_NOTE_PREFIX` and `isStrandedNote`
returns true for it, so "a row that stranded the tier" and "a row skipped because a prior run
stranded the tier" are both stranded, and the skip is sticky for as long as `--retry-stranded` is
not given. The two orchestrator sites that write it import the one constant. Red-checked: with
the detector clause reverted, the new test in `resume.test.ts` fails and nothing else does.

**Not changed.** The stranded lease itself. A hang leaves the server's op marker in place and the
next `AcquireLease` gets `operation-orphaned` twice and refuses with `container-needs-recycle`;
`force-reset-lease` is the documented recovery and both field runs needed it before every resume
after a hang. `--stop-hung-sessions` (R53) is the way not to strand in the first place, and it is
opt-in because it ends BC sessions on the user's server. Whether `StopHungRun` takes effect on a
hosted sandbox is not measured ([[R53]] proved it on a container, `itest:hang`). The loop-exit
hazard that produced the hang is [[R196]].

**2026-09-28 note, same mechanism from a different cause.** [[R289]]'s P1 probe work on `itest:hang`
hit the same stranded-lease shape again, this time not from an AL hang but from the coding tool's
own memory reaper killing the LethAL gate process itself, mid-run, on Cronus28 (R289's P1 run 4).
Afterwards `lethal doctor` reported an orphaned lease and `lethal force-reset-lease` cleared it; no
container restart was needed that time and doctor went green right after.

Checked from the code, to answer plainly whether the next `lethal run` would recover on its own: it
depends on whether an OPERATION was in flight when the client died, not on the lease's token alone.
`ControlState.Codeunit.al`'s `TryAcquire` (`extensions/lethal-control/src`) checks the operation
marker FIRST: if `"Op Kind"` is not `none` and the lease is past its expiry plus grace, the acquire
is refused with reason `operation-orphaned`, never auto-granted. This is the case a killed gate or
a hang both leave behind, since neither one calls the matching `TryFinishRun`/`TryEndPublish` to
clear the marker. Only a lease that is EXPIRED AND IDLE (`"Op Kind" = none`) is reclaimed
automatically, by a fresh grant, on the very next acquire. `doctor.ts`'s `checkLease` does not
distinguish the two for its "not ok" verdict (a live token alone is enough to report "held"), but its
advice text is the same either way: run `force-reset-lease`. So automatic takeover already exists,
but only for the idle case; a mid-operation kill, whatever kills it, still needs the manual command.
This is a restatement of the paragraph above for a new trigger, not a new defect: documentation
only, no code change proposed.
