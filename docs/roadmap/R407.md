**Filed 2026-10-02 when R383 closed by ruling.** LethAL refuses al-runner coverage for the whole run
when any file declares more than one object (`alRunnerCoverageSupport` `supported: false`, the CLI
guard falls back to `"none"`, the index skips the file). The reason is no longer upstream #3713
(fixed), but a frame defect measured on `v2.12.0-main.c39ad5de`: al-runner compiles LethAL's
INSTRUMENTED bundle, finds the source project with the same app id, labels coverage with the
SOURCE path, and reports a later object's line as (previous object's closing line in the SOURCE)
+ (distance in the INSTRUMENTED text). Evidence in `docs/roadmap/R383.md`.

**Upstream issue:** https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/5222 (posted
2026-10-02 at the owner's request). Re-measure when upstream answers or when the pinned al-runner build moves:
`packages/runner/tests/r383-real-frame.test.ts` holds the captured payloads and the fresh-app-id
control, so the same capture on a new build either matches the control (fixed) or the evidence
(not fixed).

**Already landed, as infrastructure (R383, `lethal/r383`):**
- `fileLineMapEntries` moves the base past every top-level object, indexed or not.
- `resolveFileLine` (`line-map.ts`) maps a file line to `(type, id, object line)` by position.
- Both transports resolve by position; the `--server` procedure rule (R318 renamed members first,
  lookup-unnamed lines keep `scope`, otherwise position wins with one warning).
- `buildAlRunnerCoverageIndex(dir, { admitMultiObjectFiles: true })` turns the admission on. Only
  tests pass it today.

**To close:** once al-runner reports every object in one frame, flip the default (the index
admits, `supported` stops answering the multi-object question, the CLI guard falls back on `#if`
files only), and re-run `itest:alrunner`'s multi-object legs against the FUTURE table,
`docs/superpowers/specs/2026-10-02-r383-multiobject-precommitment.md` (`bc2511ba`), which bcdev
already matched exactly (killed 6, survived 1, no-coverage 5). The legs today match the refusal
table, `docs/superpowers/specs/2026-10-02-r383-multiobject-refusal-precommitment.md`; moving them is
a re-freeze of `al-runner.multiobject.baseline.json` under R332. If upstream picks the
source-mapped answer (every object's own offset applied) rather than the compiled frame, LethAL
must resolve against the SOURCE, not the instrumented text, which is a different change.

## Built 2026-10-09 (`lethal/r407`, plan r3), not closed

The windows host still ran the pinned c39ad5de, so the default is NOT flipped unconditionally.
Instead (plan r1-r3 with three adversary rounds, `/coord/reviews/R-407-plan/`):

- **The frame probe** (`probeAlRunnerCoverageFrame`, `al-runner-frame-probe.ts`). A scratch layout
  under `<root>` (al-runner's cwd): `src/` (source target), `inst/active/` (the bundle) and
  `inst/batch-1/` (a batch sibling), all one app id with versions copied from the project's
  app.json, and `tests/` calling only `Probe B.Reached`. The pair file holds a TABLE with a trigger
  (Probe A), then a codeunit (Probe B), longer in the bundle than in the source. Admitted only when
  the test passes, every label is inside `inst/active/`, Probe A has no hit and Probe B's lines equal
  the MEASURED set (45, 46, 47, `packages/runner/tests/fixtures/r407-frame-probe/`). The label and
  the line set are the two independent oracles; "Probe A has no hit" only NAMES a refusal the line
  check also makes (any A hit is a line outside the set), so it is a naming refinement. Every other
  answer is a named refusal (`deadline`, `run-failed`, `test-not-passed`, `no-coverage`,
  `label-outside-bundle`, `first-object-hit`, `lines-differ`); an al-runner outcome never throws.
  One-shot sessions probe one-shot with the R147 pin (one `provisionOnce` on the test project);
  `--server` sessions probe through `AlRunnerServer`, unpinned.
- **Where it runs.** `applyAlRunnerCoverageGuard` (cli.ts), only when coverage is `"al-runner"` and
  `alRunnerCoverageSupport` lists a multi-object file. Admitted: coverage stays on and
  `buildBackend` hands `admitMultiObjectFiles` to the main backend and every pre-built worker (an
  `AlRunnerBackend` constructor field, never a config key: `AL_RUNNER_KEYS` refuses it). Refused:
  coverage `"none"` exactly as before. One warning line names the outcome and the build banner (no
  `SessionReport` field; `coverageMode` already records the effective mode). The `itest:alrunner`
  helper `runOnce` runs the same guard per leg transport and requires `admitted`.
- **Backstops** (`AlRunnerCoverageFrameError`, extends `Error`): a coverage index holding a
  multi-object file built without the admission, or before any `deploy()`
  (`AlRunnerBackend.coverageIndexOf`); a label for an admitted file outside the index's own
  deployed folder, resolved against LethAL's cwd for one-shot and absolute for `--server`, with no
  trailing-segment matching (`assertAdmittedLabel`); a `--server` scope its position contradicts in
  an admitted file (`alRunnerCoverageFromServer`). Single-object files are unchanged.
- **Limits of the `--server` scope backstop** (build review). It compares procedure NAMES only.
  Two objects in one file with a same-named member (two `OnRun` triggers, an `OnInsert` in a table
  and a tableextension) do not throw if a line shifts between them: a residual, like one-shot's.
  The other side: a reached statement whose `scope` al-runner leaves unnamed while its position
  names a procedure used to warn and now throws `AlRunnerCoverageFrameError` for an admitted file.
  If al-runner names table or field trigger scopes differently from `lineMap.lookup`, a run with an
  admitted multi-object file holding a reached trigger stops loudly. That is the safe direction (a
  stop, never a mis-score), and UNMEASURED: neither the probe nor the fixture reaches a trigger in an
  admitted file.
- **Deviation from plan r2's layout control.** r2 predicted that c39ad5de with only `src/` deleted
  would be admitted. It is not: c39ad5de then labels with the `inst/batch-1/` sibling. The working
  control deletes BOTH siblings (then admitted), and the src-only case is live proof that the label
  check alone catches a batch sibling. The orchestrator accepted the stronger control.
- **Measured (P4).** The production probe from the repo root: 43f76177 admitted on both transports;
  c39ad5de, built from source in a scratch tool path, refused on both (label `src/...`, Probe B
  reported 12 lines early, inside Probe A). Layout controls on c39ad5de: with only `src/` deleted it
  is STILL refused, because it then labels with the `inst/batch-1/` sibling (right lines, wrong
  label); with both siblings deleted it is admitted. A target `.app` in `tests/.alpackages` changes
  nothing. Cost on 43f76177: about 2 s provisioning + 2.7 s one-shot, or 7 s `--server`.
- **The gate.** `itest:alrunner`'s multi-object legs take the admission table (bc2511ba), adopted
  by `docs/superpowers/specs/2026-10-09-r407-multiobject-admission-precommitment.md`: 6 / 1 / 5,
  probe `admitted`. A third leg, `--server` + resource selector (the default user combination;
  `docs/superpowers/specs/2026-10-09-r407-resource-leg-addendum.md`), must equal the one-shot leg.
  `al-runner.multiobject.baseline.json` was re-recorded under R332: the five `Multi A.Never` and
  `Multi B.Unreached` rows go from survived to no-coverage, and nothing else changes. Of the gate's
  fixtures only `sandbox-multiobject` holds a multi-object file. Build log, red checks and timings:
  `/coord/handoff/R-407/build.md`.
- **The Windows host** pins c39ad5de, which lacks #5249. There the probe refuses, and the
  multi-object legs fail on the probe line, by name, until the owner moves the pin past #5249.
