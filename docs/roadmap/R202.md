**Measured 2026-09-03.** `scripts/r198-group-runner-probe/drive.ps1` E8 (second run) and
`drive-stop-race.ps1` (10 rounds): a 45 s bounded hang in a test method, ended from a second
session by `StopSession`. Twelve times the held request came back **HTTP 408** with "The session was
stopped by an AL StopSession call", which `isAlStopResponse` recognises and
`run-mutant-transport.ts` scores `timeout`. Once it came back **HTTP 400** with "Cannot establish a
connection to the SQL Server/Database", 3.9 s after the stop, and the session was just as dead
(its progress row never advanced, its inserted row was rolled back). Which error the stopped
thread hits first is a race inside the NST.

**Today's consequence.** `run-mutant-transport.ts` scores `timeout` only for `stopFired && 408 &&
isAlStopResponse`; any other non-2xx after the stop falls to `in-flight-unknown`. The orchestrator
reconciles: the stop tombstoned the op, so rule 1 says `completed` and retries ONCE as a fresh
attempt, which re-runs the hang, burns another budget, and ends in `result-lost` or a quarantine.
`itest:hang` pins the 408 path and has never seen the other.

**Since R-204b Part R (2026-10-06).** That retry is gone whenever our stop was not refused: a hang
need not recur (state- or timing-dependent), so the retry could also PASS and score a real timeout
`survived` (sol's review r1). The mutant is now `error` / `stop-outcome-unconfirmed` instead. The
two later holes in a "retry unless confirmed" rule (a lost stop reply, and the single path's 400
arriving before the stop's reply) are closed by the per-call stop state, settled before the retry
decision. The cost is that a test that really passed, whose answer was lost after a stop, now
reads `stop-outcome-unconfirmed` rather than `survived`; how often is unmeasured, and it is never
a kill.

**What must NOT fix it, twice refused.** "A confirmed stop plus ANY non-2xx in the grace window
scores `timeout`" was refused by the R198 revision-1 review: `stopped: true` means
`TryStopHungRun` reached `StopSession`, and its own comment says that proves nothing about the
session ending; a gateway 502 on a slow-but-passing method would become a false kill. "A confirmed
stop plus a progress row that has not advanced across two polls" was refused by the revision-2
review: a session still alive INSIDE the stopped method does not advance the row either, so "no
progress for 5 s" is what a dead session and a slow passing method look like identically. The
converse this rule needs (a row that has not advanced implies death) is false. The obvious
strengthening, asking the server whether the session is alive, is ruled out by `Lease.Table.al`'s
measurement that a web-service session cannot read `Active Session`.

**What would.** A discriminator that only BC can produce: measure whether the 400's body is an
NST error payload for OUR request (distinguishable from any gateway page), and whether the
occurrence needs a fresh publish. Until measured, `--stop-hung-sessions` keeps a ~1-in-34 chance
per hang of quarantining instead of scoring, and R198 lands without touching this path.

## Closed 2026-10-24 by ruling (coord task R-271, lethal-code)

Traced by code on master `9a7486bb` (`/coord/handoff/R-271/r202-trace.md`), after R-204b Part R, R658, R665, R699
and R692:
- **Never a timeout:** `isAlStopResponse` (single `dispatch`, grouped `runManyOnce`) requires 408, so a 400 fails it
  whatever its body says.
- **Never a verdict from the stopped run:** R236b's readback (`recoverKeptAnswer`, `runManyScored`) accepts only a
  committed, identity-checked answer for exactly this op, and a confirmed stop and a kept answer cannot both exist:
  `TryStopHungRunAt` takes `Lease.LockTable`, needs the live run marker and tombstones the op, while
  `TryFinishRun` (phase 3) needs that same marker and `KeepAnswer` runs only after it. An answer found therefore
  means our stop did not end that run, and scoring it is the run's own result.
- **No passing retry:** `stopIsRetrySafe` (`runFenced`, `runFencedMany`) retries only when every stop was refused,
  which never called `StopSession`.
- **Every path ends `stranded` with a quarantine:** single and grouped (`stop-outcome-unconfirmed`, then
  `classifyNonVerdictStep`'s R665 branch); the cold confirm and `confirmWarm`; R577's `reproduceKill`. Serve-entries
  does not apply (al-runner v3, no BC session). A possibly-live session cannot record a result (phase 3 refused
  `op-stopped`), and `quarantineInFlight` latches the session unsafe.
- R692's body text and the `overran` advice read this case correctly (the budget did run out before the stop).

What remains is the cost the row was filed for (about 1 in 34 stops quarantines the tier instead of scoring the
mutant), not a correctness risk. Scoring that 400 would need a discriminator only BC can give, measured live; two
weaker rules were refused (above). Not filed separately: a measurement would change nothing the client may do.
