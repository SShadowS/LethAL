Filed by coord PR-103 (lethal-code, 2026-11-17), as the follow-up of [[R1100]]. That item's corrected diagnosis: a request's
own growth from its start is small and flat on DO, p50 0.12 GiB at any entry count. The large `g` R987 divides by the entry
count is retained daemon memory.

**The outline.** A request is bounded by (the target daemon's current RSS - its floor) + its own growth. The own growth is a
max-only per-entry cost measured from START, never from the floor. Sized that way, it can pack far more entries without
over-charging. Before anything relies on a larger bound, three things must change with it, each with a red test. PR-103's
spec-adversary named them all:
- **R948's memory guard** reserves the request's bound in prefetch. Today it holds no reservation there and assumes 3 GiB
  (`MEMORY_CALL_ESTIMATE_BYTES`). Without this, two lanes each sending a request sized to 4 GiB can pass the guard together
  and push the container over `memory.max`.
- **PR-98's lane gate** charges max(the highest peak reading, the highest floor + the bound), not only the highest peak seen.
- **The `daemonMaxRssGb` recycle check** must cover a recycled daemon's first request. Today a first large request can
  switch the bound off for the session (`rssBoundOff`). The fix: budget per request <= `daemonMaxRssGb` - floor.

**Readings that count.** Only readings with a verified `VmHWM`, no timeout cut and no `runSelectedOnly`/`through` cut may lower
an estimate or grant step-up credit. Weak readings may only raise one.

**The proof needs:**
- the backtest's control (with the per-entry cost forced to 0, the miss count must rise);
- misses reported in bytes against the budget;
- a Contoso Coffee leg, where per-entry cost is real (R-972: 256 entries took a daemon to 21 GB);
- a lanes leg (`--workers 3`).

**Wait for:** the lazy-prove probe's data (PR-103's `proved` / `proveGrowth` fields) from a DO window. If the retained memory
is not from the proofs, the outline changes.

**The probe's data (DO t14, lethal-bugs, 2026-11-17; 3 lanes, head 3fe3bd1a; `/coord/handoff/R-984/t14.pr103.txt`).**
- **The readings.** 1,876 readings from 117 daemons; 280 had a lazy proof just before them.
- **Per-request growth.** The non-fresh per-request `proveGrowth` (n=164) is p50 0.01 GiB and p90 0.44 GiB.
- **The proofs explain the retained memory.** Per daemon, `daemonProveGrowth` at its largest `start - floor` reading, summed
  per lane, against the retained memory:
  - lane 0: 4.02 against 4.46 GiB (90%);
  - lane 1: 5.22 against 4.99 GiB (105%);
  - lane 2: 5.47 against 5.96 GiB (92%).
- **Long-lived daemons.** They retain 0.7-1.0 GiB after about 105 proved codeunits. Example: one daemon retained 1.03 GiB,
  with 0.83 GiB of proof growth over 104 proofs.
- **Fresh requests.** Their `proveGrowth` holds the first load (2.7-2.9 GiB). It is below the floor, as PR-103 predicted, and
  is left out.

So the lazy proofs are where R1100's retained memory comes from, and the outline above holds. A request's own cost is small,
and the daemon's retained memory is a per-daemon state that grows with the codeunits proved on it. A spec for this item can
also weigh the cheaper lever the data suggests: recycling a daemon after a number of proofs, or sizing by codeunits proved.
