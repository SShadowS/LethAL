**What.** Upstream added `entries` to `serve`'s `runTests` (aldevtools #5676, closing our #5635): a list of `{id, resources, test, excludeTests}` run one after another on ONE compile, one request load and one install baseline, each from the same post-install database, answered per entry (`"entry"` on each test line, an `entrySummary` per entry). With #5671 a changed resource file also reuses the compile. This is the run-time switch bcdev gets from its control app: LethAL's resource selector can send every mutant (plus its covering tests) of a batch in one request.

**Why it matters.** R-586's v1 backend is one-shot only (about 1.7 s per call on the CDO slice; bcdev 53-80 s for the whole slice). R-606 measured the mechanism (resource switch reused the compile, 2.2 ms vs 9.8 ms on sandbox-app) but could not measure a real app.

**Limits stated upstream.** With `entries`, the request's own `coverage`/`perTestCoverage` are an error (coverage per entry is not built), so the coverage pass stays separate; an install baseline that read a resource refuses an entry with `resources`.

**Upstream.** Filed 2026-10-22 from R-635's measurement on edge 57f1e4f98 (`/coord/handoff/R-635/measure.md`): a `test` array is silently ignored, so every test runs (https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5702); duplicate entry ids are accepted (https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5703); an entry that selects nothing answers total 0 with no warning (https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5704).

**To close.** After a tagged build carries #5671/#5676 and passes R632's update gate: a plan (one deep review) for a serve + entries transport in the v3 backend, with R612 (the v2-era close-on-notRun rule) resolved first; pre-commit per mutant against bcdev on sandbox-app, the table fixture and the CDO slice; measure wall time against bcdev.

## Done (R-635, head 5159e50e)

**What was built** (plan `docs/superpowers/plans/2026-10-22-r635-v3-serve-entries.md`, r3):

- **The option.** `alRunnerV3.transport` takes `"one-shot"` (the default, unchanged and pinned by test) or
  `"serve-entries"`, plus `alRunnerV3.secondEcho` (on by default).
- **The baseline** stays one-shot, inside an orchestrator bracket (`baselinePhase`). Every other run goes to a warm
  `serve` daemon as entries.
- **Each mutant is one group:** an echo test entry first, then one entry per covering codeunit. Every entry carries
  an explicit `active-mutant.txt` override. The echo reads the override and asks R222's resource selector whether it
  agrees, and must answer exactly `LETHAL-ECHO:<id>:true`.
- **The encoder and the decoder** (`al-runner-v3-entries.ts`):
  - The encoder refuses `test` arrays (#5702), duplicate ids (#5703), groups without an echo, and split groups.
  - The decoder credits rows only through the table of sent entries: ids in sent order, each row in its own
    codeunit, no row twice, counts equal per entry and in sum.
  - An entry that selects nothing is `rowMissing` (#5704).
- **A union warm-up per daemon.** It refuses by name when the backend holds no baseline rows
  (`-no-baseline-rows`), when the whole batch was refused (`-batch-refused`), when the warm-up disagrees with the
  one-shot baseline (`-warmup-disagrees`), and when it has a row R612 does not keep (`-warmup-dirty`).
- **Prefetch.** All covered mutants are sent once per mutant loop and consumed once, so R577's reproduction runs
  live.
- **R612's keep rule per entry,** with each group re-sent at most once. A lone group never stops the batch.
- **§5 coverage windows** for a pass under a mutant when the Sleep index is not empty: echo, coverage request,
  echo, and `NONE` restored in a `finally`.
- **Timers.** `v3CallDeadlineMs` is clamped and `LineReader`'s timer capped at 2^31-1 ms. A dropped prefetch
  request warns by name.
- **Harness.** `itest:alrunner-v3` takes `LETHAL_ITEST_V3_TRANSPORT`, `_SECOND_ECHO`, `_REPORT_DIR` and
  `_CONTROL_DIR`.
- **Red checks.** 105, every guard in each direction (`/coord/handoff/R-635/build.md`). Build reviews r1-r3 are in
  `/coord/reviews/R-635-build/`.
