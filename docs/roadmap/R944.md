Found by coord task R-932 (2026-11-12): Guided Experience on al-runner edge-42af5d384 (`/coord/handoff/R-932/guided.run.*`). Related:
upstream #7853 (the compile refusal itself), [[R586]].

**What happened.** al-runner refused the app with `AL0161` (#7853). LethAL's baseline then recorded each of the 104 tests as
`al-runner-v3 transport failure: v3 exited 3: ... COMPILE ERRORS`, the session ended "no green baseline tests" (exit 4), and every
mutant became an `error`. The cause is one sentence about the app, not 104 facts about tests; a reader of the report has to open a
test's message to find it.

**Wanted.** A compile refusal from al-runner (its `COMPILE ERRORS (exit 3)` with an `error AL....` line) stops the session once,
by name, before or at the first baseline call, quoting the compiler line (a file name and position, an error code and a symbol
name; no AL text beyond what alc's own message holds). Red both ways with a fake al-runner that exits 3 with a compile error.

**Built (coord R-933).** `AlRunnerV3CompileRefusedError` (`al-runner-v3-compile-refused`): an al-runner exit 3 that says
`COMPILE ERRORS (exit 3)` on a BASELINE one-shot call stops the session once, quoting each distinct `error AL....` line. On a
mutant call (a chunked or bisected batch builds its own artifact) the same refusal stays that batch's transport failure, so one
batch cannot stop the others. Red both ways in `al-runner-v3-backend.test.ts` (the baseline stops; a mutant call does not).
- **Limit, by design:** the serve transport has no such check. The baseline always runs one-shot, so a fresh session meets the
  refusal there; a session that reuses a stored baseline (`--resume`, a lend) and then meets a compile refusal on serve still
  records it per call, as before.
