Replace a `unary_expression` whose operator is `not` with its operand.

```al
if not Rec.IsEmpty() then CreateEntry();   // before
if Rec.IsEmpty() then CreateEntry();       // after
```

`negate-conditional` reaches a negation only when it wraps a COMPARISON. A `not` applied to a bare
call, identifier or member access is reached by nothing, which R159's census showed as
`unary_expression` 1,124 unclaimed and this row breaks down.

**Measured on `do-rel2/Cloud`**, by operand kind:

| operand | count |
| --- | ---: |
| `call_expression` (`not Rec.IsEmpty()`, `not Codeunit.Run(...)`) | 627 |
| `identifier` | 251 |
| `member_expression` | 172 |
| `parenthesized_expression` | 43 |
| `quoted_identifier` | 1 |
| unary minus, not this operator's business | 30 |

**1,093 `not` sites**, none claimed. The 43 parenthesized ones are where a comparison usually hides,
so refusing that operand kind cedes them to `negate-conditional` and still leaves 1,050.

**Why it compiles:** the operand is already Boolean or the `not` would not have compiled.

**The false kill is real and specific.** `if not Rec.Get(X) then Rec.Insert();` inverted inserts a
row that already exists and dies on a duplicate primary key with no test asserting anything. That is
the R138 class exactly, and the machinery exists: declare a `PlatformKillMechanism` and tag, or
refuse, when the guarded branch contains an `Insert`. Under-tagging is the unsafe direction, the
same asymmetry R143 records for `insertSkipCanRaise`.

Proposed by the Fable subagent 2026-08-19, which guessed 300 to 500 sites; measured it is roughly
double that.
