**Found 2026-10-05 by R464's final code review** (minors 2 and 3; review kept in the coord handoff
for R-464, not in the repo).

**What.** Two record scopes that `recordScopesAt` in `packages/engine/src/semantic/receiver.ts`
does not list, so the prefix proof behind `validate-to-assign`'s bare form never checks them:
1. **A reportextension's `add(X)`.** The base dataitem `X` behind it is not added as a scope
   (`types.ts` does treat `dataset_section` as one). If `X`'s table, from a dependency, has a field
   named like the added dataitem, the emitted `<dataitem>.F := V` names that field and does not
   compile.
2. **A namespace-qualified tableextension base** (`extends Microsoft.Sales.Customer`). The
   `mayHaveMember` and `extendsIt` checks compare the base name as written, so such an extension
   is skipped and its fields and procedures are not checked against the prefix. The worst case is
   the same: a mutant that does not compile.

**Why it is a gap, not a correctness risk.** Both cases fail at compile time, so they cost a site
(bisection drops the mutant); neither can produce a wrong verdict. Neither shape was measured in the
R464 corpora.

**Closing it.** Add the `add(X)` base dataitem to `recordScopesAt`; match a tableextension's base by
its last name segment (or through the symbol index's namespace resolution). Each with a red test,
then an exact site diff on BaseApp and CDO.

Related: R464, R477.
