**Nothing structurally couples `report.ts`'s `Caveat` union to the code that re-declares or reads it, and the one existing copy has already rotted twice.** Subsystem B turned `caveats` from `readonly string[]` into an 11-member `Caveat` union, so a typo at a push site is now a compile error (`TS2345`, verified by planting `"stale-tst-app"` at a real site). But two places sit outside that guarantee. (1) **`events.ts` declares `BaselineClassification` as an INDEPENDENT copy of three of those names**, under a doc comment asserting *"Not invented: these are the SAME identifiers `report.ts`'s own `caveats` array already pushes (`report.ts:918,924,930`)"* — a coupling nothing enforces, and the citation is now FALSE: `7449a89` moved those pushes to 883/889/895 before this branch existed, and subsystem B's own union block shifted them again to **901/907/913**, while lines 918/924/930 now point at the `runner-disagreement` push, mid-comment prose, and a closing brace. Fix: `Extract<Caveat, "tests-permission-refused" | "tests-testpage-unsupported" | "stale-test-app">`, which makes the coupling structural and the stale-line-number problem impossible to recur — strictly better than hand-correcting the citation, which would rot again on the next edit. `events.ts` already imports from `./report`, so this adds no dependency edge. (2) **`campaign-freeze.ts` and `campaign-anchors-run.ts` both do `JSON.parse(await readFile(...)) as SessionReport`** — a blind cast that would carry a corrupted or foreign caveat string straight past the union with no check, compile-time or runtime. Dormant today (measured: neither consumer reads `.validity.caveats`, and `report.ts`'s `renderConsole` is the only production reader, which never round-trips through JSON), and it is the generic weakness of the `JSON.parse(...) as T` pattern used throughout that file rather than a caveat-specific bug — but `lethal explain` reads a committed report off disk, which is exactly the consumer that would meet it first. Filed 2026-08-06 from subsystem B's Task 2 review.

**Closed 2026-08-07. Both halves resolved, and the row's own prescription for (1) turned out to be
the weaker of the two options.**

**(1) The coupling is now structural — but NOT via `Extract`.** The row proposed
`Extract<Caveat, "tests-permission-refused" | "tests-testpage-unsupported" | "stale-test-app">`.
That is worse than it looks: `Extract<Caveat, "typo">` is `never`, so a misspelling SILENTLY
NARROWS the resulting union instead of erroring — the same class of quiet loss this row exists to
close, wearing the fix's clothes. What shipped instead:

```ts
export const BASELINE_CLASSIFICATIONS = [ … ] as const satisfies readonly Caveat[];
export type BaselineClassification = (typeof BASELINE_CLASSIFICATIONS)[number];
```

Verified by planting `"stale-tst-app"`: `tsc` reports **TS2820 naming the member and suggesting the
correct spelling**, and three downstream sites (`orchestrator.ts`, `report-fold.ts`,
`events.test.ts`) fail too. `Extract` would have reported none of that.

**The array is the half that matters under `bun test`.** A `satisfies` clause is invisible to the
test runner — typecheck is a SEPARATE step in this repo (R115 found one such clause entirely inert
because its type was unimported), so a type-only fix would have left the guarantee unenforced by
the gate most sessions actually run. Two tests in `events.test.ts` now walk the exported array
against `CAVEAT_INTERPRETATIONS`'s own keys (the only runtime enumeration of `Caveat` there is),
plus a guard-the-guard pinning both sides non-empty. Red-checked: with `satisfies` REMOVED and the
typo planted — i.e. with the type-level half gone entirely — `bun test` still reddens.

**(2) needs no code, and the row's own worry is already answered.** The row named `lethal explain`
as "exactly the consumer that would meet it first". It already refuses:
`assertExplainableReport` checks every `validity.caveats` member against `KNOWN_CAVEATS` (derived
from `CAVEAT_INTERPRETATIONS`'s keys) and throws `MalformedReportError` naming both the bad value
and the closed set. There is already a test for it — and it plants `"stale-tst-app"`, this row's
own typo. So the `JSON.parse(...) as SessionReport` casts in `campaign-freeze.ts` and
`campaign-anchors-run.ts` stay as they are: both were measured not to read `.validity.caveats`, and
adding a second validator to a path that does not read the field would be unkeyed work that reads
as protection.
