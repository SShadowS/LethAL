**What.** `scripts/agentflow/gate-table.ts` decides which live legs a change must run from its
changed paths, over a fixed `Leg` union (`bcdev`, `lease`, `stale-publish`, `tables`, `chunked`,
`alrunner-v3`, `hang`, `coverage-differential`; R654 replaced the retired `alrunner` leg with `alrunner-v3`).
Its `LEG_CONTAINER` map types every leg's container as
`"agent-app" | "agent-data"` only, so a leg cannot be registered against Cronus28. `harden`
(C02-03), `verify` (C02-06), `testapp` (C02-05) and `agreement` (C02-08) all run only on Cronus28 and
so are absent from `LEGS`, `FULL_SET`, `LEG_ORDER` and `LEG_CONTAINER`, and from the orchestrator's
`tick.ts`, which reads that contract to decide what a change must run.

**Who hits it.** Anyone changing code these four gates would exercise: the orchestrator's automatic
leg selection cannot ask for any of them, so a change is either missed entirely or must be run by a
human remembering to do it by hand.

**Why left open here.** Widening `LEG_CONTAINER`'s type to name Cronus28 is an agentflow decision
with its own blast radius (how `tick.ts` schedules a container that is not one of the two agent
containers), unrelated to verify-agreement. C02-03's orchestrator ruling 3 asked C02-08 to register
`harden` in the gate table; the default in
`docs/superpowers/plans/2026-09-26-C02-08-verify-agreement-gate.md` (Open question 3) took that OUT
of scope and files it here instead, covering all four Cronus28 legs together.

**What would close it.** Widen `LEG_CONTAINER`'s value type to include a Cronus28 variant, add
`harden`, `verify`, `testapp` and `agreement` to `LEGS`/`FULL_SET`/`LEG_ORDER`, and update `tick.ts`
and any path rules that should select them.

**Built.** `harden`, `verify`, `testapp` and `agreement` are in `LEGS`, `FULL_SET`, `LEG_ORDER` and
`LEG_CONTAINER` (`scripts/agentflow/gate-table.ts`). The container value is a lease key that `tick.ts` only
groups by, so the type widened by one name: `agent-harden` for the legs that read `sandbox-harden`'s config
(`harden`, `agreement`); `verify` and `testapp` read `sandbox-app`'s, so `agent-app`. `tick.ts` needed no
change and no leg needs a receipt schema. `verify`, `testapp` and `agreement` emit one subleg, but `harden`
emits two, so `EXPECTED_SUBLEGS` names them (`HARDEN_SUBLEGS`); the same fix covers `chunked` and `hang`,
which had the same defect. The lists live in `packages/runner/itest/gate-sublegs.ts`, shared by the itests
and the table, and a test ties each itest to its entry. Path rules add legs
(harden fixtures and answer key; verify code, including `gaps.ts`, `closed-world.ts`, `assertion-screen.ts`,
`digest-inputs.ts` and `equivalence-marks.ts`; test-app publish; the agreement itest; and the
sandbox-app/sandbox-tests fixtures add `verify` and `testapp`). `cli.ts` is left out of the verify row on
purpose: cost, and the general runner row already selects the BC legs. All four are in
`FULL_SET`, so an unmatched path and the control app select them. They run after `coverage-differential` and
before `hang`, since verify, testapp and agreement swap a test app and can leave a stale one. Tests with a
red check per direction: `scripts/agentflow/gate-table.test.ts`.
