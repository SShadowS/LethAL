codeunit.
- Cells that write a real table count their own key range and never DeleteAll.
- Booleans are read through `Format(x, 0, 9)`. The two enum captions of `Info.Defaults` are the one exception, and an
  English-only answer.
- Two cells Commit. Their committed rows stay, so on BC they answer only on a fresh install.

**Join: 66 equal, 1 different.**
- `Assert.NoError` is an asserterror around a statement that raises nothing:
  - BC's test result reads "Microsoft.Dynamics.Nav.Types.Exceptions.NavNCLAssertErrorException: An error was expected
    inside an ASSERTERROR statement." followed by a .NET stack;
  - al-runner gives the message alone.
- **Not filed, and why:** the reason is a PREMISE, not a measurement. The premise is that this is only the test runner's
  rendering. AL could read the text through a nested asserterror (`asserterror H.ExpectNothing();` then
  `GetLastErrorText()`). That cell is the first follow-up below.
- LethAL itself reads this text: `killedByOf` in `packages/runner/src/verify.ts` calls a kill "assertion" on
  `NavNCLAssertErrorException`. That is safe while verify runs on bcdev only. On al-runner's bare text, such a kill would
  read "other".

**BC-measured facts worth knowing** (al-runner matches each):
- `HasCollectedErrors()` answers true with `GetCollectedErrors().Count()` 0, in a test with nothing collected. Two other
  fields read it, so they carry no information: the last field of `Collect.AndClear` and the second field of
  `Collect.Outside`. Whether this comes from the test runner's scope is not measured.
- A TryFunction cannot write to a real table at all on either runtime (the write is refused).
- AutoIncrement does not number a temporary table: the second insert fails at Id 0.

**Cells that stop before their target on BOTH runtimes**, so the named behaviour is unmeasured:
- `Try.InsertThenError` and `Try.InsertOk`: whether a try rolls back real writes. Both are refused before that.
- `Run.FailAfterWrite`: whether a failing Run rolls back an earlier write. The Run itself is refused, as in
  `Run.OkAfterWrite`, so these two cells measure the same rule.
- `Collect.KeepGoing`: "ET g1" is the answer whether or not execution continues after the error. `Collect.AndKeep`'s
  "Multiple errors ..." shows that it does continue.
- The two call-stack cells check only "non-empty".

**Measured since** (PR-488, family numbers-text on bc1, BC 28.4; both runtimes give the same answer in each):
