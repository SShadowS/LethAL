`/coord/handoff/R-951/full.*`). Related: [[R961]], [[R612]], [[R955]].

**What happened.** The daemon fill of R-948's baseline ran 3,564 s on DO's 112 test codeunits and the time budget stopped the session in
the baseline with 1 of 1,979 tests decided (nothing is served before the fill and its cross-check end). No drop, no OOM. The run's own
counters: `daemons 10, cached:false 43`, and 9 `serve-daemon-closed` events with reason `refusal`.
- **Restarts:** a refused row makes the daemon untrusted for the next request (R612), so it is closed and a new one started; DO
  refuses tests often (e.g. "FindSet on the Company table").
- **Uncached compiles:** al-runner's own summary said `cached: false` on 43 requests, more than one per daemon, so the daemon
  recompiled DO per request: about 32 s per codeunit request, the same as a fresh one-shot process. R-948's premise (one daemon
  compiles once and serves the suite cheaply) does not hold here.

**To find out (coord R-955, offline on an invented app).** Which of these makes a serve request uncached: the coverage flag, the request
shape (per-codeunit filter, sourcePaths), or the restart; and whether a refused row really needs a restart (R612's reason) or only the
next request's state. Then: fix the request LethAL sends (e.g. one request carrying the suite, which R-948's design left unmeasured),
narrow the restart, or report upstream with an invented repro.

**Meanwhile.** DO runs on the one-shot baseline with the memory guard (about 1.6 h for its baseline, measured in R-948's fallback).
