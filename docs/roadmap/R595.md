**Filed 2026-10-21 by coord task R-583** (lethal-code), from phase 1 of the bc-server addendum
(`docs/superpowers/specs/2026-10-21-r583-bc-servers-addendum.md`).

**What happened.** `itest:verify` ran on bc1 under master 209360d8.
- Step 1's verdicts are equal per mutant to `bcdev.baseline.json`.
- The gate then fails with `step 1: one gap G72826da4c976 (ClampPercent body)`. All four gaps exist, but none has
  the pinned id.
- Log: `/coord/handoff/R-583/gates/p1-verify-bc1.log`.

**Likely cause** (read from history, not measured live). R276 changed `gapIdOf` on 2026-10-06, and nobody re-pinned
`PREDICTED_GAPS` or `OVER_BUDGET_GAP_ID` in `packages/runner/itest/verify.itest.ts`. The last live pass was R-385,
on 2026-10-04, before that change. A gap id comes only from the source, so the gate fails on master on any server.
This is not a verdict difference.

**To close.**
1. Confirm the cause by computing the four gap ids offline with today's `gapIdOf`.
2. Pre-commit the new ids.
3. Re-pin them in the itest, with the reason in a comment.
4. Re-run `itest:verify` on a bc server.
5. Add a unit test that fails when `gapIdOf`'s output for a pinned fixture span changes, so the next such change
   cannot pass offline unnoticed.
