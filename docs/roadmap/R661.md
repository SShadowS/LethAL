**Filed 2026-10-22 by lethal-bugs during R-658** (the plan's deep review, M10; orchestrator ruling 4).

**What.** R658 wires LethAL Control's stop for every unmutated run that goes through `BcDevMcpBackend.runViaTransport`
and `runMany`. Measured on bc3 (`docs/measurements/r658/` on `lethal/r658`):
- a stopped baseline test (busy loop or `Sleep`) gets BC's AL-stop 408 within about 75 ms;
- an abandoned one strands the op marker (row D2).

A bcdev session with `coverageMode` `"procedure"` (the legacy hub) or `"line"` collects its baseline through the
bc-dev-mcp hub, not through the fenced RunMutant transport. So the stop hook R658 adds never reaches that baseline.

**Who hits it.** A user who sets one of those modes, and has a baseline test that hangs or runs past the budget.
`"procedure"` is due to be deleted (see `coverageMode`'s doc comment in `bcdev-backend.ts`).

**To close.** First measure what a hub-mode baseline overrun leaves on the server: is the marker stranded, and is the
session alive? Then one of:
- refuse an overrun by name in those modes;
- wire an equivalent stop;
- or close this by ruling, once `"procedure"` is deleted and `"line"` is shown not to strand.

Evidence: R658 (`docs/roadmap/R658.md`); R-658's plan review (`/coord/handoff/R-658/review-plan-r1-deep.md`, M10).

**Closed 2026-10-23 by ruling (R-661, lethal-bugs): measured on bc3, no code change.** Pre-commitment
`docs/superpowers/specs/2026-10-23-r661-hub-baseline-overrun-probe-precommitment.md` (master 9a1f8999); readings
`docs/measurements/r661/`.
- **Measured:** the hang fixture's `SleepsPastTheBaselineBudget` (`Sleep(25000)`) through `BcDevMcpBackend.run`, with
  a 10 s budget, in `line` and in `procedure`.
  - Both answered `deadline-exceeded` / `in-flight-unknown` at about 10 s.
  - BC's test session was still listed at +12 s, while LethAL's bc-dev-mcp child held the hub open. It was gone at
    +16 s, before its own Sleep's end. The only event between those reads was the hub close, so the close most
    likely ended it (an inference, not a direct reading).
  - LethAL Control's op marker did not move, and the next control-app acquire was granted.
  - So nothing was left once the hub connection closed, and a hub run strands no marker. That is decision row E.
- **Why that is enough:**
  - The overrun already fails safe: `runBaselineTest` reads `in-flight-unknown` as a strand, quarantines the tier,
    and stops the session.
  - The session's close ends the hub connection (`cli.ts` calls `backend.close()` in a `finally`).
  - The quarantine is conservative (the server is in fact clean), which is the safe direction.
- **Neither mode is worth a new stop path:**
  - `line` is not in the typed config (`"procedure" | "none" | "fenced"`), but nothing refuses it at runtime, so a
    hand-written value reaches the hub. It was measured and also fell in row E. Refusing an unknown value is filed as
    R681.
  - `procedure` is due for deletion after the first release (R059's ruling keeps it until then).
