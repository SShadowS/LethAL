Found by coord task R-882 (BC.History ServiceDeclaration on `bc5`, 2026-11-09). Evidence: `/coord/handoff/R-882/S3.stderr.txt` (round
2) and `owners-sd.ts` (the keyed reads below). Related: [[R847]] (the non-dependent clash check), [[R888]] (selector ids against
dependencies).

**What.** The run's selector ids were 5257-5259, inside the target's own id range. On bc5, codeunit 5257 belongs to Contoso Coffee
Demo Dataset, an installed app that does not depend on the target. BC refused the publish: "The application object of type
'CodeUnit' with the ID '5257' is defined in multiple apps". The run stopped with "Publish failed" and no LethAL hint.

**Why LethAL said nothing first.** R847's non-dependent check (`findNonDependentLeads` in `object-clash.ts`) returns at once when
the target is not installed: "a first publish cannot strip". That is right for the harm R847 guards against (a strip), so nothing
was damaged. But the injected objects (`selectorId`, `controlId`, `tableId`) are LethAL's own choice, and the same keyed
`ObjectOwners` read would have named the clash before publishing. The refusal text already exists for the dependent case
(`object-clash.ts`: "set selectorIds in the config to ids no installed app declares").

**How common.** On a standard W1 CRONUS, Microsoft's demo-data apps fill much of the space: in Service Declaration's two ranges
(5010-5049, 5250-5259), codeunits 5011, 5017-5038 and 5250-5259 are owned by Base Application or a Contoso app. Only 5010 and
5039-5049 were free. A user who picks ids in their app's own range can hit this on the first run.

**Fix sketch.** On a first publish, read the three injected ids by key (`ObjectOwners`, one call) and refuse by name with the
existing selectorIds hint. Nothing else in the target needs it: BC's own refusal covers the target's real objects, and names both
apps.
