---
id: "R210"
title: "`resolveVarRef` keys a procedure's locals/parameters by NAME alone, so an overloaded procedure name resolves against the wrong overload's declarations"
status: "open, filed 2026-09-06, measured while categorising [[R196]] Task 3's `declinedUnresolved` sample"
section: "correctness-risks"
order: 922
---

**Measured, not inferred.** Sampling 30 `declinedUnresolved` sites per corpus (an in-loop assignment
whose target `resolveVarRef` could not resolve, `scripts/sample-declined-hang-capable.ts`), the
dominant cause on BOTH real corpora was a plain procedure-local variable, declared normally in a
`var` section, that `resolveVarRef` still answered `null` for. Direct probe against one such site
(`ctx.symbols.resolveProcedure(scopeKey, procName)`) showed why: the resolved `ProcedureSymbol`'s
`.locals` list did not contain the target's own declaration at all, even though the assignment sits
textually inside a procedure whose own `var` section plainly declares it.

**Cause.** AL permits several procedures with the SAME name in one object, distinguished only by
parameter list (a form of overloading BC's compiler accepts). `buildSymbolTable`
(`packages/engine/src/semantic/symbol-table.ts`) indexes `procedures` as
`Map<scopeKey, ProcedureSymbol[]>`, and `resolveProcedure` (used by `receiver.ts`'s `lookupVar`, in
its procedure-locals and parameters steps) resolves with `list.find((p) => p.name === procName)`,
by name alone, with no parameter-list or arity disambiguation, and no way to identify WHICH physical
declaration node a given call site sits inside. When an object declares the same procedure name more
than once, every call site inside the SECOND, THIRD, or later overload resolves its locals and
parameters against the FIRST-declared overload instead, silently. A variable declared only in the
correct overload's own `var` section (or parameter list) is therefore invisible to `resolveVarRef`
regardless of how ordinary or clearly in-scope it looks at the source level.

**Measured frequency.** Sampling 30 declined sites per corpus (stride-sampled across the whole
corpus, not clustered in one file) and checking whether each site's enclosing procedure name is
declared more than once in its own file: **19 of 30 (63%) on `do-rel2/Cloud`, 16 of 30 (53%) on
`do-lethal-53470/Cloud`**. This is the single largest identified cause of `declinedUnresolved`
sites in [[R196]]'s Task 3 measurement (`docs/measurements/README.md`), well ahead of any other
cause found in the same sample.

**Two further causes found in the same sample, distinct from this one and each other, both also
real but NOT the same defect:**
- A procedure's own AL **named return value** (`procedure Foo(...) ResultName: Type`, letting the
  body write `ResultName := ...` instead of `exit(...)`) is captured by `parseProcedure` only as a
  return TYPE, never as an assignable `VarSymbol` with that name, so any assignment to it is always
  unresolvable, regardless of overloading. Confirmed directly on multiple sampled sites (the return
  value's own name matched the declined target exactly, once per site).
- AL's implicit, undeclared **`Rec`** variable (present on any table/page/report bound to a source
  table) and a **bare, unqualified reference to the bound record's own field** (valid AL inside such
  an object's procedures, referring to the current record without a `Rec.` prefix) are both plain
  `identifier` nodes syntactically indistinguishable from an ordinary local, but neither is declared
  anywhere a declaration-based symbol table can see. Confirmed on two sampled sites each (`Rec :=
  <expr>` reassigning the whole bound record; a bare field name reassigned inside a page procedure
  whose `SourceTable` declares that field).

These two are not being filed as a defect here: they are closer in kind to [[R196]]'s own §3.2.4
exclusion (record/field targets) than to a resolver BUG: nothing is mis-keyed, the thing being
assigned to genuinely is not a declared local/parameter/global, so declining it is arguably correct,
just reached through a shape (a bare identifier, not `Rec.Field`) the exclusion's original wording
did not anticipate. Recorded here so a reader of R196's `declinedUnresolved` rate does not mistake
either of them for THIS row's cause.

**Direction of the error.** Unlike [[R70]] (bare-name collision ACROSS object kinds, which could
wrongly CLAIM a receiver that should be unresolvable), this is the conservative direction: a
resolvable variable is wrongly reported as unresolvable, or, worse, and not yet measured, could
resolve to an unrelated same-named local from the WRONG overload if the two overloads happen to
share a local name, which would be a silent wrong-identity answer rather than a decline. Only the
decline direction was measured; the wrong-identity direction is a real possibility this row has not
yet probed for.

**Consequence for [[R196]]'s classifier, specifically.** `classifyHangCapable` treats an unresolved
target as a DECLINE, never a claim, so today this row's measured direction (a resolvable variable
wrongly reported unresolvable) can only make the classifier UNDER-tag, which is the failure this
row's sample measured. But the un-measured direction above (resolving to the wrong overload's
same-named local rather than declining) would let `classifyHangCapable` compare the WRONG
declaration against a loop's condition and, if that wrong declaration happens to collide with
something the condition reads, tag a site that is not actually loop-condition-relevant at all: a
false positive, not a decline. [[R196]]'s design accepts this as a bounded cost (a falsely-tagged
mutant that never itself times out has no observable effect at all, and one that does time out for
an unrelated reason gets the ordinary confirmation any tagged timeout gets), but that confirmation
does not detect or correct the false tag as such: `docs/superpowers/specs/2026-09-06-r196-hang-capable-design.md`
section 6.3 says plainly that the replay "does not prove causation", so it cannot tell a genuinely
non-terminating, correctly-tagged mutant apart from a merely-slow, falsely-tagged one. Neither this
row nor [[R196]]'s own measurement has found a real instance of the false-tag direction; it is
recorded as a known-possible, not-yet-observed risk, not a confirmed one.

**To close:** `resolveProcedure`/`lookupVar`'s procedure-local and parameter steps need to identify
the ENCLOSING declaration by the call site's own AST position (the same node `findEnclosingProcedure`
already returns) rather than by re-looking-up "some procedure of this name" from a name-keyed map.
`ProcedureSymbol` would need to carry enough to make that comparison (e.g. its own declaration node,
compared the way [[R209]]'s positional workaround compares declarations, or a real per-overload key
in the `procedures` map). Any fix should be measured against a fixture with a genuinely overloaded
procedure name before/after, since no existing gate is known to exercise this shape (not yet
checked).
