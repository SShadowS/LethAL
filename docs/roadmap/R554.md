**Filed by R-550 (2026-10-09; plan r2 condition 1, orchestrator's ruling: keep them deployed, file an item).** A report's
`requestpage` triggers deploy mutants (in the 30 wrapped BaseApp reports R-550 measured: 165 sites). A trigger mutant
has no member name, so every backend places it by its OBJECT (selection's fallback 1): every test that ran anything in
the report covers it. A test that runs a report with `UseRequestPage(false)` never executes its request page, so these
mutants SURVIVE under covering tests that never reach them (covered-but-unreached).

**Which way it fails, and why they stay deployed.** Only test selection can be wrong, never a verdict: a kill still
needs a test green at baseline to FAIL under the active mutant, so no false kill is possible; a misnumbered line cannot
move a trigger mutant at all (object placement). The cost is a `survived` that reads as "your tests reach this code and
do not catch the change" when no test reaches it. R-550's arm shows the shape live: its request-page rows survive under
`BandYDirect` and `BandYRun` on every leg. That they are UNREACHED is measured on al-runner only (its coverage never
hits the request page's lines); on BC it is assumed from `UseRequestPage(false)`, because no test reads `Shown`, so a
reached-but-unobserved request page would survive the same way.

**Not built here:** showing a request page in a test needs a `[RequestPageHandler]`; in BC's fenced session that is the
TestPage-family problem ([[R069]]'s territory), and on al-runner it goes through its handler dispatch. A measured
request-page arm, or a selection rule that reads a request-page trigger as `no-coverage` unless a test is seen
executing a request page, are the two ways to close it.

## Measured on BC (R-554, 2026-10-09): closed by ruling

The result is exactly as pre-committed in `docs/superpowers/specs/2026-10-09-r554-request-page-reach-precommitment.md`.
The probe is `scripts/r554-probe/bc-reach.ts`. It ran on Cronus28 on both legs of `itest:bcdev-wrapped`:
`fenced`, and `procedure` (the hub).
- **The request page:** all 6 mutants of R-550's `OnOpenPage` (3 per report, in `Wrapped Y Band` and in its
  unwrapped twin) are `survived`, at statement grain, with `guardReached: false` and `reachedBy: []`. BandYDirect and
  BandYRun both cover them, so on BC they are covered but unreached.
- **The control:** in the same report, the `OnPreReport` `empty-block` and `remove-assignment` mutants also survive,
  but read `guardReached: true`, reached by BandYRun. Every other mutant of the report arm also reads `true`. So
  BC's reach marker does fire inside this report; it simply never fires on the request page.
- **No error or hang:** both legs count 60 / 38 / 0, with zero error, timeout or deadline. The 28 report-arm
  verdicts equal `bcdev.wrapped.baseline.json`, and the hub leg equals the fenced leg on all 98 rows.

So `UseRequestPage(false)` does not run the request page on BC either, which agrees with al-runner.

**The ruling (by the orchestrator, when the item was assigned: close if BC agrees):** request-page mutants stay
deployed. They are what the item says they are: correctly placed, never falsely killed, and labelled `survived`
where no test reaches them. A `RequestPageHandler` arm or a selection rule is not built.

**Census (`scripts/r554-probe/census.ts`).** These are DEPLOYED mutants inside a `requestpage`. Each project goes

count is the set a run deploys. Projects use their default symbols. As in the runner, `.al` files under dot-folders

**Why some files count 0:**
- 64 BaseApp files that mention a request page deploy nothing at all: 51 XmlPorts, 12 reports and 1 report
  extension. They have no deployable site, or were refused at the trial compile or compiled out. A deployed count
  rightly gives them 0.
- The other zero-count files deploy mutants, but none inside a request page.

In total there are about 6.7 thousand request-page mutants across these corpora. Each one is a `survived` meaning
"not reached", wherever no test shows that request page.

One assumption is not measured: the reach marker FIRING inside a request page that IS shown. That would need a
`RequestPageHandler` test. The marker is emitted there in the same shape as in `OnPreReport`, and runs in the same
session. If the assumption were wrong, a survivor would be mislabelled; no verdict would change.
