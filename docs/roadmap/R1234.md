**Found by** PR-468's live leg (lethal-code, 2026-11-27). Evidence: `/coord/handoff/PR-468/live/result-live.md`.

- **What happened:**
  - After the server1 reboot wiped bc1, `bc-linux-setup.ts --server bc1` recompiled sandbox-tests against
    sandbox-app and published it.
  - `--resume-run 1` then refused: the prior run was measured against test app `package:815ceb85…`, this session
    against `package:72368909…`.
  - The fixture's SOURCE did not change between the two.
- **The question:** does `alc` produce different bytes, and so a different served-package hash (`hashPackage`
  normalises only the NAVX id), when it recompiles UNCHANGED source? For example a build timestamp, a GUID, or the
  zip's DOS times, as R1230 found for System.
  - If so, R247/R495 over-refuse: every resume after a recompile refuses, though the test app's content is the same.
  - The fix might be a content digest like PR-457's `packageContentDigest`. It must still change whenever anything
    that can change a verdict changes.
- **How to measure (offline, no BC):**
  - compile the same fixture test app twice with the same alc and symbols;
  - compare the two `.app` files: raw bytes, the `hashPackage` digest, and a per-entry content diff (which entries
    and fields differ).
  - Repeat with a different alc build if one is at hand.
- **Not in scope:** changing R247/R495. If a content digest is warranted, that is a separate pre-committed build.
