Measured by coord PR-101 (lethal-code, 2026-11-17, measure only), on the slice of [[R1097]] and a small serve drive with
`--timings` on two of its test codeunits (`/coord/handoff/PR-101/`).

**The floor.** An entry's `wallMs` minus its tests' own `durationMs` is 0.09-0.26 s per pass, median 0.145 s.
- These readings were taken on a loaded machine (load average 8.5-10), so they lean high.
- `resetMs` is 0.
- On this build the .NET sidecar is started once per request and reused across passes (0 dirty), about 0.06 s per request,
  0.2% of tests time. So most of the floor is not the sidecar (compare [[R1092]]'s older build, where each pass started its
  own).

**The size.** The run sent 4,792 entries in 54 requests: 2,793 mutant passes, 731 echo, 1,248 kill-pair and 20 warm-up. At
0.12 s each that is about 575 s, 33% of the 1,749 s of tests time (range 25-49%).

**The levers.**
- Upstream: a lower floor. Asked on al-runner #8204,
  https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8204#issuecomment-6935407050.
- Merging a mutant's passes into one entry, if v3 could run several codeunits in one entry: at most 247 s (13.7%).
  Untested, and it needs upstream support.
- LethAL side: fewer passes, by the pair cut and the echo of [[R1097]].

**Attributed (coord PR-104, lethal-preproc, 2026-11-17; `/coord/handoff/PR-104/result.md`).** Measure only, on the same
build (edge-4ebfe7913). The probes were invented 8-test apps (0 ms tests) driven through `serve --timings`, plus DO's app
with single attributes removed in a measurement copy. Two interleaved rounds per comparison.
- **Most of the floor is the company login, run again for every test codeunit of every pass.**
  - It happens when an app under test subscribes to a Guided Experience registration event (`OnRegisterManualSetup`,
    `OnRegisterAssistedSetup`; v3's login events). v3's login decision then raises the login. At each test session's
    company open, System Application's `OnCompanyOpenCompleted` subscriber then runs the whole `OnAfterLogin` chain
    (`Checklist Events`, the Guided Experience registration). Only the login's work date is memoised.
  - The invented app on BaseApp: a gap of 0.4-2.1 ms per pass without such a subscriber, 75-108 ms with one
    (95-231 ms at one entry per request).
  - DO (four such subscribers): 103-230 ms per pass. With only those four attributes removed: 24-50 ms. With DO given as
    a compiled package instead of a source path: 1.3-3 ms.
  - So about 80 ms of DO's ~0.12-0.15 s floor is this login, roughly 75-80% of it.
- **Ruled out by measurement:**
  - serve's own per-pass work: 0.2-1.7 ms on an invented app;
  - BaseApp and the Continia dependencies as packages;
  - empty login and company-open subscribers (the memo replays them);
  - DO's install data;
  - DO's test codeunits;
  - DO's only Company Triggers subscriber;
  - plain code size (generated apps up to 7,000 procedures: 1.1-2.4 ms).
  - A residual of ~20-45 ms per pass on DO is not attributed.
- **What LethAL's request shape controls:**
  - Nothing of the cost per pass. `runSelectedOnly`, `excludeTests`, `resources` and entries per request leave it unchanged.
  - It is paid per test codeunit session, so it follows the number of codeunit passes LethAL sends: mutant, echo,
    kill-pair and warm-up entries. On the slice above, the 731 echo passes alone are ~60-75 s of it.
  - **The "merge a mutant's passes into one entry" lever above does not reach this cost**, because each test codeunit
    in an entry opens its own session and pays the login again.
- **Upstream:** asked to run the raised login once and replay it per test session, as the work-date login is. Invented
  repro and numbers: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8211.
