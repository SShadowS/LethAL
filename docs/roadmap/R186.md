**Twice in one session, importing a helper out of a script executed that script.** Both times the
symptom pointed away from the cause.

1. `packages/runner/itest/tables.itest.ts` calls `main()` at top level and, before that,
   `process.exit(0)` when `LETHAL_ITEST_TABLES` is unset. Importing an assertion helper from it
   would have **killed the `bun test` process at module load with no failure message**, and
   importing it with the gate variable set would have fired a **billed live BC run from a unit
   test**. Caught in review before it landed; the helper went into
   `packages/runner/itest/notinstrumented-evidence.ts` instead, copying `baseline-guard.ts`.
2. `scripts/redact-campaign-report.ts` had its CLI body at top level. Importing
   `isMutationElementsExport` for R184's committed-file guard made the test process inherit
   `bun test`'s argv, match no report path, and die on the usage error. Fixed by wrapping the body
   in `import.meta.main`.

**The convention already exists and is not written down anywhere.** `scripts/changelog-section.ts`,
`scripts/operator-tables.ts` and now `scripts/redact-campaign-report.ts` all guard with
`import.meta.main`; `baseline-guard.ts`, `mutant-equality.ts`, `notinstrumented-evidence.ts` and
`scripts/r159-aor-spike/aor.ts` are pure modules with no CLI at all. Both shapes are correct. Nothing
states the rule, so the third instance was rediscovered by hitting it rather than by reading it.

**Measured before filing: there are ZERO offenders today.** Of 63 modules under `scripts/` and
`packages/**/itest/`, seven are imported by another module; three of those have a CLI body and all
three are guarded. So this row buys nothing today and exists because the failure mode recurs: the
trigger is somebody wanting one helper out of a script, which is exactly what happened twice above
and will happen again.

**The shape of the fix.** A test in the genre of `scripts/line-citations.test.ts`, which pins a
repo-wide convention rather than a behaviour: for every `.ts` under `scripts/` or an `itest/`
directory that ANOTHER tracked module imports, if it references `process.argv` or `process.exit`
then it must also contain `import.meta.main`.

**State its limits in the test itself, because they are real.** It is a heuristic keyed on two
identifiers, not a side-effect analysis: a module doing top-level I/O without touching either slips
through. It only judges modules something actually imports, which is deliberate — an unimported CLI
script is entitled to a top-level body, and forbidding that would be wrong. And import detection by
module basename would miss an unusual aliasing. A guard that overstates its reach is the thing
[[R184]] had to be narrowed twice for.

## OUTCOME, appended after building it. Nothing above is edited.

Built as `scripts/importable-scripts.test.ts`, three tests, and the interesting part is that **the
first version did not work and only the red-check said so.**

It tested `src.includes("import.meta.main")`. Removing the real guard from
`redact-campaign-report.ts` and leaving its explanatory comment in place still PASSED, because the
comment says the words. A file reading "TODO: add import.meta.main" would have satisfied it. That is
the same vacuous-guard shape this row's own fix text warns about, written by the person warning
about it, and nothing but running the red-check would have surfaced it.

Matching the SYNTAX instead (`/if\s*\([^)]*import\.meta\.main/`) makes it fire: the tampered file
is named along with its importer, and two of the three tests go red. Restored, 3 of 3 pass.

The limits in the plan text are stated in the test's own doc comment rather than here, because that
is where the next reader meets them. A behavioural version, importing each script in a subprocess to
see what happens, was considered and REJECTED: it would execute whatever it imported, and this
directory holds `demo-reset.ts` and `build-binary.ts`.
