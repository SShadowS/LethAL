**Measured 2026-09-26, while gating C02-04 Part A.** `itest:alrunner` against al-runner
**v2.11.0** fails the R147 assertion ("no execution context carries a `platformAppsDir`"), on
master at `5420201` and on `lethal/lane-code` at `da35dd8` alike, so it is not caused by that
branch. The verdicts are unchanged: 3 killed, 12 survived, 4 no-coverage, the frozen figures.
Only the pin check fails, which means every al-runner invocation pays `--auto-provision` again.

R147 and R182 read two `[provision]` sentences to find the platform-app directory: the cold
`Downloaded <N> app(s) ... to <dir>` and the warm `platform apps already complete at <dir>.`
(regexes in `al-runner-transport.ts`). The likely cause is that v2.11.0 prints neither in the
form those regexes expect. Not yet confirmed: read the run's `al-runner-platform-apps-unpinned`
warning and al-runner 2.11.0's actual provision output before changing a regex, and keep the
engine and test-toolkit sentences pinned as non-matches.

Evidence: the two gate logs from that session; the gate prints the al-runner build as its first
line.

**Closed.** v2.11.0 searches the engine variant's build for its platform apps and names that
directory only in verbose output, a `[pkg-cache]` search-set line, not in either `[provision]`
sentence R147 and R182 read. Fixed by having the provisioning call alone set
`AL_RUNNER_VERBOSE=1` and reading that `[pkg-cache]` line as a third basis, `package-cache`; a
mutant run's own invocation is unchanged and still sends no `--verbose`. The pin engages only on
the one-shot path, since `--server` never receives it. Live gate: `itest:alrunner` on v2.11.0,
2026-09-26, PASS, 19 verdicts identical on all four legs, pin engaged on both one-shot legs.
Follow-ups filed: R241 (a truly empty cache fails before the platform-app step, resolving the CDN's
latest 28.x to a build this al-runner install ships no engine variant for) and R242 (the `--server`
and resource legs record a `platformAppsDir` pin the daemon never actually receives).
