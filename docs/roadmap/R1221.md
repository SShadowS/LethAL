**Found by** PR-441 (lethal-code, 2026-11-25). Evidence: `/coord/handoff/PR-441/findings.md`, `candidates.md`, and the
spec-adversary's review (summarised below). Figures are shares of c5's mutants phase (c5 ran under load).

- **What a pair proves** (one request, both entries cut after the killer).
  - **NONE (the confirm):** the killer passes unmutated after the kill. Otherwise `error`/`unstable`.
  - **M (R577's reproduction):** it fails again under the mutant after that pass. Otherwise
    `error`/`kill-not-reproduced`.
  - Kill → pass → fail means a test that merely flips over time cannot make a kill. Each half's echo also proves its
    entry ran with its own selector value.
- **c5:**
  - 6,665 kills, 0 disagreements (no `unstable`, `kill-not-reproduced`, `timeout-unconfirmed` or `confirm-stopped`).
  - 6,178 pairs: 6,013 batched by R778, the rest live.
  - The 6,185 main-pass kills come from 873 distinct killing tests. Within windows of 20 kills, one confirm per killer
    would need about 1,680 NONE entries instead of 6,185.
- **C1: one NONE per (test codeunit, `through` cut) per batch**, `NONE, M_1 … M_k`. About 3.8% (batched pairs only).
  Conditions from the review:
  1. **A standing leg-C fact.** Consecutive entries of the SAME test codeunit, with DIFFERENT resources, under
     `AL_STRICT_SEQUENTIAL=1`, with echoes between, carry nothing. The channels it must cover: app and test-side
     SingleInstance, the codeunit's own and library globals, WorkDate, GlobalLanguage, a bound subscriber, a temp table
     in a SingleInstance. It also needs a positive control, and must pin that entries run in order.
     - Today a fresh NONE between M_1 and M_2 would catch state M_1 leaves. Under C1 the kill and the reproduction
       would both run after M_1, so such state would reproduce rather than be caught.
     - R766 measured SingleInstance across entries only, on alpha.5. A trailing NONE does NOT fix this.
  2. **Group by exactly (call id, `through`).** Assert that NONE and M came from one request, and make the L4 live
     fallback drop a stored pair whose M would precede a live NONE. A group key that splits the NONE cut from the M cut
     lets the existing fallback order kill, M, then NONE, which is a false kill.
  3. **Re-sends after a cut carry their own NONE.** A killer's group is never split across chunks without one.
  4. One failing shared NONE makes k mutants `unstable` instead of one (the safe direction).
- **C2: drop the NONE and M echoes.** About 3.7%, with a wide band, since the echo's own price is weakly identified.
  About 6.5% with C1, as they overlap. It needs the same leg-C fact (no SingleInstance carry across entries), and
  `resourcesHash` compared with LethAL's own sha, failing loudly when it is missing (R1220). It must never ship with C1
  unless the same fact gates both.
- **Rejected:**
  - confirming or reproducing the killer alone: little saving, and DO's order dependence (R1141) loses kills;
  - dropping either half: it reopens the false-kill path.
- **PR-442 landed** the cross-entry facts (master 62795fcc2): 14 `entry-no-cross-*` facts, gate-only.
- **C1 designed (PR-444, spec `docs/superpowers/specs/2026-11-25-pr444-shared-none-confirm.md`, master 54915d40a) and
  PARKED after its spec-adversary** (orchestrator ruling, 2026-11-25). The review found the group key `(callId, through)`,
  the order, the L4 guard and the k-fold `unstable` fan-out sound. It also found:
  - **B1, a false kill no PR-442 fact closes.**
    - A kept (safe) refusal, for example a refused Commit (whose own text says "what the runner keeps is not pinned"),
      can leave residue that the next entry of the same request sees.
    - Today the NONE between M_1 and M_2 is the only in-request canary for it (it fails, so M_2 is `unstable`). C1 runs
      NONE, M_1, M_2, so M_2's kill can reproduce on M_1's residue.
    - PR-442's writer never commits or hits a refusal; PR-56's drift check covers only the next request.
    - Fix: a canary rule (no shared pair for the Ms after any kept-refusal or `notRun` row in the group), PLUS a new
      fact for residue after a committing or refused writer, which C1 also requires (iterate `V3_ENTRY_FACTS`).
  - **S2, an empty check.** The planned same-request assertion is silently empty (`none` and `m` come from one `out`),
    or it aborts unflagged runs. Fix: stamp each `CallRows` with its real request seq and entry index; compare cuts only
    when the request went out flagged.
  - **S3, an unmeasured channel.** The .NET sidecar lives for the whole daemon, so static .NET state could carry from
    M_1 to M_2. DO's default resolves a sidecar, and leg C cannot take DotNet cases. So C1 must refuse whenever a sidecar
    is resolved, unless the owner accepts the channel by ruling.
  - **M4, the bound is too high.** The ~70% fewer NONEs (PR-441) counted one NONE per killer, but the key is
    `(callId, through)` with `through` the LAST failing test, and chunking splits groups. The real saving is lower than
    the ~3.8% bound. It cannot be re-derived from c5's events, which do not record the failing-test sets.
  - Also: the ON-vs-OFF DO A/B is blind to these hazards (c5 had 0 `unstable`, so equal verdicts are expected either
    way). It measures cost only.
- **Unpark C1 only with both prerequisites:**
  1. the residue fact (a PR-442 follow-up), reading `matches`;
  2. the owner's ruling on the .NET sidecar channel (asked with the unpark, not before).
  Then add the canary rule, S2's real assertion and M4's re-derived bound.
