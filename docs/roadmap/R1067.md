Found by PR-51's spec review (spec-adversary, 2026-11-16; `docs/superpowers/specs/2026-11-16-pr51-timeout-class-stable.md`).

**Mechanism (traced in code, not measured on a real project).** Tests A and B are in one test codeunit X, A before B in the
codeunit, and A hangs under the mutant, so X's call is cut at A's timeout before B's row:
1. X's call is cut at A's timeout row (R895); the daemon is killed and the cut recorded (`timedOutMutants`).
2. B has no row in the cut call, or `cutElsewhere` routes it, so B runs through `aloneCall`: one test, no state from the tests
   before it in X. B fails.
3. B's cold confirm sends the R653 kill pair `{NONE:[X]}`/`{M:[X]}`: the WHOLE codeunit, so unmutated B runs AFTER A and the
   rest, in context. It passes, and the confirm accepts the kill.
4. The reproduction reads the pair's M entry, which is cut at A again, so B runs alone again and fails: reproduced.
If B fails alone whatever the code (it relies on state an earlier test of X sets up: "tests of a codeunit share state in order",
`al-runner-v3-backend.ts`), nothing compared B-alone with B-alone, and the mutant is scored `killed` falsely.

The same holds for a TIMEOUT: a test that hangs only when run alone gets the same in-context confirm and alone reproduction,
and can be scored `timeout-killed`.

**Where it can happen today.** Whenever B's mutated row comes from an alone run, which needs a cut at a test of X before B:
- most directly, B first in covering order: `runOn(B)` sends X's whole-codeunit call, it is cut at A (first in codeunit
  order), B has no row and runs through `aloneCall`;
- the `cutElsewhere` routing after an earlier cut of the same mutant, or R897's `aloneAfterStop`.
PR-51's held-timeout walk confirms its LATER alone-measured fails alone (`RunOpts.alone`). Every other alone-measured first
kill, including a held timeout that itself came from an alone run, keeps today's in-context confirm, because changing it would
move verdicts PR-51 must not move.

**To close.** No event, stat or stored field names an alone request today, so stored runs cannot be classified. First step:
record PR-51's `TestVerdict.selection` (a test-result column or an event per alone request; PR-51 sets it but does not store
it). Then measure whether any v3 kill on DO or
BaseApp was confirmed in context after an alone mutated run. Then either apply the alone confirm to every alone-measured kill,
pre-committing the moved verdicts, or rule the risk away with that measurement.
