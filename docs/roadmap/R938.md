Found by lethal-code, 2026-11-12 (coord R-925). Related: [[R586]], [[R895]].

**What happened.** LethAL never passes `--environment` to al-runner, so v3 runs every session as `saas` (IsSaaS and IsSandbox answer
Yes). Microsoft's tests often call `SetTestabilitySoftwareAsAService(false)` and then expect an on-prem server; under `saas` that call
changes nothing, and code that branches on the environment takes the SaaS path. Run alone on edge-42af5d384, these baseline tests fail
under the default and pass with `--environment onprem`: Sales and Inventory Forecast's TestGetSingleInstance,
TestMissingApiUriOpenSetup, TestKeyNeededBeforeScheduledExecution, TestUpdateForecastActionThrowsErrorIfForecastingNotSetup, and Email
- SMTP Connector's SwitchingToOAuth2Authentication, GetOAuth2CredentialsTest, CheckAuthenticationSuccessTest,
CheckAuthenticationFailTest (`/coord/handoff/R-925/up/10-*`, `11-*`, `4-*`, invented env app `up/w/env/`). LethAL's bc servers are
on-prem (BC on Linux, Docker), so the same tests are measured under one environment on bcdev and another on v3.

**Invented repro.** A test that calls `SetTestabilitySoftwareAsAService(false)` and asserts `not EnvironmentInformation.IsSaaS()`:
fails on `lethal run --backend al-runner-v3`, passes on `al-runner test --environment onprem` and on a bc server.

**Wanted.** The v3 backend passes an environment, by default the one LethAL's bcdev gates measure (`onprem`), with a config field to
choose; the report names it. Measure first: re-run the R-925 apps' baselines under `onprem` and count the reds that turn green (and any
that turn red), since this moves verdicts; pre-commit the moved figures and check the v3 gate's tables.

## Design (coord R-930, lethal-code, 2026-11-12; written before any code)

**Facts (survey `/coord/handoff/R-930/survey.md`).** al-runner takes `--environment saas|onprem`; `saas` is its default (IsSaaS and
IsSandbox Yes), `onprem` answers No until a test's `SetTestability*` changes it (al-runner's help calls the on-prem answers "an
unprobed assumption"). LethAL never passes it, never reads the target's `.vscode/launch.json`, and the `alRunnerV3` config has no such
key. The only environment fields LethAL holds are `bcdev.environmentType` (passed through to bc-dev-mcp, never read) and the target's
`launch.json` `environmentType` (`OnPrem`, `Sandbox`, `Production`). Of our own projects and configs, 30 of 31 fixtures, all 77
BC.History driver configs and all 75 BC.History source projects have neither.

**Where the environment comes from, in order (first one that answers wins):**
1. `alRunnerV3.environment` (`"saas"` or `"onprem"`) in the config: explicit, so it always wins.
2. The target's `.vscode/launch.json`: its configurations' `environmentType`, `OnPrem` -> `onprem`, `Sandbox` or `Production` -> `saas`.
   If the configurations disagree, it does not answer (step 3 then decides), and the message names the disagreement.
3. Nothing answered.

The report and the run header name the environment used and where it came from (`environment: onprem (alRunnerV3.environment)`), and
it joins the v3 fingerprint (a run under one environment is never resumed or compared under the other).

**Step 3 is the open choice, and it is the owner's:**
- **(A) Refuse by name** (principle 5, "unknown is not no"; principle 1, correct first): the run stops before deploy with
  `al-runner-v3: the target's environment is unknown (no alRunnerV3.environment, no launch.json environmentType); set
  alRunnerV3.environment to "onprem" or "saas"`. Cost: it refuses ~183 of ~184 of today's configs and projects (we fix ours in the
  same change: fixtures, the itest configs, the BC.History drivers' template), and it refuses a typical user project too: many repos
  gitignore `.vscode`, and a project without a launch.json is common. The fix is one line, but it is a new required field before a
  first v3 run.
- **(B) Warn by name, and use `saas`** (al-runner's own default, today's behaviour): nothing breaks; the warning says the environment
  was not stated and that on-prem-only code paths may fail at baseline. Cost: a silent-looking default, which principle 5 warns
  against, and R-925's eight baseline reds stay red for anyone who does not read the warning.
- **(C) Warn by name, and use `onprem`** (what our gate servers are): moves today's verdicts silently for everyone; no basis for
  calling on-prem the user's environment either.

**Recommendation: (A)**, because a wrong environment produces wrong baselines and verdicts (R-925: eight reds), which principle 1 ranks
below an error, and the error names its one-line fix. Principle 22 (correct before backward-compatible, before release) allows the
break. If the owner prefers not to require a field before a first run, (B) is the fallback, with the warning as a report caveat so a
reader of the report sees it.

**Measurement before landing (whichever is chosen):** per affected app (R-925's eight; R-926's where present) and the v3 gate's
fixtures: baseline and per-mutant verdicts under `saas` and under `onprem`; count the reds that turn green, the greens that turn red,
and the verdicts that move. The v3 gate's fixtures then get an explicit environment (the one their pinned tables were measured under,
`saas`, unless the gate is re-pinned), so no gate figure moves by accident; any figure that does move is pre-committed first.
