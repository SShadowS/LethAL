id: "R445"
title: "lethal run on a test project nested inside the target compiles and mutates the test code as target code, without a warning"
section: "product-gaps"
status: "done (f46581db)"
order: 1163
---

**What.** When the test project lies inside the target project's folder, `lethal run` treats every
test `.al` file as target code. `targetAlFiles` lists every `.al` under the target folder,
`generateMutationSet` generates mutants for each of them that the run's mutation scope covers
(`--only` and `--exclude` can leave files out, but nothing leaves test files out by default), and
`prepareBatchProject` copies all of them, mutated or not, into the batch that `alc` compiles. So the published target app contains the test codeunits,
and the test codeunits carry mutant ids of their own. The same objects then exist in two apps (the
target and the test app), which BC refuses as duplicates; or the target compile fails on test-toolkit
references that the target does not declare. If it does publish, the score includes mutants in test
code. Nothing tells the user why.

**Why it is not fixed in R260.** R260 made `lethal verify` refuse this layout by name
(`test-project-nested`, `assertTestProjectSeparate`). `run`'s source hash and generation were left
alone on purpose: leaving the test folder out of the build changes the mutant set and ids for that
layout, and leaving it out of the hash alone would hide a real change to the installed build.

**Evidence.** The R-260 survey's probe: a temporary project with `src/A.Codeunit.al` and a nested
`test/T.Codeunit.al` plus `test/app.json`; `targetAlFiles` listed both files and generation emitted
specs for both. Code: `targetAlFiles` and `readTargetSource` (`baseline-snapshot.ts`),
`generateMutationSet` and `prepareBatchProject` (`orchestrator.ts`).

**What would close it.** `lethal run` warns, or refuses, when `--tests` lies inside the target or
contains it, reusing `assertTestProjectSeparate`'s containment rule, with the same fix in the
message: move the test project beside the target and update the `--tests` passed to both `lethal
run` and `lethal verify` (no config field names the test folder).

**Done (R-445).** `lethal run` refuses the layout by name, `test-project-nested`, before anything
reads or builds the target (first step of `runFromCli`). It reuses R-260's rule through one shared
function, `testProjectNestedProblem` in `verify.ts` (real paths, both ways round: the `--tests`
folder is the target, lies inside it, or contains it), with `run`'s own fix hint. Verify's refusal
and text are unchanged. For `run` only, a folder whose real path cannot be resolved is not refused
here: `run` fails reading it straight after.
- **Campaign:** campaign stages run through `lethal run` (`campaign-fence.ts` polices those
  invocations), so they are refused the same way; `lethal campaign` itself only reads reports.
- **Dry-run, by design (orchestrator ruling, 2026-10-06):** `lethal run --dry-run` takes no
  `--tests` (R266), builds and publishes nothing, so it cannot know the test folder; it lists a
  nested project's test files as mutants. A layout heuristic (a nested `app.json` holding a
  `Subtype = Test` codeunit) was measured and rejected: 0 such folders under any real target in the
  corpora, but it fires on Microsoft's System Application Test and Business Foundation Tests roots.
- **Tests** (`r445-nested-run.test.ts`): nested, same folder and containing are refused with nothing
  built (`buildBackend` and `runSession` never called); a sibling test project reaches `runSession`.
  Red-checked both ways: without the check the three refusals go red; refusing always turns the
  sibling control red. One existing test (`cli-al-runner-defaults.test.ts`, R387) passed the target
  as its own `--tests` for convenience; it now uses a sibling folder.
