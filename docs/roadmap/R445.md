---
id: "R445"
title: "lethal run on a test project nested inside the target compiles and mutates the test code as target code, without a warning"
section: "product-gaps"
status: "open"
order: 1163
---

**What.** When the test project lies inside the target project's folder, `lethal run` treats every
test `.al` file as target code. `targetAlFiles` lists every `.al` under the target folder,
`generateMutationSet` generates mutants for all of them, and `prepareBatchProject` copies all of
them into the batch that `alc` compiles. So the published target app contains the test codeunits,
and the test codeunits carry mutant ids of their own. The same objects then exist in two apps (the
target and the test app), which BC refuses as duplicates; or the target compile fails on test-toolkit
references that the target does not declare. If it does publish, the score includes mutants in test
code. Nothing tells the user why.

**Why it is not fixed in R260.** R260 made `lethal verify` refuse this layout by name
(`test-project-nested`, `assertTestProjectSeparate`). `run`'s source hash and generation were left
alone on purpose: leaving the test folder out of the build changes the mutant set and ids for that
layout, and leaving it out of the hash alone would hide a real change to the installed build.

**Evidence.** The R-260 survey's probe: a temporary project with `src/A.Codeunit.al` and a nested
`test/T.Codeunit.al` plus `test/app.json`; `targetAlFiles` listed both files and generation emitted
specs for both. Code: `targetAlFiles` and `readTargetSource` (`baseline-snapshot.ts`),
`generateMutationSet` and `prepareBatchProject` (`orchestrator.ts`).

**What would close it.** `lethal run` warns, or refuses, when `--tests` (or the config's test
folder) lies inside the target or contains it, reusing `assertTestProjectSeparate`'s containment
rule, with the same fix in the message: move the test project beside the target.
