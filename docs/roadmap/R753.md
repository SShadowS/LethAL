**Found by R-748's build review (2026-10-25).** In `packages/runner/src/line-map.ts`, `spansOf` puts a renamed split
member that has no coverage name into `unnamed`. That list feeds only the `shared` lines: it is in neither `procedures`
nor `triggers`.
- `isNamingGap` checks only `procedures` and `triggers`, so every line inside such a member that is not a shared line
  is a naming gap.
- If a named member of the same object has a row in the same test, R748 puts the object in `besideMembers` and the new
  code fires. Its message ("suspect a 1-2 line shift") then points the reader at the wrong cause.
- This predates R748 in one form: with no named member row, the same rows already raised
  `fenced-coverage-no-procedure-lines` (R747's blind spot (ii)).

**Exposure.** No BC-path fixture has a split procedure header, and R318's census found 0 renamed split members in 20,598
corpus files. So the gates cannot hit it, and the risk is a false warning, never a wrong verdict: attribution in such a
member really is object-level only.

**To close.** Have `isNamingGap` also consult the unnamed spans (a row there is "inside a known span the map declines to
name", like a trigger), with a unit test through the real line map: a row in an unnamed renamed member beside a named
member's row stays quiet, and a real gap row beside it still warns. Red-check both directions.
