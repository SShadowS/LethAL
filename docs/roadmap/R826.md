**Filed 2026-11-05 by lethal-code, from GitHub #28.**

**What was reported.** An all-operators run on one codeunit (1,342 lines, 38 procedures, 907 guards deployed) published fine in
169 s. During the baseline the BC service tier died with exception 0xc00000fd in `coreclr.dll`, which is a stack overflow. The
service stayed stopped until someone started it. LethAL's side worked: the run was quarantined, no mutant was scored, and it
exited 3. On the same codeunit, build and container, single-operator runs passed at 56 guards (`conditional-boundary`), 137
(`negate-conditional`) and 263 (`remove-assignment`). The crash run had 19 operators.

**What is checked (code read on master, 2026-11-05).** LethAL does not handle this.
- `publish-ceiling.ts` refuses a file only after a publish failure is recorded on that tier. A stack overflow in tests comes after
  a successful publish, so it cannot see one.
- `--max-guards-per-batch` splits by file, so one 907-guard file stays one batch.
- `--dry-run` prints site counts and the publish bracket, and gives no warning about run-time risk. `doctor` does not read guard
  counts. The run itself has no check.
- R349, R353, R411, R421 and R513 are about other things.

**What is not known.** The cause is an inference. The failure point is between 263 and 907 guards in that file, from one
reporter's runs. Guard count is not separated from guard shape, because every passing run had one operator and the crash had 19.
- `emitDispatch` builds a flat `if ... else if ... else` chain per statement, so guards add no call depth at the AL level.
- How the AL compiler and .NET handle a long chain, or one very large generated method, is not measured. An `else if` chain is
  still nested in a syntax tree, so a recursive pass over it could go deep.
- It could be the total count, one operator's guard shape, or the longest single chain.

**Proposal.**
1. Measure first, as a separate task: on a bc server, grow guards per codeunit, per procedure and per statement separately, and
   find what crashes, with several operators in one run. A crash stops the service tier, so use a server that can be restarted,
   under a lease, and bound it. The reporter says every other operator on that codeunit is under 80 guards, so single-operator
   runs cannot narrow the range much further.
2. Only then pick the limit. Until a figure is measured, any threshold is a guess, so do not ship one as a refusal.
3. Then add a warning to `--dry-run` and the run's first lines, in the place `--dry-run` already shows per-file counts, with an
   override flag if it refuses.
4. When a run's service tier dies, name guard count as a suspect in the quarantine message.

**To close.** A measured limit with its evidence, the warning or refusal built on it, and a reply on #28.

## What landed meanwhile (R-825, 2026-11-05)

**A warning, not a limit.** `--dry-run` and the run warn, on bcdev only and refusing nothing, when one file's largest chain is 100 or
more, or its largest fold is about 512 KB or more (`large-fold.ts`, warning code `large-method`). It names the file and the figures,
says the cause is not proven and the thresholds are not measured, and points at leaving out `lethal.empty-block` or narrowing with
`--only`. The figures were picked to fire on the outliers: 5 of 171 DO codeunits sampled, where a chain of 50 fired on 32. The largest
fold in that sample is a real 944-guard file with a chain of 473 and about 25 MB in one method.

**The residualising test (`r827-residual.test.ts`).** For every mutant it folds the real emitted text with only that mutant active, and
requires the same tree as the mutation written by hand, `else` binding included, and a reach marker on exactly the mutants the plan
marks. 776 mutants on 9 projects, and 3,893 on 31 DO files (`LETHAL_R827_CORPUS`): no differences. Breaking the real emitter five
ways, a wrong binding included, turned it red. It compares the parsed tree, so `#if` arms are not evaluated: a binding that differs in
only one build is out of its reach.

**Parked.** The measurement below waits for #28's reporter, whose question was posted on the issue, and [[R827]]'s emitter change
waits with it. No crash run has happened, and the server is still the owner's call.

**R827 has landed (R-836, 2026-11-06).** A typical file shrinks about 3-fold, and the worst files hardly at all, so it does not by itself clear the suspect for a large file. The `large-method` warning now
names `if` conditions, `case` arms and loops. The rest is [[R828]]. If a crash run is still needed after that, it uses `bc1`, and each crash needs the owner's restart (ruling, 2026-11-06).

## Checked against today's code (2026-11-08, coord R-875), and steps 3 and 4 built

**The check (master 983771e7).** All 986 DC/Cloud, DO/Cloud and DO/Test files with mutants, each alone through the real generator:
`/coord/handoff/R-826-check/`. The warning's estimate was within about 3% of the real largest method on the files it named. It
missed two just over 512 KB (590 KB and 528 KB). Its chain test (100 or more) caught no file the size did not. The worst file is
one 23.5 MB method (chain 454); the next is 3.6 MB. Median method 8 KB, p99 1.2 MB.

**Built (R-875).**
- The warning reads the real emitted text: the largest procedure or trigger, header to header. To keep a dry run cheap, a file is
  emitted only when a bound on its emitted size reaches 512 KB: the source, plus each component's copied root and 512 bytes per
  guard. On the 986 files a guard needed at most 199 bytes, and the bound was never under the real size. 77 of 986 files were
  emitted, and 24 warn: exactly the files with a real method of 512 KB or more. The chain test is gone.
- Step 4: when a run's fate is unknown on the server (`in-flight-unknown`, as when the tier stops) and its batch holds such a
  method, the quarantine reason ends "if the BC service tier stopped, one suspect (not proven, GitHub #28) is this batch's very
  large method: ...".

**Still not done:** the measurement (steps 1 and 2), any refusal or limit, a reply on #28. 512 KB is still not a measured limit.

## Measurement plan (R-825, draft 2, after one review; no server called yet)

**Server: the owner's call, still open.** The task named `bc1` (28.4). lethal has since moved to `bc4` (BC 29). This plan does not
depend on which. A limit holds only for the build and platform it was measured on, and BC 29 is further from the reporter's 28.0.

**The lead suspect, measured offline (no server): [[R827]].** One `empty-block` mutant on a procedure body folds the whole
procedure into one chain, and each branch repeats the body. A 1,050-guard procedure is 450 components, longest chain 3, 211 KB
without it, and 1 component, chain 1051, 15.3 MB with it. Every run that passed in #28 lacked `empty-block`. So a large emitted
method is the lead suspect, by inference only: it could overflow through its stack frame or the JIT (the .NET step that compiles
a method when it is first called). #28 says the crash came "during the baseline", no more than that.

**So guards are the wrong ladder.** T (total guards) does not mean the same across shapes, and draft 1's shapes did not isolate
anything: `empty-block` collapsed them all. What is climbed is S, the emitted size of the largest procedure, read from the real
build. L (longest chain), T, O (operators) and D (call depth) are recorded on every rung.

**Step 0, no server.**
1. Read real sizes: S and L for real codeunits in the corpora at all operators, through the real generator. Offline, read-only, with
   no source text in any output. It places #28's 1,342 lines on the ladder, and shows how often a real project is near a rung.
2. A probe in `scripts/r825-probe/`, smoke-tested on every side before any server. It publishes one instrumented build and runs the
   test once, with no mutant loop: there is no baseline-only mode in `lethal run`, and a passing rung would otherwise score every
   mutant. Target procedures keep their names between rungs, or the app gets a new id: a changed target risks R709.
3. Every rung is built offline, so its S, L, T and O are known before the server sees it, and alc must accept it.

**Asking the reporter (needs the orchestrator's word: it is a public comment).** On #28, ask for the same run without `empty-block`
(18 operators), on their tier, at no crash cost to anyone, and for the event log's stack and the test's call depth. That answers
the lead question on the tier that actually crashed. It could settle it before any crash here.

**The ladders.**

| ladder | built to separate | form |
|---|---|---|
| 1. size, one method | S and L | one large procedure, all operators, `empty-block` in. Rungs by S: 0.25, 0.5, 1, 2, 4, 8, 16 MB, then on to 32 |
| 2. flat, no fold | T | the same procedure, `empty-block` out: 1,000 guards, chain 3, always run to the top. This is #28's count, tested alone |
| 3. depth | D | ladder 1's last pass, reached through 30 nested procedures that each carry big guarded frames, with no recursion |

Doubling loses precision, but the limit comes from the last pass, not the crash. Ladder 2 is not capped by ladder 1: they are
different axes. Loops and tables stay out, because of R164. So loop and Tier-2 operators are absent, and O differs from #28. That
is a stated limit.

**Budget: 5 owner restarts or fewer, counting all of them.** A crash, and any quarantine, each cost one.
1. Ladder 1 climbs until it crashes: one restart.
2. Ladder 2: none expected, one if it crashes.
3. Ladder 3: one.
4. If ladder 1 crashed, its rung is repeated once with `empty-block` removed by `--operator`, at the same procedure: this splits S
   from O. One.
5. One is kept to repeat the lowest crash, because a limit should not rest on one crash on a shared server.
The count is checked before every ladder. If a step would pass 5, the plan stops and says what was not separated.

**One rung.** One lease held for the whole measurement, with the out-of-use marker written. A separate `--db` per rung, because a
failed publish sets the ceiling for later rungs. `--allow-large-run`, and `--baseline-timeout-ms` raised, because a cold start on
a multi-MB method can look like a hang, and a hang quarantines the tier. After every rung, the control app and the target must
still read back installed: an auto-restart wipes the in-memory database and could otherwise pass unseen.

**Reading a result.**
- **Pass:** the test ran green, a marker shows it reached the code, and the apps are still installed.
- **Crash:** the tier stopped answering, read twice a minute apart. Ports down alone does not prove a stack overflow: it could be
  an out-of-memory kill. So before the restart the owner saves the container's logs, exit code and OOMKilled flag. The .NET trace may
  name the cause outright.
- **Unknown:** anything else, including a timeout. Not counted as a pass or a crash, and recorded. It costs a restart if it
  quarantined.
A crash during publish is a result too, recorded as that.

**After a crash or a quarantine.** No retry and no further call. The lease stays held. A crash stops that ladder until the restart
is confirmed. Then the full setup, the doctor and `lethal clear-quarantine`, and only then the next rung. Each ladder needs the
orchestrator's word first, naming its rungs (ruling, 2026-11-05: per ladder, not per rung).

**Recorded for every rung:** S, L, T, O, D, pass, crash or unknown, the BC build, the platform, load at start and end, exit, log.
Into R826, evidence under `/coord/handoff/R-825/`.

**What would change the plan.**
- **Nothing crashes, the likely outcome if Linux stacks are larger than Windows ones (not read yet: read them first).** #28 does
  not reproduce here. No measured limit ships. A warning can still quote #28's own figures as evidence, naming them as one
  reporter's, on Windows.
- **Only size crashes:** the limit is on S, not on the guard count #28 asked about, and [[R827]] may be the better fix.
- **The reporter's 18-operator run passes:** `empty-block`'s fold is the cause on their tier, and R827 comes before any limit.
- **Linux and Windows may differ.** A limit measured on Linux can be too high for a Windows tier. The reply on #28 must say what was
  measured, and must not present it as safe for Windows.

**Then.** Pre-commit the limit, at or under the last rung that passed, before any code: `--dry-run`, `doctor` and the run warn or
refuse by name, before any publish, as the task sets out.
