**Filed 2026-10-18 by R-577** (orchestrator's ruling: the shared rule lands in two steps; al-runner first in
R577, BC here).

**What.** [[R577]] adds "a kill must reproduce" to the shared orchestrator: after the unmutated confirmation
passes, the killing test is re-run under the mutant, in the kill's own context. A pass gives `error`
`kill-not-reproduced`. R577 switches it on for al-runner only. On bcdev the same hole stays open: any test
that fails at random can be scored a kill.

**Why it is separate.** On bcdev it costs one more test run per kill, and on the group path (`RunMutantMany`,
R198/R206) the re-run replays the kill's prefix with the mutant active. That moves the frozen mechanism
figures of every BC gate (`groupedCalls`, `warmKills`, the kill-position replay counts), so each one needs a
pre-commitment and a re-record under a Cronus28 lease.

**To close.**
1. Pre-commit, per gate, the predicted counter changes with every verdict unchanged: `itest:bcdev`,
   `itest:tables`, `itest:chunked`, `itest:hang`.
2. Switch the rule on for bcdev, re-record under R332, and confirm.
3. `itest:envtool` is host-only (the external environment tool), so it stays UNMEASURED until the owner runs
   it. Name it so in the report.

## Done (2026-10-22, R-582, build 7a8ff82c)

**The change.** One line: `BcDevMcpBackend.killsMustReproduce = true`. The rule, the `--resume` carry filter,
the store column and the report fields all came with [[R577]]. A kill at position 1 re-runs as one single
`RunMutant`; a warm kill re-runs its call's prefix in one `RunMutantMany`; a timeout kill re-runs at the budget
its first run was sent, through `StopHungRunAt`. No baseline file was re-recorded: the baselines hold only
the fields `mutant-equality.ts` compares, and none of them moved. The moved counters live in
`packages/runner/itest/gate-expected.ts` and the `docs/gates/` pages.

**Gate checks added.** Every orchestrator-driven BC itest, envtool's included, checks that each kill carries
`killReproduced` and has exactly 2 mutated rows for its killing test IN THAT RUN (`killerRows(store, runId)`:
the run id is required, because the bcdev and tables fixtures keep older runs in a persistent store).
`itest:hang` checks two BC stops per timeout kill (`itest/hang-stop-rows.ts`) and pins
`HANG_FIGURES.stoppedCallsOn` 6. `itest:chunked` keeps the re-run rows apart from the covering calls and
asserts each warm kill's re-run list equals its replay list (`itest/chunked-rows.ts`). Unit tests U1, U2c,
U4-U7 are red-checked per direction (`/coord/handoff/R-582/red-unit/`).

**Close notes.**
- **envtool is UNMEASURED** (host-only). Its check is wired (`REPRODUCTION_EXPECTED.envtool`). On a hosted
  environment a re-run can score `session-reused`, the fail-safe direction.
- **[[R618]] stays open:** no BC gate resumes, so the carry path is still untested live on BC.
- **Resume cost (I3):** every pre-R582 bcdev run has `kill_reproduced` NULL, so resuming one re-executes every
  kill and republishes and re-baselines nearly every batch. Start a fresh run instead (CHANGELOG).
- **Two timeout costs (I4):** one more full budget per timeout kill, and a second `StopHungRunAt` stop whose
  outcome may be unconfirmable, which scores `error`, not `timeout-killed`. On the next real BC campaign,
  count `stop-outcome-unconfirmed` against `timeout-killed` (also in R577's Known limits).
- **R592 (M8):** `backendBuildRefusal` still lends between bcdev and v2 al-runner. Both backends now write the
  marker, so marked kills lend in both directions; read R592 with that in mind.
- **What the rule cannot catch (M9):** a RANDOM flake, yes; a test whose outcome alternates with committed
  state (fail, pass, fail), no. The unmutated confirm already catches the common non-idempotent case as
  `unstable`.
- **verify's own kills are not evidenced live (M4):** they go through the same loop, but `VerifyResult` has no
  `killReproduced`.
- `itest:alrunner` was not re-run: its itest changed only to pass the run id to `killerRows`, a filter that can
  only remove rows of older runs.
