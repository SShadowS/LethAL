Found by coord PR-67 (lethal-code, 2026-11-17), while publishing DO's Continia 30 dependencies to `bc4` with
`scripts/bc-continia-publish.ts`. Evidence: `/coord/handoff/PR-67/bc4/publish.log`; the server state is in
`docs/gates/servers.md` §"bc4: BC 29".

**What happened.**
- Continia System Application, Core and Connector App 30.0.0.0 published.
- Continia Customer Onboarding 30.0.0.0 was refused with HTTP 422: "Could not install the extension ... due to the following
  error: Text optimized index cannot be created/queried because the SQL Server Full-Text Search component is not installed".
- BC restored the original extensions. The apps after it were not attempted.

**Why it matters to a user.** A user's target or test app can depend on an app whose table declares a text-optimized index. The
server's SQL then needs the Full-Text Search component. The first sign is a failed publish, after the compile and the
dependency publishes before it. The 422 names the cause, but only for that one app, and only once LethAL (or the user) has
already changed the server.

**Possible fix.**
- `lethal doctor --project` reads the target's and the test app's dependency packages. Where a table of one of them declares
  a text-optimized (`OptimizeForTextSearch`) index, doctor says the server needs SQL Full-Text Search, before anything is
  published.
- Whether the server HAS it cannot be read over the dev endpoint (to be checked). Until then the check names the need, not the
  server's state.
- The friction log of PR-67 (`/coord/handoff/PR-67/friction.md`) also lists doctor not comparing declared dependencies with
  the server's installed versions (item 6). The two belong in one doctor check.

**Refined and built (coord PR-128, lethal-code, 2026-11-17; spec `docs/superpowers/specs/2026-11-17-pr128-text-search-dependencies.md`).**
- **The owner's answer** (q-20261117T183405-4c6fee36): bc4's SQL Server was recreated on an image with Full-Text Search
  (`FULLTEXTSERVICEPROPERTY('IsFullTextInstalled')=1`), and all 7 Continia 30 apps then installed. So the component is readable
  in SQL, but no call LethAL makes through BC reads it. The check therefore warns from the package side.
- **The package side:** a field property `OptimizeForTextSearch` in a package's `SymbolReference.json` (Customer Onboarding: 3
  fields).
- **What "installed" proves:** only that that app's install succeeded. Microsoft Base Application declares the property on 147
  fields and is installed on servers WITHOUT Full-Text Search, because it ships in the database. A NEW extension install is what
  fails.
- **The check `text-search-dependencies`** scans the project's dependency closure (the target, plus the test app with `--tests`)
  and reads installed versions by id:
  - it fails when such an app is not installed at the cached version or newer, naming the app, up to 5 table.field and the SQL
    feature;
  - it passes when each such app is installed at that version, and says only that the install succeeded.
- **Live:** bc2 FAILS (Customer Onboarding, a non-direct dependency, not installed); bc4 PASSES. Evidence:
  `/coord/handoff/PR-128/doctor-bc2-2.json`, `doctor-bc4-2.json`.
- **Not done here:** the `--predict` note in `scripts/bc-continia-publish.ts` belongs to PR-67, which owns that script.
