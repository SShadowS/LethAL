**Measured.** While the R-289 probe sidecar and the `itest:hang` gate shared one BC user, the
container's Application event log recorded event Id 705, "Request was throttled. It either
timed-out or was cancelled.", with `"Requests running": "5"`, `"Requests waiting": "6"`,
`"Operation": "ODataV4"`. Separately, `GET ODataV4/$metadata` answered headers fast, then its body
stalled short of complete and never finished: measured at 65,262 bytes, twice, on a plain `curl`
call against Cronus284, outside the sidecar. After the owner restarted Cronus28 and the probe ran as
a separate BC user (LETHALPROBE) rather than the gate's own, `itest:hang` passed 3 out of 3
([[R289]]'s 2026-09-28 P1 results). Full detail and the incident timeline:
`docs/measurements/2026-09-27-nst-wedge-incidents.md`, section 6.

**Not measured: whether five is a per-user concurrency limit.** Event 705's `"Requests running":
"5"` is a count at the moment the event fired, not a confirmed configured ceiling. The same
measurement document's section 1 quotes `"Max Active Request Count": "100"` from the same kind of
event on an earlier occasion, which does not fit a hard 5-per-user reading. "BC throttles OData V4
at 5 concurrent requests per user" is a plausible risk this item raises, not a measured limit, and
this repository has no Microsoft documentation of the behavior to cite; none is cited here.

**The measured rule, now built into the probe tooling regardless.** Probes run as a separate BC user
(LETHALPROBE), never the gate's own config's user, with at most 2 concurrent requests, and they do
not call `$metadata` at all. This is enforced in code, not left to habit:
`scripts/r289-probe/sidecar.ts`'s `pickProbesToRun` caps concurrency (unit-tested in
`sidecar.test.ts`), and the sidecar refuses to start if its own user equals the gate config's
`bcdev.username` (case-insensitively, after trimming both; `sidecar.test.ts`). See
`scripts/r289-probe/README.md` and the pre-commitment's ADDENDUM
(`docs/superpowers/specs/2026-09-27-r289-probe-precommitment.md`).

**What the earlier `itest:hang` failures overlapped with.** The 2026-09-27 occurrences behind
[[R289]] ran while the probes shared the gate's own BC user, in a window whose event log also shows
OData throttled on the event above, before the owner restarted the containers. That overlap is
consistent with the shared-user theory but does not prove it caused those failures, and it does not
cover the first (2026-09-26) occurrence, which predates the probe tooling entirely. On a restarted
Cronus28, with a separate probe user, the gate passed 3 out of 3 ([[R289]]'s 2026-09-28 P1 results).

**Open question, not a claim.** Whether LethAL's own runs can hit the same per-user throttling is
not measured. A grouped mutant run makes several `RunMutant*` calls; if enough of them land
concurrently under one BC user (for example several sessions against the same tier, or a batch of
grouped calls that overlap in flight), per-user OData throttling could affect LethAL's own gate,
independent of any probe. Nobody has measured LethAL's own peak concurrent-request count per user
against whatever this platform's real ceiling turns out to be.
