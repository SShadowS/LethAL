id: "R317"
title: "Business Central throttles OData V4 at 5 concurrent requests per user, and a shared probe user can starve the gate it is watching"
section: "backends-and-tooling"
order: 990
status: "open, filed 2026-09-28"
---

**Measured.** Business Central throttles OData V4 at 5 concurrent requests per user. While the
R-289 probe sidecar and the `itest:hang` gate shared one BC user, the container's Application event
log recorded event Id 705, "Request was throttled. It either timed-out or was cancelled.", at 5
requests running and 6 waiting on `ODataV4`. A shared user can throttle the very gate the probe is
trying to observe: the probe's own calls compete with the gate's for the same 5-request ceiling.

**What triggered it.** `GET ODataV4/$metadata` answers headers fast, then its body stalls short of
complete and never finishes (measured at 65,262 bytes, twice, on a plain `curl` call outside the
sidecar). A held `$metadata` call can occupy one of the shared user's 5 OData V4 slots for as long
as it stays open. Full detail and the incident timeline: `docs/measurements/2026-09-27-nst-wedge-incidents.md`, section 6.

**The measured rule, now built into the probe tooling.** Probes run as a separate BC user
(LETHALPROBE), never the gate's own config's user, with at most 2 concurrent requests, and they do
not call `$metadata` at all. This is enforced in code, not left to habit:
`scripts/r289-probe/sidecar.ts`'s `pickProbesToRun` caps concurrency (unit-tested in
`sidecar.test.ts`), and the sidecar refuses to start if its own user equals the gate config's
`bcdev.username`. See `scripts/r289-probe/README.md` and the pre-commitment's ADDENDUM
(`docs/superpowers/specs/2026-09-27-r289-probe-precommitment.md`).

**Every earlier `itest:hang` failure that led to [[R289]]** happened either under this shared-user
condition, or while OData was already stuck on the same event (5 running, 6 waiting), before the
owner restarted the containers. On a restarted Cronus28, with a separate probe user, the gate passed
3 out of 3 ([[R289]]'s 2026-09-28 P1 results).

**Open question, not a claim.** Whether LethAL's own runs can hit the same per-user cap is not
measured. A grouped mutant run makes several `RunMutant*` calls; if enough of them land concurrently
under one BC user (for example several sessions against the same tier, or a batch of grouped calls
that overlap in flight), the same 5-concurrent-per-user ceiling could throttle LethAL's own gate,
independent of any probe. Nobody has measured LethAL's own peak concurrent-request count per user
against this ceiling.
