**What.** R-236b (the TestPage reply readback, control app 1.0.0.20) reads a kept answer back only
AFTER a call already reports `in-flight-unknown`. There is no body-stall watchdog that reads early,
so a lost reply still costs the full budget, up to the baseline timeout or the grouped path's hard
cap, before the readback even runs. This was a deliberate scope cut, not an oversight:
`docs/superpowers/plans/2026-09-27-R-236b-testpage-reply-fix.md`, "Decisions this plan applies":
"No early readback (no body-stall watchdog); filed only."

**And.** The same section rules out any automatic recovery from a wedge: "No restart recovery. Every
wedge (a failed preflight after a hit) stops that run and goes to the owner through `coord ask`."
R-236b's own acceptance measurement exercised this directly and found nothing different: the a2-prep
session's hit and the second C1b run's call 1 both wedged Cronus284 on 2026-09-27, and both were
handled by a manual `coord ask`, never a restart the fix itself attempted. See
`docs/superpowers/specs/2026-09-27-r236b-reply-fix-precommitment.md` OUTCOME.

**Cost.** Every TestPage-reply hit still pays the full timeout before any recovery is attempted, and
every wedge still needs a human in the loop. Neither is a regression (both are pre-existing costs
R-236b did not set out to fix), but both remain open costs of the shipped design.

See R236 (the fix this scope was cut from), R263 (the wedge-rate measurement, updated 2026-09-27 with
the same day's two wedges).
