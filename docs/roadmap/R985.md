From GitHub #28's reporter (2026-11-13) and coord task R-970. Related: [[R159]] (the operator), [[R121]] (kills without an
assertion), upstream aldevtools/BusinessCentral.AL.Runner#8006.

**What was measured.** The #28 reporter, on a BC 28.0 container (`bcdev`): a `toggle-blank-temporal` mutant turned a `0D` into
`17530101D`; the value was later assigned to a `Date` field of a normal table and written with `Modify`, and BC failed the write:
"Cannot write the value 01/01/1753 to the field ... because the value is either too long or the content is invalid." SQL stores
`0D` as 1753-01-01, so BC refuses that exact value. al-runner (edge-c8fe56e05) refuses the same `Modify` instead of failing
(upstream #8006, invented repro in `/coord/handoff/R-970/p1753/`); its `Insert` of the value already fails with BC's text, and
`17530102D` writes on both.

**Why it matters to LethAL.** `toggle-blank-temporal`'s Date substitute is chosen as "the least plausible real business value", and
it is exactly the value BC will not store. Wherever the toggled value reaches a table write, the mutant dies on the write whatever the
tests assert: the overflow shape `toggle-blank-string` avoids by writing one character, and the false-kill shape R121 screens for.
Its DateTime substitute `CREATEDATETIME(17530101D, 000001T)` is not measured.

**Fix shape (not built).** A Date substitute BC stores (for example `17530102D`), measured on BC and al-runner for Insert and
Modify; the DateTime one measured too. It changes every Date mutant's text, so the tables gate (19 temporal mutants) and the v3
tables leg move: a pre-commitment first. Not measured: how many of the reporter's or the gates' temporal kills came from a write.

**Re-checked (coord R-981, 2026-11-14, edge-736fc7677):** #8006 still open; the Modify of `17530101D` is still refused (not run)
while the Insert fails with BC's text.
