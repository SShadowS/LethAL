Found by R-984's DO windows t5 and t6 (lethal-bugs, 2026-11-16; `/coord/handoff/R-984/t6-block.md`), where it was t6's BLOCK.

**Measured.** Two DO mutants, each with the same covering-test set in the same order in both windows, both kills reproduced:
- `CDOEMailHandler:462` (void-method-call): t5 timeout-killed by a test that hangs (position 14 in the covering list); t6 killed in
  432 ms by an assertion in another test (position 3).
- `CDOMailMessageBuilder:137` (toggle-blank-string): timeout-killed both times, by two different hanging tests (positions 17 and 2).

Each mutant has more than one killing test, and one of them hangs. Which one LethAL meets first depends on two inputs that differ
per window by design: R987's entries cap, MEASURED per window (about 119, 41, 208, 230, 201 and 38 entries per request in t1 to
t6), which packs the same tests into different requests that a timeout cut (R895) ends early; and [[R197]]'s order, which puts first
the tests that already killed in the same procedure this session. So the verdict CLASS (killed vs timeout-killed) and the killing
test are not stable across runs for such a mutant.

**Handled for now** by a comparison rule, not by the product (orchestrator ruling 2026-11-16; `/coord/handoff/R-998/do/verdict-rule.ts`,
tests red-checked for each condition): killed and timeout-killed count as the same verdict, with the killing test exempt, only when
one side is timeout-killed, both sides reproduced, and the covering-test set is identical. Everything else stays strict.

**Possible fix** (not built): after a request is cut at a timeout, run the covering tests not yet answered that come before the hung
test in covering order, and score the earliest failure. The verdict class then follows the covering order, as a test-at-a-time run
would. Cost: runs on mutants already known to be killed.

**To close.** Either the fix, with a test that the same mutant scores the same class whatever the request packing, or a ruling that
the comparison rule is the permanent answer.
