**Found by R-297 Task 6 (2026-09-28)**, plan
`docs/superpowers/plans/2026-09-28-R-297-instrumentation-real-corpora.md`, Task 6. Sibling of
[[R287]]'s C7 (`preproc_fragmented_else_tail`), which has the same cause.

**The shape.** `#if not SYM` / `if C then begin` / `#endif`, then statements, then the closing
`end;`, either inside a second `#if` (`preproc_split_if_then_begin`, whose `begin` is the
`preproc_split_begin` token) or bare after the shared statements
(`preproc_split_if_begin_asymmetric`, which compiles in ONE build only, as it does in the corpus).

**What goes wrong.** The statements between the `begin` and the `end` are direct, unfielded
children of the split node, not of a `statement_block`. `isStatementPosition` and `isStatementSlot`
(`packages/engine/src/ast/tree-walks.ts`) both answer false, so `remove-assignment` and
`void-method-call` skip them, and `gapBlockOf` puts them in the whole procedure body's gap.

**Measured on hand-written repros** against a de-preprocessed twin (check b, operator multiset over
the statements both contain): both shapes FAIL, the twin has `remove-assignment` and
`void-method-call` at the two block statements and the split has neither; check c FAILS on the gap
partition. No throw, and alc PASS for the symmetric shape under both symbol sets; the asymmetric
shape compiles with the symbol absent and its SOURCE fails with it defined, the same as the corpus.

**Corpus counts** (Task 0's census): dc 2 files with `preproc_split_if_begin_asymmetric`
(`CDCContiniaOnlineMgt.Codeunit.al`, `CDCReqAppvlReasonCmt.Page.al`); BaseApp 1 file with
`preproc_split_begin` (`ProdOrderComponent.Table.al`, inside [[R287]]'s C7 container).

**Why it is not a small fix.** Admitting these needs `isStatementPosition` to treat the split node as
a statement list. That predicate also decides dispatch bracing (`compile.ts`) and where a reach
marker goes (`dispatch.ts`), so it is a new placement rule, not one slot entry. The same change
would close [[R287]]'s C7.
