**Filed 2026-10-25 by lethal-spare (coord task R-771).** Evidence: `/coord/handoff/al-runner-v3-update/2026-10-25-b.log`
(line 9) and `/work/tools/al-runner-v3/infra/edge-a157b2d34.receipt.json`.

**What happened.**
1. The daily update gate checked edge `al-runner 3.0.0-alpha.5+edge.20261025 (a157b2d34)` and reported `infra-fail`.
2. The build was not at fault. The gate runs in a worktree at `.gated`'s `lethalCommit` (6529c3cc), as designed (never
   a moving master).
3. The update script on master judges the receipt against master's `V3_GATE_LEGS`. That list had gained S1E (R761)
   and N1S (R763), and 6529c3cc runs neither.
4. `scripts/al-runner-v3-update.ts` (around lines 188-197) found S1E missing and read the whole receipt as
   infra-fail. Every leg the old commit did run was `pass` or `held`.
5. `current` did not move, which is correct. But the candidate's real outcome was hidden behind a reason that names
   the receipt, not the cause.

**When it recurs.** Every time master adds a leg to `V3_GATE_LEGS` and the next `--edge` (or `--edge-rejudge`) runs
before a `--regate` of `current` at a commit that has the leg. That is the normal order of work: a lane merges a new
leg; the next morning's gate runs.

**Proposed fix (either is enough; the first is better).**
- Before gating a candidate, the update script compares `V3_GATE_LEGS` with the legs `.gated`'s `lethalCommit` can
  run. If any are missing, it re-gates `current` at the script's own commit first, under the same lock, and only then
  gates the candidate. If that re-gate fails, it stops with that failure: `current` itself no longer passes the gate
  at master.
- At least: the infra line names the cause, for example `infra-fail: .gated's lethalCommit 6529c3cc predates leg(s)
  S1E, N1S of V3_GATE_LEGS; run --regate <master> first`, instead of "every leg ... must be present".

Either way, a test with a stub receipt missing a newly added leg pins the new wording, or the re-gate call.

**Workaround used today.** `--regate 55a1466b` for `current` (dcdf9e821), then `--edge` again (R-771).

**Fixed (coord task R-777, the first proposal).** Tonight R-784 (O1), R-788 and R-790b each needed a manual regate.
- New: `gatedWithAllLegs` in `scripts/al-runner-v3-update.ts`. Before the alpha path, `--edge` or `--edge-rejudge`
  gates a candidate, it reads `V3_GATE_LEGS` at `.gated`'s commit (`git show`, `parseGateLegs`).
- If that commit lacks a leg, it logs `stale-gated` with the missing legs, and re-gates `current` at the script's own
  commit, under the same lock. The candidate is then judged at the new `.gated`.
- If that re-gate does not pass, or the script's own commit lacks the legs too (uncommitted legs), no candidate is
  gated. The run reads `skipped`: `--edge-rejudge` exits 2, and `--edge` does not mark the commit seen.
- `readReceipt` is unchanged. A receipt that is missing a leg its own gated commit has is still `infra-fail`.
- Tests: `scripts/al-runner-v3-update.test.ts`, "R777". They cover each call site; a failing re-gate; the script's
  commit lacking the legs; and the not-stale direction. Each was red-checked: never re-gating, always re-gating,
  dropping the own-commit check, and each of the three call sites left unguarded all went red.
- Checked against the real git: 6529c3cc reads as missing S1E, N1S and O1. The live `.gated` (4aa6ca6d) has all 17
  legs. There is no `--dry` mode or scratch tools root, so no live update run was made.
