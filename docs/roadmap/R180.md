## What breaks, and for whom

`empty-block` decides what to claim from the PARENT node kind:

```ts
const BODY_PARENT_KINDS = new Set([procedure, trigger, if_statement, while_statement,
                                   for_statement, repeat_statement, case_statement]);
```

`case_statement` is in that list, and it matches **nothing**. A case arm's body is a block whose
parent is `case_branch` (or `case_else_branch` for the `else`), never `case_statement`. So every
`case` arm with a `begin ... end` body is unmutated by this operator, and the entry that looks like
it covers them is dead.

This is [[R161]]'s shape one construct over: a guard that names a plausible node kind rather than the
one the grammar produces, costing sites silently. It is also the third time a `rawKind` mismatch has
hidden a whole population ([[R120]] is the other), and the second time in this row's own
investigation, since the first census pass looked for `"block"` when the grammar emits `"code_block"`
and found zero of everything.

**291 claimable sites, 22x R13's bar**, and `empty-block` claims **0** of them today.

## How this was found, and the two candidates it replaced

R159 asked whether `case_statement` (310 occurrences, the last unclaimed control structure) deserved
an operator. Two were sized and both are SUPERSEDED by the one-line fix:

- **Remove the ELSE arm**: 58 sites, 56 with no existing mutant that blanks them. Emptying the else
  BODY is 58 of the 291 above and asks the same question, so a separate operator is not needed.
- **Remove a case BRANCH**: 1,003 arms, 241 with nothing that blanks them. Where the case has no
  `else` (789 of 1,003) deleting an arm and emptying it are behaviourally identical, so most of that
  is the same fix. The genuinely distinct part is fall-through to `else`, 214 arms, and it is not
  worth an operator on its own.

Case arms are otherwise well covered: **3,218 mutants already sit inside case statements** from other
operators mutating the arm bodies' contents. What was missing is the coarse "does this whole arm
matter" question, which is exactly `empty-block`'s.

## The fix, and why it is not landed here

Add `case_branch` and `case_else_branch` to `BODY_PARENT_KINDS`, and delete `case_statement`, which
matches nothing. One line net.

**It is not landed because NO fixture contains a `case` statement.** Measured: the four `case` tokens
in `fixtures/sandbox-data` are the English word inside comments, and the other four fixtures have
none. So the fix would add 291 mutants to a real corpus and ZERO to every gate — precisely the
situation [[R171]] hit, and it was answered there by adding an arm so the change is exercised by a
gate rather than by a unit test alone.

## What the build needs

1. A `sandbox-data` arm with a `case` statement: at least one `begin ... end` arm, one single-statement
   arm (which must gain NOTHING, since only block bodies are claimed), and an `else` arm.
2. Every added mutant pre-committed before the run, per this project's standard.
3. One consideration worth checking in that arm rather than assuming: a case arm inside a LOOP whose
   body advances the loop's condition would make this a fourth non-termination source ([[R179]]).
   `sandbox-data` has no loops, so an arm placed there cannot test it; the question is whether to
   also place one in `sandbox-hang`.
