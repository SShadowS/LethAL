Found by coord task R-882 (BC.History Payment Practices on `bc5`, round 3, 2026-11-09). Evidence: `/coord/handoff/R-882/S2.report.json`,
`S2.stderr.txt` (mutant M0281). Related: [[R164]] (a hang-capable site never enters a gate), [[R501]] (the one dispatch-level hang
refusal, `openItemHangRefuses` in `loop-hazard.ts`), [[R890]] (why v3 did not see it).

**The shape.** `PaymentPracticeBuilders.Codeunit.al`, `BuildPaymentPracticeDataForCustomer` (and the vendor twin at line 41): a
`repeat ... until CustLedgerEntry.Next() = 0` walk. For an excluded customer the body skips that customer's entries:
`SetRange("Customer No.", ...)`, `FindLast()`, `SetRange("Customer No.")`, so the next `Next()` moves past them.
`lethal.swap-find-direction` turns that `FindLast()` into `FindFirst()`: the cursor goes back to the customer's first entry, `Next()`
lands on its second, which is skipped the same way, and so on. For any excluded customer with two or more entries, the loop never
ends.

**What happened.** On BC (bcdev, fenced) the test `ReportDataSetForCustomersByPeriod` ran past its budget under M0281; LethAL
abandoned it in flight and quarantined the tier. The run stopped after 403 of 880 mutants, and the next two runs refused on the
quarantine. Recovery needs a server restart (the `recover-tier` skill). On al-runner v3 (R-881 `pp1`) the same mutant
`survived`, at 6.6 s: under v3's `--isolation test` that test's data may never have reached the branch (R890).

**Why it was not refused.** `openItemHangRefuses` refuses loops that consume their record set, loops that move the record they walk
(R-696), and several callee shapes, but has no rule for a cursor JUMP (`FindFirst`, `FindLast`, `Find('-')`, `Find('+')`) on the
walked variable itself inside the walk's body. R-531's consuming-loop rule even exempts `swap-find-direction`, but only inside the
loop's own condition; this site is in the body.

**Fix sketch.** Refuse `swap-find-direction` (and any operator that changes the jump's direction or removes its filter) on a find
call whose receiver is the loop's walked record, inside a `repeat ... until <R>.Next(...)` body. Pin it with a fixture shaped like
this one, offline (R164: never in a gate).
