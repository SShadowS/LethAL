**Stay on the newest tree-sitter-al.** Policy, not a defect: a grammar bump silently changed node shapes once (v2.5.0 → v3.0.1 inserted container nodes and zeroed `statementCalls` 703,239 → 0). The bump procedure — corpus site counts plus a **per-site** baseline proof, not a multiset signature — is in `packages/engine/vendor/README.md`. Re-check on every upstream release.

---

**CHECKED AND BUMPED 2026-08-08. Full evidence in `packages/engine/vendor/README.md`
§"The 3.0.1 -> 3.2.1 bump".**

The check found us three tags behind. The vendored binary was built at `f150581`, already past the
`v3.0.1` tag, so the changes actually taken on were two parse-correctness FIXES — v3.1.0 (`TableData`
as a first option member; whitespace-tolerant `# pragma` / `# region`) and v3.2.0 (whitespace-tolerant
`# if` / `# elif`, depth-correct) — plus a parser regeneration on the same tree-sitter CLI. Nothing
renamed, nothing re-parented.

**The per-site instrument this row's procedure requires did not exist, and now does.**
`packages/engine/vendor/README.md` has always said the proof is "corpus site counts plus a
**per-site** baseline proof, not a multiset signature", and the only tool was
`probe-grammar-corpus.ts`, which reports aggregate counts and a node-kind histogram. Counts caught
the v2.5.0 to v3.0.1 disaster because `statementCalls` went to zero; they cannot catch a bump that
keeps every total while moving WHICH sites an operator claims. R120 is why that is live rather than
theoretical: `ALNodeKind` is a CURATED subset and `ALSyntaxNode.kind` CASTS the raw tree-sitter type
into it, so a re-parented node changes what a comparison matches at runtime with no type error.

`scripts/census-operator-sites.ts` emits one row per (operator, file, line, column, before, after) for
every Tier-1 operator. Over 659 real AL files (Continia Document Output's `Cloud` plus its test app,
6.0 MB): **31,110 sites, and the two JSON outputs are byte-identical.** 0 sites only in the old
grammar, 0 only in the new. Aggregate counts identical too, 100% clean parse both ways, `bun test`
2,069 pass / 0 fail, and the live tables gate PASS at 109 killed / 17 survived / 10 no-coverage with
`untargetedTriggers=0`.

**What the bump does NOT prove, and it is the honest half:** the two fixes are for shapes this
corpus does not contain, which is exactly why every number is identical. The measurement says the
bump costs nothing. It does not say it gains anything — the gain is on code the old grammar
misread, and no corpus available here carries it.

**RE-CHECKED 2026-08-08, no action.** `git ls-remote --tags` lists `v3.2.1` (`335d1ff`) as the
newest tag, which is the vendored pin. HEAD is `44ba214`, ahead of the tag and untagged.

Recording the untagged-HEAD case because it is a decision, not an absence of one: this row's
procedure is "re-check on every upstream release", and untagged work is not a release. Vendoring a
moving HEAD would mean the per-site proof is against a commit nobody else can name. If a shape this
project needs is only on HEAD, the right move is to ask upstream for a tag, not to pin the commit.

**RE-CHECKED 2026-08-19, no action.** `git ls-remote --tags` newest tag is `v4.0.1` (`58c236f`),
which is exactly what `packages/engine/vendor/` pins. Recorded rather than skipped: this row's whole
value is that the check happened on a date, and an unrecorded check is indistinguishable from one
nobody did.

**Instrument widened 2026-08-20.** The per-site proof this row's procedure depends on ran TIER 1
ONLY — `census-tier1-sites.ts`, now `scripts/census-operator-sites.ts`, covering all eighteen
registered operators across both tiers.

That was a hole in the safety net rather than a cosmetic gap. This row exists because a grammar bump
once changed node shapes silently (v2.5.0 -> v3.0.1 inserted container nodes and zeroed
`statementCalls` 703,239 -> 0), and the answer was a per-site proof. Half the operators were outside
it, and they are the half most exposed: Tier 2's receiver and shadowing predicates read node kinds
and field names directly, which is exactly what a re-parenting bump moves.

Site counts recorded before this date cover Tier 1 only and are not comparable with later ones. The
next bump's before/after must be taken with the widened instrument on both sides.
