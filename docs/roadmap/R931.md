Found by lethal-code, 2026-11-11 (coord R-920, kraken's RunModal probe for R910). Related: [[R495]], [[R630]], [[R139]], [[R910]].

**What happened.** On a throwaway Windows BC 28.4.53241.57976 W1 server ("R910Win"), `lethal run` stopped before batch 0 with
`TestAppDriftedError: proven package:5b1e9f65, read package:4d039e18`; nothing had republished the tests app. Two back-to-back GETs
of the same `dev/packages` URL (`/coord/handoff/R-920/pkg-a.app`, `pkg-b.app`, 1933 bytes each) differ in exactly 16 bytes, at offsets
12 to 27: the package id GUID in the `.app` NAVX header. The zip payload after the 40-byte header is byte-identical. LethAL hashed the
raw bytes, so every read of the same package on that server gives a new hash. R139 measured the read byte-stable on a Windows
container of an older BC; every 28.x gate since ran on Linux BC, where the id is stable.

**Invented repro.** Two copies of one `.app` whose header GUIDs differ: `hashPackage` gives two different hashes, and a session whose
backend returns a fresh id on each read stops at batch 0 with `TestAppDriftedError`.

**Fix.** `hashPackage` hashes a NAVX-shaped package with its 16-byte package id zeroed; any other bytes hash raw. A real republish
still refuses: the zip holds the manifest's version and the sources, and any change there changes the hash. The shape is exact:
"NAVX" at 0 and 36, header length 40, version 2, and the u64 at 28 equal to the bytes after the header. Unsigned alc output has
it too, so the compiled test app carries `packageHash` (`hashPackage` of its bytes) beside its raw `sha256`: the publish read-back
and verify's `testAppHash` compare with `packageHash`; the publishers' "file changed since compile" check keeps the raw `sha256`
(review of the first fix: comparing a zeroed read-back with the raw file hash would have refused every test-app publish).

**Named limits.** A SIGNED package has bytes after the zip, so it does not match the shape, hashes raw, and would still drift on a
server that re-stamps its id. Stored `package:` keys from earlier runs (snapshots, history, a resume's pending hash) no longer match
for unsigned apps: they read as a different test app, so they are not reused (the safe side).

**Gates on 58018370:** `itest:bcdev`, `lease`, `verify` on bc1; `chunked`, `agreement` on bc3; `tables`, `testapp` on bc2; full
`itest:alrunner-v3` on edge-42af5d384. Logs `/coord/handoff/R-920/<server>/<gate>.log`, `v3.log`.

**Not enough on its own (2026-11-11).** Kraken's next run on 37def9fb still stopped with `TestAppDriftedError`: the Windows server
rebuilds the package per read and stamps every zip entry with the download time, so reads seconds apart differ beyond the id. The
two reads this fix was measured on came within one 2-second zip-time window. Continued in [[R932]].
