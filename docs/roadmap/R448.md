**Found 2026-10-05 by the owner** (CI failure mail). Last green: `346de436`. First red: `6ebd3df5`,
the merge that brought R-307 into `lethal/lane-code`. Every master push since is red on the `check`
job (Windows) and green on `unit-linux`. Evidence: GitHub Actions run 37236834819 (6259 pass, 14 fail).

**Failing on Windows only:**
- `scripts/measure-peak.test.ts`, "1 GB probe": peak reported as 1079320 against a bar of 2048 MB.
  R-307 T0 made `measure-peak` read Linux `maxRSS` as bytes; on Windows the unit differs.
- 13 R307 refusal tests in `packages/runner/tests/` (`identity-refusals.test.ts` T6 (b), T8, "one
  refused row per shape", "the per-file trial", and the duplicate-basename case in the runSession
  C3 block). In each, the file meant to be refused is NOT refused (the refused rows come back
  empty), which points at a Windows-only difference in how the refusal scan sees the file (line
  endings or path separators are the first suspects). If the cause is in product code rather than
  the tests, a real Windows user's header-unreadable file is instrumented instead of refused:
  report that first.

**Why it was not caught.** Every agent session now runs in a Linux container, and `bun
scripts/verify.ts` there matches `unit-linux` only. Nobody read CI before or after merging. The
orchestrator runbook now requires a green CI run on both jobs before a merge and a master check
after each push.

**To close.** Find the root cause for each group and fix it so both jobs are green; a red test per
direction where the fix is a platform branch. Reproduce through CI by pushing the task branch (CI
runs on every branch). Close when master's `check` job is green.
