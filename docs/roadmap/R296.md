title: "itest:tables' assertMatchesBaseline fails with a bare Error: the per-mutant difference lines never reach the output"

**Found while running R-236c's live gates, 2026-09-27.** `itest:tables` is expected to fail at
`assertMatchesBaseline` (`packages/runner/itest/baseline-guard.ts`) when GH-24's arm adds ten new
mutants that are not yet in the committed `tables.baseline.json`. It threw as expected, but the
gate's console output showed only a bare `Error` and its stack, with no message at all: none of the
ten per-mutant difference lines that `assertMatchesBaseline` builds into the thrown `Error`'s
message (via `diffMutants`/`normalizeForComparison` in `mutant-equality.ts`) reached the captured
output. The run's `main().catch` handler in `tables.itest.ts` prints `err.stack ?? err.message`, and
in isolation that prints the full message fine, so the loss happens somewhere between that call and
what actually got captured, which is not yet identified.

**What it cost.** The ten expected differences had to be re-derived by hand, after the fact, from
the run's own persisted rows (store run 9, 387 mutants), fed through the gate's own
`normalizeForComparison` and `diffMutants` against the committed baseline. That worked here because
the pre-commitment for that run
(`docs/superpowers/specs/2026-09-27-r236c-testpage-pre-refusal-precommitment.md`, OUTCOME,
prediction 1) had already named the expected ten differences and their shape, so there was a known
answer to check the reconstruction against. Without a pre-commitment to fall back on, this failure
mode leaves no way to read the blocking per-mutant check from the gate's own output.

**Why it matters.** `assertMatchesBaseline` is the per-mutant regression guard: CLAUDE.md's own rule
is "a differing verdict is a BLOCK, never close enough." A gate whose failure output hides its own
evidence defeats that: every baseline mismatch on any of the live gates that call
`assertMatchesBaseline` (`itest:tables`, and any other itest that adopts it) would print the same
bare `Error`, so a reviewer reading the gate's console output alone cannot tell WHICH mutants
differ, only that something did. The gate still fails loudly (exit 1), so it cannot pass silently,
but reading the actual per-mutant evidence currently requires reconstructing it from the store by
hand, which most failures will not have a pre-commitment to check the reconstruction against.

**Evidence.** `docs/superpowers/specs/2026-09-27-r236c-testpage-pre-refusal-precommitment.md`,
OUTCOME, prediction 1: "the gate printed the thrown error as a bare `Error` plus its stack, with NO
message, so the diff lines were not in the output. The per-mutant check was therefore redone on the
same run's persisted rows."

**To close:** find why the message printed by `tables.itest.ts`'s failure handler did not carry
`assertMatchesBaseline`'s diff lines when this ran live (it reproduces neither in the unit-test
suite nor in a standalone script, so it is specific to how the live gate was invoked or its output
was captured), then either fix the loss or have the gate write the diff to a file on disk in
addition to the console, so a differing-mutant failure is never unreadable from the gate's own
output.

**Root cause (closed 2026-09-29, b2085e51).** Not a handler and not the receipt writers: a Bun bug,
oven-sh/bun#34398. Bun builds `err.stack` on the first read and reads `message` then; if a garbage
collection runs between an async throw and that read, the header comes out as a bare `Error`. Every
gate prints `err.stack ?? err.message`, and a live gate collects plenty before the catch runs (the old
tables catch awaited `emitFailed` first; `main`'s `finally` awaits `rm` of two scratch trees). Offline
there was too little heap pressure, which is why it never reproduced. Reproduced offline through the
real `assertGateBaseline` with `Bun.gc(true)` before the gate's print: bare `Error` plus frames, the
live output exactly. Fix: `baseline-guard.ts`'s `withStack` reads the stack once where the error is
made, in `throwOnDiff` (the one place all three baseline asserts throw a diff) and the two refusals.
`tests/baseline-guard.test.ts` runs a child process that forces the GC and asserts the difference line
reaches stderr; red-checked. Every other async-thrown gate error is still exposed: R346.
