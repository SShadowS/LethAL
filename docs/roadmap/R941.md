Found by lethal-code, 2026-11-12 (coord R-925, Sustainability on al-runner v3). Related: [[R900]], [[R938]]. The same gap as [[R943]] (filed separately the same day); both close on one fix, recorded in R943.

**What happened.** 4 of Sustainability's baseline tests were refused with `DotNet new Newtonsoft.Json.Linq.JObject: assembly
'Newtonsoft.Json' could not be loaded: FileNotFoundException`. `Newtonsoft.Json.dll` is in the Windows BC service folder R900 names
(`/coord/cache/bc28-service-windows`); run alone with `al-runner test ... --dotnet-assembly-dir` pointing there, the load works (the
tests then stop on a separate refusal, upstream #7775 row 4). LethAL's `AlRunnerV3Config.assemblyProbingPaths` is documented "alc's
`/assemblyprobingpaths:` for both compiles ... Not passed to al-runner: its `--dotnet-assembly-dir` is a separate, runtime knob", and
nothing else sets that knob. R-925's prep also left the probing path out of Sustainability's config, because the app itself declares
no .NET type (a dependency's code does); `alc` compiled without it, so nothing warned.

**Invented repro.** A target whose dependency uses `DotNet "Newtonsoft.Json.Linq.JObject"` at run time: `lethal run --backend
al-runner-v3` compiles and refuses the test with the load error; `al-runner test --dotnet-assembly-dir <folder>` runs it.

**Wanted.** Pass the probing paths to al-runner as `--dotnet-assembly-dir` too (one config field, two consumers, or a second field if
the folders differ), and say in R900 which folders v3 reads at run time. Measure on Sustainability's 4 tests and on the R-925 apps
that declare .NET (fsi, smtp) that nothing else moves.
