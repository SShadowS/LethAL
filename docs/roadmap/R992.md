Found by the orchestrator, 2026-11-14, on coord task R-979 (ticket 310). Related: [[R953]] / [[R972]] (admission by memory), [[R991]].

**What happened.** `build-native-parser` under `heavy-slot.sh --wait --peak build` (1 GiB) waited 36 minutes. The held slots had declared
12 + 8 + 8 = 28 GiB, so the second check (held peaks + peak + reserve = 28 + 1 + 4 = 33 > 32) refused it on every poll, while
`memory.current` read 16.9 GiB (16.9 + 1 + 4 = 21.9 fits).

**Why.** R953's rule admits a job only when BOTH checks fit: what the container uses now, and what the held slots DECLARED (because a
young job grows to its peak later). The declared sum is the safe one, and for a large job it is right. For a job far smaller than the
gap between the declared sum and `memory.current`, it is very conservative: a 1 GiB build cannot push the container over its limit
unless the held jobs reach their full declared peaks at the same moment.

**Not decided here.** R991 (R-979) only stops a refused waiter from being overtaken forever; it does not change the admission math,
which the owner ruled (R953, R960: memory decides, both checks). A change, for example a small-job allowance (a peak at or under N GiB
needs only the current-use check) or counting a held slot at the larger of its current use and a fraction of its declared peak, would
change admission for every lane and needs the owner's ruling and a measurement of how close the held jobs come to their declared peaks.

**Ruling** (kraken for the owner, `q-20261114T100041-36371d53`): measure real against declared peaks for a day, then choose (a) a
small-job skip or (b) partial counting; meanwhile do not make small jobs wait.

**Built (coord task R-987).** (1) The small-job allowance: a job declaring at most 2 GiB is admitted when `memory.current` + its peak
+ the 4 GiB reserve fits under `memory.max`, even if the declared-sum check says no, while fewer than two jobs admitted this way are held
(`memoryVerdict`'s `small`, `SMALL_JOB_MAX_GIB`, `SMALL_JOBS_MAX`). Fail closed: no `memory.current` (the rule is off, as before), or any
held slot whose class file cannot be read, means no allowance. The guard marks such a job's class file ` small` (so it is counted) and
logs each such admission to `<lock dir>/heavy-small-admits.tsv` (time, slot, class, peak, used, declared sum, max, pid). (2) The
measurement: every admitted job runs beside `scripts/heavy-slot-peak.ts`, which samples its process tree's RSS every 5 s; when it ends
`heavy-slot.sh` appends start, end, slot, class, declared GiB, measured GiB (`?` if it ended before a sample), exit code, its class file
and the command to `<lock dir>/heavy-peaks.tsv`. Found while building it: a SIGTERM to the sampler that arrives before it becomes bun
makes that forked copy of `heavy-slot.sh` run the EXIT trap (it removed the job's class file and ticket), and one that arrives while bun
starts can be lost (the sampler and the shell then wait for each other); the sampler is stopped with SIGKILL, which runs no trap
(red-checked: with SIGTERM a run of quick commands loses the class file in every run). Tests
inject readings: each condition both ways (fits, does not fit, a reading fails, a third small job, over 2 GiB), the mark, the ledgers.

**Next (the measurement day, from when this lands).** Summarise `/coord/locks/heavy-peaks.tsv` per declared class (serve 8, baseline 12,
gate 2, build 1, and custom peaks): measured against declared (median, max, the share above 80 % of declared), and how often the
allowance admitted (`heavy-small-admits.tsv`); then the owner chooses (a) or (b).
