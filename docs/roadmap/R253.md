**Reported in GitHub issue #9 (side report 2), measured by the reporter on `bc-linux`; not
reproduced here.** `HarnessVerifier.fetchCompanies` reads `api/v2.0/companies` under the same base
URL as the OData web services, and that base comes from `odataBaseUrl`, which forces port 7048. On
a Windows BC container both are served on 7048. On `bc-linux` the OData V4 endpoint is on 7048 and
`api/v2.0` is on 7052, so the call returns HTTP 404 (`Resource not found for the segment 'BC'`) and
`lethal doctor`'s `company` check fails while every other check passes and a real run works.

Not only the `company` check: `HarnessVerifier.fetchExtensionInstalled` (doctor's test-app check,
issue #23) reads the same `api/v2.0/companies` list through the same base, so it should fail the same
way there. A run never reaches either method, so the damage is a false alarm, not a wrong verdict.

**To decide the fix, measure first:** which ports a `bc-linux` server serves OData and the API on,
and whether an explicit `bcdev.baseUrl` or a separate API base in config is the honest way to name
it. Guessing a second hard-coded port would repeat `odataBaseUrl`'s own assumption.

## Done 2026-10-23 (R-253, lethal-bugs)

**Measured** on bc2 under lane bugs' lease, read-only (`/coord/handoff/R-253/bc2-api.json`, `probe-api.ts`).
`GET api/v2.0/companies` behaves as follows:
- **the API port (7152): 200**, with 2 companies;
- **the OData port (7148): 404**, `BadRequest_NotFound`, "Resource not found for the segment 'BC'.";
- **the dev port (7149): 404.**

So BC on Linux serves the API on its own port only, as the issue reported.

**Most of the fix was already there.** R-589 (69a7f009) added `bcdev.apiBaseUrl`. Every API read in `HarnessVerifier`
(`readApiRows`) uses `apiBaseUrl ?? baseUrl`, and `bc-linux-setup.ts` writes it into every gate config. So doctor
on bc1-bc3 is green today: no gate or setup log since then shows the false failure. The one false
`[FAIL] company` / `[FAIL] test-app-present` pair on record is R-589's own bc1 setup on 2026-10-21, before the
field existed. Setup's doctor step does read the result: it fails the setup run.

**What was still wrong:** a config with no `apiBaseUrl` on BC on Linux, as `lethal init` writes one.
- Doctor's `company` and `test-app-present` checks failed on a healthy server.
- R253's "a run never reaches either method" is no longer true. Since R496 every bcdev run checks each dependency
  installed through the same API read, so such a run is left unproven (`test-app-dependencies-unproven`).

**The fix, in one place** (`harness.ts`, `readApiRows`):
- With no `apiBaseUrl`, a 404 carrying BC's "Resource not found for the segment '<instance>'" wording, where
  `<instance>` is the base URL's last segment (`BC`), throws `ApiBaseUnsetError` (extends `Error`). That is the port
  not routing the instance at all. It names the base it tried and the fix: set `bcdev.apiBaseUrl`, e.g.
  `http://<host>:7052/BC`. A 404 naming any other segment (an API that is off on a Windows container) stays a real
  failure (build review M2).
- With `apiBaseUrl` set, the same 404 is a real failure, and so is any other 404.
- **Doctor** (`runCheck`) reports `ApiBaseUnsetError` as `[skip]` (`skipped: true`, `ok: true`), with the fix in its
  detail. The banner says "ok: no check failed, but N could not be checked", never "every check passed".
- **The JSON schema** (`doctor-v1`) gains the optional `skipped` field, and `ok` and the exit code now read "no check
  failed" (build review I1). The version stays 1: before R253 no check could be skipped, so every older report reads
  the same under either wording.
- **A run's dependency check** now carries the same named message.
- **`lethal init`** names `bcdev.apiBaseUrl` among the fields to fill in, for BC on Linux.

**Tests and red checks** (`harness.test.ts`, `doctor.test.ts`; `/coord/handoff/R-253/red-unit/`):
- a healthy BC-on-Linux config reads from the API port;
- with no `apiBaseUrl`, the segment 404 is `ApiBaseUnsetError`;
- with `apiBaseUrl` set, the same 404 is a real failure, and so are another 404 and a segment 404 naming another
  segment;
- doctor shows the error as `[skip]` without failing, with the banner checked, and any other failure still fails.

Red-checked, each restored:
- without the detection (`1-*`);
- detecting even with `apiBaseUrl` set (`2-*`, the over-wide direction);
- without doctor's skip (`3-*`);
- the generic segment match (`4-*`, another segment's 404 skips).
