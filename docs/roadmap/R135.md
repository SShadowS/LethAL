**LethAL's mechanism is a runtime guard wrapped around executable code, and a property cannot
dispatch at runtime.** `isMutableSite` therefore drops every declarative site, correctly. That
leaves whole BC bug classes unreachable no matter how many operators ship:

- **FlowField `CalcFormula`** — the `where(field/const/filter)` conditions and the
  sum/count/lookup method ARE business logic; a wrong filter in a CalcFormula is a classic silent
  bug. 91 CalcFormula lines in the 658-file Document Output snapshot. (`remove-calcfields` mutates
  the executable `CalcFields(...)` CALL today; the formula itself is untouchable.)
- **Query objects** — dataitem links, filters, method columns. **Zero query objects in the DO
  corpus** (2026-08-12 census), so this surface has no measured population yet; census a corpus
  that has them (BC.History) before ranking it.
- **Filter-bearing properties** — `DataItemTableFilter`, `SourceTableView`,
  `RunPageLink`/`SubPageLink`, `TableRelation` conditions.

Grammar 4.0.x removed the parsing blocker: single-entry links now parse as `link_value` with named
`where`/`field`/`const`/`upperlimit` markers (this repo measured that change during the 4.0.0
bump), so operators would have precise tree shapes to target. What is missing is deployment:

- **Option A — per-mutant artifact variants**: compile N artifacts, each with one declarative
  mutation applied in source. Publish cost is per MUTANT instead of per batch, which R45/R90
  measurements say is the expensive axis; a campaign's per-mutant cost jumps from ~433 ms to a
  full publish+sync each.
- **Option B — schema-neutral rewrites only**: restrict to mutations that keep table schema
  identical (a `where()` condition flip is schema-neutral; changing a CalcFormula method may not
  be) so ForceSync stays cheap. Still per-mutant publishes.
- **Option C — refuse the class permanently and say so in the report** (the R69 shape: measure
  the foregone population, name it, close by ruling).

The decision needs a measurement: per-mutant publish+sync cost on a container for a
one-property-changed artifact, times the surface's real population. Until then, no operator work
here — an operator spec against a nonexistent mechanism is the speculative-fix shape R11 refused.

## The measurement, 2026-08-14

`scripts/r135-publish-probe/` — a two-table app whose FlowField `CalcFormula` carries a
`where(... "Category" = const('A'))` condition, republished thirteen times against Cronus281 (BC
28.0.46665.47126) with that literal flipped, with nothing changed, and with a stored field added and
dropped:

    property-changed   publish + sync + install median  4404 ms  (n=3)
    no-change control  publish + sync + install median  4433 ms  (n=3)
    schema-changed     publish + sync + install median  4351 ms  (n=6)
    compile median 664 ms; cold first publish 5278 ms

**The publish is the cost and what changed does not move it.** That single fact decides two of the
three options.

## The ruling: Option C

Full reasoning in `docs/superpowers/specs/2026-08-14-r135-declarative-mechanism-ruling.md`.

**Option B is rejected on measurement, not judgement.** Its premise was that schema-neutral rewrites
keep ForceSync cheap. There is no cheap ForceSync to protect: a schema-neutral change, a schema
change and no change at all cost the same. Option B would shrink the reachable surface and buy
nothing on the axis it was proposed for.

**Option A is measured and rejected for now.** 4.4 s is a floor for a two-table app; BC publishes
whole extensions, so a per-mutant artifact for a real project is a whole-project publish — 40.8 s on
Document Output (R45), 36–97 s per single-file hosted publish with 331 guards timing out entirely
(R90). Today's amortised deployment is 0.25 s per mutant (one 40.8 s deploy over 163 sites); Option A
makes it 40.8 s each, about **163x**, and the 91 CalcFormula sites in the DO snapshot would be about
**62 minutes of publishing alone**. It is also a SECOND deployment mechanism rather than a slower
one — no selector, no artifact-id echo over a many-mutant manifest, no batch to bisect — and
publishing is the failure-prone step that stranded a real run (R44, R90). Kept as [R145](R145.md),
blocked on demand rather than on effort.

**Option C is the ruling: LethAL does not mutate declarative surfaces, and the report must say so.**
The second half is not implemented — the dropped sites reach one stderr `warn` and never the report —
so [R144](R144.md) is required, not optional.

## What the ruling costs, named

- **91 CalcFormula lines** in the 658-file Document Output snapshot are unreachable. A wrong filter
  in a `CalcFormula` is a classic silent BC bug and LethAL will not find it.
- **Zero query objects** in that corpus, so that surface has no measured population at all. A census
  of a corpus that has them would be needed before this ruling could be said to cover queries.
- **Filter-bearing properties** are uncounted. The nearest figure is the 154 declarative specs across
  47 DO files `isMutableSite` dropped when R40 first admitted pages, which counts wrongly-claimed
  SPECS rather than sites worth mutating. R144's report surface would make it a number a reader sees.

Grammar 4.0.x already removed the parsing blocker, so nothing here waits on the grammar; if the
ruling is revisited, the tree shapes are in place.
