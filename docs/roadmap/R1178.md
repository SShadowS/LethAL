**CORRECTED 2026-11-22.** This item's first version blamed PR-297's flag: tail kills reordering R197's ledger so a refused test
outranked a walk kill. That was wrong. c2's kill did not come from the walk at all, and the flag played no part.

**What moved.** Three mutants outside PR-302's named 1,590 cut-error set moved `killed -> error` between c2 and t1: M2519,
M2548, M2549.

**What happened (read from the events and the stores):**
- **In c2** the walk scored each `error` (cause `runner-refused`, the cascade note ending "this failure is not trusted: ...").
  PR-144's withheld-kill recheck then made it `killed` (c2's `mutant-rechecked` recovery events). The recheck's killer is red
  at the main baseline, so it covers no mutant and is never in the walk.
- **t1's first leg** scored them `error` the same way, but it was stopped by SIGTERM (my watchdog), so the recheck did not run
  ("al-runner-v3-recheck-skipped-stopped ... 53 withheld kill(s) stay error").
- **The resume (t1b) re-walked them.** The procedure's kills (M2507, M2508) were CARRIED from the store, and a carried kill does
  not call `recordKill` (inferred from the code, `orchestrator.ts` kill sites), so the ledger was empty and the walk order fell
  back to fewest members first (`test-order.ts`).
  - The first held error it read was the plain `Report.SaveAs` refusal, whose note has no "this failure is not trusted"
    text. `withheldKillOf` (`report.ts`) rejects it, so recheck rule (a) skipped the mutant.

**The defect.** Only the FIRST held error of a walk is kept (`orchestrator.ts`, the PR-81 hold; `adoptHeldError` at the end).
Whether a mutant is a recheck target therefore depends on walk order. Any run can show it, flag on or off: a resume, or a
different ledger.

**The fix (PR-341).** When the first held error is not withheld-eligible and a later held error in the same walk is, keep the
eligible one for the note. The main-pass verdict stays `error`, and PR-144's rules (b)-(e) still decide the recovery: the kill
reproduces, the killer passes alone at the recheck baseline, the same build, nothing lost. Red then green on a two-held-error
walk.
- Gates: a verdict can move only in the v3 RC leg (`sandbox-recheck`, the one leg with `recheckWithheldKills`). Notes can move
  in any leg with two or more held errors in one walk: scan before the gates.
- Also check whether carried kills should feed the ledger on `--resume` (a second, separate question).
