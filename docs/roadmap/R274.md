**What.** `ExplainGap` gives `blockStartLine` and `blockEndLine`, the block's line range, but not the
block's own source text with each surviving mutant's site marked. A reader still has to open the
file and cross-reference `members` against line numbers by hand to see the mutants in context.

**Who hits it.** Anyone reading `explain` output without the source file open beside it: the gap
names lines, not the code at those lines.

**Evidence.** `ExplainGap` has block lines only; `startIndex`/`endIndex` are report-only (present on
the report row, not projected onto the gap).

**What would close it.** Read the block's source span (the same offsets `gapIdOf` already hashes)
and render it with each surviving mutant's site marked inline, as a new optional field so existing
consumers are unaffected.

**Found by.** C02-09's own review of GitHub issue #11 (point 5), filed as a follow-up rather than
folded into this task's scope.

**Sized 2026-10-06 (R-277b): not small, left open; needs an owner choice.** `explain` reads only the
report, and the report holds no block source: each row carries its own `originalText` and
`mutatedText`, never the block around it, and no project path to read it from. Two ways in, each
with a cost:
1. **Put the block text in the report.** More target source in every report, which is what this
   public repo's redaction rule (`scripts/redact-campaign-report.ts`) strips before a report is
   committed; the redactor and its check would have to cover the new field too.
2. **Let `explain` read the source from disk** (a new `--project <dir>` argument). No source in the
   report, but explain then depends on a checkout matching the run (the R205 snapshot question: the
   text read later may not be the text that ran), so it would need the run's source hash to refuse
   a mismatch.
The second keeps reports clean and is the likely choice; it is its own task.
