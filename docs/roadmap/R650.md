**Filed 2026-10-22 by lane bugs during R-647** (the build review `/coord/handoff/R-647/review-build-opus.md`, M1).
Related: [[R647]], [[R556]], [[R586]].

**What.** Since r10 ([[R647]]), leg T of `itest:alrunner-v3` reaches `held` without calling `assertGateBaseline`. Its
text check is the `compareMutants` call that `legT` hands to `judgeLegT`. `compareMutants` counts a paired row whose
`mutatedTextSha256` is missing on either side as `textUnverified`, never as a difference. `assertGateBaseline`'s
`compareWithCommitted` guards against that with R556's bare-hash refusal: when the committed baseline records a hash per
mutant, a run with any row that has no hash is refused ("the text check would switch itself off"). The held path has no
such refusal. So if a LethAL change dropped the mutated-text hashes (no `mutatedText`, or a redacted one), a held run
could carry a row whose mutated text changed, and `judgeLegT`'s key-set equality would not see it.

**Who it hurts.** The update gate, only on `held`. A held build is kept under `held/` and never moves `current`, but its
rows are read as "only known rows moved", and a re-record after it could freeze a text change unseen.

**To close.** Apply the same bare-hash refusal on the held path: before `judgeLegT` judges `held`, refuse (gate-fail) when
the own baseline records hashes and any row of the run has none. Red tests for each direction (hashes present: held;
one row bare: gate-fail).

**Fixed (dd7215d0, lane bugs, R-650).** R556's predicate now lives once, as `bareHashRows` in `mutant-equality.ts`: when
the baseline records any mutated-text hash, it returns the run's rows that have none, else nothing. `compareWithCommitted`
calls it (same message as before), and `judgeLegT` calls it first in its `held` branch, with the own baseline and the
run's rows (`legT` now passes `own` and `now`). A non-empty result is `gate-fail`, naming the refusal, the count of rows
without a hash and the first key. The `pass` path is unchanged: it already meets the refusal in `assertGateBaseline`.
- Tests in `packages/runner/tests/r586-gate.test.ts`: T-a12 (held rows, hashed own baseline, one run row bare:
  `gate-fail`), T-a13 (the same rows, every hash present: `held`), T-a14 (no hash on either side: `held`, which is R556's
  own rule: `compareWithCommitted` refuses only when the baseline records a hash, and `baseline-guard.test.ts`'s legacy
  bare-array test passes on such a baseline).
- Red checks, logs in `/coord/handoff/R-650/red-unit/`: dropping the new `held` check turns T-a12 red; making the
  predicate return every row turns T-a13 red; dropping the "baseline records a hash" guard turns T-a14 red (and R296's
  baseline-guard test, through `compareWithCommitted`). Each restored to green.
- **No figure moves; no pre-commitment.** The own baseline `al-runner-v3.tables.baseline.json` holds 406 rows, every one
  with a hash, and so does `tables.baseline.json`. The last live leg T (`/coord/handoff/R-647/live/alrunner-v3.log`,
  2026-10-22) passed through `assertGateBaseline`, so the same refusal already ran on that build's rows and found no bare
  row (its 12 text-unverified rows are twins sharing a hash across the scheme change, not rows without one). So on every
  current build the new check cannot fire, and `held` and `pass` judge as before.
- **Live on the final head 21dc2195** (`baseline-guard.ts` sits on every gate's path): `itest:alrunner-v3` against
  pinned alpha.2, all eight legs PASS (`/coord/handoff/R-650/live/alrunner-v3.log`); and, by orchestrator ruling, ONE
  representative BC gate, `itest:bcdev` on bc1, PASS 3 / 12 / 4 both runs (`/coord/handoff/R-650/live/bcdev-bc1.log`).
  The extraction can only block, never change a verdict, so one BC gate shows `assertGateBaseline` still passes a real
  committed baseline end to end; the other BC gates were not run.
