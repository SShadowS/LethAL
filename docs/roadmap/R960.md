Reported on GitHub #28 (2026-11-12, coord R-946): al-runner 3.0.0-alpha.13 against BC 28.5 data, `--workers 4`, stopped at the mutant
phase with `AlRunnerV3EntriesRefusedError` ("install code read a resource file"); the user reran it one-shot. Related: [[R786]],
[[R927]], [[R766]].

**What the code does today (checked 2026-11-12 on master).**
- R786's fallback (re-run the session one-shot) applies on the default transport only when every unkept warm-up row is a refusal by
  name. A refusal of the WHOLE request (`entries-batch-refused`, as an app whose install code reads a resource file gets: al-runner
  #5635) is thrown from `send()` before that check, so the default transport stops with an error, after the whole baseline.
- R927's early probe catches `entries-batch-refused` before the baseline, but only on an EXPLICIT serve-entries transport.
- Under `--workers > 1` a fallback is refused by name anyway (R766), so the user's run would have stopped either way; the message
  should say to drop `--workers` or set `"transport": "one-shot"`.

**Wanted.** On the default transport, treat `entries-batch-refused` at the warm-up like R786's named-row case: fall back to one-shot,
with the warning naming the reason. Better still, probe before the baseline on the default transport too, so the fallback costs
nothing. Under `--workers > 1`, refuse by name before the baseline, saying how to run it.
