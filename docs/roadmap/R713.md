**Filed 2026-10-24 by R-705 (lethal-bugs)**, evidence `docs/measurements/r706/readings.json` and [[R706]], [[R712]].

**What.** LethAL's bcdev backend runs tests through LethAL Control `RunMutant` (the web-service path, runner 130450).
There an unhandled outbound HTTP call fails with "The request was blocked by the runtime to prevent accidental use of
production services." In VS Code, the test runner hub and al-runner v3 it fails with "...the connecting endpoint
violates security requirements...". An AL test that asserts on that text can pass in a user's CI and fail under bcdev,
or the reverse. This is a known difference of the paths, not a LethAL defect (the owner's ruling in R712 makes the hub
the oracle).

**To close.** Decide whether bcdev should document the difference, warn when a test's failure text is the
web-service one, or run such tests through the hub.

## Done

**Measured by reading the code, no probe needed.** No mutant is scored from failure text. A test that is red at the
bcdev baseline is dropped from the green set by outcome and never kills anything. The two texts are already measured
and pinned (`docs/measurements/r639/`, `r706/`). The cases (CI means the hub path):

| Shape | CI | bcdev baseline | Effect | Class |
|-------|----|----------------|--------|-------|
| a. `asserterror`, no text assert | green | green | scored normally | none |
| a1. asserts the hub text | green | red (the web text sits in the failure) | test dropped; a mutant only it covers is `error`; one also covered by green tests is scored on those and may survive where CI kills it | coverage loss, safe direction |
| b. asserts the web-service text | red | green | test can kill; a mutant only it kills is a kill CI would not give | false kill, un-guarded |
| c. HTTP error unexpected | red | red | dropped, cause unnamed before this item | none |
| c2. call reached only under a mutant | green | green | a real kill in both worlds | none |

**Chosen answer: name the cause, change no verdict.** `describeWebServiceHttpText` (`webservice-http-text.ts`) is a
substring match on `BC_HTTP_INTERNAL_TEXT`. In the orchestrator's `select`, a baseline-failing test that matches goes
into a batch-local map. `unsupportedCoverageNote` gains a branch (after the permissions and TestPage branches, before
v3 and the generic wording) that leads with "web-service HTTP text differs from the hub's". One `warning` event with
code `bcdev-http-text-differs` fires per batch, which covers a1 mutants that green tests also cover. No SessionReport
field, no Caveat, no events union change. The no-verdict-move test runs the same suite with the web text and with an
unrelated text and compares counts and verdicts.

**Residual, un-guarded: shape (b).** The test passes at baseline, so no failure text exists to match. Seeing it would
mean reading test source for the web sentence, a new detector with no measured population. It needs a user who wrote
bcdev's text into a test and whose own CI is already red on it. Known and left.

**Limit: the warning is not limited to bcdev.** `select` is shared with the al-runner v3 backend, so the note and the
`bcdev-http-text-differs` warning would also fire on a v3 build that wrote the web-service text, with wording that is
false there. It cannot fire today: the pinned v3 build writes the hub text, and a build that wrote the web-service
text would read `unlike-bc` in leg C and be refused by name in a session. If that ever changes, limit the map to the
bcdev backend.
