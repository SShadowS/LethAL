**Priority.** Filed 2026-10-08 by R514's build, from decision (1) of the R-514 plan (r2,
`docs/superpowers/plans/2026-10-08-R-514-reused-baseline-confirm.md`) and the review's M4. A
false-kill risk, narrower than [[R514]]'s: it needs a test to slow down by more than 2x INSIDE one
run, which is the margin [[R53]] accepted. Not verified live.

**What.** [[R514]] confirms a position-1 `timeout` unmutated only when the batch's baseline was
reused (R192). A batch whose baseline was measured in the same run still scores a position-1
`timeout` as `timeout-killed` with no confirm, on the reasoning that a fresh baseline measures the
day it runs on. Two shapes break that reasoning:

1. **A test that slows more than 2x within a run.** The budget is `max(2 x baseline duration,
   --mutant-timeout-ms)`. A test whose duration grows past twice its baseline (and past the floor)
   between the baseline and a later mutant, for a reason that has nothing to do with the mutant,
   times out and is scored a kill. This is R53's accepted 2x ruling, restated as a known exposure.
2. **Workers on different tiers (`workers > 1`).** The baseline runs once, on the session's own
   backend, and its durations set the budgets on every worker. A worker whose server tier is slower
   than the one the baseline ran on gets budgets measured elsewhere, so a slower tier can turn an
   ordinary run into a position-1 timeout and a kill. (Today `workers > 1` is refused for an
   authoritative backend, so this reaches al-runner only; it reaches bcdev the day that refusal is
   lifted.)
3. **al-runner one-shot gets only about a 1x margin, fresh or reused.** `AlRunnerBackend.sendOneShot` sets the
   in-run test timeout to `floor(timeoutMs/2000)` seconds, half the budget, so a mutated run "times out" when its
   test body passes budget/2. R514's confirm is judged as a kill when its wall clock (compile and startup included)
   is at most budget/2, the same threshold the mutated run crossed. Example: reused budget 180 s, in-run limit 90 s;
   the test body runs 86 s unmutated (89 s wall clock), 91 s under an unrelated mutant, which times out; the confirm
   passes at 89 s and 2 x 89 <= 180, so the mutant is scored `timeout-killed`. Found by R-514's final build review
   (I1). Fix: judge the confirm against the threshold the run actually enforced, e.g. a backend capability giving the
   in-run timeout as a fraction of the budget, so the rule becomes `2 x confirm <= budget x fraction`. Separately on
   al-runner, a genuine hang under a low `--mutant-timeout-ms` can become `reused-budget-stale` because the confirm's
   wall clock includes the compile: a lost kill, never a false one (review M3).
   The fresh "no drift" false kill (a test whose body is within the sub-second remainder of its wall
   clock times out under every mutant) needs the floor not to bind (wall > floor/2); at the defaults
   one-shot already had about 1.5x (R-516 plan r2, review M5).

**Evidence.** Before the fix, the R514 test "R514 ruling: a fresh baseline's position-1 timeout is
not confirmed" in `packages/runner/tests/resume.test.ts` (describe "R514: a reused baseline's
durations set today's budgets"): the baseline measures `BSlow` at 1000 ms, later in the same run it
takes 5000 ms under mutants that do not touch it, and every scored mutant was `timeout-killed` with
zero unmutated confirms. The five repros of `/coord/handoff/R-516/repro.md` (committed red in
3e2122e5) measured all three shapes: (a) fresh drift, (b) a slower worker tier, (c) al-runner
one-shot reused and fresh.

**Fixed (a29e3187; the `itest:hang` check in 8f6821f7), for bcdev and al-runner one-shot.** Every
position-1 timeout, fresh batch or reused, is confirmed by one unmutated run on the worker that saw
it, and the kill stands only if `2 x confirm <= the budget the run was sent`; otherwise the mutant is
`error`, cause `timeout-unconfirmed` (explain schema v15) or, where the budget came from a reused
snapshot, `reused-budget-stale`. `confirmWarm` uses the same half-budget rule on fresh batches.
al-runner one-shot now runs a test with an in-run limit equal to the budget and a client deadline of
twice it (`oneShotLimits`). The repros flipped: "R516 T1 (repro a)", "R516 T2 (repro b)", "R516 T3a"
and "R516 T3b" (repro c), with direction tests T1b, T5, T6, T8 and T12 and the red-checks in
`/coord/handoff/R-516/redchecks.md`. Known lost-kill bands, never a false kill: a test whose budget
is twice its measured duration (above the floor), and on al-runner one-shot a test whose compile
plus body takes more than half the budget. **al-runner `--server` and resource-with-server are NOT
closed here: [[R517]].** Live gate pending: `itest:hang` against
`docs/superpowers/specs/2026-10-08-r516-hang-confirm-every-timeout-precommitment.md` and
`itest:alrunner` unchanged against
`docs/superpowers/specs/2026-10-08-r516-alrunner-unchanged-precommitment.md`; then `done`.

**Proposed fix.** Extend R514's confirm to every position-1 timeout, or only where the measured
risk is (a duration recorded long before the mutant, or on another worker's backend). The cost is
one unmutated run per genuine hang kill. Decide with a measurement of how often a fresh run's tests
drift past 2x; R514's probe (`scripts/r514-probe/probe.ts`) prints the first-call figures for the
hang fixture only.

**To close.** A ruling, or the confirm extended with both directions pinned and red-checked (a
genuine hang stays `timeout-killed`; a drifted test does not).
