**Filed by R-297 Task 8 (2026-09-28)**, plan
`docs/superpowers/plans/2026-09-28-R-297-instrumentation-real-corpora.md`. Sibling of [[R301]] (class
C, the split-header procedure whose arms share ONE `var` section, which R-297 Task 5 fixed) and
[[R303]] (a member whose var section alone is split by `#if`, refused rather than double-declared).

**The shape.** `preproc_split_procedure` covers a procedure whose HEADER differs per `#if` arm but
which shares one `var` section and one body. `preproc_split_procedure_preamble` is the sibling shape
where each arm ALSO has its own `var` section — the preamble (declarations) is split too, not shared.

**What breaks.** [[R301]]'s fix gives `preproc_split_procedure` one shared `var` section to declare
the reach latch in. A `preproc_split_procedure_preamble` has no such single place: one latch
declaration cannot serve both arms' separate `var` sections, the same problem [[R303]] names for an
ordinary member whose var section alone is split. R-297 Task 2 confirmed this stays unfixed: the
`a-preamble` test in `packages/schemata/tests/compile.test.ts` still throws
`a reach marker sits outside any procedure or trigger body` for a spec inside the preamble
procedure's body. Two tests only cover it (an isolated position test, which is green even at HEAD
since the preamble parses as a sibling of `var_section` rather than inside it, and the throwing
test); no compile is claimed.

**Size.** R-297 Task 0's census: 0 files in DC/Cloud, System Application, BusinessFoundation or
BaseApp hold this shape. It is filed because the sibling shape ([[R301]]'s `preproc_split_procedure`)
is real (DC/Cloud 3, BaseApp 4) and the preamble variant would hit the same throw if a corpus ever
has one, not because one has been seen.

**What would close it.** Either R303's per-member refusal (no latch, `reachGrain: "unplaced"`,
named in a warning) extended to this shape, or a per-arm latch placement (declare the latch in
EACH arm's own `var` section) — the same open question [[R303]] leaves for its own shape. Whichever
is chosen should close both items the same way, since the underlying problem (one latch, more than
one `var` section to put it in) is identical.
