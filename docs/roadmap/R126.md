**`ExecutionBackend.run()` takes one test and returns one verdict, and that shape is what makes
al-runner's warm server mode unprofitable.** Measured 2026-08-08 on al-runner 2.1.0.0 (see
`docs/measurements/README.md` §"al-runner 2.1.0.0 server mode"): the server's `runTests` has no
per-test selection at all, so every call runs the whole suite. With `run()` called once per test
that is T² test executions per mutant against the CLI path's T. So server mode is refused (R97).

**The asymmetry is the opportunity.** A single whole-suite server response already carries a verdict
for EVERY test, and the response comes back in about 1 s warm against about 7 s cold for the same
request. A backend that could answer "here are all verdicts for this activation" in one call would
turn the missing filter from a cost into a non-issue: one call per MUTANT, not T calls, and not T²
executions. That is strictly fewer test executions than the CLI path performs today, not merely
fewer process spawns.

**What has to be measured before any of it is built, and none of it is:**

- **Isolation.** The CLI sends `--isolation test`, which is what
  `AlRunnerBackend.capabilities()`'s `isolation: "full-reset"` claim rests on. Nothing is measured
  about whether the server protocol accepts an isolation setting or what it defaults to. Running a
  whole suite inside one warm process is not obviously the same semantics as one process per test,
  and if it is not, the capability claim becomes a lie before the speed arrives.
- **Whether the orchestrator wants all verdicts.** Today it stops a mutant at the first failing
  test. A whole-suite answer gives it more than it asked for, which is useful (it names every test
  that noticed, not just the first) but changes what a run RECORDS — so it needs a gate, not just a
  green unit suite.
- **Cold-start provisioning.** `--server`'s usage line takes only `--package-cache` and `--cache`;
  there is no `--auto-provision`, which R125 established is what makes a cold machine work at all.

**Do not start from the deleted code.** `ServerTransport` decoded a single aggregate envelope and
2.1.0.0 streams per-test NDJSON lines plus a `{"type":"summary",...,"protocolVersion":2}` line; the
old decoder read one line, found no `tests` array and would have returned an empty list. It is
deleted for that reason (R97). The protocol shape to build against is the one in the measurements
doc, re-measured, not the one in this repo's history.

Filed 2026-08-08 while closing R97.

**RE-CHECKED 2026-08-08 against al-runner 2.1.1.0.** Nothing this row waits on has moved, and the
check is recorded so the next session does not repeat it from scratch.

- **Cold-start provisioning is still unaddressed in server mode.** The usage line remains
  `al-runner --server [--package-cache PATH ...] [--cache DIR]`. No `--auto-provision`, so a server
  started on a machine with no artifacts has no documented way to obtain them — and R128 measured
  that the `provision` subcommand is not a substitute, because it resolves a different version for
  platform apps than the one a run selects.
- **No isolation knob is documented for the server.** The CLI has `--isolation codeunit|test|disabled`
  and LethAL sends `test`, which is what `capabilities()`'s `isolation: "full-reset"` claim rests
  on. The `--server` section says nothing about it. Until that is measured, adopting server mode
  would move the capability claim onto an unmeasured default.
- **The command set is still `runTests, shutdown`, with `execute: TODO`** in upstream's own help.
- **The CLI grew per-test selection (`--test PATTERN` / `--filter PATTERN`) and the server did
  not.** That widens rather than closes the gap R97 measured: the one-call-per-mutant design this
  row proposes is still the only way server mode could pay, because the server cannot be asked for
  one test.

Nothing here justifies building yet, and nothing here justifies closing the row either.
