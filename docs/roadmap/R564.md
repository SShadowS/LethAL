**Filed 2026-10-10 by the [[R562]] build** (orchestrator ruling (a) on plan r1, `/coord/reviews/R-562-plan/`).
An over-refusal: mutants that cannot hang are not deployed.

**What.** [[R531]]'s HOP (a consumer one hop away) and R562's FILTER HOP (a filter one hop away) both follow
EVERY procedure of the called name whose parameter count fits the call (`r531ProcsIn`). AL chooses an overload by
the arguments' TYPES, so when two overloads have the same parameter count, the one the call never reaches is
followed too and its sites are refused.

**Measured payoff.** DO Cloud, R562: each of the two callee tables (`CDOEMailTemplateAttachment`,
`CDOEMailTemplLineReport`) has two 1-parameter overloads of the filter procedure, one taking
`CDO E-Mail Template Line` and one taking `CDO Document Template Line`. `CDOEMailTemplateLine`'s OnRename passes
`xRec`, a `CDO E-Mail Template Line`, yet the `CDO Document Template Line` overloads' `remove-setrange` x3 and
`empty-block` x1 per table are refused: **8 of DO's 23 removed keys** (`/coord/handoff/R-562/measure.md`).
Choosing by type would bring DO to 15 keys (about 0.05% of its specs). R531's own HOP was not measured for this
over-refusal.

**To close.** Narrow `r531ProcsIn`'s candidates by argument type where the type is known: a Record argument's
table (`declaredType`, which the HOPs already use for receivers) against the parameter's declared Record type;
keep every arity-fitting overload whenever a type is unknown (the refusal direction). Re-dump DO and CDO and
every corpus R531's HOP touches against the master legs; the change only adds keys back, so expect no tuple or
ordinal to move.
