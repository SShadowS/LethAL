**R125 fixed `itest:alrunner` by sending `--auto-provision`, and stated the cost it added rather than
glossing it.** On a machine whose al-runner artifact cache does not already hold the project's BC
version, the FIRST `al-runner` invocation of a run triggers the download (~1 GB for a w1 artifact
set) *inside that mutant's own timeout budget*. Every later invocation is a no-op, because artifacts
cache per BC version. So a first run on a fresh machine can lose its first mutant to a provisioning
download rather than to a real verdict — and `OneShotTransport` would score that as
`deadline-exceeded`, which is an infrastructure outcome rather than a wrong verdict, but it is still
a mutant nobody measured for a reason that has nothing to do with the mutant.

**The fix R125 names and does not build: provision ONCE at session start, before any mutant.**
`AlRunnerBackend.status()` already runs before a session (it probes `--version` and refuses a
non-v2 binary), and `al-runner-contract.ts` (R123) already spawns the binary once per session to
measure the wire contract — so there is an established place for a one-time, out-of-budget step that
a mutant's clock does not pay for.

**What is NOT measured, and it bounds how confidently this can be designed.** Every al-runner
measurement in this repo was taken on a machine whose cache is warm, including R125's own. Nobody
has watched the cold path fail. Specifically unknown: whether `al-runner provision <bundle>` alone
is now sufficient (R125 measured it as NOT sufficient on 2.1.0.0 — it split engine artifacts and
platform R2R apps across two version directories, neither complete — so the one-time step may have
to be a real `--auto-provision` run rather than the `provision` subcommand), how long the download
takes, and what a partially-provisioned cache does on the next run. That measurement comes first;
al-runner ships several times a day and the sufficiency of `provision` is exactly the kind of thing
that moves.

**A cheaper half-measure to consider and reject deliberately:** simply raising the first mutant's
timeout. It hides the symptom, makes every run's first budget a lie, and still leaves the download
inside a mutant's clock where a genuine hang and a genuine download look the same.

Filed 2026-08-08 from R125's own "not built here" note, so the refinement is tracked rather than
living only inside a closed row's prose.

# The blocking measurement, done 2026-08-08 on al-runner 2.1.1.0

## `al-runner provision <bundle>` is still not sufficient, and the cache shows why

The split R125 described on 2.1.0.0 is visible in this machine's artifact cache right now:

```
~/.local/share/al-runner/artifacts/28.0.46665.53459/   platform-apps, test-apps        137 MB   (no engine)
~/.local/share/al-runner/artifacts/28.0.46665.53492/   platform-apps, test-apps        137 MB   (no engine)
~/.local/share/al-runner/artifacts/28.1.49838.50794/   501 entries incl. engine DLLs   358 MB   (complete)
```

Running the subcommand reproduces it in one command:

```
$ al-runner provision fixtures/sandbox-app
[provision] ... Downloaded 6 app(s) (115 MB total) to .../artifacts/28.0.46665.53492/platform-apps
[provision] test toolkit already present at .../artifacts/28.1.49838.50794/test-apps.
```

**It resolves the PROJECT's version (28.0.46665.53492) for platform apps and the BINARY's version
(28.1.49838.50794) for the test toolkit, in the same invocation, and fetches no engine artifacts at
all.** So it populates a directory the run will not select and leaves the one the run WILL select
untouched. R125's finding is unchanged on 2.1.1; this is not a case of "upstream fixed it".

**Design conclusion, now measured rather than guessed: the one-time step must be a real
`--auto-provision` invocation, not the `provision` subcommand.** `--auto-provision` resolves ONE
version for everything and reports engine artifacts explicitly
(`[provision] BC 28.1.49838.50794 engine artifacts already complete at ...`).

## A live source comment was wrong, and it is corrected

`buildAlRunnerArgv` said `--auto-provision` "resolves the version from the PROJECT rather than from
the binary — which is the version whose symbols the project actually carries". Measured: with no
`--bc-version` the runner announces `selecting BC 28.1.49838.50794, the exact build this binary was
compiled against` and provisions THAT. It then runs happily against a fixture whose `.alpackages`
carry 28.0.46665.47126 symbols, so the stated reason for the flag working is not the reason it
works. Corrected in place.

This matters here because it decides WHICH version a one-time provisioning step must ask for: the
same one the run will select, which is the binary's — exactly what `--auto-provision` already does
and what `provision` does not.

## What is still not measured, and why it is not cheap

**The cold path itself.** Every al-runner measurement in this repo, including this one, is on a warm
cache. Making it cold means deleting `28.1.49838.50794` — 358 MB, and the artifact set every
al-runner gate on this machine selects. If the re-download were slow or failed, `itest:alrunner`
would be down until it completed. That is a real cost to impose on someone else's machine for a
measurement whose design conclusion is already settled by the above, so it was not done.

What a cold measurement would still add: how long the download takes inside a mutant's budget, and
what a partially-provisioned cache does on the next run. Both matter for the ERROR MESSAGE the
one-time step should print on failure, not for whether to build it.

## The half-measure stays rejected

Raising the first mutant's timeout hides the symptom, makes every run's first budget a lie, and
leaves the download inside a clock where a genuine hang and a genuine download look identical. The
measurement above does not change that.

# CLOSED 2026-08-09 — built, and the row's own model of the cost was wrong

## The measurement that changed the design's justification

One `--auto-provision` invocation on `fixtures/sandbox-app` + `fixtures/sandbox-tests`, on al-runner
2.1.1.0, on this machine's WARM cache. Its `[provision]` lines, read off stderr:

```
[bc] no --bc-version given - selecting BC 28.1.49838.50794, the exact build this binary was compiled against.
[provision] BC 28.1.49838.50794 engine artifacts already complete at .../28.1.49838.50794.
[provision] Resolving BC version prefix '28.0'...
[provision] Resolved: 28.0 -> 28.0.46665.53508
[provision] fetching Microsoft platform R2R apps for BC 28.0.46665.53508 ...
[provision] Downloaded 6 app(s) (115 MB total) to .../28.0.46665.53508/platform-apps
[provision] test-toolkit apps missing - downloading...
[provision] Downloaded 107 test .app file(s) (20 MB) to .../28.0.46665.53508/test-apps
```

**Three findings, and the first is the one that matters.**

1. **The project's BC version is resolved by PREFIX to the LATEST matching Microsoft build.** `28.0`
   became `28.0.46665.53508`. The cache already held `28.0.46665.53459` and `28.0.46665.53492` from
   earlier runs — three directories for one project, one per upstream publish. So the download is
   **not a once-per-machine cost**: a cache that was warm yesterday is cold the moment Microsoft
   ships a new 28.0 build, and the cost lands on whichever mutant runs first, every time. That is a
   far stronger reason to build this than the "fresh machine" case the row was filed on.
2. **`--auto-provision` resolves TWO versions, not one.** The row says it "resolves ONE version for
   everything". Measured: the ENGINE at the binary's build, the platform R2R apps AND the test
   toolkit at the project's resolved build. The cache confirms it directly — the `28.1.49838.50794`
   directory holds engine DLLs and `test-apps` but **no** `platform-apps`, while the `28.0.*`
   directories hold `platform-apps` and `test-apps` and no engine.
3. **The provisioning ran TWICE inside the single invocation.** It downloaded the 115 MB of platform
   apps, reported them written, and then immediately said `platform R2R apps missing - downloading...`
   and downloaded them again. Not acted on here (it is upstream's), but it doubles what a cold first
   mutant would have paid and it is worth knowing before anyone times this.

## Why `al-runner provision <bundle>` is still not the step, with a corrected reason

The row says the subcommand "fetches no engine artifacts at all". It does not fetch them because
they were already complete, and it SAYS so: `[provision] BC 28.1.49838.50794 engine artifacts already
complete at ...` — the same line the row attributes to `--auto-provision` as the distinguishing
feature. The real gap is elsewhere: the subcommand resolves the test toolkit at the BINARY's version
(`test toolkit already present at .../28.1.49838.50794/test-apps`) while a RUN resolves it at the
project's, so after `provision` the directory the run will select has platform apps and no toolkit,
and the first mutant downloads 20 MB of test apps anyway. Measured directly: after running the
subcommand, `28.0.46665.53508/` contained `platform-apps` only.

## What shipped

`AlRunnerBackend.provisionOnce()` — the transport's own argv (so the provisioning invocation and
every later one resolve symbols identically), `--auto-provision`, and a `--test` sentinel that
matches nothing. Called from `runSession` immediately after the backend status check, through a
structural check rather than a widened `ExecutionBackend`: no other backend provisions anything.

It uses the TEST bundle, because at session start the instrumented directory does not exist yet while
`testDir` always does, and a test app necessarily declares the same BC version as the target it tests.

**Best-effort, and that is a design constraint rather than a shortcut.** Nothing it does can fail a
session: if it cannot spawn, the run proceeds and the first mutant pays the download, which is
exactly the behaviour before this existed. It emits a message when it actually FETCHED something,
because that is what explains a slow start and says the cache had moved.

## The half-measure stays rejected

Raising the first mutant's timeout hides the symptom, makes every run's first budget a lie, and
leaves a genuine hang and a genuine download indistinguishable. The prefix-resolution finding makes
it worse, not better: the "first" mutant to pay would change from run to run.

## What is still not measured

A genuinely cold engine cache (deleting `28.1.49838.50794`, 358 MB, which every al-runner gate on
this machine selects). Not done, deliberately. What it would add is how the error message should be
tuned when provisioning fails part-way — not whether to build this, which the prefix finding settles.
