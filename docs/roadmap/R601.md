**Filed 2026-10-21 by lethal-bugs during R-389.** This is the merge review's M3
(`/coord/handoff/R-389/review-build-merge.md`).

**What.** R389 records a closed-world run's test-app identity and its baseline snapshots with the
`|pending` suffix. The suffix is removed only by the post-execution re-ask, when the guard gives
the same closed answer again.

A run that ends before that re-ask keeps `|pending` forever. The cause can be a crash, Ctrl-C, or
any exception after the lease. (A quarantined run does reach the re-ask.) A pending run was never
resumable, and its snapshots are never reused. On a server with LethAL Control 1.0.0.23 and no app
depending on the test app, the normal case, that made `--resume` after a crash, its main use,
effectively off. The refusal did not say why in words.

**Fixed (plan `docs/superpowers/plans/2026-10-22-r601-resume-pending-closed-world.md`, r2).**

- **The rule.** `resumableTestApp` (`packages/runner/src/closed-world.ts`) is the one test-app
  comparison of both resume sites: `assertSameTestApp` before the lease and the R496 recheck under
  it. It accepts a prior whose identity equals this session's, or equals this session's CLOSED
  identity plus `|pending` when the prior's recorded server (`runs.resource_key`, now read into
  `RunRow.resourceKey`) equals this session's. An unknown server never matches.
- **The resumed run checks itself.** It records its own identity `|pending` and its own re-ask after
  execution confirms it, or revokes it. **Revoke on every flip** (orchestrator ruling on review
  I-A): when ANY session's re-ask flips, fresh or resumed, the same transaction revokes every run
  of the project still recorded as `<identity>|pending` on the same server (`resource_key`), with
  their snapshots (`revokeTestAppHash`'s `chain`), so no pending run lends after a session on that
  server saw the answer change. An unknown server fails closed: a session with no key revokes the
  project's pending runs on every server, and a pending run with no key (which can never resume)
  is revoked by a flip on any server. A later session never confirms the pending run. Its
  snapshots are still never reused (deferred: the cost is one baseline for the batch open at the
  crash).
- **The words.** An accepted resume says so in `resume-reusing-run`. A refused pending prior says
  which case it is: the guard is open now (quoting the guard's own reason), or the answer, the test
  app or the server differs.

**Stated limits** (orchestrator ruling Q1, 2026-10-22).

- A dependent published and removed again inside the gap between the crashed run's first ask and
  this session's (0 -> 1 -> 0) is not seen. This is R389's limit, now as long as the crash gap.
- A server RESTART inside the gap is not seen. The `bc1`-`bc3` servers keep their databases in
  memory, so a restart loses every app, and "0 dependents now" says nothing about before it. Filed
  as the probe [[R632]] (a server start time or boot id, and whether publishes show in BC's
  history).
- The server key omits the tenant (`quarantineResourceKey`).
- A crashed run whose own re-ask answered differently, and which died in the moment before its
  revoke, or whose revoke write failed (the transaction rolls back whole), stays `|pending` and can
  be resumed by the rule.
- A guard that answers OPEN at a session's start is a changed answer too, but nothing records it,
  so it revokes nothing. Only a post-execution re-ask that flips revokes. A flip in a session whose
  identity is not proven (no `historyTestApp`) has no identity to match and revokes no other run.
- A session still running when another session's flip revokes its row (two sessions of one
  project, one store, one server) throws loudly at its own confirm ("holds no pending identity")
  after a full run, and no verdict of it is carried. Fail-closed (review M-B).
