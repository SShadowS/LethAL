**Filed 2026-10-21 by lethal-bugs during R-389.** This is the merge review's M3
(`/coord/handoff/R-389/review-build-merge.md`).

**What.** R389 records a closed-world run's test-app identity and its baseline snapshots with the
`|pending` suffix. The suffix is removed only by the post-execution re-ask, when the guard gives
the same closed answer again.

A run that ends before that re-ask keeps `|pending` forever. The cause can be a crash, Ctrl-C, or
any exception after the lease. (A quarantined run does reach the re-ask.) A pending run is never
resumable, and its snapshots are never reused.

This is the safe direction, by design. But on a server with LethAL Control 1.0.0.23 and no app
depending on the test app, which is the normal case, it applies to essentially every bcdev
session. So `--resume` after a crash, its main use, is effectively off there.

The R247 refusal shows the prior hash with `|pending`, but it does not say why in words.

**Candidates.**
1. Let a resume accept a pending prior run when the guard, asked now, gives the same closed answer.
   The gap this leaves is a 0 -> 1 -> 0 change inside the window, which R389's stated limit
   already accepts. The resumed run's own end-of-run re-ask still covers the rest.
2. At minimum, word the refusal: "its closed-world answer was never confirmed (the run ended before
   its post-execution check)".

**Evidence.** `PENDING_SUFFIX` and `confirmClosedWorld` (`packages/runner/src/closed-world.ts`,
`packages/runner/src/store.ts`). The resume.test.ts test "interrupted before confirmation: nothing
carries, no baseline is reused; control: confirmed carries" pins today's refusal.
