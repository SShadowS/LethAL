**Filed 2026-10-25 by lethal-spare (coord task R-767, an owner request).** Follows R760, which measured
`assertBound` at 0.35 s per send (31,125 ms over D1's 90 serve checks).

**What.** Before every send, `assertBound` walks `active/` and the test dir twice each (once for the `.al` hash, once
for the non-`.al` files) and re-reads every `.al` file. Timed on D1's trees (CDO `Cloud`, 554 `.al`, and `Test`, 104):
- one async walk of `Cloud`: 108 ms; the same walk with `walkFilesSync`: 6 ms;
- reading and hashing every `.al` file: about 95 ms async, 16 ms with `readFileSync`;
- the four helpers per check (`hashAlTree`, `otherFilesDrift` on both roots): about 370 ms before, 36 ms after.

The cost was Bun's per-call overhead on `node:fs/promises` (about 150 µs per awaited call), not the hashing.

**Fix.** `hashWalked`, `listOtherFiles` and `otherFilesDrift` (`packages/runner/src/baseline-snapshot.ts`) walk, stat
and read synchronously. Same walk (`walkFilesSync` shares `walkFiles`' collector, so links refuse exactly as before),
same bytes, same hash: every send still re-hashes every `.al` byte. No stat fast path was added, so the guard's meaning
is unchanged, and a same-size rewrite with the mtime restored is still caught (new T22 case). The calls block the JS
thread for about 30 ms per check, which R-766's parallel lanes accept (they run one after another).

**Tests.** T22 gains four R767 cases (same-size rewrite with mtime restored; an `.al` added to `active/`; one
removed; a test `.al` added), each red-checked: all four go red when the tree hash is a constant, and the
same-size case alone goes red when the hash keeps each file's length but leaves its bytes out.

**Not done.** A stat fast path (size, mtime, ctime, ino, with git's racy-entry rule) would cut the remaining ~30 ms
further; skipped because it changes what the guard trusts. `<deps>` already has its size+mtime rule (R608).
