**Evidence that it is not R-236b.** Full analysis:
`.superpowers/sdd/2026-09-27-R-236b-testpage-reply-fix/hang-rootcause-report.md`. Summary: R-236b's
client diff (since `35214ad`) only touches `callOf`/`scoreManyAnswer`, which run AFTER a call is
already classified, and adds an optional timeout to `postAction` that `GetOperationStatus` and
`StopHungRunAt` don't use; a 408-with-stop answer is `outcome: "timeout"` with no `operation`, so it
never reaches R-236b's readback at all. Server-side, `ControlState.Codeunit.al` (which holds
`TryStopHungRunAt`) is unchanged, and `RunMutantMany` changed only in its last statement
(`KeepAnswer`), which a looping (non-terminating) method never reaches. Two offline reproductions
(the deleted scratch test, copy at
`C:/Users/SShadowS/AppData/Local/Temp/claude/U--Git-LethAL-wt-lane-bugs/01994069-c6e6-468b-ad23-4e5aa5c0d94f/scratchpad/zz-hang-rootcause.test.ts`,
and the permanent test added by this session, `packages/runner/tests/run-mutant-many.test.ts`
describe block "runMany — a confirmed stop with no 408") confirm both a confirmed-stop-then-408 and
a confirmed-stop-then-no-408 classify correctly on HEAD, with `GetOpAnswer` never called before a
408 arrives and called only after the hard-cap abort when it doesn't. So the flake is pre-existing
in the stop path itself (client or server), not something R-236b's readback introduced.

**Why it is not proven.** `hang.itest.ts`'s `finally` deleted the scratch SQLite store and
quarantine dir on every exit, including a failed one, before either occurrence's failure message
could be read — so the one record that would say WHY the stop did not land (the stranded verdict's
`failureMessage`, carrying the watchdog's `stopDetail`: last stop refusal, last progress row, stop
hook error) was already gone. Fixed in this session
(`diag(hang): print error mutant failures, quarantine detail and warnings before teardown deletes
them`): on an assertion failure `hang.itest.ts` now prints every `error` mutant's full
`test_results.failure_message`, every quarantine record's `detail`, and the run's warning events
before rethrowing.

**Next step.** The next `itest:hang` run that hits this will print the cause instead of losing it —
read that output to learn whether `StopHungRunAt` was refused, threw, or the status poll that names
the op as still running failed, and file the fix (or close this as a platform flake) from that
evidence.
