**What.** `fixtures/sandbox-hang`'s M0004 (`lethal.void-method-call` on `HangLogic.Codeunit.al`
line 37, deleting the `Advance();` call that is `CountUpTo`'s loop progress) is one of the ON leg's

request at budget, `StopHungRunAt` confirms the stop, BC answers 408 naming the AL `StopSession`
call, and the client records `timeout`. On both occurrences below the ON leg instead came back with
M0004 scored `error`, a stranded quarantine, and the run stopping at 4 of 40 mutants: the server
never recorded a completed stop for that op.

**When.**

  `docs/measurements/2026-09-27-nst-wedge-incidents.md` §3: afterwards `HarnessInfo` and the company

**Evidence judged not caused by R-236b.** Full analysis:
`docs/measurements/2026-09-27-r289-hang-rootcause.md`. Summary: R-236b's
client diff (since `35214ad`) only touches `callOf`/`scoreManyAnswer`, which run AFTER a call is
already classified, and adds an optional timeout to `postAction` that `GetOperationStatus` and
`StopHungRunAt` don't use; a 408-with-stop answer is `outcome: "timeout"` with no `operation`, so it
never reaches R-236b's readback at all. Server-side, `ControlState.Codeunit.al` (which holds
`TryStopHungRunAt`) is unchanged, and `RunMutantMany` changed only in its last statement
(`KeepAnswer`), which a looping (non-terminating) method never reaches. Two offline reproductions
(the deleted session-scratch test, and the permanent test added by this session,
`packages/runner/tests/run-mutant-many.test.ts` describe block "runMany, a confirmed stop with no
408") confirm both a confirmed-stop-then-408 and
a confirmed-stop-then-no-408 classify correctly on HEAD, with `GetOpAnswer` never called before a
408 arrives and called only after the hard-cap abort when it doesn't. So the flake is pre-existing
in the stop path itself (client or server), not something R-236b's readback introduced.

**Why it is not proven.** `hang.itest.ts`'s `finally` deleted the scratch SQLite store and
quarantine dir on every exit, including a failed one, before either occurrence's failure message
could be read, so the one record that would say WHY the stop did not land (the stranded verdict's
`failureMessage`, carrying the watchdog's `stopDetail`: last stop refusal, last progress row, stop
hook error) was already gone. Fixed in this session
(`diag(hang): print error mutant failures, quarantine detail and warnings before teardown deletes
them`): on an assertion failure `hang.itest.ts` now prints every `error` mutant's full
`test_results.failure_message`, every quarantine record's `detail`, and the run's warning events
before rethrowing.

**Third occurrence, with diagnostics (2026-09-27, `lethal/lane-bugs`, control app 1.0.0.20, Cronus28,
rerun under R-236b's C2 acceptance, lease `048`).** Same shape: M0004 `error`, stranded, run stopped

- Four `lease-renew-unanswered` warnings fired during the same hang (`RenewLease` `AbortError` twice

- The readback added by R-236b behaved correctly here, which is evidence FOR "not caused by R-236b"
  rather than against it: the server's kept-answer row still named the PREVIOUS op (`a9/35209`), not
  M0004's (`a10/35210`), so `GetOpAnswer` found nothing to accept and the verdict correctly stayed

Full detail: `docs/superpowers/specs/2026-09-27-r236b-reply-fix-precommitment.md` OUTCOME, C2.

## How to rerun P1 if `itest:hang` fails again

Adapt `scripts/r289-probe/README.md`'s "One P1 run" recipe to Cronus28:

```bash
S=<scratchpad>/r289; R=1; rm -f $S/stop
bun scripts/r289-probe/sidecar.ts --container Cronus28 --config fixtures/sandbox-hang/lethal.config.local.json \
  --creds scripts/r289-probe/sidecar-creds.cronus28.json \
  --out $S/p1-$R-sidecar.ndjson --stop-file $S/stop &
pwsh -NoProfile -File scripts/r289-probe/container.ps1 -Container Cronus28 -Config fixtures/sandbox-hang/lethal.config.local.json \
  -Out $S/p1-$R-container.ndjson -Parts sql,service,stats -StopFile $S/stop &
pwsh -NoProfile -File scripts/r289-probe/container.ps1 -Container Cronus28 -Config fixtures/sandbox-hang/lethal.config.local.json \
  -Out $S/p1-$R-sessions.ndjson -Parts sessions -StopFile $S/stop &
LETHAL_ITEST_HANG=1 LETHAL_R289_TRACE=$S/p1-$R-trace.ndjson LETHAL_ITEST_CONFIG=lethal.config.local.json \
  bun run itest:hang 2>&1 | tee $S/p1-$R-gate.log
touch $S/stop; wait
bun packages/runner/src/cli.ts doctor --config fixtures/sandbox-hang/lethal.config.local.json
```

- `fixtures/sandbox-hang/lethal.config.local.json` is the Cronus28 config (server `Cronus28`,
  instance `BC`). `scripts/r289-probe/sidecar-creds.cronus28.json` holds the sidecar's own
  credentials and is gitignored.
- The probe BC user is LETHALPROBE. Never point the sidecar at the gate's own config's user: sharing
  a user with the gate is what the throttling finding ([[R317]]) says can starve the gate you are
  trying to observe.
- Pass `container.ps1`'s `-Parts` as one comma-separated string, for example `-Parts sql,service,stats`.
  `pwsh -File` hands it to the script as a single string, and the script splits it itself; this has
  worked since fix `98eda1c` (before that fix the collector wrote only its header).
- Lease rule: take a coordination lease on Cronus28 before each run, one run at a time, and release
  it right after. Run `lethal doctor` against the same config after EVERY run, pass or fail. Do not
  restart the container or its server; if doctor does not recover within 10 minutes, stop and ask the
  owner (the precommitment spec's section 6, "Wedge policy").
- Stop rule (precommitment spec, section 5): stop after the first failing run whose timeline gives a
  decided row of the decision table (section 3), or after 2 failing runs whatever they show. Never
  exceed 4 runs.
- A run killed from outside, for example by the coding tool's own memory limit, and not by the gate
  or the hang itself, is VOID: it does not count toward the stop rule and its sidecar/container
  output is not read as a result. This happened once, 2026-09-28 (run 4 above).
- If the gate is killed mid-run and `lethal doctor` then reports an orphaned lease, recover it with
  `lethal force-reset-lease --server <url> --instance BC --config <cfg>` before the next run. See
  [[R201]] for why this is manual: an expired lease with no operation in progress is reclaimed
  automatically by the next acquire, but an expired lease with a stranded operation marker (a run or
  publish that never finished) is not; it is refused as `operation-orphaned` and needs this command.
