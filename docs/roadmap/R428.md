**Seen three times on 2026-10-04 in the kraken container** (32 cores shared by four sessions running
suites at once):
1. The R-384 lane's final review run: an r214-history timeout; the file passed 22/22 on a re-run.
2. The R-384 lane's own first final run: one `(fail) (unnamed)`, clean on the next full run.
3. The orchestrator's post-merge check of b28e1cb7: `bun scripts/verify.ts` gave 5824 pass / 8 skip /
   2 fail, both unnamed. A `beforeEach`/`afterEach` hook in `packages/runner/tests/r214-history.test.ts`
   timed out at 5001 ms, and R358's leak check then reported leaked `lethal-r214-hist-*` temp folders
   (the folders the test creates with `mkdtemp` and did not remove after the hook timed out). Alone
   the file passed 22/0 in 5.19 s; a full re-run on the same tree was 5824 / 8 / 0. Load average was
   about 4 to 10 during these runs.

The file runs close to the 5 s default per test even when alone (5.19 s for 22 tests is fine in
total, but its setup copies a project tree per test), so load pushes one hook over the limit. The
second failure is a consequence, not a separate bug: the timed-out hook never reaches its cleanup.

It is a "fails under load" problem, not a wrong result, but each occurrence costs a re-run and can
hide a real failure behind "it's the flaky one".

**To close.** Measure the hook's time under load, then either give the slow setup an explicit timeout
or make the copy cheaper, and make cleanup run even when the hook times out (so R358 never sees a
leak from it). Red-check the cleanup by forcing the timeout.

**Correction, 2026-10-04.** The text above is kept as first filed. Measured later: the slow part is
the 22 test BODIES (a `mkdtemp` plus two `cp -r` of 6 files, 2,790 bytes), not a `beforeEach` or
`afterEach` hook. The file has only an `afterAll`. The whole file runs in 0.73 to 1.01 s, even beside
a concurrent full verify at load average up to 7.6, and the slowest test takes 0.11 s. The 5 s
timeouts were the whole process starved, not setup cost.

The leak mechanism: bun does not cancel a test that timed out, so its late `mkdtemp`/`cp` lands after
`afterAll` has run its `rm`, and recreates the `lethal-r214-hist-*` folder for R358 to find.

The fix: every whole test (setup and body) is tracked; `afterAll` awaits them all, removes each root, then sweeps
`lethal-r214-hist-*` in the temp folder (safe: the test preload makes that folder private to the
process). Red-checked with a forced late setup: without the fix R358 reports the leaked folder, with
it R358 stays green. The per-test timeout is 15 s, local to this file. It is a starvation guard, not
a fit to setup cost: a stall past 15 s is something we want to see fail. No suite-wide timeout moved.

2026-10-04, run 002: the tracking was extended from the setup promises to the whole test (setup and
body), because a timed-out body that keeps running could recreate a folder after the sweep (commit
named in the coord submission).

2026-10-04, run 003: `afterAll` now has an explicit 30 s timeout (it must outlast the 15 s per-test
guard), because under bun's 5 s default hook timeout the wait for a starved body could time the
cleanup out and leak the folders; red-checked with a late 8 s body.
