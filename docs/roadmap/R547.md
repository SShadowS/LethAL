**Found by the R-463 plan review (opus spec-adversary, adversary-r1 finding 5c, 2026-10-09).** Not caused
by R-463 and not changed by it.

Inside an open `reportextension` block (`insideOpenItem` in `packages/builtin-tier1/src/loop-hazard.ts`
answers true: an extension of a dependency report, or an anchor item that is open), a bare call `BaseProc()`
to a procedure the BASE report declares reaches R-500 shape 2's one-hop follow (`callTargets` in
`loop-hazard.ts`) through its on-table branch, which looks the name up on the innermost data item's table.
It never looks at the base report, so `BaseProc` is not followed, and the mutants inside `BaseProc` are not
hang-refused through this caller. When `BaseProc` iterates or writes a loop's exit state, a mutant there can
hang the session that runs the report.

**To build it.** In `callTargets`' bare branch inside a reportextension, also resolve the name on the base
report when the project declares it (unique by name), and red-test both directions: an open block's bare
`BaseProc()` refuses `BaseProc`'s mutants; the same call from a closed block does not. Count the sites on
BaseApp first (the 4 BC.History projects with reportextensions).

**Built (coord task R-547, branch `lethal/r547`, commit 6ec70aac).** Measured first
(`/coord/handoff/R-547/measure.md`): 0 deployed mutants change on any corpus; the hole is real on own-code AL.
`callTargets`' bare branch inside a reportextension now ALSO follows the name onto every base-report
candidate that declares it (`baseCandidatesOf` in `loop-hazard.ts`), beside the data item's table. Not "unique
by name", as first written: every same-named report counts (in a `#if` wrapper too, any arm), and so does a
split-header object (`symbols.splitObjects`) or an unparsed one (`symbols.unparsedObjects`) whose text names a
report and the base, by the token rule `projectDeclaresProcedureOnTable` uses (`identifierTokens`, now exported
by the engine). Ambiguity leans to refusal. Tests in
`packages/builtin-tier1/tests/r547-r548-reportext-base.test.ts`: a trigger caller, an extension-procedure
caller and the base closure are refused; the same calls from a block anchored on an ordinary table item keep
their mutants; two same-named bases (one in an undecided `#if` arm) and a split-header base are followed. Each
red-checked one direction at a time (`/coord/handoff/R-547/build.md`).

**Measured, not a residual.** `CurrReport.BaseProc()` inside a reportextension does NOT compile: alc 18.0.43
reports `error AL0161: 'BaseProc()' is inaccessible due to its protection level`, for a public and a
`protected` base procedure alike (runtime 13 and 16), while the bare `BaseProc()` binds it (`warning AL0432`
from an `[Obsolete]` marker). So `CurrReport` needs no mapping.

**`this.BaseProc()` (opus build review, finding 1).** At runtime 16, `this.BaseProc()` in a reportextension
BINDS the base procedure, public or `protected` (AL0432 for both; at runtime 13 `this` is not a keyword). It is
real on BaseApp: `MfgGetOutboundSourceDocs.ReportExt.al` calls `this.GetLocation`, a protected procedure of
base report "Get Outbound Source Documents". `callTargets`' member branch now maps a `this` receiver inside a
reportextension onto the base candidates (the extension's own `P` stays `bareCallee`'s same-object shape), and
`argWritten` reads `this.P(...)` like a bare `P(...)`. Test: an open block's `this.BaseProc()` refuses
BaseProc and its closure (red-checked by dropping the mapping).

**Residuals (named, not built).**
- A paren-less bare call in an expression (`if BaseIsDone then`) is not a call node and is not followed. The
  grammar gap every call-based rule here shares (`claimsRecordMethod`'s header documents it).
- An unparsed (`ERROR`) base candidate is followed by name only; its structure cannot be read.
- A base report outside the project: unchanged (the extension block already counts as open,
  `modifiedItemOpen`).
