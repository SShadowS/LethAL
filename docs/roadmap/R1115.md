Filed by coord PR-134 (lethal-preproc, 2026-11-17), from [[R1114]]'s direct check (`/coord/handoff/PR-134/result.md`).
- **What happens:**
  - `keptRefusalDrift` (`al-runner-v3-backend.ts`) compares a test's row with its baseline when the mutant "cannot reach"
    it: a NONE entry, or a test before the mutant's first covering test (`coveringOf`, built from the mutant's plan).
  - A plan holds only tests that pass at baseline. A test that FAILS at baseline is in no plan, so it always counts as
    unreachable, even when it does run the mutant's site.
  - For example, DO's `CreatePDF_WithValidData_ShouldCreatePDF` fails at baseline on an activation Confirm that sits after
    `CreateReports` is entered. M17235 removes that check, and the test then passes, on a fresh daemon too.
- **The effect:** a false `kept-refusal-drift`, so the daemon is closed and recompiled for nothing. x2 had one (43.7 s).
  - It is the safe direction (a restart, never a kept daemon), so it is a cost, not a verdict risk.
- **The fix to weigh (pre-commit and red both ways):** skip baseline rows that are not green in the drift comparison,
  because their reach is unknown.
  - For a test that is green at baseline and outside the plan, coverage says it never reaches the site. Its row cannot
    change, so the check keeps its meaning there.
  - What is lost: a red-to-pass flip after a kept refusal would no longer be caught. In PR-134's direct check that flip
    came from the mutant, not from contamination.
