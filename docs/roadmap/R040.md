**The uninstrumentable-object-kind gap costs 41% of a real app's mutation sites — and the reason given for it is WRONG.** On Continia Document Output: **287 of 449 files carrying sites, holding 8,259 of 20,036 sites (41%), are never mutated** — pages, reports, enums, and both `pageextension` and `tableextension`. A DO score is therefore computed over 59% of the app while reading as a whole-app number. `canCarryMutationSelectorVar` (`packages/schemata/src/compile.ts`) refuses every kind but codeunit and table, on the stated grounds that "only a codeunit or a table can carry the injected `var MutationSelector: Codeunit "Mutation Selector";` declaration, so a guard in any other object kind cannot compile (AL0118)". **Measured 2026-07-27 and disproven**: a probe app declaring that exact var inside a `page`, a `pageextension`, a `tableextension` AND a `report` compiles clean — `alc 17.0.29` exit 0, zero errors, artifact produced. The real constraint is the same one R38 turned out to be: WHERE in the object the `var` is anchored, not WHICH object kind. A page needs it after `layout`/`actions`, a report after `dataset`, a tableextension after `fields` — exactly the per-kind anchor reasoning the table branch already encodes. So this is anchor work on `injectSelectorVarIntoObject`, not a language limit, and the 41% is largely recoverable. Note the follow-on: the operators must then also target those bodies (`OnAction`, `OnOpenPage`, `OnAfterGetRecord`), and `notInstrumented` under-reports on a narrowed run (`fileCount: 0` with `totalFiles: 551`), which should be fixed alongside.

## Superseded status

done for page/report — **11,777 → 18,115 mutant sites on Document Output**, app coverage 59% → 90%, instrumented artifact compiles clean (0 errors, 9.0 MB). `CARRIER_KINDS` now admits page and report, which take the TRAILING anchor a trigger-less table already used; measured, not assumed. Enabling them immediately exposed a second defect the codeunit/table world could never surface: **204 sites matched by `negate-conditional`/`conditional-boundary` are not inside executable AL at all** — an AL page property is declarative but parses with statement syntax (`SubPageLink` reads `"No." = field("Customer No.")`, a filter reads `"Format" = ''`), so the operators claimed them and nothing could wrap them; one such site aborted the whole session at `buildComponents`. Fixed with `isMutableSite` checked once at spec generation rather than per operator, since it is a precondition of emitting a mutant at all, and the drop is counted and warned rather than silent. **Still open: `pageextension`/`tableextension`** (1,717 sites). They compile with the var, but they do not match `objectHeadersOf`'s header regex, and it is UNMEASURED whether BC attributes an extension's coverage to the extension's own id or the base object's — guessing wrong mis-keys `coverageFilter` and manufactures false survivors, the R29 failure exactly. **Probe run 2026-07-27 (`docs/measurements/tableextension-coverage-probe.al`), and the attribution fear was unfounded**: BC reports a tableextension's code under the EXTENSION's own object id (`…:79481`), not the base table's, so keying extension mutants on the extension id is correct. The real blocker is narrower and now named: **`objectType` arrives as the raw numeric `15`** (BC's TableExtension enum) where LethAL's manifest writes `"tableextension"`, so the `(objectType, objectId)` keys would not match and every extension mutant would silently become `no-coverage`. Remaining work: extend `objectHeadersOf`'s header regex to extensions, and map BC's numeric extension object types in `buildCoverageMap`/`normalizeObjectType` — the mapping must FAIL LOUDLY on an unknown type rather than defaulting, because a silent mismatch is indistinguishable from "nothing covered this". Coverage also came back object-level only (`procedure: undefined`), so extension mutants would lean on `coverageFilter`'s object-level fallback. **Extensions landed 2026-07-27**: `pageextension`/`tableextension` admitted as carriers (trailing anchor, measured), header regexes extended with the extension kinds ordered BEFORE `page`/`table` so a bare alternative cannot shadow them, and BC's numeric object types **14 = PageExtension** and **15 = TableExtension** mapped — both measured live, never read from documentation. `objectTypeName`'s unmapped fallback now warns once per type instead of silently stringifying, since that silence is precisely what hid this defect. **Document Output: 11,777 → 19,832 mutant sites, 162 → 438 instrumented files, nothing skipped**; the fully instrumented artifact compiles clean (0 errors, 9.07 MB). Both gates PASSED after the extension change: **`itest:bcdev` 3/10/3** and **`itest:tables` 63/10/2 with `untargetedTriggers` 0**, per-mutant. `itest:tables` ran on **Cronus283**, freshly prepared, because Cronus282 would not start (`hcsshim::ActivateLayer ... being used by another process`, surviving a host reboot — the user is rebuilding it). That makes the result stronger than a re-run would have been: the frozen numbers reproduced on a container built from scratch, so they describe the fixture and the code rather than accumulated state on one machine.
