**The bcdev backend could never run on a Linux or macOS host, and the publish tool was not pinnable.** Two defects, one report (PR #1, StefanMaron, measured against a live Linux Docker BC 28.1 container). (a) `defaultAlToolPaths()` hardcoded `bin/win32/` regardless of `process.platform`, so every non-Windows run spawned a Windows PE `alc.exe`/`altool.exe` that cannot execute — and the released Linux x64/arm64 and macOS binaries advertise this backend, so that was every non-Windows user. It surfaced as an opaque, MESSAGE-LESS `Error` many layers up (see R65). The extension ships per-RID builds side by side — verified here 2026-07-31 against `ms-dynamics-smb.al-18.0.2498801`: `bin/win32/{alc,altool}.exe`, `bin/linux/{alc,altool}`, `bin/darwin/{alc,altool}` — so the fix is a per-platform dir + suffix, with `platform` injected into `defaultAlToolPaths` so the branch is testable from any host, and a loud throw (not a guessed `linux`) on a host the extension ships nothing for. (b) `bcdev.altoolPath`, the publish-side twin of R43's `alcPath`: the extension's bundled `altool` 17.0.2273547 silently ignores `BC_SERVER_USERNAME`/`BC_SERVER_PASSWORD` for `publishapp` and its `auth login` is AAD-only, while the `microsoft.dynamics.businesscentral.development.tools` 18.x dotnet tool reads them and publishes. Follow-up fix on the same branch: the "no AL extension installed" gate keyed off the DISCOVERED install, so a config naming both tools was still refused on the container path — it now keys off the resolved pair (`resolveAlToolPaths`), which is what makes the override usable on a machine with no VS Code extension at all. Evidence: `packages/runner/src/publisher.ts`, `packages/runner/src/cli.ts`, `docs/benchmarks/runs.jsonl` (`bc-linux-sandbox-container`, the ledger's first plain-container rows).
