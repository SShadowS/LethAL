**Filed by R-340 (2026-10-09), its plan review r2 Minor-2.** `IDENTITY_SCHEME` exists because a mutant can change under an
unchanged identity key (R468's pair change, [[R340]]'s again: a newly typed argument makes `swap-call-arguments` pick
another pair at the same call). Every path that CARRIES a verdict or a mark refuses across a scheme change. Two
comparisons do not read the scheme or the mutated text:

- `campaign compare` (`compareCampaignStage`, `diffMutants` / `keyOf`), and
- every frozen `packages/runner/itest/*.baseline.json` gate comparison.

Neither carries a verdict (both sides really ran), so no false kill. But a mutant that changed under the same key with
the same verdict reads as "identical", and one whose verdict changed reads as a regression in the code under test: a
wrong diagnosis. Measured for R340: 0 fixture sites touch a trigger header name, so no gate is affected; the DO/CDO
campaign stages were not measured.

**To close:** have `campaign compare` report "identity scheme changed, UNVERIFIED" when the archived stage report's
`identityScheme` differs from the new one (the R355 pattern for coverage mode), and make the gate comparisons include
the mutated text (or refuse a baseline recorded under another scheme by name).

**Done: the MECHANISM (R-556, 2026-10-09; plan `docs/superpowers/plans/2026-10-09-r556-scheme-and-text-aware-compare.md`
r2, opus plan review applied).** The RECORDS are [[R560]]: by the orchestrator's ruling this item closes with the
mechanism, and R560 lists every gate baseline and campaign stage that stays text-UNVERIFIED until re-recorded.
- A newly recorded gate baseline or frozen stage records `identityScheme` and, per row, `mutatedTextSha256` (sha256 of
  the mutated text, `\r\n` as `\n`): a HASH, never the text, so a committed stage publishes no source. One reader
  (`readGateBaseline` / `parseGateBaseline`, baseline-guard.ts) accepts the legacy bare array and the object form, and
  refuses any other shape; every direct reader goes through it.
- Compare (`compareMutants`, mutant-equality.ts): same key and same hash -> the same mutant; same key and a different
  hash -> a per-mutant difference, "mutated text differs under an unchanged key" (neutral: a rename or whitespace edit
  in the target also changes it); a hash on one side only -> text UNVERIFIED, counted; across a scheme change a row is
  hash-verified only if its hash is unique in its tuple group on both sides (byte-identical twins share text while their
  ordinals move), the rest UNVERIFIED. A scheme change alone is never a refusal: "identity scheme changed" (R355's
  pattern), for gates as for campaigns.
- Gates: a legacy baseline passes as before with one line saying a mutant changed under an unchanged key is UNVERIFIED;
  a baseline WITH hashes refuses a run row WITHOUT one (the check cannot switch itself off).
- Campaigns: `campaign compare` returns an `identity` block beside R355's `coverage` (`verified` only when both sides
  record the same scheme and every row's text was checked); `campaign freeze` records the report's scheme and hashes,
  and REFUSES a report carrying the redaction marker (`REDACTION_MARKER` is never hashed anywhere).
- No committed baseline or stage was re-recorded (R332); see [[R560]].
