**Filed 2026-10-23 by coord task R-686** (lethal-code). A wording gap, never a verdict.

**What.** When BC's suite discovery lists no methods for a test codeunit, `RunOneMethod` answers only `expected
exactly one method M, found 0`. Since [[R686]], LethAL names "an OnRun that raises" as the cause when it is proven
(`TestCodeunitDiscoveryError`), but it cannot show the OnRun's own error text, so the user must open the codeunit in
BC's Test Tool to see it.

**To close.** Measure on a bc server what BC records for the codeunit itself when its `OnRun` raises during
`SelectTestMethodsByRange` (the codeunit line's result and error fields, under `Test Suite Mgt.`). If it is
readable, have `RunOneMethod` and `RunMany` add it to the found-0 answer, and have LethAL quote it. Needs a control-app
version bump and the hang gate.

**Evidence.** `/coord/handoff/R-537/measure.md` ("BC 28.4 (bc2)"); `/coord/handoff/R-686/plan.r2.md`.

**Measured 2026-10-25 by R-689 phase 1 (lethal-preproc), on bc2 (BC 28.4 W1).** Evidence: `/coord/handoff/R-689/`
(`measure.md`, `probe-bc2.jsonl`, `out/`), probe `scripts/r689-probe/`, pre-commitment
`docs/superpowers/specs/2026-10-25-r689-onrun-discovery-precommitment.md` (master 6f2e7ccd). LethAL Control unchanged.
- **What BC stores: nothing.** After `SelectTestMethodsByRange` on a test codeunit whose `OnRun` raises:
  - the suite holds one Codeunit line, with a blank `Result` and empty `Error Message Preview`, `Error Code`, full
    message and call stack;
  - there is no Function line;
  - the `AL Test Suite` record shows no failure.
  The same holds in LethAL Control's own suite (`LC1`) after a real `lethal run`, which refused with
  `TestCodeunitDiscoveryError` ([[R686]]).
- **Where the error is:** in the discovering session's last error, right after discovery.
  - `GetLastErrorText()` = the OnRun's own text.
  - `GetLastErrorCallStack()`'s first frame names the codeunit's `OnRun`, under `Test Runner - Get Methods`, which
    catches it. That is why discovery does not raise and lists no methods.
- **Readable by what, without a control change: nothing.** No web service is published on the Test Runner's objects.
  An API page on `Test Method Line` does exist on bc2, 99906 "Test Results API", from an app not identified. But the
  table holds no error, so it cannot show one.
- **To close (after the talk):** LethAL Control 1.0.0.24.
  - Call `ClearLastError()` right before `SelectTestMethodsByRange` in `RunOneMethod` and in `RunMany`'s
    `ResolvePairs`.
  - On found 0, add `discoveryError` and `discoveryErrorFrame` to the answer, when the stack's first frame names the
    requested codeunit.
  - LethAL quotes them in `TestCodeunitDiscoveryError`, and `MIN_CONTROL_VERSION` moves to 1.0.0.24.
  - Every BC gate is re-proven on all three servers, plus the hang gate.
  - The full proposal is in `measure.md`.

## Built (code and unit tests) 2026-10-25 by coord task R-689b (lethal-code); status stays open until the live proof

LethAL Control 1.0.0.24 (shared with [[R733]]); `MIN_CONTROL_VERSION` is 1.0.0.24. Not yet published to any server.
- **AL (`RunOneMethod`):** `ClearLastError()` right before `SelectTestMethodsByRange`; the last error text and call
  stack are copied into locals right after it. On found 0 the answer adds `discoveryError` and
  `discoveryErrorFrame` only when the text is non-empty AND the stack's FIRST frame (the text before the first `\`)
  contains `(CodeUnit <requested id>)`. The `error` field is unchanged. A source test pins the statement order.
- **Client:** `run-mutant-transport.ts` reads both fields on the found-0 (line-count) answer onto a new optional
  `TestVerdict.discoveryError {text, frame}`. A non-string, or only one of the two fields, throws. `failureMessage` is
  byte-identical (every found-0 matcher anchors on `, found 0`: R686, R688), pinned by a test. The baseline found-0
  refusal quotes `BC's discovery error: <text> (at <frame>)` in `TestCodeunitDiscoveryError`, and in the
  `StaleTestAppError` + `ONRUN_HINT` path; with no fields the messages are unchanged.
- **RunMany is deliberately NOT changed.** A grouped found-0 is `suite-unresolved`, whose `reason` `groupedFoundNone`
  (R688) parses from its END; adding text there risks that parse, and master's client talks to bc1-bc3 during the
  hold. The client never quotes a grouped found-0: it re-runs singly, and each single answer carries the fields. The
  baseline is always single.
- **Hub mode never quotes.** Hub-mode baselines (`procedure` or `line` coverage, `runOnHub`) do not carry the quote;
  only the transport path (coverage `none` or fenced; fenced is the default) does.
- **Limits:** (a) a `--resume`-reused baseline is rebuilt from the store's `failureMessage`, so there the quote is
  absent and the old wording shows. (b) An `OnRun` that raises inside a helper codeunit has a first frame naming the
  helper, not the test codeunit, so nothing is quoted (a known gap, by design: no other error is passed off as this
  codeunit's).
