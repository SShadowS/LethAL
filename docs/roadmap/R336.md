title: "The grammar does not parse `tableextension ... extends <number>`, so the whole extension becomes a root ERROR node"
section: "correctness-risks"
status: "open, filed 2026-09-29"
order: 1028
---

**Found by R-302 run 004 (2026-09-29), while checking [[R331]]'s mirror case.** Hand-written repro;
`alc` compiles it:

```al
tableextension 50102 "Repro Tab C2 Ext" extends 50101
{
    procedure Validate(A: Integer; B: Integer)
    begin
    end;
}
```

The native parser returns `source_file > ERROR` for the whole object, because `extends` is expected
to be followed by a name. So no mutant is generated in such an extension, and no structural check
can see what it extends or declares.

**What protects the build today.** [[R331]]'s rule 3 reads the TEXT of every unparsed root object
that starts with `table` or `tableextension`. If that text declares a procedure of the call's name,
Tier 2 does not claim the call. Without that, `validate-to-assign` emitted a mutant that failed
`alc` with AL0132, on this branch and on `master`.

**How often.** 0 extensions extend by number in DC/Cloud, BaseApp, System Application and
BusinessFoundation (a text census).

**Closing.** Report it upstream on SShadowS/tree-sitter-al with the repro above (not filed yet: a
public post). When the grammar parses it, pin the extension as a structural `tableextension` whose
base is an integer, and drop nothing: the text fallback stays for objects that still fail to parse.
