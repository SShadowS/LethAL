**Filed 2026-11-06 by lethal-bugs (coord task R-834).** Related: [[R814]], [[R586]].

**What was wrong.** A new user's walk stopped before any mutant ran:
- `bun run build:binary` made a binary with no parser, and said nothing.
- Nothing said where Microsoft's symbols or a Linux `alc` come from without a BC server or VS Code. The `bin/linux/alc` on our machines is a local wrapper, not Microsoft's.
- `lethal doctor` skipped al-runner on a config that also had `bcdev`, though the README said it printed the install command.
- A wrong `alcPath` read as "contract DIVERGED, re-measure". A run never said which al-runner it ran.

**What landed.** `build-binary` refuses with no addon; `scripts/fetch-ms-symbols.ts` (public NuGet feed) and `scripts/fetch-alc.ts` (pinned AL Language 18.1.2842859, .NET needed); `path` defaults to `~/.local/bin/al-runner`; `doctor` checks any `alRunnerV3` section; a named refusal for a missing `alc` or LLVM; one line naming the al-runner binary; README and gift-card README rewritten for the no-server route.

**Proof.** Three walks from a fresh clone with an empty HOME and `env -i`. The last reached a whole gift-card run from the docs: killed 34, survived 15, no-coverage 11, equal to the README's bcdev counts. A last check at the final code ran with no `dotnet` on PATH. Logs: `/coord/handoff/R-834/`.

**What that does not prove.** This is a container with an empty home, not a separate machine. `/work`, `/coord` and the corpora were physically present: no mount namespace is allowed here, and there is no `strace`. So reach was checked by a static grep. `alRunnerV3.path` was set by hand, because the default would have found this box's pinned build; the `~/.local/bin` default is proven by unit test only. Per-mutant equality with bcdev was not diffed. macOS, arm64 and Windows were not tried.
