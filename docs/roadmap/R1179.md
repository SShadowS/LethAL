Found by coord PR-341 (lethal-preproc, 2026-11-22), tracing R1178. Evidence: `/coord/handoff/PR-302/` (t1 and its resume
t1b on DO). Related: [[R197]], [[R1174]], [[R1178]], [[R47]].

**What the code does (read):**
- `recordKill` (`test-order.ts`) is called only at the three live kill sites in `orchestrator.ts`.
- Every session starts from `newKillLedger()`.
- A mutant carried from the store on `--resume` (its verdict, `killingTest`, `killPosition` taken from the prior run) never
  calls `recordKill`.

**The consequence.**
- In a fresh run, a procedure's earlier kills promote their killers for the procedure's later mutants (R197).
- In a resumed run, those earlier mutants are carried, so the ledger is empty for that procedure, and `orderCoveringTests`
  falls back to the next key (fewest members first).
- DO t1b (the resume of PR-302's t1) re-walked M2519, M2548 and M2549 in a different order than t1's first leg did. It read a
  different held error first, and so they missed PR-144's recheck (R1178).
- The same reorder can move a `killingTest` (R197's key) between a fresh run and a resumed one.

**Resumes are routine** (a SIGTERM, a watchdog stop, a time budget). So a resumed run's per-mutant table is not guaranteed to
equal a fresh run's, even on the same build.

**To decide.**
- **Seed the ledger:** on resume, feed each carried kill to `recordKill` in its original scoring order, so the remaining walks
  match a fresh run's. The carried row must give the qualified killer (`killingTestRef` or the covering set).
- **Or rule it a known limit** and say so in the report when a resume carried kills.
- A per-mutant equality test, fresh run against stopped-then-resumed run on a fixture with ledger-sensitive procedures, would
  pin either choice.
