**The question.** R-771's timing on the new `current` (edge-a157b2d34) read slower than dcdf9e821's, but under other
load. The talk demo runs on `current`.

**A/B under the same load** (`ab.sh`, 20:32-20:39Z):
- Method: the same `cli.ts run` that `scripts/v3-timing.ts` makes, with only `alRunnerV3.path` changed to each build's
  kept, gated folder. `current` was never moved. One warm-up, then 5 rounds with the builds alternating inside each
  round.
- Gift card: best 1.6 vs 1.7 s, median 1.9 vs 1.9 s. Equal.
- D1: best 26.7 vs 25.0 s (+6.8%), median 27.6 vs 26.4 s (+4.5%). Under the 10% bar.
- The one phase that clearly grows is D1's one-shot baseline call: 4.35 vs 3.43 s.

**Not #5743.** The login WorkDate lookup costs about 6 ms per test session: 0.07 vs 0.01 s of run time over ten
sessions with demo data.

**The upstream regression**
([#5872](https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5872)). A plain `al-runner test` on
a157b2d34 spends about 4 s in "compile" on every warm run:
- 4.0-5.2 s, against 0.15-0.31 s on dcdf9e821;
- reproduced with Microsoft-only packages and an invented ten-codeunit app;
- not network (`--no-download` makes no difference, and there are no connects);
- 18,216 `pread64` calls against 1,748;
- `--require-compile-cache` takes about 1 s on a157b2d34, so a usable entry exists.

Suspect, not bisected: a157b2d3 (#5841, the translations step).

**LethAL impact (corrected by R-797).** I first wrote that the cost is paid once per serve daemon start and once per
one-shot call. R-797 measured that this is wrong for LethAL's calls (below), so #5872 is not what slows D1. There is no
LethAL-side fix to make, and no pin-back (R125).

**R-797: `--require-compile-cache` wins nothing for LethAL, so it is not adopted (2026-10-25).** Evidence:
`/coord/handoff/R-797/` (`oneshot-rounds.txt`).
- **Where the 4 s goes.** In a157b2d34's al-runner (`runtime/corpus.rs:330-347`), a run whose selected tests "look
  free of data" (`observe::text_looks_pure`) first takes a LEAN path: a compile without the compile cache, of only
  what the tests reach. That path is where #5872's warm runs spend about 4 s. `--require-compile-cache` "never takes
  this path" and goes straight to the cached full compile. So the flag is sound:
  - same answers, because the lean path is an optimization the observe rule guards, and the full path is its
    reference;
  - a miss fails by name (`--require-compile-cache: there is no usable entry ...`).
- **LethAL's calls do not take that path.**
  - Method: the exact one-shot call the backend makes (`al-runner test --output-json --isolation test
    --test-timeout-secs 120 --codeunit 68933 --package-cache <CDO> --bc-version 28.4.53241.53758 --no-download
    --coverage-json <f> <project> <CDO Test>`), on a scratch copy of the CDO project. 4 warm rounds per arm,
    interleaved.
  - Result: a157b2d34 plain 2.7-3.95 s against 3.1-3.9 s with the flag; dcdf9e821 2.8-3.9 s either way. No
    difference beyond noise.
  - The serve warm-up grew only about 0.5 s on D1 (R-791 A/B), against the about 4 s a lean-path hit costs.
  - The contract probe is cached per build and key, so a session does not pay it.
- **So R-795's D1 growth (best 20.8 to 23.3 s) is not #5872.** Its deploy part is alc beside R790's speculative
  baseline, which lethal-code's R-798 is measuring. The rest is a157b2d34's own execution (run time 0.05 against
  0.02 s per call). The flag is not passed anywhere, and no code changed. #5872 still matters for plain
  `al-runner test` users, and stays filed upstream.
