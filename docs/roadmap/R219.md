**Found by pointing `lethal` at a real customer project for the first time since the campaign
work**: `DO.Support-NewFormat/DocumentOutput`, 553 `.al` files in the Cloud app, 111 in its test
app. Everything up to the batch build works. The run then refuses:

```text
cannot build the batch project: "ControlAddin\HTMLEditor\Script\events.js" and
"ControlAddin\PrintServiceCallback\Script\events.js" both rebase onto "Script\events.js".
Instrumented AL files are written flat, so a resource named relative to an AL file must sit at the
batch root, and these two would overwrite each other. Rename one of the directories.
```

The refusal is correct and is doing its job. The project has three `controladdin` objects whose
resource trees collide hard once flattened: **3 files named `events.js`, 5 named `main.js`, 3
named `Start.js`, 2 `styles.css`, 2 `window-debugger.js`**. Renaming a customer's directories is
not an answer.

This blocks BOTH backends, because the refusal lives in `prepareBatchProject`, which every backend
goes through.

## Why the obvious fix does not work, measured

Issue #8's un-flattening (write each instrumented file at its own project-relative path) removes
the collision by construction, and there is a stashed implementation. It was parked once already
with the note "al-runner will not compile a root-level `.al` together with one in a subdirectory".

**That note is wrong.** Measured against al-runner 2.11.0, a bundle holding `X.al` at the root and
`sub/Y.al` compiles both, and breaking the nested one reports its errors.

The real rule is a SOURCE-ROOT convention, and it is sensitive to the directory's NAME. Breaking
the root-level `.al` and asking whether al-runner notices:

| subdirectory | result | root file |
| --- | --- | --- |
| `sub/` | exit 3 | compiled |
| `src/` | exit 0 | **ignored** |
| `app/` | exit 0 | **ignored** |
| `source/` | exit 3 | compiled |

When the bundle root contains `src/` or `app/`, al-runner treats it as the source root and skips
everything outside it. That is exactly why the retry fails: the scaffolding is written at the
bundle root and the instrumented sources under `src/`, so the sources compile and
`Mutation Selector` is missing (`AL0185`).

Moving the scaffolding into `src/` fixes THAT, verified by hand on a produced bundle. It is still
not enough:

```text
bundle: src/A.al + ControlAddin/B.al,  B deliberately broken
al-runner: exitCode 0
```

A sibling directory is skipped too, **with no diagnostic**. Continia declares its three
`controladdin` objects in `ControlAddin/`, outside `src/`, so un-flattening would silently drop
three AL objects from the built app. Today's flat write produces no `src/` directory in the bundle
at all, which is the only reason it works there.

Silently dropping AL is worse than a loud refusal, so the refusal stays. The experiment branch
`unflatten-retry` (commit `1ead4dc`) carries the attempt and this reasoning; it is not for merging.

## Options, none of them free

1. **Rename resources on copy and rewrite the `controladdin` declarations to match.** Keeps the
   flat write. Means editing a declaration's `Scripts`/`StyleSheets` lists, which is AL rewriting
   of a kind nothing else here does, and the add-in must still work at runtime.
2. **Un-flatten, and place BOTH the scaffolding and every AL file under one source root.** Fixes
   `alc`/bcdev outright, since it compiles a directory recursively and has no such convention. For
   al-runner it needs every `.al` moved under `src/`, which breaks a `controladdin`'s relative
   resource paths, so those resources need rebasing too. This is the direction that actually solves
   the collision, and its cost is that the two backends want different layouts.
3. **Ask upstream for a flag** that compiles the whole bundle regardless of `src/`, or at minimum a
   WARNING when AL files are skipped. The silent skip is the part worth reporting either way: a
   consumer gets a successfully built app with objects missing and nothing said. **DONE: reported
   as StefanMaron/BusinessCentral.AL.Runner#3714**, with both shapes measured (root-level and
   sibling-directory) and the observation that `sub/` and `source/` do not trigger it while `src/`
   and `app/` do.
4. **Do nothing and document it.** A project with colliding add-in resources is not measurable by
   LethAL. Honest, and it is what today ships.

Option 3 is worth doing regardless of which of 1 and 2 is chosen, because the silent skip will
bite something else later.

## What DID work on this project, worth recording

- `doctor` passes and names the al-runner-only caveat correctly.
- `--dry-run` completes over the whole app: **440 files, 38,781 mutant sites, 37,449 deployed**,
  and 198 declarative sites dropped with the [[R144]] announcement naming each file and kind.
- The selector-id refusal fired correctly and usefully: the default 79199 is outside the app's
  declared `6175271-6175468`, and the message named the flag and the range. Worth knowing that the
  range has only **four** free ids left, so a real project can be close to having no room for the
  three objects LethAL injects.
- The [[R183]] canary reported that al-runner 2.11.0 DISCARDS a row written inside `Codeunit.Run`
  when the error fires, which 2.7.0.0 did not. That is the residual keeping `authoritative: false`,
  and it may have closed. It needs re-measuring against bcdev before anything is claimed.

**Fix (ruled 2026-10-07: keep the flat write).**
- A duplicate basename (case-insensitive) is written as `<stem>.<8 hex>.al`, where the hex comes from
  the sha256 of its project-relative directory, normalised to `/` with its case kept. A unique
  basename is unchanged.
- `flatNamesFor` (schemata) is the one map. It is built over the whole project, and both writers use
  it (`writeInstrumentedProject`, and `prepareBatchProject`'s copy). It refuses a name it cannot make
  unique.
- The batch records its renamed files in `lethal-flat-names.json`, written only when there are any,
  so every other batch is byte-identical. Every reader that quotes a batch file translates through
  it: the line map (`readAlSources`), the al-runner coverage index's refusal texts and file lists, an
  `AlcCompileError` (a note naming each renamed file), and the installed bundle's stored paths.
- The coverage index keeps its keys flat, which is what al-runner compiled and what Cobertura
  reports.
- **Run 002 (sol, review of run 001): what al-runner actually reports, MEASURED 2026-10-07 on
  c39ad5de.** A duplicate pair `Sales/Helper.Codeunit.al` + `Purchase/Helper.Codeunit.al`, each
  covered by its own test. On BOTH transports (one-shot `--coverage-out` and `--server`
  `perTestCoverage`), al-runner labels coverage with whichever path it knows for the app id:
  - the project SOURCE path (`proj/Sales/Helper.Codeunit.al`) when the batch sits beside the source;
  - from a copy elsewhere, the FIRST batch's own flat path (`run/batch/Helper.Codeunit.8de4e0ea.al`),
    not the copy's.

  The cwd did not matter. Lines and `--server` scopes are the compiled file's, and the two files
  were never confused. The run 001 index keyed renamed files by their flat names only, so a
  source-path label matched neither and the coverage would have vanished: covered mutants would
  read `no-coverage`. Each renamed file is now ALSO keyed by its project path. A reported path
  ending in a bare duplicate basename that matches neither key is refused by name, never dropped.
  End to end through `lethal run` with `alRunner.coverage: "al-runner"`, on both transports, each
  helper's mutants are covered by exactly its own test, and the verdicts are identical across the
  transports.
- **Run 003 (sol, review of run 002): no suffix guessing for a shared file name.** Matching the
  longest suffix credited the wrong file in two constructions: `Sales/Helper.al` against
  `X/Sales/Helper.al` in a project whose root is named `X`, and a project file literally named like
  another file's flat name. And two paths that differ only by case (`Sales/` and `sales/` on a
  case-sensitive file system) folded to one key, and the later file silently replaced the earlier.
  Now:
  - Two files whose keys collide once lower-cased are refused before indexing.
  - A reported path whose LAST SEGMENT two or more files own is resolved exactly. Under the project
    directory it is a project-relative path; directly in the batch directory it is a flat name. It
    is refused if it resolves in neither, or in both to different files. The one-shot transport
    reports paths relative to its cwd and `--server` reports them absolute (measured again on
    c39ad5de), so the path is resolved against the cwd first.
  - A last segment only one file owns still matches by suffix. It cannot reach another file, and
    the measured "first batch's flat path" (a directory LethAL no longer uses) needs it.
  - `buildBackend` hands the project directory to the al-runner backend for this.
- The record's name is reserved: a project resource that would land on it, as it is or rebased, is
  refused. `scripts/campaign/compile-only.ts` passes the one whole-project map to both writers.
- **R-219c (2026-10-08), the run 003 review's minors:**
  - The `--server` scope warning names the file a label RESOLVED to, not a guess from the label's
    basename. Those differ when a project file is named like another file's flat name.
  - On `--server`, a coverage-index refusal now stops the session, as it does on the one-shot
    transport. Before, it read as an `error` verdict on every test.
  - Without a project directory, a source-path label for a shared name is refused (pinned by test).
  - What is not measured, how al-runner picks the label, is filed as [[R505]].
