**Found 2026-10-08: master's Windows `check` job failed on 736dd7ff.** The R505 test "a resource
changed is named" saw no change: it rewrites `addin/x.js` at the SAME size (`console.log(1)` to
`(2)`) right after the first check. It passed on the R-505 branch and on e7a9ffba, so it is
intermittent.

**The hole is in the product, not only the test.** `watchProjectInputs` (`source-drift.ts`) is
stat-gated: once a file's bytes were seen equal, it re-read them only when size, mtime or ctime
moved. An edit that lands inside the timestamp resolution of that check can leave all three equal,
so the bytes were never compared again. That this is what happened on Windows is INFERRED, not
measured: NTFS stamps the write time from the coarse system time (a tick of about 15.6 ms), and the
test's write, check and rewrite fit inside one tick. A
real user's same-size edit made at the wrong moment would be missed the same way, and the run would
read coverage al-runner labels with the edited files.

**Fixed:** git's "racy clean" rule. A stat is cached only when its mtime and ctime lie more than
`RACY_MS` (3 s, wider than any filesystem's granularity, FAT's 2 s included) before the check that
saw the bytes equal. A file written around that check is re-read at every check until it ages, so
the cost is a re-read of recently written files only. Two tests force a stat that never moves
(`watchProjectInputs`' new `statFile` parameter): a FRESH unchanged stat must still name a same-size
edit, and a SETTLED one is trusted (the stat gate). Each goes red under its own revert (cache every
stat; never cache). The watch's LIMITS paragraph now states what the gate still cannot see: a
same-size edit with an identical stat on a file settled more than 3 s ago, and a filesystem whose
clock runs behind this machine's (it can settle a file too early).
