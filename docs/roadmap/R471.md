**Found 2026-10-05 under R-469**, beside R470. Measured against the kraken daily al-runner build
(`/work/tools/al-runner/current`) and alc 18.0.43.

**Repro** (self-contained, no dependencies, `runtime` 13.0): one project with

```al
codeunit 50690 "Mutation Selector"
{
    procedure IsActive(Id: Integer): Boolean
    begin
        exit(Id = 0);
    end;
}

table 50693 T2
{
    fields { field(1; Code; Code[20]) { } }
    keys { key(PK; Code) { } }
}

report 50698 R
{
    ProcessingOnly = true;
    dataset { dataitem(T2Item; T2) { } }

    trigger OnPreReport()
    begin
        if MutationSelector.IsActive(7) then;
    end;

    var
        MutationSelector: Codeunit "Mutation Selector";
}

reportextension 50699 RE extends R
{
    trigger OnPreReport()
    begin
        if MutationSelector.IsActive(8) then;
    end;

    var
        MutationSelector: Codeunit "Mutation Selector";
}
```

- `alc /project:. /packagecachepath:./.alpackages`: exit 1, `error AL0155: A member of type
  GlobalVariable with name 'MutationSelector' is already defined in Report 'R' by the extension
  ...` on both declarations.
- `al-runner .`: exit 0, `Tests: 0 passed 0 failed 0 errors 0`. No diagnostic.

**Why it matters to LethAL.** R470 makes LethAL emit exactly this shape for a same-project report
and reportextension that both carry mutants. On bcdev the batch is scored `error`; on al-runner
the same artifact compiles and the mutants are scored. So the al-runner path can look green where
the authoritative backend errors, and an al-runner result is not evidence that the artifact is
valid AL. More generally, al-runner does not run every check alc runs; this is one measured
instance.

**To close.** LethAL side: R470's fix removes this artifact shape. Whether to report the
divergence upstream to al-runner is the owner's call. If LethAL wants a guard independent of
R470, the al-runner path could alc-check the emitted bundle where alc is available (cost:
one compile per batch).

**Reported upstream 2026-10-09 (R-546): al-runner #5471**
(`https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/5471`). It has a minimal
self-contained repro (one invented file, runtime 13.0, no dependencies) that still reproduces on
`v2.12.0-main.43f76177` and `v2.12.0-main.c5bbaf89`: alc exits 1 with AL0155, and al-runner exits 0
with no diagnostic. The repro and logs are in `/coord/handoff/R-546/upstream/r471/`. A duplicate search found
none. This item stays open for the LethAL-side question above.

**v2 retired (R654); re-measure on v3.** The measurements above are on the .NET al-runner, deleted in R654 S3
(35f3c67f). On the Rust al-runner this is likely moot: LethAL compiles every batch and the test app with alc before
v3 sees them, and refuses to run bytes alc did not prove (the v3 gate's X legs, #5602). So an AL0155 batch would be
refused before v3 runs it. That is not measured with this repro. To close: run it through `--backend al-runner-v3`
and confirm the batch is refused by alc, not scored.

**Closed 2026-10-23 by ruling (coord task R-537, lethal-code): moot for LethAL.** Measured with the repro above plus
one invented test codeunit, swept over runtimes by `/coord/handoff/R-537/r471/sweep.sh` (its `sweep.log` keeps every
exit code):
- **What decides it.** The v3 backend compiles every batch with alc before v3 runs it, so a batch alc rejects never
  reaches v3. The unit test "leg X (a): a batch alc rejects throws AlcCompileError and v3 is spawned 0 times" and the
  v3 gate's leg X (a) pin that.
- **AL0155 depends on the runtime.** alc 18.0 rejects the shape with AL0155 at `runtime` 13.0, 14.0 and 15.0
  (exit 1), and reports nothing at 16.0 and 17.0 (exit 0).
- **v3 agrees with alc from runtime 16.** alpha.2 (91253f2d6) and edge (57f1e4f98) pass the test with exit 0 at
  every runtime from 13.0 to 17.0. Below 16.0 each prints a note: alpha.2 says the app runs as 16.0, and edge says it
  knows members only from runtime 16. The difference below 16.0 is filed upstream (#5471, the v2 report, is closed):
  [aldevtools/BusinessCentral.AL.Runner#5750](https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/5750).
