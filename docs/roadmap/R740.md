**Filed 2026-10-24 by lethal-preproc during R-738** (opus build review). Related: [[R738]], [[R741]], R31 and R139.

**What.** [[R738]] refuses a baseline failure "Function ID <n> was called. The object with ID <id> does not have a
member with that ID." only when `<id>` is one of the TARGET's declared objects (`staleTargetMember`). The same failure
naming a DEPENDENCY's object is left as an ordinary failure. That arises when a dependency app (a library the tests or
the target use) was upgraded under a tests app that was not recompiled. Such tests leave the green set, their calls
never reach the target, they write no coverage rows, and every mutant they would cover reads `no-coverage`: R738's
measured silent under-report, except that LethAL did not cause it.

**Why it was not refused in R738.** The remedy differs (republish the tests app against the CURRENT dependencies, not
"against the current target"), and refusing every such failure would also refuse a suite whose one test calls a
library member that legitimately changed. Not measured.

**To close.** Measure under a pre-commitment: a dependency app with a member the tests call, upgraded to a build
without it while the tests app stays installed, then a `lethal run` baseline. If the drop is silent, decide on a ruling
between a named refusal with a dependency-specific remedy (the object id resolved to its app when possible) and a named
warning plus a report caveat that counts the dropped tests.

**Done 2026-10-24 by R-740 (lethal-preproc).** Evidence: `/coord/handoff/R-740/measure.md` (runs 1 and 2), probe
`scripts/r740-probe/`, pre-commitment `docs/superpowers/specs/2026-10-24-r740-stale-dependency-member-precommitment.md`
(master 5eb017b1, addendum 1 71f7bd92).
- **Measured (run 1, bc2):** a library upgraded through altool, without a member the tests call, under an unchanged
  tests app, was accepted. The test failed with BC's sentence naming the LIBRARY's object (93820). The run did not
  refuse: exit 0, "score 100.0%", the test sat with the genuine failure under `unsupportedTests`, and the 2 target
  mutants only it covered read `no-coverage`.
- **Ruled (A), built:** `staleDependencyMember` (stale-test-app.ts) reads the same anchored first-line sentence as
  R738's `staleTargetMember`, for an object the project does NOT declare, together with the failure's first stack
  frame (the calling object and app). `scoreBatch` refuses with `StaleDependencyMemberError` right after R738's
  refusal and before `select`. The message names the tests, the object and the calling frame, and gives a NEUTRAL
  remedy: recompile and republish the calling app against the dependencies installed now, or leave its test files
  out with `--tests-only`.
- **Proved live (run 2, the built head):** refused by name, exit 1, naming TestLib, object 93820 and the frame "R740
  Tests(CodeUnit 93840).TestLib line 4 - R740 Probe Tests ...". No report was written and no mutant was scored.
- **Tests:** r740-stale-dependency.test.ts (4), plus the orchestrator test that R738 had as "a non-target object does
  not refuse", now "refuses as a stale DEPENDENCY member" and not as R738's error. Red-checked: drop the throw; let a
  target id through; cut the frame wrongly.
- **The price (accepted by ruling):** when the stale caller is an app the user cannot rebuild (a third-party test
  library stale after a platform update, say), the run refuses until that app is fixed. The only way round it is
  `--tests-only`, which narrows whole test FILES. Excluding a single test method is [[R745]] (after the release).
- **Limits:** as [[R738]]'s (English text; the fenced path's layout). An object the project declares in a file
  `objectHeadersOf` cannot read (an interface, an enumextension) would read as a dependency's. A tableextension member
  is [[R741]]. A stale call inside an `asserterror` whose `ExpectedError` does not match still drops as an ordinary
  failure: BC's sentence then sits inside the Assert text, which the anchor does not read (as R738).
