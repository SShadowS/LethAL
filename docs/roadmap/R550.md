**Why a report arm needs its own design**, not a copy of R-536's:
- Execution differs by backend. In the fenced BC session a test must RUN the report (`Report.Run`/`SaveAs*` with a
  request-page handler, or a call into the report's own procedures), and what the session allows is a measurement in
  itself; al-runner runs a report through its own request-page handler dispatch and does not render, so the two
  backends reach a report's data-item triggers by different routes.
- [[R500]]'s open-item dispatch refusals apply to report data-item code: a report arm's sites must be chosen so they
  are not hang-refused, or the arm measures the refusal instead of the numbering.
- A report's data-item triggers are trigger mutants, placed by object (selection's fallback 1), so the numbering
  evidence has to come from a procedure placed below a mutated trigger, as `Doubled` and `Label` do in R-536.
