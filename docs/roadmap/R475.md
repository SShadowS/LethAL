**Closed 2026-10-05 (9a05a40e), identity scheme 24.** Every identity comparator now orders strings
by UTF-16 code unit (`compareCodeUnits` in `packages/schemata/src/ids.ts`): file and operator order
in `numberIdentityOrdinals`, file and mutant-id order behind `assignIdentityOrdinals`, the operator
tie-break in `assignMutantIds` (mutant codes) and in the component nesting order. That is the order
file discovery and the generation hash already used, so the host's collation no longer reaches a
key. The Windows probe in "To close" is no longer needed.
- **The false kill, reproduced.** `r391-cross-file-twin.test.ts` ("R475: resuming unchanged source
  under another host collation …"): twins in `Aa_Twin.Table.al` and `Z_Twin.Codeunit.al`, run 1
  kills Aa's twin and aborts on an unrelated sentinel before Z's twin runs, run 2 resumes under a
  Danish `localeCompare`. With the old comparator Z took Aa's key under an equal source hash and
  rule 1 carried `killed` onto it (received `Aa survived`, `Z killed`); fixed, Z is executed and
  survives and Aa's kill carries.
- **Measured: 0 moves.** Over 1.76M sites (every fixture and example, CDO Cloud and Test, BaseApp
  and its tests) under en, da, sv and en upper-first collations, 0 keys and 0 mutant codes move;
  no built-in operator pair orders differently. Only a synthetic twin project moves (8 keys under
  da). Scheme 24 still, because keys recorded on a host with another collation could differ (23 was
  held for R-446, which landed as 25, and is unused). No gate baseline moves.
- **Red checks:** six, one per comparator, in the coord handoff `R-475`, `red-checks.md`.
- **Left open:** the covering-test name tie-break uses the host collation too and can change a

**Found 2026-10-05 by the adversarial review of R-391's built code** (coord handoff `R-391`);
pre-existing, not introduced by R391.

**What.** `numberIdentityOrdinals` (and the ordering helper beside it in
`packages/schemata/src/project.ts`) sorts the run's entries with `a.file.localeCompare(b.file)`,
then by offset. `localeCompare` without a locale argument uses the runtime's DEFAULT collation. A
collation that orders file names differently (Danish sorts `Aa...` after `Z`, for one) numbers
cross-file twins in a different order for byte-identical source.

**Why it matters.** Twins are told apart by that ordinal. Under R391's rule 1 a verdict carries by
key when the generation source hash is unchanged. The hash does not depend on the host, but the
numbering would. So one results store used from two hosts with different default collations could
hand a twin another twin's key with the hash equal, and `--resume` would carry `killed` onto the
wrong mutant. Plain key matching before R391 had the same exposure.

**Measured so far.** In the kraken Linux container Bun's default collation is `en-US` whatever
`LANG` says (C, en_US and da_DK probed by the reviewer). The Windows host's default (Bun/ICU there,
possibly a Danish system locale) is NOT measured.

**To close.**
1. **Probe** the Windows host: `bun -e "console.log(['Aa','Z'].sort((a,b)=>a.localeCompare(b)))"`.
   That is a host-only check; ask the owner.
2. If the default collation is ever not `en`-like, sort with a fixed collation
   (`localeCompare(b, "en")`) or by code unit (`<`). Either is an identity change for any project
   whose file order differs, so it needs an IDENTITY_SCHEME bump and the usual baseline check.
