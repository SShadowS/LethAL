**Found 2026-10-05 under R-469** (an alc probe for R469's protected-var question). A consequence of
R254, which made `reportextension` a carrier kind.

**What.** PLAN's `injectSelectorVarIntoObject` (`compile-plan.ts`) declares
`MutationSelector: Codeunit "Mutation Selector"` in EVERY object that carries a mutant. A report's
globals are visible to its reportextension, so when a report and a reportextension of it sit in
the SAME project and both carry mutants, the instrumented project declares the same global twice.
MEASURED with alc 18.0.43 on a self-contained probe (a report and a reportextension of it, each
with `var MutationSelector: Codeunit "Mutation Selector";`): `error AL0155: A member of type
GlobalVariable with name 'MutationSelector' is already defined in Report 'R' by the extension ...`,
on both declarations. It needs no `protected`: a plain `var` on both sides fails. TWO
reportextensions of one report collide the same way (AL0155 "already defined in ReportExtension
'RE2'"), even when the report itself declares nothing or lives in a dependency, so the condition is
two or more instrumented objects among a report and its reportextensions in one project. A name
unique to each extension, derived from its own object id (`MutationSelector50699`), compiles clean
beside the report's `MutationSelector` and a sibling extension's (measured, same probe). Tables with
tableextensions and pages with pageextensions do NOT collide (the extension's own declaration
shadows the base's, even a protected one of another type, measured in the same probe).

**What a run does today (traced, not run live).**
- bcdev: the deploy throws `AlcCompileError`; R461's plain build compiles (the unmutated target
  has no selector), so bisection runs. No single mutant breaks the compile (it is a pair
  condition), so `bisectFailingMutant` cannot confirm a culprit and answers `environmental`.
  Every mutant in the batch's execute set is then recorded `error` with that note, and the batch
  is abandoned. With one batch, that is the whole run. Loud, not a silent wrong verdict.
- al-runner: `al-runner <bundle>` on the same probe compiles and exits 0, so al-runner accepts an
  artifact BC rejects. Both declarations have the same type, so gating is most likely unaffected
  there, but the two backends disagree about whether the run is valid at all.

**Why no gate caught it.** `itest:tables`' R254 arm keeps its base report `Data Band Report` code
free (so the arm measures the extension's own coverage), so the base never gets a selector. R254's
BaseApp count (+543 reportextension mutants in 13 files) counted sites and never compiled a project
in which a base report and its extension both carry mutants (confirmed by R254's author).

**To close.** Census the same-project report/reportextension pairs where both carry deployed
mutants (BaseApp, CDO). Fix in PLAN: give a reportextension's selector a name that cannot collide,
or reuse the base report's visible one; prefer the variant with the least state. Pin it with a
fixture-free unit test of the emitted text AND an alc probe of the emitted pair. Say whether keys
move.

**Closed (cad4420d, R-469; plan and reviews in the coord handoff `R-469`).**
- **Census** (`measurement.md`, real pipeline, 227 projects): 10 colliding groups, all in BaseApp's
  Base Application. 13 reportextensions against 10 base reports, each base report also declaring the
  selector; about 2,700 deployed mutants in those files. `Get Demand To Reserve` has three
  extensions that also collide with each other. CDO 0, fixtures 0.
- **Fix, in PLAN:** `selectorVarName` names a reportextension's selector `MutationSelector<its object
  id>`; every other kind keeps `MutationSelector`.
  - Stateless: it never depends on whether the base report or a sibling also got one.
  - If that identifier already occurs in the extension's own text, `_1`, `_2`, ... is appended.
    A same-named global in another file of the namespace is not checked, the exposure
    `MutationSelector` itself has.
  - The name rides in the chain payload beside the latch, and EMIT writes it in `emitDispatch`,
    `branchText` and `REACH_MARKER`.
  - A reportextension with no numeric id is refused at the new site `compile.selector-name`. That
    is unreachable from parsed source, since the parser yields `ERROR` (measured).
- **Tests** (`r470-reportext-selector`): a report, three reportextensions (with a var section,
  without one, and one already using its id-named identifier) and a codeunit. Each was red-checked
  against its wrong fix:
  - no rename: 3 tests red;
  - rename every kind: the report/codeunit control red;
  - declaration-only rename: 2 red. alc would pass this one, because the stale guards bind to the
    base report's selector, which is why exact text is what pins the fix;
  - no hygiene suffix: the suffix test red.
- **alc on the EMITTED text** of that project (`tools/alc-emitted.ts`): exit 0. On master's emission:
  4x AL0155, report against extension and extension against extension.
- **No key or site moves.** The exact site diff against master is EMPTY: 235 capture files
  byte-identical over BaseApp (2,155,896 rows), CDO and every fixture (`site-diff.md`).
  - sandbox-data's manifest pin is unchanged; only `DataBandExt.ReportExt.al`'s instrumented text
    was re-pinned.
  - `itest:tables` under a Cronus28 lease: PASS, 310 / 70 / 22, every per-mutant verdict equal to
    its baseline.
  - The instrumented text changes, so a project with reportextensions re-measures its baseline
    once.
