**Found by R-385 (D6 of `docs/superpowers/plans/2026-10-04-R-385-resident-microsoft-dependencies.md`).**

## What

R-385 made the bcdev path fingerprint Microsoft dependencies, `System` and the control app's
dependencies by the bytes the server holds. al-runner keeps the old reading on purpose:
`dependencyFingerprint(..., {kind: "declared"})` writes `M <id> <declared version>` for a Microsoft
app, plus a `K declared` line so such a fingerprint can never equal a bytes one.

The gap is wider on al-runner than it was on bcdev: al-runner provisions Microsoft apps at the
project's version prefix resolved to the LATEST Microsoft build (`al-runner-backend.ts`, the
provisioning code), so two al-runner runs a week apart can run different Microsoft code under the
same declared version, and the digest does not move.

## Why it has no effect today

`lethal verify` is bcdev only (`cli.ts`, the verify backend check), so al-runner digests are recorded
but never compared.

## What would close it

Before verify supports al-runner: read each Microsoft dependency (and `System`, and Test Runner)
from the platform-apps directory al-runner actually provisioned for the run (R147 pins it for the
one-shot legs), hash those packages as the bcdev path does, and drop the `declared` mode. A test
must show that a newer provisioned build of a Microsoft app at the same declared version makes the
tests new.
