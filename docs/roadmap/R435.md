**Fixed 2026-10-23 by coord task R-435.** `testAppDependencies` (`orchestrator.ts`) now gives a backend that does
not publish but has `dependencyPackageDirs` (v3) a third Microsoft mode, `{kind: "folder"}` in `digest-inputs.ts`.
The fingerprint queues `Application` by its id, hashes every Microsoft package it finds in the package folder,
walks their dependencies, and writes a `K folder` line. It skips System, the control app and the installed check
(v3 publishes nothing). A Microsoft dependency that is in neither the folder nor the artifact cache (below) refuses by name: the run goes on, but is
`test-app-dependencies-unproven` and lends nothing.
The folder is searched first. A Microsoft app that is not there is then looked up in v3's artifact cache
(`<cacheDir>/artifacts/<bcVersion>/apps/*.Source.zip`, where v3 keeps Library Variable Storage and Business
Foundation Test Libraries): the zip is hashed by its bytes, and its id and dependencies come from the `app.json`
inside it. If both places hold the app, the folder wins, as in v3 (measured: the CDO smoke loads Library Assert from
`.alpackages`). A backend with no package folder keeps `declared`.
Tests: "R435: Microsoft dependencies by the bytes in the package folder" (`digest-inputs.test.ts`) and the "R435"
tests under "R496 T11" in `orchestrator.test.ts`.

**Cost.** Every v3 test-app fingerprint changes once, so a `--resume` of a v3 run made before this change refuses
once (`TestAppRepublishedError`), and stored v3 snapshots stop matching once. A project with a Microsoft dependency
that is in neither the package folder nor the artifact cache (or a v3 config with no `cacheDir`, whose cache LethAL
cannot name) runs unproven on every run: no `--resume`, no `--skip-known-survivors`, no lending.

**Limits.** System.app and the binaries are not hashed. The fingerprint is taken before v3 runs, and v3 downloads
the cache zips during a run on a fresh cache: so the first run of such a project is unproven, later runs are proven,
and a `--resume` of that first run is refused. If several cache zips carry one app id, all are hashed. The load probe (`/coord/handoff/R-435/load-probe/`) showed v3
loads Library Assert from the `--package-cache` folder on alpha.2 and edge, with no competing cache copy; the
"folder wins" rule rests on the CDO smoke only.

Original item:

**Found by R-385 (D6 of `docs/superpowers/plans/2026-10-04-R-385-resident-microsoft-dependencies.md`).**

## What

R-385 made the bcdev path fingerprint Microsoft dependencies, `System` and the control app's
dependencies by the bytes the server holds. al-runner keeps the old reading on purpose:
`dependencyFingerprint(..., {kind: "declared"})` writes `M <id> <declared version>` for a Microsoft
app, plus a `K declared` line so such a fingerprint can never equal a bytes one.

The gap is wider on al-runner than it was on bcdev: al-runner provisions Microsoft apps at the
project's version prefix resolved to the LATEST Microsoft build (`al-runner-backend.ts`, the
provisioning code), so two al-runner runs a week apart can run different Microsoft code under the
same declared version, and the digest does not move.

## Why it has no effect today

`lethal verify` is bcdev only (`cli.ts`, the verify backend check), so al-runner digests are recorded
but never compared.

## What would close it

Before verify supports al-runner: read each Microsoft dependency (and `System`, and Test Runner)
from the platform-apps directory al-runner actually provisioned for the run (R147 pins it for the
one-shot legs), hash those packages as the bcdev path does, and drop the `declared` mode. A test
must show that a newer provisioned build of a Microsoft app at the same declared version makes the
tests new.

## Since R654 (2026-10-23): the gap is v3's now

The .NET al-runner and its provisioning were deleted in R654 S3 (35f3c67f). The R654 plan asked whether the Rust
al-runner (`al-runner-v3`) fingerprints its `packagesDir` by bytes. It does not. `testAppDependencies` (in
`orchestrator.ts`) uses `{kind: "declared"}` for every backend that does not publish the test app, and v3 does not.
v3's `dependencyPackageDirs` hands over `alRunnerV3.packagesDir`, so the packages are found there, but each Microsoft
app is still fingerprinted by its declared version.

What changes: v3 does not provision. It reads the Microsoft apps from the `packagesDir` the config names. So the
digest only misses a change when someone replaces a Microsoft app in that folder with another build at the same
declared version. That is narrower than v2's "latest build from the CDN", but it is the same gap.

**To close (v3).** Before verify supports `al-runner-v3`: hash each Microsoft dependency (and `System`, and Test
Runner) from `packagesDir` as the bcdev path does, and drop the `declared` mode. A test must show that swapping a
Microsoft app in `packagesDir` for another build at the same declared version makes the tests new.
