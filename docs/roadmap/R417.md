**Found in the Task 6 review of R413 (kraken-move, 2026-10-03).** `QuarantineStore.read` answered
"no record" when the store path was a regular file: on Windows through `ENOENT` since the store was
written, and on Linux too after R413 mapped `ENOTDIR` the same way. Then `clear()` returned
"cleared" and the quarantine check in `cli.ts` (`read(key) !== null`) reported the tier clean, though
nothing could have been read: empty-vs-empty on a safety latch.

**Ruling (owner's coordinator, 2026-10-03).** A store path that EXISTS but is not a directory is a
broken configuration, refused on both platforms with a typed error naming the path. A MISSING store
directory still means no record.

**To close.** `read()` on `ENOENT`/`ENOTDIR` stats the store dir: missing is no record, present
and not a directory throws `QuarantineStoreNotADirectoryError` (extends `Error` directly). `clear()`
goes through `read()`, so it refuses too. R361's recycle-write test, which used a file at the
quarantine path to make the WRITE fail, injects a store whose `record()` throws instead
(`SessionConfig.quarantineStore`, a test seam). Tests in `packages/runner/tests/quarantine-store.test.ts`.

**Follow-up (merge review, 2026-10-03).** A store dir whose PARENT is a file still read as no record
on Windows, which reports `ENOENT` (not `ENOTDIR`) for a child of a file. `read()` now walks up to
the nearest existing ancestor: a directory there is a genuinely missing store, a non-directory is
refused with the typed error naming it. The parent-file test, `clear()` included, runs on both
platforms.
