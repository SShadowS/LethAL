**Filed 2026-11-05 from GitHub #47, coord task R-819.** Related: [[R268]], [[R586]].

**What broke.** A BC 29 dev endpoint serves System Application, Base Application and Business Foundation as Ready-to-Run
wrappers: a package with `readytorunappmanifest.json` and one inner `.app`, and no `NavxManifest.xml` on top.
`readAppIdentity` needs that manifest, so `assertBcVersionMatchesPackages` skipped each wrapper and refused with
`al-runner-v3-system-application-not-found`, a false refusal.

**A second refusal behind the first, found checking the other callers.** `packageFolderReader` skipped a wrapper too ("it
cannot be the dependency either"), and `openPackage` refused one. So past the first refusal, a v3 run would have stopped
with "the package of dependency ... could not be read", and a bcdev run's dependency digest would have refused a served
wrapper the same way. Neither was reported, because the first refusal came first.

**Fixed at one point.** The validated unwrap moved beside `readAppIdentity`: `unwrapSymbolPackage`, `symbolPackageIdentity`,
`symbolPackageId`.
- `assertBcVersionMatchesPackages`, `packageFolderReader` and `openPackage` all read through it. Only the exact shape is
  unwrapped, and the inner manifest must agree with `EmbeddedAppId`. Anything else still throws.
- The digest still hashes the file's own bytes: al-runner reads that file, so a different file is a different input.
- A broken wrapper in the version check now names itself, not "no readable System Application".

**Other `readAppIdentity` callers, read and left alone.** The publish and verify paths read LethAL's own target and test
apps, which are never wrappers. `dependency-report-source.ts` has its own wrapper check. `bc-symbol-cache.ts` reads only
`System`, which is not one of the three wrappers named in #47.

**Evidence and limits.** Tests use a synthetic wrapper of the shape #47 describes (`r819-issues.test.ts`): no BC 29 package
may be committed, and none was run here. The reporter's folder is the real proof, so the fix is unproven on a real BC 29
package until they, or a BC 29 server, confirm it. No BC 29 server is on hand.
