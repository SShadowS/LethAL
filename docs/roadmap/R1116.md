Filed by coord PR-135 (lethal-preproc, 2026-11-17). Upstream:
https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8267. Evidence: `/coord/handoff/PR-135/result.md` and `dup/`.
- **The defect (a wrong answer, not a refusal):**
  - On edge-4ebfe7913, `Rec.Insert()` called as a statement for a primary key that already exists raises nothing. The row
    is not inserted, and the first row is kept.
  - BC raises `The record in table ... already exists`.
  - The return-value form (`if Rec.Insert() then`) answers false correctly.
  - A clean two-object repro (`dup/`) shows it: `asserterror` finds no error, `Count()` stays 1, the first `Name` is kept.
- **The verdict risk:** a mutant whose only effect is to make code insert a key that already exists (a removed or negated
  "if not Get then Insert", a dropped key assignment) runs on in al-runner where BC stops with an error.
  - So a test that BC fails passes on v3, and the mutant is scored **survived** where BC kills it: a false survivor.
  - Not a false kill. A test that expects the error (an `asserterror` on a duplicate insert) fails on v3, which reads as a
    red baseline, not a kill.
- **How many survivors could be this** (`/coord/handoff/PR-135/count-insert.ts`): a static, per-procedure method. It
  counts SURVIVED mutants whose own procedure holds a bare `X.Insert();` / `X.Insert(true);` statement (not in an `if`,
  `exit` or assignment) at or after the mutant's line.
  - **DO (R-984 x2, the cumulative store):** 6,071 survivors.
    - 1,127 have such an Insert after them in their procedure; 884 of those are guard-changing operators.
    - **50 are a guard operator on an existence check** (`Get`/`IsEmpty`/`Find*` in the mutated text), the classic
      "if not Get then Insert".
  - **115 other al-runner stores** (a report and its source on disk): 14,269 survivors.
    - 1,143 have such an Insert after them; 863 of those are guard-changing operators.
    - **75 are on an existence check.**
  - **Read these as candidates, not as false survivors.** Most such mutants never make the key collide, so the figures are
    the population in which they can occur.
  - The method misses an Insert in a CALLED procedure, so the reach is wider than this static count.
  - The 50 + 75 existence-check mutants are the ones to re-check first, on BC or on an al-runner build with #8267 fixed.
- **Until #8267 is fixed:**
  - v3 survivors in this population are not trustworthy as survivors.
  - The bcdev backend (real BC) is unaffected.
- **Next, when #8267 lands:** re-score the existence-check candidates on the fixed build. Each one that turns killed was a
  false survivor.
