Found by coord task R-947 (2026-11-13), following R-945's measurement (`/coord/handoff/R-945/slow/`, `/coord/handoff/R-947/`). Related:
[[R954]], [[R515]], [[R934]], [[R940]].

**What happened.** Microsoft's Password module, al-runner edge-2bd87774f: `GenerateSecretPassword` loops `repeat ... until
IsPasswordStrong(...)`, so a mutant that makes `IsPasswordStrong` always false hangs every test that generates a password; al-runner
reports those correctly as timeout rows. But the same mutants' `TestVerifyStrongPasswordSequences` rows read: the kill, `fail` in 8 ms;
the UNMUTATED confirmation, `pass` in about 620 s (with a 600 s stop) or 181 s (with 180 s); the reproduction, `fail` in 17 ms. The long
one is the confirmation inside a batched kill-pair request that also held the hanging entries: when al-runner's row has no
`durationMs`, `verdictFromRunnerTest` stores the call's wall time as the test's duration. The verdict (killed) is right; the
duration is not the test's.

**Why it matters (principle 5: unknown is not a number).** Stored durations are read as test times: R-945's study had to exclude such
rows by guesswork (it first mistook these for real 181 s finishes, and nearly set a stop rule on them); R515's confirm-based budget
raise takes the largest duration a passing confirmation measured, so a batch wall inflates that test's budget; per-test sums and rate
or timing lines (R934, R940) count the wall once per row. In R-925's Regulatory store 718 rows share two such values; R-926's
Subcontracting store has 7,903 rows at 20-70 x their baselines.

**To build.** A row with no duration of its own stores none (unknown), with the call's wall in a separately named field if a reader
needs it; every reader of the duration says what it does with unknown (R515's raise, R934's sums, R940's estimate, the rate and timing
lines). Red both ways; pre-commit any moved figure.

**Build notes (R-947).** R515's raise was found UNCHANGED: `noteMeasured` runs only where the in-run stop is the budget (bcdev and
v3 one-shot, where a confirm is one test's own call), never on serve-entries, so the batched wall never inflated a budget and the
raise still reads the confirm's wall. What changed: a v3 row with no own time carries a `callId` (one per al-runner process or serve
request) and its call's wall is charged once per call in a mutant's summed time and in the R914 estimate; bcdev's grouped entries
now set `measuredDurationMs` from their own server-reported time; the store gains `test_results.own_duration_ms` (NULL = unknown;
it may hold a fractional value, since SQLite keeps what it is given in an INTEGER-affinity column).

**Fixed (240d2c1b; pre-commitment f957b418, amendment 5fb479b1, correction 38c9b6d4).** Red both ways
(`/coord/handoff/R-947/redchecks.md`, plus the one-id-per-serve-request test). The build review found the first grouping ("same wall
value = same call") charged bcdev grouped entries' distinct tests 0 and moved five snapshot values; replaced by the explicit `callId`,
and no snapshot moves. Gates on 240d2c1b: the full v3 gate (every leg), `itest:bcdev` and `itest:lend` on bc1: PASS, no figure moved.
A store written before the column (a copy of R-940's unfinished Password run) opened, gained `own_duration_ms` (its 559 old rows NULL,
the 110 new rows with own times) and resumed with 124 verdicts carried; every mutant decided in both has the same verdict. Not done:
older scripts that read `duration_ms` as a test's time (`r514-probe`, `r206-run-compare.py`) still do.
