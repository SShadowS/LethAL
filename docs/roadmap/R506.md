**Found by R-504's plan review** (`/coord/handoff/R-504/review-r1-opus-adversary.md`, M4). Same
class as [[R191]] and [[R504]], which fixed it for the lease client only.

Each of these arms an abort timer for the `fetch`, clears it in the `finally` around the `fetch`,
and then reads the body with no abort and no `bounded(...)` race. A 2xx whose body BC starts and
never finishes holds the caller with no LethAL timer behind it:

- `HarnessVerifier.fetchHarnessInfo` (`harness.ts`): the `HarnessInfo` read behind `verify()`,
  `lease()` and the reachability check.
- `HarnessVerifier.fetchApiRows` (`harness.ts`): the BC API list reads (the extension and
  dependency rows).
- `postOData` (`activation.ts`): the `MutationControl` activation call.
- `DeploymentVerifier.readRegisteredArtifact` (`deployment-verifier.ts`).

The last two also read the body as `res.json().catch(() => ({}))`. A body that is not JSON, or
that errors part-way, becomes a plausible empty object, which is this project's signature bug:
"nothing read" looks the same as "nothing there".

**`lethal force-reset-lease` is only partly bounded until this lands.** R504 bounds the
`ForceResetLease` call, but `performForceResetLease` runs `HarnessVerifier.verify()` first, and that
read can still stall on its body.

Proposed fix: the R504 shape at each site. Keep the abort armed until the body is parsed (clear the
timer in one `finally` around fetch and body read), race the whole read with `bounded` from
`bc-fetch.ts` at the same limit, and replace the `{}` default with a thrown, labelled error. Pin each
with a 200 whose body never completes; against today's code that test does not finish.

**Closed by R-506 (abc6919b).** Every BC body read in the runner now goes through the shared
`bc-fetch.ts` helpers (`withDeadline`, `readJsonBody`, `bounded` with an error factory). A timeout
or an unreadable body throws (the new `BcAnswerUnreadError`, or the site's own class), never an empty
value. Both `{}` defaults are gone. The dead `postOData` and `MutationControlClient` are deleted. A
stalled or unreadable HarnessInfo or API answer, or a timeout before the headers, no longer makes an
env-tool session republish the control app. Proof: the per-site tests in
`/coord/handoff/R-506/redchecks.md`, each red-checked.
