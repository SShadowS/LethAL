Found by the daily al-runner update (lethal-bugs, 2026-11-15; `/coord/handoff/R-815/daily-2026-11-15.out`). Related: [[R886]]
(LethAL hands al-runner the pinned build's sidecar), [[R998]] (a sidecar of another build), [[R1013]] (the regression set).

**What happened.** edge-5a58a0f16 passed every gate leg and became `current`. Its regression-set run reported one row
REGRESSED: `u7586-refusals` `Codeunit51137.UriSchemeThroughSystemApplication` (a System Application `Uri` call, which passed on
a184cfc79) was refused with `dotnet-unavailable: DotNet 'System.Uri' sidecar not built`. The script then built the sidecar
(`al-runner-v3-update.ts` builds it only after a pass, so a failed build cannot change the outcome). Re-run by hand on the same
binary once the sidecar existed beside it, the test passes, with and without `--dotnet-sidecar`: al-runner finds the sidecar next
to its binary.

**Why it matters.** The gate legs and the regression set measure a build in a state no LethAL run uses: LethAL passes the pinned
build's own sidecar on every call (R886). So:
- a build that moves .NET types into the sidecar reads as a regression in the set, though LethAL's runs are unaffected (this case);
- the other way, a defect that only shows WITH the sidecar (a wrong .NET answer) is never seen by the gate or the set.
Not a verdict moving away from BC: no LethAL run measured the sidecar-less state.

**To close.** Build the sidecar into the candidate's scratch folder before the gate legs and the regression set, and run both with
it, as LethAL's runs will. A failed sidecar build still does not fail the gate: those runs then go without it, and the note says
so. A unit test with a fake builder shows the set's al-runner calls receiving the sidecar, and the outcome unchanged when the
build fails.
