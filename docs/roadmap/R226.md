**Measured while qualifying the orchestrator's containers.** Running the full unit suite
immediately after a sequence of live gates gave:

```
3032 pass, 2 fail
✗ lethal doctor on an al-runner-only project (R146) > the al-runner check runs the REAL probe
    `run` runs, not a doctor-only opinion                                          [5001.00ms]
✗ lethal doctor CLI wiring — environment (direct container) > a wrong appId does not fail the
    environment check                                                              [5000.39ms]
✗ lethal doctor CLI wiring — environment (R34) > a Stopped reused environment ...   [5001.03ms]
```

The same commit, same machine, containers idle: **3034 pass, 0 fail**. The two doctor files run in
isolation: **49 pass, 0 fail**, in 78 seconds. The durations are the finding: every failure sits on
5000 ms to within about a millisecond, which is a budget expiring rather than a behaviour changing.

These tests are doing the right thing. `doctor`'s whole point is that it runs the REAL probe rather
than a doctor-only opinion, so spawning a real process is the test being honest. The problem is
only that a fixed wall-clock budget is a property of the machine, not of the code, and this repo's
own rule is to assert phase ordering with call counters on stateful fakes and never with
wall-clock timing.

## Why this is a correctness risk rather than a nuisance

It is one today and a real hazard the moment the autonomous orchestrator runs. That flow runs the
offline ladder and the live ladder on the same machine, and a red unit suite is a gate failure.
So a candidate would be blocked, or a container quarantined, because an unrelated live gate was
still finishing. The failure carries no signal that it was a timing artifact: the test name reads
like a genuine doctor regression.

It also degrades the loudest thing the suite has. A gate that fails sometimes for reasons unrelated
to the diff is a gate people learn to re-run, and re-running until green is how a real regression
eventually merges.

## The mechanism, measured a second time

The first measurement said "2 fail under load, 0 fail idle, 49/49 in isolation" and concluded the
cause was a live ladder running alongside. The second measurement, later the same day with two BC
containers merely UP and idle, says something worse:

- the two doctor files alone: **47 pass, 2 fail**, not 49/49;
- one of those same tests run alone with `-t`: **passes, in 3.98 s**.

So the budget is marginal by itself. A single probe consumes about four fifths of its five seconds
on a quiet machine, and running 49 tests concurrently is enough to tip it. A live ladder is not
required; having the agent containers running at all is.

That changes the operational conclusion. "Do not run `bun test` beside a live ladder" is necessary
and NOT sufficient, because the orchestrator's containers are up whenever it is working.

## What closing it would take

Two independent halves, and the first is worth doing regardless:

1. **The executor must not run `bun test` concurrently with a live ladder.** Cheap, and still
   worth doing. But the second measurement shows it is not sufficient: the budget is marginal on a
   quiet machine, so the tests can fail while nothing else is running.
2. **Give the probe budget a floor that is not wall-clock, or make it configurable and generous in
   CI.** The honest version is that these three assert "the real probe ran", not "the real probe
   ran within 5 s", so the budget is incidental to what is being proven and should be large enough
   that only a genuine hang trips it.

Until then, a doctor timeout in a full-suite run is not evidence of a doctor defect. Re-run the two
files in isolation before believing it, which is the check this row exists to make routine.
