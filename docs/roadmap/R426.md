**Filed by R384 (its plan's stated limit, orchestrator ruling R1, 2026-10-04).** `lethal verify`'s
reach filter sends a new test T to a survivor S only when T's own coverage reaches S's member (the
same `coverageFilter` rule a fresh `lethal run` uses to pick S's covering tests). Two kinds of kill
leave no trace in T's own coverage:

- **State left by an earlier test in the same call.** If T kills S only because another test in the
  same `RunMutantMany` call changed shared state first, T's coverage need not reach S, so the filter
  drops T from S's request and S stays `survived`.
- **Code run in another session.** A mutant reached through a background session, a job queue
  entry or a scheduled task runs outside T's session, so T's per-test coverage does not record it.

A fresh `lethal run` picks covering tests by the same rule and has the same blind spot, so filtered
verify still AGREES with a fresh run (`itest:agreement`); it does not reach the unfiltered verify's
stronger "every new test against every survivor" answer in these cases.

**Today:** documented in README and `docs/using-lethal-from-an-agent.md`, with the opt-out
`--no-reach-filter`, which restores the old every-survivor behaviour. Measured on Continia Document
Output at `5f2a71d`: no `StartSession` and no `TaskScheduler.CreateTask`; `Job Queue Entry` appears
in 6 app files and 3 test files, `SingleInstance` in 7 and 5 (R384's measurement, coord handoff
`R-384/measurement.md`).

**To close.** Either detect the risk per project (for example: a codeunit that starts a session or
schedules a task, or a `SingleInstance` codeunit the mutant's member reaches) and turn the filter
off with a named reason, or measure on a real suite that no such kill exists and close by ruling.
