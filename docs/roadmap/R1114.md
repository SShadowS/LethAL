Filed by coord PR-133 (lethal-preproc, 2026-11-17), from DO window x2's events
(`/coord/handoff/R-984/x2.run.events.ndjson`, seq 33892-33896).
- **What happened:**
  - On daemon request 129 (a prefetch of 77 entries), the kept refusal `RecordRef.Duplicate on a RecordRef that is not
    open` (keep entry `recordref-method-not-open`) was followed by `CreatePDF_WithValidData_ShouldCreatePDF`, which
    passed. Its baseline row is `fail`.
  - `serve-drift-after-kept-refusal` fired, the daemon was closed (`kept-refusal-drift`), and the request re-ran on a
    fresh daemon. The verdict was protected.
- **Why it matters:**
  - The drift check compares only rows that cannot differ under the mutant (a NONE entry, or tests before the first
    covering test). So this drift is not a mutant effect.
  - It is either state left by the kept refusal (or by an earlier request in that daemon), which would make the keep
    false; or a test whose answer varies; or a coverage gap.
  - The drift check does not see contamination in a covering test, so a false keep could move a verdict where the check
    is blind.
- **The events cannot settle it.** They do not record the fresh re-run's rows. The re-run raised no second drift.
- **Next:**
  - Re-run that request's codeunits in the same order, on a daemon kept after a `RecordRef.Duplicate` refusal and on a
    fresh daemon, and compare the row.
  - If the kept daemon gives `pass` and the fresh one gives `fail`, narrow `recordref-method-not-open` (Duplicate out)
    and re-census it.
  - If both give the same row, record the test as one whose answer varies.
- **Related:** [[R1092]], PR-133's pre-commitment `docs/superpowers/specs/2026-11-17-pr133-x2-restarts-precommitment.md`
  §5.

**Checked directly by coord PR-134 (lethal-preproc, 2026-11-17): the keep is clean; the drift was the mutant's own
effect.** Evidence: `/coord/handoff/PR-134/result.md`.
- **The method:**
  - A scratch copy of DO's app with LethAL's resource selector written by hand, and guards on the mutants in question.
  - One `al-runner serve` daemon per scenario, driven with DO's own tests (edge-4ebfe7913).
  - Nothing of it is committed.
- **The keep is clean.** After the `RecordRef.Duplicate` refusals of all three DO mutants that raise it (M17220, M10323,
  M10444), in a separate request or in the same one, the next `CreatePDF_WithValidData_ShouldCreatePDF` gives its baseline
  `fail`.
  - So does a replay of the whole daemon history before the drift (76 requests, 480 codeunit calls) with no mutant
    active.
- **The real cause:** M17235 (a void-method-call that removes `IsAppActiveOrAskToActivate`) makes that test PASS on a
  FRESH daemon.
  - The test fails at every baseline (on the activation Confirm), so it is in no mutant's plan. The drift check took it as
    "before the first covering test", meaning unreachable. But the mutant reaches it.
  - The drift was a false alarm. It cost one daemon restart (43.7 s), in the safe direction.
- **No x1/x2 verdict needs a re-check:** the keep did not contaminate the daemon.
- **The drift check's gap** (red-at-baseline tests treated as unreachable) is filed as [[R1115]].
