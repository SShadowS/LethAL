**Found by the code lane during R-318 Task 3 review (2026-09-30).** `AlRunnerBackend` caches
`this.coverageIndex ??= await buildAlRunnerCoverageIndex(this.activeDir())` in both `readCoverage`
and the `--server` suite path (`packages/runner/src/al-runner-backend.ts`, around lines 871 and
1094; introduced by R220, `db711deb` / `9425a2bd`), and `deploy()` never clears it.

**Why it matters.** A session has two or more batches whenever `--max-guards-per-batch` splits the
project (`planArtifacts`), and one backend instance (one per worker) deploys every batch.
`writeInstrumentedProject` instruments only the files that hold a mutant in THAT batch, so one
file's emitted line numbers differ between batches. Batch 2's al-runner coverage lines are then
mapped through batch 1's layout: hits credited to the wrong member or dropped, so covering-test
lists are wrong, which means false `no-coverage` or false `survived`. `compileCheck` (bisection)
also redeploys on the same instance.

**Why no gate saw it.** Every al-runner gate fixture runs as one batch.

**Repro** (by the code lane, fails at HEAD): a real `deploy()` on two batch directories with a
4-line shift, `stale-index.test.ts` in the code lane's scratch (`coverage-index-cache/`).

**Likely fix.** Reset `coverageIndex`, and any server-suite cache built from the deployed layout,
in `deploy()`. Check every other cache on the backend for the same shape.

**Closed by `e210b79f`.** Root cause confirmed with the code lane's repro through the
real `deploy()`: batch 2's covered line 9 came back as `Other`, which is where line 9 sits in batch
1's text. `deploy()` now calls one private `resetLayoutState()` first, which drops `coverageIndex`
AND `serverSuite` (the `--server` suite results, previously cleared only by `activate()`, so a run
after a deploy with no activate in between was answered from the previous batch). `compileCheck`
goes through `deploy()`. Audited and deliberately NOT reset: `deployedDir` (set by the deploy),
`coverageScratch`/`coverageSeq` (fresh file names, no content), `platformAppsDir` (session pin),
the transport's `lastBcBuild`/`firstMissingImplementation` and the daemon's process and stderr
(binary output, not layout). The resource selector is re-installed per deploy already. Tests:
`al-runner-backend.test.ts` (the repro through `deploy()` and through `compileCheck()`, plus the
suite cache across a deploy) and `al-runner-multibatch.test.ts` (`runSession` with
`maxGuardsPerBatch: 1`, every mutant's covering tests pinned in both batches; without the reset
batch 1's six `Target` mutants go `no-coverage` and `Other`'s two go `survived`). Red-checks in
`.superpowers/r349-redcheck.log`. The live `itest:alrunner` run is the controller's, per R345.
