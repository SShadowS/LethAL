**The R69 router's gate 1 is DEAD in the only configuration where a real TestPage suite survives — so the routed path could never have fired for the case it was built for.** Gate 1 (`selectRoutedTests`, `testpage-router.ts`) keys on the FENCED BASELINE's failure text: it routes a test only if `describeTestPageUnsupported` matches the baseline failure. But a suite containing a real TestPage test only completes baseline at all under `coverageMode: "procedure"` (R76), and on that path the TestPage test **PASSES baseline** — no failure message exists, so gate 1 never fires. **This was already OBSERVED and misread.** R76's measured run reported the 4 pageextension mutants as `error(unstable)` from the fenced VERDICT run refusing fast (140-181 ms, `CreateNavTestService`). That was recorded as "verdicts always run fenced" — true, but it buried the real finding: the refusal had MOVED from baseline to the mutant run, which is exactly where gate 1 cannot see it. The router was watching the wrong event. **Fix is a redesign of the routing TRIGGER, not of the transport:** key on `describeTestPageUnsupported` applied to the MUTANT RUN's refusal, not the baseline's. That is the actual design work standing between R69's built-but-unwired path and a scored TestPage mutant — and it is independent of R74/R75, which are separate discards.
