`defaultAlToolPaths` took the newest installed AL extension and joined a fixed layout onto it:

```ts
const bin = join(extensionsDir, al, "bin", layout.dir);   // layout.dir === "win32" on Windows
return { alcPath: join(bin, "alc.exe"), altoolPath: join(bin, "altool.exe") };
```

It never checked the result existed. That was fine while every VSIX had the same shape.

**Measured 2026-08-19, mid-session.** The AL extension published `18.0.2668733` as a
**per-platform** VSIX: the Windows binaries sit directly in `bin/`, and there is **no `bin/win32`
directory at all**. `18.0.2498801`, still installed alongside it, is the older multi-platform VSIX
with `bin/win32`, `bin/linux` and `bin/darwin` side by side. Discovery picked the newer one, built
`…/18.0.2668733/bin/win32/alc.exe`, and every live gate died:

```
could not run alc (C:\…\ms-dynamics-smb.al-18.0.2668733\bin\win32\alc.exe):
Executable not found in $PATH (ENOENT)
```

**Nothing about that message names the layout**, and it arrives AFTER generating, instrumenting and
publishing — the expensive part. It surfaced while running the R165 gate and was initially mistaken
for a fault in that change, which is exactly the cost of a diagnosis that points at the wrong thing.

## The fix

Walk the installed extensions **newest first** and return the first one that actually HAS the tools,
trying two layouts per extension:

1. `bin/<rid>/alc<suffix>` — correct on the older multi-platform VSIX, where the `bin/` root holds a
   different platform's binaries;
2. `bin/alc<suffix>` — the per-platform VSIX.

Order matters and is the point: preferring `bin/` would hand a Linux host a Windows PE on an older
VSIX, which is the regression R64 fixed. The suffix keeps the fallback honest the other way too — a
Windows-only VSIX has `bin/alc.exe` and no `bin/alc`, so a Linux probe finds nothing and moves on
rather than returning something it cannot execute.

Existence is now what selects, so a half-installed or wrong-platform extension is skipped instead of
producing a path nobody checked.

## Verification

Four new tests, each naming a real shape: the `bin/` layout resolves; the per-RID directory WINS
when both are present; a newer extension carrying no tools is SKIPPED in favour of an older one that
does; and a Windows-only VSIX is not offered to a Linux host. Red-checked — removing the `bin/`
fallback fails exactly the first.

Five existing tests had to lay down real binaries, because they asserted a path SHAPE against
directories that were empty. That they passed while the tool did not exist is the same gap in
miniature.

The same hardcoded path lived in `scripts/compile-fixtures.ts`, `scripts/r161-emit-proof.ts`,
`scripts/r159-aor-spike/compile-proof.ts` and two skills (`al-compile`, `control-app`); all now try
both. `bun run compile:fixtures` passes again on the new extension.

**Not covered:** `altool` is assumed to sit beside `alc` and is not probed separately. If a future
VSIX splits them, discovery returns an `altoolPath` that does not exist and the failure moves to
publish time. Left as-is deliberately — no VSIX has ever split them, and probing both would double
the IO on every startup for a case with no evidence behind it.
