**Filed 2026-11-27 by lethal-preproc, from PR-478's bc3 proof under LethAL Control 1.0.0.31.** Evidence:
`/coord/handoff/PR-478/prove/bc3/` (`bcdev.log` failed, `bcdev-rerun1.log` passed, `run.log`).

**What happened.**
- `itest:bcdev` on bc3 (17:41-17:42Z, box load 125-173, bc2's proof running beside it):
  - the per-mutant verdicts matched (killed 3, survived 17, no-coverage 6);
  - no mutant was refused as `session-reused`;
  - but `assertSessionLiveness` failed: `distinct session ids among grouped pass/fail rows must equal the group calls that
    answered (20 minus 0); got 8`.
- The same build passed the same gate on bc2 a minute later. A re-run on bc3 (17:44Z) passed every check.
- 20 sequential OData calls on bc3 just after got 20 distinct, rising ids (`prove/session-ids.ts`), so plain id recycling
  between calls was not seen.

**Why it matters.** The invariant guards R206's freshness predicate. Two readings fit the failed run:
- 20 grouped calls ran in only 8 sessions, so a session served more than one call, yet its test-run counter read fresh.
  That would be the guard failing open, a false "fresh" that can carry state between mutants;
- or the stored session ids are wrong (a store or report fault).

Either matters. 1.0.0.31 does not write the counter outside the gated client path (source pins), and bc2 and the re-run
pass, so it is not attributed to 1.0.0.31. That is a reading, not a measurement.

**Rule (orchestrator ruling, 2026-11-27): never delete a store from a failed gate run.** A failed gate keeps its
scratch store and prints where it is. Today `itest:bcdev` (and the other itests) delete theirs in `finally`, which lost
this failure's rows. Making every gate keep a failed run's store is part of this item's fix.

**The measurement the ruling sets:**
1. Three `itest:bcdev` runs on bc3 under 1.0.0.31, each store kept, beside another proof (similar load).
2. On any failure, read the stored rows (repeated ids, or a misread), then the same loop under 1.0.0.30.
3. If 1.0.0.30 also fails, this item is pre-existing and does not block 1.0.0.31. If only 1.0.0.31 fails, it blocks PR-478.
4. If all pass, PR-478 submits with the failed log and the passing runs, and this item stays a priority bug.

**Next.**
- Keep a failing run's store: the itest's scratch store is deleted at the end, so the 20 calls' rows are lost.
- Per call, record the session id, the test-run counter, the call's start and end, and the worker.
- Try to reproduce under the same load (two proofs at once).
