**Filed 2026-11-27 by lethal-preproc, from PR-478's bc2 and bc3 proofs under LethAL Control 1.0.0.31.** Evidence:
`/coord/handoff/PR-478/prove/bc2/` and `prove/bc3/` (`run.log`, `bcdev.log`, `bcdev-rerun1.log`, `tables.log`); the
readers `/coord/handoff/PR-478/r1241-runs.ts` and `r1241-rows.ts`.

**What happened.** Both proofs ran at once in ONE worktree (`/work/lethal-wt/pr-478`), so both servers' gates wrote to
the same fixture stores (`fixtures/sandbox-app/lethal.sqlite`, `fixtures/sandbox-data/lethal.sqlite`).
- **bc3, `itest:bcdev`, 17:41Z:** `assertSessionLiveness` failed with `... (20 minus 0); got 8`. Verdicts matched, and no
  `session-reused` refusal fired. A re-run passed.
- **bc2, `itest:tables`, 18:14Z:** the same invariant failed with `... (459 minus 0); got 322`. Verdicts matched.

**The cause, measured from the stores** (which persist: they are the project's own store, not the deleted scratch dir).
- **sandbox-app store:**
  - run 2 (bc3's failed run, 17:41:43-17:42:20) has 20 grouped rows, **20 distinct ids**, 20 mutants;
  - run 3 (bc2's `itest:bcdev`) started at 17:41:53 in the same store;
  - no session id appears in two runs.
- **sandbox-data store:**
  - run 1 (bc2's failed tables run) has **459 distinct ids**, exactly its 459 grouped calls;
  - run 2 (bc3's tables run) started at 17:56:03 and was still running when bc2's check read the store.
- **The mechanism:** each itest takes its run id as `SELECT MAX(id) FROM runs`. That is `latestRunId` in
  `itest/kill-reproduction.ts` (used by bcdev, chunked and hang); tables, lend and test-app-publish inline the same query.
  - So the failing check read the OTHER server's run, part-written at that moment (8 of its 20, 322 of its 408 grouped
    rows).
  - **The guard did not fail open, no session id repeated, and 1.0.0.31 is not involved.**
- **Controls:**
  - three `itest:bcdev` runs on bc2 from a separate worktree (its own store) at load 173-253 all passed;
  - 20 sequential OData calls on bc3 got 20 distinct, rising ids.

**Why it matters beyond these two failures.** The same wrong run id feeds `killReproductionFailures` (R582) and the
liveness check. A gate whose run overlapped another server's in one store can therefore pass for the wrong reason: its
checks read another run's rows. A run checked while it was the newest read its own rows, and its result stands. The
overlaps are named per gate from `run.log` times.

**Rule (orchestrator ruling, 2026-11-27): never delete a store from a failed gate run.** The stores that settled this were
the persistent project stores. The itests' scratch dirs, which they delete in `finally`, held no results.

**The fix (to build):**
- each itest takes its own run's id from the session, never `MAX(id)`. The report or the session result can carry it, or
  the itest records `MAX(id)` before `runSession` and requires exactly one new run after it;
- a gate refuses to start while another live process holds the same fixture store, naming the other process;
- red-checked by two concurrent runs in one store.

**Operating rule until then:** concurrent proofs on different servers each run in their OWN worktree.
