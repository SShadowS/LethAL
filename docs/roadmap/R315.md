**Found by the R-303 plan's Task 4** (`.superpowers/sdd/2026-09-28-R-303-latch-placement-split-var/`,
session scratch, archived once the branch lands), the proof step for [[R303]] and [[R312]]. Every
other proof in that task passed clean on real corpora: fixtures byte-identical, DC/Cloud, System
Application and BusinessFoundation instrument with only the expected file changes (the latch
declaration moving, mechanically verified), the `reach-latch-refused` count stays 0 for those three,
and `r303-oracle.ts` finds 0 BAD after where it found 40 (DC/Cloud) and 1 (System Application)
before. What did not happen is an offline `alc` compile of DC/Cloud's own emitted target: the one
corpus in this plan large and dependency-heavy enough that its compile was never attempted before,
so R303 and R312 have never been proven to compile at corpus scale, only on hand-written repros
(Task 2) and via the text oracle (Task 0, 4).

**Why.** DC/Cloud (`U:/Git/DC/Cloud`) declares 7 Continia Software dependencies, all needing version
27.x: Continia System Application >=27.1.0.0, Continia Online Connector >=27.0.0.0, Continia
Business Foundation >=27.1.0.0, Continia Approvals >=27.0.0.0, Continia Connector App >=27.1.0.0,
Continia Core >=27.1.0.0, Continia Delivery Network >=27.1.0.0 (plus Microsoft platform/application
symbols at 26.0.0.0, matching `runtime 15.0`).

A search of every `.alpackages` folder on this machine (`find U:/Git -iname "Continia*.app"`, then
widened to the whole Continia dependency list by name) found:

An unbounded search (`find U:/Git -iname "Continia*_27.1*.app"`) found zero matches anywhere on the
machine. The Microsoft platform/application 26.0.0.0 symbol set alone IS available complete
(`U:/Git/Project-X/.alpackages`: Application, Base Application, Business Foundation, System
Application, System), so the gap is entirely on the Continia side.

Four of seven Continia dependencies cannot be staged at a compatible version: three are strictly
below the declared minimum (System Application, Business Foundation, Connector App, all stuck at
27.0.0.0 against a 27.1.0.0 requirement), and one has no 27.x build anywhere, only a build two major
versions ahead (Online Connector). Staging a partial or version-mismatched set risks hundreds of
unrelated `AL0xxx` errors from API drift between major versions, which would hide the one error this
proof exists to look for (`AL0631`) exactly as a missing-symbol set would (the same risk the plan's
Step 5.2 names for missing symbols). Following the plan's rule, no partial set was compiled.

**What this means.** R303 and R312 are proven correct on hand-written repros (every named shape,
every symbol subset, `alc`-verified, Task 2) and on the text oracle applied to real corpus emission
(Task 4: 0 BAD after the fix across DC/Cloud, System Application and BusinessFoundation; before the
fix the oracle found BAD lines only in DC/Cloud, 40, and System Application, 1, with BusinessFoundation
already at 0). They are not proven by an actual `alc` compile of a real corpus's emitted target. The
text oracle checks AL syntax shape, not full semantic compilation against real symbols.

**What would close it.** Stage all 7 Continia dependencies at DC/Cloud's declared minimum versions
(or a provably compatible higher version within the same major, unlike the Online Connector gap
above) plus the matching Microsoft platform/application 26.0.0.0 symbols. Then instrument DC/Cloud
through the real pipeline (`generateMutationSet` plus `writeInstrumentedProject`, Control dependency
staged), offline `alc` compile the emitted target against those staged symbols, and compile a
de-preprocessed negative control of the same source for comparison: the same method Task 0 and
Task 4 used on the hand-written repros and on dc/sysapp/bcf. Re-run whenever a compatible Continia
27.1.x symbol set becomes reachable on this machine, or against a different real corpus whose
dependencies fully resolve.
