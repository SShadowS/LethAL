**`resolveIdentifierType` answers from the WRONG OBJECT when two objects declare a same-named procedure, and R82 made that reachable.** `packages/engine/src/semantic/types.ts`'s `findEnclosingProcedure(node, obj.node)` returns the enclosing `procedure`'s name before the walk can ever reach `obj.node`, so the `current !== objectNode` guard gates nothing: `resolveIdentifierType` iterates `symbols.objects` in PARSE ORDER, answers from the first object declaring a procedure of that name, and — worse — `return null`s without trying the remaining objects when that object does not declare the identifier. R84 fixed `extractType`, the other half of the same row, and left this; the R84 row itself names it ("the census resolves it by walking out from the identifier, which ALSO avoids `resolveIdentifierType`'s object-iteration scoping"). **Measured, not argued.** A two-codeunit counterexample: `Zzz Scope Victim.RunLink` declares `Record "Data Main"` + `Record "Data Related"` and calls `Link(MainRow, RelatedRow)`; `Aaa Scope Decoy` declares its own `RunLink` with BOTH locals as `Record "Data Main"`. Victim alone: **0 specs, correctly refused.** Decoy parsed first: **`swap-call-arguments` CLAIMS the site** and emits `Link(RelatedRow, MainRow)`, which `alc` 18.0 rejects — `error AL0133: Argument 1: cannot convert from 'Record "Data Related"' to 'Record "Data Main"'` (and the mirror for argument 2). That is the exact failure R84 exists to prevent, arriving as an `AlcCompileError` on a whole project, after the expensive part. **Calibration on `do-rel2/Cloud`** (244 objects): 1,793 distinct procedure names, **184 (10.3%) declared by more than one object**; of 390 claimed sites, **27 (6.9%) are typed by an object other than the one declaring the enclosing procedure** — 0 of them wrongly TODAY — and **73 of 463 candidate sites (15.8%) are LOST** to the same defect, which is the safe direction. So: live mechanism, common precondition, zero wrong instances on the one project censused, and the direction is asymmetric only by luck of naming. **Fix:** key the scope from the identifier's OWN enclosing object (`objectScopeKeyOfNode` already exists for this), or at minimum `continue` instead of `return null` so a wrong first match cannot both shadow and terminate. Not R82's to fix — R82 is what made it reachable, being `ctx.types`'s first consumer. Found by an adversarial review of the landed work; counterexample and `alc` rejection re-measured independently.

**CLOSED 2026-08-07.** The fix is the first of the two the row proposed — key the scope from the
identifier's own enclosing object — rather than the `continue`-instead-of-`return null` fallback,
because keying correctly makes the iteration unnecessary rather than merely safer. A node has
exactly one enclosing declaration, so there is nothing to iterate and no order to depend on.
Extensions are keyed on the same footing via `extensionScopeKey`, since `indexMembers` files their
members there and answering `null` for them would have traded wrong answers for missing ones.

**Measured on the real corpus with the operator's own `targets` predicate, and SET-DIFFED rather
than counted** — a count that merely went up would not prove nothing was dropped:

| | sites claimed |
| --- | --- |
| before | 390 |
| after | **437** |
| lost | **0** |
| gained | **47** |

The `before` figure of 390 reproduces exactly what R85 recorded independently, which is what makes
the instrument trustworthy here. This row predicted 73 lost of 463 candidates, and 463 − 73 = 390
confirms the same arithmetic; **47 of those 73 come back**, so 26 remain lost to something other
than this defect. Whoever picks that up should not assume R87 explains them.

**Two honest limits:**

- **The 47 recovered sites are not known to compile.** The claim is now correct by construction —
  both arguments have equal declared types in the identifier's own scope — but no `alc` run covers
  them. R85's live instrument would exercise this if it ever runs on a real project.
- **The census cannot see any of this.** `scripts/census-swap-call-arguments.ts` resolves by walking
  out from the identifier and so never touched `resolveIdentifierType`; its numbers were correct
  before and after, which is exactly why the defect survived being censused twice.

A red-check found the globals fall-through untested after the first two tests passed — the third
time in this session that testing a helper in isolation proved nothing about the path that matters.
Four tests now pin it: two for scoping, one for the fall-through, one for local-shadows-global.
