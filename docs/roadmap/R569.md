**Filed 2026-10-10 by coord task R-521** (measured in `/coord/handoff/R-521/measure.md`, "R520: the second hop").
A real hang that is NOT refused. This is the narrow rule left after [[R520]] closed by ruling.

**What.** [[R500]] refuses a procedure in another project object that open report-item code calls, plus its
same-object closure. It does not follow that callee's own call into a THIRD object. In BaseApp, the report
`Export Item Budget to Excel` repeats until its NextLine procedure (and, in a second loop, NextColumn) returns 0.
NextLine calls `Item Budget Management`.NextRecord (hop 1, refused). For a Period dimension, NextRecord returns the
step count of `PeriodPageManagement`.NextDate over the virtual `Date` table (hop 2). Master deploys 28 mutants in
NextDate. One of them, a `remove-assignment` of the step the `Date` table's Next returns, keeps the step at 1 for
ever, so the report never ends.

**The rule.** Follow a second object hop only from a one-hop callee whose RETURN VALUE, or a `var` argument, feeds a
loop exit or an exit guard in open-item code, and only into the procedures that value comes from. Do not follow
every call of the one-hop callee: that is [[R520]]'s general hop, closed by ruling at 21,025 deployed.

**Price.** A name proxy (second hop only into cursor-shaped members: a name containing `next`, starting with
`find`, or `read`/`eos`/an iterator) prices it at 39 calls, 45 procedures, **564 deployed (0.025% of BC.History)**:
BaseApp 35 procedures / 329, Quality Management 10 / 235. The exit-fed rule should cost at or below that. DC, DO,
CDO and the fixtures have no open report-item code, so 0 there.

**To close.** A plan (a new rule, not a fix), then build it, measure the identity effect per project, and confirm
the `Export Item Budget to Excel` NextDate mutants are refused.

**Built** (coord task R-569, plan `/coord/reviews/R-569-plan/plan.r1.md` as amended by `plan.r2.md`;
`exitFedHop2` in `loop-hazard.ts`, tests in `r569-exit-fed-hop2.test.ts`). The rule, in plain words:
- Start from every exit of open-item code: the condition of each `while`/`repeat` loop, and the guard of each
  `CurrReport.Break`/`Quit` (and the XMLport twins).
- Find what feeds that exit in the same procedure or trigger: the calls in the exit itself, and the calls on the
  right side of assignments whose value flows by name into it (R532's rule, with R568's boundary: through another
  object's function, only its receiver feeds, not its arguments).
- Follow a call through the value it RETURNS: its `exit(...)` values, its named return variable, and the guards of
  its `exit`s. A procedure of the same object stays on the same hop. A procedure of another project object is the
  hop-1 callee (already refused by [[R500]]). From the hop-1 callee and its same-object procedures, a call into a
  THIRD object whose value feeds the return is the hop-2 target. It is refused exactly like a hop-1 callee: the
  whole procedure, its same-object procedures, and the event subscribers [[R500]]'s pass already follows.
- Inside a procedure reached through its return value, a call that writes a fed name through a `var` parameter is
  followed too (`Helper.Calc(Result); exit(Result)`), because it feeds the returned value. This holds in the
  report's own helpers too: in `GetNext(): Boolean begin Mgt.Advance(Found); exit(Found) end;`, `Mgt.Advance` is
  the hop-1 callee and its calls into a third object are hop 2.
- In the exit's own trigger or procedure, and in report procedures it reaches only through `var` arguments, a
  `var` call into a procedure of the same report is followed as before. A `var` call into ANOTHER object's
  procedure is not (see Residuals).
- No hop 3. A test-only switch (`r569Seam`) gives master's behaviour; `r569HopTargets(ctx)` lists every hop-2
  target with the report, the hop-1 callee and how it feeds (`exit` or `ret-var`), for measurement scripts.

Price: `<cost: re-measured by lethal-code>`. No scheme change (`IDENTITY_SCHEME` stays 39).

**Residuals** (stated limits, not built):
- **The entry-var path.** A hop-1 callee ENTERED through a `var` argument passed from the exit's own trigger or
  procedure (or a report procedure it reaches by `var`) is not followed. One passed from a report procedure
  reached through its return value is followed.
  The prototype measured it at 906 deployed, all in `Fixed Asset - Projected Value` (`Calculate Normal
  Depreciation`.Calculate and `Calculate Custom 1 Depr.`.Calculate with their closures). In each sample read, the
  loop had a second exit that makes progress on its own (`UntilDate >= EndingDate`). The sample read 7 such
  targets and found 0 hangs. **Re-open when** a loop is found whose ONLY exit is fed through a `var` argument
  passed into another object's procedure from the exit's own trigger or procedure (or a report procedure it
  reaches by `var`).
- **Also not followed:** a `var` write made by an event SUBSCRIBER (the IsHandled/Result pattern); events raised on
  the way; a global written in another trigger (feeds are read in the exit's own scope only, as in [[R531]]); hop 3.

**Named over-refusal.** An `OnPreDataItem` Break can only skip a finite item, never keep one running, but the rule
counts its guard as an exit. In BaseApp this refuses `Assemble-to-Order Link`.AsmExistsForJobPlanningLine (12
mutants), reached from the `Assembly Header` item's `OnPreDataItem` Break in `Whse.-Source - Create Document`
through `Job Planning Line`.AsmToOrderExists. Kept by ruling: it is small, and a refusal errs safe.
