**This row exists because I told the maintainer something false.** Asked whether al-runner iterates
mutants the way bcdev does, I answered that it cannot: that bcdev compiles once and flips the active
mutant at runtime, while al-runner must bake the mutant into the AL and recompile, because it has no
live server to hold state. The first half is a correct description of what LethAL does TODAY. The
"because" was wrong, and it was wrong in the direction that makes this backend look inherently
unusable at scale.

The maintainer pushed back and asked for the al-runner source to be read rather than reasoned about.
It was, by a model from another family (gpt-6-astra, 41 files), and the two load-bearing claims were
then verified here directly.

## The mechanism

A **source-backed resource** is read from disk on EVERY AL read, and resource contents are absent
from the compile cache key. So the host can rewrite a text file, and the already-compiled AL sees
the new value with no recompilation.

Verified in the al-runner source, not taken on trust:

- `AlRunner/Patches/NavAppResourcePatches.cs`: `AppResourceStore.TryRead` does
  `File.ReadAllBytes(candidateFull)` per call for a source-backed resource. Only the resource FOLDER
  LIST is memoised, never the bytes. Its own comment: "The on-disk file IS what the AL compiler
  would have packaged." (A PACKAGE-backed resource is memoised in `_packageResources`, so this
  applies to source bundles only.)
- `AlRunner/ProgramSupport/Dependencies.cs` : the output-cache key enumerates `"*.al"`, hashes each,
  and adds a manifest fragment and the dependency list. Resource file contents never enter it.

## Measured, not inferred

A four-file fixture: an app declaring `"resourceFolders": ["LethALResources"]`, a `SingleInstance`
selector whose `Active()` reads `NavApp.GetResourceAsText('active-mutant.txt', TextEncoding::UTF8)`,
a codeunit guarded on two mutant ids, and one test that discriminates. Every `.al` byte-identical
across all three requests on ONE warm server; only the text file changed:

| resource | outcome | `cached` | wall |
| --- | --- | --- | ---: |
| `M0001` | pass | false | 8.8 s |
| `M0002` | **fail** | **true** | **0.1 s** |
| `M0001` | **pass** | **true** | **0.1 s** |

The verdict follows the file, al-runner reports a cache HIT, and the second and third mutants cost
0.1 s each instead of a compile.

## What this is worth

Today every mutant rewrites `MutationSelector.Codeunit.al` with `emitStaticSelector`, so `Active()`
is a compile-time constant and al-runner recompiles. That is 12.5 s cold and 0.4 s warm-incremental
on a two-file fixture, and **65 s per invocation on Continia Document Output's 553 files**. Under
this mechanism the compile is paid ONCE and each further mutant costs a test run.

It also removes the reason [[R220]] gives for `--server` being a trade rather than a win. The
argument there was "T tests warm against k compiles cold", true while every mutant recompiles. With
a runtime selector the comparison becomes T tests against k tests, and the whole-suite-per-mutant
cost of the missing per-test filter becomes the dominant term instead of the compile.

## What was ruled OUT, so nobody re-investigates it

The first hypothesis, the maintainer's and mine, was al-runner's in-memory database: seed a row,
have `Active()` read it. It does have an in-memory store (BC's own `TempTableDataProvider`), but
**state does not survive a request**. `RunAllBundlesForServer` calls
`BcRuntime.ResetForNewBundleReload()` unconditionally per request, whose own comment says the reload
"starts with empty in-memory tables" (`AlRunner/Program.cs`). `testIsolation: "disabled"` does not
help: it removes the per-test restore INSIDE a run, not the per-request reset. So the DB is a real
in-memory database and the wrong channel.

## Built, and what the gate now asserts

Landed as `AlRunnerConfig.selectorMode: "static" | "resource"`, defaulting to `"static"` so nothing
changes for a caller who does not ask. `deploy()` does the setup ONCE (declare the resource folder
in the deployed bundle's own `app.json`, write `emitResourceSelector`'s AL, seed the file with the
baseline value) and `activate()` then writes ONLY the text file.

The `app.json` edit is made in the backend rather than in `writeInstrumentedProject`, deliberately:
the resource channel is an al-runner fact, `active/` is this backend's private copy, and no other
backend inherits a manifest change it has no use for.

`itest:alrunner` gains a FOURTH leg. Its per-mutant verdicts must equal the baked-in selector's,
and that comparison is the point rather than the counts: the resource is read at RUNTIME, so a
selector that failed to re-read, or a file written after the request started, would score a mutant
against the PREVIOUS mutant's value and still produce a plausible-looking table. All 19 verdicts
match; `itest:bcdev` re-run and unchanged.

Wall clock on the two-file gate fixture, same 19 mutants:

| transport | wall |
| --- | ---: |
| one-shot, baked-in selector | 137.1 s |
| `--server`, baked-in selector | 30.7 s |
| `--server` + resource selector | **20.0 s** |

The fixture understates it, and that is worth saying plainly: two files make a compile cheap, so
most of what remains is test execution. The mode exists for the case where a compile is 65 s.

## MEASURED AT SCALE, and it corrects the headline number

The 0.1 s figure above is a four-file toy and does NOT survive contact with a real app. Measured on
a 553-file application (a scratch copy of Continia Document Output), five mutants in one added
codeunit, `--only` that file, both legs through `--server`:

| selector | total | per mutant | marginal, minus the one 66 s cold compile |
| --- | ---: | ---: | ---: |
| static, recompile per mutant | 346.4 s | 69.3 s | 69.3 s |
| **resource** | **124.7 s** | **24.9 s** | **~11.7 s** |

All five verdicts identical between the two legs.

So the win is real and large, and it is **~6x on the MARGINAL cost**, not the ~700x the toy implied.
Two honest qualifications:

1. **The compile is removed; the per-request reload is not.** 11.7 s per mutant is not "run two
   tests"; it is the cost of al-runner resetting and reloading a 553-file bundle's runtime state per
   request even on a cache hit. This confirms a caveat raised in the source review and not believed
   until measured: the same-directory server path "still reloads the cached DLL and rebuilds runtime
   state; it does not retain one unchanged live database or necessarily one `Assembly` instance".
2. **The ratio improves with mutant count**, because the 66 s compile is now paid ONCE rather than
   per mutant. Five mutants is the worst case for showing it off: at 100 mutants the same figures
   project to roughly 6,900 s against 1,240 s.

### Two things the rig itself proved

Building it required two workarounds, and both are upstream issues this repository already filed,
now confirmed on a real application rather than a minimal repro:

- **#3712** (`Split(a, b)`): three call sites in one file, patched in the scratch copy purely to get
  a compile. Without it the app does not build at all.
- **#3714** (a `src/` directory makes sibling directories invisible): the app declares its three
  `controladdin` objects in `ControlAddin/`, a sibling of `src/`, and al-runner skipped them,
  producing **892 errors of the form `ControlAddIn 'CDO.Editor' is missing`**. Moving the three
  `.al` declarations under `src/` fixed all 892; the resource trees stayed where they were, because
  a `controladdin`'s resource paths are project-root-relative. That is the strongest evidence yet
  for #3714, and it also confirms [[R219]]'s reading of why those paths do not need rebasing.

## What is NOT yet proven

- Interaction with LethAL's real instrumentation, where `Active()` is called at every mutated site.
  The probe used `SingleInstance` with a lazy load, which is what makes the read once-per-reset
  rather than once-per-guard, and that needs checking against the isolation resets on a real suite.
- Whether `GetResourceAsText` is available on every BC runtime version LethAL targets.
- The baseline case, which needs a reserved id matching no mutant.

## Cost of the change, roughly

`emitStaticSelector` gains a resource-reading variant, `AlRunnerBackend.activate()` writes a text
file instead of rewriting AL, and the instrumented project gains a `resourceFolders` entry and a
one-line resource file. The `itest:alrunner` gate already runs a `--server` leg asserting per-mutant
verdicts identical to the one-shot transport, so it is exactly the instrument this change needs.

`emitMutationSelector` and `emitStaticSelector` must keep exposing an identical procedure set; a
third emitter joins that rule.
