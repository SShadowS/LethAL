**`bun scripts/redact-campaign-report.ts <report.json> --check` does not check. It redacts.** The
flag is read as `args[0] === "--check"` only, so when it follows the path the script takes the WRITE
branch, rewrites `<report.json>` in place, and then dies with `ENOENT: no such file or directory,
open '--check'` after printing a reassuring `0 field(s) redacted`.

**Reproduced, not reasoned.** Hit by accident in this session against
`docs/campaign/2026-08-03-do/rung2.report.json`. No damage, because that file was already fully
redacted so the rewrite was a no-op and the tree stayed clean. On an UNREDACTED report the same
invocation destroys the thing the user was trying to inspect, and the exit code and the ENOENT
suggest the run failed rather than that it succeeded at the wrong job.

**Why it matters more than an argument-order nit.** This is the script that guards a PUBLIC repo
against publishing customer AL, and `--check` is the half CI depends on. A check flag that silently
becomes a write flag is the same class of defect as an assertion that cannot fail: it reports
success for work it did not do. The usage string in the script's own error message reads
`[--check] <report.json> [...]`, which is correct but only enforced positionally.

**The shape of the fix.** Accept `--check` anywhere in argv, and refuse an unrecognised argument
that starts with `-` rather than treating it as a path. Both are the same one-line-each change to
the argument scan. A test that runs the flag in BOTH positions against a fixture and asserts the
file is byte-identical afterwards is what stops it regressing.

**Found alongside** [[R184]], which is the larger gap in the same script: it does not know the
mutation-elements export format exists, so it cannot refuse a second source-bearing shape.
