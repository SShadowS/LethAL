**Filed 2026-10-22 by lethal-bugs during R-599** (the r1 plan review's M6, `/coord/handoff/R-599/review-plan-opus.md`).

**What.** `residentPackage` in `scripts/bc-linux-setup.ts` returns `null` ("the server holds none") for ANY non-2xx
answer from the dev endpoint's `dev/packages`, apart from 401 and 403. R599 moved the fixture decisions onto the
strict read (`strictResidentPackage` and `packageStatus` in `scripts/bc-app-content.ts`: only a 404 is absent, any
other failure stops the run), but three readers still use the lenient one:
- `downloadSymbols` (setup's dependent compiles, `bc-republish.ts`'s compiles and its `alpackages` mode): a 500 for a
  Microsoft package reads as "the server holds no Microsoft X", which fails by name, so this one only misnames the
  cause;
- the Continia step's `residentVersion` (`decideContinia`, through `realContiniaOps`): a 500 for a Continia app
  reads as absent, so the step PUBLISHES it, where it should stop;
- `bc-republish.ts`'s compile reading a LethAL dependency outside the named apps.

The shared symbol cache's download uses it too; a failure there also reads as "holds no Microsoft System" and stops
the fill by name.

**Who hits it.** A setup or republish run while the server answers 5xx for a package (a restart, a timeout page).
The Continia case is the one that acts on a wrong reading.

**To close.** Move these readers onto `strictResidentPackage`, keeping the 404-only rule, with a test per reader
that a 500 stops the run. R599 left them as they were so its own diff stays on the fixture decision.

Evidence: `residentPackage`, `downloadSymbols`, `realContiniaOps` in `scripts/bc-linux-setup.ts`;
`packageStatus` in `scripts/bc-app-content.ts`.
