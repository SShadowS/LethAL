**Filed 2026-10-22 by lethal-bugs during R-624** (the plan review's M6, `/coord/handoff/R-624/review-plan-opus.md`;
the orchestrator asked for it as its own item because it is PRODUCT code, unlike R624's setup scripts).

**What.** `BcDevMcpBackend.fetchPublishedAppPackage` in `packages/runner/src/bcdev-backend.ts` returns `null` for
any non-2xx answer from `dev/packages` (`if (!res.ok) return null`) and for every thrown error except
`UnfilteredExtensionsQueryError`. Its doc says so on purpose: R139's check 2 is proactive and must not stop a run
that check 1 would complete. So a 500, a 404 ("not resident") and a timeout are one value.

**Can a run act on it? No: every consumer fails closed on `null`.** Read 2026-10-22 on master:
- R139 check 2 (`orchestrator.ts`, the published-package check): `null` becomes `{ kind: "failed" }`, reported to
  the operator; check 1 stays the authority.
- the test-app hash guard (R-372/R-389, `orchestrator.ts`): a failed read gives no hash, which is treated as drift
  and throws `TestAppDriftedError` before the batch records anything.
- `publishTestApp` (`test-app-publish.ts`): `null` before the fence refuses (`resident-unreadable`); after the
  publish it is `unavailable`, which is never `accepted`.
- the dependency fingerprint (`digest-inputs.ts`, `publishedPackageReader` and the published test app read, plus
  `verify.ts`'s use of it) and the bytes-mode dependency check in `orchestrator.ts`: `null` throws
  `DependencyUnreadableError`.

None reads `null` as "absent, so proceed differently", so no verdict, publish or score can move on a 5xx. The cost
is diagnosis: a 5xx is reported as "check the dev-endpoint read credentials, or that the app has ever been
published" (`resident-unreadable`) or as "could not be read", sending the operator after the wrong cause.

**Ranking.** Below R624, which ACTS on a wrong reading (setup publishes a Continia app on a 5xx). This one misnames.

**To close.** Keep the never-throws contract, but carry the cause: return the HTTP status (or "timeout",
"refused") alongside the `null`, for example a `{ unread: <cause> }` value, and put it into each consumer's message.
A test per consumer that a 500 names `HTTP 500` and a 404 names "not resident". Or rule that the conflation is
acceptable and close by ruling.

Evidence: `fetchPublishedAppPackage` in `packages/runner/src/bcdev-backend.ts`; `publishTestApp` in
`packages/runner/src/test-app-publish.ts`; `publishedPackageReader` in `packages/runner/src/digest-inputs.ts`.

## Done

Closed by ee9f0a3b (plan `docs/superpowers/plans/2026-10-22-r630-r636-read-cause-and-link-cap.md`, r2).
- `fetchPublishedAppPackage` returns `{ unread: <cause> }` (`PackageUnread` in `backend.ts`) in place of `null`.
  The text comes from `unreadOfStatus` and `unreadOfError` in `bcdev-backend.ts`: the real HTTP status (401/403
  the login, 5xx a server error), a 404 worded "no such app on the server, or the dev-endpoint path is wrong"
  (not proven to mean "not resident"), a timeout (also an AbortError or TimeoutError), a refused connection, DNS,
  and a refused redirect. The login is blanked out of any message. `UnfilteredExtensionsQueryError` still throws.
- All 7 consumers keep their outcome and name the cause: R139 check 2 (`fetchPublishedTestApp`,
  `reportPublishedTestApp`), the test-app hash guard (`testAppHashFor` returns the failed read explicitly,
  `TestAppDriftedError` and the R462 `StaleTestAppError` say "the read failed: <cause>"), `publishTestApp` before
  the fence (the credentials hint only after a 401/403) and its read-back, `dependencyFingerprint` through
  `publishedPackageReader`, bytes mode's System and control reads, `bcdevDependencyFingerprint`, and
  `proveReadBack`.
- Tests: one per consumer through its real code path, with a 500 and a 404, asserting the same outcome and the
  named cause; each red-checked both ways (`/coord/handoff/R-630/redcheck.md`). Live gates on the final head
  (itest:bcdev, itest:verify, itest:testapp) are still to run.
