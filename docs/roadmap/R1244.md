**Found by** lethal-preproc on PR-479 (479a, the experimental `bcdev-client` backend), forced leg 4's warm phase: a
normal narrowed `bcdev-client` run of `fixtures/sandbox-data` (`--only src/DataFilterOps.Codeunit.al --operator
lethal.empty-block`) on bcwin, LethAL Control 1.0.0.31.

- **What happened, both times:** the baseline op of `Data Tests` (79310) ran, and about 34 s into the baseline the run
  ended. After the op, every authenticated call to bcwin hung:
  - `ReadClientAttestation` and teardown's `GetOperationStatus` gave no answer within 30 s;
  - `lethal doctor` then read no answer from `HarnessInfo` or the companies list;
  - the unauthenticated `/cs` (405), OData (401) and dev (200) endpoints answered in about 10 ms.
- **The first time** bcwin restarted itself (its ServiceInstanceId moved) and a smoke op at 12:27Z passed. **The second
  time** it stayed down for over 18 minutes, until a restart was asked of kraken.
- **Before it:** table 2 (450 mutants on the same codeunit, the same config) ran cleanly. Between table 2 and the wedge
  came forced legs 1 (wrong company), 6 (planted baseline-red) and 5 (drift; customer 10000's phone patched over the
  standard API and restored), and the publish of the scratch app "LethAL Forced Run Probe" (not yet run).
- **Measured after kraken's container restart (13:10-13:38Z),** with `/coord/handoff/PR-479/smoke/diag-att.ts`: one client
  op on Data Tests (all 71 methods ran: 70 pass, plus the known baseline-red `NegationFlipChangesTheCount`; End, both
  Deactivates and the driver's close all normal):
  - `ReadClientAttestation` for that op never answers: bcwin resets the connection after 165.3-165.4 s, the same in all
    three runs. The rows' filter is the table's primary key, so it is not a slow read. A smoke op on Sandbox Tests
    (2 methods) reads its rows at once.
  - with ONE read, HarnessInfo, polled every 5 s, answered at once throughout, and bcwin stayed healthy;
  - a SECOND read under the same lease got the same reset, and from the first reset on, every authenticated call hung
    (HarnessInfo, the companies list, ReleaseLease). bcwin was wedged again. So the wedges are this read plus the
    calls sent after it.
  - The block survived a docker restart, so it is not a lock held by a live session. Cause still unknown. Table 2's
    baseline read the same codeunit's rows in under 5 s before the forced legs ran.
  - kraken's capture of the 12:31Z wedge: `Get-NAVServerSession` count 0. The event log has two "Could not obtain lock
    to check for unused forms in session" warnings (UnusedSessionMonitor), at 12:26Z and 12:31Z, each on a different
    web-client session.
- **The cause narrowed (14:00-14:13Z): it is the SIZE of an OData answer on bcwin's port 7048, not LethAL.** Bisected
  with scratch copies of Data Tests (`/coord/handoff/PR-479/forced/subset-dtcopy.ts`; outputs under `smoke/`):
  - a TestPage test alone, the three commit-boundary tests alone, tests 1-35, 36-71, 1-53, 19-71, 1-62 and 1-67 all
    read at once. A full copy under another id, 1-68 and 1-69 never answer. So no single test causes it; the row
    count does.
  - 67 rows are a 29,256-byte answer, so the line sits at about 29.7 KB.
  - **Without LethAL:** two authenticated GETs of `$metadata` (ODataV4 and api/v2.0, both large) on port 7048 got no
    answer within 120 s, and bcwin was wedged again right after. The web client on port 8080 served a 554 KB file in
    0.07 s, so the network path to the host is fine.
  - Table 2's 71-row answers were read in under 5 s this morning, before bcwin restarted itself at about 12:22Z. So
    something on bcwin's OData service changed then.
- **The cause (kraken, `/coord/handoff/PR-479/wedge-1413/`, `httperr.txt`):** an ENVIRONMENT limit, not BC and not
  LethAL.
  - Inside bcwin, OData wrote 1.19 MB of `$metadata` in 1.3 s, so BC is fine.
  - Through Docker Desktop's port forward, a CHUNKED answer stalls at exactly 65,535 bytes. The dev endpoint answers
    with a `Content-Length` and gets 4.5 MB through.
  - HTTP.sys logged 5 `Connection_Abandoned` on `ReadClientAttestation` at 12:54Z.
  - The bcwin event log's "COMMIT called and skipped" warnings are routine (R1247), and its errors around 12:20Z are
    forced leg 1's planted company, the tenant remount of a restart, and a 503 while it came back.
  - **Not explained:** from this container, 67 rows (a 29,256-byte answer) arrived and 68 (about 29.7 KB) did not,
    well under 65,535. The limit as seen from here sits lower than kraken's localhost reading, maybe through how the
    NST writes its chunks. Nor is it known why table 2's 71-row reads passed this morning: the forward may have
    degraded at the self-restart. Neither is needed for the fix.
- **What LethAL owes, and how PR-479 pays it** (amendment 8 of the 479a spec):
  - a client read that can grow with the suite (one row per method) must not depend on one large answer: LethAL
    Control 1.0.0.32 pages `ReadClientAttestation` at 10 rows (at most about 15 KB a page);
  - after a lost or inconsistent read the run stops, so no further call goes to a server that just lost an answer
    (ruling 2);
  - a stalled answer names how far it got: "the answer stopped after N body byte(s) (chunked): response truncated".
  - A user's server behind a proxy like this one can be hit the same way by the other unbounded answers (R1246).
- **Fixed in code meanwhile (PR-479, 90f79b7dd):** the run ended with a bare `AbortError: The operation was aborted.`
  that named nothing. A control call our own timer aborts now says which action gave no answer within how long, and a
  lost attestation read is `client-attestation-unreadable`.
- **Why it matters:** a client op that leaves every authenticated call hanging takes the whole server down for every
  user on it, whatever the cause. A real user's CI server could hit it.
- **Next:** PR-479's proof of 1.0.0.32 (amendment 8 items 7-10); close this row with that commit. bcwin stays as it is,
  so its client legs also show the paged read working behind the capping forward.
