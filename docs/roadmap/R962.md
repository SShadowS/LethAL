Found by the Opus delta review of coord task R-948 (R961's memory guard), 2026-11-13. Related: [[R961]], [[R766]], [[R955]].

**What.** Under `--workers N`, a lane whose next group the memory guard refuses calls `LaneSink.memoryStop`, which closes the ordered
commit as a benign stop. Mutants that other lanes finished AFTER the stopping one, but that were not yet committed in order, are then
thrown away without being named (unlike `ParallelStopError`, which names them) and counted in `unscheduledCount` as left out, although
they ran. Edge case: when the commit was already closed by `unsafeBreak`, `memoryStop` still marks the stop as the guard's, so the
mutants after the unsafe break are counted as left out, which the plain unsafe stop does not do.

**Why it is low.** No verdict is wrong: a discarded mutant is reported left out, never scored or carried, and a resume re-runs it.
The cost is the work those mutants did, and a count that says "left out" for work that ran.

**Wanted.** Either commit the finished-but-uncommitted mutants in order before closing (they are complete results), or name them as
discarded in the report; and leave an `unsafeBreak` stop's accounting untouched by a later guard stop.
