**Filed 2026-10-04 at the adoption of the R-384 plan.** R-384 makes `lethal verify` run each new test
only against the survivors its baseline coverage reaches, when coverage is usable. The filter is off
with `--no-reach-filter`, in coverage mode `none`, and in the hub modes. No existing field of the
verify report fits that state, so R-384 prints it on stderr only. A survivor no new test reaches stays
`survived` with an empty `testsRun` and a `failureNote`.

So the JSON alone cannot answer "was this survivor run against every new test, or only against the
tests that reach it?", and two verify reports of the same survivors under the two modes look alike.
A reader who keeps only the report, such as a campaign comparison or an agent, loses that fact.

**To close.** Record the filter state per run (on, or off with its reason) and, per survivor, whether
the filter narrowed its request. That is a new verify-report field and a verify schema bump (v5), so
it follows the ripple rules in CLAUDE.md for report fields. Readers of older reports must treat a
missing field as "unknown", never as "off".

**Closed 2026-10-04** (plan `docs/superpowers/plans/2026-10-04-R-425-verify-report-filter-state.md`).
The verify report is now schema v5. `reachFilter` is `{"state": "on"}` or `{"state": "off",
"reason": ...}`, with one closed reason per R-384 stderr text (`no-reach-filter`,
`coverage-mode-none`, `coverage-mode-procedure`, `coverage-mode-line`, and `coverage-mode-al-runner`,
which cannot occur today because verify runs on bcdev only). Each planned result row carries
`reachNarrowed`, true when the filter left at least one new test out of that survivor's request; the
tests left out are not stored, because the report already holds them (`newTests[].test` minus
`testsRun`) and `droppedNewTestsOf` derives them. Both fields are absent when verify had not decided:
an early refusal, a skipped row, or a session that latched before the filter ran. The stderr counts
are not stored; they can be derived from the rows.

`packages/runner/src/verify-read.ts` reads every report older than v5 as unknown, never off and never
inferred from `testsRun`, and a v5 report without the field as not decided, pinned on a real v4
report from R-384's gate run. The version bumps although the fields are additive, because only the
version tells "not decided" from "predates the record"; v4 is kept as published.

Measured on Cronus28: `itest:verify` and `itest:agreement` pass with the new fields, every R-384
pin unchanged (both itests change by addition only); with `reachNarrowed` forced false, `itest:verify`
fails at step 3 on the narrowed survivor, as planned. No SessionReport, identity, fingerprint or
explain input moved.
