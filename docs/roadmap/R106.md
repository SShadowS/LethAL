**`report-fold.ts`'s `untargetedTriggerCount` has no presence check of its own, unlike the three events the fold treats as mandatory.** It sums `coverage-split` events with no assertion that any arrived — `orchestrator.ts` emits one per batch whenever `caps.coverage !== "none"`, and the fold currently trusts that unconditionally, the same trust model `deployMs`/`baselineMs`/`generateMutationSetMs` rely on for their own `phase-left` sums. If that assumption were ever violated (a batch running coverage-mode filtering that never emits `coverage-split`), the fold would silently under-report the count as a plausible zero rather than throw — the exact "absent tally read as a measured zero" shape the fold's mandatory-event design otherwise exists to close. Closing it needs a third signal (was `caps.coverage` ever non-`"none"` for a published batch) with the same shape as the `batchPublishedCount` reasoning the mandatory-baseline-evidence check already uses; deferred rather than added to the event-stream refactor without a concrete failure it is known to prevent. Evidence: `packages/runner/src/report-fold.ts:148-158`.

**CLOSED 2026-08-07, and the row's proposed condition was wrong in a way worth recording.**

This row said the check needs "a third signal (was `caps.coverage` ever non-`none` for a published
batch) with the same shape as the `batchPublishedCount` reasoning". Two corrections:

- **No third signal was needed.** `FoldStatics.caps` already carries the coverage mode, so the
  "was coverage claimed" half was available to the fold all along.
- **"For a published batch" is the wrong predicate, and shipping it would have broken real runs.**
  `runSession` emits `coverage-split` at step 5, AFTER the step-4 early `continue` that fires when a
  batch has NO green baseline test. An all-red baseline is a legitimate, completed run — it records
  every mutant `no green baseline tests` — and owes no split. Red-checked: widening the condition to
  any published/finished baseline batch fails **77 tests**, including a dedicated red-baseline case.

The shipped predicate is therefore *a batch finished baseline with at least one GREEN test, under a
coverage mode that is not `none`*. `none` owes nothing either — that branch hands every mutant every
green test and never calls `coverageFilter`.

Also fixed on the way: the shared `baseEvents()` fixture in `report-fold.test.ts` had no
`coverage-split`, describing a stream `runSession` cannot produce. It has one now.
