**`report-fold.ts`'s `untargetedTriggerCount` has no presence check of its own, unlike the three events the fold treats as mandatory.** It sums `coverage-split` events with no assertion that any arrived — `orchestrator.ts` emits one per batch whenever `caps.coverage !== "none"`, and the fold currently trusts that unconditionally, the same trust model `deployMs`/`baselineMs`/`generateMutationSetMs` rely on for their own `phase-left` sums. If that assumption were ever violated (a batch running coverage-mode filtering that never emits `coverage-split`), the fold would silently under-report the count as a plausible zero rather than throw — the exact "absent tally read as a measured zero" shape the fold's mandatory-event design otherwise exists to close. Closing it needs a third signal (was `caps.coverage` ever non-`"none"` for a published batch) with the same shape as the `batchPublishedCount` reasoning the mandatory-baseline-evidence check already uses; deferred rather than added to the event-stream refactor without a concrete failure it is known to prevent. Evidence: `packages/runner/src/report-fold.ts:148-158`.
