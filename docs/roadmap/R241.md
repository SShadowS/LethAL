**Measured 2026-09-26, while diagnosing [[R235]].** A cold al-runner v2.11.0 run on a truly empty
artifacts root (`AL_RUNNER_ARTIFACTS_ROOT` pointed at a scratch directory, the user's cache
untouched) exits 2 before it reaches the platform-app step. It resolves the project's `28` prefix to
the CDN's latest build, downloads that build's engine artifacts, and then refuses because this
al-runner install ships no engine variant for it. Verbatim tail:

```
[provision] no cached BC 28.x - resolving latest full version from the CDN...
Resolved: 28 -> 28.5.54151.55147
...
[provision] BC 28.5.54151.55147 engine artifacts complete.
BC version selection failed: no shipped engine variant supports BC 28.5.54151.55147 (major 28). Available variants: 27.0.38460.53934, 27.3.44313.53909, 27.5.46862.53931, 28.0.46665.54371, 28.1.49838.54368, 28.2.50931.54349, 28.3.52162.54374, 28.4.53241.54387. Select a cached BC version this install ships an engine for (--bc-version), or update al-runner.
```

**Who it hits.** A user on a fresh machine, or CI with no warm cache, running `--backend al-runner`.
Every invocation fails the same way, so the baseline cannot run and every mutant would score
`error`: the same class as [[R125]] (a run that measures nothing because the runner never got to
the tests). It does NOT affect `itest:alrunner` on this machine, because the cache is warm.

**What would fix it.** Either LethAL passes `--bc-version` naming a build this install ships an
engine for (which means reading the variant list, and choosing a build is a decision LethAL has so
far left to the runner), or al-runner resolves the prefix only to builds it has a variant for. The
second is an upstream fix. Pinning or downgrading al-runner is not a fix (CLAUDE.md, R125).

Evidence: the cold transcript in `docs/measurements/README.md` §"al-runner v2", the 2.11.0 entry,
and the R235 plan (`docs/superpowers/plans/2026-09-26-R-235-alrunner-provision-sentence.md`,
"Out of scope").
