**1. The exact build.**
- `scripts/refusal-family.ts` now has one source, `REFUSAL_FAMILY_BC_VERSION = "28.4.53241.56646"`. It is the build LethAL's DO
  configs and serve runs name (R1194). `runArgs` passes it on every family's run.
- zip-blob's own `--bc-version` is gone; its helper flags stay.
- **keep-census too** (`scripts/keep-census.ts`, its one-shot calls and its serve daemon), which builds its own al-runner commands
  from the families and passed a bare `28`. It now passes the same constant, so its next run is on the exact build. Its earlier
  censuses ran on `28`; they are not re-run here. A source guard in `refusal-family.test.ts` refuses a literal `--bc-version` in
  either script (red-checked: a `28` put back into keep-census turned it red).
- Out of scope, still on `28`: `scripts/upstream-repros.ts` and `scripts/r766-probe/drive.ts`, which do not run the families.
- **A test pins it:** the build is four numbers, and every family's arguments carry exactly one `--bc-version`, that build.
  Red-checked: a bare `28` in `runArgs` turned it red; restored green.
- **Re-run** (al-runner main-bf3a3e863, all 26 families, before on master's `28`, after on the fix): **3,418 cells, 1 move,
  against a pre-committed 0.**
  - The move is dotnet-exception cell 51021, `JObject.AddTwice (guarded)`.
  - Before: refused as `DotNet new Newtonsoft.Json.Linq.JObject: assembly 'Newtonsoft.Json' could not be loaded`.
  - After: refused as `DotNet Newtonsoft.Json.Linq.JObject.Add raised the .NET exception System.ArgumentException`.
- **What the move means:** under `28`, al-runner cannot load Newtonsoft for that cell. The fixed run gets the al-runner answer
  PR-32 recorded beside its BC check (`/coord/handoff/PR-32/bc-check-expected/dotnet-exception.expected.tsv`, row 51021, the
  `alRunner` column, the same text).
  So no earlier differential rests on a wrong-runtime result; only a fresh run of master's script would have given it.
  - Not explained here: why its twin cell 51022 (`AddTwice text`) loaded Newtonsoft under `28` too.

**2. Which BC build DO's own CI runs.** From DO's pipeline settings in the read-only corpus (`.devops/`; names only, no source
text here):
- The CI build (`.devops/CI/build.yml`): `BcArtifactVersion` `28`, type Sandbox, country `base`, no specific select. That is the
  latest BC 28 sandbox build.
- The daily and weekly "Current" builds (`.devops/Current/azure-pipeline-current.yml`): `//28/base/Latest`.
- Nightly next-minor and next-major builds run the insider artifacts (`///base/NextMinor`, `///base/NextMajor`).
- DO's `app.json` targets platform and application `28.0.0.0`, runtime 17.0.

**So DO's CI is on BC 28, not 29, and there is no BC 29 fidelity question to file.** One caveat: DO tracks the latest 28 minor,
while LethAL's DO configs and al-runner pin 28.4.53241.56646. When DO's CI moves to a later 28 minor (or to 29), the symbols and
the cached .NET service tier (`/coord/cache/bc28-service-windows` holds 28.0.54946.56477) stay at what they are until someone
updates them. bc4's BC 29 stays only the oracle of the refusal-family differentials (R1193 notes the same gap per family).

- **Whether the gap matters for v3:** LethAL is consistent with itself at 28.4. bc1-bc3 (the authoritative bcdev servers) run

  the cached 28 service tier. DO's CI runs a newer 28 minor, so a verdict could differ from DO's own CI only where BC changed
  behaviour between 28.4 and 28.5+. That is not measured, and no difference is known.
- **No new item is filed.** Measuring it needs a 28.5+ BC server, which none of bc1-bc4 is. If one is set up, the R1193-style
