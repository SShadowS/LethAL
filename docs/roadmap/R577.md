**Filed 2026-10-11 by R-394**; **measured and re-titled 2026-10-18 by R-577**. Evidence:
`/coord/handoff/R-577/measure.md` (14 runs), and from before: `/coord/handoff/R-394/measure.md` §3 and
`/coord/handoff/R-394/repro-pagecov.md`.

**What happened.** A `lethal run --backend al-runner` (coverage "none") on BC.History Simplified Bank
Statement Import, the wizard codeunit plus the import-preview page, 38 mutants, scored **M0035** (the preview
page's `OnAfterGetRecord`, `remove-assignment`) as **killed** by `WizardAllStepsCsvSeparatorSemicolonAndDecimalSeparatorComma`
with `Assert.AreEqual failed. Expected:<Comma> ... Actual:< >`. Run alone, and in a full re-run, M0035 survived.

**Measured (R-577, al-runner f06ee78c, 14 runs of the same 38 mutants):**

| Transport | Runs | Runs with a false kill |
|---|---|---|
| `--server` + resource | 8 | 1 (M0035) |
| `--server` + static | 3 | 1 (M0017) |
| one-shot + static | 3 | 1 (M0010) |

Every false kill has the same killing test and the same failure text, on a different mutant each time. The
three real kills are identical in all 14 runs. The test failed 3 times in about 510 runs (0.6%).

**The cause is the test, and LethAL's confirm rule.**
- **A measured flaky upstream (Microsoft) test.** `Bank Stmt File Wizard Tests.WizardAllStepsCsvSeparatorSemicolonAndDecimalSeparatorComma`
  writes its CSV with a random amount (`LibraryRandom.RandDecInRange`, two decimals, formatted with
  `<Decimals>`, which drops a zero fraction). The wizard reads the decimal separator from the first data line
  only, so about 1 time in 100 it finds no separator and the test fails. That would happen on BC too. It is not an
  al-runner defect and not `--server` state; the earlier guess (state carried in the daemon) is withdrawn.
  Reporting it to Microsoft is the owner's call.
- **LethAL's confirm rule.** A test that fails under the mutant is re-run with NO mutant active (the kill
  confirmation in the orchestrator's covering loop). If that passes, the mutant is `killed`. A 1% flaky test
  passes that re-run 99% of the time, so the chance failure is confirmed as a kill. Nothing checks that the
  failure REPEATS under the mutant. Any backend can produce this.

**Why it matters.** A kill must mean that the mutant made a green test fail. Nothing in the report flags this
one. On a real project it inflates the score and hides a survivor.

**To close (rulings 2026-10-18).**
1. "A kill must reproduce": after the unmutated confirmation passes, re-run the killing test UNDER THE MUTANT,
   in the same context as the kill (the same group prefix or chunk replay when `killPosition` > 1). A second
   failure counts as reproduced even with a different text; both texts are recorded. A pass gives `error`
   with the new cause `kill-not-reproduced`, never `survived`.
2. Switched on for al-runner here, with a pre-commitment and the local gates. The BC half is [[R582]].

## Done (2026-10-21, R-577)

**The rule.**
- **Where:** a shared orchestrator rule, switched on per backend by `ExecutionBackend.killsMustReproduce`.
  `AlRunnerBackend` sets it, and since [[R582]] so does `BcDevMcpBackend`.
- **What runs:** after the unmutated confirmation passes, `reproduceKill` re-activates the mutant and runs
  the killing test again, at the budget the killing run was sent. At `killPosition` > 1 it replays the
  call's own prefix with the mutant active.
- **Reproduced:** a second fail (any text) for a fail kill, and a second timeout for a timeout kill (the
  orchestrator's ruling B2). Only then is the mutant `killed`/`timeout-killed`, with the required marker
  `killReproduced` and the second text in `reproducedFailure`.
- **Not reproduced:** anything else gives `error` with the new cause `kill-not-reproduced`, and the covering
  loop goes on with the remaining tests. A later killer that reproduces still scores the kill.
- **Lost re-run:** a lost, deadline or stranded reproduction keeps its own cause, and a later
  infrastructure error wins over a pending `kill-not-reproduced`.
- **`--resume`:** with the rule on, a stored kill without the marker is not carried. That check sits beside
  R557's run-level trust filter, and both only remove.
- **Schemas:** explain moves to v17.
- **Tests:** unit-tested per direction (`/coord/handoff/R-577/redcheck.md`, about 60 rows, including the
  R557 x R577 composition).

**Measured.**
- **The cause** (`/coord/handoff/R-577/measure.md`, 14 runs before the rule): the false kill came from a
  ~1% flaky Microsoft test and LethAL's unmutated-only confirmation, on every al-runner transport. It was
  not `--server` state.
- **The gate:** pre-committed in `docs/superpowers/specs/2026-10-20-r577-kill-must-reproduce-precommitment.md`,
  with the addendum for R557's names legs. `itest:alrunner` PASSED on 8555860f:
  - every verdict unchanged;
  - every kill on all 20 legs reproduced, with 2 killer rows each;
  - cli-default: activations 23, suite runs 22.
- **The slice with the rule on** (6 runs; `/coord/handoff/R-577/scratch/runs/on1`-`on6`):
  - M0005, M0006 and M0007 were killed and reproduced in all 6;
  - no other kill;
  - in on3 (M0026) and on4 (M0024) the wizard test failed at random under a mutant (the same
    `Expected:<Comma> ... Actual:< >`), passed unmutated, and passed again under the mutant. Each is
    `error` / `kill-not-reproduced`. Before R577 each would have been a false kill.

**Known limits.**
- **Timeout half:** no al-runner gate has a timeout kill. It is now measured live on BC: [[R582]]'s
  `itest:hang` on bc2 (2026-10-22, build 7a8ff82c) re-ran all 10 timeout kills (5 on ON, 5 on SINGLE),
  and each was stopped by BC a second time in band, with no `stop-outcome-unconfirmed`
  (`/coord/handoff/R-582/gate/bc2/hang.log`).
- **Cost:** one more test run per kill. On `--server` that is one more whole-suite run (plus a recompile
  with the static selector), and a timeout kill waits out one more budget.
- **On BC ([[R582]]), two timeout costs:** a timeout kill waits out one more full budget,
  `max(2 x duration, floor)`, which on a slow real suite is minutes; and its re-run is a second
  `StopHungRunAt` stop, with the R202/R-204b risk of an unconfirmed outcome or a lost acknowledgement. That
  scores `error` (`stop-outcome-unconfirmed` and similar causes), not `timeout-killed`, so a real hang can
  now end as `error`. On the next real BC campaign, count `stop-outcome-unconfirmed` against
  `timeout-killed`.
- **Silence:** when a later kill stands, the report says nothing about an earlier failure that did not
  repeat (accepted, M6 of the build review).
- **The Microsoft test:** `WizardAllStepsCsvSeparatorSemicolonAndDecimalSeparatorComma` is a measured flaky
  upstream test. Reporting it is the owner's call.
