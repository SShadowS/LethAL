**Filed 2026-10-11 by R-563** (found while checking [[R563]]'s census; `/coord/handoff/R-563/r563-measure.md`).
This is a plausible hang that is NOT refused. Not measured beyond one object.

**What.** A loop over a RecordRef ends when its Next call returns zero. Inside its body, the code moves the loop's own cursor and then
puts it back:
- it narrows the set and calls `FindFirst` on the same RecordRef;
- later it calls `Reset`, then `Get` back to the saved record, then `SetView` back to the saved view;
- and only then does `Next` advance.

If a mutant deletes the restore (`void-method-call` on the `Get` or the `SetView`), the cursor stays on the
narrowed record. `Next` then continues from there, and can revisit rows it already passed, so the loop may never
end.
- [[R531]] does not see it: R531 covers loops whose condition is a Find/IsEmpty/Count test, never `Next`.
- The value refusals on the loop's own exit condition (R196, R239) do not reach a statement in the body.

**Where.** DO `/work/src/DO/Cloud`, `CDO E-Mail Handler`.RunReportID, and the same procedure in CDO
(`/work/src/do-lethal/Cloud`). On master 24e7dafe the procedure has 127 deployed mutants in DO and 107 in CDO. Among
them in DO are `void-method-call` on the restoring `Get` and on the restoring `SetView`.

**To close.**
1. Census, per corpus, the `Next` loops whose body calls a positioning method (`Find*`, `Get`, `SetPosition`) on the
   loop's own cursor (by name, a RecordRef, or a Record).
2. Price the refusal of the restore calls and their guards.
3. Read a sample for real hangs.
4. Refuse, or close by ruling.
