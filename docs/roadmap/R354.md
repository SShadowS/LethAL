**Found closing R252 (2026-09-30), by the bugs lane's note, confirmed by reading.** `sessionFingerprint`
(`packages/runner/src/resume.ts`) digests the project, tests, backend, filters, symbols, scheme and
selector ids, but not the coverage mode (`caps.coverage`: none, procedure, fenced, al-runner). The
backend does not determine it either: bcdev runs none, procedure or fenced.

**Why it matters.** With coverage off, a mutant no test reaches scores `survived`; with coverage on
it scores `no-coverage`. So `--resume` of a coverage-off run under a coverage-on config carries
`survived` verdicts that the new mode would have scored `no-coverage`, and the other way round.
Since R252 such a carried survivor also has no attribution in a coverage-on report, so
`lethal explain` refuses the report. History (`--skip-known-survivors`) has the same question:
a survivor recorded under coverage off is not a survivor under coverage on. Not observed live.

**To close.** Put the coverage mode in the fingerprint as a conditional key (the R127 / C02-06
pattern, so older digests keep resuming where the mode is unchanged: decide how an old record with
no mode is read), refuse a resume across modes by name, scope history the same way, and test both
directions, red-checked.
