**Measured on a Document Output PR** (2026-09-25, bcdev on a hosted BC 29 sandbox, 3 touched files,
527 deployed mutants, 136 tests; reported in GitHub issue #19): 137 mutants sat on lines the PR did
not change and cost ~833 s of the first 935 s of mutant time. One unchanged procedure reached from
an `OnInsert` trigger cost 523 s alone. The workaround, filtering `report.json` by `file:line`
afterwards, fixed the reading but not the cost.

**Landed:** a line-scoped mutant filter, `packages/runner/src/line-filter.ts`, applied inside
`generateMutationSet` after per-file dedup and after `--operator`, so what it deploys is a strict
subset of an unfiltered run and it cannot change a verdict. A mutant is kept when its span shares a
line with a range, so an `empty-block` over a whole body with one changed line stays in: the PR
changed its behaviour. `--changed-since` runs `git diff -U0 --relative <ref>...HEAD` in the
project and keeps `.al` files only; a pure deletion adds no line. The 1,000-site pre-flight counts
after the filter. A range naming no project `.al` file, and a filter keeping nothing, both refuse.
The report carries `lines` (ranges plus the excluded site count), the `line-narrowed` caveat,
`reliability: narrowed`, and a `NARROWED (lines)` banner line; the ranges are in the resume
fingerprint. Pinned by `packages/runner/tests/line-filter.test.ts`, including a `runSession`
end-to-end case.

**Not measured live yet.** No gate exercises the flag against a real server; the claim that it
cannot change a verdict rests on the post-dedup placement, the same argument R127 makes for
`--operator`.
