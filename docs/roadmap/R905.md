Found by coord task R-899 (lethal-code, 2026-11-10). Related: [[R642]] (the owner's heavy-job caps), [[R724]].

**What happened.** The container held two BaseApp-class jobs: preproc's R-903 and bugs' R-902 smoke run, both running on BC.History
COPIES under `/coord/handoff/`. My `corpus-snapshot.ts diff bch` started anyway, as a third. Its guard printed
`2 other slot(s) held, 0 other heavy job(s) ... 0 other BaseApp corpus job(s)` and took the free `heavy.2`. Memory was fine (51 GB), so
nothing was hurt. But the owner's rule is at most two heavy jobs while a BaseApp job runs.

**Why.** `corpus-snapshot.ts`'s guard (`holderIsBaseApp`, the unslotted `ps` scan) decides "BaseApp" in two ways: a corpus-snapshot
holder's own set is `bch`, or some process of the holder names `/work/src/BC.History`. Its own header says a job over a corpus COPY is
invisible to that scan. Every other lane's BaseApp-class job runs on a copy, so every one of them reads as not BaseApp.

**Fix sketch.**
1. Whoever takes a slot records the job's class beside the lock, for example `/coord/locks/heavy.<n>.class` holding `baseapp` or
   `other`, written right after the flock and removed on exit. It is stale by pid, as the lock already is.
2. The guard counts held slots by that class, and treats an unknown class as BaseApp (the safe side).
3. One test per direction:
   - two held `baseapp` slots: a third BaseApp job is refused (rc 75);
   - two held `other` slots, all v3: a third job is allowed, as the owner's three-v3 rule says.
4. Every script that takes a slot needs the class line: the gate scripts, the corpus runs and hand-run `flock` calls in each lane. That
   is the larger part, and it crosses lanes. Until it lands, lanes count held slots themselves before a heavy start, not only the
   guard.
