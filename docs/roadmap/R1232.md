**Found by** PR-463 (lethal-code, 2026-11-27), which answered R1219. Evidence: `/coord/handoff/PR-463/findings.md`,
`full/req.jsonl`.

- **What was measured:** one al-runner daemon, one test thread, DO's 108 one-test entries.
  - The login (≈ 90% of each entry) is CPU: 211 ms per entry on an ambient core, 1.7% off-CPU.
  - With 30 spinners on its 5 cores (≈ 6×), it took 1,728 ms per entry; run-queue wait was 95% of the rise.
- **Observed, not pre-committed:**
  - With the run queue small (0-8%), the SAME work's on-CPU time went from 16.6 s to 52.2 s as other processes'
    busy share of the cores rose from 0.51 to 0.93.
  - So on this host, a busy neighbourhood slows the work itself, not only its turn on the CPU.
- **The question:** for a full DO run, what number of lanes (runnable al-runner test threads) per core gives the most
  entries per hour?
  - If CPU time inflates with neighbour load, more lanes than cores can LOSE throughput, not just share it.
- **How to measure:**
  - a fixed DO entry set, run at 2-3 lane counts on the same cores;
  - per arm, entries per hour plus `perf stat` instructions:u and cycles:u (so IPC shows the inflation);
  - interleaved arms, with outside load named (the owner's server1 speed rule).
- **Not covered here:** the login's own CPU (al-runner's company-open execution) is an upstream lever. R1182 ruled out
  replay as a cut.
