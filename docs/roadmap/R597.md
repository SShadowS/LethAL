**Filed 2026-10-21 by R-595** (lethal-preproc; orchestrator ruling).

**What.** On bc2, a BC server on Linux, `lethal verify` refused with `test-app-version-below-resident`. Its
user-facing `refused.detail` text tells the user to clear the resident record with `Sync-NAVApp -Mode ...`. That
is a BcContainerHelper / Windows PowerShell command, and it does not exist for the Linux bc1-bc3 servers. A
user there gets a fix they cannot run. Evidence: `/coord/handoff/R-595/itest-verify-bc2.log`, the step-3
refusal.

**Built.** The refusal text (`publishTestApp` in `packages/runner/src/test-app-publish.ts`) now names both fixes,
each labelled: on a BC server on Linux, call the automation API's bound actions `Microsoft.NAV.uninstall`, then
`Microsoft.NAV.unpublish`, on the extension; on a Windows container, `UnPublish-BcContainerApp`, then
`Sync-NAVApp -Mode Clean`. No server-kind field reaches that code (the
config has none), so it names both. `scripts/bc-republish.ts` never unpublishes, so it is not named. Two tests
pin the wording, one per kind (`packages/runner/tests/test-app-publish.test.ts`).

**To close.**
1. **The removal step on Linux is measured** (lethal-bugs, R-389, on bc3, 2026-10-21; recorded with R389):
   uninstall the app, then call the automation API's bound `Microsoft.NAV.unpublish` action on the extension,
   which removes it over HTTP. That is reachable from a lane, with no BcContainerHelper. The dev endpoint only
   publishes, and `scripts/bc-linux-setup.ts` has no unpublish yet.
2. Make the message name the fix that fits the server: that step (uninstall, then the bound
   `Microsoft.NAV.unpublish` action) for the Linux servers, and `Sync-NAVApp` only for a Windows container. Or
   name both, each labelled.
3. Add a test that pins the wording per server kind.
