**Filed by coord task R-727 (2026-10-24), option (a).** [[R727]] shipped option (b). Before the first publish, a run
reads the control app's `DependentCount` for the target and warns when it is larger than the run's own tests app.
That count has no names, and it counts every PUBLISHED version, installed or not, so old versions inflate it.

**Measured for R-727 (bc3, read-only):** no standard BC endpoint gives an app's dependents by id. The `$metadata` of
the automation API v2.0 (25 entity sets, among them `extensions`, `extensionUpload` and `extensionDeploymentStatus`),
API v2.0 (152) and OData v4 (82) has no dependency entity or property. The only hit is LethAL's own
`LethALControl_DependentCount`. Naming the dependents therefore needs a control-app read.

**The build.**
- A new `ControlApi` procedure, `InstalledDependents(AppId)`. It joins the system table "Application Dependency"
  (`Dependency App ID` = AppId) with the installed-app table and returns, for INSTALLED dependents only, JSON rows of
  id, name, publisher and version. A bad GUID raises an error, never a plausible empty list.
- R727's warning then names each dependent other than the tests app.
- An older control (404) falls back to R727's count.

**Cost.**
- **The AL change:** an `alc` compile, plus the hang gate, which CLAUDE.md requires for control-app AL.
- **Publishing:** bump `extensions/lethal-control/app.json` to 1.0.0.24, then update `CONTROL_APP` and
  `CONTROL_SHA256` in `scripts/bc-linux-setup.ts` and publish to bc1, bc2 and bc3.
- **Re-proof:** a new control build means re-proving every BC gate on all three servers (CLAUDE.md's proof rule):
  about 10 BC legs × 3 servers, several hours of server time.
- **Client:** `MIN_CONTROL_VERSION` stays where it is (the read is optional), and there is a test of the
  404-to-count fallback.
- That re-proof is why this waits until after the Directions talk.

## Built (code and unit tests) 2026-10-25 by coord task R-689b (lethal-code); status stays open until the live proof

LethAL Control 1.0.0.24 (shared with [[R689]]). Not yet published to any server.
- **AL:** `ControlApi.InstalledDependents(AppId)` joins "Application Dependency" (`Dependency App ID` = AppId) to
  "NAV App Installed App" on `Package ID`, so only installed versions appear. A bad GUID raises. Answer:
  `{"appId", "installedDependents": [{id, name, publisher, version}]}`, the version from the four Version fields.
  `Permissions` gained `tabledata "NAV App Installed App" = R`. `DependentCount` stays: closed-world (R389) still
  reads it for the tests app, with its published-superset meaning.
- **Client:** `HarnessVerifier.fetchInstalledDependents` (appId echo checked, a malformed row or list throws),
  `ExecutionBackend.installedDependents` (bcdev only). R727's warning (code `installed-dependents`, unchanged) now
  NAMES each installed dependent except the run's own tests app, excluded by its app.json id.
- **The 404 fallback is dropped (no back-compat before release).** `MIN_CONTROL_VERSION` is now 1.0.0.24, so no older
  control app can reach the read. The closed-world 404 branch and `DependentCountUnavailableError` went with it: a 404
  is now a plain failure (closed-world warns and stays open-world; R727's warning says it could not check).
- **Known gap:** the warning names installed apps. It cannot see a dependent that is published but not installed,
  which BC does not remove on a refused upgrade.
- **Still to do:** the live proof, and a live check that the warning names the extra app on harden's server.
