**Found by** lethal-code, 2026-11-24, fixing the PR-256 pin it broke (branch `lethal/fix-stopgroups-pin`). PR-410's
VERIFY on a master merge failed, and plain master failed too.

- **What happens:**
  - `scripts/al-runner-v3-update.ts` (the publish step near the `R814: gated build ... [skip ci]` commit) checks the new
    row only with `parseGatedBuilds` and the pin digests. It then commits `packages/runner/src/al-runner-v3-gated-builds.json`
    with `[skip ci]` and pushes it to master.
  - Unit tests read that file: `pr256-stop-groups.test.ts` (which records may allow the stop-groups flag),
    `pr402-login-replay.test.ts` (no record reads `login-replay`) and `r814-gated-builds.test.ts`.
  - edge-e5176a9fd's row was the first to read `stop-groups: matches`. That broke the PR-256 pin, and no check saw it
    until the next VERIFY of a branch merged with master.
- **Why it matters:**
  - A row that changes a capability fact changes what a run may do. Here it allowed `alRunnerV3.stopGroups` on `current`.
  - The pins exist so that such a change is named on purpose. A `[skip ci]` push bypasses them.
  - It also breaks the standing rule that files a test reads go to master through a branch, never as a `[skip ci]` push.
- **The fix to decide:** the publish step either runs the tests that read the gated-builds file (at least those three)
  on the publishing worktree before it pushes, and refuses on red, or pushes the row through a branch with CI. Not built
  here.
