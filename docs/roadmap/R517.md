**Priority.** Filed 2026-10-08 by the R516 + R515 build, from the R-516 plan (r2, section D3b) and
its adversarial review (I1, I4). A false-kill risk on al-runner `--server` and resource-with-server
only. Found by reading the code; NOT measured live: no `itest:alrunner` leg produces a timeout.
[[R516]] closed the matching false kill for bcdev and al-runner one-shot, and says it does not cover
this path.

**What.** The `--server` daemon is spawned with no `AL_RUNNER_TEST_TIMEOUT_SEC`
(`defaultServerSpawn` in `packages/runner/src/al-runner-backend.ts` inherits the process
environment), so al-runner's `TestExecutor` stops a test at its own `DefaultTestTimeoutSeconds` of
60 s, timed on the test BODY (al-runner source `AlRunner/TestExecutor.cs`, read at 43f7617, the
container's current build). LethAL never sends it the budget. Meanwhile every per-test
`durationMs` on that path is the whole SUITE's wall clock (`runViaServer` gives each test
`suite.wallMs`), so every budget and every unmutated confirm is judged on the suite, compile
included. `ensureServerSuite` sets its own deadline at `max(budget, 10 min)`.

The sequence (the review's, exactly): T's body is 58 s and the rest of the suite plus the compile is
30 s. The baseline is 88 s, so the budget is 180 s (the default floor). Under an unrelated mutant T
takes 61 s and al-runner times it out at its 60 s default. The confirm runs the suite unmutated in
88 s; 2 x 88 <= 180, so R516's rule scores it `timeout-killed`: a false kill.

**A second sequence, through [[R515]]'s re-budget (R516 build review, I1).** The suite takes 100 s,
so the budget is 200 s. M1 does not touch T, but T times out at the daemon's 60 s; the confirm takes
105 s, 2 x 105 > 200, so M1 is not killed, and R515 would re-budget T to 210 s. M2 times out at the
same 60 s; its confirm takes 103 s, 2 x 103 <= 210: a false `timeout-killed`. Raising the budget
moved no stop. Closed in the R516 build by skipping the re-budget where the backend's
`inRunStopIsBudget` is false (al-runner under `serverMode`): see [[R515]]. The first sequence above
is NOT closed by that, since it needs no re-budget.

**Evidence.** The names above: `defaultServerSpawn` (no env), `runViaServer` (`suite.wallMs` as
every test's duration), `ensureServerSuite` (deadline `max(budget, 10 min)`), and
`DefaultTestTimeoutSeconds = 60` in `TestExecutor.cs` (read via `/work/src/al-runner-src` at
43f7617; the env var is read in the same file, else the default). Not measured.

**Proposed close.** Spawn the daemon with `AL_RUNNER_TEST_TIMEOUT_SEC = ceil(F / 1000)`, where F is
the session's `--mutant-timeout-ms` floor (fixed for the daemon's life), and judge a server confirm
as `2 x measuredDurationMs <= F`, using R272's per-test figure rather than the suite's wall clock.
Probe first, live: does the daemon honour the variable, and does each row carry the test's own
duration.

**Follow-up in this item (ex-Q2 of the R-516 plan, review I4).** On al-runner ONE-SHOT, judge the
confirm on `measuredDurationMs ?? durationMs` instead of the wall clock. That closes R516's one-shot
lost-kill band (a genuine hang is reported `timeout-unconfirmed` whenever compile plus body takes
more than half the budget; e.g. a 65 s compile, R222's 553-file app, loses every hang kill under a
budget below 130 s) and [[R514]]'s M3. It needs the same probe for one-shot's per-test figure.

**To close.** The probe's answers recorded; the daemon spawned with the floor; the server confirm
judged on the per-test figure; an offline test of the review's sequence (a false kill today, not
after) red-checked both ways; the re-budget sequence above still not a kill, and, if the fix makes
the daemon's stop the budget, `inRunStopIsBudget` turned true under `serverMode` only with an offline
test that a re-budgeted run really gets the larger stop; `itest:alrunner` unchanged on every leg.

**Fixed in b89f2f34 (live gate pending).** Plan `/coord/handoff/R-517/plan.md` r2, after an
adversarial review (`review-r1-opus-adversary.md`). `done` once `itest:alrunner` passes against
`docs/superpowers/specs/2026-10-08-r517-alrunner-server-timeout-precommitment.md` (no figure moves;
one new check: the CLI-default leg's daemon argv carries `--test-timeout 180` exactly once).

*What the probe answered* (measured on 43f76177, `/coord/handoff/R-517/measure.md`, probe committed
as `scripts/r517-probe/`): the daemon has ONE stop for its life; a `runTests` request cannot carry a
timeout (refused by name); `--test-timeout N` on the `--server` start line works and beats an
inherited `AL_RUNNER_TEST_TIMEOUT_SEC`; each server row carries the test's own duration (body plus
per-test setup, no compile), and a timeout row says which stop fired (`Test exceeded {N}s
timeout.`). The host pin c39ad5de is not measured; the reported stop below is what keeps that from
mattering.

*The fix.*
- The daemon's stop is LethAL's: `runSession` hands every backend (session and workers) the floor
  and the baseline timeout through `useMutantBudgetFloor` before the first run, and `AlRunnerServer`
  starts the daemon with `--test-timeout S`, `S = ceil(max(F, baselineTimeoutMs) / 1000)` (180 at
  the defaults). `--server` refuses to start a daemon without it (`AlRunnerServerStopUnsetError`,
  which stops the session). `inRunStopMs` answers `S x 1000`; `inRunStopIsBudget` stays false, so
  R515's re-budget stays skipped on `--server`.
- A position-1 timeout confirm is judged on the test's own figure against the stop al-runner
  REPORTS: `verdictFromRunnerTest` parses N into `reportedStopMs`, and the confirm passes only if
  `2 x (measuredDurationMs ?? durationMs) <= min(budget, reportedStopMs, inRunStopMs)`. On a backend
  that declares `inRunStopMs` an unparsed stop stays `timeout-unconfirmed`. bcdev is unchanged
  (its `measuredDurationMs` is its `durationMs`; it reports and declares no stop). The note names
  the reported stop when it is below the budget.
- (review C1) Any `runTests` throw closes the daemon before rethrowing: a late answer to an overrun
  request was read as the next request's answer, scoring a mutant on the previous activation's
  results (a false kill, before this fix, for a suite slower than 10 min).
- (review I2) A suite with a timeout row closes the daemon after its results are read: a timed-out
  test's thread is abandoned, not stopped, and kept writing into later requests, the unmutated
  confirm included. A covering test after the hung one is `error` with a note naming the hung test.

Offline tests: "R517 S1" (the review's sequence, survived), "R517 S2" (the stop below the budget),
"R517 S3" (a genuine hang still killed), "R517 S5 (a)/(b)" (the enforced and the unparsed stop),
the one-shot pair, the wiring pair (resume.test.ts); the D1 argv, refusal, C1, I2 and M3 tests and
`parseReportedStopMs` (al-runner-backend.test.ts). S1, C1, I2 and M3 were committed red first
(f25c2493). Red-checks per direction: `/coord/handoff/R-517/redchecks.md`.

*What it does not close (lost kills, never false ones).* A test whose own body is between S/2 and
S (90 s to 180 s at the defaults) can never have a timeout confirmed on `--server`; a body over S is
red in the baseline. A genuine hang on `--server` now takes S (was 60 s) plus a daemon restart and
a cold compile. A suite that overruns `max(budget, 10 min)` is an `error` and a fresh daemon. Tests
after a hung one have no row ([[R519]] would confine that). The one-shot follow-up (judging on the
body, not body plus compile) is implemented but NOT live until [[R518]] lands: a one-shot timeout
exits 3 and is scored `error` before any confirm. That was measured on 43f76177 only; the host pin
c39ad5de is not measured.

*Review fixes (final build review).* D4c's restart now fires on any row whose status is neither
`pass` nor `fail`, not on the timeout wording: al-runner's OnRun-trigger timeout ("... exceeded the
{N}s timeout, so none of its test methods ran.") does not match `RUNNER_TIMEOUT_MESSAGE` but
abandons its thread the same way (I-1). A confirm failed by the in-run stop alone (twice the test's
own run fits the budget, not the stop) is `timeout-unconfirmed`, never `reused-budget-stale`, and
its note says raising `--mutant-timeout-ms` raises the stop (I-2). A reported stop other than the
configured one warns once per session (`alrunner-stop-mismatch`, M-a).
