Found by coord task PR-07 (2026-11-15), from R-998's DO window (`/coord/handoff/R-998/do/result.md`). Related: [[R954]],
[[R1014]], [[R895]], [[R897]].

**What.** R954 gives the mutant phase one stop for every test: `max(60 s, 20 x the largest green baseline test + 5 s)`.
al-runner's `--test-timeout` is a `serve` START option, with no per-request value (al-runner `serve --help`), so a daemon
has one stop for all of its tests. DO's slowest green test takes 87.8 s, so every test gets 1,761.8 s. A mutant that makes
a 0.1 s test loop forever then costs about 29 minutes before its timeout row ends the request. R-998's window met a run of
these (CDOeDocsSendCodeMigration), and R1014's overrun came from them.

**What is not the cause.** The re-send after such a timeout is needed: it carries the OTHER mutants' entries after the cut
(R895), and the hanging test itself is not re-sent (its row is the verdict). PR-07 (R1014) made a spent budget and a stop
signal end that loop, and a signal end the hanging request at once.

**Why not simply per test.** A stop from each test's own baseline (for example 20 x its own time + 5 s, at least 60 s),
enforced by LethAL with `announceStart` and a wall clock (killing the daemon past it), would end a hang in minutes. But a
mutant that only makes a test slow (still finishing within today's stop) would turn from killed or survived into
`timeout-killed`. That moves verdicts, so it needs a pre-committed measurement:
- the mutants of a real project whose verdict would change;
- each one's time against its own baseline;
- the bcdev reading where one exists.

**To do.** Measure on DO's stored windows which timeouts and slow passes a per-test stop would reclassify; then decide.
