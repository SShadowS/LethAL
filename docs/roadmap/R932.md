Found by lethal-code, 2026-11-11 (coord R-920 follow-up, kraken's second RunModal run on R910Win with LethAL 37def9fb). Related:
[[R931]], [[R843]], [[R139]], [[R910]].

**What happened.** With R931 in, run 1 still stopped with `TestAppDriftedError` (`19551c6b` vs `801cb1b1`). Run 2 reached deploy,
then R843 warned that the installed tests app's `SymbolReference.json` is not valid JSON (`Unrecognized token '\u0000'`).

**Why.** The package the Windows server serves is not the file that was published: it is rebuilt per request.
- Every zip entry is stamped with the download time (`/coord/handoff/R-920/pkg-a.app`: all four entries 18:16:46 server time, the
  minute kraken fetched it). The two back-to-back reads R931 was built on fell in one 2-second zip-time window, so they differed only
  in the header's package id. Reads seconds apart also differ in every entry's time, so a byte hash changes even with the id zeroed.
- It holds four entries (`NavxManifest.xml`, `SymbolReference.json`, `DocComments.xml`, `[Content_Types].xml`): no source, no
  `MediaIdListing.xml`, no entitlement, a different manifest than the compiled app's.
- Its `SymbolReference.json` is UTF-8 JSON followed by 936 NUL bytes (2,054 bytes; the compiled app's is 1,118 bytes with none). The
  NULs come from the server's rebuild, not from the app LethAL compiled.

**Measured.** Three reads 93 minutes apart (`pkg-a.app` 18:16, `pkg-c.app` 19:46, `pkg-d.app` 19:49, in `/coord/handoff/R-920/`;
pkg-a is kept for the tests as `packages/runner/tests/fixtures/r932/pkg-a.app.b64`, since `*.app` is gitignored) have identical entry names, sizes and bytes; only the entry times and the header id differ.
Kraken published the tests app over the dev endpoint (`Publish-BcContainerApp`).

**Rejected: a content hash.** Hashing the entries instead of the zip bytes would be stable, but review showed it is unsafe: the
served package holds no source, so a same-version republish that changes only test BODIES hashes equal, and the drift guard,
snapshot reuse and `--resume` would accept stale verdicts. It also cost 8 s and 2.4 GB per call on a BaseApp-sized unsigned package.

**Fix.** `hashPackage` stays R931's (id zeroed, bytes hashed). A served test-app package with no AL source proves no identity
(`servedWithoutSource` in orchestrator.ts; `provenWithoutHook`, and the hook path after `proveReadBack`): no drift check, no
baseline-snapshot or verdict reuse, `--resume` refuses, and the warning `test-app-identity-unproven` says why and how to fix it. A
hook session's source-less read-back that is byte-equal to its publishApps file is still proven (R498). One parser
(`parseSymbolReferenceJson` in app-package.ts) strips trailing NUL padding for both served-package readers (R843's
`declaredObjectsOfPackage`, R403's `compiledMembershipOf`); a NUL elsewhere still refuses.

**Named limit.** On such a server the run itself works but proves nothing about which test app it measured: a run there cannot be
resumed or lend its baseline. A Linux user whose test app is built without source loses the same reuse, with the same warning.
