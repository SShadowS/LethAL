**What R69 measured.** A benefit share against a bar written before the number was known: at least 5% of deployable mutants covered
only by TestPage tests continues R69, under 5% closes it. Result: 439 of 19,081 = 2.30%, on Document Output (`do-rel2`, 19 TestPage tests
of 1,287). The cost side was qualitative: "a permanent client-services surface on every customer container plus a second verdict path to
keep honest across four gates". No per-test or per-mutant cost was measured. The path was blocked by R74 and R75 and could not rescue a
baseline hang (R69 Task 7 wedged the fenced session twice).

**Does it overturn "unprofitable"?** As a general claim, yes. It held for the one app measured. By R69's own bar, 4 of the 6 apps with
coverage data clear 5%, three of them by far (45-59%). Document Output stays under the bar (4.2% of its tests refused today). DC's test share
(38.2%) suggests it would clear the bar, but DC has no coverage data here. The bar measures benefit only: **the cost is still unpriced**,
so this does not show a routed path would pay off.

**Recommendation for the owner, cheapest first:**
1. **Change the record now:** R69's verdict is "unprofitable on Document Output", not in general.
2. **Do not rebuild the routed path yet.** Its costs and its hang risk are unchanged, and it is the most expensive option.
3. **Next, measure the reach rule.** 40-44% of refusals come only through a helper that MAY open a page. If most of those tests never
   open one when run, a narrower rule recovers them with no new path. It is a live measurement on a throwaway server, with a time cap,
   since a page test that is wrongly admitted can wedge a fenced session (R69 Task 7).
4. **Consider a labelled hybrid:** for a mutant whose only tests are refused on BC, report al-runner v3's verdict, marked non-authoritative.
   v3 already runs TestPage tests, so the cost is reporting. The limit: nothing checks those verdicts against BC, and R895 and R890 show the
   two backends can differ.
5. **Only then re-price a routed path**, with a spike, if real users' suites look like BankDeposits.

**Separate limit found here:** on Linux BC, a test that renders an RDLC report fails ("not implemented on Linux BC"). It cost 19 of
BankDeposits' 75 tests. The gate servers and `bc5` are Linux, so this applies to any report-heavy suite measured there.

## Do helper-reach refusals really open a page? (coord R-908, 2026-11-10; the owner's ruling on step 3 above)

Pre-commitment: `docs/superpowers/specs/2026-11-10-r908-testpage-reach-precommitment.md`. Plan, review, scripts and per-test classes: `/coord/handoff/R-908/` (`classes.tsv`).
Measured on `bc5`, a throwaway BC 28.4 W1, with the refusal switched off in a scratch copy of LethAL. 170 tests across three apps, in 19 random groups, 60 s per test. Every run ended normally: **no wedge, no
quarantine, no restart, no test hit the time cap.**

**What a page open looks like on Linux BC.** A direct page-opening test, alone, per app: each failed fast with `Unexpected CLR exception thrown.: System.NotSupportedException: Specified
method is not supported.` and a top AL frame at the page call. LethAL's own page-refusal text (`TESTPAGE_REFUSAL_RE`, `CreateNavTestService()`) has only been seen on Windows and does not match this.

| app | helper-reach tests | opened a page | passed | of those, with an `asserterror` | handler not run | failed earlier |
|---|---|---|---|---|---|---|
| BankDeposits | 41 | 37 | 0 | 0 | 4 | 0 |
| VAT Group Management | 51 | 51 | 0 | 0 | 0 | 0 |
| Intrastat Core | 78 | 68 | 8 | 7 | 0 | 2 |
| **total** | **170** | **156 (91.8%)** | **8** | **7** | **4** | **2** |

- "Opened" is strict: every one of the 156 has a `NotSupportedException` whose top AL frame is at a page-opening call in the source (10 distinct frames, each read: `OpenEdit`, `OpenView`, `OpenNew`, `Trap`, `Page.Run`, `RunModal`).
  Two of those sit in production code the tests reach (`Bank Deposit-Post.OnRun`'s closing `Page.Run`, `Purch.-Get Drop Shpt.`'s `RunModal`).
- "Did not open" is a range, because a pass can hide a page failure. 7 of the 8 passing tests have an `asserterror`, which can swallow it (not examined one by one). Only `ItemLedgerEntryForPurchase` is a clean pass. So between **1 and 8 of the 164 decided tests** did not open a page: **0.6% to 4.9%**.
- Controls held: all 3 pilots read `opened`; no plain control showed a page failure.
- **Recovery:** BankDeposits and VAT Group Management have no passing reach test, so admitting the "did not open" set recovers none of their tests or their TestPage-only mutants. Intrastat recovers at most 8 of its 84 refused tests; it has no finished v3 report, so its mutants are not priced.

**Answer: the helper-reach rule is right.** At least 95% of decided reach tests really open a page. A narrower rule would recover almost nothing and would add risk.

**Recommendation for the owner:**
1. **Do not build a narrower reach rule.** The 40-44% of refusals that come through a helper are real page uses.
2. Of R908's steps above, the labelled v3 hybrid (step 4) and re-pricing a routed path (step 5) are what is left. A page-heavy Microsoft suite needs one of them to be measured at all. Which, if either, is the owner's call.

**Found on the way, for separate items if the owner wants them:**
- **The reader misses pages reached through dependency code.** R-882's 3 ServiceDeclaration `NotSupportedException` failures, "cause not found" in R-882, are page opens: `ShowItemChargeAssgnt` (Base Application) and `LookupRelatedNoSeries` (Business Foundation). They were not refused, because the reader scans the test app's own source. On Linux BC they failed fast. On a Windows server such a test could hang.
- **The Linux page failure is not named in reports.** LethAL's text for it is the Windows one, so on Linux such a test reads as an ordinary failure.

## Step 4, the labelled v3 hybrid: built, measured empty, parked (coord R-911, 2026-11-10)

**Parked by the owner, 2026-11-10. Not merged.** The code is on branch `lethal/r911`, head `dcfd7baa04`, kept pushed as is.

**What it is.** `lethal run --backend bcdev --v3-verdicts <v3 report>` joins a finished al-runner v3 report of the same source and tests. Under the owner's ruling it shows v3's KILL only, on a BC `no-coverage` row whose only covering tests BC refused (TestPage), labelled non-authoritative. The row's verdict, the counts and the score never move. A report that cannot be shown to describe the same mutants refuses the run by name. Only a v3 report run with `--no-client` is accepted, so both sides ran the non-GUI branch. Plan, reviews and rulings: `/coord/handoff/R-911/plan.md`. Pre-commitment: `docs/superpowers/specs/2026-11-10-r911-v3-verdicts-precommitment.md` (amendment 1 swapped BankDeposits for VAT Group Management).

**Measured live.** bc5 (throwaway BC 28.4 W1), al-runner edge-3138effad with `noClient: true`, one source tree per app for both legs. Evidence: `/coord/handoff/R-911/` (`bc-*.report.json`, `v3-*.report.json`, `check.txt`).

- All 8 pre-committed properties pass on both apps. Two are proven: the join is accepted, and an event replay without the join gives identical verdicts, counts and score. The counts add up exactly. The four properties about shown kills hold only because there are none. They are proven by the unit and integration tests, not by live data.
- **Why it is empty:**
  - **PaymentPractices:** every eligible mutant survives on v3. An earlier GUI-branch v3 run had 2 kills there, and under `--no-client` they survive too.
  - **VAT Group Management:** 61 of the 64 tests BC refuses did not pass on v3 under `--no-client`, so they show nothing.
  - **BankDeposits:** no test passed on v3 under `--no-client` (70 not run, 5 failed), so the join refuses it. The not-run causes are `CurrentClientType`, request pages with a handler, and `Page.Run` with a record, which al-runner does not pin without a client.

**The three options the owner was given:**
1. Land it as is: correct, and it costs nothing when unused.
2. Park it until al-runner pins more no-client behaviour, keeping the branch. **Chosen.**
3. Accept GUI-branch v3 reports with a stronger caveat. That would give PaymentPractices its 2 kills, against the comparability rule.

**Revisit when** al-runner pins, under `--no-client`, `CurrentClientType`, report request pages with a handler, and `Page.Run` with a record. Those are the main reasons the refused tests do not run on v3. Then re-run the v3 leg (`/coord/handoff/R-911/run-v3.sh`) and the join, and check the kill count before reviving the branch.
