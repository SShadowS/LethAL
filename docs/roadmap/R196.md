title: "Deletion and value operators make a loop infinite when they hit its exit flag, and unlike `negate-conditional` on `until X.Next() = 0` nothing refuses or marks the site"
status: "open — filed 2026-09-02 from the first DO 29 run. Not scheduled"

**Measured.** Two genuine hangs in one codeunit, both in the same procedure and both at the loop's
exit flag: `remove-assignment` on the assignment that sets the flag (the operator identified it as
*"removal of the loop-exit flag assignment on line 76"*), and a twin at line 107. Each cost the
180 s budget, an `in-flight-unknown` quarantine, and a [[R192]] resume, because
`--stop-hung-sessions` was off (the skill said not to pass it unasked; that advice is now changed).

**The rule already exists for one operator.** [[R164]] rules that a hang-capable site must not
enter a scored gate, and `negate-conditional` refuses `until X.Next() = 0` on that ruling (the R175
re-run measured four such refusals on one codeunit). `remove-assignment`, `flip-boolean-literal`,
`swap-additive` and `shift-integer` can all produce the same hang on a counter or flag that a
`while`/`until` condition reads, and none of them looks.

**What would close it.** A shared classifier: is the assigned variable (or the literal's enclosing
assignment target) read by the condition of an enclosing or following loop in the same procedure?
If so, either refuse the site with a named refusal (the R164 direction) or emit the mutant tagged
`hang-capable` so the orchestrator applies the stop hook unconditionally and the report can say
why a `timeout-killed` is not a test finding. The second keeps the mutant, which is the more
honest answer: a test that fails to notice an infinite loop is a real gap, and BC's own session
stop makes it scoreable. Measure the claim rate on the reference corpus first; a classifier that
refuses every assignment inside a loop body is too broad to ship.
