**al-runner shipped 2.1.0.0, and `itest:alrunner` went from 3 killed / 13 survived / 0 no-coverage
to 0 / 0 / 0 with `baselineGreen=false`.** Measured 2026-08-07, immediately after the tool
auto-updated itself between two runs in one session.

Cause, from al-runner's own output — not inferred:

```
[bc] no --bc-version given — selecting BC 28.1.49838.50794, the exact build this binary was
     compiled against. Override with --bc-version.
BC runtime apps are not available as R2R packages — only symbol/dev packages were found.
    'Microsoft System Application' v28.0.46665.47126  →  fixtures/sandbox-tests/.alpackages/…
```

The fixture's `.alpackages` carry **28.0.46665.47126** symbol-only packages. 2.0.1.0 was compiled
against a BC build those satisfied; 2.1.0.0 is compiled against **28.1.49838.50794** and, with no
`--bc-version` given, selects that one — for which the fixture has no runtime (R2R) packages at all.
al-runner then refuses, correctly and loudly, naming `al-runner provision` as the fix.

**Three things this measurement establishes.**

1. **Not a LethAL defect, and proved rather than assumed.** Downgrading the global tool with
   `dotnet tool update --global MSDyn365BC.AL.Runner --version 2.0.1 --allow-downgrade` and
   re-running the gate returns **3 / 13 / 0, PASS**, on an otherwise untouched tree. The difference
   is entirely the upstream release.
2. **The gate's first line is what made this a five-minute diagnosis** instead of a hunt through a
   session's worth of unrelated changes. `al-runner build under test: al-runner v2.1.0.0` is
   printed before anything else, exactly so a difference gets attributed to the build before it gets
   attributed to us. It worked.
3. **R100's fix carried the diagnosis intact.** Every mutant's note reads
   `no green baseline tests — all 2 failed with the same message: …` followed by al-runner's whole
   provisioning paragraph including `al-runner provision`. Before R100 this would have read
   "your test suite is broken".

**The gate is currently pinned to 2.0.1.0 by a global `dotnet tool` downgrade.** That pin lives on
one machine and nothing in this repo records or enforces it — a fresh checkout, or the next
auto-update, gets 2.1.0.0 and a red gate with no explanation. That is the actual gap.

**Options, none of them taken yet.**

- **Provision for the new build** (`al-runner provision`, or the fixture's `.alpackages` refreshed
  to 28.1) and re-freeze the baseline against 2.1.0.0. Correct long-term; costs a large download and
  a re-measured baseline, and the frozen figures must be re-confirmed rather than assumed to carry.
- **Pass `--bc-version 28.0.46665.47126`** from `buildAlRunnerArgv` so the runner's default no longer
  moves under us. Cheap and makes the gate reproducible, but pins LethAL's own fixture to a BC
  version that will itself age.
- **Record the tool version the gate requires** somewhere the gate itself asserts, so an unpinned
  machine fails with "you are on 2.1.0.0, this baseline was measured on 2.0.1.0" instead of 0/0/0.
  Note R123's contract probe did NOT catch this: the wire contract did not change, the BC build
  selection did.
