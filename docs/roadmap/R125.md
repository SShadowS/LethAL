**al-runner shipped 2.1.0.0, and `itest:alrunner` went from 3 killed / 13 survived / 0 no-coverage
to 0 / 0 / 0 with `baselineGreen=false`.** Measured 2026-08-07, immediately after the tool
auto-updated itself between two runs in one session.

Cause, from al-runner's own output — not inferred:

```
[bc] no --bc-version given — selecting BC 28.1.49838.50794, the exact build this binary was
     compiled against. Override with --bc-version.
BC runtime apps are not available as R2R packages — only symbol/dev packages were found.
    'Microsoft System Application' v28.0.46665.47126  →  fixtures/sandbox-tests/.alpackages/…
```

The fixture's `.alpackages` carry **28.0.46665.47126** symbol-only packages. 2.0.1.0 was compiled
against a BC build those satisfied; 2.1.0.0 is compiled against **28.1.49838.50794** and, with no
`--bc-version` given, selects that one — for which the fixture has no runtime (R2R) packages at all.
al-runner then refuses, correctly and loudly, naming `al-runner provision` as the fix.

**Three things this measurement establishes.**

1. **Not a LethAL defect, and proved rather than assumed.** Downgrading the global tool with
   `dotnet tool update --global MSDyn365BC.AL.Runner --version 2.0.1 --allow-downgrade` and
   re-running the gate returns **3 / 13 / 0, PASS**, on an otherwise untouched tree. The difference
   is entirely the upstream release.
2. **The gate's first line is what made this a five-minute diagnosis** instead of a hunt through a
   session's worth of unrelated changes. `al-runner build under test: al-runner v2.1.0.0` is
   printed before anything else, exactly so a difference gets attributed to the build before it gets
   attributed to us. It worked.
3. **R100's fix carried the diagnosis intact.** Every mutant's note reads
   `no green baseline tests — all 2 failed with the same message: …` followed by al-runner's whole
   provisioning paragraph including `al-runner provision`. Before R100 this would have read
   "your test suite is broken".

Filed 2026-08-07 while running the live gates for R110.

---

**FIXED the same day, and the downgrade is reverted — LethAL supports the newest al-runner.**
`buildAlRunnerArgv` now sends `--auto-provision`, placed ahead of the positional bundle dirs.
`itest:alrunner` is **3 killed / 13 survived / 0 no-coverage, `baselineGreen=true`, PASS** on
**al-runner 2.1.0.0**, identical to the frozen baseline, with the global tool back at the latest
version and no pin anywhere.

**Why `--auto-provision` and not the two alternatives**, each of which was tried and measured
first:

- **`al-runner provision <bundle>` is not sufficient on its own.** It puts the ENGINE artifacts
  under the version the BINARY was compiled against (28.1.49838.50794) and the platform R2R apps
  under the version the PROJECT resolves to (28.0.46665.53459) — two different artifact
  directories, neither complete. A plain run afterwards still selected 28.1 and still refused, with
  the same symbol-only message, 16 times in one gate.
- **`--bc-version 28.0.46665.53459` moves the failure rather than fixing it.** The run then selects
  the directory that HAS the platform apps and refuses for the opposite reason: `BC 28.0.46665.53459
  engine artifacts are incomplete`, listing six missing `Microsoft.Dynamics.Nav.*.dll`. It would
  also pin LethAL's own fixture to a BC build that ages.
- **`--auto-provision` resolves the version from the PROJECT** — the version whose symbols the
  project actually carries — and fetches whatever half is missing. It is upstream's own named
  remedy ("or re-run with `--auto-provision`"), so this is adapting to a documented interface rather
  than working around a bug. Artifacts cache per BC version, so the download happens once and every
  later mutant is a no-op.

Placed BEFORE the positional dirs deliberately: bundle dirs are positional and repeatable in v2, and
the contract probe extracts them from the END of the argv it captures — a trailing flag broke that
test, which is the test doing its job.

**The cost this ADDS, stated rather than glossed:** on a machine with a cold artifact cache the
FIRST mutant invocation now triggers the download (~1 GB for a w1 artifact set) *inside* a mutation
run, under that mutant's own timeout budget — so a first run on a fresh machine can lose its first
mutant to a provisioning download rather than to a real verdict. Every later invocation is a no-op.
Provisioning ONCE at session start, before any mutant, is the obvious refinement and is not built
here.

**What this does NOT close:** nothing yet asserts which al-runner version a baseline was measured
against, so a future release that changes VERDICTS (rather than provisioning) still surfaces as a
figure mismatch a reader has to attribute by hand. R123's contract probe did not catch this one —
the wire contract did not change, the BC build selection did — so that gap is real and is the shape
worth watching next.
