**The hub's coverage map emits object-level entries for objects the target does not own, and nothing said so.** Surfaced by R58's per-test differential oracle, which was looking for the opposite failure. `buildCoverageMap`'s object-level fallback fires whenever `AppMethodIndex.lookup` misses AND the object declares no local procedure — and a Base App or test-framework object satisfies both, because it is not in the target's `SymbolReference.json` at all. Measured on `sandbox-data`: the hub attributes `Codeunit:198`, `Codeunit:423`, `Codeunit:2000000002`, `Table:5330`, `Codeunit:130011/130012` (the test framework), `Codeunit:71002` (LethAL's own control app) and nine more to individual tests. Harmless TODAY — no mutant lives in those objects, so no covering set changed on either fixture — but it is `byObject` credit for code the run does not own, which is one manifest-id coincidence away from `coverageFilter`'s object-level fallback returning a non-empty WRONG set, i.e. R29's exact shape. The fenced path does not have it: rows are scoped to `AppMethodIndex.declaredObjects()` before anything is emitted. Fix is the same scope check on the hub path, but it moves hub attribution and so must not ride along inside R58's differential.
