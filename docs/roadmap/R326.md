**Filed by RUST-03 S4.2d (2026-09-29)**, orchestrator ruling. Evidence: AMENDMENTs 8 and 9 in
`docs/superpowers/specs/2026-09-28-rust-03-precommitment.md`; the probe and task reports stay in
the RUST-03 session ledger.

**What was measured.** Lead E is the p5 transient in W8, the whole-BaseApp spec-level identity
capture. It is the p5 phase peak minus the p5 post-GC RSS, where p5 is the manifest-row loop in
`writeInstrumentedProject` (`packages/schemata/src/project.ts`). All figures are from marked W8 runs
on the native parser, 2026-09-29:
- At `ccb3350f`, unchanged: E 4,064 / 4,197 / 5,009 MB (median 4,197; run-to-run spread 945 MB).
- The same tree with `astHash: ""` (the per-mutant `astSubtreeHash` call stubbed out): E 2,367 and
  2,398 MB. The marked whole-run peak also fell by about 2.8 GB (10,673 to about 7,890 MB).
- `cd717f60` hashed in one pre-order walk: fragments encoded into one reusable buffer and fed to
  incremental BLAKE3, flat trees walked by index, so no canonical string, no per-level strings, no
  wrappers. Its output was byte-identical (a 45-literal golden test, zero differences over 1.6 M
  nodes, the identity listing `eeb5e3e2` unchanged). But E was 4,377 MB against 3,879 MB unfixed in
  the same session, and the W8 median peak 12,179 MB against 12,087 MB unfixed. The fix was reverted
  (`fdf15987`), since it saved no memory.

**What this means.** The stub's saving did NOT come from building the canonical string or the node
wrappers. The stub also removed things the fix kept: the hashing library's per-call objects, the
1.69 M stored 64-hex hash strings, and part of the identity-tuple garbage (`astHash` is one element
of each identity key). One of those, or the JSC heap sizing itself to the live data, is the likely
source, but none of them was measured on its own.

**What would close it.** Ablations on a marked W8 run that each remove ONE of those costs while
keeping the others (for example: hash computed but not stored; hash stored but identity key built
without it; digest via a reused hasher), attributing the 1.8 GB, then a fix with its own prediction
if one named cost is large enough. Or a ruling that E is JSC headroom and not worth chasing. W8 is
already under its 16,384 MB ceiling (AMENDMENT 7: median 11,778 MB), so this is a RAM item, not a
crash risk.

**Re-measured 2026-10-24 (R-326), on today's code.** `scripts/r326-w8-memory.ts` is today's W8: a
`generateMutationSet` of BaseApp (`BaseApp/Source/Base Application`, 743,985 specs) then `writeInstrumentedProject`
(708,932 manifest rows), with a full GC and `heapStats()` at each phase boundary and an outside 1 s RSS poll.
**Limits:** it reads at phase boundaries, not at RUST-03's in-loop p5 marker (that harness was scratch, never
committed), and it passes no config preprocessor symbols, so only `app.json`'s own apply.

| | master 20a6923d | with R-326's C1 |
|---|---|---|
| whole-run peak | 11,174 MB | 5,128 MB |
| generation-phase peak | 10,655 MB | 4,879 MB |
| writer-phase peak (the manifest rows; 45 to 53 s) | 5,034 MB | 5,062 MB |

- **The peak is now generation's, not the writer's.** On master it came from `visibleDeclarationText` re-slicing
  whole object texts once per procedure; C1 (one pass, same string) removed about 5.8 GB of it.
- **The writer's whole transient is now about 1.0 to 1.1 GB.** That is below the 1.8 GB this item set out to
  attribute, and it includes everything the writer does, `astSubtreeHash` among it. Evidence:
  `/coord/handoff/R-326/` (`w8-*.json`, `w8-*.rss.tsv`, `w8-*.marks.log`).
