**Filed 2026-10-24 by lethal-preproc during R-728.** Evidence: `/coord/handoff/R-728/measure.md` (bc2 probe
`scripts/r728-probe/`). Related: [[R728]], [[R709]], R31 and R139 (`StaleTestAppError`).

**What was measured.** A target build that removes a procedure two installed dependents call was published through
LethAL's own deployer (`ContainerDeployer.publish`, altool, ForceSync). BC ACCEPTED it, installed the new target, and
left both dependents installed. Their calls then answered HTTP 400: "The object with ID ... does not have a member with
that ID".

**The risk (not yet measured through a run).** Every `lethal run` publishes the instrumented target over the installed
tests app, and publishing the tests app is the user's job. A user who removes or renames a target procedure and runs
before republishing the tests app gets an accepted publish and a tests app that is broken at run time. At the baseline,
each test that calls the removed member would FAIL or error, rather than answer the control app's "expected exactly
one method X, found 0" (the only text `describeStaleTestApp` reads). So `StaleTestAppError` would not fire. Those tests
would drop out of the green set, and every mutant they covered would read `no-coverage`: the silent under-report R31
and R139 exist to prevent.

**To close.**
1. Measure first, through a real test run under a pre-commitment: publish a target through the deployer that removes
   a member a test in the installed tests app calls, run that test's baseline through the control app (RunOneMethod,
   as a run does), and record the exact answer and how `runSession` classifies it.
2. If the baseline would drop the test from the green set without a named refusal, refuse it by name, for example by
   recognising "does not have a member with that ID" in a baseline failure as a stale tests app, with the recovery
   (republish the tests app built from the current source). Build it test-first, with a red test per direction (a
   genuinely failing test must still read as failing, not stale).
