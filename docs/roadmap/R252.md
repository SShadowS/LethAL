**Reported in GitHub issue #9 (side report 1), 2026-09; not reproduced here yet.** After a run with
`coverageMode: "none"`, a `survived` mutant has no `coverageAttribution`. `explain.ts`'s survivor
validation refuses exactly that shape (`is \`survived\` with no coverageAttribution, so whether any
test is measured to have executed it cannot be decided`) and throws `MalformedReportError`, so
`lethal explain` cannot read a report produced by a supported config value.

The refusal is right in spirit: with coverage off, nothing measured which tests executed the mutant.
But the file is not malformed; the answer is known and is "not measured".

**Open question:** should `explain` accept a missing attribution when the report says coverage was
off, and print "coverage not measured" for those survivors, rather than refuse? It would need to
know the run's coverage mode from something the report records on purpose (whether it does today
is part of the question), never inferred from the missing field itself: a missing attribution on a
fenced report is still a real defect and must still refuse. The
attribution values it accepts are `KNOWN_ATTRIBUTIONS`, derived from `ATTRIBUTION_INTERPRETATIONS`.

**To close:** a test that feeds `explain` a `coverageMode: "none"` report with a survivor and no
attribution, plus one that keeps the refusal for the same survivor on a fenced report; red-check both.

**Done 2026-09-30 (a7bd0c55).** Reproduced first: a report built through `runSession` with a
`coverage: "none"` backend had three survivors with no `coverageAttribution`, and
`assertExplainableReport` threw `MalformedReportError` on the first. The report did not record the
coverage mode anywhere (only the `run-configured` event and the fold's statics held it), so the fix
records it on purpose: `SessionReport.coverageMode`, optional, set by `buildReport` from
`BackendCapabilities.coverage`, additive under report v3. `explain` accepts a survivor with no
attribution ONLY when that field is `"none"`, and shows it as `attribution: "not-measured"` with
`COVERAGE_NOT_MEASURED_INTERPRETATION` ("Coverage not measured", neither covered nor uncovered). Any
other mode still refuses as malformed. A report WITHOUT the field, which includes every report
written before this change and the one in GitHub issue #9, still refuses, but the message now says
the report predates `coverageMode` and that a re-run with this LethAL makes it explainable. The new
attribution value changes a published value domain, so under R233 `EXPLAIN_SCHEMA_VERSION` is 8
(`schemas/explain-v8.schema.json`) and v7 is frozen. Tests in `packages/runner/tests/orchestrator.test.ts`
("R252: ...") and `schemas.test.ts`, each red-checked. This answers GitHub issue #9's side report 1.

**Left as is (orchestrator, 2026-09-30).** A coverage-off survivor whose own marker says it was not
reached (`guardReached: false`) reads `reach: "not-decided"`. The only existing state that fits,
`unreached-and-uncovered`, names coverage, which a coverage-off run did not measure; a precise value
would be another explain value change and version bump, not worth it for this case.
