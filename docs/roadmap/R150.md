`explain.ts` exists because an agent consuming a mutation report had to re-derive, by hand and at a
cost of $18.56, a sentence the report could not emit. The projection fixed the meaning problem and
left a size one: its `survivors` array grows with the survivor count and nothing bounds it.

**Measured on a committed report** (`docs/campaign/2026-08-03-do/rung2.report.json`, 473 mutants,
125 survivors):

| Artifact | Size |
|---|---|
| The report | 408 KB |
| `lethal explain` of it | 243 KB |
| ...of which `survivors` | 206 KB |
| `lethal explain --top 15` | 30 KB |

The product refuses unscoped runs above 1,000 mutation sites, so roughly 500 KB of projection is
the ceiling a single run can reach. That is a file many agents cannot hold, and there was no
`--top`, no filter and no summary mode: the only way to bound it was a tool outside LethAL, which
means every consumer needed `jq` in the loop before it could read the output LethAL built for it.

**What shipped.** `--top <n>` keeps at most n survivors, and the output always carries a
`survivorSelection` block: `total`, `shown`, `omitted`, `rankedBy`.

Three decisions inside that are the actual content of this row:

1. **The block is emitted even when nothing was capped.** A field that appears only on truncation
   forces a consumer to infer completeness from an absence, and an absence also means "an older
   build". Reading `total` unconditionally settles it.
2. **A cap must choose, so it ranks.** `rankSurvivors` orders by how much evidence each row
   carries: execution-proven first, then the R116 covered-but-unreached pair, then object-level
   attribution, then rows no signal places a test at. Ties break on file, then line, then
   `mutantCode`, which makes the order TOTAL — the same report and the same cap produce the same
   rows on every machine. Uncapped output is untouched and still in report order, and `rankedBy`
   says which of the two a consumer is holding.
3. **`--top 0` is refused, not clamped.** It reads equally well as "none" and as "all", and a
   projection that picks one would be guessing about completeness.

The cap bounds SURVIVORS only. `notMeasured` is never shortened, and a test asserts that rather
than leaving it to the help text.

Evidence: `packages/runner/src/explain.ts` (`ExplainSurvivorSelection`, `survivorActionabilityRank`,
`rankSurvivors`), `packages/runner/src/cli.ts` (`--top`, help text), and the
`explain — survivorSelection and the cap` block in `packages/runner/tests/explain.test.ts`.
Red-checked both ways: hardcoding `omitted: 0` reddens two tests, and dropping the rank from the
cap reddens three.

No `EXPLAIN_SCHEMA_VERSION` bump: `survivorSelection` is an ADDITIVE field, which that constant's
own doc comment exempts, and a consumer that ignores it is unaffected by it.
