**Found 2026-10-05 by R464's per-site evidence** for the 33 R473 rows that became untagged
(plan `docs/superpowers/plans/2026-10-05-R-464-implicit-record-resolver.md`, section "Evidence for
the 33 untagged rows"). A correctness risk in the UNSAFE direction (under-tagging a platform kill),
already on master.

**What.** `swap-modify-flag` tags `Insert(true)` -> `Insert(false)` with `run-trigger-skipped-insert`
only when `insertSkipCanRaise` (R143) finds the table's `OnInsert` assigning a primary-key field
DIRECTLY. R143 documents the gap as its limit 1: it does not follow calls. Where `OnInsert` fills
the key through a procedure, skipping the trigger can leave the key blank, and a second insert
then raises a duplicate key: exactly the mechanism the tag exists to flag. Such mutants are
untagged.

**Measured rows** (BC.History, each a sole-argument `Rec.Insert(true)` R473 tagged on an
unresolved receiver; R464 resolves the receiver, so `swap-modify-flag` claims it untagged):
- BaseApp `SalesQuote.Page` (two `Rec.Insert(true)` sites): `Sales Header` `OnInsert` -> `InitInsert`
  -> `"No." := NoSeries.GetNextNo(...)`.
- BaseApp `JobCreationWizard.Page`: `Job` `OnInsert` -> `InitJobNo` assigns `"No."`.
- Quality Management `QltyInspectionGenRules.Page`: `Qlty. Inspection Gen. Rule` `OnInsert` ->
  `SetEntryNo` -> `Rec."Entry No." := ... + 1` (the key).
The same gap applies to every receiver master already resolves (for example a
`SalesHeader.Insert(true)` on a declared record variable); not counted yet.

**To close.** Measure first: the 4 rows above plus every resolved-receiver `Insert(true)` on
BaseApp, CDO and the other BC.History apps whose `OnInsert` calls any procedure. The likely fix is
R-452's conservative cut for the skip detectors: any procedure call in `OnInsert` keeps the tag
(over-tagging is R143's accepted direction for a screen). Pre-commit any `itest:tables`
`platformArtifactKills` move. Queued after R464.

**Done (R-476).** `insertSkipCanRaise` now asks R-452's `skipCanRaise(.., "insert")` first: the tag
stays when `OnInsert` holds any call not proven harmless, when a project codeunit subscribes to the
table's insert events, or when a project tableextension declares `OnBeforeInsert`/`OnAfterInsert`.
Only then can R143's direct-assignment proof drop it. The cut also closes R143's limits 2 and 3.

- **Final review** (sol, `/coord/handoff/R-476/sol-review-final.md`; no new under-tag from the
  composition). Its three retained gaps:
  1. `Rec := Seed` in `OnInsert` copies the key and was not read as assigning it. Fixed: a
     whole-record assignment to `Rec`/`xRec` counts, with a red-checked test. Re-measured: totals
     identical (`compare2.txt`), so the shape occurs in no corpus.
  2. A non-key write (or `Init()`) can change a value a later statement raises on. Not a tag case:
     R138 and R452 rule a changed value of the record's own fields an ordinary changed-value kill.
     The module and report prose now say that is a ruling, not a proof.
  3. Without an arm map, a member-level `#if` `OnInsert` is not seen and the tag drops. Production
     always passes the map (`generateMutationSet`); the gap is shared with `Modify`/`Delete` and is
     stated in the module. The measurement ran without one (as R-464's did), the same on both sides.
