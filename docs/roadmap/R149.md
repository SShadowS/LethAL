`al-runner-contract.ts`'s doc comment states the reason the probe is trustworthy:

> this spawns al-runner directly, but through `buildAlRunnerArgv`/`alRunnerEnv`, the SAME argv and
> env the transport sends, **because a probe that blesses a command line nobody runs measures
> nothing.**

R147 makes that sentence half false. Every per-mutant invocation now carries
`--package-cache <the pinned platform-apps directory>` and NO `--auto-provision`, while the probe
still builds its three real invocations with no pin and therefore still sends `--auto-provision`. So
the probe measures one argv and the verdicts come from another, differing by exactly the flag R147
changed.

Two of the five facts make this more than bookkeeping:

- **`compile-failure-not-scorable`** is the fact standing between a project that failed to compile
  and a batch of false SURVIVED verdicts. It is measured under an argv no mutant uses.
- **`unknown-flag-rejected`** is what makes "al-runner still refuses argv it does not understand"
  trustworthy, and it is the fact whose whole test is the exit code.

**Why it was not fixed inside R147.** The probe runs from `cli.ts` BEFORE `runSession`, so before any
provisioning has happened, and therefore before a pin exists. Closing this means either moving the
probe after the provisioning step, giving the probe its own throwaway provisioning, or adding a
second pinned measurement of the two facts above. All three are changes to R123's own design, which
R147's row does not ask for, and smuggling one in is the mistake this repo files rows to avoid.

**What is NOT a fix:** having the probe simply skip when a pin exists. That trades a probe measuring
the wrong argv for no probe at all, which is the weaker of the two.

Cheapest honest step if this is picked up and the full fix is not wanted: have the report SAY that
the contract was measured under `--auto-provision` while the verdicts were produced under
`--package-cache <pin>`, so the two are not silently conflated.

Evidence: the doc comment quoted above, the three `buildAlRunnerArgv` call sites in
`al-runner-contract.ts` (none of which carry a pin), and R147's spec at
`docs/superpowers/specs/2026-08-15-r147-pinned-platform-apps.md` §3, which records the gap rather
than closing it.

---

**The cheapest honest step taken 2026-08-19; the design fix deliberately NOT taken.**

This row named its own fallback: "have the report SAY that the contract was measured under
`--auto-provision` while the verdicts were produced under `--package-cache <pin>`, so the two are not
silently conflated." That is what landed.

`contractSummary` — the one line printed on every al-runner session, whose own doc comment promises
"a run records the contract its verdicts were produced under" — now reads:

```
[lethal] al-runner wire contract: al-runner v2.1.2.0 | version=matches … | banner=false
  | measured-under=--auto-provision (a session that PINS produces its verdicts under --package-cache instead; R149)
```

**Derived, not asserted.** `measuredProvisioning` is read off the argv the probe is about to SEND,
by checking the built array for `--package-cache`, and `buildAlRunnerArgv` makes the pin and
`--auto-provision` mutually exclusive so exactly one is always present. If R123 ever gains a pin, the
line follows without a second edit somewhere else. A test pins that directly, because a constant
that happens to be right today is the failure mode this row is about.

Four tests, red-checked: removing the clause fails three of the four.

**What is still open, and it is the substance.** The two facts that make this more than bookkeeping
are still measured under an argv no mutant sends: `compile-failure-not-scorable`, which stands
between a project that failed to compile and a batch of false survivors, and `unknown-flag-rejected`,
whose whole test is the exit code. Saying so in the summary does not measure them under the right
command line. The three options this row already listed — move the probe after provisioning, give it
its own throwaway provisioning, or add a second pinned measurement — are unchanged, and all three are
changes to R123's design rather than to this line.

**CLOSED 2026-08-20, and the trade-off this row assumed was avoidable.**

The row framed the fix as a choice: move the probe after provisioning, give it its own throwaway
provisioning, or add a second pinned measurement — all three changes to R123's design, and the first
of them gives up the property that makes the probe worth having, which is refusing BEFORE anything is
generated or published.

**Both measurements now happen, so nothing is given up.** `runAlRunnerContractProbe` takes an
optional `platformAppsDir`; `cli.ts` still calls it unpinned before the session and still refuses
early, and `runSession` calls it again with the pin the moment provisioning establishes one,
refusing at the same severity if the contract differs there. The pinned result is emitted as an
`al-runner-contract-pinned` warning carrying `measured-under=--package-cache`, so a reader can see
which argv produced which answer.

`compile-failure-not-scorable` is the reason this was worth a second measurement rather than a note:
it is what stands between a project that failed to compile and a batch of false SURVIVED verdicts,
and until now no run had ever measured it under the flags its own mutants use.

**A correction to this row.** It named `unknown-flag-rejected` as the second fact "measured under an
argv no mutant uses". It is not, and never was: its argv is the binary plus the impossible flag and
nothing else, so it carries no provisioning flag in either direction and R147 could not have touched
it. A test pins that reading so the claim cannot drift back.

**Verification.** Three unit tests drive the probe with a capturing spawn and assert the argv it
BUILDS — `--auto-provision` unpinned, `--package-cache <pin>` pinned with no `--auto-provision`, and
the unknown-flag probe unaffected either way — red-checked by removing the threading. Three more
drive `runSession` with a stub: the pinned summary is emitted and names the pin, a backend with no
al-runner path emits none, and a backend that establishes no pin does not re-measure.

The stub route is not a shortcut. `itest:alrunner` calls `runSession` directly rather than
`runFromCli`, and the result is an EVENT rather than printed output, so a green gate is silent on
this either way — the same blind spot [[R148]] hit. The gate was run regardless and passes **3 / 14 /
0** with the re-measurement in the path, which is what proves it does not break a real session.

**Cost:** one extra probe per pinned al-runner session, roughly 15-25 s against runs measured in
minutes, and it is skipped entirely when no pin was established (the pre-session probe already
measured that session's real argv) and on every non-al-runner backend.
