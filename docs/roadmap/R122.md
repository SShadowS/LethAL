**Two more `error` shapes still record no `cause`, and one of them is mislabelled.** R114 gave the
strand a machine value, keyed at exactly the two sites that write `STRANDED_NOTE_PREFIX` so the new
`cause: "stranded"` and `isStrandedNote` (`packages/runner/src/resume.ts`) describe the same set of
mutants — an equivalence a test now asserts in both directions. That deliberately left two
neighbouring shapes alone, and they are worth naming rather than rediscovering.

**(a) The op-in-flight-never-cleared pair claims `deadline-exceeded`, and it is not one.** Both
branches in `runMutantsOnBackend` that handle `RunMutant` refusing a duplicate claim on an operation
that then never clears — one on the covering run, one on the kill-confirmation rerun — set
`cause = "deadline-exceeded"` and call `quarantineInFlight`. But `deadline-exceeded`'s own
interpretation promises the reader that LethAL's client timer expired and the mutant is over; that is
precisely what these branches CANNOT say, and their own note admits it ("the operation never cleared
— the container may still be executing it"). They quarantine, which is the tell: nothing that knows a
run is finished needs to quarantine a tier. By meaning they are strands. They also inflate
`counts.deadlineExceeded`.

They were left out of R114 because moving them would break the equivalence that makes the fix
trustworthy: they do NOT write `STRANDED_NOTE_PREFIX`, so `cause === "stranded"` and
`isStrandedNote` would stop agreeing, and `--resume` would re-run mutants `explain` calls stranded.
Fixing (a) properly means making those two sites write the strand note as well — which changes what
`--resume` SKIPS, so it needs its own red-check and its own thought about whether skipping them is
right.

**(b) The lost-ack-completed pair records no `cause` at all**, and correctly so far as it goes: those
are the branches where `GetOperationStatus` PROVES the operation completed server-side, the container
is explicitly not stranded, and only the answer was unreadable. That is a third thing — neither "the
budget elapsed" nor "we do not know if it finished" but "it finished and we could not read it" — and
`MutantErrorCause` has no member for it, so `failureNote` is its only account. `lethal explain` says
nothing for these, which is honest but unhelpful: the operator's correct move (re-run just this
mutant; the tier is fine) is knowable and unstated.

Acceptance for either half is the same shape R114 used: an explain projection over a report
containing the outcome must emit a prescription that names what to do, and the machine value must
agree with whatever predicate `--resume` uses to decide re-running. Evidence: read alongside
`docs/roadmap/R114.md` and `ERROR_CAUSE_INTERPRETATIONS` (`packages/runner/src/report.ts`). Filed
2026-08-07.
