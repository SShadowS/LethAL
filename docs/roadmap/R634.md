**Filed 2026-10-22 by lethal-preproc during R-629** (orchestrator ruling). Related: [[R629]], [[R389]],
[[R164]].

**What.** Every hang refusal ([[R164]]: a hang-capable site must never reach a scored run) is decided over ONE
project's files: the session's `projectDir`. An app B that DEPENDS on the target A, is installed on the test
server, and loops in a way that calls one of A's procedures (directly, or through an event A raises that B
subscribes to) is in no hang context. A mutant of that procedure that never returns, or always returns the same
value, then hangs any test that reaches B's loop. The run scores it `timeout-killed`, a false kill.

**How it was found.** R-629 split the 235 nested-copy keys by where the refusing loop lives
(`/coord/handoff/R-629/measure.md`, section "Step 0: where the refusing loop lives"):
- 163 keys are refused by a loop in the parent's own code (bch 157, dc 6). Those cannot run beside the mutated
  copy, because the two apps declare the same objects.
- **72 bch keys are refused by a loop in a SIBLING System Application module whose app.json depends on the key's
  module.** Examples: Azure AD Graph <- Azure AD User Management (28), Azure AD Plan <- Azure AD Licensing (14),
  Record Reference <- Retention Policy (8). 13 of these run the reverse direction (the loop is in a module the
  key's module depends on) and are UNVERIFIED.

Those 72 were closed with R629 as "modular System Application install only", because LethAL's users mutate their
own apps and Microsoft ships System Application as one app. But the SHAPE is real for an ISV app suite: app B
depends on the target A, subscribes to A's events or calls A's procedures in a loop, and is installed on the test
server.

**Price.** Not measured for any customer suite. DC's split today: S = 0, because DC's Integration also depends on
Cloud, the parent. A census can measure it wherever both the dependent's and the target's source are present.

**Why it is not urgent.** No measured corpus has a sibling-reached key outside Microsoft's System Application
modules.

**To close.**
- **Detect the condition.** [[R389]]'s closed-world guard already asks the control app's `DependentCount`, but for
  the TEST app. Ask the same for the TARGET app (bcdev only; al-runner runs only project and test source, so
  dependency code cannot loop there).
- **Act on it.** When the target has installed dependents and their source is not given to the session:
  - warn, naming the dependents and the R164 limit; or
  - refuse by name until a ruling;
  - or accept the dependents' source (a `--dependent-source <dir>` style option) and add their loops to the hang
    context.
- **Test** with a fixture pair, target plus a dependent app whose loop calls a target procedure: the guard fires,
  and with the dependent's source given, the refusal covers the target procedure.

## Closed by ruling (2026-10-22, R-634)

Evidence: `/coord/handoff/R-634/measure.md`, tools in `/coord/handoff/R-634/tools/`. Measured by parse from the cached
dumps.

- **Same-corpus dependents** (app.json graph; every dependency is direct):
  - dc: 2 targets, 9 non-test pairs (mostly DC/Cloud <- Agent, CZ, DemoApp, FR, OnPrem, PL, Toolkit, US);
  - do: 1 (Cloud <- DemoApp, FR, OnPrem);
  - cdo: 1 (the same three).
  Each also has test-app dependents, and those were included.
- **The price: 0.** Each target's hang analysis was rerun with the dependent's files added. That refused **0 more
  deployed keys** on all 25 pairs (dc 11, do 8, cdo 6).
- **The method works:** a positive control on bch (Azure AD Graph <- Azure AD User Management) refused 16.
- **Its limit:** it undercounts a path that runs through a THIRD app.
- **Events:** the hang rules follow event subscribers only in part. R500's one-hop rule follows subscribers in the
  context's own files; R569 to R572 do not. Subscribers to target objects that hold a loop: dc 0, cdo 0, do 4, all
  in DO/Test. Read by parse, each of the 4 steps its own cursor with `Next` and calls no target procedure inside
  the loop, so none can hang.
- **What a detector would cost:** asking `DependentCount` for the target is one call per session, bcdev only.
  R-389's earlier probe on Cronus284 measured it under 1 ms. But the count always includes the test app and its
  older published versions. A "has dependents other than the test app" check therefore needs a new control-app
  action, a version bump, and a republish to bc1-bc3, with every gate re-proven per server.
- **Ruling (orchestrator):**
  - close with the measured price of 0;
  - state the limit in `README.md` (Limits) and `docs/gates/hang.md`;
  - reopen if a future corpus shows a price.

  A warning was rejected, because it would fire on every dc, do and cdo run, each of which has dependents, while
  the measured risk is 0. A `dependentSources` option was rejected, because it is about a day of work for 0
  measured keys.
