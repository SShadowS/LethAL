**A STRANDED mutant records no `cause`, so every consumer keyed on `MutantOutcome.cause` is blind to exactly the case R91 measured.** `orchestrator.ts`'s in-flight-unknown branch (the `quarantineInFlight` at ~3687) writes a rich `failureNote` — `STRANDED_NOTE_PREFIX`, the budget, and the `--mutant-timeout-ms` / `--resume` advice — and then `break`s, never reaching the `cause = "deadline-exceeded"` assignment ~45 lines below in a different branch. So the outcome ships with `cause: undefined`. Measured on real campaign data: all three `error` verdicts in `rung1.run2-partial` carry `cause: undefined`. Consequence, found while building `lethal explain` (subsystem B, Task 4): the projection's R91 prescription — *"stranded error, not a verdict — re-run with `--mutant-timeout-ms` raised"* — is keyed on `cause`, which is the correct machine value to key on, and it can therefore NEVER FIRE for a strand. That is this project's signature shape: machinery that runs, reports success, and measures nothing. The prose the operator needs exists, but only inside a free-text `failureNote` that no consumer can key on without regexing prose — which the explain contract explicitly forbids. Fix is one line at the strand site (assign `cause = "deadline-exceeded"`, or a dedicated `"stranded"` member if the two should stay distinguishable — decide which, because `deadline-exceeded` currently means "the budget elapsed and we know the mutant is done", while a strand means "we do not know"). It was deliberately NOT done under subsystem B, because it changes what a run RECORDS and belongs with its own red-check. Acceptance: an explain projection over a report containing a strand must emit the R91 prescription — the property it cannot have today. Filed 2026-08-06.
