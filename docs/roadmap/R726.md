**Found 2026-10-24 (R-724 part 2).** CI run 40105067954 (attempt 1, Windows `check`) failed 27 tests, all in
`packages/runner/tests/resume.test.ts` (R389 16, R512 8, R514 3). Each said `this test timed out after 5000ms`. The
rerun passed. Linux passed. No lock or EBUSY line was found.

**Measured shape (not "a slow runner").**
- A single-process async-I/O stall of about 130 s, starting at D1 (run mode). One test passed at 5002 ms, and the
  recovery test took 2427 ms.
- Other test files ran at normal speed. The extra wall time (205 s against 113 s on the rerun) is that one worker's tail.
- The same family as R449 (SQLite-heavy tests timing out at the 5 s default on the Windows job only).
- Locally the slowest test in the file takes under 0.1 s (244 tests in about 5 s). Verify keeps bun's 5 s default on
  Windows, because `/proc/pressure` cannot be read there.

**Mitigation, not a fix.**
- `resume.test.ts` sets `setDefaultTimeout(30_000)`, with a comment citing this item. Verify's global default is unchanged.
  This turns about 27 failures into about 4 for a stall like that one, and runs the file near the 180 s watchdog.
- `makeProject` and `runSession` in that file log a phase that takes over 1 s to stderr.
- `scripts/verify.ts` (`scanFailures`, used by `testStep`) prints each failing test's error text under its `(fail)`
  line on the console (the first 20 failures, 12 lines each, each line cut to 300 characters). It reads bun's real shape: an
  assertion error comes before the `(fail)` line and `^ this test timed out after` comes after it. For a failing
  test's file it also prints that file's passes over 1 s. `scripts/verify.test.ts` pins it.

**Still open.** Why one worker's async I/O stalled for about 130 s on the Windows runner. The next occurrence will now
name the failing tests, the slow phase and the slow neighbours in the CI console. The same family (one process
stalling, unexplained) includes [[R616]]'s 05:33Z outliers on Linux, tracked here by ruling (orchestrator, 2026-10-25).

## 2026-10-24, second occurrence (coord task R-726)

**The second run.** CI run 40133236973 (attempt 1, Windows `check`) failed 6 tests in
`scripts/corpus-snapshot.test.ts` at the 5000 ms default. The log shows one test's `git rev-parse` (through `gitIn`,
`Bun.spawnSync`) failing with an empty stderr in the middle of the stall, and other tests passing slowly (2 to 4.6 s).
The rerun passed. Linux passed.

**What the two files share.** Heavy file I/O in verify's per-run temp folder on the Windows runner: `resume.test.ts`
writes project files there, `corpus-snapshot.test.ts` builds git repos there. The resume stall involved no process
spawn (that file spawns nothing), though the corpus-snapshot failure did hit one; the two may differ in detail. Scanning
of the new temp files (for example by antivirus) is a plausible shared cause. It is NOT proven. The stall hit one test
worker of the job's four (`LETHAL_VERIFY_PARALLEL: 4`).

**Mitigation, now shared.** `testTimeout` in `scripts/verify.ts` returns 60000 ms on Windows CI (platform and CI flag are
now parameters), with the receipt line `per-test timeout: 60000 ms (Windows CI, R726: single-worker I/O stalls on the
runner)`. A stall of about 130 s now fails about 2 tests instead of 27. The 180 s per-file watchdog is unchanged, and the
Linux pressure rule and the local Windows default (5 s) are unchanged. `resume.test.ts`'s own
`setDefaultTimeout(30_000)` is removed, because the shared rule covers it. Its slow-phase logging stays.

**What it costs.** A hanging test now fails after 60 s instead of 5 s. Three hanging tests in one file reach the 180 s
per-file watchdog, which kills the file and names the file rather than the tests; the 900 s run limit caps a
widespread hang. Every path still fails loudly.

**Not covered:** about 20 tests that pass their own explicit timeout below 60 s (for example 2 s, 15 s, 30 s) keep it,
since a test's own timeout wins over `--timeout`. They stay exposed to the same stall.

**Build review fix.** `testTimeout`'s `platform` and `ci` parameters have no defaults: with defaults, three older tests
read the real runner and failed only on Windows CI (reproduced by spoofing `process.platform`).
