**al-runner v2 makes BC artifacts a hard local prerequisite, and rejects a symbols-only `.alpackages`.** v1 compiled against symbols and stubbed the rest, so `--backend al-runner` needed nothing but the binary. v2 links real MS DLLs: it needs a service-tier artifact set locally (measured: 500 DLLs / 335 MB for 28.1.49838.50794) and **code-bearing** MS platform apps for any project that actually depends on them. It never downloads silently — `al-runner provision` or `--auto-provision` is an explicit step. Measured 2026-08-05: pointing `--package-cache` at `fixtures/sandbox-app/.alpackages` aborts with a provisioning-gap message and exit 2, because those MS apps are symbols-only; the same is true of a bccontainerhelper `Applications.<country>` folder, since v2 pulls platform apps from the w1 artifact's `Extensions/`. Our own fixture happens to resolve 0 dependencies and runs without any cache, so the fixture gates will NOT surface this — a real project will, on its first run. Whatever we ship must say which artifacts are missing and name the provisioning command, not fail as "al-runner not runnable". One upstream defect on that path is reported: `DownloadArtifacts platform-apps <version>` for a version with no CDN artifact dies with an unhandled `HttpRequestException` 404 and a raw stack trace instead of a named failure ([#1659](https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/1659)) — reachable by following the runner's own provisioning-gap message with the version stamped on a real project's `.alpackages`.

---

**CLOSED 2026-08-07, and the row's prediction was exactly right.** Reproduced by pointing a real
session's `--package-cache` at `fixtures/sandbox-app/.alpackages`, which holds symbol-only Microsoft
apps like every real project's does: **all 16 mutants came back `error note=no green baseline
tests`, `baselineGreen=false`, caveat `baseline-red`** — and al-runner's own message, which names
every missing app and gives `al-runner provision` as the fix, was gone entirely. The row asked that
we "say which artifacts are missing and name the provisioning command, not fail as 'al-runner not
runnable'"; what actually happened was worse than that, because the failure blamed the target's
TESTS.

The fix is `noGreenBaselineNote` (`orchestrator.ts`) and it is deliberately NOT an al-runner
detector — no prose match, because a message-shape rule is an English-only rule upstream can reword
in a day. It is structural: when not one baseline test passed, quote what they said. Any backend,
any cause.

**Two things this does NOT do**, so nobody reads the row as closing more than it did:

- The artifact prerequisite itself is unchanged and is upstream's design. v2 still needs a
  service-tier artifact set locally (500 DLLs / 335 MB for 28.1.49838.50794) and still rejects a
  symbols-only cache. We surface it; we do not remove it.
- Nothing auto-provisions. `--auto-provision` and `al-runner provision` exist and are now NAMED in
  the failure, which is the right division: downloading 335 MB is the operator's call, not a side
  effect of a mutation run.

The upstream 404 defect this row also mentions ([#1659](https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/1659), `DownloadArtifacts platform-apps` dying with an unhandled `HttpRequestException` for a version with no CDN artifact) is untouched and still reported.
