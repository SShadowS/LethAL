**`buildTypeTable` truncates every subtype, so "same type" is wrong for exactly the types where it matters.** `extractType` (`packages/engine/src/semantic/types.ts`) keeps only the first whitespace-delimited token of a declaration, so `Record "Sales Header"` and `Record "Purchase Header"` both answer `Record` — and so do two different `Codeunit`s, two `List of [...]`s, two `Option`s, two `Enum`s. **Measured while counting R82** (`scripts/census-swap-call-arguments.ts`, `do-rel2/Cloud`): of 893 call sites whose arguments the table calls same-typed, **135 (15.1%) are not** — 118 `Record`, 9 `Codeunit`, 4 `List`, 2 `Option`, 2 `Enum`. An operator that trusted the answer would emit an artifact that does not compile at those sites, and the failure would arrive as an `AlcCompileError` on a full project instead of as a wrong mutant, i.e. after the expensive part. **Not a live defect today, and that is the only reason this is a row rather than a fix:** `ctx.types` has NO consumer in the shipped pipeline — no operator, no analysis reads it, only its own unit tests do. So it is a precondition of the first operator that does, which is R82. The fix is the declaration text the symbol table already holds (`VarSymbol.typeText` is the FULL text; the census resolves it by walking out from the identifier, which also avoids `resolveIdentifierType`'s object-iteration scoping), plus a decision on what "same type" means for `Label` (two labels with different constant text ARE the same type — the census collapses them deliberately) and for `Code[20]` vs `Code[10]` (the census keeps them distinct, which is conservative but rejects safe swaps). Evidence: `docs/measurements/README.md` §R82.
