**Found during R-321 (2026-09-29).** Seen on two full-suite runs in the lane-code worktree, on the
same machine, each time with the file passing 51 of 51 when run on its own:
- the test "each verb ANNOUNCES exactly which committed paths it verified" timed out at 5,000 ms;
- the test "`compare` runs COMPARE against the baseline `freeze` just committed" timed out at
  5,011 ms, and its later `run("compare", ...)` then read an empty output (`Received: ""`), reported
  as an unhandled error between tests.

Two more full runs in the same session each had one failure that passed on a rerun, but the test's
name was not captured, so they are not counted here.

**Why it happens (lead, not measured).** Both tests spawn `lethal campaign` subprocesses and real
`git` against a temp directory. Under a full suite (229 files, about 4,400 tests, 3 to 5 minutes)
the machine is loaded, and a spawn-heavy test can pass 5 s. The file already knows this for its
hooks: `HOOK_TIMEOUT_MS` is 60,000 because a cold CI runner once took longer than 5 s
(CI 32075875426). The TESTS in the same file still run on Bun's 5 s default.

**Why it matters.** A full-suite failure that passes on rerun trains people to rerun and move on,
which is how a real failure gets waved through.

**What would close it.** Give the spawning tests the same generous per-test timeout the hooks
already have (the reason in `HOOK_TIMEOUT_MS`'s comment applies to them too), then confirm with
several full-suite runs that the file no longer fails; or show a different cause.

**Closed 2026-09-29 (R-335, 31d95e8a).** Every test in `campaign-subcommands.test.ts` that spawns a
subprocess, directly, through `deps.git`, or through the `run` CLI helper, now carries
`TEST_TIMEOUT_MS` (a sibling constant reusing `HOOK_TIMEOUT_MS`'s value and reasoning for tests
rather than only hooks): 40 of the file's 51 tests. The other 11 are left on Bun's default, either
because they never reach a git call (a blank or absolute path, an invalid `--stage`, an unreadable
manifest, or a missing committed baseline all refuse before any spawn) or because they inject a fake
`GitRunner`. Swept the rest of `packages/*/tests` and `scripts/**/*.test.ts` for the same shape and
fixed 8 more files the same way, each with its own local `SPAWN_TEST_TIMEOUT_MS`:
`campaign-fence.test.ts` (2 tests), `cli-error-rendering.test.ts` (5), `cli.test.ts` (2),
`schemas.test.ts` (1), `native-binding.test.ts` (1), `parser-equivalence.test.ts` (1), and
`redact-campaign-report.test.ts` (8). Files that already set a per-file or per-test timeout
(`agent-contract.test.ts`'s two `runCli` tests, `changed-since-git.test.ts`'s file-level
`setDefaultTimeout(60_000)`, and the opt-in `grammar-crosscheck.test.ts` /
`probe-grammar-crosscheck.test.ts` legs) were left alone. `scripts/importable-scripts.test.ts` spawns
`git ls-files` only inside its `describe` body, during collection rather than inside a `test()`, so
it is not subject to this failure mode and needed no change.

Proved under load: `bun test packages/runner/tests/campaign-subcommands.test.ts` run 3 times
concurrently with a full `bun test` in the background, 51/51 passing every time (64.16 s, 82.47 s,
74.57 s of wall time for the whole file; slow because the machine was loaded, which is the point,
and still well inside each test's own 60 s ceiling). The full suite itself finished clean once the
concurrent runs settled: 4371 pass, 7 skip, 0 fail, 4378 tests across 229 files.
