**The sequence, at either grain.** A test exceeds its budget (2 × baseline, floor 180 s) and the
watchdog fires the stop. `TryStopHungRun`/`TryStopHungRunAt` takes the lease lock; the op marker
is still active (single grain) or the progress row still reads `running` for that method (R198),
because the test's last statement has returned but the tail after it has not committed: the
platform's `PlatformAfterTestRun` persisting the result, `RunAllTests` returning, and (today) the
whole of `TestResultsToJSON` plus phase 3. The stop is accepted, `StopSession` lands at the
session's next database call (E11 of `scripts/r198-group-runner-probe/`), the held request
answers 408 naming the AL `StopSession` call, and `run-mutant-transport.ts` scores `timeout`,
which the orchestrator records `timeout-killed` with the test as `killingTest`. The test passed.

**Why it is not a rule violation and still wrong.** Under R53's rule a run that exceeded its
budget IS a timeout, whether or not it would have passed a moment later; the design accepts that
at the budget edge. What this row records is that the acceptance covers the tail AFTER the test
passed, not only the test itself, so a slow-but-finite test (a `shift-integer` on a loop bound,
say) that finishes just after its budget can be recorded as killed by a test it satisfied. The tail
is not only the platform's own persistence (tens of ms, since `StopSession` lands at the next
database call, E11): a test whose last statements are pure CPU work is cancelled only after about
3.9 s (probe E8, two runs on Cronus283), so its body can finish up to that long after the stop was
sent (R-204's trace, 2026-10-24; the earlier "50 ms" here understated it). R198's `PROGRESS_BETWEEN_FIRST` puts the `between` write
immediately after `RunAllTests` returns, which is the smallest tail available from AL (the
platform's own persistence is inside `RunAllTests`), and its per-method refusal means a stop for
method k can never land on k+1; but a survivor with 112 covering tests has 112 such tails in one
op where today's single-method run has one per call.

**What would narrow it, and what would not.** After the 408 and before scoring `timeout`, read
`GetOperationStatus` once and refuse the `timeout` (score `in-flight-unknown`) when
`opProgress.lastCompletedIndex >= stopDecision.methodIndex`: a `between` write that committed
before the session died proves the method finished. It is a narrowing, not a proof: a session
killed inside the blocked `between` write rolls it back and the row still reads `k - 1`. Nothing
in hand proves "the test passed" from outside the session once the session is dead. Not
scheduled; the R198 build applies the narrowing and states the residue.

## Closed 2026-10-24 as narrowed (coord task R-204, orchestrator ruling)

Traced by code on master `995ced2b`, control app 1.0.0.23 (`/coord/handoff/R-204/r204-trace.md`).

**Narrowed three times.**
1. R198 (grouped): the `between` write right after `RunAllTests`, and a stop for method k never lands
   on k+1.
2. R-204b Part A (single, `9dc63a03`): `completedBeforeStop` reads the progress row after the 408 and
   scores `stopped-after-completion` (an `error`) when the method's completion committed first.
3. R577's kill reproduction, on for bcdev since R582: a `timeout-killed` needs a SECOND mutated run to
   time out too. A first run that only hit the window and then passes on the re-run is
   `kill-not-reproduced` (a cost, not a kill). A false `timeout-killed` needs both mutated runs in the
   window, a mutant that slows the test to within the window of its budget, and an unmutated confirm
   that finishes in at most half the budget: roughly the square of an unmeasured per-run chance.

**What remains.** W1 (the stop holds the progress lock, or lands on `ProgressBetween`'s database call
before its commit, so the `between` write rolls back) and W2 (inside the platform, after the test
returns and before its result commits), both reachable today; and the CPU-only tail above (up to
about 3.9 s). No client-side signal tells them from a real hang stopped mid-test: the progress row has
no finish time or result, no kept answer is written, the client's duration is the budget by
construction, BC's 408 text names only a session and correlation id, and a 408 carries no rows. A
client-only rule would also refuse the hang gate's real `timeout-killed` mutants. The only evidence is
on the server, the platform's committed test result (Part B), which needs a control-app change and
cannot see W2. Both that and the measurement that would size the residual move to [[R703]], after
the release.
