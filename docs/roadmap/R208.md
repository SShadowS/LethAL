**What is missing.** `docs/superpowers/specs/2026-09-03-r198-run-mutant-loop.md` §7 and §8 pin two
forced-chunk campaigns, a survivor at `groupedCalls = ceil(n/2)` and a kill at `ceil(k/2)`, as if
a gate ran them. No itest mentions `max-methods-per-call` or `maxMethodsPerCall`; the only hits
are `packages/runner/src/cli.ts` and unit tests, and R198's own roadmap row describes the chunked
proof as a differential UNIT test. Every live gate runs each mutant's covering tests in ONE call.

**Why it matters more under R206.** The warm confirmation replays the PREFIX OF THE CALL that
produced the failure (`chunkPrefix`), never the prefix of `ordered`. Unchunked, the two are the
same list, so every live gate exercises a case where confusing them changes nothing. Chunked, a
killer at ordered position 5 under `--max-methods-per-call 2` is `killPosition 1` of chunk 3 and
its replay is one method; an implementation that replayed `ordered[0..5]` would run four extra
methods, and a session-scoped state populated by chunk 1 or 2 would not be present in the real
chunk 3 but would be in the wrong replay, so the two can disagree on `unstable` versus `killed`.
Also, under R206 a replay is a `RunMutantMany` call and is counted in `groupedCalls`, so the kill
campaign's number would be `ceil(k/2) + 1` whenever the killer lands at chunk position > 1; the
numbers R198 pinned were never right for a build that confirms warm kills.

**To close.** A campaign on `fixtures/sandbox-data` with `--max-methods-per-call 2` (the fixture
has kills at ordered positions up to 5, run 334), pre-committing per mutant: `killPosition` within
its chunk, the replay's method list (readable from the store as the `mutantCode: null`,
`op_kind: many` rows written for that mutant), `groupedCalls`, and `warmKills`. Cost is one more
tables run per gate (about four minutes), or a narrowed `--only` on the one codeunit whose
mutants have five covering tests. Until then the chunked warm path is unit-covered only, and
R206's spec says so in §6.
