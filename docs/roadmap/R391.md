**What.** An identity tuple (object, member, operator, subtree hash) has no file and no namespace in
it. Twins, meaning mutants with the same tuple, are told apart by an ordinal numbered over the
manifest (`identityOrdinalsOf`, called from `writeInstrumentedProject` in
`packages/schemata/src/project.ts`). So two files in different namespaces that each declare a
codeunit named `Foo` with the same procedure and the same body produce twins that share a tuple.
Removing one site in the first file renumbers the twin in the second file.

**The two-file shape.** Two files in different namespaces declare codeunit `Foo`, each with
`P(): Integer` and `exit(1)`. The first file wraps its `exit(1)` in `#if FLAG`; the second does not.
Record the first file's mutant as survived under `[FLAG]`. Change only the first file's condition to
`#if OTHER` and run again under `[FLAG]`. That site disappears, and the unchanged second-file mutant
takes ordinal zero. `--skip-known-survivors` (`filterHistory` in
`packages/runner/src/selection.ts`) then skips it on the other file's verdict.

**Why it matters.**
- This is already true on master: an ordinary edit that deletes a site renumbers a cross-file twin.
- R-214 adds one more trigger, a changed `#if` condition or a changed symbol set, because a site
  that a build compiles out is no longer generated.
- It is a sibling of R374 (twins across batches). R-307 fixes R374 by numbering once per run, which
  does not cover twins in different files, because they are in one run already.

**Evidence.** Reviewer's finding 1 in `H:/lethal-coord/reviews/R-214-001/review-r1.md`, checked
against `project.ts` and the history lookup in `store.ts`.

**What would close it.** Either put the file (or the namespace plus object id) into the identity
tuple, which is an IDENTITY_SCHEME bump, or have history check that the twin's file is unchanged
before it carries a verdict. Pin it with the two-file transition above: the second file's mutant
must run, not be skipped.

**Closed (baaf290b, R-391; plan and reviews in the coord handoff `R-391`).** Neither form above
was taken as written. The key keeps its shape (no IDENTITY_SCHEME bump, no baseline moves), and
every carry passes ONE rule, `carryRecord` (`selection.ts`), inside `filterHistory` (history) and
`carriedVerdictFor` (resume, and so `batchCarriesEntirely` and `replayCarriedBatch`):
1. **Same source:** the recorded run's `generation_source_sha256` (a new `runs` column written by
   `createRun`) equals this session's generation hash. The verdict carries by key, as before:
   identical source gives identical numbering. This holds for an interrupted run too, whose
   `source_sha256` is never written.
2. **Changed or unknown source:** the verdict carries only to a mutant that is the SOLE member of
   its tuple in its file in BOTH runs, and it matches on (tuple, file). The recorded run's twin facts
   are a run fact, `runs.twin_tuples`, written after generation and before any mutant row, never
   counted from rows, which an interrupted run has only partly. NULL (not measured) carries
   nothing. `[]` (measured, no twins) lets singletons carry.
3. **Otherwise** the mutant runs. Refused key matches are counted in one session warning,
   `carry-refused-renumbered`.

Three adversarial reviews shaped it (gpt-6.1-sol's quota was out; a Claude spec-adversary stood in):
- A file-only check let an edit in one file shift a LATER file's twins onto that file's own key: a
  false kill on resume.
- Counting twins within one file by position let a same-file deletion carry a kill.
- Counting twins from rows let an interrupted run's partial rows make a twin look like a singleton.

Each case has a test in `packages/runner/tests/r391-cross-file-twin.test.ts`; the stub backend
kills by the active mutant's file and line, never by deploy order. The tests are: two files and
three twins in history; three twins in the resume kill direction; a same-file removal; partial
rows; a history undercount; a statement moved to another file; controls for a singleton across an
edit, no-edit twins in history, and an interrupted run resumed with no edit (rule 1 via the new
column while `source_sha256` is NULL); NULL columns; NULL against `[]`.

RED-CHECKED:
- counting twins from rows (partial rows and undercount go red);
- key-only (8 of 13 red);
- never rule 1 (both no-edit controls red);
- rule 1 reading `source_sha256` (the interrupted-resume control red);
- tuple without the file (the moved-statement test red).

**The R193 same-file residual R391 was asked about cannot carry a kill.** A same-file deletion
changes the source (no rule 1) and leaves twins in the file in at least the recorded run's facts
(no rule 2), so the remaining twin runs. Residuals that remain, none new (key-only carries both):
- the kind collision: the tuple has the object name, not its kind, so a codeunit "Twin" replaced
  by a table "Twin" in the same file name carries;
- a changed CONTEXT around an unchanged statement, filed as R474.

Stranded skips (which record `error`) stay key-matched, and marks are unchanged.
