**R121's screen shipped with its useful mode untested by any live gate.** The rule is "the failure
text does not begin with `Assert.`", and `SessionReport.assertionScreen.discrimination` reports which
of four things happened: `partial` (the rule separated something), `vacuous` (everything was flagged,
so it separated nothing), `none`, or `no-text`.

Every fixture raised through bare `Error(...)`, so every gate produced `vacuous` or `no-text`, and
the `partial` branch — the only one where a reader is told anything actionable — was proven by unit
tests and by re-scoring the committed 73-kill Document Output corpus, and by no live run.

## What landed

Option (1) from this row's own list, and only option (1): **a fixture arm that produces both kinds of
failure text**. Option (2) (a second real project with a hand-classified kill corpus) is not
something a session can produce.

**Feasibility was measured before any AL was written** (`scripts/r132-assert-probe/`, published to
Cronus283 and unpublished afterwards), because the row said the whole question was whether the
containers have Microsoft's test libraries and what a dependency costs:

- `Library Assert` 28.0.46665.49944 is installed **Global on both** fixture containers (Cronus283 and
  Cronus281), alongside `Test Runner`, `Any` and the other toolkit apps.
- Its symbols download straight from the container's own dev endpoint, so the dependency costs one
  file in `.alpackages` and one `app.json` entry — no toolkit install.
- The failure text really begins with `Assert.`:
  `Assert.AreEqual failed. Expected:<1> (Integer). Actual:<2> (Integer). probe message.` and
  `Assert.IsTrue failed. probe message`, from `Locked = true` labels that do not localise.

**The arm is a TWIN PAIR** (`codeunit 79318 "Data Assert Ops"`): two procedures of identical shape,
`DoubledLevel` covered by a test raising through `Library Assert.AreEqual` and `TripledLevel` by one
raising through bare `Error(...)`. All four of their mutants are killed, so the verdicts are a
control and the only difference between the two halves is which side of the screen their kills land
on. Both are Integer in and out deliberately: `AreEqual` compares Variants and reports the TYPE it
saw, so a Decimal actual against an Integer expectation would fail on the type rather than the value.

**Which gate hosts it, and what happened to the `vacuous` pin.** The table fixture, because
`fixtures/sandbox-app` is shared with `itest:envtool`, whose environment currently reports `Stopped`
— changing it would move the frozen figures of a gate nobody can re-measure. The tables gate
therefore gives up the `vacuous` assertion it used to carry, and **`itest:bcdev` picks it up**: its
suite is still bare `Error(...)` only. After this wave both states are pinned live, by two gates,
which is more than was pinned before.

## Live evidence

Pre-commitment: `docs/superpowers/specs/2026-08-14-r132-assertion-arm-precommitment.md`, committed
(`8c6cce9`) before any live run, stating all four verdicts, all four SCREEN memberships, and the
bcdev gate's own predicted `vacuous`. **Every prediction matched and none was edited.**

| | predicted | measured |
| --- | --- | --- |
| `DoubledLevel` empty-block | killed, NOT flagged | killed, not flagged |
| `DoubledLevel` return-value | killed, NOT flagged | killed, not flagged |
| `TripledLevel` empty-block | killed, flagged | killed, flagged |
| `TripledLevel` return-value | killed, flagged | killed, flagged |
| tables `discrimination` | `vacuous` -> `partial` | **`partial`** |
| bcdev `discrimination` | `vacuous` (competing: `no-text`) | **`vacuous`** |

Aggregates moved exactly as pre-committed: killed 187 -> **191**, survived **31**, no-coverage **10**,
deployed 228 -> **232**, raw 248 -> **252**, score **191/222**, `platformArtifactKills.killedCount`
**1**, `untargetedTriggerCount` **0**, exactly one baseline failure by name. The re-recorded
`tables.baseline.json` differs by **+28 lines / -0** — four new rows, no pre-existing verdict touched
— and the gate was then run a SECOND, SEPARATE time and passed unchanged. `itest:bcdev` came back
3/10/3 with its new assertion green.

`assertAssertionScreenTwinPair` pins the result BY MUTANT, not by a count: asserting
`discrimination === "partial"` alone would pass if the screen happened to split the fixture somewhere
else entirely.

## What this is NOT

**It is not evidence about the rule's precision.** The 26.1% figure comes from 73 hand-classified
kills on Continia Document Output; a fixture built to produce `partial` proves the pipeline runs and
reports what the unit tests say it reports, and nothing about how often a flagged kill is really
false. This row exists partly to prevent that confusion, and the arm's own AL comments, the design
spec and the gate's comments all say so at the site.

**It does not tune the rule.** No screen code changed in this wave.

One deliberate loose end: the test app's `app.json` description was corrected in place without a
version bump, so the container's published 1.0.0.13 carries the previous wording. Nothing reads that
field — R139's check compares the version and the TEST SET, both of which match — and a republish for
a metadata string was not worth a gate cycle.
