Coord task R-960 (lethal-bugs), from the owner's ruling of 2026-11-13 (CLAUDE.md at master 83902e3c). Related: [[R953]] (the
memory rule), [[R952]] (the FIFO queue), [[R905]] (the slot class).

**What was wrong.** After R953, `heavy-slot.sh` and `corpus-snapshot.ts`'s in-slot guard applied BOTH the memory rule and the
old count rule (two heavy jobs while a BaseApp-class job runs, else three; R642, R905). The count rule refused jobs that fit by
memory: on 2026-11-13 it refused a 0.2 s repro with 8 GiB used of 32, and it queued a module pool build behind it.

**Built.** Where the cgroup names a limit, the memory rule alone decides (`memoryVerdict`, R953): used now + the job's peak + a
4 GiB reserve, and the held slots' declared peaks + the job's peak + the reserve, both under `memory.max`. The two checks are
separate on purpose: `memory.current` already holds what the running jobs use, so summing it with their declared peaks would
count every job twice. The class (`baseapp` or `other`) only sets a job's default peak. The slot files go from three to six
(`SLOTS` in `scripts/corpus-snapshot.ts`, the loop in `scripts/heavy-slot.sh`): a job count remains only as that file-count
ceiling, set high enough not to bind (three capped serve runs, 3 x 8 + 4 = 28 GiB, already fill the memory). On a host with no
cgroup limit the old count verdict still decides, as before R953. The daily al-runner update already decided by memory (R952).
Not changed: `v3-timing.ts`'s own guard (a timing tool; its count also feeds its load figures).
