**Filed by R-297 Task 8 (2026-09-28), consolidating the plan's ruling 6.** Plan:
`docs/superpowers/plans/2026-09-28-R-297-instrumentation-real-corpora.md`, r1 summary:
"`describeObjectKinds` [is] filed, not fixed."

**What is wrong.** `describeObjectKinds` (`packages/schemata/src/compile.ts`) names the object
kind(s) a file declares by reading `root.namedChildren` directly (or `[root]` when `root` is itself a
`*_declaration` node) and keeping the ones ending in `_declaration`. It does not unwrap
`preproc_conditional_object`, the wrapper [[R298]]'s object-container rule and Task 3's
`objectDeclarationsOf` (`packages/engine/src/ast/tree-walks.ts`) already know how to see through. So
for a file whose only object sits inside `#if ... #endif`, `describeObjectKinds` sees the wrapper
node, not the codeunit/table/page inside it: either it reports the wrapper's own kind (which does
not end in `_declaration` the way an object kind does) or, on the `root.namedChildren` path, it
finds nothing ending in `_declaration` and falls back to `"no object declaration (root is
preproc_conditional_object)"` — a wrong answer for a file that, since R298's fix, DOES carry a
real object and DOES instrument.

**Where it shows.** `describeObjectKinds` feeds two report fields in
`packages/runner/src/orchestrator.ts`: `declarativeSites[].kinds` (a page whose only matched sites
are declarative) and `skipped[].kinds` (a file `canCarryMutationSelectorVar` rejects outright). A file
whose SOLE object is wrapped and supported does not reach either path today (`canCarryMutationSelectorVar`
finds it via a recursive search regardless of the wrapper), so the wrong string has not yet been
observed reaching a report. The gap is real for a MIXED file: one wrapped object plus a second,
unsupported one in the same file (the shape [[R299]] already refuses whole, and any future per-file
skip [[R307]] adds), where the reported "kinds" string would name the wrong thing for the reader
trying to tell which object was skipped.

**What would close it.** Route `describeObjectKinds` through `objectDeclarationsOf` instead of reading
`namedChildren` directly, so it reports the object kind(s) actually inside any `preproc_conditional_object`
wrapper, the same way `enclosingObjectDeclaration` and `canCarryMutationSelectorVar` already see
through it. A test with a wrapped-and-unwrapped mix should show the correct kind list before and
after.
