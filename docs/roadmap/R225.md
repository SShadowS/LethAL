**Measured, not inferred.** Cronus284 and Cronus285 were provisioned as dedicated containers for
the autonomous issue orchestrator
(`docs/superpowers/specs/2026-09-13-issue-orchestrator-design.md`), bootstrapped with control app
1.0.0.18 and the fixture apps, and then qualified by running the frozen gates against them.

The first `itest:tables` run against the fresh Cronus285 did this:

```
verdicts: killed=0 survived=0 noCoverage=0 baselineGreen=true score=null
quarantined: {"reason":"baseline test in-flight-unknown running PageActionComputesNonZero"}
AssertionError: expected exactly 1 baseline failure (the TestPage test), got 0
```

The second run, with no change of any kind in between, passed: the full frozen table, 299/63/15
over 377, the expected single named baseline failure, and the per-mutant baseline matching.

## What `in-flight-unknown` means here

It is not a verdict. `BcDevMcpBackend`'s call raced a client-side timer and the timer won, so the
transport cannot distinguish "the mutant hung" from "our timer fired" and refuses to fabricate
either. The comment at that branch says so: *fail safe: report infrastructure, never fabricate a
kill*. That is the right behaviour, and it is why the run scored nothing rather than scoring
wrongly.

`Data Tests.PageActionComputesNonZero` is the one test on this fixture that opens a `TestPage`. On
a warm container the fenced session refuses it quickly and that refusal IS the expected baseline
failure the gate asserts by name. On a cold one it appears to take longer than the client budget.

## What is NOT established

The mechanism. "First page open in a freshly bootstrapped tenant is slow" is a hypothesis
consistent with two observations, and two observations are not a measurement. It could equally be
first-publish warmup, a one-off scheduling artifact, or something specific to this BC 28.4 image.
Isolating it would mean: restart a qualified container and re-run, bootstrap a third container and
run twice more, and time the TestPage call on a cold versus warm tenant directly.

## Why it matters beyond a one-off annoyance

The autonomous orchestrator treats a live leg's result as evidence, and this shape is the worst
kind of non-evidence: it looks like a hard gate failure. An automated flow that read it as one
would either quarantine a perfectly healthy container or, worse, attribute it to the candidate.

The design already has the right home for it, and this row is the measured reason that home
exists: a leg that quarantines on a BASELINE test is `inconclusive`, never a candidate block,
because nothing about the candidate was measured. What this row adds is that **container
qualification must include a discarded warm-up run**, so a fresh container is never qualified or
rejected on its first result.

Neither the warm-up nor the `inconclusive` classification explains the mechanism, and both are
worth having anyway.

## Closed 2026-10-24 by ruling (coord task R-225, lethal-code)

**The call that went cold is no longer made.** Since R-236c (`71b8df1b`), LethAL refuses
`PageActionComputesNonZero` before sending it, because it has a reachable call that may open a TestPage, and
`itest:tables` pins that: the refused list must be exactly that test, by name; the report must name the refusal
(`tests-testpage-refused`); and BC's own TestPage refusal (`tests-testpage-unsupported`) must be ABSENT, which is
what shows the test was never sent. So no baseline call can wait on a cold first TestPage open, on any server.

**Measured on today's servers** (`/coord/handoff/R-225/census.md`): 51 stored `itest:tables` logs on bc1-bc3
from 2026-10-21 to 2026-10-24: 48 PASS, 1 record run (its confirm passed), 2 FAIL. Neither FAIL is this shape:
one is R692's HTTP 500 on a mutant's reproduction (M0232, `/coord/handoff/R-608/live/tables-bc1.log`), the other
a missing launch file in a fresh worktree, so the gate never started. Every first `itest:tables` run after a
server setup or restart passed, including the first bc2 run after R-632b's restart. No log shows a baseline
quarantine that scores nothing.

**Not built:** a setup warm-up or a "server cold, re-run" refusal; with the TestPage call gone there is no cold
first call left to warm or to name. If a fresh server's first run ever quarantines on a baseline call again, the
quarantine already names it (it is never a silent score), and that would be a new item.
