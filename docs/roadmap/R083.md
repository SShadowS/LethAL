**Is `InherentPermissions` a better `PermissionReduce` target than `Permissions`? Unknown, and worth one measurement before anyone assumes either way.** R13 measured that `Permissions` is purely ADDITIVE — it grants indirect rights to code executing in the object (arm A5: BC’s demand moves from `Insert` to `IndirectInsert`), so reducing it is observable only in a session that already lacks the right, which is why `PermissionReduce`’s kill needs the rare permission-lowering test. `InherentPermissions` is a DIFFERENT property and the R13 decision explicitly does not cover it. **What is measured:** Continia Document Output carries **2** occurrences across 554 files, both on CODEUNITS and both `InherentPermissions = X` (zero on tables — consistent with R1’s note), and this repo’s own `fixtures/sandbox-probes` table 79200 carries `InherentPermissions = RIMD`. **What is NOT measured, and must not be assumed:** whether it can REFUSE an operation a SUPER session would otherwise be allowed — the claim that it constrains rather than grants comes from reading the AL compiler’s option list, not from any run, and an unmeasured platform claim written into this file is the exact failure R33 §2 records. Order of work: probe table 79200 through the fenced path with the property reduced and intact, THEN decide. Even a positive result leaves 2 sites on the one project censused, far below the >=13 bar — so this is a question to close cheaply, not a build.
