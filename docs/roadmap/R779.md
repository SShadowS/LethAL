**Filed 2026-10-25 by lethal-bugs during R-762** (item B's timing runs). Related: [[R768]], [[R762]], [[R765]].

**What.** [[R768]] retires the §6 Sleep coverage rule on a build whose pin and whose own session probe both read
`sleep-is-noop` gone: a covering pass under a mutant is then never refused by §6, mutant calls ask for no coverage, and
serve-entries opens no coverage window. Whether that happened in a given run is decided once in the backend's status
check, but nothing prints it: neither `lethal run` nor the D1 gate leg shows it; only leg X reads the backend's getter
(`isSleepRuleRetired()`). So a run's output, receipt or report gives no sign which behaviour applied, and two runs of
the same project on two builds (one pinned gone, one not) can differ in refused-versus-survived rows with nothing in
their output naming why. R765's probe-cache receipt line already shows the pattern to follow.

**To close.** Print one receipt line per v3 session from the status check (beside the probe-cache line), e.g.
`[lethal] al-runner-v3 §6 Sleep rule retired (pin <id> and the session probe read sleep-is-noop gone) (R768)` or
`... §6 Sleep rule applies (<reason>)`; optionally carry it into the status details. A test per direction (retired build
prints "retired"; unpinned or probe defect-present prints "applies" with the reason). No verdict or figure moves.

**Done (2026-10-25, lethal-preproc, coord task R-779).**
- `sleepRuleLine` (`al-runner-v3-pins.ts`) builds the line from the decision `status()` already made
  (`sleepRuleRetiredFor`). So the word "retired" or "applies" cannot disagree with the behaviour; only the reason is
  looked up. The reasons: no pin names this build; the pin reads `sleep-is-noop` something else; the pin reads it gone
  but this session's probe read it otherwise (or did not measure it); or both read it gone.
- `status()` prints it on each call, beside the probe-cache line. A session calls `status()` once (the orchestrator,
  `runnerBuild()` only before the build is known, the parallel queue's one owner backend), so that is one line per
  session. For example
  `[lethal] al-runner-v3 §6 Sleep rule retired (pin edge-dcdf9e821 and this session's probe read sleep-is-noop gone)
  (R768, R779)`. Its details carry `§6 Sleep rule retired|applies (R779)`. No `SessionReport` field.
- Tests in `al-runner-v3-backend.test.ts`:
  - `status()` with the decision true, then false, prints exactly one line with the matching word, and carries it in
    the details;
  - `sleepRuleLine`'s reasons: no pin; pin gone but the probe read otherwise or did not measure; both gone. The fourth
    branch, a pin that reads `sleep-is-noop` something other than gone, has no test: every pin in `V3_BUILD_PINS`
    reads gone today, so no real build reaches it. It changes only the reason text, never the word.
- Red-checked: with no line printed, and with the word inverted, both directions go red.
- No gate figure moves: no leg asserts on stderr lines or on the status details.
