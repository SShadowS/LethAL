[R130](R130.md) recorded that al-runner's `--auto-provision` provisions the platform apps TWICE in
one invocation. Re-measuring it on **al-runner 2.1.2.0** (2026-08-14) found the cost is not one-off:

| invocation, same warm machine, `fixtures/sandbox-app` + `fixtures/sandbox-tests` | wall clock | platform-app downloads |
| --- | --- | --- |
| `--auto-provision` (what LethAL sends today) | **17.0 s** | **2 x 115 MB** |
| same, third consecutive run | 17.0 s | 2 x 115 MB |
| `--package-cache <artifacts>/<build>/platform-apps`, NO `--auto-provision` | **7.1 s** | **0** |
| no flags at all | 1.4 s, FAILS | 0 |

The middle row is the finding. Handed the platform apps it already has, al-runner runs the same two
tests, passes them, and skips both provisioning passes. **Ten seconds and 230 MB per invocation, on
a cache that already holds every byte.**

LethAL invokes the CLI once per (mutant x covering test) on the al-runner backend, so this is paid
on every one of them. `itest:alrunner` is 16 mutants; a real project's run multiplies it out.

**What LethAL would do about it.** Not "drop `--auto-provision`" — R125 measured that the flag is
what makes a cold machine work at all, and removing it is the mistake that row exists to prevent.
The shape is:

1. Provision ONCE per session, which R128 already built.
2. Read the resolved platform-app build out of the runner's own line —
   `[provision] Resolved: 28.0 -> 28.0.46665.53655` — the way R129 already reads
   `[bc] selected BC ...` off stderr. Note this is a DIFFERENT build from the engine build R129
   captures (28.0.x vs 28.1.x), which is the same disagreement R130 recorded between the two
   provisioning passes.
3. For every subsequent mutant invocation, pass `--package-cache <artifacts>/<that build>/platform-apps`
   and no `--auto-provision`.

A side benefit worth as much as the seconds: pinning the directory found at session start makes a
mid-session Microsoft publish unable to move the platform apps under a running campaign. Today the
prefix resolves forward on every invocation, so a run that starts on `…53655` can finish on `…53700`
with no record that it did.

**What has to be measured before it lands**, because this changes the argv that produces every
verdict:

- Does the run still work when the project's declared dependency version differs from the resolved
  platform-app build? The fixture declares `28.0.46665.47126` in `.alpackages` and the runner
  resolved `28.0.46665.53655`; that mismatch is what `--auto-provision` papers over today.
- What happens on a machine with NO artifacts, where step 1 has to provision first — the R125 case.
- `itest:alrunner`, frozen at 3 / 13 / 0, judged per mutant. A change to the argv that produces
  verdicts is exactly the class of change that gate exists for, and the gate PRINTS the al-runner
  build it ran against.

Evidence: `scripts/r126-server-probe/` holds the scratch-fixture setup this was measured in;
transcripts in the R130 row and in `docs/measurements`.

# CLOSED 2026-08-15

## What shipped

`parseAlRunnerPlatformAppsDir` (al-runner-transport.ts) reads the directory and the app count off
al-runner's own COMPLETION sentence, `[provision] Downloaded <N> app(s) ... to <dir>`.
`AlRunnerBackend.provisionOnce` pins it only when three conditions hold, and reports which one
refused when they do not. `runSession` applies the pin to `cfg.backend` and to every worker backend,
and THROWS on a backend that cannot take it. `buildAlRunnerArgv` sends `--package-cache <pin>` and
omits `--auto-provision` exactly when a pin is present, which is the one place the two are made
mutually exclusive. The pin is recorded on `ReportValidity.executionContexts[].platformAppsDir`.

Spec, reviewed by the `spec-adversary` subagent and revised against its ten findings:
`docs/superpowers/specs/2026-08-15-r147-pinned-platform-apps.md`. Live pre-commitment, committed
before the gate ran: `docs/superpowers/specs/2026-08-15-r147-live-precommitment.md`.

## The measurement, re-taken on 2.1.2.0 on 2026-08-15

| invocation, same warm machine, `fixtures/sandbox-app` + `fixtures/sandbox-tests` | wall clock | platform-app downloads | exit |
| --- | --- | --- | --- |
| `--auto-provision` (what LethAL sent), fully warm | **17.1 s** | **2 x 115 MB** | 0 |
| `--package-cache <build>/platform-apps`, no `--auto-provision` | **6.8 s** | 0 | 0 |
| the same, three runs after a deliberately COLD provision | 7.9 / 8.0 / 7.8 s | 0 | 0 |
| the shape a REAL config sends: the project's `.alpackages` AND the pin | 8.0 s | 0 | 0 |
| today's real shape: `--auto-provision` AND the project's `.alpackages` | 24.7 s | 2 x 115 MB + 20 MB toolkit | 0 |
| no flags at all | 1.3 s | 0 | **2**, refuses |
| `--package-cache <a directory that does not exist>` | 1.3 s | 0 | **2**, refuses |

**The new per-invocation cost is 6.8 s and zero bytes, against 17.1 s and 230 MB.**

## Three of this row's own statements were corrected by measurement

1. **The row pinned the resolved build at `28.0.46665.53655`.** Every run on 2026-08-15 resolved
   `28.0.46665.53671`. Microsoft published inside the one day between filing and closing, which is
   the moving-target hazard this row argued about, observed rather than argued.
2. **The row proposed reading `[provision] Resolved: 28.0 -> <build>` and joining it onto an artifact
   root.** That was not built. The runner prints the DIRECTORY itself, so it is read rather than
   constructed, and no second copy of al-runner's layout is created.
3. **The row named the `fetching ... <path>` line as a source.** It is not read, for two measured
   reasons. It is an INTENT sentence printed before the download starts, so it can name a half-written
   directory. And `od -c` shows it carrying a raw `0x1A` (SUB) byte where an arrow glyph was mangled
   by the console code page, so keying a parse on its separator would bind LethAL to a console
   encoding. Its wording had already moved once: R130's 2.1.1.0 transcript ends it in a literal `...`
   with no path at all.

## The load-bearing assumption, measured rather than assumed

`provisionOnce` sends a DIFFERENT bundle set from a mutant invocation: the test bundle alone with a
filter matching no test, where a mutant sends the instrumented target plus the test bundle. al-runner
resolves the BC version prefix from the bundles it is given, so the two could in principle name
different directories. Measured, both on 2.1.2.0, cold and warm: both name
`...\28.0.46665.53671\platform-apps`. R128's choice of the test bundle is left alone rather than
widened to the project directory, which would change a closed row's step for no measured gain.

## Why a verdict-producing argv was allowed to change

A wrong pin cannot produce a wrong verdict. Measured: `--package-cache` at a directory that does not
exist is silently dropped from the scan (`package caches: 0 dir(s)`) and the run hits the same
provisioning-gap refusal as no flags at all, **exit 2 with empty stdout**, which `OneShotTransport`
maps to `kind: "error"`. Traced in code as well as observed: exit 2 and 3 become `kind: "error"`
directly, exit 1 with empty stdout makes `parseAlRunnerPayload` throw into the same result, and an
empty `tests` array misses the name lookup and answers `outcome: "error"`. There is no route from a
missing platform app to `status: "fail"`, because a missing platform app is a missing SYMBOL and the
bundle fails to compile before any test runs.

## The live gate

`itest:alrunner`, al-runner **v2.1.2.0**, 2026-08-15, **646 s** wall clock. Every one of the ten
pre-committed predictions held:

- killed **3** / survived **13** / no-coverage **0** over 16 sites, `baselineGreen` true;
- per-mutant identical to `al-runner.baseline.json`, and the two consecutive runs verdict-identical
  to each other;
- the three kills all in `SandboxLogic.Codeunit.al` from exactly `lethal.conditional-boundary`,
  `lethal.return-value` and `lethal.empty-block`; the three `SandboxPricing` mutants survived;
- `bcBuild` `28.1.49838.50794` (R129, unchanged);
- **`platformAppsDir` populated on both runs**, at
  `...\28.0.46665.53671\platform-apps`, which is the new assertion this row added.

The 646 s is recorded as an OBSERVATION, not as evidence: no prior wall-clock figure for this gate was
ever committed, so there is nothing to compare it against. The improvement claim rests on the
per-invocation table above. For scale, this gate makes roughly 70 invocations (two runs, each a
baseline plus 16 mutants against 2 green tests apiece, al-runner reporting `coverage: "none"`), so at
10.3 s saved apiece the saving is on the order of twelve minutes — an estimate from a stated
assumption, not a measurement.

## The side benefit, now real

Pinning the directory found at session start makes a mid-session Microsoft publish unable to move the
platform apps under a running campaign. Before this, the prefix resolved forward on every invocation,
so a run that started on `…53655` could finish on `…53671` with nothing recording that it did — which
is precisely what the cache did between this row being filed and being closed. It holds WITHIN a
session and not across a `--resume`, because `sessionFingerprint` deliberately does not cover the pin
(widening it would break every resume on every upstream publish). The report shows that seam instead
of hiding it: carried verdicts never receive `platformAppsDir`.

## What this did NOT fix, and it is filed

The R123 contract probe still builds its invocations with no pin, so it measures `--auto-provision`
while the verdicts come from `--package-cache`. Its own doc comment promises the opposite. Filed as
[R149](R149.md) rather than smuggled in here, and noted in `al-runner-contract.ts` so the promise does
not read as true. The R7/R8 canary and that probe together keep paying roughly ten seconds each at
session start, four invocations, so session START did not get faster.
