**Filed 2026-11-06 by preproc.** Related: [[R830]], [[R196]].

**What.** [[R830]] refuses the CALL when its same-object callee writes what the loop reads. It does not refuse the sites INSIDE that callee.
So with `repeat Advance(); until Counter >= Limit`, the call is refused, while `remove-assignment` of `Counter += 1` in `Advance`, and
`void-method-call` of a nested `Inner()`, stay claimed and hang the same way.

**Note for whoever builds it.** `itest:hang` has hangs of this kind in `Advance`, but it reaches `Advance` through an event, which this
rule would not follow, so those rows should stay.

**Closed by ruling, 2026-11-06 (orchestrator, coord task R-842).** Counts on master f901f666, by parse, with the production operators:
- Specs on or feeding the write in a callee chain: fixtures 0, CDO 0, DO 0, DC 0, BC.History 5,121 before any filter. A sample of 30 read by parse: 1 hang, 4 maybe, 25 no hang, so refusing them all costs about 19 real mutants per hang.
- With an "only step" test (no other cursor, no call or clock in the exit, no second writer, no other exit): 0 / 0 / 0 / 0 / 11, all in SalesPost's `UpdateInvoiceRounding`: 6 hang, 1 maybe, 4 no hang.

Getting from 5,121 to 11 took about five extra shape rules, and 4 of the 11 are still false refusals, so it is not built.
**Since 2026-11-07:** #49's fix landed, so a hang costs a timeout on BC 28 and BC 29 alike, and the line below is the record of its day.

**The limit.** The only-step test is a shape test, so a true hang can fall outside it. What catches such a mutant is the timeout, which is not a guard on BC 29 on Linux until SShadowS/LethAL#49 lands: there it can end the run. In the README's Limits.
