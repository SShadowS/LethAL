**Found by R-731** (2026-10-24), reading the compile-failure path while planning [[R731]] and [[R732]]. DC's compile
showed that one or two bad mutants out of 117971 sites is the normal shape of a failure, and the result of such a
failure was a whole batch of `error` rows.

**Cause.** In `runSession`'s deploy catch (`packages/runner/src/orchestrator.ts`), after `bisectAndNote` returned, a
loop recorded every mutant of `execute` as `error` and moved on to the next batch. The culprit changed only the note.
The batch was never redeployed without it. Second, `bisectFailingMutant` (`packages/runner/src/bisect.ts`) assumed
exactly one bad mutant: with two or more, the complement still failed and the result was `environmental`, which names
nobody. The old tests asserted `counts.errors > 0` and the note text, which hold whether one mutant or all are `error`.

**Fix (f5bd3631), steps 1 and 2 of the plan; step 3 is [[R735]].**
- `isolateBreakingMutants` (`bisect.ts`) replaces `bisectFailingMutant`. It compiles the empty set first (fails:
  environmental, nobody blamed), finds the smallest failing prefix, confirms the last mutant of it fails alone, removes
  it and recompiles the rest. A mutant that compiles alone is tried as a pair with an earlier one; a pair is reported
  as a group, a wider interaction as unresolved. The budget is `MAX_ISOLATION_COMPILES = 64`.
  Cost: each breaking mutant among n takes about log2(n) + 2 compiles (search, confirm alone, recompile the rest).
  Before a new round the search checks that the budget left can pay for it, and if not it stops with the rest
  `unresolved` (the same result as hitting the cap, without burning the remaining compiles on a round that cannot
  finish).
- A lone mutant is named only if its alc output holds an `error AL<nnnn>` line (a non-zero exit with none is not a
  verdict on a mutant). Its note is the source `file:line` plus alc's own codes; no source text.
- `writeInstrumentedProject` takes `fixedIds` (every isolation candidate and the redeploy keep the failed artifact's
  ids; a spec with no id, or an id used twice, throws) and `isolatedOut` (written into the manifest, so it is
  hash-covered).
- The batch loop redeploys the clean set through the same `deployStep` as the first deploy (R709, version-conflict
  retry, R90 record, throw on anything but an alc rejection), then rebinds `manifest`, `execute`, `runnable`,
  `candidates` and the per-file guard counts. Culprit rows are written once, after the redeploy's outcome is known, and
  only for mutants in `execute`. Every edge fails closed to `error` rows with a named note: the empty build fails, the
  budget is spent, the rewritten manifest is not exactly the clean set (checked before publishing), or alc rejects
  the clean set.
- `lethal verify` (`expandGapIds`) accepts a row with no manifest entry only when the manifest's `isolatedOut` lists it
  and the verdict is `error`. bcdev refuses to send a removed id to RunMutant.

**Tests.** `bisect.test.ts`, the "R734" block in `orchestrator.test.ts` (k=1, k=2, budget, environmental, failed
redeploy, indeterminate redeploy throws, id mapping by site, stored artifact digests, resume, stranded row, R90 count),
`verify.test.ts`, `bcdev-backend.test.ts`, `packages/schemata/tests/project.test.ts`. Red checks, one per guard:
`/coord/handoff/R-731/red-iso/red-checks.md`.

**Left open.** Isolating many culprits inside the budget: [[R735]]. The build review added the pinned "alc rejection
fails before any publish" tests (bcdev: publish and verify counters stay 0; al-runner-v3: the test app is never
compiled; envtool deploys through the bcdev backend, so it is the same test) and a direct test of
`redeployClean`'s rewritten-manifest check. The fixed-id redeploy is proven
offline only; a live gate run on a failing batch has not been done.
