**Found by R-731** (2026-10-24), reading the compile-failure path while planning [[R731]] and [[R732]]. DC's compile
showed that one or two bad mutants out of 117971 sites is the normal shape of a failure, and the result of such a
failure is a whole batch of `error` rows.

**Cause.** In `runSession`'s deploy catch (`packages/runner/src/orchestrator.ts`), after `bisectAndNote` returns, a
loop records every mutant of `execute` as `error` and moves on to the next batch. The culprit changes only the note.
The batch is never redeployed without it, so a culprit found in 10 compiles still costs every other mutant its
verdict. Second, `bisectFailingMutant` (`packages/runner/src/bisect.ts`) assumes exactly one bad mutant: with two or
more, the complement still fails and the result is `environmental`, which names nobody.

**Why the old tests did not catch it.** The bisection tests in `orchestrator.test.ts` assert `counts.errors > 0` and
the note text, which hold whether one mutant or all of them are `error`.

**Plan** (`/coord/handoff/R-731/plan.md`, steps 1 and 2; step 3 is [[R735]]).
1. `isolateBreakingMutants(mutants, compile, cap)` in `bisect.ts`: compile the empty set first (fails: environmental,
   nobody blamed), then find one culprit by halving, confirm it fails alone, remove it, recompile the rest, and repeat.
   A pair that fails only together goes to a group-error list. At the compile cap the rest is left unresolved.
2. Redeploy the clean set with the SAME mutant ids (`fixedIds` on `writeInstrumentedProject`). Each culprit is `error`
   with a note naming the alc code, file and line. Every edge fails closed: cap reached, an environmental failure, a
   failed redeploy, or an id mismatch leaves those mutants `error` with a named note, never scored.
