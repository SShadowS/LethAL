Found by coord task R-998 (2026-11-14), from R-984's DO window t1 (`/coord/handoff/R-984/result.md`, `t1.run.stderr.txt`).
Related: [[R945]], [[R1000]], [[R1004]], [[R964]].

**What.** In t1, 7 of the 35 daemon closes in mutant requests were on a refusal that starts `a stale Issued Reminder
Header buffer from its own write, after a lock other tha`. That is as far as LethAL's close summary prints it. No store
holds the full text: the rows of a request whose daemon closed are re-sent and never stored. al-runner's own binary holds
only pieces of the template. The BC.History shapes of this family (`after a rollback other than...`, `after a failed
guarded Codeunit.Run...`) are #7964's and are different texts.

**Why it matters.** R-998 keeps three refusal families on the serve daemon after measuring each clean. This one cannot
join without its full text and a trigger to measure, so DO keeps paying a warm-up for each of these closes (t1: about
100 s each).

**To do.**
- Make the close reason carry the whole refusal text: in the stats summary, or as a progress event per close, so a
  window's log has it.
- Then reduce the shape to an invented repro, measure it with R-967's kit, and either keep it or file it upstream.

**Progress (coord PR-09, 2026-11-15; evidence `/coord/handoff/PR-09/`).**
- **Done:** a `serve-daemon-closed` event carries the refusal's whole first line (`text`) and the refused row's test
  name (`test`). Events stay local and are never committed.
- **The full text** (from al-runner's template, and confirmed by a DO run on the PR-09 head): `a stale <table> buffer
  from its own write, after a lock other than LockTable or a ReadIsolation read in the open transaction (not pinned)`.
- **The site.** A DO run narrowed by `--only` to the four files around R-998's closes met it 8 times.
  - Every time it was ONE test: test 13 of 28 in its codeunit, whose baseline row is a kept cascade refusal. So it
    covers no mutant, and these closes cost time, never a verdict.
  - Under some mutants the earlier refusal is not met, so the test runs on into the stale buffer.
  - The test inserts its own record. App code then locks the table through a RecordRef (`RecordRef.LockTable()`),
    changes the row through a FieldRef and modifies it. The test then deletes its own (stale) record.
- **Not reduced yet.** 15 invented shapes all PASS on edge-a184cfc79 (`probe/app/src/Stale.al`, rounds 1-4). They
  cover:
  - a second variable locking or writing with `FindSet(true)`, `ModifyAll`, `LockTable(true)` + `Get`, and
    ReadIsolation;
  - a RecordRef locking, writing through a FieldRef, then the own record modified or deleted.

  The trigger depends on something in DO's path not yet isolated, so the family is neither measured nor kept.
- **No shortcut either:** leaving the test out of mutant entries is not verdict-neutral (R-998's trailing rule). Test
  28 of the same codeunit passes at baseline and runs after it.
- **Next:** reduce from the site with al-runner's own diagnostics (an `al-runner` trace of the DO test under one of
  the mutants), or ask upstream which shapes the rule `stale_rule.rs` names "a lock other than LockTable".
