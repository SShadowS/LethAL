Found by lethal-code, 2026-11-11 (coord R-914, Subcontracting on al-runner v3). Related: [[R922]].

**What happened.** Two of Subcontracting's 231 baseline tests fail on v3 with `The changes to the Warehouse Request record cannot be
saved because some information on the page is not up-to-date`, on the unchanged app. The raising statement is pinned: in the
warehouse release of a transfer order (reached from posting a warehouse receipt, its second release call), a Modify that runs after
an Insert of the same row failed. A buffer whose Insert failed never read the row, so BC's version rule should not refuse the Modify;
this looks like a v3 difference, not missing demo data, but that is not shown.

**Why not filed upstream.** Seven invented variants (one key, two keys, one buffer reused) all pass on v3, as BC would. A failing
repro would be a guess. Evidence and the variants: `/coord/handoff/R-914/upstream/9-warehouse-request-not-up-to-date-NOTE.md`,
`repro-9`, `repro-9b`.

**Next step.** Run one of the two tests under `al-runner debug` and list the writes to that Warehouse Request row between the two
release calls; build the repro from that sequence and file it at aldevtools/BusinessCentral.AL.Runner.

**Reproduced and filed (coord R-923, 2026-11-11):** https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/7798. Still fails on
edge-42af5d384. The release uses one buffer: it sets the inbound key and does an insert-else-modify, then the outbound key and the same.
On a second release both rows exist, so both Modifies run; v3 accepts the first pass and raises on the second pass's outbound Modify.
The invented repro (two existing rows, the same upsert twice) fails the same way; one row only, or one pass, passes. Not measured on BC;
Microsoft's own tests release twice and pass there. This item stays open until #7798 is fixed and the two tests pass on v3.
Evidence `/coord/handoff/R-923/r929/`.

**Closed (coord R-981, 2026-11-14): fixed on edge-736fc7677.** #7798 was closed upstream on 2026-11-12. On edge-736fc7677 the repro
passes and Subcontracting's test codeunit 149910 (`Subc. WIP Transfer Post Test`) runs 7 of 7 green, both
`PostWIPTransferOrder_FullWhseHandling_*` tests included; on edge-42af5d384 the same run fails those two with the Warehouse Request
error. The repro needed one edit first: its `Direction::In` is not valid AL (alc refuses it with AL0107, `In` is a keyword), the
current build now refuses it as alc does, so it runs as `Direction::"In"`. Evidence `/coord/handoff/R-981/`.
