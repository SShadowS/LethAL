Found by lethal-code, 2026-11-11 (coord R-914, Subcontracting on al-runner v3). Related: [[R922]].

**What happened.** Two of Subcontracting's 231 baseline tests fail on v3 with `The changes to the Warehouse Request record cannot be
saved because some information on the page is not up-to-date`, on the unchanged app. The raising statement is pinned: in the
warehouse release of a transfer order (reached from posting a warehouse receipt, its second release call), a Modify that runs after
an Insert of the same row failed. A buffer whose Insert failed never read the row, so BC's version rule should not refuse the Modify;
this looks like a v3 difference, not missing demo data, but that is not shown.

**Why not filed upstream.** Seven invented variants (one key, two keys, one buffer reused) all pass on v3, as BC would. A failing
repro would be a guess. Evidence and the variants: `/coord/handoff/R-914/upstream/9-warehouse-request-not-up-to-date-NOTE.md`,
`repro-9`, `repro-9b`.

**Next step.** Run one of the two tests under `al-runner debug` and list the writes to that Warehouse Request row between the two
release calls; build the repro from that sequence and file it at aldevtools/BusinessCentral.AL.Runner.
