title: "A base report's `protected var` written by a `reportextension` is not seen by loop-hazard's `writesPresetExitName`"

**Found by the R-463 plan review (opus spec-adversary, adversary-r1 finding 5d, 2026-10-09).** Not caused
by R-463 and not changed by it.

R-500 shape 1 (`writesPresetExitName` in `packages/builtin-tier1/src/loop-hazard.ts`) refuses a write of a
report GLOBAL that an open item's exit guard reads and that open-item code never writes, because its value is
fixed before the walk starts. It runs only for a site inside a `report_declaration`, and its doc comment
already states "Not seen: a write in another object". A `reportextension` is such another object, and it can
reach the base report's globals: a `protected var` of the base report is accessible from an extension (alc
18.0.43, measured in the R-463 plan review). So an extension's `OnPreReport` (or any extension code that runs
before the walk) that writes such a name, `Continue := true` say, is not refused, and a mutant that leaves
the name in its walking state can make the open item loop forever.

**To build it.** Make `presetExitNames` include the base report's `protected var` names, and refuse their
writes inside every project `reportextension` of that report (outside open-item code), the same way as in the
report. Red-test both directions: the extension's write is refused; the same write of an extension's own
global (not read by any exit guard) is not.

**Built (coord task R-547, branch `lethal/r547`, commit 6ec70aac).** `writesPresetExitName` now runs inside a
reportextension too, with the names from `extensionPresetExitNames`: the extension's OWN preset names
(`presetExitNames` over its blocks, so the guards of its `modify(X)` triggers and of the items it adds, with its
globals seeded with the base's `protected var` names), plus every base-report candidate's preset names that the
candidate declares `protected var` (`protectedVarNames`). A non-protected base global is not accessible from an
extension (AL0161). The base candidates are R547's `baseCandidatesOf` (every same-named report, `#if`-wrapped,
split-header or unparsed). `argWritten`'s bare branch inside a reportextension now reads the base candidates'
`var` parameters before the built-in fallback, and answers `unknown` (refuse) when they disagree or a candidate
cannot be read. Measured on the BUILT branch (production generation, against master 0e017cb5, 2026-10-09):
BaseApp hang-refuses exactly 2 more deployed mutants, both in `MfgWhseSourceCreateDocument.ReportExt.al`,
procedure `SetProdOrder` (an `empty-block` and a `remove-assignment` of the base `protected var` `WhseDoc`);
hang-refused 44,207 -> 44,209. E-Document Core, SubscriptionBilling, Sustainability, the R549 pageextension
projects (VAT Group Management, Bank Account Reconciliation With AI, CDO, DO) and the fixtures: unchanged.
0 identity keys, ordinals or kill tags moved (no scheme bump). The `this.` follow (R547) and the extension-guard
widening add no further deployed site on any corpus. Tests in `packages/builtin-tier1/tests/r547-r548-reportext-base.test.ts`: the base Integer item
asserted open; the protected write refused; the extension's own same-named global (the base one not protected)
kept; an extension guard's own global and a base protected var read only by an extension guard refused; a `var`
argument to a base procedure refused and a by-value one kept. Each red-checked one direction at a time
(`/coord/handoff/R-547/build.md`).

**Residuals (named, not built).**
- A write in the BASE report of a protected var that only an EXTENSION's exit guard reads (adversary-r1 F3c).
  Closing it needs the report-side rule to look at every extension. Measured cost: none known.
- Deleting a call to a procedure that writes a preset name WITHOUT a `var` argument (`InitContinue();`) is not
  refused, in a report or an extension: pre-existing R500 shape 1, filed as [[R555]].
- A value that reaches the name through another variable (unchanged from R500 shape 1).
- An UNPARSED (`ERROR`) base candidate gives no names: `protectedVarNames` and `presetExitNames` read the
  object's `body` field, which such a node does not have (opus build review, finding 2). A call into it
  still answers `unknown` in `argWritten`.

**Build review (finding 3).** The "candidates disagree -> `unknown`" rule is pinned where `unknown` is
`false` (inside `presetExitNames`): two same-named bases, one in an undecided `#if` arm, with `BaseInit(var
C)` and `BaseInit(C)`; the extension's open block calls `BaseInit(Stop)` and breaks on `Stop`, and its
`Stop := false` in OnPreReport is refused. With both `var`, the open call writes `Stop` and the write is
kept. Red-checked: `procs.some` keeps the disagree case; answering `unknown` always refuses the both-var case.
