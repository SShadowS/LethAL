**Found by RUST-01 Task 0 (2026-09-27), running the normal product pipeline
(`generateMutationSet` + `writeInstrumentedProject`) over whole real corpora.**

**What throws.** `assertNoOverlap` (`packages/engine/src/ast/printer.ts:54`, called from
`printWithRewrites`) throws `overlapping rewrites at <a>..<b> and <c>..<d>` when two edits'
spans are not disjoint. Two of the seven non-fixture corpora RUST-01 Task 0 ran the normal
pipeline over hit it:

- **dc** (`U:/Git/DC/Cloud`, 475 files): exit 1, `overlapping rewrites at 130..9494 and 910..910`.
- **sysapp** (`U:/Git/BC.History/System Application`, 1,718 files): exit 1,
  `overlapping rewrites at 603..2981 and 1105..1105`.

In both cases the shape is the same: one WIDE edit (9,364 bytes for dc, 2,378 bytes for sysapp)
and one ZERO-WIDTH insert whose position falls strictly inside the wide edit's span. Task 0 did
not identify which specific file in either corpus produced the failure (only the corpus-level
`generateMutationSet`/`writeInstrumentedProject` call threw); `assertNoOverlap` reports offsets
into a printed edit list, not a file path.

**Why it matters.** A target project with this shape cannot be instrumented at all — the whole
run aborts with a thrown `Error`, not a narrowed or degraded result. It also blocks RUST-01's own
whole-corpus identity capture (Q2 of `docs/superpowers/sdd/2026-09-27-RUST-01-native-parser/`'s
brief): the WASM pipeline's own identity listing for dc and sysapp does not exist, so there is
nothing for the native pipeline's identity capture to be compared against on those corpora.

**Related but distinct: [[R251]].** R251 (open, unverified) flags that `injectMutationSelectorVar`
compares objects by node identity, and that specs coming from two separate tree walks over one
object could in principle produce two overlapping *selector-variable* edits — but R251's own text
says "the real pipeline may never reach this" and its scratch reproduction was never checked
against a real corpus. This finding is a live, real-corpus reproduction of `assertNoOverlap`
throwing, but the offsets do not fit R251's shape: a duplicate selector-var insertion would be a
narrow edit anchored right after an object header, not a multi-KB wide span colliding with an
unrelated zero-width insert elsewhere in the same object. Until the specific edits are identified,
it is not known whether this is R251's mechanism finally reproducing on real input or a second,
different way to reach the same assertion — that identification is the first step to closing this.

**What would close it.** Reproduce standalone (`generateMutationSet` + `writeInstrumentedProject`
on the specific dc/sysapp file that throws, once located — bisecting the corpus, or adding a
file path to `assertNoOverlap`'s thrown message, would find it), inspect the two colliding specs
to see which operators/mechanisms produced the wide edit and the nested zero-width insert, then
decide whether the shape is a genuine authoring conflict (drop or merge one of the two mutants)
or whether `assertNoOverlap` is too strict — a zero-width insert nested fully inside a wider
replace may be composable rather than conflicting, in which case `printWithRewrites` should
support that case instead of refusing it.
