**Found by RUST-01 Task 0 (2026-09-27), running the normal product pipeline
(`generateMutationSet` + `writeInstrumentedProject`) over whole real corpora.**

**What throws.** `assertNoOverlap` (`packages/engine/src/ast/printer.ts`, called from
`printWithRewrites`) throws `overlapping rewrites at <a>..<b> and <c>..<d>` when two edits'
spans are not disjoint. Two of the seven non-fixture corpora RUST-01 Task 0 ran the normal
pipeline over hit it:

- **dc** (`U:/Git/DC/Cloud`, 475 files): exit 1, `overlapping rewrites at 130..9494 and 910..910`.
- **sysapp** (`U:/Git/BC.History/System Application`, 1,718 files): exit 1,
  `overlapping rewrites at 603..2981 and 1105..1105`.

In both cases the shape is the same: one WIDE edit (9,364 bytes for dc, 2,378 bytes for sysapp)
and one ZERO-WIDTH insert whose position falls strictly inside the wide edit's span. Task 0 did
not identify which specific file in either corpus produced the failure (only the corpus-level
`generateMutationSet`/`writeInstrumentedProject` call threw); `assertNoOverlap` reports offsets
into a printed edit list, not a file path.

**Why it matters.** A target project with this shape cannot be instrumented at all — the whole
run aborts with a thrown `Error`, not a narrowed or degraded result. It also blocks RUST-01's own
whole-corpus identity capture (Q2 of `docs/superpowers/sdd/2026-09-27-RUST-01-native-parser/`'s
brief): the WASM pipeline's own identity listing for dc and sysapp does not exist, so there is
nothing for the native pipeline's identity capture to be compared against on those corpora.

**Related but distinct: [[R251]].** R251 (open, unverified) flags that `injectMutationSelectorVar`
compares objects by node identity, and that specs coming from two separate tree walks over one
object could in principle produce two overlapping *selector-variable* edits — but R251's own text
says "the real pipeline may never reach this" and its scratch reproduction was never checked
against a real corpus. This finding is a live, real-corpus reproduction of `assertNoOverlap`
throwing, but the offsets do not fit R251's shape: a duplicate selector-var insertion would be a
narrow edit anchored right after an object header, not a multi-KB wide span colliding with an
unrelated zero-width insert elsewhere in the same object. Until the specific edits are identified,
it is not known whether this is R251's mechanism finally reproducing on real input or a second,
different way to reach the same assertion — that identification is the first step to closing this.

**Resolved: a second, different mechanism, fixed alongside R251 in the same commit.** This item's
throw was the wide var-section-replace edit described above, in `injectSelectorVarIntoObject`.
R251's own dedup keying (in a different function, `injectMutationSelectorVar`, which decides whether
an object already received its selector) turned out to be real too, independently: at HEAD, feeding
`compileSchemataForFile` specs from two separate tree walks over one object gave two overlapping
selector-variable edits, confirming R251's suspicion. `0185b3a` fixed both: this item by anchoring
after the declaration-only prefix instead of replacing the section, R251 by keying the object dedup
on the object's `startIndex` (R209) instead of node identity. See [[R251]] for its own closing note.

**What would close it.** Reproduce standalone (`generateMutationSet` + `writeInstrumentedProject`
on the specific dc/sysapp file that throws, once located — bisecting the corpus, or adding a
file path to `assertNoOverlap`'s thrown message, would find it), inspect the two colliding specs
to see which operators/mechanisms produced the wide edit and the nested zero-width insert, then
decide whether the shape is a genuine authoring conflict (drop or merge one of the two mutants)
or whether `assertNoOverlap` is too strict — a zero-width insert nested fully inside a wider
replace may be composable rather than conflicting, in which case `printWithRewrites` should
support that case instead of refusing it.

Found by RUST-01 Task 0.

**Closed 2026-09-28, `0185b3a` (R-297 Task 2).** The two colliding edits were both real: the injector
(`injectSelectorVarIntoObject`, `packages/schemata/src/compile.ts`) used to REPLACE the object's whole
`var_section` with a rewritten copy holding the selector, a wide edit spanning the entire section;
any spec whose `before` node sits inside that same section (a `variable_declaration`, an
attribute-carrying `#if`) produced its OWN edit at a position strictly inside that wide span, and
`assertNoOverlap` correctly refused the pair.

**The fix: stop replacing, start anchoring.** The selector line is now inserted once, right after the
object's leading run of DECLARATION-ONLY children (`isDeclarationOnly`, an allowlist:
`variable_declaration`, `var_attribute_item`, `comment`, `multiline_comment`, `pragma`,
`preproc_region`, `preproc_endregion`, and a `preproc_conditional_var` whose named children are all
`#if` markers or themselves declaration-only). The run stops at the first child that is not
declaration-only, so the wide replace-the-whole-section edit is gone and the two edits no longer
overlap. An empty run anchors right after the `var` keyword; a missing `var` keyword still throws.

**The latent attribute sibling.** The allowlist rule surfaced a second, silent defect on the way: a
`#if` holding ONLY an `[EventSubscriber(...)]`-style `attribute_item` is not declaration-only (an
attribute is not a declaration), so the anchor correctly stops before it. But at HEAD, before this
fix, the selector was wrongly emitted INSIDE such a `#if`, landing on the attribute's own line and
producing 18 `AL0432` warnings under the symbol-absent build (`CDCCloudMigrationMgt.Codeunit.al`,
dc). The same class recurred in BaseApp's `ContactSyncProcessor` shape (an `[Obsolete(...)]` `#if`
followed by an empty-bodied overload) and is fixed by the same anchor rule. Both shapes are the same
family as upstream grammar issue #29
(<https://github.com/SShadowS/tree-sitter-al/issues/29>, tracked in [[R291]]): a construct
tree-sitter-al 4.4.1 attaches to the object's `var_body`/`preproc_conditional_var` rather than to the
object as an ordinary member, with no error node to signal it. The LethAL-side workaround (the
declaration-only allowlist, checked by `assertSelectorPlacement`'s denylist oracle) stays until a
grammar bump removes the need to special-case it.

**Corpus figures (R-297 Task 7, same-session BEFORE/AFTER on dc, sysapp, bcf).** dc: one OK-before
file's selector line moved as predicted, `CDCCloudMigrationMgt.Codeunit.al`, from mid-object (after
`#endif`, between the `[EventSubscriber(...)]` `#if` and the next procedure) to after the object's
last plain declaration; specs and the operator multiset unchanged (103 = 103). sysapp: neither of its
two movers was OK-before (both were among the corpus's FAIL-before files, so their placement was
never observed as a running defect there). bcf: no selector move. No OK-before file changed outside
the files this fix was expected to touch, in any of the three corpora.
