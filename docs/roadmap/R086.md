**No kill records WHY it died, so a false kill and a real one are indistinguishable in the record.**
MEASURED 2026-08-03 on the R82 gate run: `failure_note` was `NULL` for **all 109** killed mutants in
the run database. The fixture's arm E — a swap killed by BC's *"The length of the string is 18, but it
must be less than or equal to 10 characters"* under a test that asserts NOTHING — was stored
identically to arm A, killed by a genuine assertion. The distinction survived there only because the
fixture was built to make it inferable; on a real project nobody could infer it, and the reader was
told their tests caught something when the platform did. Direction of the error is the bad one: it
flatters the suite. Not hypothetical and not operator-specific — any mutant that makes the platform
raise (overflow, division by zero, a JIT field-load failure) read as a kill the assertions earned.

**THE GAP WAS A READ, NOT A CAPTURE — this row said the opposite for one commit and the correction is
the useful part.** The text was already persisted: `test_results.failure_message` is NOT NULL for
**110 of 110** failing rows in the same run 148, message plus `;`-separated AL callstack, written by
`RunMutantTransport.failureTextOf` (`packages/runner/src/run-mutant-transport.ts`) on the fenced path
mutants actually take and stored with a `mutantRowId` FK. What was missing was one JOIN: `MutantOutcome`
(`packages/runner/src/report.ts`) carried `killingTest` and `failureNote` but never the killing test's
failure text.

**FIXED by recording, not by classifying.** `MutantOutcome.killingTestFailure` now carries the failing
run's text verbatim on every `killed` and `timeout-killed` outcome, sourced from the MUTATED run's
verdict and never from the null-activation confirmation rerun (which passes by definition, so wiring
it there would leave the field silently absent on every kill while every survivor-side test stayed
green — empty-vs-empty, red-checked). It rides the `mutant-scored` and `mutant-carried` events, folds
into the report, persists to `mutants.killing_test_failure` behind the usual guarded migration,
carries across `--resume`, is cleared by `invalidateBatch` alongside `killing_test`, and prints as an
indented first line under the mutant row in `renderConsole`. Additive, so no `REPORT_SCHEMA_VERSION`
bump. Per R72's discipline the verdict does not move: a killed mutant stays killed, and this
annotates.

**THE DISCRIMINATOR THIS ROW FIRST PROPOSED IS MEASURABLY WRONG, and was deliberately NOT shipped.**
It said the top callstack frame being in the TARGET app identifies a platform artifact. Classified
over all 109 mutant-attributed failing rows in run 148: **4 have a target-app top frame, and only ONE
is arm E.** The other three (M0059, M0062, M0066) are ordinary kills where the target's own
`TestField`/`Get` raised — *"Category must have a value in Data Main"*, *"The Data Main does not
exist"* — which is exactly the class the R82 spec §4 insists must be read APART from a false kill,
since production validation detecting a bad state is a real kill. **75% false-positive rate on the
only run the rule has been checked against.** The candidate the data does support (the failing frame's
statement is not the mutated statement AND the message is a platform-class error), the localisation
ceiling on any prose rule (R66), and the fixture's structural blindness to how a real Library-Assert
suite stacks — all moved to **R121**, which is what R85's kill-rate split now waits on.

Evidence: `docs/measurements/README.md` §"R82 live"; both corrections found by an adversarial review
of the landed work and re-measured independently.
