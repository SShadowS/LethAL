**Measured.** Run 2 (pre-R198, one HTTP call per test) and run 3 (R198, one `RunMutantMany` call
per mutant) on the same 741 mutants. 17 verdicts differ: 9 are run 2's stranded hangs scored
`timeout-killed` by the stop (expected); **8 are `survived` → `killed`**, every one in cache code
(`CDOVariantMatchCache` 82–84, `CDOTemplateVariantMgt` 531–533 and 913), every killer at position
3, 3, 4, 7, 7, 9, 9 or 110 of its group call, every failure a stale-cache assertion. 20 more kills
kept their verdict and named a different killer with R197's order unchanged. 0 moved the other way.

**Mechanism.** Each method is its own `CODEUNIT.Run` under Microsoft's `Test Runner - Isol.
Codeunit`, and the database rolls back per method (probe E1/E7). A `SingleInstance` codeunit's
variables live for the SESSION, and a group call is one session. Before R198 every request got a
fresh session (probe E11: session ids strictly increase, never reused), so the target's match cache
was cold for every test and a mutant that removes its invalidation was unobservable. Warm, it is
caught. The kill confirmation re-runs the killing test alone, unmutated, in a fresh (cold) session,
so it passes and the kill stands. The reviews of R198's design named this state as unmeasured; the
design claimed "isolation identical to today" for the database and was right about that only.

**What it is and is not.** Not a false kill in the ordinary sense: the failure is caused by the
mutant, in a context (a warm cache) the product and the target's own CI both have. Not today's
semantics either, and the same mechanism could hide a kill (a test that passes warm and would fail
cold); none did here. The pre-R198 cold-per-test context was an accident of one session per
request, not a design.

**Options, decided by the row's owner, not here.** (A) keep grouping; confirm a kill at position
k > 1 WARM by replaying methods 1..k unmutated through the same call, so a failure that reproduces
without the mutant is `unstable`, never a kill; record the kill position per mutant; state the
semantics as a caveat. (B) `--no-group-runs` by default: pre-R198 verdicts, and the wall-clock gain
(148 → 111 min here) forfeited. (C) a session per method inside the call (`StartSession`): cold
state and no round trip, at a session start-up per method and a third stop design.

**Decided and built: (A), 2026-09-03.** The design
(`docs/superpowers/specs/2026-09-03-r206-warm-confirmation.md`, revision 5) was refused three
times and approved on the fourth; the things the reviews caught are in its tables. What landed:

- **The ruling**, as the `session-warm` caveat on every report with a grouped call: a kill is the
  test failing (or exceeding its budget) with the mutant active, in a session that was fresh at
  the call's start, where the same ordered prefix of tests passes (and completes inside budget)
  without it in another fresh session. A cold-only kill is a survivor here, the accepted direction.
- **The session guard** (`testRunsBefore`): the control app (1.0.0.18) counts the test methods
  each SESSION has run in a dedicated `SingleInstance` field with one writer and no reset, and
  every answer that ran reports the count at the call's start. Anything but 0 is a reused session:
  a fail or timeout measured there is `session-reused`, never a kill; a pass stays survived. The
  predicate lives in the same kind of state as the target's cache, so it needs no belief about BC's
  session handling, and covers the first call of a resumed run. Run 3's own 408 texts already
  measured the sandbox handing every request a fresh session (ids 79 apart across a 185 s hang's
  polls), and every gate now checks from the store that the recorded session ids are live data.
- **The warm confirmation**: a kill at group position k > 1 replays the CALL's methods 1..k
  unmutated through one ordinary `RunMutantMany`; confirmed iff complete, all k ran, all passed,
  and for a timeout method k finished inside its cold budget; every other ending is an error with
  its own cause (`warm-prefix-unstable`, `unstable`, `warm-timeout-unconfirmed`,
  `warm-confirmation-incomplete`). `killPosition` on every kill, `warmKills` on the report.
- **The per-method cost cut** (§4): one suite per call, keyed on the (codeunit, method) pair,
  filtered `RunTests`, results read back off the function line. Measured on the sandbox by run 4.
- **The hang fixture's `SpinUntil` arm**, the only live warm timeout: its `void-method-call` hangs
  at position 2 and is scored `timeout-killed` only after the replay, `killPosition` 2.
