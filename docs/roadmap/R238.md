id: "R238"
title: "A session that THROWS after recording a recycle still deletes its created environment, because teardown reads `quarantined` from a report that does not exist"
section: "correctness-risks"
status: "open"
order: 948
---

**Found in the C02-04 R232 review (2026-09-26), confirmed by reading. Pre-existing.**
`withEnvTeardown` (`packages/runner/src/cli.ts`) passes
`quarantined: report?.quarantined !== undefined` to the env-tool session's `teardown`. When the
session body throws, `report` is `undefined`, so teardown runs as NOT quarantined, even when the
session had just written a durable `container-needs-recycle` record before throwing.

**Consequence:** in create-mode, a created environment is deleted instead of kept for recovery,
and the "keeping environment ... (session quarantined)" hint is never printed. Two paths reach it:
an uncertain R19 test-app publish (since R232 it quarantines, latches and rethrows) and an
`indeterminate` or `anomalous` target deploy, which has done the same all along. Deleting a
created environment removes the tier the quarantine record names, so the record then points at
nothing and the operator has no environment to inspect.

**Fix shape:** decide teardown's `quarantined` from what the session actually recorded, not from
the report alone: for example, re-read the quarantine store for the session's resource key in the
`finally`, or have `runSession` attach the fact to the error it rethrows. Test: a body that
records a recycle and then throws must reach `teardown` with `quarantined: true`.

Not measured live.
