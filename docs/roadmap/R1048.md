Found by coord task PR-33 (2026-11-15) while measuring family 10 ([[R1047]]). Evidence: `/coord/handoff/PR-33/ws-run/result.md`
(both runs), `issue-restrictive-default.md`. Related: [[R026]] (LethAL's permission canary: a codeunit without TestPermissions
defaults to Restrictive).

**The difference, measured.** Regression entry `u8160-restrictive-default`, run by lethal-bugs on bc2 (BC 28.4 W1, Microsoft's
Permissions Mock 28.4 installed, through LethAL's web-service path):
- `InsertUnderRestrictiveDefault`, a codeunit with no TestPermissions that inserts into its own app's table before any
  `PermissionsMock.Set`, fails on BC: `Sorry, the current permissions prevented the action. (TableData 51600 URD Row Insert:
  Upstream Repro Restrictive Default)`. al-runner edge-5a58a0f16 passes it.
- `InsertWithTestPermissionsDisabled`, the same write with `TestPermissions = Disabled`, passes on both.

Ten cells of family 10's first BC-check app had the same shape and were refused the same way on BC; al-runner passed the three it
ran.

**Why it matters for LethAL.** A wrong verdict, not a refusal: a test that writes before lowering its permissions passes on
al-runner and fails on BC. Under a mutant, al-runner then scores the test against a baseline BC would not give. Not measured: a
server without Permissions Mock.

**How far the refusal reaches (PR-35, measured).** A 6-test probe (`/coord/handoff/PR-35/probe`, pre-committed in
`docs/superpowers/specs/2026-11-15-pr35-8160-at-risk-precommitment.md` addendum 1), run by lethal-bugs on bc3 (BC 28.4 W1,
Permissions Mock installed, LethAL's web-service path, which goes through Microsoft's runner): under the Restrictive default
**every write is refused**, wherever it happens. That covers the test app's own table, the app under test's table written from the
test, and the app under test's own codeunit writing its table (BC then names the target app as the writer). **Reads are allowed.**
With `TestPermissions = Disabled` the same write passes. al-runner edge-5a58a0f16 passes all six. (The pre-committed prediction
that writes outside the test app pass was wrong.)

**The at-risk set in stored results (PR-35).** By parse (`/coord/handoff/PR-35/at-risk.ts`), over PR-15's 84 BC.History projects
and DO:
- 58 of the 83 distinct projects install Permissions Mock, directly or through Tests-TestLibraries. Of their 399 test
  codeunits, 83 declare no TestPermissions or declare Restrictive (79.2% declare Disabled or another value).
- **306 test methods in 20 projects write a non-temporary record before their first permission lowering.** By table owner:
  the test app 33, the app under test 47, another app 226.
- **123 of them pass in the project's stored al-runner baseline;** BC, as LethAL runs it, would fail them. 183 already do not pass
  there (refused or failing for other reasons).
- **455 of those projects' 1,848 kills rest on an at-risk test**, joined on the method name; no name is ambiguous. In 12 projects
  that is over 5% of the kills; in recref, privacy, transl and usrperm it is all of them.
- DO installs the mock, but all 76 of its test codeunits declare TestPermissions: no at-risk test.
- Per project: `/coord/handoff/PR-35/at-risk.out.txt`; per test: `outcomes.tsv`; per kill: `kills.tsv`.

**The pre-committed predictions, scored.**
- P1 (at least 80% declare TestPermissions): missed narrowly, 79.2%.
- P2 (fewer than 100 passing at-risk tests, in fewer than 10 projects): missed, 123 in 20.
- P3 (DO installs no mock): missed. DO installs it, but has no exposed codeunit, so no at-risk test.
- P4 (under 5% of each project's kills): missed in 12 projects.
- Addendum 1 (writes outside the test app pass): missed; every write is refused.
- Validation: the only stored BC baseline of an at-risk test is the control's (refused, as predicted).

**Limits of the set.**
- Tables with `InherentPermissions` are not excluded, so some of the 226 "another app" writes may pass on BC.
- 258 more tests reach another codeunit before any lowering ("indirect"). These are left out: a stored BC baseline (R-882 S3,
  Service Declaration, mock installed) has 7 of them passing.
- Not explained: Microsoft ships suites with this shape as passing (recref declares Restrictive and inserts in Initialize before
  `PermissionsMock.Set`). How Microsoft's own pipeline runs them is not known here.
- No fixed build exists, so nothing is re-scored. The refusal ledger has no entry for this class, since it raises no refusal; the
  record is this item.

**Filed.** https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8160 (upstream's #7640 says the per-method Restrictive
default is pinned; this shows it does not stop the write).
