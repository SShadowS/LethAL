**Found by RUST-01 Task 0 (2026-09-27), running the normal product pipeline
(`generateMutationSet` + `writeInstrumentedProject`) over whole real corpora.**

**What throws.** `assertNoUnsupportedObjectMix` (`packages/schemata/src/project.ts`) refuses a
file that declares more than one AL object header when at least one of them is not an injectable
kind (codeunit/table). One of the seven non-fixture corpora hit this:

- **sentinel** (`U:/Git/BusinessCentral.Sentinel`, 67 files): exit 1, on
  `BusinessCentral.Sentinel.Test\stubs\NoSeriesLine.Table.al` — the file mixes a table, an enum
  and a codeunit in one file.

**This is a deliberate, documented limitation, not a defect.** `assertNoUnsupportedObjectMix`'s
own doc comment in `project.ts` states the residual plainly: two-or-more objects that are ALL
injectable are supported since [[R006]] (R6) — each mutant is attributed to its own enclosing
object, and a declaration is injected into every object that received a guard, not just the
first. What stays refused is specifically the MIXED case, and the same doc comment gives the
reason it is not yet built: `generateMutationSet` only drops a file's specs when the WHOLE file
has zero injectable objects, so a file holding one injectable and one non-injectable object still
reaches this check with specs generated for both, and "there is no per-object DROPPING of just the
[non-injectable] object's mutants (the same kind-filter ... applied at object granularity instead)
— that is a real capability extension, not yet built. Refusing the shape is the honest answer
until it is." R006 itself is closed for the all-injectable case; this is its unclosed residual.

**Why it matters.** A real project that declares this shape — an injectable object (table/codeunit)
sharing a file with a non-injectable one (enum, page, report, ...), such as Sentinel's
`NoSeriesLine.Table.al` mixing a table, an enum and a codeunit — cannot be instrumented at all for
that file: the whole run aborts with a thrown `Error` rather than instrumenting the injectable
object and skipping the rest. It also blocks RUST-01's own whole-corpus identity capture (Q2 of
`docs/superpowers/sdd/2026-09-27-RUST-01-native-parser/`'s brief): there is no WASM-pipeline
identity listing for sentinel to compare the native pipeline's capture against.

**What would close it.** Per-object dropping instead of a whole-file refusal: keep attributing and
instrumenting the file's injectable object(s) as R6 already does for the all-injectable case, and
drop only the non-injectable object's mutant specs (the same `canCarryMutationSelectorVar`/
`INJECTABLE_OBJECT_TYPES` kind-filter `generateMutationSet` already applies file-wide, applied at
object granularity instead), rather than refusing the whole file.

Found by RUST-01 Task 0.

**2026-10-02 (R307):** the failure described here is now a named per-file skip. The file is refused
whole, the rest of the project still runs, and the report lists it in `excludedSites` with reason
`instrumentation-refused`. This item stays open for per-OBJECT dropping, which would instrument
the injectable object in such a file instead of skipping all of it.

**Closed 2026-10-05 as a ruling: a stated limit, no change** (R-299 measurement,
`/coord/handoff/R-299/measurement.md`, master ae12ca1f).
- **Measured.** An object-header scan, plus the real `generateMutationSet` path, which reports which files the instrumentation trial refuses:

  | Corpus | Projects | `.al` files | Sites | Mixed files | Sites lost |

  **Zero** mixed files anywhere: 0 sites lost of about 2.34 million. A synthetic Sentinel-shaped file (table, enum and codeunit) is refused by the same path, and splitting it per object finds its 9 sites, so the detector works. Sentinel itself, the only known hit (a test stub), is not on this machine.
- **Why no change.** Per-object dropping would recover nothing on any measured corpus. Since R307, a mixed file is a named per-file skip that marks the run `narrowed` (R399), not a run abort.
- **Limit.** If a real project shows the shape in production code, re-run the R-299 measurement before reopening.
- **Two observations, recorded here rather than filed** (each 0 hits on every corpus above):
  - The injectable-kind list `INJECTABLE_OBJECT_TYPES` (codeunit, table) is narrower than `CARRIER_KINDS` (which adds page, report, pageextension and tableextension). So a file mixing, say, a codeunit and a page is refused, although every object in it could carry the selector variable; its "kept in sync by hand" comment is stale. The cheapest step, if it is ever needed, is to derive the first list from the second.
  - The object-header pattern used by `assertNoUnsupportedObjectMix` does not recognise `permissionset`, `enumextension`, `interface`, `entitlement` or `profile`. A codeunit sharing a file with one of them is not seen as mixed, so the file is instrumented. Such an object holds no mutation sites, so nothing is injected into it.
