**Found by** PR-454's spec-adversary (lethal-code, 2026-11-26), from PR-427's events (codes, times and counts only).
Evidence: `/coord/handoff/PR-454/timeline.md`, spec `docs/superpowers/specs/2026-11-26-pr454-renew-unanswered-stop.md` r2.

- **The gap.** PR-454 stops a session when lease renews go unanswered for a while (R1227). On PR-427 the control app
  answered renews again from 8.95 h to 11.03 h. In that period the run scored 44 kills, 16 survivors and 8 errors.
  - Against al-runner on the same mutants (al-runner is not authoritative), 22 of the 72 late verdicts are al-runner
    survivors, against 7 of 60 before the window (R1227).
  - With PR-454, they would not have been scored: its stop at the first streak ends the session. A tier that degrades
    with no renew streak at all would still not be caught.
- **Signals in the data (per hour, hours 9-10 against hours 1-8):**
  - calls ending in a test failure: 29-37, against 5-18;
  - completed calls: 17-18, against 3-8;
  - average kill time: 4-9 s, against 34-86 s;
  - average survivor time: 121-197 s, against 650-1200 s.
  - Calls ending at the 330 s cap were routine from hour 1, so the cap is not the signal.
- **Not designed.** Candidate shapes:
  - a periodic canary: a NONE run of a known-green codeunit must stay green;
  - a drift test on the failure rate of covering tests against the baseline;
  - re-confirming kills late in a long run.
  - Each needs measurement first.
- **Measured by PR-455 (lethal-code with lethal-bugs, 2026-11-26).** Pre-commitment
  `docs/superpowers/specs/2026-11-26-pr455-reconfirm-precommit.md` (39ecd7e3e); evidence `/coord/handoff/PR-455/`
  (`findings.md`, `sample-*.tsv`, `join.tsv`, `join.txt`).
  - **History could not decide it.**
    - Failure-rate and call-profile drift are set by each project's tests: healthy email and subs look like edocs'
      suspect hours.
    - Kill concentration does not separate.
    - The rising disagreement with v3 was confounded by code order.
  - **The decisive re-confirm.** 15 late and 15 early kills per area (edocs 8.9-11.04 h, queue2 2-3 h, subs 5+ h)
    were re-scored on bc4, freshly set up after restart #3, at the same pin ac413797d, matched by the FULL site key.
    - **All 90 re-scored `killed`:** 0 flips late, 0 early, in every area, with 0 errors.
    - By the rule, every area is NOT DEGRADED. That includes edocs' kills from the window after the renews went
      unanswered.
    - So the late disagreement with al-runner (22 of 72) was an al-runner vs BC difference, not false kills from a
      failing tier.
  - **Sized down.** No canary and no drift detector are built: no evidence shows a tier that degrades with renews
    answered. PR-454's renew stop (R1227) stays as hygiene; lethal-bugs corrects R1227's false-kill premise.
  - **Reopen when any of these appears:**
    - a future re-confirm sample (the same rule) shows late flips on a tier whose renews stayed answered;
    - a run whose late verdicts are suspect for a NAMED reason (fresh-tier re-scores disagree, or a per-mutant
      replay-on/off or BC/BC difference), not only al-runner disagreement;
    - a BC degradation that is reproduced and observable.
- **Reopened 2026-11-27 (lethal-bugs, PR-427's email3 run).** Evidence: `/coord/handoff/PR-427/email3/` (`events.ndjson`,
  `store.sqlite`). The run is bcdev on bc4, LethAL ac413797d, one batch of 4,875 guards, started 2026-11-26 12:46Z, and
  12 h long with no renew streak. It scored 1,873 mutants.
  - **The measure is passing rows only.** A passing test runs to its end, so a mutant cannot shorten it. There are
    11,628 such rows, and each is divided by the SAME test's own baseline duration in this run.
    - The median ratio by sixth of the run is **0.27, 0.46, 1.36, 3.37, 1.69 and 2.60**. The 75th percentile reaches
      5-7x.
  - **The same test, early against late:** 54 tests passed in both the first and the last sixth. Their median is
    **12.1x slower** late.
  - **The mutants got heavier too, but that does not explain it.** Methods per group call went from 6.4 to 28.7 to 33.0
    as later files have more covering tests. That changes how many tests run, not how long the same passing test takes.
  - **Verdicts still reproduce.** 765 of 766 covered mutants scored both here and in the first Email run (2026-11-25)
    have the same verdict. The one difference is `CDOEMailHandler.Codeunit.al` line 435, `lethal.remove-assignment`
    (M0610): killed before, error after (`warm-confirmation-incomplete`). So this is slowness, not yet a wrong verdict.
  - **Open question: server state or run-side state.** The resume (2026-11-27 00:47Z) runs a fresh baseline in a new
    process on the same server, with no restart. Its per-test durations, compared with the run's first baseline,
    decide it. The result goes here.
