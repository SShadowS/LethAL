**Found while running the v4.0.1 to v4.3.0 grammar bump's per-site proof.** The A/B reported 27
`lethal.swap-enum-member` rows removed and 27 added, at identical file, line and column, differing
only in which member the mutant swapped to. That looked like a grammar regression.

It was not. Running the census TWICE under the SAME grammar over the SAME input produced 19 such
rows, so the instrument disagreed with itself:

```text
B vs B2, same grammar, same input:
  A rows: 791794   B rows: 791794   delta: 0
  only in A: 19   [lethal.swap-enum-member 19]
  only in B: 19   [lethal.swap-enum-member 19]
```

**The cause, confirmed rather than inferred.** `readdir(projectDir, { recursive: true })` does not
guarantee a stable order, and this script used the result unsorted. File order reaches
`enumValuesOf` through `buildSemanticContext`, so an enum extended by more than one
`enumextension` gets its members merged in visit order. `swap-enum-member` picks a sibling by index
and WRAPS at the end of the list, so for a value that is the last member the chosen replacement is
`members[0]`, and that first member changed depending on which extension was visited first.

The worked example: `"Report Selection Usage"::"P.Self Billing Invoice"` is the last of 65 members
and the enum carries two extensions (Manufacturing and Service). The mutant swapped to `"SM.Quote"`
on one run and `"Prod.Order"` on the next.

Confirmed by fixing it: with `.sort()` added, two runs over BaseApp's 8,020 files produce ZERO
differences, `swap-enum-member` included.

**The pipeline was never affected, and that is the important half.** `orchestrator.ts` calls
`entries.sort()` before parsing, and `census-fixture-mutants.ts` sorts too. This script was the only
one that did not. So no run, no report and no committed baseline ever carried this: real mutants are
deterministic.

**Why it is filed as a correctness risk anyway.** This is the instrument
`packages/engine/vendor/README.md` names as the per-site half of a bump's proof, the half that
exists because aggregate counts cannot see a bump that moves WHICH sites an operator claims. An
instrument that disagrees with itself can fail in both directions: it manufactured a grammar
regression here, and 19 spurious rows could equally have masked 19 real ones. Every earlier bump's
"BYTE-IDENTICAL" census claim was made with this defect present; those corpora appear not to have
contained a multi-extension enum with a wrapping swap, so the results stand, but they were not
guaranteed to.

`swap-enum-member` post-dates the 3.2.1 and 4.0.0 bumps recorded in that README, which is why this
did not surface until now.

**Fixed** in the same commit that records it, with the sort commented as load-bearing so nobody
tidies it away, and red-checked by running the fixed script twice over BaseApp.
