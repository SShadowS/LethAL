title: "No fixture is a NAMESPACED AL app, which is why every gate stayed green while namespaced projects got zero coverage attribution"

**What happened.** Issue #9 reported that fenced coverage attributed nothing on a real 233-file
extension: 1,606 coverage rows came back, `declaredRows` was 0 for every test, and all 147 mutants
were reported `no-coverage`. The same suite killed 73 of 147 with `coverageMode: "none"`, so the
code was reachable from the tests all along and only the attribution was empty.

The root cause was in `AppMethodIndex.fromSymbolReference`
(`packages/runner/src/app-package.ts`), fixed in the commit that files this row. It read the object
arrays at the ROOT of `SymbolReference.json` only. A namespaced app puts nothing there. Measured
with `alc` 18.0.2668733, compiling one codeunit twice:

```text
plain                                     Codeunits: [1]
namespace Pageworks.Barcode.Engine;       Codeunits: [0]
                                          Namespaces: [1] -> Pageworks -> Barcode -> Engine -> Codeunits: [1]
```

One nesting level per dotted segment, each level carrying its own full set of object arrays.

**Why this row exists rather than just the fix.** The fix is a recursive walk and is unit-tested
against the measured shape. The GAP it exposes is not fixed: **no fixture in this repository is a
namespaced app**, and namespaces are the modern default for an AppSource extension. Every live gate
(`itest:bcdev`, `itest:tables`, `itest:alrunner`, `itest:envtool`, `itest:chunked`) ran green
throughout, because all of them mutate apps whose objects sit at the root of the symbol reference.

So the class of defect remains uncovered end to end. A future change to symbol-reference reading,
line-map scoping or coverage attribution can break every namespaced project again and no gate will
notice. The unit test pins the parse; nothing pins the pipeline.

**What would close it.** A namespaced fixture measured live. The cheapest honest version is to add
a `namespace` declaration to one existing fixture and re-record that gate's baseline, since the
verdicts should not move: a namespace changes symbol-reference layout and object naming, not
behaviour. That prediction is exactly the kind worth pre-committing before the run, because if a
verdict DOES move, the namespace is affecting more than layout and that is worth knowing.

**Severity, stated plainly.** This failed silently and favourably. Nothing errored, the run
completed, and the report read as "your tests do not cover this code". The doc comment above
`warnOnThinFencedCoverage` already described that outcome as the most reassuring possible
misreading, and it took a user running a real app to find it. The warning fired correctly and named
the two candidate causes, but printed neither side's keys, so the reporter could not tell from the
outside which one it was. Making that warning carry a sample of the rows' `(type, id)` keys and a
sample of the declared set is a smaller, separate improvement worth doing.

See also [[R210]], another defect found by measurement against real code rather than by review.
