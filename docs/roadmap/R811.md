**Filed 2026-11-05 by lethal-preproc, from coord task R-810.** Related: [[R422]], [[R780]], [[R809]].

**Why R-809's hand alc failed and LethAL's D1 does not.** [[R422]] rewrites `\` to `/` in the `logo`, `screenshots` and
`resourceFolders` of the app.json LethAL writes for each TARGET batch (`normaliseAppJsonPaths`, from
`writeStampedAppJson`). A hand compile of the project does not go through that. Nothing changed in alc 18.1: R422
measured the same AL1001 on 18.0. How R-794's hand compile passed is not known (its scratch copy is gone).

**The gap.** Two paths compile the TEST project where it stands, with its raw app.json, so R422 never reaches them:
- v3: `compileTestAppAgainst`, on every `lethal run --backend al-runner-v3`;
- bcdev: `compileTestApp` in `test-app-publish.ts`, which `lethal verify` uses.

`compile-fixtures` compiles only our own fixtures (all `"logo": ""`), and the setup script only our apps.

**Measured (2026-11-05, alc 18.1, gift card on v3, no BC server).** A scratch copy of the tests with `"logo":
"Images\\Logo.png"` and the file present: exit 1, `TestAppError` compile-failed, `AL1001`, no mutant scored. The same
copy with `/`: exit 0, 34 / 15 / 11, the gift card's own figures. So the `\` is the only cause. `resourceFolders` gives
`AL0863: The folder 'Res\Sub' does not exist`. bcdev's `lethal verify` path was read, not run (no server).

**Can a real project hit it?** Yes, on a Linux host. It fails loudly and scores nothing, so no verdict is at risk. Of
the corpora here, `DC/FR` carries a backslash logo on a target (R422 covers that). `DO/Test` and `CDO/Test` carry a logo
in a test app, with `/`. No test app here has a `\` today; one made on Windows could.

**Fixed.** The refusal said the test app "does not compile against this batch", which sends the user to the wrong
place. Both paths now add what happened and what to write (`testAppBackslashHint`). It reads alc's own text, so only
AL1001 or AL0863 naming a `\`, on a non-Windows host, gets it, and a project that compiles is not touched.

**Not built at first: rewriting it as R422 does.** That means compiling a COPY of the test dir, because LethAL never
changes the user's project. v3's proof reads the test dir after the compile and alc can write there (R780).

**Plan (R-812).**
- **Only a project that needs it changes path.** `normaliseAppJsonPaths` moves to its own module, so `test-app-publish.ts`
  can use it without an import cycle. With no `\` in `logo`, `screenshots` or `resourceFolders`, alc compiles the test
  dir in place, exactly as today: same bytes, same order, same cache key.
- **With a `\`:** the test dir is copied to a scratch folder LethAL owns, and that copy's app.json gets the rewrite. The
  user's project is never written. The copy drops only `.alpackages` and `.git`. It must not use `isToolResourcePath`:
  a dot-directory can hold real `.al` source.
- **What alc compiled.** The copy's app.json is `normaliseAppJsonPaths` of the app.json bytes in the `pre` read, not a
  re-read. Every other file is the test dir's. So alc compiled: the `pre` bytes, plus a pure function of them.
- **The key and the proof.** Both keep reading the TEST DIR's raw bytes, as today. The rewrite is a pure function of
  bytes the key already covers, so one key still means one compiled input, and a hit stays a hit.
- **The new hole, closed.** On this path alc reads a copy, so a file that changes after the copy and before `post`
  would leave the proof naming bytes alc never saw. So here `post` must equal `pre`, or deploy stops. In-place
  compiles keep today's rule, because real alc can write there (R780). alc's writes land in the copy and are dropped:
  the proof never sees them, and an strace of a whole D1 run (R790) shows al-runner opens no `.xlf`.
- **What al-runner reads:** the test dir, raw `\` included. Only alc is affected, measured by comparing per mutant.
- **bcdev (`lethal verify`).** Same helper. Here the compiled `.app` is what gets published, and it carries the rewritten
  logo path. The `package:` hash is taken from those bytes, so it stays bound. This needs a BC leg, which waits for
  allocation.
- **The warning.** The same `app-json-backslash-path` code, once per session, naming the test project.
- **R-810's hint is removed:** after this, no `\` can reach alc in those three fields, so it would be dead code. A real
  missing file still fails with alc's own AL1001, by name.
