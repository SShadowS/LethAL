**Filed by** PR-456 (lethal-code, 2026-11-26), on the orchestrator's word. The cost was measured by lethal-bugs on
PR-427: three bc4 restarts in one day voided about 2,800 decided verdicts.

- **Today.** R680 records LethAL Control's server generation and refuses `--resume` and `--resume-run` when it has
  changed (`ServerGenerationChangedError`).
  - R969 added a database id that `force-reset-lease` never touches, so a lease reset on a SURVIVING database carries.
  - A restart that loses the database still refuses. That includes every restart of the Linux BC servers, whose
    databases are in memory.
- **R959's ruling** kept that refusal: re-verifying the published apps (ids, versions, hashes) cannot see company data,
  and a fresh container with the same apps republished would pass it.
- **The new condition** (the orchestrator, 2026-11-26) answers R959's objection with a measurement. Earlier verdicts
  carry only if both hold:
  - the re-setup republished the SAME apps (target, tests, dependencies, control app: ids, versions and hashes);
  - the resume's FRESH baseline equals the stored baseline per test.
  - The baseline measures what the company data does to the tests themselves.
  - Verdicts from a degraded window (R1227) or a lost batch never carry.
- **Design:** PR-456, `docs/superpowers/specs/2026-11-26-pr456-resume-across-restart.md`.
- **First POSITIVE live proof (lethal-bugs, PR-427, 2026-11-28).** bc4 and bc5 were both restarted ~09:30Z, which lost
  their in-memory databases. The restart was asked for because the tier was degrading (R1228), not for this test.
  - **Setup:** LethAL 07e94cc2c `--no-kill-ledger`. Both servers were set up again with the SAME saved files: target and
    test `.app` (sha256 `9018b8b5…` and `f5abccd7…`), LethAL Control 1.0.0.29 and 7 dependency apps. The doctor was clean;
    then `--resume` ran with the same scope. Evidence: `/coord/handoff/PR-427/f2-header/` and `/coord/handoff/PR-427/f4-a/`
    (`report.part1.json`, `events.part1.ndjson` for run 1; `stderr.txt`, `events.ndjson` for the resume).
  - **bc4: 258 of 258 survivors carried.** The fresh baseline equalled run 1's (667 tests), and all 41 prior kills were
    re-run with the prior killer tried first. The 171 errors were re-executed and no-coverage was re-derived, as
    designed.
  - **bc5: 79 survivors carried, against the "at most 133" the resume announced.** The fresh baseline was equal, and 72
    of 115 prior kills were re-run.
    - **Gap open:** 54 survivors are not accounted for in the resume's own messages. The 43 kills are only not yet
      reached: kills always re-run.
      - **Ruled out by lethal-code** (read-only, store copy, 2026-11-28): R646 (all 133 ran every covering test in run 1,
        with the same covering set now), the refused-tests drop, the identity key (generation, dependency and source
        hashes equal; ordinal, procedure and astHash equal per site), and batching (one batch, 403 sites on both sides).
      - **Suspect, unconfirmed: R307's carry-disabled twins.** 41 of the 54 uncarried survivors share astHash and
        operator with another site, against 32 of the 79 carried. A fail-closed rule drops such a mutant when its coarse
        tuple matches a site the run numbered no ordinal for, and it says so only as a count.
      - A survivor that is not carried is re-run with no warning that names it; that silence is a gap of its own.
      - Confirming it needs an offline replay of the resume index on the saved manifest
        (`/coord/handoff/PR-427/f4-a-carry/`). lethal-code asked the orchestrator to file that task.
    - Whatever the cause, nothing carried that should not have. At worst survivors are re-run instead of carried: a cost
      question, not a verdict one. If R1229 failed to carry survivors it should have, that is filed as its own R item.
