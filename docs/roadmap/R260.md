id: "R260"
title: "A test project nested inside the target project makes any edit to it refuse lethal verify with source-changed, blocking the write-a-test-then-verify loop for that layout"
section: "product-gaps"
status: "open"
order: 964
---

**What.** `hashTargetSource` deliberately hashes a test project's `.al` files too when that test
project lies inside the target project's own directory tree, because the target build copies them
in. `assertSourceUnchanged` compares this hash against the one the source run recorded and refuses
`source-changed` on any difference. So for a project laid out with its tests nested under the
target, editing or adding a test, exactly what someone verifying a survivor is expected to do,
changes the hash and `lethal verify` refuses before it runs anything. The refusal text names this
case explicitly and tells the caller to run `lethal run` again, which is not the loop verify exists
to shortcut.

**Why the hash rule was not changed.** Decision 8 chose to hash the nested test project on purpose:
the target's installed build really does contain those files, so excluding them would let a
build-affecting edit slip past the source-changed check. The gap is real for the write-a-test loop,
but narrowing the hash risks exactly the false-negative the check exists to prevent, so it was left
as a named, deliberate limitation rather than special-cased.

**Evidence.** `assertSourceUnchanged`, `hashTargetSource` (`packages/runner/src/verify.ts` and
`packages/runner/src/baseline-snapshot.ts`), and the `source-changed` refusal wording's own nested-
test sentence. Carried as item 3 from C02-06 part a's final review.

**What would close it.** A layout where the test project sits beside, not inside, the target
(already the recommended shape per the refusal text), or a source hash that can distinguish "a test
file changed" from "a target file changed" and only refuses on the latter.
