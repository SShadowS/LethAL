**Mutation sites written inside `tableextension`/`pageextension` are refused.** `OBJECT_KINDS` (`packages/builtin-tier2/src/receiver.ts`) omits extension objects, so no Tier-2 operator claims anything declared in one. Safe direction — a missed site costs one operator's signal — but a great deal of real BC code lives in extensions, so the practical coverage loss on a customer project could be large. (The *shadowing* half of this was the unsafe direction and is fixed: `resolveTable` now scans `tableextension` objects targeting the resolved table.)

**Why the remaining residual is not an R30 item.** The row's last unproven claim was that "the
pageextension half is claimed, deployed and never executed", because a pageextension's code is only
reachable through a `TestPage` and a TestPage cannot run on the fenced path. That was a live
question while R69 was open. R69 is now closed: recovery was measured at 2.30% of a real app's
deployable mutants and the routed path was DELETED (`c1da575`). So those four `no-coverage` verdicts
are the product's stated answer, not a gap waiting on R30, and the report names the refusal.

**The other residual is real but belongs elsewhere:** nothing has exercised a `pageextension` on a
real customer project end to end. The MECHANISM was measured on one before it was built
(`scripts/probe-r30-pageext.ts`: 18 Tier-2-shaped calls on records declared inside pageextensions on
Document Output, against zero on a pageextension's implicit `Rec`), which is what this row promised.
Scoring one live is a coverage question about TestPage-reachable code, which is R69's closed ruling
again, not an extension-support question.
