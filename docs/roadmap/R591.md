**Filed 2026-10-21 by coord task R-589** (lethal-code), found while writing `scripts/bc-linux-setup.ts`.
Not measured live; read from the code.

R589's three BC on Linux servers share one host (192.168.2.157) and differ only by port (OData
7048/7148/7248, dev 7049/7149/7249, API 7052/7152/7252). Three places assume the default ports:

- **The itests build their OData URL with `odataBaseUrl(bcdev.server, bcdev.serverInstance)`**
  (`bcdev.itest.ts`, `tables.itest.ts`, `hang.itest.ts`, `harden.itest.ts`, `bcdev-names.itest.ts`
  and the rest), and `odataBaseUrl` forces port 7048. They ignore `bcdev.baseUrl`, which
  `odataCfgFor` (cli.ts) honours. A `bc2` config would run its OData traffic against `bc1`.
- **The itests pass no `port` to `BcDevMcpBackend`**, so bc-dev-mcp falls back to its 7049 default.
- **`ContainerDeployer` (publisher.ts) passes only `server` to `altool publishapp`**, in the itests
  and in `cli.ts`'s `buildBackend`. Whether altool honours a port written into `--server` is not
  measured.

bc-dev-mcp's Automation API calls default to port 7048 too; the setup script sets
`BC_DEV_API_PORT` in the config's `env` for that, which bc-dev-mcp reads.

**Effect:** until this closes, only `bc1` can run a BC gate. Writing a `bc2`/`bc3` config is safe
(the setup script and `lethal doctor` use the right ports); running a gate with one is not.

**To close:** the itests take OData from `odataCfgFor` and pass `bcdev.port`; the altool publish is
measured with a port in `--server` (or given its own flag); a unit test pins each; then R589's
per-server `itest:bcdev` proof on `bc2`.

**Folded into R-589 (orchestrator ruling, 2026-10-21).** Built on branch `lethal/r589`, not yet
proven live. `configuredOdataBaseUrl` (cli.ts) is the one OData derivation: `bcdev.baseUrl` when
set, else the 7048 one. `devPortOf` gives `bcdev.port` to every `BcDevMcpBackend` and
`ContainerDeployer` the itests build, and to `deployerFor`. `altoolServerArgs` (publisher.ts) sends
altool's own `--port` flag (listed by `altool publishapp --help`) when a port is known, and the old
argv when none is. `packages/runner/tests/port-wiring.test.ts` pins both directions on each plane
and scans the itests, so a new one cannot go back to `odataBaseUrl`. This item closes with R589.

**A fourth plane, found live on bc1 (2026-10-21).** `lethal doctor`'s `company` and
`test-app-present` checks failed with HTTP 404 "Resource not found for the segment 'BC'": the
harness sent its API reads (`api/v2.0/companies`, the automation `extensions` list) to the OData
root, and BC on Linux serves the API on its own port. New optional `bcdev.apiBaseUrl` (and
`ActivationConfig.apiBaseUrl`) carries the API root; absent, API reads stay under the OData root as
before. The setup script writes `http://192.168.2.157:<api>/BC`; that path is BC's usual API shape
and bc-dev-mcp's, not yet measured on bc1.

**Known argv change (build review L3).** A config whose `server` carries a port (`http://bc:7049`)
used to send it to altool verbatim; it now sends `--server http://bc --port 7049`, dropping any path
on `server`, and a config that set `port` (once meant for bc-dev-mcp alone) now also sends
`--port`. Equivalent for altool by its `--help`, not measured.
