**What.** R272 asked for a gap's covering tests ranked by reach, then by duration. `lethal explain`
shows each test's `baselineDurationMs` but orders by reach, then by name (`compareCodeUnits`): the
duration is displayed, never a key (orchestrator ruling 2026-10-06, R-272b option (a)).

**Why not a key yet.** R197 already tried baseline duration as a test-order tie-break, and the
tables gate's two-pass check refused it: ten `killingTest` values differed between two consecutive
runs, because a test's duration differs between runs (`packages/runner/src/test-order.ts`, module
comment). On bcdev the recorded figure is the per-test call's wall clock, mostly call overhead
(`runOnHub`'s comment: seconds of overhead against tens of ms of test body), and the first call of a
session pays the MCP spawn (`connect()` caches the client), so the first-discovered test reads
slowest every time.

**What would close it.** Measure, from two runs of one fixture's `test_results.duration_ms` (or the
report's `testMethods[].baselineDurationMs`): how often two tests swap rank between runs, and how
large the first-test bias is. If the spread between tests is above the run-to-run noise, make
duration the second key (possibly dropping each batch's first dispatched test, or using BC's own
in-VM figure, which `runOnHub` receives and discards); otherwise close this as a ruling.

**Found by.** R-272b's plan review (B3), 2026-10-06.
