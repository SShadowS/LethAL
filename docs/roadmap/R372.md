id: "R372"
title: "A test edited on disk but not republished runs its OLD body in lethal run, yet the run records the NEW body's digest, so verify reads the edit as already measured"
section: "correctness-risks"
status: "done (ad8e544f)"
order: 1059
---

**What.** `lethal run` treats publishing the test app as the user's own workflow. R-278 records
each test's digest from the test source ON DISK (`orchestrator.ts`, right after `discoverTests`),
on the assumption that the server's test app was built from that source. Nothing checks that
assumption for a test whose body changed:

- R56/R139's guard refuses only a test the server does not have at all: `StaleTestAppError` is
  thrown when the baseline answers `found 0` (`missingFromServer` in `scoreBatch`,
  `packages/runner/src/orchestrator.ts`).
- R139 check 2 compares the published package's version and test NAMES with the local ones
  (`comparePublishedTestApp`, `packages/runner/src/published-test-app.ts`) and only warns
  (`published-test-app-mismatch` in `reportPublishedTestApp`), never refuses.

So a test edited on disk and not republished runs its old body on the server, while the run records
the new body's digest. A later `lethal verify` (which republishes the test app from disk) sees the
on-disk digest equal to the recorded one and treats the test as old, so the edit skips the new-test
checks (R-278) or is not selected at all (R258): the unsafe direction.

**Evidence.** The two sites above, and R-278's recording site in `runSession`.

**What would close it.** Digest the tests from the AL source inside the PUBLISHED package, which
R139 check 2 already downloads (`reportPublishedTestApp`), and record those digests, or refuse the
run when they differ from the on-disk ones. On al-runner, where nothing is published, the on-disk
source is what runs, so the current recording is already right there.

**Closed.** On a backend that publishes, `runSession` now digests the `.al` entries of the published
package that R139 check 2 already reads (`reportPublishedTestApp`, `testAppIdentity`), never the
disk. Where that source cannot be read (no `.al` entries, a test the package lacks, a failed read, a
request that cannot be formed, or an env-tool session that publishes its own test apps after the
read) the run records NULL and warns `test-digests-unavailable`; al-runner keeps the on-disk digest.
The probe (`scripts/r372-package-source-probe/RESULTS.md`) measured that the dev `/packages` read
returns the exact published `.app` with its source under every `resourceExposurePolicy` tried, and
the OLD body after an unpublished edit. The env-tool gap is R373.
