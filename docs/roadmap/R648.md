item takes R648.

**What.** The first `bun scripts/verify.ts` on master 08f9f88f (R-614's merge) reported two failures named
`(unnamed)`:
- `scripts/snapshot-late-write.test.ts`, after 5.07 s;
- `packages/runner/tests/r619-one-lend.test.ts`, after 6.66 s.

Another verify overlapped that run (`/coord/locks/verify-ledger.tsv` records the overlap). Both files pass alone, and a
full re-run passed (9817 / 0). The shape is bun's default 5 s timeout firing on a hook or a slow test under parallel
load: an `(unnamed)` failure is how bun reports a hook (for example `snapshot-late-write.test.ts`'s `afterAll`) that
timed out, not a test that asserted wrong.

**Why it matters.** A flaky red verify costs a re-run and can hide a real failure behind "it was just load". Verifies
overlap more since the container allows three heavy jobs.

**To close.** Measure first: which hook or test in each file takes the time, and how long it takes alone and under one
overlapping verify (`verify-ledger.tsv` gives the overlap). Then either make that work cheaper, or give exactly that
hook or test an explicit timeout with a comment naming the measured cost. Do not raise the global default. A red
check: the explicit timeout reverted, run under a forced overlap, goes red again.

Evidence: `scripts/snapshot-late-write.test.ts`, `packages/runner/tests/r619-one-lend.test.ts`, the verify ledger.

## Done (R-648, c0e269ed)

**What "(unnamed)" is.** Measured on bun 1.4.2: a timed-out `beforeAll` or `afterAll` is reported as `(unnamed)`
(a slow `beforeEach`/`afterEach` or test is reported under the test's name). Each hook has its own 5 s budget. So
both failures were file-level `afterAll` hooks: the file's own (`snapshot-late-write`'s folder removal; for
`r619-one-lend`, the `scratchDirs` helper's removal of its 62 folders) or the preload's (`test-preload.ts`, once
per file under `--parallel`). All three delete folders on the shared disk, so a disk stall, not CPU, sets their
time. The old log cannot say which of the two fired.

**Measured.** Alone and beside a second full verify these hooks take 0 to 85 ms, and the tests 1.0 s
(`snapshot-late-write`, which runs a child `bun test` that sleeps 1 s) and at most 0.33 s (`r619-one-lend`). Two
overlapping verifies alone never reproduced the failure (0 of 14 legs). With 3 disk writers added (R-616's
stand-in) the same hooks reached 307 ms, other files' disk-removing `afterAll` hooks 2.45 to 3.44 s, and
`snapshot-late-write`'s tests 3.5 s.

**Fix.** Those three `afterAll` hooks and `snapshot-late-write`'s three tests get their own 30 s timeout, with the
measured cost in the comment; the global default is unchanged. Red check: a 6.7 s stall injected into either
`afterAll` goes red as `(unnamed)` in both files without the timeouts, and green with them.

**Widened: `baseline-wiring.test.ts`** ("no non-test source ... writes a baseline"). CPU-bound: it built a
TypeScript program over all 401 scanned files (7.0 MB) and checked each: 2.2 s alone on Linux, 2.85 to 5.44 s
beside a second verify (one leg failed at 5437 ms), 6656 ms on master CI's Windows `check` (run 39778141456,
attempt 1). **The full scan is kept** (orchestrator ruling): a text pre-filter on `LOOKS_LIKE_BASELINE` halved the
time and reads as exact, but a guard that could stop guarding to save 3 s is a bad trade, so it was built, then
dropped before submit. What stays:
- the test's own **30 s timeout**, about 4.5x the 6.66 s Windows time and well under verify's 180 s watchdog;
- a pure short-circuit that skips checker lookups while no baseline variable is known yet (with an empty set no
  identifier can match, so the result is identical).
