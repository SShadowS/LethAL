**A failed tool spawn can report nothing at all — and it happened again on the PUBLISH path 2026-08-05.** Second measured instance: an env-tool publish of a 660-guard instrumented file failed and surfaced as a bare `Error` with no text at `bcdev-backend.ts:468`, exactly the shape R64's wrong-platform binary produced. The user sees a stack trace and no cause; the actual cause was a proxy timeout (R90). Confirms this is a CLASS rather than the single path R64 fixed. Original text follows.  `ArtifactCompiler.compile`'s catch stringifies `err.message` (`packages/runner/src/artifact.ts`), and a Bun spawn `ENOENT` arrives with an EMPTY message — so R64's wrong-platform binary presented as a bare `Error` with no text, and took a long external debugging session to trace. The path fix removed one CAUSE, not the class: a missing exec bit on `bin/linux/alc` (the AL extension's own activation is what chmods those, so an unpacked-but-never-activated VSIX has them non-executable), a pinned `alcPath` typo, or a partial install all still land in the same silent catch. Fix: include `err.code`/`err.path` (and a `String(err)` fallback) in both spawn catches — `artifact.ts` and `publisher.ts`'s `altool publishapp failed` wrapper — and consider an existence/executability check inside `defaultAlToolPaths` so the failure names the file instead of the operation.
