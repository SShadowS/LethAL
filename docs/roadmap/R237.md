**Found in the C02-04 R232 review (2026-09-26), confirmed by reading.** `EnvToolClient.run`
(`packages/runner/src/env-tool.ts`) reports every failure as a plain `EnvToolError`: a spawn that
never started ("failed to run", e.g. a mistyped `envTool.toolPath`), LethAL's own timeout, a
non-zero exit, output that is not JSON, and an R107 `successWhen` mismatch all share one type
with no field to tell them apart.

**Consequence:** since R232 the R19 test-app publish runs inside the publication fence, and
`isConfirmedTerminalPublishFailure` (`orchestrator.ts`) reads any `EnvToolError` other than
BC's version-conflict text as UNCERTAIN. A tool that could not even be started never reached the
server, yet the session keeps the lease, writes a durable `container-needs-recycle`, and the
operator must recycle and run `lethal clear-quarantine`. The safe direction, but a false
quarantine. An unreadable `publishApps` file had the same problem and was fixed at the publisher
(`EnvToolPublisher.publishFile` now throws `ArtifactPrepareError`); the spawn failure cannot be
fixed there, because it happens inside the shared client.

**Fix shape:** give the shared client a typed signal for "the command never started" (its own
error class extending `Error` directly, or a field on `EnvToolError`) and have
`isConfirmedTerminalPublishFailure` treat it as pre-publish. Only the spawn-throw branch
qualifies; the timeout branch kills a process that may already have reached the server and must
stay uncertain. Test: a hook whose spawn throws ENOENT releases the lease and records nothing.

Not measured live.

**Done (6b277d14), 2026-09-30.** Measured first, offline, on Windows with Bun 1.3.14, calling
`Bun.spawn` exactly as `publisher.ts`'s `bunSpawn` does. Every never-started case threw
SYNCHRONOUSLY from `Bun.spawn` with no pid: a missing absolute path, a bare name not on PATH, a
missing relative path, an existing `.txt`, a directory and a missing `cwd` (all `ENOENT`), and an
`.exe` that is not a program image (`EUNKNOWN`, `uv_spawn`). Every started case RETURNED a process
whose `exited` resolved: killed by the abort signal (143, `SIGTERM`), exit 3, and non-JSON on exit
0. So the boundary is "`Bun.spawn` threw", not an error code, which would have missed `EUNKNOWN`.

`bunSpawn` wraps only that throw in `ProcessNotStartedError` (its message is `describeThrown` of
the cause, so other callers print what they printed before). `EnvToolClient.run` maps only that to
`EnvToolNotStartedError`, which extends `Error` directly and carries the tool path, the redacted
command and the cause. `isConfirmedTerminalPublishFailure` reads it as confirmed terminal, so the
fence ends the publish as `failed` and releases the lease. A timeout, a non-zero exit, a killed
tool, non-JSON output and any other spawn rejection stay plain `EnvToolError`s and quarantine as
before. `EnvToolPublisher.publishFile`'s duplicate-package skip and R250's `publishing` identity
read only `EnvToolError`, so neither swallows the new error. Tests in
`packages/runner/tests/env-tool-client.test.ts` (one per measured case, real spawn) and
`orchestrator.test.ts` (the real fence: a missing tool releases, a timeout, a non-zero exit and a
started-then-killed tool quarantine), each red-checked.
