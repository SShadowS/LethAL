**Found in the C02-04 R232 review (2026-09-26), confirmed by reading.** `EnvToolClient.run`
(`packages/runner/src/env-tool.ts`) reports every failure as a plain `EnvToolError`: a spawn that
never started ("failed to run", e.g. a mistyped `envTool.toolPath`), LethAL's own timeout, a
non-zero exit, output that is not JSON, and an R107 `successWhen` mismatch all share one type
with no field to tell them apart.

**Consequence:** since R232 the R19 test-app publish runs inside the publication fence, and
`isConfirmedTerminalPublishFailure` (`orchestrator.ts`) reads any `EnvToolError` other than
BC's version-conflict text as UNCERTAIN. A tool that could not even be started never reached the
server, yet the session keeps the lease, writes a durable `container-needs-recycle`, and the
operator must recycle and run `lethal clear-quarantine`. The safe direction, but a false
quarantine. An unreadable `publishApps` file had the same problem and was fixed at the publisher
(`EnvToolPublisher.publishFile` now throws `ArtifactPrepareError`); the spawn failure cannot be
fixed there, because it happens inside the shared client.

**Fix shape:** give the shared client a typed signal for "the command never started" (its own
error class extending `Error` directly, or a field on `EnvToolError`) and have
`isConfirmedTerminalPublishFailure` treat it as pre-publish. Only the spawn-throw branch
qualifies; the timeout branch kills a process that may already have reached the server and must
stay uncertain. Test: a hook whose spawn throws ENOENT releases the lease and records nothing.

Not measured live.
