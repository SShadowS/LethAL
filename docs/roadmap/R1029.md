**Question.** DO scored about 260 covered mutants in a 3.5 h window (R-984 t3). Is it database rollback, timeouts, compiles, or
something else? These are the controlled measurements with invented apps on al-runner `serve`. Each daemon gets one warm-up
request, then requests shaped like LethAL's: per mutant an echo entry and the test codeunit's entry, each with its own
`active-mutant.txt` override. Times are `entrySummary.timings.wallMs` (median) and the summary timings.

**Per-entry cost, one factor at a time** (edge-5a58a0f16, `--bc-version 28`, test isolation; minimal app = 1 table, 1 test):

| factor | echo entry | test entry | note |
|---|---|---|---|
| minimal app | 0.5 ms | 0.5 ms | |
| 2,000 tables of 10 fields | 0.4 ms | 0.4 ms | compile 0.5 s once |
| 200 fields | 0.6 ms | 0.6 ms | |
| 1,000 resource files | 0.4 ms | 0.4 ms | |
| codeunit isolation | 1.1 ms | 1.1 ms | |
| same override for every entry | 0.4 ms | 0.4 ms | |
| test inserts 1,000 / 10,000 rows | 0.7 / 0.6 ms | 8 / 46 ms | the test's own work |
| 10 / 50 tests in the entry | 1.2 / 1.2 ms | 7 / 22 ms | about 0.5 ms per test |
| install inserts 1,000 / 10,000 rows | 5 / 46 ms | 8 / 46 ms | re-run per entry |
| install loops 5M times, no writes | 278 ms | 275 ms | re-run per entry; codeunit isolation 208 / 210 ms |
| install loops 1M times, 1 / 10 tests in the entry | 43 / 45 ms | 43 / 43 ms | per ENTRY, not per test |
| OnCompanyOpenCompleted inserts 1,000 / 10,000 rows | 6 / 56 ms | 6 / 53 ms | re-run per entry |
| depends on Base Application | 0.4 ms | 0.4 ms | + about 260 ms install baseline per REQUEST |
| DO's package set and build (edge-847b1fa5a), Base Application only | 0.5 ms | 0.5 ms | + 246 ms per request |
| the same with DO's five Continia dependencies | 0.5 ms | 0.5 ms | + 263 ms per request; warm-up 1.2 s |
| coverage | - | - | refused with entries ("coverage is not supported with entries") |

Request size is linear (DO's package set: 200, 1,000 and 4,000 entries in one request, about 0.4 ms each). Daemon age is flat
(300 requests in a row at about 0.34 s each; with 1,000 rows per test they drift to 0.64 s, with spikes up to 2.1 s).

**Compiles** (`cache-20k.ndjson`, an app of 2,000 procedures with 20,000 guarded statements). On one daemon every request shape
is `cached: true` (compileMs 0.5): other entry counts, test filters, `excludeTests`, test and codeunit isolation, no entries,
coverage, per-test coverage. A fresh daemon is always `cached: false`, even with the same `ALRUNNER_CACHE`: it compiles in
858 ms, while the disk cache saves only the setup (127 ms against 18.5 s cold). So there is one compile per DAEMON, never per
request. On DO that is about 29 s per daemon start (PR-18), and t3 started 53 daemons.

**Which factor reproduces DO's cost: none of the per-entry ones.** Every invented app costs under 1 ms of overhead per entry, DO's
package set and dependencies included. PR-18's trace of DO itself agrees: an entry's wall time is its tests' time plus about
10-20 ms per test. What DO pays for:
- test volume: each entry runs its whole covering codeunit, about 47 tests per mutant (PR-18), against a minority that cover it;
- restarts: each daemon start compiles again (#8143) and warms up over the union of codeunits seen so far, which on DO soon is
  the whole suite (111 codeunits, 1,973 tests, about 100 s per restart); t3 had 46 restarts, from 37 refusal closes and 5
  timeouts;
- per request: Base Application's install baseline (about 0.25 s) and, in baseline requests, coverage (3.8-5.2 s, PR-18);
- per entry: the install and company-open code of the app under test (#8144), small on DO (one install codeunit, one
  company-open subscriber in 589 files).

The t3 figure "8,521 entries" is mostly warm-ups: the 337 scored mutants needed about 1,635 entries (PR-18), so "0.67 s per
entry" was never a per-entry cost.
