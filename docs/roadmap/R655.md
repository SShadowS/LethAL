**Filed 2026-10-22 by lethal-code**, from R-652's measurement (`/coord/handoff/R-652/measure.md` §1) and its
plan review (`/coord/reviews/R-652-plan/adversary-r1.md`, item 5). This is an old gap. R652 did not cause it
and does not change it.

**What.** `AlRunnerV3Backend.assertBound` hashes the instrumented copy with `hashAlTree(active)`. That function
walks with `links: "skip"`, so a link is left out of the hash. It is only reported to `onSkippedLinks`
listeners. A link created under `active/` after the alc proof, pointing at a folder or file with `.al` in it,
leaves the hash unchanged, so the check passes. al-runner follows links, so it would read AL that alc never
proved.

The test dir already refuses this case: `hashTestDir` walks with `links: "refuse"`, and since R631 a link that
appears there mid-run is drift (`AlRunnerV3UnprovenBatchError`).

**Why it is small.** `active/` is LethAL's own staged copy (`stage` copies the batch into it), and the
user's target is checked for links before any compile (R631). A link there can only be added mid-run by
something outside LethAL. That is the same threat as an edit, which the check does catch.

**To close.** Hash `active/` under the R631 rule: a link refuses, as `AlRunnerV3UnprovenBatchError`, both at
`deploy()` and in `assertBound`. Add a red-going test in each direction: a junction holding an `.al` file
added under `active/` after `deploy()` is refused, and a tree with no link still runs. Also check whether
v2's `AlRunnerBackend` and the snapshot hash (`hashAlTree` callers) have the same gap.

**Done (d3867ec8, coord task R-655).** Class SMALL: the change can only refuse.

**Measured first** (`/coord/handoff/R-655/measure.md`): `active/` never legitimately holds a link.
`prepareBatchProject` walks the target under the R631 rule and writes every file with `copyFile` or
`writeFile`, which never create a link. `stage` and the resource selector use `cp` and `writeFile`. The
package cache is a separate folder. Every `active/` the last v3 itest left had 0 links. Bun's `cp` does
carry a link over, so a link in a batch dir would reach `active/`: that is why `deploy()` refuses too.

**Changed.**
- `hashAlTree` now walks under `hashTestDir`'s rule: a link refuses by name (`ProjectSymlinkRefusedError`).
  This covers all three callers: v3's proof at `deploy()`, v3's `assertBound`, and the orchestrator's
  baseline snapshot key (`batchHash`). The snapshot key had the same gap: a skipped linked `.al` was left
  out of the key, so a snapshot could be reused across two different builds.
- In v3, `linkIsUnproven` turns that refusal into `AlRunnerV3UnprovenBatchError` naming the link, at
  `deploy()` and in `assertBound`. The test dir's existing R631 catch uses the same helper.
- v2's `AlRunnerBackend` calls no `hashAlTree` and has no bound check, so nothing changed there. It is
  being retired under R654.

**Tests**, each red-checked both ways: a junction added under `active/` after `deploy()` is refused at the
next send; a link in the batch is refused at `deploy()`, before v3 starts; `hashAlTree` refuses a linked
folder and a linked `.al` file. A guard that refuses every tree turns the existing "an unchanged folder
runs" test red.
