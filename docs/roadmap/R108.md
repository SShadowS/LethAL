**A batch whose TOTAL guard count exceeds the measured publish ceiling still pays for the failure — R90 refuses per FILE only.** R90's pre-flight (`assertUnderCeiling`, `packages/runner/src/publish-ceiling.ts`) is called once per file, deliberately: batches split at file granularity, and a file that alone exceeds the ceiling cannot be rescued by any flag. But the ceiling is a property of what gets PUBLISHED, and a batch publishes several files at once — so N files each comfortably under the bracket can sum past it and time out, with nothing said beforehand. **Refusing that case would be wrong** and is deliberately not the ask: `--max-guards-per-batch` is exactly the lever for a batch total, so a refusal would be the false-refusal direction R90 was careful to avoid, and the user has a fix the tool should not pre-empt. The gap is that nothing WARNS. R90's own complaint was "nobody can discover the ceiling before paying for it"; for the multi-file batch shape that is still true after R90. Fix: when a batch's summed guard count crosses the tier's `smallestFailure`, print a warning naming the batch total, the measured bracket, and `--max-guards-per-batch` as the lever — a warning, never a refusal. Filed 2026-08-05 from subsystem C's Task 3 review; both directions (single file over the bracket, batch total over the bracket) already have tests, so the behaviour is measured, not assumed.

**Closed 2026-08-07. Shipped exactly as the row scoped it — a warning, deliberately not a
refusal.**

`batchCeilingWarning` (`publish-ceiling.ts`) fires from the same pre-flight block as
`assertUnderCeiling`, after the per-file loop so a genuine refusal preempts it, and still ahead of
compile and publish — which is the whole value, since R90's complaint was that nobody can discover
the ceiling before paying for it. The message names the batch total, the file count, the measured
bracket with its date, and `--max-guards-per-batch` with its current value; it also says in so many
words that this is **NOT refused**, because the reader's next question is why the tool did not stop.

**Why it must stay a warning**, restated in the code so a later session does not "fix" it:
`--max-guards-per-batch` is exactly the lever for a batch total, so refusing would be the
false-refusal direction R90 was careful to avoid — the user has a fix and the tool should not
pre-empt it.

**Tested at the SESSION, not at the function.** Three `runSession` tests drive a real two-file
project with a seeded `failed` publish row, and assert the `{ type: "warning", code:
"batch-over-ceiling" }` event. The seeded threshold is derived from the fixture's own per-file
counts (`max(perFile) + 1`) rather than hardcoded, so a fixture that grows a mutant cannot silently
turn this into a per-file *refusal* test still wearing a batch-total name — and one test asserts
`total > perFileMax` outright, since on a one-file project this warning is unreachable and the test
would pass having measured nothing.

**Red-checked at the call site**: neutering `if (batchWarning !== undefined)` in `runSession`
reddens the session test while all five unit tests of `batchCeilingWarning` stay green — which is
precisely the gap that would have gone unnoticed had only the function been tested.
