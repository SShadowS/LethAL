**Filed 2026-10-22 by lethal-preproc during R618** (orchestrator ruling 1a, from the R618 plan
review, finding I3).

**What.** [[R586]] added `runMayLend` (`store.ts`): the one run-level trust check, in a fixed order
(1: `backendBuildRefusal`, 2: R557's mark through `runLendsAlRunnerNames`, 3: R557 C1's renamed
baseline errors). No production code calls it. Its only caller is `tests/r586-run-may-lend.test.ts`
(R586's T14). `orchestrator.ts` imports only `backendBuildRefusal` and `runLendsAlRunnerNames`, and
each lend site copies the steps inline, with its own checks in between:

- **History**, `ResultsStore.priorSurvivorKeys`: step 1, then identity scheme, coverage mode, test
  app, build symbols, `carry_hidden`, hidden files, then step 2, then step 3 (only when the caller
  passes `alRunnerTestNames`).
- **`--resume`**, `resolveResume` (`cfg.resume === "last"`): `findResumableRun`'s SQL (same
  backend), then step 1 (`assertLends`), test app, symbols, `carry_hidden`; step 2 and step 3 come
  after, and are a WARNING with an empty carry (`resume-al-runner-test-names`), not a refusal.
- **`--resume-run`**, `resolveResume` (a run id): project, then backend EQUALITY, then step 1, then
  scheme, mode, test app, symbols, fingerprint, `carry_hidden`; then step 2 and 3 as for `--resume`.
- **Baseline-snapshot reuse**, `scoreBatch`: `findBaselineSnapshot`'s SQL, then step 1
  (`snapshot-backend-build-changed`), step 2, then step 3 on the snapshot's OWN error rows rather
  than `baselineErrorMethods`, then the R-236c scope check.

So the four copies already differ in order and in what a refusal does, and none of them is the
function the tests pin.

**Why it matters (a test passing for the wrong reason).** T14 proves `runMayLend` refuses in the
right order. It passes whatever any production site does: reorder a site, drop step 1 at a site,
or change what a refusal does there, and T14 stays green. The R586 order is the safety argument
for every lend (a v3 verdict must never reach another backend or build), and a regression at one
copy is invisible to it. [[R618]]'s gate covers only the sites a bcdev session reaches (history
step 1, snapshot step 1); the resume sites' step 1 is unreachable on bcdev.

**To close.** Make every site call `runMayLend` (or one function per site that wraps it), and
delete the inline copies, so the tested function is the one that runs. Or, if the sites must keep
different orders, delete `runMayLend` and give each site its own order test, red-checked per site
(delete the call at that site, its test goes red). Either way, no test may pin a function with no
production caller.

## Done (2026-10-22, R-619)

Plan: `docs/superpowers/plans/2026-10-22-r619-one-lend-decision.md` (its r2 section rules).

- **One decision.** `runMayLend` is now a method, `ResultsStore.runMayLend`, and the four lend
  sites each call it exactly once: history (`priorSurvivorKeys`), `--resume` and `--resume-run`
  (`resolveResume`, through one local helper called in each branch), and baseline-snapshot reuse
  (`scoreBatch`). The order inside is fixed: step 1 (backend and build), then the site's own checks
  (a new `siteChecks` slot), then R557's mark, then the renamed baseline errors. That is the order
  every site already had, so no outcome moves. The inline copies are gone (`assertLends`,
  `lendWhy`, the resume step 2/3 expression, the two snapshot R557 blocks).
- **One deliberate change (orchestrator ruling b).** A snapshot whose run row is missing now
  throws instead of being reused. `findBaselineSnapshot` only returns snapshots whose run exists,
  so this cannot happen in production.
- **Evidence of no outcome change.** `tests/r619-one-lend.test.ts` runs R586's T14 cases through
  the real sites and checks only effects (lend or not, the throw, the warning code and text). Its
  33 effect tests passed on master before the build (`/coord/handoff/R-619/effect-tests-on-master.log`).
  It also covers review I1: a renamed error only in the snapshot itself refuses; one only in the
  run's own baseline rows does not.
- **The test that would have caught this.** The same file logs every `runMayLend` call per site
  (a spy on the method), so deleting one site's call, or changing the step order, goes red. Red
  checks, one per site and per step: `/coord/handoff/R-619/redcheck.md` (11 breaks, all red).
  `--resume`'s step 1 cannot fire in production (its SQL already selects backend and build), so
  step 1 is red-checked through `--resume-run`. The build review added one more `--resume` order
  test (a changed test app wins over R557's mark), red under the same order break.
- **Live gates, figures unchanged.** `itest:lend` and `itest:bcdev` PASS on bc1, and
  `itest:alrunner` PASS (`/coord/handoff/R-619/lend-bc1.log`, `bcdev-bc1.log`,
  `alrunner-final.log`).
