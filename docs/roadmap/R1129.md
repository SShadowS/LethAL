Found by coord PR-161 (lethal-bugs, 2026-11-18). CI run 44359001306, attempt 1, on branch lethal/pr-161 (a docs-only change: one roadmap
file). The Windows `check` job failed with 2 tests. The same commit's re-run of the failed job passed, and master was green at the
time.

**The two failures (attempt 1's log):**
- `R622 the per-file watchdog > isChildOf: a live child of this process is one; this process and a dead child are not` timed
  out after 60,000 ms. Its own timeout is `ownTimeout(30_000)`, raised to the shared 60 s on Windows CI (R726c). The test makes up
  to three PowerShell calls for the parent table, "1 to 3 s each when cold" by its own comment, so 60 s means a stalled call, not a
  wrong answer.
- `R622 the per-file watchdog > serial: a file that spins past the limit stops the run in seconds, named once` failed
  `expect(r.seconds).toBeLessThan(15)` with 17.484. The watchdog did its job: it printed its FAIL line for `spin.test.ts` once.
  The run as a whole took longer than the test's wall-clock bound. The same output also carries the test child's
  `snapshot guard: CI=true ... a missing snapshot is refused` line, from the spawned verify, which reads as noise around the bound.

**Why it is a defect.** CLAUDE.md asks for phase ordering to be asserted with call counters on stateful fakes, never wall-clock
timing. A watchdog is about time, so a bound is natural here. But the 15 s total and the stalled PowerShell call measure the
runner's load, not the watchdog. On a slow Windows runner they redden an unrelated change. Each such run emails the owner, and it
invites "just re-run", which hides a real failure the next time.

**To close (proposal, for the lane that owns verify.ts):**
- The serial test asserts what the watchdog reports: the FAIL line once, and the kill time its own line states (at most the limit
  plus the grace, from the reported time, not from the wall clock around the whole spawned run).
- isChildOf moves its PowerShell table read behind one injectable reader, so the unit test checks the parent logic with a fake
  table. One separate test may keep a single real OS read, with the Windows timeout named.
- Red-check each change both ways (R-427).

**Fixed by coord PR-164 (lethal-bugs, 2026-11-18; `/coord/handoff/PR-164/result.md`).**
- `isChildOf(pid, parent, read = parentTable)`: the OS read is injectable.
  - Its unit test runs on a fake table. A live child is one; the process itself, a wrong parent (a reused pid) and a gone pid are
    not; each question asks for that pid only (a call counter, no time).
  - One test keeps a single real OS read of `parentTable`, one PowerShell call on Windows. A Linux-only test checks that an ended
    child is absent from the real table.
- **The serial spin test** asserts what the watchdog did, not the time it took:
  - the FAIL line once;
  - a stop line it printed (SIGTERM sent, or the backstop);
  - and in junit, `spins` did not pass. SPIN ends by itself after 25 s and then passes, so this tells the watchdog's stop from the
    file ending on its own.
  - This differs from the proposal above: it uses the junit status instead of the reported kill time, so no time is read at all.
- **Red checks:**
  - isChildOf ignoring the reader: red;
  - isChildOf not comparing the parent: red ("Expected: false, Received: true");
  - signals and the backstop's kill made no-ops while every line is still printed: red after 25 s ("Expected: not pass");
  - the SIGTERM line not printed while the kill still happens: red (the stop-line match).
  - Each was restored, and VERIFY FULL passed.
- Not changed: the Linux-only `--parallel=2` spin test keeps its `seconds < 15` bound. It is skipped on Windows and has not
  flaked; it can follow the same pattern if it ever does.
