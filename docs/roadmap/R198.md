**Measured.** On the hosted DemoPortal sandbox, 9,963 RunMutant calls averaged 462 ms (survivors)
and 513 ms (kills); the same test methods on a container this morning averaged 110 ms in the
baseline. The test itself is the smaller part on the sandbox; the HTTPS round trip, the session
setup and the fence's three phases are the rest. A survivor ran 35 tests on average and cost 17 s;
the run's 196 survivors cost 55 minutes, more than its 296 kills (26 minutes) despite being fewer.
The baseline has the same shape: 407 `RunMutantWithCoverage` calls, 215 s, on every batch and on
every [[R192]] resume.

**What would change it.** A `RunMutantMany` action on the control app: one request carries the
mutant id and a LIST of test methods; the server activates the mutant once, runs them in order
inside the same fenced session, stops at the first failure when asked to (the kill path), and
returns one result per method. The client then issues one call per mutant for a survivor instead
of 35, and the first-failure stop keeps the kill path as cheap as [[R197]] can make it.

**What has to hold.** The fence: phase 1 claims the op, phase 3 tombstones it, and today those
bracket exactly one test. Several tests inside one op means one `opSeq` for the group and a lost
ack that can only be reconciled for the group. The stop hook (R53) stops the session, which now
holds several tests' worth of state; the 408 must still be attributable to OUR stop. Coverage per
test for the baseline needs `StartApplicationCoverage`'s clear-on-start to be called per method
inside the group, or the baseline keeps the one-call shape and only the mutant phase batches.

**What is NOT claimed.** That a container run gets faster in proportion: at 0.11 s a call the
transport is a smaller share, and the per-test AL cost stays. The number to measure first is the
share of a hosted call that is round trip, by timing an empty RunMutant (a test that returns
immediately) against the same test's baseline duration.

## Review, 2026-09-02

The first design was written and put through the spec-adversary agent before any code. It was
refused, with reasons the row now carries in its status. The short version: grouping N methods
under ONE fence claim removes the per-op tombstone that makes R53's stop honest (a stop that lands
after method k passed and method k+1 began scores a kill nobody earned), the draft's progress
fields on the lease row would be written with a whole-record `Modify` from an unlocked read, and the
draft asserted per-method isolation across an added `Commit` without measuring it. None of those
is a patch; two are platform probes. The spec's REVIEW section lists all ten findings and the
prerequisites in order. The saving this row measured (survivors at 55 of 80 minutes on the hosted
run) is unchanged and still the largest left; it now has a price tag that includes two probes and a
progress table, and the second draft starts from the review's "sound and kept" list.

## Probed, 2026-09-03

The user's question, "why one call per test; can the runner iterate itself and keep progress
somewhere that survives the rollback?", was put to the platform instead of argued.
`scripts/r198-group-runner-probe/` (README has the table) measured on Cronus283:

- grouping N methods under the STOCK runner leaks one method's writes into the next (the control:
  `LEAK: K1 ... is visible in the next method`), which is the review's F5 made real;
- a runner with `TestIsolation = Function` rolls back per method inside one run, and a `Commit()`
  from its triggers does not carry the test's writes;
- a "current method" row committed by the runner (or by a server-side loop) is readable inside
  the tests AND from a second session mid-run, so the R53 stop can refuse a stale target (`stop
  for T1: refused: runner is at T7_Hang/before`) and end the right one (408 after 3.9 s of a 45 s
  bounded hang);
- `OnBeforeTestRun` returning `false` after the first failure skips the rest, and a skipped method
  never reaches `OnAfterTestRun`;
- a `SingleInstance` variable cannot serve the cross-session half: it is per session.

The shape that survives review is not the group but the LOOP: one HTTP call runs today's
one-method suite run N times in request order, writing committed progress between runs. Every
method is its own `CODEUNIT.Run` exactly as today, so isolation, `OnRun`, test-codeunit globals
and `RequiredTestIsolation` are all today's by construction, R197's order is kept, and the price
is ~25 ms per method on a container against the ~300 ms round trip it removes on a hosted
sandbox. Two independent models were consulted (gpt-5.6-sol named the globals/`OnRun` hazards of
grouping and proposed the loop; gemini-3.7-flash's answer was priors and is not relied on). Next:
redraft the spec around the loop, with a dedicated progress table, a per-method refusal in the
stop, the watchdog inside the transport, and the group answer asserted complete and identity-
matched; then the adversarial review again; then code.

## Built, 2026-09-03

Commit `0451532`, control app 1.0.0.17. What landed is the design as reviewed six times, and the
proof is where the design said it would be: a differential test (one fake backend with and
without `runMany`, identical verdicts, `killingTest` and `coveringTests`), thirty transport tests
against one fake fetch routed by action, the three gates pinning `groupedCalls` as NUMBERS (bcdev
15, tables 362, al-runner 0), and the hang gate's ON leg scoring its four hangs through
`RunMutantMany` + `StopHungRunAt` + BC's 408 with every timeout row carrying `op_kind = many`.

Two things the build found that the design had not:

- `RunMutantMany`'s answer to a client-chunked call is `complete` (the server ran everything it
  was given), so the client's cursor advances on `complete` as on `cap`; only `failure` ends the
  walk. The differential test with `--max-methods-per-call 2` is what said so.
- The "ours first" rule's own-attempt conjunct on the progress row was untested: the first red
  check left it green because every fake excluded the row on the marker first. The pinning test
  now uses the late-original shape R194 names (same opSeq, different attempt).

R202 stays open (a non-408 after a stop is never scored), R203 is closed by this build at both
grains, R204 is narrowed by the after-408 status read at both grains and stays open. The next
hosted run measures the prediction and R197's, R194's and R192's owed numbers with it.

**Run 3 on the hosted sandbox (2026-09-03 12:35 to 14:26), the measurement the prediction was
waiting for.** Same 741 mutants as run 2, `--stop-hung-sessions` on. Wall-clock **148 → 111 min**
and twelve loop iterations → one: the eight hangs scored `timeout-killed` through `StopHungRunAt`
and BC's 408 (the stop works on the hosted path; every stop answered 408, R202's 400 did not
recur), zero lost acks, zero quarantines. The same 237 survivors cost **4,163 → 3,165 s (−24%)**,
the same 439 kills 786 → 726 s. **The prediction (73 → 10 to 20 survivor-minutes) FAILED: measured
69 → 53.** The round trip is gone, but the loop spends **~330 ms per method on hosted SQL** where
the container spends 55 ms (probe E7): suite delete/create/select, ~80 line writes, the runner's own
commits, and two committed progress writes, per method. Hosted SQL commit latency is the floor now,
not HTTP; cutting the per-method database work is the next step and is filed under this row.
**And 8 verdicts moved `survived` → `killed`, which is [[R206]]**: a group call is one BC session,
`SingleInstance` state carries between a mutant's tests, and the design's isolation claim held for
the database only. Decision pending there.

**Before/after on the container gates, from their stores (2026-09-03).** The verdict gates
passed on the first build and said nothing about time; the wall-clock did. tables: 3.5 min before
R198, **32 min** on the first gated build, 3.5 min after one fix; bcdev: 6 s, 80 s, 6 s. The 28
minutes were the watchdog's 5 s sleep outliving each request (`await watchdog` waited for the
interval to expire after BC had answered), ~4.7 s × 362 calls. `settle()` now wakes the sleeper,
and a transport test pins that a call returns within a second of the answer under a 5 s poll
interval (red-checked: 5,001 ms with the wake removed). On a container the round trip is ~10 ms,
so R198 cannot make these gates faster in any visible way; the number to hold them to is "not
slower", and the first build failed it silently.
