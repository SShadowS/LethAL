**Measured.** On the hosted DemoPortal sandbox, 9,963 RunMutant calls averaged 462 ms (survivors)
and 513 ms (kills); the same test methods on a container this morning averaged 110 ms in the
baseline. The test itself is the smaller part on the sandbox; the HTTPS round trip, the session
setup and the fence's three phases are the rest. A survivor ran 35 tests on average and cost 17 s;
the run's 196 survivors cost 55 minutes, more than its 296 kills (26 minutes) despite being fewer.
The baseline has the same shape: 407 `RunMutantWithCoverage` calls, 215 s, on every batch and on
every [[R192]] resume.

**What would change it.** A `RunMutantMany` action on the control app: one request carries the
mutant id and a LIST of test methods; the server activates the mutant once, runs them in order
inside the same fenced session, stops at the first failure when asked to (the kill path), and
returns one result per method. The client then issues one call per mutant for a survivor instead
of 35, and the first-failure stop keeps the kill path as cheap as [[R197]] can make it.

**What has to hold.** The fence: phase 1 claims the op, phase 3 tombstones it, and today those
bracket exactly one test. Several tests inside one op means one `opSeq` for the group and a lost
ack that can only be reconciled for the group. The stop hook (R53) stops the session, which now
holds several tests' worth of state; the 408 must still be attributable to OUR stop. Coverage per
test for the baseline needs `StartApplicationCoverage`'s clear-on-start to be called per method
inside the group, or the baseline keeps the one-call shape and only the mutant phase batches.

**What is NOT claimed.** That a container run gets faster in proportion: at 0.11 s a call the
transport is a smaller share, and the per-test AL cost stays. The number to measure first is the
share of a hosted call that is round trip, by timing an empty RunMutant (a test that returns
immediately) against the same test's baseline duration.
