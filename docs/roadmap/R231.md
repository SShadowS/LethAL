---
id: "R231"
title: "Report lists that name mutants by `mutantCode` alone are ambiguous on a multi-batch run: ids restart at M0001 in every batch"
section: "correctness-risks"
status: "open"
order: 943
---

**Found by gpt-6-sol reviewing the C02-01 plan (2026-09-25), confirmed by reading.** `assignMutantIds`
(`packages/schemata/src/ids.ts`) numbers from `M0001` per artifact, and `planArtifacts`' doc
comment says so outright: "a batch boundary is where mutant ids restart"
(the doc comment on `planArtifacts`, `packages/runner/src/orchestrator.ts`). So on a run with `--max-guards-per-batch` (or any
multi-batch plan) two different mutants can both be `M0001`.

Several `SessionReport` fields name mutants by `mutantCode` alone, with no `batchIndex`:
`likelyEquivalentSurvivors.byRisk`, `readerMarkedEquivalent.matched`/`contradicted`,
`platformArtifactKills` lists, and the R175/R206 mutant lists (see the `mutantCodes, sorted`
fields in `packages/runner/src/report.ts` ~1041, ~1082, ~1247, ~1271, built ~2085-2207).

**Consequence:** a consumer joining those lists back to `mutants[]` by code can attach one batch's
risk, mark or kill mechanism to another batch's mutant. Every gate runs one batch except
`itest:chunked`, so no gate would notice. Single-batch runs are unaffected.

**Fix shape:** qualify each entry (`{ batchIndex, mutantCode }`, or a `B<n>/M<nnnn>` token) or move
the fact onto the mutant row. C02-01 takes the second route for `equivalenceRisk` and `readerMark`
on the rows it needs, and leaves these aggregate lists as they are. Changing a list's element shape
is a meaning change under R157 and bumps `REPORT_SCHEMA_VERSION`.

Not measured live.
