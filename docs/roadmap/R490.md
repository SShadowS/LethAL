**Found 2026-10-06 in the orchestrator's merge review of R-488** (opus adversary, R488's residual). Low likelihood.

**What.** [[R488]] excludes the requested test's look-alikes up front (from the discovered test list) and then
learns any extra name from a "tests" result. A run that ends at the deadline carries no test list, so the
learn step stops there. If a look-alike was NOT in the discovered list and it hangs under a mutant, the call returns
`deadline` and the requested test reads `deadline-exceeded`: the mutant is scored timeout-killed by a test that did not
hang. That is a false kill.

**Who can hit it.** Only a test that al-runner runs but test-project discovery misses: for example a
`Subtype = Test` codeunit inside the SOURCE (app) directory, since al-runner is given both directories. On a
normal layout the look-alike is discovered and excluded before the first call.

**To close.** Measure first whether any corpus has a test codeunit in the app directory. Then either seed
the exclude list from the source directory too, or refuse a one-shot deadline result while discovery is
incomplete. `--server` and resource legs are unaffected.

**Closed 2026-10-07 as a ruling (R-490).** The measurement is in the R-490 coord handoff (`measure.md`).
It holds names and counts only.

- **The premise was wrong.** A whole-call deadline in the one-shot `AlRunnerBackend.run()` returns
  `deadline-exceeded`. That is an ERROR, never a kill: scoring gives `timeout-killed` only for a test outcome
  `timeout`.
  - A look-alike that hangs inside al-runner is stopped by al-runner's own per-test budget. That budget is set
    deliberately below LethAL's deadline, so the look-alike comes back as its OWN row in the result.
  - R488's learn, exclude and refuse path handles that row.
  - The worst case is therefore a lost verdict (an error), not a false kill.
- **The shape is absent everywhere.** Measured on BC.History (519 project folders), CDO (6), DC (14), DO (7) and the
  17 master fixtures, the counts are:
  - 0 look-alikes;
  - 0 codeunit ids shared with a test codeunit;
  - 0 test projects nested inside a source project.

  Test codeunits sit in a source directory in only three places. Two are BC.History folders: a test library with no
  `[Test]` method, and the Performance Toolkit Samples app. The third is the single-project fixture
  `sandbox-coverage-probe`. None of them is a look-alike. Test discovery found 54,183 tests with 0 unsupported
  shapes and 0 errors.
- **The shape is narrow by construction.** A look-alike of `Codeunit<id>.<m>` must live in codeunit `<id>`.
  - Measured locally: al-runner does run a source-directory test codeunit, but a codeunit with a different id is
    not selected by the qualified pattern.
  - The SAME id fails to compile (exit 3), so no baseline passes.
- **Not built:** seeding excludes from the source directory (an extra full parse of the target for nothing), and
  refusing a one-shot deadline (it only renames an error cause).
- **Guard (test only).** `al-runner-backend.test.ts`, "a hang from an undiscovered look-alike is
  deadline-exceeded, never a kill (R490)". Red-checked: making the deadline path return `timeout` turns it red.
