**Noted by lethal-bugs while fixing GH-24's latch naming (2026-09-26); pre-existing, UNVERIFIED.**
`injectMutationSelectorVar` (`packages/schemata/src/compile.ts`) decides which object already received
the selector variable by comparing tree NODES by identity. In the implementer's scratch script, specs
found by two SEPARATE walks over the same object (one with a global `var` section) produced two
overlapping edits for that one object.

The real pipeline may never reach this: it walks each file once, so the specs share node objects. That
is why it is filed and not fixed. R209 set the rule that positions, not node identity, decide sameness;
this call site may not follow it.

**To decide it:** write the smallest test that feeds `compileSchemataForFile` specs from two walks of
one object with a global `var` section, and check whether the output has one selector variable or two.
If two, key the check on the object's start/end position (R209) and red-check.

**Closed 2026-09-28, `0185b3a` (R-297 Task 2).** Decided: the test was red at HEAD. Feeding
`compileSchemataForFile` specs from two separate tree walks over one object with a global `var`
section produced `overlapping rewrites in <file> at 31..54 (var_section) and 31..54 (var_section)`:
two distinct selector-variable edits at the identical span, exactly the overlap this item predicted.
`injectMutationSelectorVar` now keys its per-object dedup `Map` on the object's `startIndex` (R209)
instead of on node identity, so both walks land on the same map entry and only one selector variable
is emitted. Red-check: reverting to the identity-keyed `Set` reproduces the failure
(`R251: specs for one object from two separate tree walks yield exactly one selector`, expecting one
selector line and getting two). Found alongside, in a different function
(`injectSelectorVarIntoObject`) and fixed in the same commit: [[R297]]'s wide var-section-replace
edit, a second, distinct mechanism that also threw `overlapping rewrites` on two real corpora.

**A known risk accepted, not closed.** [[R297]]'s anchor fix makes the selector edit a zero-width
insert (`start === end`). `assertNoOverlap` only rejects `curr.start < prev.end`, so two zero-width
inserts at the identical offset sort adjacent and do not trip it: the guard would not catch a
duplicate selector if this item's start-offset dedup ever regressed. Only the `R251` test above
(one selector line, not two) still guards that case.
