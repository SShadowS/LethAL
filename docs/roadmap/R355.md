**Found by the review of R-354 run 001 (2026-09-30).** Review:
`H:/lethal-coord/reviews/R-354-001/review.md`, Important finding.

`freezeStageTo` (`packages/runner/src/campaign-freeze.ts`) stores normalized per-mutant verdicts, which
do not record the coverage mode, and `campaign compare` (`campaign-subcommands.ts`) compares them
without it. So a stage frozen under `procedure` coverage and a later run under `none` can compare
"identical" even though an unreached mutant means `no-coverage` in one and `survived` in the other.
It injects no old verdict into a new run (R354 covers that); it treats an old-mode baseline as valid
comparison evidence.

**To close.** Since R252 every new report records `coverageMode`. Make `campaign compare` read it
from the frozen stage report and the new report, and refuse by name when they differ, or when the
frozen one predates the field and the new one's mode is not the one the stage was frozen under
(decide how an old frozen stage without the field is handled; the safe direction is to say so,
never to assume). Test both directions, red-checked.

**Done 2026-09-30 (838d7379, docs 6734baf8).** Built to the orchestrator's ruling, which replaced
"refuse a stage that predates the field" with "compare it, and say so":
1. `campaign compare` refuses by name only when the stage and the report both record a coverage
   mode and they differ. The message names both modes, the stage and R355.
2. A stage with no recorded mode is still compared, but never reported as a bare "identical": the
   console says "coverage mode UNVERIFIED" and the `coverage` field of the new
   `campaign compare --json` document (`campaignCompareSchemaVersion` 1) carries the statement. The
   type `CompareCoverageMode` requires `statement` whenever `verified` is false. A report written
   before R252 gets the same treatment from its side.
3. `campaign freeze` writes the stage baseline as `{ "coverageMode": <mode>, "entries": [...] }`.
   The plain list form written before R355 is still read, with its mode unknown
   (`parseStageBaseline` in `packages/runner/itest/baseline-guard.ts`). Gate baselines are
   untouched.
4. `campaign freeze` refuses a report with no `coverageMode`, so every newly frozen stage is
   strict; a re-freeze under a different mode is refused too.

No committed baseline or report was rewritten or re-frozen. All six committed stage baselines are
the list form, and none of their reports records a mode, so every one now compares with the
unverified statement. Measured against each stage's own archived report, before and after: gift-card
`rehearsal` (60) and credit-limit `demo` (42) match, as before; DO `rung1` (224 differences),
DO `rung2` (772) and r85 swap-population `rung2` (748) differ exactly as they did before R355,
because R166 changed the identity key after they were frozen; DO `rung1.resumed-run` was already
refused for its missing pre-commitment. `baseline-guard.test.ts` pins that all six still read with
their mode unknown.
