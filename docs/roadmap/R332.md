**Found by the R-321 plan's review** (`H:/lethal-coord/reviews/R-321-plan/`): review r1's third
Important finding ("A missing 'frozen' baseline currently records itself and passes") and review
r2's Minor finding on making that a filed item rather than an open question. R321 fixed this for
its own two symbol baselines only ([[R321]]); this item is the general gap across every other
frozen live gate.

**The mechanism.** `assertMatchesBaseline` (`packages/runner/itest/baseline-guard.ts`, lines 60-61
at `b8e1d70c`):

```ts
if (baselineRaw === undefined) { await writeFile(baselinePath, ...); ... return; }
```

No committed file at `baselinePath` means the function WRITES the current run's report as the new
baseline and returns as if that had always been the baseline. So deleting a committed baseline
file, by accident or otherwise, does not fail the next gate run: it makes that run's own result
the new "frozen" truth, and the gate reports a pass built on nothing it checked. There is no
warning and no distinct exit code; the log line looks like the ordinary first-time recording that
happens when a gate is set up.

**Every caller, read at HEAD (find each by `rg assertMatchesBaseline packages/runner/itest`;
callers may be added):**

- `packages/runner/itest/al-runner.itest.ts` — `assertMatchesBaseline(first, BASELINE_PATH,
  "al-runner itest")`, baseline `al-runner.baseline.json`. Unconditional: reached on every run,
  with nothing gating it. Records whenever the file is absent.
- `packages/runner/itest/bcdev.itest.ts` — `assertMatchesBaseline(first.report, BASELINE_PATH,
  "bcdev itest")`, baseline `bcdev.baseline.json`. Unconditional, same as al-runner's.
- `packages/runner/itest/envtool.itest.ts` — `assertMatchesBaseline(report, BASELINE_PATH,
  "envtool itest")`, baseline `envtool.baseline.json`, guarded by `refuseSelfRecordWhileUnverified()`
  just above it. That guard only throws when `UNVERIFIED_MOVES` is non-empty AND the baseline file
  is absent; when `UNVERIFIED_MOVES` is empty (the normal case once its constants have been
  confirmed against a live `itest:bcdev` run and cleared), a deleted `envtool.baseline.json`
  records itself exactly like the other gates. The CLAUDE.md-documented refusal only covers the
  window while moved constants are still unverified, not a baseline deleted afterward.
- `packages/runner/itest/tables.itest.ts` — `assertMatchesBaseline(first.report,
  BASELINE_PATH, "tables itest")`, baseline `tables.baseline.json`. Unconditional.
- `packages/runner/itest/harden.itest.ts` and `packages/runner/itest/harden-expected.ts`
  (baseline `harden.baseline.json`). Two call sites, one baseline. In `harden.itest.ts`:
  `if (baselineExisted) await assertMatchesBaseline(a, BASELINE_PATH, "harden itest")` — this call
  only ever DIFFS (the file already existed when the run started, so `assertMatchesBaseline` never
  reaches its write branch here). The record actually happens in `harden-expected.ts`, inside
  `recordAfterBothLegs`, called unconditionally from `harden.itest.ts` after leg A's own checks:
  `await legB(); await assertMatchesBaseline(reportA, baselinePath, "harden itest")`. So a deleted
  `harden.baseline.json` records itself as soon as both leg A and leg B pass their own assertions,
  the same shape as the other gates, just reached through one extra hop.

**The R321 pattern that would close it.** `assertMatchesFrozenBaseline` (added in R321, same file):
an absent baseline is REFUSED, not written, unless the caller passes an explicit one-time `record`
flag; recording with that flag set still refuses to overwrite an existing file, and a record run
exits without a passing receipt (`al-runner.itest.ts`'s symbol legs: record mode prints "RECORDED
... NOT a pass" and exits 3). Deleting a frozen baseline under this pattern makes the gate fail
loudly, naming the missing file, instead of silently adopting whatever the next run measured.

**What would close it.** Move every caller above from `assertMatchesBaseline` to
`assertMatchesFrozenBaseline` (or equivalent): a refusing guard plus an explicit, one-time record
mode gated by its own env var, mirroring R321's `LETHAL_ITEST_RECORD_SYMBOL_BASELINES`. Each gate
needs its own record-mode switch and its own "never a pass" exit. And one red-check per gate:
delete that gate's baseline file, run it, and confirm the gate FAILS rather than quietly recording
and passing. `envtool.itest.ts`'s guard needs the same treatment even though it already refuses in
one case; the refusal should not depend on `UNVERIFIED_MOVES` being non-empty.
