`packages/engine/src/semantic/types.ts`'s `computeType` has cases for literals, identifiers,
parenthesized and unary expressions, and the four binary precedence classes. It has **no case for
`call_expression` and none for `member_expression`**, so it answers `null` for `GetAmount()` and for
`Rec.Amount` alike. Both fall through the `switch` to `default: return null`.

That is not an abstract gap. BC code does its arithmetic on record fields and on function results,
so the two missing cases sit exactly where the numbers are.

**Measured 2026-08-19** while spiking R159's arithmetic operator, on `do-rel2/Cloud` (554 `.al`
files). Of 1,121 arithmetic expressions, 170 were refused because an operand could not be typed at
all, and the node kinds behind those refusals are:

| operand kind the type table could not answer for | count |
| --- | ---: |
| `call_expression` | 81 |
| `member_expression` | 49 |
| `additive_expression` | 36 |
| `identifier` | 29 |
| `quoted_identifier` | 19 |
| `subscript_expression` | 12 |
| `qualified_enum_value` | 3 |
| `date_literal` | 1 |

`additive_expression` at 36 is a knock-on rather than a separate hole: a nested `a + b` types as
`null` because one of ITS operands is a call or a field, so fixing the two leaf cases shrinks that
row too. `identifier` and `quoted_identifier` at 48 combined are a different miss and are not
explained by this row.

**Why it matters beyond R159.** Any operator that consults types inherits this. R159's prototype
claims 100 sites and refuses 170 as untypeable, so its measured footprint is a FLOOR: the true
number is somewhere in 100 to 270, and the decision recorded in the spike (build the additive half,
hold the multiplicative half) was taken on the floor. `swap-call-arguments` already resolves types
by walking out from the identifier precisely to avoid this path (see R84 and R87), which is evidence
the gap has been worked around rather than closed.

**The safe direction is the one it currently takes.** An unresolved operand is REFUSED, so the
failure mode is lost sites, never wrong AL. R87 measured the same asymmetry on the same instrument
and said so. This row is about recovering the lost sites, not about fixing a correctness bug.

**What a fix needs.** `member_expression` is the tractable half: resolve the receiver to a table and
read the field's declared type, which the symbol table already indexes. `call_expression` needs a
procedure's return type, which the symbol table also has for first-party objects but not for
platform methods, so the honest shape is "answer where we can, keep answering `null` elsewhere"
rather than a guess. Whoever does it should re-run `scripts/r159-aor-spike/census.ts` before and
after and SET-DIFF the claimed sites rather than compare counts: R87 is the precedent, and a count
that merely goes up does not prove nothing was dropped.

---

**CLOSED 2026-08-19.** Both cases added, plus the field index they needed.

- `SymbolTable.fieldsOf(tableName)` indexes every `field(<id>; <name>; <type>)` of a table,
  INCLUDING the fields a project `tableextension` adds to it, keyed on the extended table's name
  because that is the name an expression uses to reach them. Case-insensitive, since AL is.
- `member_expression`: resolve the receiver identifier to `Record "X"`, then look the member up in
  X's fields. Type text is kept VERBATIM (`Code[20]`, not `Code`), matching `VarSymbol.typeText`.
- `call_expression`: an unqualified call resolves against the enclosing object; a qualified one
  resolves a `Codeunit "X"` or `Record "X"` receiver and reads the procedure's declared return type.

**A platform method keeps answering `null`, deliberately.** `Rec.Count()`, `StrLen(...)` and
`Rec.Get(...)` are the base application's, not this project's, and a table of guessed return types
would go stale silently. Answering `null` costs sites; answering wrongly costs a whole-project
compile, which is what R87 recorded (`AL0133`).

**The load-bearing measurement is an ABSENCE.** Every consumer of `typeOf` could have started
claiming different sites, `swap-call-arguments` above all. Set-diffed with
`scripts/census-tier1-sites.ts` on `do-rel2/Cloud`, the same instrument and corpus R87 used:

| | sites |
| --- | ---: |
| before | 20,844 |
| after | **20,844** |
| added | **0** |
| removed | **0** |

Byte-identical, `swap-call-arguments` 523 either way, and identical on all three fixtures too, so
**no live gate moves and nothing needed re-freezing**. The reason is recorded in R84/R87: that
operator resolves types by walking out from the identifier and never went through this path.

What DOES move is the R159 arithmetic spike, which is what this row was filed to unblock:
**100 -> 120 claimable sites** (additive 73 -> 93), untypeable operands 170 -> 141. R159's decision
was taken on the floor of 100 and the direction is unchanged: additive still clears R13's bar
comfortably, multiplicative is still 27 with its division-by-zero hazard unaddressed.

**One bug worth recording, because it cost half an hour and would recur.** A `\b` written through a
shell-escaped `python -c` became a literal 0x08 BACKSPACE byte inside the regex literal
`/^\s*Codeunit\b/i`, which then never matched, and every qualified call typed as if its receiver
were a table. `cat -A` shows it as `^H`; `grep` and an editor show nothing. A sweep of every file
this session wrote that way found exactly one occurrence. Prefer writing a script FILE over an
escaped `-c` string when the content contains regex escapes.
