**Filed 2026-10-18 by coord task R-583** (lethal-code), from the daily al-runner update. The current pin stays on
f06ee78c.

**What happened.** The daily update built upstream al-runner `069cbf32` and ran `itest:alrunner` on it. The
gate failed, so `/work/tools/al-runner/current` was not moved and still points to f06ee78c.
- Only one leg broke: the one that runs `al-runner --server` with `selectorMode: "resource"`. In that mode,
  LethAL compiles the bundle once and writes the active mutant to a source-backed resource file,
  `active-mutant.txt`, which the compiled AL reads at run time.
- On 069cbf32, every baseline test in that leg fails with `NavNclResourceNotFoundException: A resource matching
  'active-mutant.txt' could not be found`. So no mutant gets a green baseline, and each reads `error`.
- The one-shot legs and the plain `--server` leg pass with identical verdicts.

**Evidence.** The update log is in the orchestrator's session scratchpad (`alrunner-update-1018.log`). The leg is
R222's resource-selector transport.

**Suspects.** Upstream commits 783d592 and 76bb389 both change how `--server` rebuilds the app tree. A rebuild
that no longer carries the bundle's resource files, or that runs before LethAL writes the resource, would give
exactly this error.

**Bisected (2026-10-18, `/coord/handoff/R-583/bisect.md`).** The first bad upstream commit is f23b9b5f. From
that commit on, al-runner compiles at the app's own `app.json` runtime. LethAL's resource selector calls
`NavApp.GetResourceAsText`, which needs runtime 14.0 (`AL0666`), and the fixtures declared 13.0. So the error
is a LethAL assumption, not an upstream regression. The tests then still ran against a dependency copy that
ignores the runtime, and that part IS upstream's. It is reported as
https://github.com/StefanMaron/BusinessCentral.AL.Runner/issues/5573.

**To close.** Bisect f06ee78c..069cbf32 (50 commits) in a scratch build, never touching `current`. Then:
- **an upstream regression:** report it to al-runner with a minimal repro, and keep the pin until it is fixed;
- **a LethAL assumption that broke** (for example, when or where the resource is written relative to the server's
  rebuild): plan the fix, get it reviewed, and re-run the gate on the new build.

**Built (2026-10-20, branch `lethal/r583`).** It follows plan r3, `/coord/reviews/R-583-plan/plan.r3.md`, which
amends r2. The status stays open until the live gates pass.

- **The finding.** It was a LethAL assumption, not an upstream regression. From f23b9b5f on, al-runner compiles at
  the app's own `runtime`. The resource selector (`emitResourceSelector`) calls `NavApp.GetResourceAsText`, and
  that needs 14.0 (`AL0666`).
- **A door that already existed.** Before this, `--server` read neither `exitCode` nor `compilationErrors` from the
  summary (`readSummary` kept neither).
  - So on 069cbf32, at runtime 13, the R387 default (`--server` plus the resource selector) scored rows from a
    bundle al-runner had refused.
  - Those were false SURVIVES, not false kills, because the baseline and every mutant behaved the same.
  - One-shot was already safe in the measured shape: it reads an exit 3 that carries `compilationErrors` as an
    error.
- **The refusal.** `assertResourceSelectorRuntime` compares the `app.json` runtime as a number, major.minor.
  - Below 14.0, or unreadable, it throws `ResourceSelectorRuntimeError`: "runtime <X> is below 14.0, which the
    resource selector needs (NavApp.GetResourceAsText, AL0666); set app.json runtime ≥ 17.0 or
    alRunner.selectorMode static".
  - With no runtime field it allows the run. That al-runner then compiles at its newest runtime was measured on
    069cbf32 only.
  - It is called by `runFromCli` before any probe or instrumentation (campaign stages run through it), by
    `dryRunFromCli`, and by `deploy()` on `active/app.json`.
  - `lethal verify` is bcdev only, so it does not call it.
  - `deploy()` decides the selector mode once; `activate()` reads the stored mode.
  - `alRunnerAdvisory` now takes the runtime. Below 14.0 it says to raise the runtime instead of calling resource
    faster. There is no fallback ([[R584]]).
- **The net.** `compileFindingsOf` reads two things:
  - on both transports, the `compilationErrors` entries: the one-shot envelope's, or the `--server` summary's,
    which `readSummary` now keeps along with `exitCode`;
  - on one-shot only, the `EMIT-ZERO`, `EMIT-EXCLUDED` and `PARTIAL-EMIT-DROP` blocks in that invocation's own
    stderr, matched by prefix. The daemon's stderr is never read, because it spans the daemon's life.
- **What counts (revised after build review r1).** `compileOwnerOf` sorts each diagnostic by owner.
  - **The output shapes behind it.** They were measured on 069cbf32 and are recorded in
    `/coord/handoff/R-583/output-shapes.md`:
    - a test-app `EMIT-EXCLUDED` is `V2_sandbox-tests` on `--server`, and the hyphen is kept;
    - on one-shot it is a column-0 block whose `SourceFile(` paths are absolute;
    - a Tests-TestLibraries drop is one column-0 line, `Microsoft_Tests-TestLibraries v28.5...: EMIT-EXCLUDED`,
      with paths under `/tmp/al-runner-deps`;
    - on `--server` that drop appears on stderr only.
  - **TARGET** needs positive evidence: an object LethAL emits (`MutationSelector`), a `SourceFile(` path under
    the target bundle, or an owner that names it (its directory, `V2_<dir>`, or `<Publisher>_<Name> v<version>`).
    A target diagnostic refuses.
  - **TEST** needs the same kinds of evidence for the test app. A test-app diagnostic keeps today's behaviour:
    absent rows become per-test `error`.
  - **DEPENDENCY** applies when every path lies outside both projects, or every module named is another app. The
    run is scored anyway, and the session emits the warning `al-runner-dependency-emit-excluded` once per drop.
    On `--server` such a drop is visible only on stderr, which is never read per request, so it is not warned
    there.
  - **UNATTRIBUTED** covers everything else. It refuses as "a compile diagnostic not attributable to the test app
    or a dependency", with the owner printed.
  - **Where a stderr block ends.** It continues only through indented lines and a column-0 `<lead>: AL diagnostics
    that identified ...` line. Anything else ends it, such as the `→` summary or the next `[2/2] ...` bundle line.
  - On a mutant run, every row of a refused run becomes `error` with the message.
  - On the baseline (`activate(null)`), the backend throws `AlRunnerTargetCompileError`. That error extends
    `Error`, propagates out of `runOnce` and `scoreBatch`, and stops the session by name.
  - No `SessionReport` field or `Caveat` was added.
- **The net is effective only on builds that diagnose.** f06ee78c prints nothing for this case, because it ignored
  `runtime`.
- **The runtime move.** "All to 17" (owner, 2026-10-18).
  - Every fixture, example and `scripts/*-probe` app, and `extensions/lethal-control`, now declares runtime 17.0.
    The fixture and example versions went up by one patch.
  - An offline alc compile, before and after, found no new or changed diagnostic
    (`/coord/handoff/R-583/compile-17.md`).
  - The unit-test fixtures under `packages/runner/tests/fixtures` (runtime 16.0) were not moved.
- **The control app.** LethAL Control is now 1.0.0.22, and `MIN_CONTROL_VERSION` is 1.0.0.22.
  - 1.0.0.21 belongs to `lethal/r389`. Whichever of the two lands second rebases its version above the other's, so
    R-389 becomes 1.0.0.23 if this lands first.
  - The Global republish on Cronus28 and Cronus284 is the owner's step, and it comes before any bcdev gate.
- **The gates.** `itest:alrunner`'s resource legs now prove that the resource channel ran (`resourceLegFailures`
  over `watchResourceSelector`). The live gates have not been run.
