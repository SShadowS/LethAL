**Filed 2026-11-05 from GitHub #29.** Related: [[R112]] (`clear-ceiling --config`), [[R109]] (doctor).

**What was wrong.** Three small things.

1. `lethal doctor` only looked for the Microsoft System package in `packageCachePath`. A target that depends on another
   app whose `.app` is missing from the cache passed doctor, then failed the first local compile with AL1022.
2. A tenant left `OperationalWithSyncPending` by an aborted publish answers HarnessInfo with HTTP 503. Container health
   does not show it and a restart does not clear it. The error said only `HarnessInfo failed: HTTP 503`.
3. `clear-quarantine` refused `--config`, so a wrapper that always passes it could not run the command.

**Fixed.**

1. Doctor has a `dependencies` check. It needs `--project` and a `packageCachePath`; without either it shows as a
   skipped check naming what to pass (so the banner says something could not be checked), and with `envTool.downloadSymbols`
   declared a gap is skipped too, because a run fills the cache first. It reads each dependency from the
   target's `app.json` and each package in the cache, subfolders included, through its manifest (`symbolPackageIdentity`, so Ready-to-Run
   wrappers count), never by file name. Only the target's direct dependencies are checked, not the dependencies of the cached packages. The rule is alc's, measured with alc 18.1 on synthetic apps: a package matches by
   app id (publisher and name are not compared), and it is compatible when its version is equal or higher (the major part
   is not held fixed; 2.0.0.0 satisfied a 1.2.0.0 dependency). The `application` and `platform` entries of `app.json` are not read.
   Files that are not readable packages are listed, not fatal.
2. A 503 from HarnessInfo appends a hint (`SERVICE_UNAVAILABLE_HINT`, `harness.ts`) that names the sync-pending tenant as
   a possible cause. The error stays a `HarnessVerificationError`, and doctor shows the text because it passes the message through.
3. `clear-quarantine` takes `--config` in place of `--server`/`--instance`, through the same `resolveTierIdentity` as
   `clear-ceiling`. An explicit pair wins over the config. A tier taken from the config is printed before it is cleared. An empty `--server` or `--instance` is still an error. Neither a pair nor a config is refused. The flag table, the
   usage text, the README and `docs/using-lethal-from-an-agent.md` say so.

**Evidence.** `packages/runner/tests/doctor-dependencies.test.ts`, the 503 tests in `harness.test.ts` and `doctor.test.ts`,
the clear-quarantine tests in `cli.test.ts`.
