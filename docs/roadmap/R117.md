**Cross-file `file.ts:NNN` citations rot silently, and this repo now has four measured instances — two of which invalidated their own pointer in the commit that wrote them.** The pattern: a comment or doc cites a line range to justify a claim, an unrelated edit shifts that range, and the citation now points at something else while still reading as evidence. Measured instances. (1) `events.ts`'s `BaselineClassification` cites `report.ts:918,924,930` for three caveat pushes — those are at 901/907/913, and 918/924/930 now land on a different push, mid-comment prose, and a closing brace; it had ALREADY rotted once before (`7449a89` moved them to 883/889/895). (2) `interpretation.ts` cited `report.ts:194-195` for `ExecutionContext.basis`; a later task in the same subsystem added 213 lines above it, moving the target to 407-408, where 194-195 now lands mid-sentence inside an unrelated interpretation. (3) `orchestrator.ts`'s `failureNote` comment cited `:3700` for a string that is at `:3712` — **the twelve-line comment containing the citation pushed its own target down by exactly twelve lines, in the same commit**. (4) `docs/superpowers/plans/2026-08-03-do-live-campaign.md` and `specs/2026-08-03-do-live-campaign-design.md` both cite `orchestrator.ts:2360-2365` for the in-flight-unknown quarantine; that range is now the permission canary. Note (4) is also cited by `docs/campaign/2026-08-03-do/rung2.precommit.md`, which **must not be edited** — it is a pre-commitment record, and editing one after the fact is what subsystem D exists to prevent; the fix there is a pointer note in the campaign README, never a rewrite. **The rule this establishes: cite greppable NAMES, never line numbers.** Every target in every instance above was uniquely greppable (`"How that is known"`, `` `let failureNote` ``, the pushed caveat literal), and the repo already does this correctly in places — `explain.ts` cites "orchestrator.ts's `let failureNote` declaration" with no number. Work: sweep for `\.ts:[0-9]` in comments and docs, replace with names, and fix instances (1), (2)-class residuals and (4)'s two editable docs. Filed 2026-08-06 from subsystems B and D.

**Closed 2026-08-07. Both halves landed: the sweep, and a guard that makes the next one impossible
to add silently.**

**The scale was four times what the row measured.** The row named four instances. The actual count
across live source, tests and the roadmap was **106 pointers in 43 files** — 97 replaced, 9 kept.
That matters for the reading of the row: this was never four mistakes, it was the repo's default
way of citing, so a sweep without a guard would have been undone within a session. (The row already
suspected this: the previous session added more while writing about the ones it was fixing.)

**Two scope decisions the row left open, both settled deliberately:**

- **Same-file pointers are banned too.** Measured instance (3) — the twelve-line comment that
  pushed its own target down by exactly twelve lines — is a file citing ITSELF. Banning only
  cross-file pointers would have missed the worst of the four.
- **The guard is a TEST, not a lint rule.** Biome 1.9 (this repo's linter) has no custom-rule
  mechanism, so a lint rule would mean adopting a second linter. A test also gets to fail when the
  ALLOWLIST rots, which a lint rule could not express.

**What the guard covers, and what it deliberately does not.** `scripts/line-citations.ts` scans
live source (`packages/*/{src,tests,itest}`), `scripts/`, `docs/roadmap/`, top-level and `docs/`
Markdown, and every `fixtures/**/README.md`. Three directories are exempt BY RULE rather than by
allowlist entry, because their bodies must not be rewritten at all: `docs/campaign/` (sealed
pre-commitments), `docs/superpowers/plans/` and `docs/superpowers/specs/` (dated records). A pointer
inside one of those is a record of a claim, not a claim being made now — so instance (4)'s two
"editable docs" were NOT edited after all. That is a correction to this row's own work list.

**The allowlist is keyed on the citation TEXT, not on the line it sits on** — an allowlist keyed on
a line number would rot exactly the way the citations do. A test proves it has no dead entry, so an
allowlist that outlives its citation cannot hide the next one.

**Two pointers turned out to have rotted in SUBSTANCE, not just in line number**, which is worse
than the row claimed and is the strongest argument for the rule. `events.ts` pointed at a line of
`orchestrator.ts` for `args.runnerDisagreementTests.add(qualifiedTestName(ref))`: that call no
longer exists anywhere in `orchestrator.ts` (the code now assigns
`runnerDisagreementTest = qualifiedTestName(ref)`). A name-based citation would have been a dead
`rg` — visible. A line number pointed at a real line and read as evidence. R092 pointed at lines
2111-2112 of `orchestrator.ts` for its `const siteCount` declaration, which is at line 2195 — 84
lines off.

**The guard caught the first re-offence while this very row was being written**: two new pointers,
added to the paragraph above to describe pointers that had rotted, reddened `bun test` on the next
run. That is the property a one-off sweep could not have.

**What this does NOT close:** the guard proves no pointer carries a line number. It does not prove
the NAME resolves. A citation naming a symbol that no longer exists is still silent — see the
`runnerDisagreementTests` case above, which was found by hand. A checker that greps each cited name
in each cited file is the natural next step and is not built here.
