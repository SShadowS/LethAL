Designed by lethal-code, 2026-11-13 (coord R-956, an Opus reading of the guard; full note `/coord/handoff/R-956/r959-decision.md`).
Related: [[R959]], [[R680]], [[R247]], [[R495]].

**The flaw.** `--resume-run` refuses when LethAL Control's server generation changed (`assertSameServerGeneration`,
`ServerGenerationChangedError`). The generation lives in the `LC Lease` row and is re-minted in two different events: when the row is
created (a database that was lost, as an in-memory one is on a restart) and by `ForceResetLease`. A host reboot with a persistent
database does not change it by itself; in R959's case the reboot orphaned a lease operation, and the documented recovery
(`force-reset-lease`) minted the new generation that the resume then refused. One marker stands for "the database is gone" and "the lease
was reset by hand".

**Why re-verifying the apps is not enough.** Published app ids, versions and hashes cannot see company data: a fresh container with the
same apps republished passes that check with fresh data.

**Design (not built).**
- LethAL Control 1.0.0.26: a `Database Id` field on `LC Lease`, minted only when the row is created (or on upgrade when blank), never
  touched by `ForceResetLease`; `HarnessInfo` reports it and the client refuses an empty one.
- The run row records it at the same read as the generation.
- A resume carries decided verdicts across a generation change only when the database id is equal, every existing resume check passes
  (proven test-app identity R247/R495, closed-world answer R389/R601) and the tier is out of quarantine; a missing id on either side
  refuses (runs recorded before the bump refuse as today). The lease is still asked at the live generation; the baseline snapshot stays
  keyed on the generation. Mutants without a verdict, infra-error and in-flight verdicts are redone.
- Report: the existing `resumed` caveat, plus a banner line "carried N verdicts across a lease reset: database id X unchanged, server
  generation A -> B".
- Proof: unit tests red both ways; an `itest:lend` leg that seeds a run, runs `force-reset-lease` without a restart, then `--resume-run`,
  every carried verdict equal per mutant to the seed (and `seedRunFrom` must copy the database id, R680's trap). A live negative leg (a
  real in-memory restart changes both ids) waits for the next server1 restart.
- Known limit, the same as today: a database restored from a backup taken after LethAL Control was installed keeps the same id with older
  data.

**Why not built now (orchestrator, 2026-11-13).** A control-app bump means publishing to every gate server and re-proving every server's
gates; the orchestrator batches control changes for the owner. Meanwhile R-956 keeps the refusal and makes its message say what to do.

**Built (coord R-990, 2026-11-14, LethAL Control 1.0.0.26, batched with [[R999]]; owner approval q-20261114T110356-6ee35c8d).**
- AL: `LC Lease` field 16 `Database Id`, minted with the row and, on install or upgrade, when blank (`EnsureLeaseSeeded`); never
  written by `TryForceResetLease`. `HarnessInfo` reports it as `databaseId`.
- Client: `MIN_CONTROL_VERSION` 1.0.0.26; `HarnessVerifier.verify()` refuses a missing or empty `databaseId`; the session reads it
  right after the generation (`LeaseSessionConfig.databaseId`, wired by the CLI) and refuses an empty one; `runs.database_id` records
  it; `seedRunFrom` copies it.
- The rule (`assertSameServerGeneration`): a generation change with the same, non-empty database id on both sides resumes, with the
  warning `resume-across-lease-reset` ("carrying run N's verdicts across a lease reset: database id X unchanged, server generation A ->
  B"); every other resume check still applies, and the lease is asked at the live generation. A different id, or none on either side,
  refuses as R680 did, with a message that says so. The baseline snapshot stays keyed on the generation.
- Differences from the design: the warning is a `warning` event, not a new report field (a `SessionReport` field would need every
  committed sample report regenerated live), and it names no verdict count (the count is known only after the resume index is
  built). The quarantine condition is the session's own, unchanged.
- Tests: `orchestrator.test.ts` "R969: the database id decides ..." (same id carries; another id, none recorded, none read refuse;
  an empty id stops the session), `harness.test.ts` R969 cases; red-checked each way.
- **Not built (next):** the `itest:lend` leg (seed, `force-reset-lease` without a restart, `--resume-run`, carried verdicts equal per
  mutant), and the live negative leg after the next server1 restart.
