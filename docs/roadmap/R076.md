**A real `TestPage` test may make a fenced BASELINE unsurvivable — which would put the shipped R69 diagnosis out of reach on the very corpus that motivated it.** MEASURED 2026-08-01 (R69 Task 7): a `[Test]` opening a REAL page (triggers, FlowFields, a writing `pageextension`) reproduced the Cronus283 `in-flight-unknown` hang **deterministically, twice**, wedging the NST (`StopPending`) and needing a Docker-level restart plus `force-reset-lease`. This RETIRES an over-generalisation of LethAL's own: the 2026-07-31 reading "TestPage does not hang, it is REFUSED, fast (87 ms)" was taken on a CODE-FREE probe page and does not generalise. Both behaviours are real and are DIFFERENT failure modes — trivial page: fast refusal (routable); real page: hang. **Why this outranks the routing question** (Fable, 2026-08-01): `orchestrator.ts` quarantines and breaks on `in-flight-unknown` during BASELINE DISCOVERY (~:2377-2392), long before `resolveRoutedCandidates` (~:2825) — so a hanging baseline test ends the session before any routing decision exists, AND before the R69 report that names the refusal is ever produced. If Continia Document Output's 9 TestPage test files hang rather than fast-refuse, a DO run never completes baseline discovery at all: that is a product-survivability defect independent of routing, and it would mean the other ~95 test files cannot be scored either. **The one experiment that settles it, and it settles three questions at once:** run each of the 9 DO TestPage files individually through a fenced session with R53's `--stop-hung-sessions` ARMED, and classify each into {fast-refuse, hang-recovered-to-scored, hang-wedges-NST}. That yields (a) the fast-refuse split, which decides whether wiring the R69 router could ever pay, (b) whether R53's stop path — proven on MUTANT runs only — generalises to a BASELINE hang, and (c) whether a real suite's baseline is survivable at all. **Threshold pre-committed BEFORE measuring, so the result cannot be rationalised:** wire the router only if at least ~a third of the 9 fast-refuse AND hang containment works; otherwise DELETE the client-services half (control-app batch path, `batch-transport.ts`, `testpage-router.ts`, the routing entry), keep `testpage-unsupported.ts`, and close R69 as "named, not recovered; recovery measured unprofitable". Carrying dead false-verdict-capable code as insurance is the trade this repo's history says loses; the spec plus commit `47fbd19` is a complete re-derivation kit. **Prediction on record:** the fast-refuse slice is expected near-empty — a TestPage test that never exercises a real page barely exists. **STATIC READING TAKEN 2026-08-01, and it confirms the prediction without spending a live run — plus it CORRECTS a sizing figure R69 has been citing.** (1) THE "9 of 104 test files" FIGURE IS NOT REPRODUCIBLE against any Document Output checkout on this machine. The largest available (`/u/Git/DO/Test`) has **17** test codeunits and **146** `[Test]` methods, not 78/1,246; `DocumentOutputRelease` has 16 codeunits. Neither contains a `CDO Email Editor` at all, which the R69 row cites as declaring a TestPage 18 times. So the corpus that produced 9-of-104 is either a branch not checked out here or the count was wrong. Treat 9-of-104 as UNVERIFIED until someone reproduces it; the shape of the finding survives, the number does not. (2) On the corpus that IS available: **3 of 17 test codeunits declare a TestPage** (29 declarations), and those files hold **27 of the suite's 146 `[Test]` methods — 18%**. Proportionally similar to the unverified 8.6%, so the slice is real and non-trivial either way. (3) DECISIVE FOR THE THRESHOLD'S FIRST HALF: **every one of those TestPages opens a REAL page. Not one is trivial.** `CDO Setup Wizard`, `CDO Setup`, `CDO SMTP Setup`, `CDO Azure Application Setup`, `Email Account Wizard`, `CDO E-Mail Templates`, `CDO eSeal Service Setup` — setup and wizard pages with source tables and open-time logic — plus a MODAL handler (`ConfirmEnableModalHandler(var ConfirmManagement: TestPage "Cust. Consent Confirmation")`), and base-app `Issued Reminder` with `.Visible()` assertions on its actions. That is precisely the shape R69 Task 7 measured as HANGING, and the opposite of the code-free probe page that fast-refused. So the fast-refuse slice on real code is predicted EMPTY, and the router — even fully fixed and wired — would rescue nothing here. The remaining open half of the threshold is hang CONTAINMENT. **CONTAINMENT MEASURED 2026-08-01 — IT DOES NOT WORK. Classification: QUARANTINED. Both halves of the pre-committed threshold have now FAILED.** Reinstated the real-page TestPage test in `fixtures/sandbox-data-tests`, published to Cronus283, ran the tables gate with `--stop-hung-sessions` ARMED. The flag DOES act: the run resolved in **34.3 s** instead of hanging indefinitely, and the hung test returned `outcome: "error"` with `socket connection was closed unexpectedly` — BC's session was genuinely killed. But that forced-stop result is still `in-flight-unknown`, so baseline discovery still called `quarantineInFlight` and broke: `quarantined: {"reason":"baseline test in-flight-unknown running PageExtCountsMatchingRelated"}`, **byte-identical to the un-flagged case, 0 mutants scored. The flag changes LATENCY, NOT OUTCOME.** **This is structural, not one observation** (verified in code, so it generalises): `stopHungSessions` occurs exactly THREE times in `orchestrator.ts` — the config field (:397), `buildResumeIndex` (:1847), and the report caveat (:3032). It is NEVER consulted by the baseline-discovery loop, and `requiresUnsafeLatch` (`operation-outcome.ts:29-31`) returns true for `in-flight-unknown` unconditionally, taking no flag input. R53's stop path was built for the MUTANT loop and cannot reach baseline. Cheaper failure than expected, and that IS the flag's one benefit: recovery took `force-reset-lease` + `clear-quarantine` (seconds), with the NST staying `Running` — no Docker restart, unlike Task 7's un-flagged reproduction. Honest limit: n=1 clean armed observation (a first run was lost to a tooling artifact, not BC behaviour), so do not over-read the exact timing or the no-wedge specific; the QUARANTINED mechanism rests on the code, not the count. Gate restored and re-verified at 69/9/6. Evidence: `.superpowers/sdd/2026-08-01-r69-phase2-batch-runner/r76-containment-report.md`. **CONSEQUENCE, and it outranks R69:** a suite containing ONE hanging TestPage test cannot complete a run at all — not the mutants, not the other tests, and not the R69 report that would have named the refusal. Fixing THAT (making a baseline hang a scored, session-safe skip rather than a tier quarantine) is the real successor here, and it is verdict-neutral and cheaper than the router. **SOLVED 2026-08-01, AND THE FIX WAS ALREADY IN THE PRODUCT — `coverageMode: "procedure"`. MEASURED, not reasoned.** `bcdev-backend.ts`'s `run()` dispatches to `runOnHub()` (`bcdev_test_run`, the SignalR TestRunnerHub, `GuiAllowed=Yes`/`ClientType=Web`) whenever the call's coverage mode is `procedure`/`line`; the gates only ever ran fenced because `DEFAULT_COVERAGE_MODE = "fenced"` and no fixture config overrode it. Re-ran the tables fixture with `PageExtCountsMatchingRelated` LIVE and `coverageMode: "procedure"`: the hub **opened the real `TestPage "Data Main List"` — live triggers, a FlowField, and a pageextension that WRITES from `OnOpenPage` — and returned `pass` in 451 ms** at baseline, where the fenced path hangs indefinitely and quarantines. Exit code 0, **no `quarantined` key anywhere, ZERO recovery needed** (NST stayed `Running`; no `force-reset-lease`, no restart). Counts under that mode: **69 killed / 9 survived / 2 no-coverage / 4 error(unstable)** over 84 recorded — and `no-coverage` fell 6→2 precisely BECAUSE the TestPage test now contributes coverage. So R76's product-survivability defect is closed by a CONFIG VALUE: one hanging TestPage test no longer takes a whole suite down. **What it does NOT fix, and this is the R69/R76 split made concrete:** mutant VERDICTS always run fenced regardless of `coverageMode` — `orchestrator.ts:3316`/`:3445` pass `{ coverage: "none" }`, and `run()` routes anything that is not `procedure`/`line` to `runViaTransport`, the fenced RunMutant OData path. So the 4 pageextension mutants the TestPage test now COVERS still cannot be SCORED: their fenced verdict run refuses. **But it refuses FAST — 140-181 ms, `CreateNavTestService` — it does NOT hang.** That is the decisive new datum: with the hub supplying baseline, the refusal MOVES from an unroutable baseline hang to exactly the fast, completed refusal R69's gate 1 was built to recognise.
