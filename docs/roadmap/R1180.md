**Found by** PR-340's build review (S1) and its first live gate run (amendment 2 of
`docs/superpowers/specs/2026-11-22-pr340-v3-carry-walk.md`).

**What is not measured:** a carry walk sends three batch `strictOrder` requests on the lane's own serve daemon. Ordinary
requests then follow on that daemon. Whether the walk leaves anything behind that changes them is not measured anywhere.
- **On `itest:alrunner-v3-carry`:** 13 mutants fit one prefetch window, so the daemon's requests (one warm-up, one prefetch,
  one live) all precede the 3 walks. The gate prints its after-walk check (`judgeCarryOrder`) as "not exercised".
- **On the full v3 gate:** no fixture has a labelled survivor, so no walk runs at all.

**Why it is believed clean, not proven:**
- al-runner starts each request's sessions fresh;
- the walk restores the lane's resource file in `finally`;
- the walk's own second request runs with no mutant, so leftover mutant state would show as a red no-mutant row, which
  can never kill.

**To close it:** the first full DO run on a head with PR-340, and a `LETHAL_V3_CARRY_WALK=off` control on the same build
and head. Every mutant WITHOUT the `[singleinstance-carry-*]` tags must have the same verdict and `killingTest` in both runs.
On DO, walks interleave with thousands of later requests on the same daemons. Any difference among unlabelled mutants is
a BLOCK.
