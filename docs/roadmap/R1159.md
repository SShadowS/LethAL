Found by coord PR-255 (lethal-bugs, 2026-11-20), when `current` moved from edge-4ebfe7913 to upstream main ccd0f823d (gated, ledger
row `main-ccd0f823d`). The post-gate upstream-repro report against the old `current` read: 244 tests, 32 flipped to BC, 7
"regressed", 125 still differ, 80 still match.

**1. A new refusal on DO, and edge's wrong answer in the same shape.**
- `the value of field 'RelationFieldNo' of platform table 'Field' is not known for field ... of table ..., a TableRelation without
  a field of a shape not measured`.
- On the private DO corpus (a one-shot of the new `current` against 9835579c6's): 7 tests went from pass to not run, and 1 more
  from fail to not run as the cascade, in 2 test codeunits. With PR-250's cut that is 1,332 mutants covered and 567 verdicts moving
  to error (72 kills, 495 survivors; lethal-preproc's count). It is the largest single coverage loss of the move.
- **Measured on BC** (bc4, BC 29.0.54011.57673; invented repro, no project code): reading `Field.RelationFieldNo` for a
  `TableRelation` that names a table but no field gives **0**, for a one-field key and a two-field key alike. The control (a named
  field) gives the field's number.
  - main ccd0f823d answers the one-field cell 0 (as BC) and refuses the two-field cell: rule-3-correct, but now measured.
    Filed upstream: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8592.
  - **The whole matrix** (PR-317, 2026-11-22; `/coord/handoff/PR-317/`): 19 target keys of width 1-3 over Code, Integer, Text,
    Guid and BigInteger, times 5 source field types, gives 95 cells. On BC 29.0 every cell answers `RelationFieldNo = 0`, with
    `RelationTableNo` = the target. main ccd0f823d answers 3 (all 0) and refuses 92. The full table went on #8592 so every cell can
    be pinned at once: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8592#issuecomment-7071704322.
  - **edge-4ebfe7913 answered 1 in both cells: wrong.** So y2/y3 DO verdicts that went through this shape are suspect, as R1155's
    by-value verdicts are. Sizing them is a separate small task, sized like PR-249.
- **Daemon churn checked:** the 7 tests refuse in the BASELINE and the text is on no keep list, so PR-250's cut keeps them out of
  every mutant request. They cannot close a daemon under a mutant, and PR-244's near-miss and storm warnings have nothing to fire on.

**2. The repro gate cannot judge .NET repros on this build.**
- 6 of the 7 "regressed" repros are refusals: `dotnet-unavailable: DotNet 'System.Uri' (TimeSpan, Type, Timers.Timer) the .NET
  runtime of BC build 28.4.53241.53758's service tier is not known`.
- The cause: the build fetches the service tier's runtimeconfig from Microsoft's artifact feed for the run's BC build. For the
  repros' build 53758 the feed answers HTTP 404.
- DO is NOT affected: its build 28.4.53241.56646 runs with 0 such refusals (the same one-shot).
- Follow-up: give the repro gate a BC build whose runtimeconfig the feed has, or report upstream if 53758's should exist.

**3. A repro control that was never measured (fixed with this item).**
- The 7th "regression", u8193's control `OpenPageWithOtherName`, shared its key with the first test. On edge the first test was
  refused (#8193), so the control's insert never collided. ccd0f823d fixes #8193; the first test then inserts, and under codeunit
  isolation the control collides.
- BC does the same: the old repro fails the control on BC with the same text (measured).
- The control now has its own key, and BC's measured answers (all three pass) are in `scripts/upstream-repros/manifest.json`. Not an
  al-runner regression; nothing was filed upstream.
