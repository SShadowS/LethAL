Found by coord task R-953 (2026-11-13), deciding R-950's eight Cryptography Management survivors (`/coord/handoff/R-953/survivors.md`).
Related: [[R175]] (attribution lost), [[R964]], [[R963]].

**What happened.** Mutant M1200 (empty-block) sits in `SignedXml.SetSigningKey(SignatureKey: Codeunit "Signature Key")` (lines 80-83 of
`Xml/SignedXml.Codeunit.al`; the codeunit declares five `SetSigningKey` overloads). R-937's run on al-runner edge-42af5d384 recorded
`coverageAttribution: "exact"`, `reachGrain: statement`, covering tests `SignXmlDocumentWithSigningKeyAsSecretText` and
`...AndRsaAlgorithm`, and scored it SURVIVED. Those tests declare `SigningKey: SecretText` and call the SecretText overload (line 61),
never line 80. The two tests that do reach the `Signature Key` overload were refused at baseline on that build. So the mutant was
executed by no test, and "survived" is not a measured result; the honest verdict is no-coverage. Same shape for M1201, M1322, M1323
(`SignedXmlImpl.SetSigningKey`) and, by the survivors table, M1190, M1191, M1259, M1262 (an `InitializeSignedXml` overload).
On edge-c8fe56e05 these eight are refused instead (an error), so today's figure is not false, but the attribution is.

**Cause (measured by coord task R-954, `/coord/handoff/R-954/where.md`).** al-runner's per-test coverage is correct per line: it
marks only the overload the test ran. The bug was LethAL's. Coverage was keyed by object and procedure NAME (`memberKeyOf` in
`selection.ts`), so a test that ran one overload gave "exact" coverage to mutants in every overload of that name.

**Blast radius** (`/coord/handoff/R-954/blast/count.md`): 2,345 survived rows in stored runs sit in an overloaded procedure whose
covering tests may have run only another overload (153 file/procedure pairs; R-928's run holds 919 of them, 668 in SharePoint).
1,672 killed rows have the same shape and are harmless (a kill is measured). No store keeps per-test coverage lines, so the
at-risk rows cannot be decided after the fact; about 80 reports could not be resolved at all (their trees are gone).

**Measured over-count (coord R-958, 2026-11-13, `/coord/handoff/R-958/result.md`).** Five of those apps re-run fresh after the fix
(master 27393bd9, edge-c8fe56e05), per mutant against their stored runs: of 1,120 at-risk survivors, 445 (40%) were wrong and are
now no-coverage, 173 (15%) still survive on fewer covering tests, and 502 (45%) keep exactly the same tests (never affected). So
the 2,345 above is an upper bound, about 2.5 times the wrong ones in this sample. Per app (flagged / now no-coverage): SharePoint
668 / 177, Cryptography Management 213 / 145, Rest Client 111 / 73, AI 98 / 50, SAF-T 30 / 0. No at-risk survivor became killed,
and nothing outside the at-risk rows moved on Cryptography Management, whose re-run used the same al-runner build as its old run.

**Fix.** Each manifest entry in an overloaded procedure carries `procedureOverloadIndex` (its overload's place among the
same-named procedures in source order, from the schemata compiler). The al-runner and bcdev fenced coverage paths turn a covered
line into an overload index by the same line map, and selection gives such a mutant exact coverage only from tests that ran
THAT overload. A coverage entry without an index makes no exact claim for an overloaded mutant. Expected effect, pre-committed
on master: survived can move to no-coverage; nothing else moves.

**Limits.** bcdev hub coverage (the opt-in mode that names procedures through bc-dev-mcp) carries no overload index, so in hub
mode an overloaded mutant falls back from exact coverage; a killed mutant there can move. A `--resume`, or an installed artifact
built before this fix, carries its old coverage and its old verdicts forward: re-run fresh to get the corrected figure.
