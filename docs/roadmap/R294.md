**Found while building R-236c's TestPage scanner** (`docs/superpowers/plans/2026-09-27-R-236c-testpage-pre-refusal.md`,
section D1), which chose to read variable scope from the AST directly instead of through
`resolveVarRef` because of this gap.

**What happens.** `resolveVarRef` (`packages/engine/src/semantic/resolve-var-ref.ts`) is meant to
answer `null` only for a genuine member name, such as the `Name` in `Rec.Name`, never for the
receiver itself, such as the `Rec` in `Rec.Name` or the `Card` in `Card.OpenView()`. Its guard,
`isMemberName`, checks `parent.namedChildren[0] !== node` (the receiver is the field access node's
first named child). But `ALSyntaxNode` builds a fresh wrapper object on every access to
`.namedChildren` (documented in [[R209]], a neighboring identity bug), so `parent.namedChildren[0]`
is never the same object as `node`, even when both wrap the very same underlying tree-sitter node.
The `!==` comparison is therefore true for every identifier under a `member_expression`, receiver
included, and `resolveVarRef` refuses every one of them.

**Reproduction (three lines).** Given `var Card: TestPage "My Page"; ... Card.OpenView();`, calling
`resolveVarRef` on the `Card` identifier inside `Card.OpenView()` returns `null`, even though `Card`
is a plainly declared local. The same holds for `Rec.Field := 1`, calling `resolveVarRef` on `Rec`.

**Consequence to measure before any fix.** `packages/builtin-tier1/src/loop-hazard.ts`'s
`classifyHangCapable` calls `resolveVarRef` to compare a loop condition's variable against an
assignment's target. A member-expression receiver in a loop condition or an assignment never
resolves today, so the classifier declines those sites instead of tagging them hang-capable. A fix
here can therefore ADD hang-capable tags and move gate figures that depend on
`classifyHangCapable`'s output. Measure the effect on both reference corpora (`do-rel2/Cloud`,
`do-lethal-53470/Cloud`) before landing, the same way [[R210]] measured its own fix.

**Why not fixed here.** R-236c's plan states plainly: do not change `resolveVarRef` (loop-hazard
and the operators depend on today's behaviour). The scanner reads scope from the AST itself instead
and files this gap.

**To close:** give `isMemberName` a comparison that survives wrapper rebuilding, such as comparing
`node.startIndex` against `parent.namedChildren[0]?.startIndex` (the same positional-identity
approach [[R209]] and [[R210]] already use for this class of problem), then measure the effect on
`classifyHangCapable`'s tagged counts on both reference corpora before landing.

**Closed 2026-10-05 by R-294 (6154426f, fixed together with [[R295]]).** Cause as described: a
reference comparison of wrappers the engine rebuilds on every access, so every receiver was
refused. Fix: `isMemberName` compares the identifier's span with the `member_expression`'s
`object` field, so `R` in `R."Field Name"`, `A` in `A.B.C` and the receiver of `R.Method()` resolve,
and the member halves (`"Field Name"`, `B`, `C`, `Method`) stay refused. A type-aware scan of
`packages/*/src` for `===`/`!==` between two `ALSyntaxNode` values found two more, both off this
path and both harmless (`swap-enum-member`'s `collectLabels` counts the site's own label as taken,
but the candidate loop never offers the current member; `schemata`'s `resolveStatement` and
`resolveSite` take the general path, which yields the same text), so they are reported, not
changed. The census found only safe refusals here, never a wrong mutant; the loss was hang tags
(20 BaseApp, 1 CDO for this fix alone; 36 and 1 with [[R295]]'s fix, measured together). The
combined census numbers, the wrong-row counts by class, the implicit-`with` refusal the review
added, and the `IDENTITY_SCHEME` 11 bump are in [[R295]]'s closing note. Since R196 the newly seen hang-capable sites are refused rather than
tagged.
