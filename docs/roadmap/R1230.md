**Found by** PR-456's restart probe (b) (lethal-code with lethal-bugs, 2026-11-26). Evidence:
`/coord/handoff/PR-456/probes/` (`result-2026-11-26.md`, `zipcmp.ts`).

- **The symptom.** `runs.test_app_deps` differed after every bc4 restart on 2026-11-26 (63d9c6c0 → 549e8f02 →
  0e18165d), with the same dependency files published each time.
- **The cause, measured.**
  - `dependencyFingerprint` (`digest-inputs.ts`) hashes the System package's served bytes: the line
    `P sha256(bytes)`.
  - Three downloads of System 29.0.57585.0 from bc4 (2026-11-05, 2026-11-14 and 2026-11-26) are each exactly
    5,004,132 bytes and have three different sha256.
  - `zipcmp.ts` reads them as identical in content: the same 486 entries with the same name, CRC-32 and size, and an
    identical NAVX header. ONLY the DOS date and time of all 486 entries differ.
  - So BC builds the System package on request and stamps it with the current time.
  - Partner apps are fine: Continia Core is served back byte for byte as published.
- **Why it matters.**
  - R496's check compares that digest on every resume, so a resume across a restart is refused when nothing changed.
  - R1229's survivor carry cannot pass at all.
  - A resume on the SAME generation also refuses whenever System is re-downloaded, unless a cache keeps the old copy.
- **The fix shape (not built):** the `P` line hashes the sorted set of (entry name, CRC-32, uncompressed size) from
  the zip's central directory, plus the NAVX header. That is stable over a re-zip and changes with any real content.
  - The `X` lines stay on bytes: partner packages are served back exactly, as measured.
  - Stores recorded before the fix keep their old digests, so a one-time refusal on resume is expected and stated (no
    back-compat before release).
  - Red tests: two re-zipped System packages with equal content → the same digest; one changed entry → a different
    digest.
