Found by coord task R-881 (PaymentPractices, BC.History, on al-runner v3 edge-05d692e5e). Evidence: `/coord/handoff/R-881/`
(`pp.*`, `pp1.*`, `result.md`).

**What.** On BC, the guard asks the control app (`LC Control State.IsActive`), which matches the artifact's random id and a mutant id
that is set only for test runs, so a freshly published artifact's install or upgrade code cannot see an active mutant. al-runner v3 runs the target's install code inside each run, and that code reads LethAL's selector
resource like any other code. So the mutant chosen for the run is already active while install runs.

**Seen.**
1. One-shot (`pp1`): 6 mutants in table code that the app's install routine reaches are scored `error`: "install routine codeunit ...
   OnInstallAppPerCompany could not run: failed (behaviour not pinned): <the mutated check's error>". On BC those mutants would run
   their tests normally.
2. The serve-entries default (`pp`, round 1): the warm-up refused every entry with "the install code read a resource file, and an entry
   with resource files of its own would need an install baseline of its own". `batchRefusalReason` turns that into
   `al-runner-v3-entries-batch-refused`, and the run stops in the mutant phase. R786's one-shot fallback does not apply, because the
   one-shot baseline held passing rows there (31 of 36), not the same refusal. Setting `"transport": "one-shot"` runs the app.

**The second risk.** A mutant in install-reached code that does not make install fail can change the rows install creates. Tests
then run on data BC would never have, and a kill or a survival can differ from BC's.

## Fixed (coord task R-884, d78f93b3)

Evidence: `/coord/handoff/R-884/` (`result.md`, `probe/`, `mech/`, `gate-v3.log`, `pp-*.report.json`). Pre-commitment:
`docs/campaign/2026-11-09-r881-bc-history/r884-precommit.md`.

**Measured first.** On al-runner edge-05d692e5e, install triggers (per company and per database) see `ExecutionContext::Install`, and
tests see `Normal`. An invented fixture showed both effects on master: two kills that came only through a row the install code wrote,
and one install failure scored `error`.

**The fix.** Both v3 selectors answer false while `GetExecutionContext()` is not `Normal`: `emitResourceSelector` (serve-entries)
before it reads the resource, and `emitStaticSelector` (one-shot) before it tests its baked id. BC's `emitMutationSelector` is unchanged,
and its output's sha256 is pinned in `selector.test.ts`.

**Results, all as pre-committed.**
- The fixture's 3 install-path verdicts became `survived`, as on BC; its other 11 did not move.
- The full v3 gate shows 0 differences.
- PaymentPractices one-shot against `pp1`: only the 6 `error` mutants moved, all to `killed` by the test's own path. The other 874 are
  identical, so no `pp1` kill came from install-written rows.
- The serve-entries warm-up refusal is gone: the default transport ran all 880 and equals one-shot.

**Still open, and not covered by this fix.**
- Upgrade code: the guard covers it, but al-runner's context during upgrade code (and whether it runs upgrade codeunits at all) is not
  measured. Only Install is.
- A target whose OWN install code reads its own resource files still gets the serve-entries warm-up refusal. This fix only stops
  LethAL's selector from reading the resource there.
