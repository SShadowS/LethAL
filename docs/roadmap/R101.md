**v2 surfaces we should use, not just survive.** From the v2 CLI (`al-runner --help`, `--guide`), measured against a local build 2026-08-05: (a) **`--bc-version` becomes mandatory for us** — the runner picks "latest artifact present in the cache" by default and, per its own guide, **does not print the selection**, so a second artifact appearing on the machine can silently change verdicts between runs; a verdict gate cannot accept that. (b) `--out <path>` (failure-classification JSON) and `--output-junit` give per-kill evidence, which is what **R86** is about. (c) `--define` / `--preprocessor-symbols` — real projects need AL preprocessor symbols to compile outside their environment, and LethAL has no way to pass any today; omitting a required one produces real-looking test failures. (d) `--no-cache` — upstream notes defect classes that appear only on a cache HIT or only on a MISS; worth having on the red-check path. (e) `--version` exists now, which is what R93's version-detect branches on. (f) `RunnerOutOfScopeException` — SMTP, outbound HTTP, printing, external file I/O and web-service publishing now throw loudly instead of returning a fake value, so tests touching them error on v2 where v1 may have passed them; that changes what a `survived` verdict means for those tests and should be named in the report.

**Correction to (a), measured 2026-08-07 against the released 2.0.0.0 and 2.0.1.0 on this machine.**
The runner does NOT silently pick the latest artifact in the cache. With no `--bc-version` it prints
`[bc] no --bc-version given - selecting BC 28.1.49838.50794, the exact build this binary was
compiled against.` — announced, and pinned to the binary rather than to whatever is on disk. Pinning
`--bc-version` is still worth doing (a verdict should not depend on which build produced the binary),
but it is a preference, not the correctness hole stated above. (e) is done: `status()` now probes
`--version` and refuses a binary that does not identify as v2 (`51e6415`). (b) is partly overtaken —
R86 landed per-kill evidence from the message al-runner already returns, without needing `--out`.

# Decided part by part, 2026-08-08, against **al-runner 2.1.1.0**

2.1.1 published while this was being worked; the tool was bumped forward from 2.1.0.0 and
`itest:alrunner` re-run, **3 / 13 / 0 unchanged**. Every measurement below is on 2.1.1.

## (a) `--bc-version` — the correction stands, with a new wrinkle worth knowing

Re-measured. With three artifact versions on disk the runner announces on stderr:

```
[bc] no --bc-version given - selecting BC 28.1.49838.50794, the exact build this binary was
     compiled against. Override with --bc-version.
```

So the correction already recorded is confirmed: the selection is ANNOUNCED and pinned to the
binary, not silently taken from the cache.

**New: 2.1.1's own `--help` contradicts that announcement.** It documents the default as "the latest
version present in `~/.local/share/al-runner/artifacts`". Anyone deciding whether `--bc-version` is
needed by reading `--help` gets the rule that WOULD be a correctness hole, and the runtime does
something else. Recorded because it is exactly the kind of thing that makes a future session
re-derive the wrong conclusion from the documentation.

**The real residual is not the flag, it is that LethAL never RECORDS the answer.** The line above is
printed to stderr and nothing reads it, so no report says which BC build produced its verdicts.
Filed as **R129** rather than buried here.

## (b) `--out` / `--output-junit` — REFUSED, with the measurement

Measured on a three-arm probe (an outbound `HttpClient.Get`, an external file write, and a plain
`Error()`):

```
runtime/Runtime.NavFile.ExpandFileName                                        (BC's file sandbox)
out-of-scope/HttpClient.Get                                                   (al-runner's guard)
runtime/BusinessApplication.Codeunit79150.PlainControl_Scope__410633901.OnRun (a plain Error())
```

Two things kill it. An ordinary assertion failure classifies as `runtime/` plus a
compiler-generated scope name carrying a hash suffix — unstable by construction, and useless as a
key. And it lands in the SAME top-level bucket as BC's platform refusal, so the one distinction
LethAL would want from a classifier is the one it does not make. Only the `out-of-scope/` prefix
separates anything, and the ordinary message already carries it (see (f)).

Upstream agrees about its status: `--out`'s own help says "classification is a runner-development
diagnostic". Keying anything verdict-adjacent on it would couple LethAL to something explicitly not
a contract. `--output-junit` is a CI report format for a test-results tab, which LethAL is not.

R86 already landed per-kill evidence from the message al-runner returns anyway.

## (c) `--define` / `--preprocessor-symbols` — OPEN, and the row frames it wrongly

**The gap is in LethAL's own compile step first.** A search for `/define` across
`packages/runner/src` and `packages/schemata/src` returns nothing: LethAL passes no preprocessor
symbol to `alc` either. Fixing only the al-runner half would leave the instrumented app compiled
from the wrong branch, so this is not an "al-runner v2 surface we should use", it is a compile-path
gap that al-runner merely also exposes.

**The consequence is worse than the row says.** The row predicts "real-looking test failures".
A missing symbol can just as easily compile the OTHER branch cleanly, in which case LethAL mutates
and scores code the customer does not ship, and nothing fails.

**Measured incidence, so whoever picks this up knows the priority.** On Continia Document Output,
554 `.al` files: exactly ONE `#if`, on `DOSMTP`, in one codeunit, with a `# else` branch — and the
undefined default is the branch the Cloud build wants. The offline gate-0 compile of the fully
instrumented project succeeds (554 files, 441 instrumentable, 20,826 raw specs). So the gap is real,
and its incidence on the only real corpus available is zero-impact. Left open at that priority
rather than built against a synthetic fixture.

## (d) `--no-cache` — REFUSED

`--cache` is the AL-OUTPUT cache (compiled test DLLs, keyed on a hash of the `.al` sources), not the
BC artifact cache that R128 is about. Within a single LethAL run **both cache states already occur
by construction**: the target bundle is a freshly instrumented app per artifact, so it MISSES every
time, while the test bundle is unchanged across the whole run and HITS after the first. The probe
run above shows the runner reporting both. Turning the cache off would slow every run to reach a
state each run already reaches.

## (f) `RunnerOutOfScopeException` — MEASURED, and the row's name for it does not exist

There is no `RunnerOutOfScopeException`. Measured wire text, verbatim:

```
InvalidOperationException: out-of-scope: HttpClient.Get - external-http - see docs/scope.md#external-http
```

(the separators are en dashes in the real message). The stable, machine-readable part is the
**`out-of-scope: ` prefix**, followed by the API, a CATEGORY (`external-http`), and a doc anchor.

**Three findings, all of which change what a detector would be:**

1. **The marker does not localise.** It is emitted by al-runner itself, in a fixed structural form,
   not from BC's localised message table. That matters far beyond this row: R66 records that BC's
   prose localises, and R121 has been looking for a discriminator that is not English-only. On the
   al-runner path, this is one.
2. **The row's list conflates two mechanisms.** "SMTP, outbound HTTP, printing, external file I/O
   and web-service publishing" are not uniformly served. External file I/O is refused by **BC's own
   sandbox**, not by al-runner's guard — `NavNCLInvalidPathException: Files outside of the current
   users folder cannot be accessed` — which is prose and WILL localise. Only what al-runner itself
   intercepts carries the marker.
3. **A plain `Error()` is distinguishable.** It surfaces as `NavNCLDialogException: <the message>`,
   so the exception-type prefix already separates an assertion from a refusal.

**Not built, and the reason is cost, not doubt.** Naming this in the report is a per-mutant note or
a caveat, which changes what a run RECORDS and therefore needs a gate. The only fixture that could
gate it is `fixtures/sandbox-tests`, which is shared by `itest:bcdev`, `itest:envtool` AND
`itest:alrunner` — and an outbound-HTTP test behaves differently on a live BC server than under
al-runner, so adding one moves three frozen gates in three different ways. That is a deliberate
piece of work, not a rider on this row.

# (c) BUILT 2026-08-09, and the row's framing was wrong twice

## The measurement that decided how to build it

`scripts/r101c-define-probe/` — one AL source with two `#if` sites, compiled four times with the same
`alc`, changing only `/define:`. Full table in that directory's README.

| `/define:` | exit | bytes |
| --- | --- | --- |
| (omitted) | **0** | 3473 |
| `LETHAL_PROBE_SYMBOL` | **0** | 3505 |
| `LETHAL_PROBE_SYMBOL,LETHAL_PROBE_SECOND` | **0** | 3516 |
| `LETHAL_PROBE_SYMBOL;LETHAL_PROBE_SECOND` | **0** | 3517 |

Four distinct hashes, four successful compiles. **An undefined symbol is silent**: nothing warns,
nothing fails, a different program is built. That is what makes this a correctness hole rather than a
configuration inconvenience.

## What is specific to LethAL, and is worse than the row said

The AST layer does not evaluate `#if` at all — tree-sitter treats the directives as trivia. Running
`generateMutationSet` over the probe produces 3 specs and they sit in BOTH branches, including a
`return-value` on an `exit(Total)` inside the `#if`. With the symbol undefined, `alc` drops that
block AND the mutation guard wrapped around it, so the mutant is deployed but unreachable and comes
back `survived` or `no-coverage`. Both read as statements about the test suite. Neither is one.

## What shipped

- `LethalConfigFile.preprocessorSymbols`, a TOP-LEVEL key (a project property, not a backend one),
  with `validatePreprocessorSymbols` refusing non-strings, empty entries, and any entry carrying a
  comma, semicolon or whitespace — splitting or trimming would silently build a branch nobody chose.
- `ArtifactCompilerConfig.preprocessorSymbols` -> `alc /define:A,B`. **This is the half the row's
  framing missed**, and the one that matters more: it is the compile that produces the instrumented
  target every bcdev verdict comes from.
- `AlRunnerConfig.preprocessorSymbols` -> one repeated `--define SYM` per symbol. Repeated rather
  than the comma form because 2.1.1's help says the comma form's entries are "validated identically
  to `--define`", so they are the same thing and the repeated form cannot be broken by a symbol
  containing a comma.
- `SessionReport.preprocessorSymbols`, REQUIRED and always present, including as `[]`. A report that
  cannot say which symbols were defined cannot say which program it scored, and `[]` is a real
  configuration rather than a missing one.

Both call sites are red-checked: removing either one reddens exactly the test written for it.

## What was NOT built, and why

No fixture with an `#if`. The incidence measurement stands — Continia Document Output, 554 `.al`
files, has exactly ONE `#if` (on `DOSMTP`) and the undefined default is the branch the Cloud build
wants, so there is no real project to verify a gate against. The offline probe is the verification,
and it is re-runnable; a live gate would only re-measure the same compiler.
