**One `--auto-provision` invocation downloaded the same 115 MB of platform apps twice.** Measured
2026-08-09 on al-runner 2.1.1.0, on `fixtures/sandbox-app` + `fixtures/sandbox-tests`, reading the
runner's own `[provision]` lines off stderr:

```
[provision] Resolved: 28.0 -> 28.0.46665.53508
[provision] fetching Microsoft platform R2R apps for BC 28.0.46665.53508 ...
[provision] Downloaded 6 app(s) (115 MB total) to .../28.0.46665.53508/platform-apps
[bc] selected BC 28.1.49838.50794 (...)
[provision] Resolving BC version prefix '28.0'...
[provision] Resolved: 28.0 -> 28.0.46665.53508
[provision] platform R2R apps missing - downloading...        <-- they were written 20 lines ago
[provision] Downloaded 6 app(s) (115 MB total) to .../28.0.46665.53508/platform-apps
```

The second pass runs AFTER `[bc] selected BC ...`, re-resolves the same prefix to the same build, and
declares the apps missing at the same path it had just reported writing them to. It then goes on to
fetch the test toolkit, which the first pass had said was "already present" at a DIFFERENT version's
directory — so the two passes are not merely redundant, they disagree about where the toolkit lives.

**Why this is filed rather than fixed.** It is upstream's, it costs time and bandwidth rather than
correctness, and R128's one-time provisioning step already moves that cost out of every mutant's
timeout budget. What it changes is the SIZE of the number anyone measuring a cold first run should
expect: double.

**What would make it actionable.** A cold measurement (deleting the artifact set every al-runner gate
on this machine selects, ~358 MB) would say whether the doubling also applies to the engine
artifacts, which are the ~1 GB half. R128 declined that measurement deliberately and this does not
change the reasoning. Reporting it upstream needs the same evidence: a clean-cache transcript, not
this warm-cache one.

**RE-MEASURED 2026-08-14, al-runner v2.1.2.0 — still reproduces, and the cost is per invocation.**

Same shape as the 2.1.1.0 transcript above, on `fixtures/sandbox-app` + `fixtures/sandbox-tests`:

```
[provision] Resolved: 28.0 -> 28.0.46665.53655
[provision] fetching Microsoft platform R2R apps for BC 28.0.46665.53655 .../platform-apps
[provision] Downloaded 6 app(s) (115 MB total) to .../28.0.46665.53655/platform-apps
[bc] selected BC 28.1.49838.50794 (...)
[provision] Resolving BC version prefix '28.0'...
[provision] Resolved: 28.0 -> 28.0.46665.53655
[provision] platform R2R apps missing - downloading...        <-- written 30 lines earlier
[provision] Downloaded 6 app(s) (115 MB total) to .../28.0.46665.53655/platform-apps
```

What the 2026-08-09 entry did not know is that this is not a cold-machine event. Three CONSECUTIVE
warm runs each downloaded both times. And the control settles what it costs:

| invocation | wall clock | platform-app downloads |
| --- | --- | --- |
| `--auto-provision` (LethAL's argv today) | 17.0 s | 2 x 115 MB |
| third consecutive run of the same | 17.0 s | 2 x 115 MB |
| `--package-cache <artifacts>/<build>/platform-apps`, no `--auto-provision` | 7.1 s | 0 |
| no flags | 1.4 s, FAILS with the provisioning-gap message | 0 |

So it costs LethAL ~10 s and ~230 MB per CLI invocation, and LethAL makes one per (mutant x covering
test). Filed as [R147](R147.md) with the shape of the fix and the three things that must be measured
before it can land — it changes the argv that produces every verdict, so it belongs behind
`itest:alrunner` rather than in this row.

**Still upstream's bug.** Nothing here says LethAL should fix al-runner's provisioner; it says
LethAL can stop asking it to run twice.
