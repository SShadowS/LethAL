title: "A refused `BeginPublish` is always read as a lost lease, so an owned-but-idle lease is left held until its ttl"

**Found by gpt-6-sol reviewing C02-05 (2026-09-26); pre-existing, not measured live.**
`LeaseSession`'s publish path (`packages/runner/src/orchestrator.ts`) calls `noteLeaseLost` on every
refused `BeginPublish`, and `finish()` then skips the release. But the control app refuses a
`BeginPublish` for more than one reason (`BeginPublish` in
`extensions/lethal-control/src/ControlState.Codeunit.al`): a stale or already-completed op sequence,
or a different active attempt, can be refused while our lease tuple is still valid.

**Consequence:** in those cases the session stops (correct) but never releases a lease it still owns,
so the container stays locked to it until the ttl lapses. Other sessions on Cronus28, LethAL or
CentralGauge, wait. No verdict is wrong; the cost is availability. C02-05's test currently pins
`releaseCalls === 0` for a refused `BeginPublish`, which records today's behaviour, not a ruling that
it is right.

**Fix shape:** on a refused `BeginPublish`, ask the server whether our lease tuple still holds (the
same status call reconciliation uses). Lost: behave as today. Owned and no active marker: stop work
and release through the normal op-gated teardown. Owned with an active marker: keep it (fail closed).
Tests for all three, red-checked.

**Closed by `01c3d1c4` (2026-09-30).** The client could already tell the answers apart, so no AL
change was needed. On a refused `BeginPublish`, `LeaseSession.onBeginPublishRefused` now:
- `alreadyCompleted:true` (a tombstoned op seq, answered only under our tuple): latches the session
  and lets `finish()` release through its normal op gate.
- otherwise probes with `RenewLease`. `renewed:false` is loss, as before: no release. A lost tuple
  never comes back, so `renewed:true` proves the tuple held at the refusal; it then reads
  `GetOperationStatus`. An idle marker latches and releases through the op gate. ANY active marker
  latches and KEEPS the lease, and warns `lease-kept-under-marker` with the new expiry, the marker's
  `opKind`/`opAttemptId`/`opSeq`, and the way out (`lethal doctor`, reconcile, then
  `lethal force-reset-lease`). Keeping skips ONLY the release (`e21c152e`): `finish()` still runs
  its marker handling, so a marker it proves ours (our own op stranded by a lost ack) still gets
  the durable `container-needs-recycle` record, and one it proves foreign still gets none.
- a probe that throws proves nothing and is treated as loss, as before: no release.

**The trade in the KEEP case:** the probe's renew has just extended the ttl, so the container can
stay locked LONGER than before this fix. That is deliberate: a longer hold is accepted in exchange
for never releasing while an operation marker is set. The warning names the expiry so an operator
can see how long, and the commands to free it sooner.

Tests (in `packages/runner/tests/orchestrator.test.ts`, C02-05 block): lost keeps its zero-release
pin; alreadyCompleted and owned-with-no-marker prove the release answered `released:true` from a
fake that refuses `op-in-flight` while a marker is set; owned with our own marker pins no release,
the recycle record and the warning's content, and owned with another session's marker pins no
release, no record and the warning; both probe throws pin no release. Each branch was
red-checked by reverting it. The misleading `after-lease-acquired-uncertain` warning a hook adds
on the same refusal is filed as R362.
