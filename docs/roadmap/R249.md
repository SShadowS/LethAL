title: "A refused `BeginPublish` is always read as a lost lease, so an owned-but-idle lease is left held until its ttl"
section: "correctness-risks"
status: "open"

**Found by gpt-6-sol reviewing C02-05 (2026-09-26); pre-existing, not measured live.**
`LeaseSession`'s publish path (`packages/runner/src/orchestrator.ts`) calls `noteLeaseLost` on every
refused `BeginPublish`, and `finish()` then skips the release. But the control app refuses a
`BeginPublish` for more than one reason (`BeginPublish` in
`extensions/lethal-control/src/ControlState.Codeunit.al`): a stale or already-completed op sequence,
or a different active attempt, can be refused while our lease tuple is still valid.

**Consequence:** in those cases the session stops (correct) but never releases a lease it still owns,
so the container stays locked to it until the ttl lapses. Other sessions on Cronus28, LethAL or
CentralGauge, wait. No verdict is wrong; the cost is availability. C02-05's test currently pins
`releaseCalls === 0` for a refused `BeginPublish`, which records today's behaviour, not a ruling that
it is right.

**Fix shape:** on a refused `BeginPublish`, ask the server whether our lease tuple still holds (the
same status call reconciliation uses). Lost: behave as today. Owned and no active marker: stop work
and release through the normal op-gated teardown. Owned with an active marker: keep it (fail closed).
Tests for all three, red-checked.
