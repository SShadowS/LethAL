**What.** `gapIdOf` hashes the file path (separators normalised), the block's offsets and its raw
source text. Moving the block elsewhere in the file changes its offsets, so it gets a new id even
though nothing inside it changed; and a CRLF checkout's raw block text differs byte-for-byte from an
LF checkout of the same commit, so the two checkouts hash to different ids for the same code. Neither
case is a bug: the id is defined to change under exactly these conditions, so any edit or move gives
a fresh id (owner decision, Q1). It is a limit a user can be surprised by.

**Who hits it.** Anyone comparing gap ids across two runs where the file moved, or across two
checkouts with different line-ending settings (for example CI on Linux against a Windows clone): the
same logical gap gets two different ids, and nothing says why.

**Evidence.** `gapIdOf` hashes offsets and text.

**What would close it.** Not a fix so much as a documented limit today; a future change could hash a
normalised (line-ending-independent) text, or an offset-independent identity, if the churn this
causes in practice justifies it.

**Filed under `product-gaps`** per controller ruling (2026-09-27): the roadmap has no
`known-limits` section.

**Found by.** C02-09's own review of GitHub issue #11, filed as a follow-up rather than folded into
this task's scope.

**Done (R-276b).** What it breaks, first: gap ids are written into each artifact's manifest and
`lethal verify --survivors <gapId>` resolves them against the INSTALLED artifact's own manifest,
so a run's explain output and its verify always agree. An id only stops working when carried to
another run's artifact, and verify then REFUSES it as unknown, by name; it never resolves to the
wrong block.
- **CRLF vs LF: fixed.** A line-ending difference is not an edit, so by the owner's own rule it
  should not move the id. `gapIdOf` now hashes the block's LINE span and its LF-normalised text
  instead of byte offsets and raw text. Pinned in `packages/schemata/tests/project.test.ts` ("R276:
  a CRLF and an LF checkout of the same source give the same gap ids"); red-checked both halves
  (raw text, byte offsets).
- **A moved block: stays a new id**, by the owner's Q1 ruling (any edit or move gives a fresh id).
  Documented here as a limit.
- **Explain schema: no bump.** A gap id is an opaque string read verbatim; nothing recomputes it from
  source. Old artifacts keep their ids. The manifest pins moved: with every id replaced by its
  first-seen index, the old and new manifests are byte-identical for all five pinned fixtures (same
  gap partition; no `.al` file moved).
