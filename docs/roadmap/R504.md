title: "The lease client's `postLeaseAction` clears its abort timer once the headers arrive, so a lease response body BC never finishes has no bound (the R191 class)"
section: "correctness-risks"

**Found by R-503's plan review** (`/coord/handoff/R-503/review-r1-opus-adversary.md`, M4; plan r2
section 1). Follows [[R503]]; same class as [[R191]].

`postLeaseAction` in `packages/runner/src/lease.ts`, which every `LeaseClient` action goes through,
arms an abort timer at `cfg.timeoutMs` (default `DEFAULT_TIMEOUT_MS`, 30 s) for the `fetch`, then
clears that timer in the `finally` around the `fetch` call. So the timer covers only the wait for
the response headers. The `res.json()` body read that follows has no abort, and no `bounded(...)`
race wraps it. A 2xx whose body BC starts and never finishes holds the caller until the runtime
gives up, which is the R191 shape on the lease connection.

Where it bites: the orchestrator's reconcile path reads `LeaseClient.getOperationStatus` there
(`reconcileStrandedPublish`, `reconcileLostAck`, `classifyRetryRefusal`, `pollUntilOpClears`,
`onBeginPublishRefused`, `nextOpSeq`, `finish`). A stalled body on any of them stalls the session
with no LethAL timer behind it. Every other `LeaseClient` action (`AcquireLease`, `RenewLease`,
`ReleaseLease`, `BeginPublish`, `EndPublish`, `RecoverOp`, `ForceResetLease`) shares the same
function and the same gap.

R503 did not change this: it bounds the transport's OWN `RunMutantTransport.getOperationStatus`
(the `runMany` watchdog's poll), which is a different method on a different connection.

Proposed fix: keep the abort armed until the body is parsed (clear the timer after `res.json()`,
as R191 did for `RunMutant` and `postAction` does when bounded), so one timer spans headers and
body. Pin it with a fake 200 whose body never completes; against today's code that test does not
finish.

Unmeasured: whether Bun's socket idle timeout ends such a body read on its own, and when.
