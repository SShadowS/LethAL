`examples/gift-card` is the demo application for Directions EMEA 2026: a small store-credit
extension whose eight tests are green and do not notice that `GetBalance` would return the whole
store's outstanding liability if one `SetRange` were deleted.

**What IS measured.** Both projects compile offline (`bun run compile:fixtures`, which now covers
`examples/` as well as `fixtures/`, red-checked), and a real `--dry-run` reports **40 mutation sites,
36 deployed, 1 batch**, with the four displaced sites named. Ten of the twelve operators appear.
Two facts came out of that run rather than out of reasoning, and both changed the app:

- `flip-filter-literal` DOES claim the `'<%1'` filter in `BlockExpiredCards`, which was an open
  question when the app was designed.
- `if GiftCard.Blocked then` produces **no mutant at all** — no operator claims a bare boolean
  condition — so `RedeemBlockedCardFails` kills nothing of its own. That is written down in the
  example's README rather than quietly left for someone to notice on stage.

**What is NOT measured: every verdict.** The killed / survived / no-coverage split, and which
specific mutants land where, are predictions. In particular the whole demo rests on ONE claim that
has never been tested against a server: that the `remove-setrange` mutant in `GetBalance` SURVIVES.
It should, because every test creates exactly one gift card and the filter is therefore not
load-bearing, but "should" is the word this repository exists to distrust.

The one thing that could falsify it was test isolation, and that was CHASED rather than left as a
worry (see the pre-commitment's Verification section). Writes are measured to roll back, but the
GRANULARITY — per test or per run — is measured nowhere, and under per-run rollback four earlier
tests' entries would still be present and the planted survivor would come back killed. The suite now
clears both tables at the top of every test, so it is correct either way; the open question is filed
as [[R156]].

**The pre-commitment now EXISTS**, written before any live run:
`docs/superpowers/specs/2026-08-16-gift-card-demo-precommitment.md` predicts all 36 deployed
verdicts by (procedure, operator, statement) — 20 killed, 9 survived, 7 no-coverage, score 68.97% —
and names the four rows whose outcome it is least sure of, the isolation failure that would break
the demo, and one stage-mechanics finding the exercise produced on its own (nine survivors, ranked
by evidence, put the planted bug SIXTH, so `explain --top 5` would cut it off the list).

**What closes this row:** a rehearsal run against a container, compared per-mutant against that
file with every disagreement recorded as a finding, then frozen with `lethal campaign freeze` so that any drift between the rehearsal and the stage is a diff rather than
a surprise. That is the same discipline R136, R134 and R132 used, and the demo deserves it more than
they did: those had a gate to catch them, this has a room.

Evidence: `examples/gift-card/README.md` (the inventory and the two measured surprises),
`scripts/compile-fixtures.ts` (the compile gate now covering `examples/`), and the absence of any
frozen baseline under a records directory for this app.
