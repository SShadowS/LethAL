**Measured 2026-09-26 on Cronus28, twice, while gating GH-24a on `lethal/lane-bugs`.**
`itest:hang` fails with `lethal.remove-assignment at line 104: expected killed, got
timeout-killed`. The mutant is `sandbox-hang`'s `HangLogic.DrainQueue`, deleting `Pending -= 1`
inside `while Pending > 0 do begin ... end`. The gate's own comment records why it was `killed`
before: the surviving `Drained += 1` keeps counting and overflows Int32 in about 4.4 seconds,
which raises inside the budget. Every other verdict on that gate is unchanged, and `itest:bcdev`,
`itest:tables` (with GH-24's pre-committed arm) and `itest:chunked` pass on the same build.

**Cause (reasoned, not yet measured).** GH-24 emits `MutationSelector.Reached('<id>')` at the
mutant's own statement (`reachGrainOf` and `REACH_MARKER` in the schemata `dispatch` module). For
a statement inside a loop body the marker runs on EVERY iteration: a call into the selector, which
forwards to `LC Control State.NoteReached`. `NoteReached` exits early once `ObservedActive` is set,
but the two calls themselves remain per iteration. A loop that must run about two billion times to
overflow now takes longer than the budget, so the kill becomes a timeout. The only change between
this run and the passing master run is the marker and control app 1.0.0.19.

**Why it matters.** GH-24's plan (Decision 12) states that existing verdicts cannot move because
the marker has no effect on target state. That is true for state and false for TIME. A mutant
whose kill depends on how fast a loop runs (an overflow, a counter, anything racing the budget)
can move between `killed` and `timeout-killed`. Both are kills, so the score is unchanged here,
but `killingTest`, `killPosition` and warm-kill confirmation can differ, and a gate pinning the
verdict fails.

**Options, not decided.**
1. Make the marker cheap after the first hit inside the target itself: a global `Boolean` in the
   generated `MutationSelector` (one per artifact, reset by the control app per test through a
   new call, or by making the selector SingleInstance), so the hot path is one local test.
2. Place the marker once, before the loop, when the resolved statement is inside a loop body
   (this changes what "reached" means for the first iteration only).
3. Accept the move and re-pin `itest:hang`'s row as `timeout-killed` (owner's call: it is a
   frozen gate figure).

Evidence: `H:/lethal-coord/tasks/GH-24/run001/itest-hang.attempt1.log` and `itest-hang.log`
(both runs), the `DrainQueue` row comment in `packages/runner/itest/hang.itest.ts`.

**Fixed 2026-09-26 (owner ruling: option 1), `2304074` and `0a9cc84`.** The marker is now
`if not LethALReachLatch then begin MutationSelector.Reached('<id>'); LethALReachLatch := true; end;`,
where `LethALReachLatch` is a Boolean LOCAL of the procedure or trigger that holds the marker. After
the first hit the loop's hot path is one test of a local, with no call at all. A local starts false
on every call, so it cannot carry across a test or an `ObservedActive` reset, and the reach control
arm still reads `[true, false]` in one grouped call. The declaration skips comments before `begin`
(`0a9cc84`). Measured on Cronus28, the `DrainQueue` overflow kill (mutant `durationMs`, one sample
each, scoped with `--lines`): master with no marker 4863 ms; the per-iteration marker over 20000 ms
(timed out at the gate's 20 s budget); the latch 7935 ms. `itest:hang` passes again with that mutant
`killed`, and `itest:bcdev`, `itest:tables` (the GH-24 arm as pre-committed), `itest:chunked` and
`itest:alrunner` pass on the same build.
