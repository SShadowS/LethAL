**Found by the code lane closing R356 (2026-09-30).** Under `%TEMP%` there were 3,369
`lethal-alrunner-canary-*` directories (4.6 MB), and the count went from 3,369 to 3,377 during one
full `bun test` run. By date they grow on every day the suite ran since 2026-07-26 (340 on 09-26,
242 on 09-29). The canary code removes its directory in a `finally`, so the leak is likely a unit
test, or a path with a stubbed `rm` or an early return, that creates one and never reaches it.
Also measured then, not deleted: 682 `lethal-alrunner-cov-*` (22.8 MB, the R356 leak, now fixed)
and 91 `lethal-alrunner-contract-*` (0.1 MB).

**Not audited yet:** the other `mkdtemp` users outside `al-runner-*.ts` (`cli.ts`,
`campaign-freeze.ts`, `env-tool-session.ts`, `test-app-publish.ts`).

**To close.** Find which test or path creates a canary directory without removing it (run the
suite file by file and count), fix it, and add a guard that fails when a test file leaves a
`lethal-*` temp directory behind (for example an after-all check in the test preload). Audit the
other `mkdtemp` users the same way.

**The product side.** `runFromCli` makes `<tmp>/lethal-XXXXXX` for every `lethal run` (the
instrumented copy of the project for every batch, every worker's build and, for bcdev, the
compiled `.app`) and never removes it; `verifyFromCli` did the same with `lethal-verify-XXXXXX`.
The first fix (c069f978) removed both, on the belief that nothing reads them after the function
returns. That was WRONG for the run's folder, and review caught it: the orchestrator records each
batch's `appPath` and `instrumentedDir` in the store, both inside that folder, and `lethal
verify` reads them back (`loadInstalledArtifact`), so removing it made every verify after a run
refuse with `local-copy-unreadable`. The fix round REVERTS the run-side removal: the run's folder
is kept on purpose, and removing it safely is filed as R360. `verifyFromCli`'s own folder is
removed on every path out, best-effort with a warning (`removeScratchQuietly` in `cli.ts`); the
review found that safe, since nothing reads it after verify returns. Tests: `cli.test.ts` "verify
removes its scratch directory when the backend build fails" (RED-CHECKED: with the removal
commented out it goes red and the guard names `cli.test.ts: lethal-verify-XXXXXX`), and
`cli.test.ts` "lethal run then lethal verify on one store (R358)", which drives the real
`runFromCli`, `runSession` and `verifyFromCli` against one store with fake backends and
asserts verify reaches `compileTestApp`, the first backend call after `loadInstalledArtifact`,
with the run's artifact id. RED-CHECKED: with c069f978's `cli.ts` (run-side removal) put back it
goes red, printing `artifact-files-unusable` / `local-copy-unreadable` on the run's `fake.app`;
restored, green. The three test files that drive `runFromCli` (`cli.test.ts`,
`cli-envtool.test.ts`, `changed-since-git.test.ts`) remove the run folders themselves after
their last test (`removeRunScratchAfterAll` in `helpers/scratch.ts`), so the guard stays green.

**The test fixes.** `packages/runner/tests/helpers/scratch.ts`: `scratchDirs()`, called once at
the top of a file, returns a `mkdtemp` that records each directory and removes it in that file's
`afterAll` (it tries every one, then fails the file on any it could not remove). 27 test files
now make their temp dirs through it. The canary tests remove the real directory themselves, the
two coverage backends are `close()`d, the I7 test closes its store, `campaign-subcommands`
removes its `beforeAll` directory, and the two stray `mkdtemp` calls are deleted. The three
prefixes that did not start with `lethal-` are renamed so the guard covers them.

**The guard** (`scripts/test-preload.ts`). The preload makes one private directory per
`bun test` process, `<real tmp>/lethal-unit-run-XXXXXX`, holding the fake home (R264, which
itself used to leak one `lethal-test-home-*` per run) and `tmp/`, and points TEMP, TMP and TMPDIR
at `tmp/`. A scan of the shared temp folder would blame the wrong file whenever another session
writes there; this directory only this process uses. Measured on Bun 1.3.14: a preload's
`afterAll` runs ONCE for the whole run, not per file, and `Bun.main` names the test file that is
running. So the preload's `beforeEach` and `afterEach` record each test's new `lethal-*` entries
against `Bun.main`; when the next file starts, or the run ends, any of them still present fail
the run, naming the file and the entries. A file may clean up in its own `afterAll`, which runs
after its last test, so nothing is judged earlier (a per-test `afterEach` check was tried first
and wrongly failed seven files that clean up correctly that way). An entry a `beforeAll` makes
and never removes is caught by the run-end check, without a file name. The private directory is
removed at the end. Cost: two `readdirSync` of a near-empty directory per test. RED-CHECKED: with
the canary test's `realRm` cleanup line removed, the full suite exits 1 with
`al-runner-canary.test.ts: lethal-alrunner-canary-66bZ0g`; restored, green. Bun prints this failure as an `(unnamed)` failure under the LAST test file that ran, whichever file leaked (review M3); the message names the leaking file, and says so. A failed removal of the private directory is appended to that message rather than replacing it (review M2).

**Suite time**, full `bun test` from the root on this machine: 78.6 s before (0 fail, 965 entries
left behind), 78.1 s after (4,818 pass, 0 fail, nothing left in the private directory and nothing
in the outer temp, child processes included). After the review fix round (64488c59): 73.3 s,
4,816 pass, 0 fail.

**Outside the guard.** A child process does not see the redirect: Bun, including
`node:child_process` under Bun, gives a child the environment the parent STARTED with unless
`env` is passed (measured 2026-09-30). The run above left nothing in the outer temp, so no child
leaks today. The same gap applies to R264's fake home; filed as R359.
