**Filed 2026-10-24 by lethal-preproc during R-707.** Evidence: `/coord/handoff/R-707/measure.md` (bc2, step 4),
`scripts/r707-probe/`. Related: [[R605]], [[R707]].

**What was measured (bc2).** Target A 1.0.0.1 and a dependent B were installed. A was upgraded to 1.0.0.2 with a
procedure removed that B calls. BC recompiled B, found the break, and refused with 422:

> `error AL0132: 'Codeunit "R707 Target"' does not contain a definition for 'Answer'`. **The original extensions
> could not be restored** due to Cannot install the extension R707 Probe Target ... 1.0.0.1 because a newer version
> 1.0.0.2 was already installed. Extensions that were previously installed but could not be reinstalled. These
> extensions should be manually reinstalled ...

State after: A had one row, 1.0.0.1, `isInstalled = false`. B had no row at all, and its web service answered 404.
So the refusal removed the dependent and left the target uninstalled. A refused publish of the SAME version, in
place (step 3), did restore. The cause BC names is the installed-version record from [[R605]]: the failed upgrade
raised the record to 1.0.0.2, so the old 1.0.0.1 cannot be put back.

**Why.** BC recompiles an INSTALLED dependent from the source inside its RESIDENT package, not from the new
source a script has on disk (measure.md: the AL0135 is from the dependent's own source).

**Who can trigger it.**
- BOTH `scripts/bc-linux-setup.ts` and `scripts/bc-republish.ts` could, before R-707, on a CO-CHANGE: a target
  change that compiles with the NEW tests source (which both scripts checked) but breaks the RESIDENT tests
  source. Publishing the new tests app together with the target does not help, because BC checks the resident one
  first. Both now read each installed dependent's resident source, compile it against the new target build, and
  refuse `resident-dependent-breaks` before anything is sent. A dependent that is not installed has no resident
  source and is not checked. A check that fails for another reason (a symbol download, no alc) is refused as
  `dependent check failed (not a compile result)`. Only FIXTURE dependents are checked: an ad-hoc app that
  depends on a fixture target is not.
- Anyone publishing by hand over the dev endpoint, or a future script that skips the check.
- OPEN, not traced: whether a gate's own minted target deploy under an old tests app can trigger it.

**How to recover a stripped server.** Not measured; rests on R605. The owner restarts the server, which clears
the R605 record. Then re-run `bun scripts/bc-linux-setup.ts --server bcN`, which republishes the target and the
tests app. (Not a lane's job: a restart is host-only.) A `--mint` publish of the target, which outranks the
record, is a possible recovery without a restart; also not measured.

**The limit.** Only an AL compile break was measured as the cause of the refusal. Another refused upgrade (a
dependency or permission error, for example) may fail to restore the same way; that is not measured.

**To close.** Measure another refusal cause, or find a way to clear the record without a restart (the same open
question as [[R605]]). Until then the fix is prevention: the resident-source check in both scripts. A script
that removes the dependent first and republishes it is filed as [[R711]].
