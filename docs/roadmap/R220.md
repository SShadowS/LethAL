**Found while asking why a real-project al-runner run was going to take 25 hours.** The answer
turned out to be two separate things, and both have a remedy that already exists upstream.

## 1. It was not slow. It was failing, 65 s at a time

Pointed at Continia Document Output, every al-runner invocation fails identically:

```text
FATAL: dependency compile failed - cannot continue.
  COMPILE-FAIL - CDO Send Mail Management.cs(174,81):
  error CS1501: No overload for method 'ALSplit' takes 3 arguments
<bundled>: EMIT-EXCLUDED - Continia Document Output: 323 object(s) could not be compiled
<bundled>: EMIT-ZERO (892 AL error(s))
```

**Minimal repro, six lines**, and the A/B is the whole finding:

```al
procedure P(Input: Text): List of [Text]
begin
    exit(Input.Split(','));        // exit 0
    exit(Input.Split(',', ';'));   // exit 3, FATAL
end;
```

AL's `Text.Split` with TWO separators generates `ALSplit(receiver, ',', ';')`, and the runtime
library al-runner provisions has no 3-argument overload. Continia uses it three times in
`src/Features/Email/Sending/CDOSendMailManagement.Codeunit.al`.

Not a BC-build selection problem, tested on all three available:

| BC build | result |
| --- | --- |
| 28.1.49838.54169 (auto-selected) | `ALSplit` FATAL, 323 objects dropped |
| 28.1.49838.54368 (al-runner's own engine build, downloaded) | same, 2,275 AL errors |
| 28.1.49838.50794 (cached) | al-runner CRASHES: `[Cecil] method ...ExecutionScheduler..ctor(6) not found - Ncl shape changed` |

So a project using two-separator `Split` cannot run under al-runner at all, and LethAL's honest
`error` verdict per mutant is the correct outcome. Worth reporting upstream: it is a supported AL
construct the compiler accepts and the provisioned runtime cannot execute.

## 2. The cost model: LethAL throws away al-runner's warm state

Even with the build working, the shape is wrong. LethAL's `OneShotTransport` spawns a FRESH
al-runner process per test, and each one pays a full cold compile of the whole app:

| bundle | seconds per invocation |
| --- | ---: |
| `fixtures/sandbox-app`, 2 files | 3.1 |
| Continia Cloud, 553 files | 65 |

At 1,386 tests that is ~25 hours for the BASELINE alone, before a single mutant.

al-runner already solves this and says so in its own help:

- **`--server`** — "Long-running JSON-RPC daemon over stdin/stdout (warm deps + BC patches loaded
  once; **~19s->~4s per run**). Commands: `runTests` (streaming per-test results), `execute`,
  `shutdown`. Full wire schema: `docs/server-mode.md`."
- **`--watch`** — resident, re-runs in-process on change, "deps loaded once ~seconds/save, not a
  cold re-run".

A ~5x per-run improvement is upstream's own number, and it is the floor rather than the ceiling
here: the daemon amortises the compile that dominates a 553-file bundle, which is exactly the cost
that makes the one-shot model unusable at real scale. `runTests` streaming per-test results is the
shape LethAL's baseline phase wants.

## 3. The one that matters most: al-runner now has COVERAGE

`AlRunnerBackend.capabilities()` reports `coverage: "none"`, and that is half of why the backend is
[[R183]]'s `authoritative: false`: an unreached mutant comes back `survived` instead of
`no-coverage`, which under-reports rather than lying, but makes the score unquotable.

al-runner 2.11.0 has `--coverage`: "Statement-level coverage via BC's own StmtHit instrumentation
(no rewrite of emitted AL output, the hook lives in `Ncl.dll`). Writes Cobertura XML."

**Measured on our own fixture, and it agrees with bcdev:**

```text
al-runner --coverage --coverage-out cov.xml fixtures/sandbox-app fixtures/sandbox-tests
  SandboxLogic.Codeunit.al     line-rate 0.8571
  SandboxPricing.Codeunit.al   line-rate 0.0000
  SandboxTests.Codeunit.al     line-rate 0.6250
```

`SandboxPricing` at ZERO is exactly where `itest:bcdev` reports its four `no-coverage` mutants
(M0016-M0019) and where `itest:alrunner` currently reports four `survived`. The frozen gates say
3 / 12 / 4 and 3 / 16 / 0, and that difference of four IS this file. So wiring `--coverage` into the
backend would move those four to `no-coverage` and make the two backends agree on the one axis they
currently disagree about.

That is a measured correspondence on a real gate, not an inference from the help text.

## What closing it would take, in order of value

1. **Read `--coverage`.** Parse the Cobertura XML into the same coverage shape the fenced-coverage
   client produces, and flip `capabilities().coverage` off `"none"`. The gate baseline moves from
   3 / 16 / 0 to 3 / 12 / 4 and becomes a per-mutant match with `itest:bcdev`, which is a much
   stronger gate than either is today.
2. **Re-measure [[R183]]'s other residual.** The canary already reports that 2.11.0 DISCARDS a row
   written inside `Codeunit.Run` when the error fires, which 2.7.0.0 did not. If that holds against
   bcdev, both reasons for `authoritative: false` are gone and the ruling should be revisited rather
   than left standing on stale evidence.
3. **Replace `OneShotTransport` with the `--server` daemon.** The largest cost win, and the one that
   decides whether al-runner is usable on anything bigger than a fixture. Needs a JSON-RPC client,
   lifecycle handling and a story for a hung run, so it is the biggest of the three.
4. **Report the `Split` overload gap upstream.** Independent of all of the above and cheap.

Items 1 and 2 together would change what this backend IS, so they should be done before anyone
spends effort on 3.

See [[R219]] for the separate blocker that stopped this project being instrumented at all, and
`docs/measurements/README.md` §"al-runner v2" for the contract this would extend.
