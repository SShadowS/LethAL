Found while writing PR-70's CI templates (`docs/ci/`; review of 2026-11-16).

**What.** When the line filter (`--lines`, `--changed-since`) keeps no deployable mutation site, the orchestrator refuses with
"the line filter ... kept no deployable mutation site ... Refusing rather than reporting a score for nothing" (Issue #19), and
the CLI exits 1, the generic error code. In a pull-request pipeline the common case is exactly this:
- a pull request that touches no `.al` file;
- a comment-only `.al` edit;
- an edit to lines that hold no mutant.

So the pipeline goes red with no defect found.

**Today's workaround** (in the templates): a path filter on `*.al`. A comment-only `.al` edit still fails.

**Possible fix.** A distinct exit code (or a documented outcome) for "nothing to mutate in the selected lines", which CI maps
to a pass, kept apart from `4` (every mutant errored), which must stay a failure. Refusing to report a score for nothing is
right; the problem is only that the refusal shares exit 1 with real errors.

**To close.** A distinct, documented exit code and the templates updated to map it.
