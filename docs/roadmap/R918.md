Found by coord task R-915 (BC.History Subscription Billing and E-Document Core on al-runner v3, 2026-11-11). Evidence: `/coord/handoff/R-915/` (`edoc.s1.*`, `sb.s1.*`). Related: [[R761]], [[R763]], [[R916]], [[R915]].

**What happened.** Both apps ran one-shot, not on the serve-entries default, with `al-runner-v3-serve-default-fallback`:
- Subscription Billing: `multi-object-or-wrapped` (page extensions among others).
- E-Document Core: `multi-object-or-wrapped` (permission sets, a control add-in, a page, a table, ...), and `unproven-test-name-shape`: its test codeunits are named like `E-Doc. Flow Test`, and R761's proven codeunit shape has no `-`.
- E-Document Core then scored **19 of 15,287** mutants in a 14,400 s `--time-budget` session. Subscription Billing scored 4,823 of 17,838 in its first session.
- Every `--resume` session falls back too (the `resume` reason), so resuming a time-budgeted run never gets serve back.

**Why it matters.** R761 keeps serve only where it was measured equal to one-shot. The MO and WR shapes were measured on one-shot only. Any real BC app of this size has at least one such file somewhere, often in an object LethAL does not instrument (a permission set, a control add-in). So the default is one-shot for exactly the apps that need serve's speed, and large apps cannot be finished.

**Invented repro.** A target with one codeunit and one `permissionset` object in an `#if` region, a test codeunit named `A-B Test` with one passing test. `lethal run --backend al-runner-v3` (no `transport` key) warns `al-runner-v3-serve-default-fallback` with both reasons and runs one-shot. Remove the permission set and rename the codeunit: it runs on serve.

**Wanted, in order of cost:**
1. Leave out of the shape check files whose objects LethAL never instruments and v3 never needs to place for coverage (permission sets, control add-ins, enums without code, ...), if serve's risk for MO and WR is only about mutated or placed objects. That needs reading why R761 kept those shapes off serve.
2. Prove serve for the MO and WR shapes and for `-` in a codeunit name, as R763 did for method names: a leg per shape, per mutant equal to one-shot.
3. Let a `--resume` session pick serve when the first session did, since the transport is not in the fingerprint.

**Fixed (coord R-924), except the `-` name shape, which is [[R922]] (coord R-919).**
- **Why R761 kept the shapes off serve:** only because they had been measured on one-shot only; R761 names no other risk.
- **2, the shapes proven:** new gate legs MOE and WRE run MO's and WR's sessions on serve-entries. Both equal the one-shot legs'
  frozen baselines per mutant (MOE 14 of 14, WRE 102 of 102), with the same counts, killers, warnings and notes. Pre-committed on
  master (e1ca5d11); both are default legs and in `V3_GATE_LEGS`. So the `multi-object-or-wrapped` fallback reason is removed.
- **1, non-instrumented objects:** no separate rule is needed once the shapes are proven. Checked on this item's invented repro (a
  permission set wrapped in `#if` beside the sandbox target, without the `-` name): the default runs serve, with no fallback, and
  equals a one-shot run per mutant (22 of 22). Evidence: `/coord/handoff/R-924/`.
- **Builds already in the gate manifest (orchestrator ruling, 2026-11-11, option a):** those rows were gated before MOE and WRE
  existed, yet now take serve for these shapes too. `current` (edge-42af5d384) passed MOE and WRE in this task's gate; alpha.14
  (alpha.14-ef00a6a8f, the newest release) is re-gated with `--refresh-rows` at this branch's head, MOE and WRE included. Covered
  by the ruling, NOT by measurement: alpha.12-d4bc8d3a5, alpha.13-23e7631be, edge-05d692e5e, edge-3096bf68f, edge-3138effad,
  edge-6bb821b98, edge-897b441eb, edge-9597b4a01 and edge-a0825f1d9. The ground: the shape-specific part (coverage placement) is
  built from the deployed text the same way on both transports, and every one of those rows passed S1E, N1S and O1 on serve. Before
  the release there is no back-compat duty, so a later task may drop the older rows from the manifest instead.
- **Not exercised by any leg:** `#elif`, a multi-object file inside one wrapper, several objects in one wrapper, nested wrappers,
  a multi-object TEST file, and the §6 serve coverage window (the fixtures have no `Sleep`) (build review r1).
- **Live check (Subscription Billing, R-915's app, sources rebuilt from BC.History, edge-42af5d384, the DEFAULT transport, full
  set, one `--time-budget 7200` window).** It took serve-entries (no fallback warning; 10 daemons, 46,442 entries), with the same
  baseline as R-915 (626 of 727 passed). Rates over the mutant loop only (the `mutants` phase's elapsed time, baseline excluded;
  `/coord/handoff/R-924/sb/rate.ts`), where "executed" counts mutants that ran (not no-coverage) and "decided" counts every scored
  mutant:
  - serve: loop 5,712 s, **73.1 executed per hour** (116), 3,098 decided per hour (4,916);
  - R-915 one-shot: session 1 loop 13,401 s, **6.2 executed per hour** (23), 1,296 decided per hour (4,823); session 2 loop
    12,259 s, 10.9 executed per hour (37), 1,420 decided per hour.
  - So serve executes about 12 times as many mutants per hour as one-shot's session 1 (about 7 times session 2). Most decided
    mutants are no-coverage (4,800), which run nothing on either transport.
- **3, `--resume`:** already holds on the default. Under `isolation: "auto"` (the default since R896) a resume keeps serve-entries,
  and R-915's Subscription Billing resume logged no `resume` reason. Only an explicit `isolation: "test"` or `"method"` still falls
  back, and there the reason is real: the reused baseline snapshot has no rows to compare the serve warm-up with.
