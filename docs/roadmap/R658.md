**Filed 2026-10-22 by lethal-bugs during R-649** (its pre-commitment row B: "filed if a real project could hit it").

**What was measured.** R-649's probe on bc2 (`docs/measurements/r649/bc2-probe.json` on `lethal/r649`,
`/coord/handoff/R-649/probe/drive.log`) ran a test codeunit whose test does `Sleep(600000)`, as a BASELINE call
(`RunMutant`, `mutantId ""`, budget `BASELINE_TIMEOUT_DEFAULT` = 120 000 ms):
- LethAL's client gave up at 120 060 ms (`deadline-exceeded`, `in-flight-unknown`, "RunMutant timed out before headers").
- BC did NOT stop the test. The op (`r649-92932-22828`) was still `completed: false` at every 10 s poll up to 720 s after
  dispatch.
- At the end, the control-app lease release answered `{"released": false, "reason": "op-in-flight"}`.
- **Twenty minutes later it was still running.** A read-only check under a fresh coord lease
  (`/coord/handoff/R-649/probe/bc2-status.log`): 11 `GetOperationStatus` polls from 15:56:34Z to 16:01:37Z all read
  `completed: false`, `state: running` in `LongSleepThenAssert` (started 15:41:33Z) — about 9 minutes past the end of
  a 600 s Sleep. `lethal doctor` then reported bc2's control-app lease **orphaned** (held by the probe, expired
  15:53:48Z) and suggested `lethal force-reset-lease`. No reset was run, because a reset while the op is live could let
  the next session overlap it. bc2 was taken out of use pending an owner recycle (a host action).
- So one abandoned baseline op made a whole BC server unusable for every lane, and the only in-product way forward
  (`force-reset-lease`) is unsafe while the op still runs.

**Why.** LethAL Control's stop (R53) is wired only for MUTANT runs (`BcDevMcpBackend.runViaTransport` passes a stop hook
only when `mutantId` is not `""`). A baseline call that times out on the client side is simply abandoned; the server
keeps executing it.

**Who hits it.** A real project with a baseline test that hangs or runs past the budget (a long `Sleep`, a wait on an
external resource, an infinite loop in a test helper). The run reports the test as not green and moves on, but the BC
server stays busy with that op, the control-app lease stays held by it, and the next session on that server may be
refused or misread its op sequence until the op ends on its own (or never, for a true hang).

**To close.** Measure first, then decide: whether a baseline timeout should invoke the same stop path as a mutant
timeout (`StopHungRunAt` / the R53 stop), and what the session reports when it does; and what the next session sees
while such an op is still in flight. Cover it with a live probe like R-649's and a hang-gate leg, since only
`itest:hang` exercises the stop.

Evidence: R-649's probe log and JSON (above); `BcDevMcpBackend.runViaTransport` in
`packages/runner/src/bcdev-backend.ts`; R53.
