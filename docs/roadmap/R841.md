**Ruling (coord, 2026-11-06): no refusal.** LethAL does not refuse these shapes. A run already handles them without a wrong
verdict and without losing a mutant silently, so extending `continuationRefusal` would only refuse projects that run fine.

## What

`continuationRefusal` looks only at a `preproc_conditional_statement`, and only at what comes before and inside the `#if`.
These shapes get past it. Each one's source compiles, and the instrumented artifact fails alc, under builds `[]` and `[LETHALX]`
unless stated. The parse has no ERROR node.

| Shape | Parse | Artifact |
|---|---|---|
| `repeat A += 1; until A` `#if X` `* 2` `#endif` `> 3;` | tail mid-condition | AL0175 |
| `if Flag then Bar()` `#if X` (empty or comment) `#endif` `else Foo(1);` | `else` read as a `call_statement` | AL0110, orphaned ELSE |
| `if Flag then A := 1` `#if X` `+ B` `#endif` `else A := 2;` | tail in a then branch | AL0111 |
| the same with no `else`, ending in `;` | tail in a then branch | AL0631 |
| `case A of 1: Bar()` `#if X` `;` `#else` `else Foo(1);` `#endif` `end;` | `preproc_conditional_case` | AL0224, `[LETHALX]` only |
| `case A of 1: Bar()` `#if X` `; 2: Foo(1);` `#else` `;` `#endif` `end;` | `preproc_conditional_case` | AL0224 |

For-to, case-head and case-label tails, `if` condition tails, argument tails and a nested empty `#if` compiled fine.

## What a run does (measured 2026-11-06, coord task R-841)

Method: one throwaway project per shape (the shape's codeunit, a healthy second codeunit, a small test app), run through
the real `lethal run --backend al-runner-v3` under no symbol and under `LETHALX`, 12 runs. The bcdev path's compile stage
was driven offline with the real `runSession`, the real `ArtifactCompiler` and real alc, and a fake backend that stands in
for the server (12 runs). The two paths gave the same rows.

**The four outcomes**, and which one each shape is:
- (a) the run stops loudly and names the file: none of the shapes.
- (b) bisection drops only the affected mutants, and the report says so by name: **all six shapes, in both builds**
  (shape 5 only under `LETHALX`; with no symbol its artifact compiles and nothing is dropped).
- (c) mutants are silently lost: none. Every run had as many rows as the generator had sites (`mutation set: N sites -> N
  deployed`, then N rows).
- (d) a wrong verdict: none seen.

What the run does, step by step (`runSession`, `checkPlainBuild`, `isolateAndNote`, `redeployClean` in `orchestrator.ts`,
`isolateBreakingMutants` in `bisect.ts`):
1. Alc rejects the artifact: an `AlcCompileError`. Anything else aborts the run; only this is bisected.
2. The unmutated target is compiled once (`compilePlainCheck`, R461). The source compiles, so no `UnmutatedBuildFailedError`.
3. Isolation emits the warnings `compile-isolation` and `compile-isolation-result` ("N of 64 compile-only runs: K culprit(s),
   G in pairs, U unresolved"), finds the mutants that break the compile alone or in pairs, and removes them.
4. The clean set is redeployed and scored. Each removed mutant gets an `error` row whose `failureNote` names the mutant id,
   file, line, operator and the alc code, for example "mutant M0008 (<file>, line 14, lethal.loop-truncate) fails to
   compile on its own: AL0175" (the row writes the file and line joined by a colon).

## What an `error` row does to the score

`mutationScore` is built in `report.ts` (the report builder, near `const denom`):
`denom = counts.killed + counts.timeoutKilled + counts.survived`, and
`mutationScore = (counts.killed + counts.timeoutKilled) / denom`, or `null` when `denom` is 0.
An `error` mutant is in **neither** the numerator nor the denominator. `noCoverage` is excluded the same way.

On a measured run, shape 1 with no symbol (`score: 85.7%`): 6 killed, 1 survived, 3 no-coverage, 1 error. Score is 6 / (6 + 1)
= 85.7%. If the error mutant had been scored: as a survivor, 6 / 8 = 75.0%; as a kill, 7 / 8 = 87.5%. So one error row hides a
move of 10.7 points down or 1.8 up, depending on a verdict nobody observed. Shape 3 has two error rows: its score is
6 / (6 + 4) = 60.0%, and if both had survived it would be 6 / 12 = 50.0%.

The score is therefore not wrong, but it describes a smaller set, and the more mutants a shape drops the less it says.
The report shows `counts.errors` and each row's note. When EVERY mutant errors, the report carries the `all-errors` caveat,
`mutationScore` is `null`, and the process exits 4.

## The limits, and how they were closed

1. **Run-time meaning of the build is the same as alc's: closed 2026-11-06.** With no symbol and with `LETHALX`, shape 1 was
   made observable: `procedure Loop(): Integer` returns the loop count, which is 4 with `until A > 3` and 2 with
   `until A * 2 > 3`. The test app asserts the count with its own `#if LETHALX`. Through a real `lethal run` on v3, the
   baseline passed in both builds (`1/1 passed`). A control with the expectations swapped went red in both builds, and its
   failure text read `Loop ran 4 times, this build expects 2` (no symbol) and `Loop ran 2 times, this build expects 4`
   (`LETHALX`). So v3 runs the arm alc compiles. For alc's own side, a probe puts an undefined name in the `#if` arm
   (`* NoSuchVariable`): alc exits 0 with no symbol and fails AL0118 with `/define:LETHALX`, so alc takes the arm exactly
   when the symbol is defined.
2. **Zero mutants applied: closed 2026-11-06.** Two ways to get there, both through the real `runSession` and bisection with a
   fake alc, pinned in `packages/runner/tests/r841-isolation.test.ts`:
   - the empty artifact fails (the `environmental` plan of `isolateBreakingMutants`, a `none` plan): every mutant is an
     `error` row carrying alc's text, nothing is redeployed, `mutationScore` is `null`, and the report carries `all-errors`;
   - every mutant is isolated out (the clean set is empty): `redeployClean` is not called, every mutant is an `error` row
     naming itself, the same `null` score and `all-errors`.
   Neither gives an empty report that reads as a pass.
3. **Shape 1 pinned offline: closed 2026-11-06.** The same test file pins shape 1 through the real isolation path. CI has no
   alc, so alc is faked there: the fake refuses an artifact exactly when its manifest holds the loop-truncate mutant, which
   is what real alc did. The real-alc reading is the one above. Red-checked in both directions (drop the error row; mark a
   healthy mutant as an error).
4. **Live, on real BC.** `bc2`, BC 28.4, 2026-11-06: a copy of `sandbox-app` with shape 1 as one extra codeunit, through `lethal run
   --backend bcdev`. 21 sites, 21 rows: `M0002` `lethal.loop-truncate` an `error` row naming AL0175 at its line, and 3 killed, 12
   survived, 5 no-coverage, the fixture's own 3 / 12 / 4 plus the shape's one no-coverage mutant. Isolation used 4 of 64 compile-only
   runs. This matches the 24 offline runs. `itest:bcdev` passed on `bc2` after it. Logs: `/coord/handoff/R-841/bc2/`.
5. **Upstream.** The `else` misparse is https://github.com/SShadowS/tree-sitter-al/issues/39.
