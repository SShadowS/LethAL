**Filed 2026-11-06 by lethal-code, from R-845.** Related: [[R845]], [[R843]], [[R709]].

**What.** The clash check of [[R843]] and [[R845]] compares the target with the installed apps that depend on it, directly or through
another app. It reads each one from the package the server holds. It cannot see an installed app that is NOT a dependent, because
the control app's `InstalledDependents` lists apps by the app they depend on, and no action lists installed objects or fields.

BC refuses that clash too (R845 batch, cases U3, L2, L3h), and does not try to restore: the target and its dependents are gone, the other
app is untouched. Two unrelated apps adding one field to `Customer` is the likely real case. Today the run stops after the fact with
`UpgradeClashRefusedError`, which names the recovery section.

**To close.** A control-app action that reads `AllObj` (object type and id, with the owning app) and `Field` (table, field id and name,
with the owning app), and a check that compares the target against every installed app, not only the dependents. It needs a control-app
version bump (`MIN_CONTROL_VERSION` in `packages/runner/src/harness.ts`), AL changes verified by an offline `alc` compile and the hang
gate, and the proof table in `docs/gates/servers.md` redone for each server.

**Also not covered by the check** (from the [[R845]] limits): a test app an env-tool hook publishes before the target's deploy, an env
tool's own publish command (its schema mode is unknown),report columns, and trailing spaces in names.

**What is built.**

- `extensions/lethal-control/src/ControlApi.Codeunit.al`: two read actions, `ObjectOwners(ItemsJson, MaxMs)` and `FieldOwners(ItemsJson,
  MaxMs)`, by primary key (`AllObj`: type, id; `Field`: TableNo, No., or TableNo and FieldName). At most 200 items; one row per item
  read, in order, the target's own rows included; `read` says how many were read before `MaxMs` ran out. `outcome` is `owner`,
  `none` or `unresolved`; an owner row carries `appId`, `appName`, `appPublisher`, `appVersion` (the client needs all four to read
  that app's package; the plan named only the id). A field row carries `fieldName` and `tableName` as BC holds them. An explicit `case`
  maps the 13 kinds (`Table` is never `TableData`, `XmlPort` is `XMLport`); an unknown kind raises. `Permissions` declares both tables.
  Compiled offline with alc 18.1.43 (clean, no diagnostics): the symbols were `Microsoft_System_28.0`, System Application,
  Application, Base Application and Business Foundation 28.1 from `/work/tools/r315-dc-symbols/Cloud/.alpackages`, and a Test Runner
  built with alc from the cached 28.4 source zip, in a scratch folder (nothing written under the repo).
- `packages/runner/src/harness.ts`: `HarnessVerifier.fetchObjectOwners` and `fetchFieldOwners`, as strict as `fetchInstalledDependents`:
  a bad `read`, a row count other than `read`, a row that is not the item at its place, an unknown outcome, or an owner with no
  full app all throw `HarnessVerificationError`. Fewer rows than items is a partial read, returned as such. The client timeout is the
  time left.
- `ExecutionBackend` gets optional `installedVersions`, `objectOwners`, `fieldOwners`, implemented on bcdev only.
- `packages/runner/src/non-dependent-clash.ts` (new, pure): what is new in the target (`newObjects`, `newTableFields`), one control per
  kind (`controlObjects`), and the batched read with the 10 s deadline (`readInBatches`).
- `packages/runner/src/object-clash.ts`: `findNonDependentLeads` (skip on a first publish; base set from the INSTALLED version's
  package; new-only items; offline third-app table ids by `resolveTableIds`; blind-kind controls; leads), run in `checkObjectClashes`
  BEFORE its early returns. A lead is read from its own package and compared as a dependent is; that comparison alone refuses. A
  dependent that was not actually compared is read as a lead. `ObjectClashError` says the app is "not known to be a dependent" and to
  remove the clash in the target or in that app. `orchestrator.ts` passes the reads in for bcdev.
- Tests: `r847-owners-verifier.test.ts`, `r847-non-dependent.test.ts`, the R847 block of `object-clash-session.test.ts` (zero deploys by
  call counter) and the source pins in `control-app-source.test.ts`. Each was reddened by a real mutation (see the coord report).

## Part 2, step 1 (2026-11-06): probe measured, control 1.0.0.25 built

Probe on bc1 (scratch pair T and unrelated X, both extending Customer; logs in `/coord/handoff/R-847/probe/`). The item stays open
until the servers run 1.0.0.25 and the gates and proof table are redone.

**Measured.**

- Cost: a keyed read is cheap. `AllObj` by key at N=1, 10, 100, 1000: median server time 0 to 21 ms, total round trip about the
  ping (about 82 ms median) with no per-read cost above it; one 1000-item `AllObjWithCaption` run showed 533 ms server time, the
  other two 15 to 18 ms. `Field` by key: 13 to 18 ms at N=1000.
- Kinds: `AllObj` has a row, with the owner app, for all 13 kinds (Table, Codeunit, Page, Report, Query, XMLport, Enum,
  EnumExtension, PermissionSet, PermissionSetExtension, TableExtension, PageExtension, ReportExtension). The join from the row's
  `App Package ID` to the app works for a dev-published app.
- Fields: `Field` names a tableextension field's own app, not the table's (Customer 91591 and 91592 came back owned by T and X;
  Customer 2 by Base Application). The control for the field read therefore holds.
- `SetRange(FieldName)` IS case sensitive: `NAME` and `name` found nothing for Customer `Name`. The AL comment that said otherwise
  is fixed, and the client keeps its exact compare.
- A name item matching more than one row can therefore not arise from case. The `unresolved` path stays as a guard: an unexpected
  second row is a warning, never a guess at which is the owner.
- A published-but-not-installed app is invisible to both tables (0 rows for its objects and its field). That is the plan's
  "remaining assumption", now measured: such an app is not seen until installed.
- A permission set's `AllObj` name came back upper-cased ("R847 PROBE X PS"). No comparison depends on it: `ObjectOwners` answers
  owner, kind and id only, and the client matches by kind and id, never by `AllObj`'s name.
- `AllObjWithCaption` is not used: `AllObj` plus the package join answers everything the check needs.

**Done on the branch.** Control app 1.0.0.25 (`app.json`), `MIN_CONTROL_VERSION` 1.0.0.25, the `harness.test.ts` literals and a
new refusal test for 1.0.0.24, `docs/gates/README.md`, the agent guide's "or newer" line, `CONTROL_APP` and `CONTROL_SHA256` in
`scripts/bc-linux-setup.ts` (shared by `bc-demo-setup.ts`), `scripts/testdata/bc-demo-kraken-pin.json`. Built clean with offline
alc 18.1.43 into `/coord/handoff/R-847/control/`.

## Part 2, step 2 (2026-11-06): published and proven

Control 1.0.0.25 is on `bc1`-`bc4` and `bc-demo`, each read back at the pinned sha256. All 13 non-hang gates passed on `bc1`, `bc2`, `bc3` and `bc4` (BC 29), and `itest:hang` on `bc2` and
`bc3`, with no differing figure. Proof: `docs/gates/servers.md`; `bc4`'s logs are under `/coord/handoff/R-826b/bc4/`.

**One live read through the real client.** `fetchObjectOwners` and `fetchFieldOwners` against the published app on `bc1` and `bc4`: four objects in 39-72 ms, four fields in 81-101 ms, under a lease, with
owners, `none` rows and a case-different field name (`none`) as expected. Output: `/coord/handoff/R-847/owner-read/result.txt`.

**The Continia stack, read live on `bc3`.** The objects each of the 5 Continia packages declares (up to 200 an app, so 479 of 856), asked through the real client, one lease, nothing published: 477 name the right
Continia app, 2 read `none`, and each batch took 92-367 ms. This is what a clash would be measured against: a new target object at one of those ids reads as owned by that app, and that app's package is then read and
compared. Output: `/coord/handoff/R-847/owner-read/bc3-continia.txt`.

**A limit that read found.** The 2 `none` rows are tables with `ObsoleteState = Removed` in the package: `AllObj` has no row for them. So a removed table in another app is invisible to this check. What BC does with a
new target table at such an id is not measured; a miss lands where it lands today, at `UpgradeClashRefusedError`. The same run's first read asked for Continia Document Capture ids, and all read `none`: that app is not on `bc3`.

**Open: the one line that keeps this item open.** The gates cannot see this check: their target is already minted, so nothing is new and no control call is made. So no live run has gone from a real clash to a
refusal through the new path; only its parts are covered, by the unit tests, the probe and the live reads above. It needs a scratch app on a leased server.
