Filed 2026-11-16 by lethal-code, from a wait the orchestrator spotted (PR-67).

**What happened.** PR-67's scoped DO run (one codeunit, one test codeunit, al-runner-v3) was queued with
`scripts/heavy-slot.sh --wait --peak 12 baseapp`. Twelve GiB was copied from the full DO runs of R-984. The run waited 54
minutes. Used memory was about 10 of 32 GiB the whole time, but the declared peaks of the held slots were 28 GiB, so
`held + 12 + 4 reserve > 32` refused it on every try. The ledger already had the answer. `heavy-peaks.tsv` (written by
`cleanup` in heavy-slot.sh since R992) showed short DO v3 runs that measured 3.2 to 3.9 GiB against a declared 12. Only one
3.5-hour full run reached 9.3. The R-926 serve legs that held two of the slots at a declared 8 GiB peak, as the orchestrator
read them, under 2.

**The gap.** heavy-slot.sh records each job's declared and measured peak, but it never reads them back. A job declared far
too high blocks other jobs for as long as it waits and for as long as it runs. Nothing tells the person who declared it.

**What to build** (small, advisory only, never a refusal):
- When a job is admitted or queued, look up recent ledger rows for the same command shape. A first cut of the shape: the
  class, the program (`bun ... cli.ts run`, `bun run itest:...`) and the `--project` value.
- If the job's declared peak is more than twice the largest measured peak in those rows, and there are at least 3 of them,
  print one line to stderr. The line names the declared peak, the measured largest and how many rows, and says what peak
  to declare instead (the measured largest plus a margin). Name the rows' dates so a stale ledger is visible.
- Unit tests stay off `/coord`: the ledger path comes from the lock dir the tests already set.

**Not in scope:** changing the admission rule itself. Admitting by the measured peak instead of the declared one would be a
policy change for the owner (the declared peak is the job's promise, measured over its whole life).
