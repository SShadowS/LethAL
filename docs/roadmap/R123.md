**The canary measures the wrong thing now.** `al-runner-canary.ts` runs two probes per
`--backend al-runner` session: R7 (`asserterror` guarding a non-raising statement reports `pass`)
and R8 (a table object's global does not survive a trigger's write). Its design was right — measure
the build in use rather than trust a code comment — and it has now been vindicated in the least
useful way: v2 FIXES both, so on any current install it reports `defect-not-reproduced` twice and
tells a reader nothing about the binary that is about to produce their verdicts.

**Meanwhile the thing that does move is unmeasured, and it moves fast.** al-runner publishes several
times a day. During the R93 port, in one session: **2.0.0** was the released binary when the work
started, **2.0.1** published before it finished, and 2.0.1 changed the runner-enforced timeout
message BACK to v1's `Test exceeded <n>s timeout.` from 2.0.0's `TIMEOUT after <n>s`, keeping
`status: "error"`. Under the decode as first written — anything not `pass` and not matching the
regex is `fail` — that single string turned every hung mutant into a KILL. Silently, and invisible
in aggregate counts.

What stopped it was not a better regex. It was making the unclassified case **fail closed**: an
`error` this build cannot positively classify scores `error` (not measured) rather than falling
through to `fail`. That is a property, not a guess about wording, and it is the shape the probe
should generalise.

**What the probe must measure, once per session, refusing loudly on anything unrecognised:**

- the binary's own `--version` (already stamped by `itest:alrunner`, not yet by a normal run);
- the qualified test-name shape — `CodeunitNNNN.Method` today;
- the runner-enforced timeout: which `status` and which message text, by actually timing one out;
- exit codes for a compile failure, an execution failure, and an unknown flag;
- whether `--output-json` stdout carries a banner (2.0.0 did; 2.0.1 did not on the paths measured);
- whether `AL_RUNNER_TEST_TIMEOUT_SEC` is still honoured;
- whether the server protocol honours a second `sourcePaths` entry (R97, upstream #1658);
- R7 and R8, kept — a machine with an older binary on its PATH still deserves the warning.

Each of those has a measured "today" value in `docs/measurements/README.md` §"al-runner v2 — the CLI
and wire contract", so the probe has a baseline to compare against on its first run rather than
having to be told one.

**Operational note the user asked for, 2026-08-07: re-check for an al-runner release roughly every
12 hours while any al-runner work is in flight.** `dotnet package search MSDyn365BC.AL.Runner
--exact-match` lists published versions; `dotnet tool update --global MSDyn365BC.AL.Runner --version
<v>` moves the installed one in either direction. Until this probe exists, that check is a human
habit, which is exactly the kind of thing this project does not rely on elsewhere — the whole point
of the row is to replace it with a measurement.

Evidence: R93 (closed), R94 (the wording change), `docs/measurements/README.md`. Filed 2026-08-07
when R93 shipped the decode without the probe it asked for.

**CLOSED 2026-08-07.** `packages/runner/src/al-runner-contract.ts` measures five facts once per
`--backend al-runner` session and REFUSES the session on any divergence — version, unknown-flag
rejection, qualified test-name shape, timeout classification, and "a compile failure must not be
scorable". It spawns al-runner directly rather than through `OneShotTransport` (a probe routed
through the transport cannot see an exit code the transport already collapsed), but through the
SAME `buildAlRunnerArgv`/`alRunnerEnv` the transport uses, so it cannot bless a command line nobody
runs. `unmeasurable` refuses too: "we could not confirm the contract" is not "the contract holds",
and the canary's deliberate demote-to-warning is right for a defect canary and wrong here.

**Two things the row did not anticipate, both found by running the probe against the real binary
rather than by reasoning about it:**

- **The compile-failure fact was wrong as first written.** It pinned `exit 3`, taken from an
  invocation where every bundle was broken. A real run has a target that fails to compile beside a
  test bundle that compiles, and al-runner answers THAT with exit 1 and empty stdout. Exit 1 is
  inside the range the decode reads verdicts from, so the check was pinning a case that never
  happens and missing the one that does. It is now stated as a property — "must not yield a readable
  envelope naming the requested test" — which is version-proof in a way an exit code is not.
- **Passing the same bundle dir twice crashes al-runner** with an unhandled `ArgumentException` out
  of its own report serialiser. That is R124, and it is the reason the probe's compile case sends a
  broken target beside the real test bundle instead of the same dir twice.

The row asked for the server-protocol fact (R97) as well. It is NOT measured: `serverMode` now
throws outright, so there is no configuration in which that path can run, and probing something the
adapter refuses to use would measure nothing anyone can act on. Re-add it if #1658 lands and server
mode is re-enabled.

The row also asked for R7/R8 to be kept. They are — `runAlRunnerCanary` is untouched and still runs,
after the contract probe rather than before it, because a moved contract makes the canary's own
reading of the binary untrustworthy too.
