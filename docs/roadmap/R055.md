**The baseline and the mutants are measured on DIFFERENT RUNNERS, and a test that fails on the baseline's runner silently converts real survivors into `no-coverage`.** The entry first said "coverage collection makes tests fail" — **measured 2026-07-27 and that framing was wrong.** `BcDevMcpBackend` routes by mode (`bcdev-backend.ts`, `status()`'s own doc comment): with `coverageMode: "procedure"` (the DEFAULT) the BASELINE goes through the bc-dev-mcp hub, while every MUTANT goes through the fenced `RunMutant` OData action; with `"none"` both go through `RunMutant`. So the default path establishes the green set on one runner and produces every verdict on another. **A/B, back-to-back on one environment, same 56 tests, same source, only the mode differing, run in BOTH ORDERS:** `none` first -> GREEN 0/56 then `procedure` -> RED 12/56; and `procedure` FIRST -> RED 12/56 then `none` -> GREEN 0/56. Order-independent. (The first pass ran `none` first and the entry claimed that excluded elapsed state — it did not: it excluded drift FAVOURING the `none` arm, not state left BY it. An external review caught the overstatement and the reversed order was run to close it.) The failures are a property of the HUB path, not of coverage collection perturbing anything, and not of drift. Failure texts are ordinary (`Assert.IsTrue failed ...`, `Unhandled UI: Confirm ... has not been activated`), including on PURE-LOGIC tests with no database involvement. **Consequence chain, each step measured:** a test fails on the hub -> it leaves the green set -> its coverage observation leaves with it -> mutants in the procedure it covered fall to `no-coverage`. All **14** such mutants on Document Output sit in `CreateOrSendAutStatements`, and **9 of the 12** baseline failures are the Statement/AutStat tests that cover it. Plus **21** mutants reported `error` for want of a green covering test. Direction is safe — verdicts always come from the fenced path, which passes these tests (R37 confirms no false survivor) — so the damage is confined to WHICH mutants get scored, not to what a scored mutant says. **Fix — NOT yet implemented, and the obvious version is not good enough.** The candidate was: re-check a baseline failure on the fenced runner before dropping it from the green set. An external review (Fable 5, 2026-07-27) found three problems, two confirmed against the code: (a) **truncated coverage** — the observation being preserved comes from the FAILED hub run, which stopped at the failure point, so a test that dies at the activation Confirm BEFORE reaching `CreateOrSendAutStatements` never credits it and the 14 stay `no-coverage`; the fix would not deliver its own motivation, and this is unmeasured. (b) **plumbing** — it makes the baseline take the fenced path under `coverage: "procedure"`, and `orchestrator.ts` (~line 1982) states in terms that a call site without `resyncOpSeq` is "safe only while the backend reports `coverage: "procedure"` (the baseline then never takes the fenced RunMutant path)"; it also needs `pendingMutantId` proven null, and `baselineDuration` must take the FENCED timing since the mutant budget is `2 x baseline` and the runners differ by ~20x. (c) **its own verification would pass for the wrong reason** — "a no-op wherever the baseline is already green" means all four frozen gates pass whether the fix works, is inverted, or is deleted, so any red-check needs a fake whose two runners DISAGREE. See R57 (root cause), R58 (the real fix), R59 (the unsafe direction this leaves open).
