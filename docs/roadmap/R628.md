**Filed 2026-10-22 by coord task R-572** (lethal-code), on the orchestrator's ruling after the R-572 re-price r2
(`/coord/handoff/R-572/reprice-r2/shpfy-classification.md`). An OVER-refusal, measured; no hang is deployed.

**What.** [[R572]]'s value-path slice is by NAME: it carries a same-object callee's globals into the chain
procedure's path at every depth. In BC.History's Shopify Connector, 31 paging loops call
`Shpfy Communication Mgt.ExecuteGraphQL`; two or more calls below it, the request is built from the global shop
record (URL and access token). So the shop joins the path, every procedure that writes it at record level is a
writer, and the fixpoint adds their globals: 87 keys in ExecuteWebRequest (46), CreateHttpRequestMessage (18),
CheckOutgoingRequests (12), SetShop (7) and GetContent (4) are refused. A sample of 14 across all five is 0 real:
each mutant either sends the same request or makes it fail, which raises `Error` and ends the loop; the page
cursor lives in the caller and none of these procedures write it.

**Why it is not simply narrowed.** A by-name slice cannot tell "a deep global only addresses the request" from
"a deep global feeds the loop's exit". Carrying callee globals one level only removes these 87 but ADMITS a real
hang: the chain reads the exit's state through two same-object calls and the loop body writes it (unit test 37b
in `packages/builtin-tier1/tests/r572-flag-fed.test.ts`, red under the one-level carry). Test 36 pins the
over-refusal in its current direction.

**Price.** 87 keys in BC.History (Shopify Connector); none in DC, DO, CDO or the fixtures (their guard-off parts
were identical with and without the deep carry).

**To close.** A precision rule that keeps probe 37b refused, for example separating values that reach the result
only through an opaque built-in boundary (an HTTP send, a server response) from values that reach it through AL
assignments; or a ruling that the over-refusal stays.
