Found by coord R-893, compiling BC.History BaseApp offline. Related: [[R893]] (the measurement), [[R883]].

**What.** alc resolves a `dotnet { assembly(...) }` declaration, and every DotNet type a dependency's symbols declare, only through `/assemblyprobingpaths:<dir>[,<dir>...]`. LethAL builds its alc command line in `ArtifactCompiler` (`packages/runner/src/artifact.ts`) with `/project`, `/packagecachepath` and `/out`, and never with probing paths. The CLI, config and scripts have no field for them either. So any project that uses DotNet, which is common on-prem, compiles in the user's VS Code but fails in every LethAL batch. Each missing type gives an AL0451 ("An assembly named 'X' could not be found in the assembly probing paths") and an AL0185 (`DotNet 'X' is missing`).

**Measured.** BaseApp 28.6 without probing paths: 787 errors, 726 of them AL0185. With the BC 28.4 service folder and .NET 8 as probing paths: 1 error, a 28.1-against-28.6 skew.

**Where the user's setting lives.** VS Code's AL extension reads `al.assemblyProbingPaths`, an array of folders, from the workspace's `.vscode/settings.json`, or from the user or workspace-file settings. Its default is `["./.netpackages"]`, relative to the project folder. A typical on-prem value names the service tier's folder, for example `C:\\Program Files\\Microsoft Dynamics 365 Business Central\\280\\Service`, plus `C:\\Windows\\Microsoft.NET\\assembly`.

**To build.**
1. A LethAL config field: `bcdev.assemblyProbingPaths`, or top-level, since al-runner-v3 compiles too. Paths are relative to the project.
2. When the field is absent, fall back to the project's `.vscode/settings.json` `al.assemblyProbingPaths`, the way `launch.json` already supplies defaults. If that is absent too, use `./.netpackages` when it exists.
3. Pass them as one comma-separated `/assemblyprobingpaths:` argument on every alc call: batches, bisection, compile-only and the test-app build.
4. Name the paths in an AL0451 failure, so the fix is obvious.
5. Tests: an invented project with a `dotnet` declaration fails with AL0451 without the field and compiles with it, pointing at a folder holding a small built assembly.

**Notes from R-893.**
- A folder copied from a Linux BC service tier holds some assemblies renamed to `*.dll.orig` (`System.Drawing.Common`, `Microsoft.Data.SqlClient` and two more). alc does not load those, so the user must point at a folder with the real names.
- Mixing .NET runtime folders (8.0 and 10.0) gave generic-type conversion errors (AL0133, AL0122) in System Application. One runtime version per run is safer.
- **Corrected 2026-11-11 (R-927): the cause of the AL0133/AL0122 errors is the Linux service folder's assemblies, not mixing
  runtimes; the bullet above is withdrawn.** The folder used
  here and in R-898/R-903 (`/coord/cache/bc28-service`, copied from a Linux BC 28.4 service tier) is the wrong one for alc. The
  owner measured it on Windows alc: with that folder, the same AL0133/AL0122 counts; with a Windows BC 28.4 service folder
  (`/coord/cache/bc28-service-windows`) as the only probing path, all 8 System Application modules that hit them build with 0
  errors. Use a Windows service folder's assemblies, also with the Linux alc. `scripts/r900-probing-probe.ts` defaults to it now.

**Built (coord task R-897).** A top-level config field `assemblyProbingPaths` (like `preprocessorSymbols`). When it is absent,
LethAL falls back to the project's `.vscode/settings.json` `al.assemblyProbingPaths` (JSON with comments), then to `./.netpackages`
if that folder exists, then to none (the argv is then unchanged: every fixture resolves to none). Relative entries resolve against the
project. One `/assemblyprobingpaths:` argument is passed on every alc call through `ArtifactCompiler`: batches, bisection, the test
app, v3's compiles and `compile-only`.
- **Refused by name:** a missing path or a file (`AssemblyProbingPathMissingError`), and a path containing `,` or `;`. Measured: alc
  splits the list on both characters.
- **AL0451:** the error gets a LethAL note naming the paths passed and where LethAL reads them.
- **Visibility:** the list is in the resume fingerprint (only when non-empty) and in the v3 test-app cache key. `doctor` shows the list
  and its source, and a run prints them.
- **Resolved once, before anything is provisioned:** next to `validateIds`, so a missing path refuses before an envtool environment
  exists (R3's order).
- **A malformed `.vscode/settings.json`:** refused by name only when its text mentions `assemblyProbingPaths`. Otherwise LethAL
  warns once naming the file and moves on to `./.netpackages`, so a project that never used probing paths is not stopped.
- **Not wired, by design:**
  - al-runner's runtime `--dotnet-assembly-dir` is a separate knob.
  - The TEST project's own `.vscode/settings.json` and `.netpackages` are not read: the test app gets the target project's resolved
    list. A test app with DotNet declarations of its own would need them in the target's list or in the LethAL config.
- **One visible change with no paths:** an AL0451 error now ends with LethAL's note ("passed alc no assembly probing paths ..."). The
  argv, the fingerprint and the cache keys are byte-identical.

**Proven.**
- An invented project (`scripts/r900-probing-probe.ts`) fails with AL0451 and AL0185 without the paths. It compiles with them, taken
  from the config or from `.vscode/settings.json`.
- BaseApp 28.6's control build through LethAL's own compiler (`/coord/handoff/R-897/baseapp-control.log`):
  - without: 787 errors (726 AL0185, 3 AL0451), with LethAL's note;
  - with R-893's four folders from the config: 1 error, R-893's AL0280 28.1-against-28.6 skew. That is exactly R-893's hand-run alc
    result.
