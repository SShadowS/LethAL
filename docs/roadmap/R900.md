Found by coord R-893, compiling BC.History BaseApp offline. Related: [[R893]] (the measurement), [[R883]].

**What.** alc resolves a `dotnet { assembly(...) }` declaration, and every DotNet type a dependency's symbols declare, only through `/assemblyprobingpaths:<dir>[,<dir>...]`. LethAL builds its alc command line in `ArtifactCompiler` (`packages/runner/src/artifact.ts`) with `/project`, `/packagecachepath` and `/out`, and never with probing paths. The CLI, config and scripts have no field for them either. So any project that uses DotNet, which is common on-prem, compiles in the user's VS Code but fails in every LethAL batch. Each missing type gives an AL0451 ("An assembly named 'X' could not be found in the assembly probing paths") and an AL0185 (`DotNet 'X' is missing`).

**Measured.** BaseApp 28.6 without probing paths: 787 errors, 726 of them AL0185. With the BC 28.4 service folder and .NET 8 as probing paths: 1 error, a 28.1-against-28.6 skew.

**Where the user's setting lives.** VS Code's AL extension reads `al.assemblyProbingPaths`, an array of folders, from the workspace's `.vscode/settings.json`, or from the user or workspace-file settings. Its default is `["./.netpackages"]`, relative to the project folder. A typical on-prem value names the service tier's folder, for example `C:\\Program Files\\Microsoft Dynamics 365 Business Central\\280\\Service`, plus `C:\\Windows\\Microsoft.NET\\assembly`.

**To build.**
1. A LethAL config field: `bcdev.assemblyProbingPaths`, or top-level, since al-runner-v3 compiles too. Paths are relative to the project.
2. When the field is absent, fall back to the project's `.vscode/settings.json` `al.assemblyProbingPaths`, the way `launch.json` already supplies defaults. If that is absent too, use `./.netpackages` when it exists.
3. Pass them as one comma-separated `/assemblyprobingpaths:` argument on every alc call: batches, bisection, compile-only and the test-app build.
4. Name the paths in an AL0451 failure, so the fix is obvious.
5. Tests: an invented project with a `dotnet` declaration fails with AL0451 without the field and compiles with it, pointing at a folder holding a small built assembly.

**Notes from R-893.**
- A folder copied from a Linux BC service tier holds some assemblies renamed to `*.dll.orig` (`System.Drawing.Common`, `Microsoft.Data.SqlClient` and two more). alc does not load those, so the user must point at a folder with the real names.
- Mixing .NET runtime folders (8.0 and 10.0) gave generic-type conversion errors (AL0133, AL0122) in System Application. One runtime version per run is safer.
