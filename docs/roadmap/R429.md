**Found by the R-405 part (a) work (lethal-preproc), 2026-10-04.** Source: R378's plan `docs/superpowers/plans/2026-10-02-R-378-member-wide-inactive-arms.md` §1 B5 lists `TypeTable` among the project-wide indexes that read `#if` declarations without arms.

**What is known.** R-405 part (a) made the symbol table, the table-trigger readers and the receiver filter arm-aware (`liveMembers`, R405). It did NOT change `TypeTable`.

**What is NOT known.** Nobody has measured it. It is not known whether `buildTypeTable` sees declarations inside a member-level `#if` at all, or sees them from the arm the build does not compile. If it does, a variable or procedure type could resolve from an inactive arm, so a site could be refused or mis-typed. No wrong verdict has been seen from it.

**What would close it.** Measure first: build a project with a variable or a field declared inside a member-level `#if X` / `#else`, and read what `buildTypeTable` holds under `[]` and `[X]`. If it reads an inactive arm or drops an active one, filter its members by arm the way R405 (a) does with `liveMembers`. Then diff the keys: a newly admitted mutant can move an identity ordinal (see the scheme 8 note in `packages/schemata/src/project.ts`), so a change needs the key diff over the gate projects and possibly another `IDENTITY_SCHEME` bump.

**Closed 2026-10-04 as a ruling: no defect** (R-429 measurement, `/coord/handoff/R-429/measurement.md`, branch at master 1e010ed6).
- `buildTypeTable` (in `packages/engine/src/semantic/types.ts`) keeps no index of its own: `typeOf` computes every type from the `SymbolTable`, which `buildSemanticContext` (in `context.ts`) builds with the raw arm map. So a member-level `#if` is read by R405 (a)'s `liveMembers` rules:
  - an active arm's procedures and `var` sections are typed;
  - an inactive arm's are absent;
  - an undecided file and a run with no map give `null`.
- Only two callers use the answer, `swap-call-arguments` (same-type check) and `swap-additive` (numeric check). For both, `null` refuses the site (safe), and a WRONG type would emit AL that alc rejects (unsafe).
- **Synthetic shapes**, measured under no map, `[]`, `[X]` and undecided: a `var` declaring `V: Integer` in one arm and `V: Text` in the other types `V` as the active arm's type; `F(): Integer` / `F(): Text` follow the arm the same way; a name only in the inactive arm is untyped. alc 18.0.41 compiles the shapes project under `[]` and `["X"]`.
- **Oracle check**: blank each file's inactive arms (the text alc compiles) and compare the type of every identifier, field access and call in active code. Over 71 project-by-symbol-set runs (every fixture/example under its gate sets, every r214/r364 unit fixture under `[]` and each symbol its directives name): **0 wrong types, 0 undecided files**, and 6 sites lost, all at positions the type table never types.
- **Real generation path** (`r214-capture` on the shapes project): the two extra mutants under `[X]` are `swap-call-arguments` sites typed Integer only in that build and correctly refused under `[]`. No mutant used an inactive arm's type.
- Nothing to fix, so no keys move and no scheme change.
- The positions the type table never types (a `#if` in a global var body, around locals or parameters, around fields, a split header whose arms disagree) lose mutants only. They are filed as R432; an object wrapped whole in `#if` stays R343.
