Coord task R-972, from preproc's R-969 (Contoso Coffee Demo Dataset peaked at 18.3 GB, `/coord/handoff/R-969/contosocoffeed.rss.tsv`).
Related: [[R948]] (the daemon recycle bound), [[R953]] / [[R972]] (admission by memory).

**Which process, and why R948 did not catch it.** Re-run with every process of the tree sampled every 2 s
(`/coord/handoff/R-972/measure.sh`, `base.procs.tsv`; edge-c8fe56e05, the same source, tests and config): LethAL's own process stayed
at 0.5 GB; the one al-runner serve daemon grew from 1.6 GB to 21.2 GB inside single prefetch requests of 256 entries (about 0.6 GB a
second) and fell back after each. R948's recycle reads the daemon's RSS between requests, after it fell, so it never fired.

**What drives it (measured).** 64 entries per request instead of 256 (`cap64.*`): daemon peak 6.3 GB, all 20,790 verdicts and killing
tests identical: about 77 MB an entry over a 1.35 GB floor. NOT the app's size: the same run restricted with `--only` to the 21 files
holding its covered mutants (604 deployed instead of 20,790, `only604.*`) peaked at 21.0 GB with the same requests. Invented apps do not
reproduce it (`repro/`: 20,000 procedures, or a test inserting 20,000 rows, stay under 330 MB at 256 entries), so it rests on what
Contoso's demo-data tests do, and no upstream issue is filed until an invented repro shows it.

**The cause, found on R-980 (offline, edge-736fc7677): the app's RESOURCE FILES, not its tests.** Driving `al-runner serve`
directly with the raw Contoso app and test app: entries that each give one resource its own value (as LethAL's mutant selections do)
grow the daemon by about 68 MB an entry, held to the end of the request; identical entries with no resource replaced stay flat. All
three test codeunits grow the same, and demo data on or off makes no difference. Contoso's `.resources` folder holds 38 MB (171
images, documents and XML files); with it removed from `resourceFolders`, 32 entries stay at about 800 MB. An invented app (one
codeunit, one test, a 4-byte `switch.txt` the entries replace and an inert filler resource no code reads) reproduces it: a 40 MB
filler costs about 85 MB an entry (one 64-entry request on a fresh daemon: 5.6 GB), a 10 MB filler about 19 MB, no filler or
`"resources": {}` stays under 350 MB; a second request reuses the memory. R-972's repro missed it because its apps had no resource
but the replaced one. Filed upstream: https://github.com/aldevtools/BusinessCentral.AL.Runner/issues/8026. Drivers and the
generator: `/coord/handoff/R-980/`. This build's per-request sizing stays as it is: it measures the cost, whatever its cause.

**Built: measure each codeunit, and send the unmeasured 16 at a time.** While each serve request runs, the daemon's RSS is read every
200 ms (seam `requestRssReader`). A request that did not grow the daemon while the daemon holds 512 MiB or more over its floor may have
reused memory an earlier request left: it says nothing (its calls keep their state). Every other request is a reading, a daemon near
its floor that did not grow included (a cost of about 0: the gate fixtures' requests often grow it by 0 bytes, and treating that as
"unknown" kept them at 16 unmeasured entries, which split MOE's 7 kill pairs on a gate run). A test entry costs (peak - the daemon's floor, the lowest start seen) /
the request's test entries (echoes not counted: `groupsThatFit` charges test entries only), charged to every call the request ran, each
call keeping its highest (never an average, never falling). Read from the start instead of the floor, a daemon that keeps memory reads
low; divided over every entry, one-codeunit groups read half: both were measured on Contoso (65 and 64 MiB read, trees 10.1 and 9.2
GiB) and fixed, each with a red-checked test. The next request
takes groups in order while it stays within 256 entries, 16 entries of calls no request has measured, and 4 GiB of measured cost
(`groupsThatFit`, `al-runner-v3-entries.ts`); the first group is always taken. So a heavy codeunit met late, after cheap ones, still goes
16 at a time until it is measured (a review found that a session-wide slow start would not). The prefetch and R778's kill-pair batches
(a kill sized as its two real groups, NONE and M, never split) cut each chunk when it is sent; R912's batch-refusal judgement stays on a fixed
256-entry chunk, so it never depends on a reading. A lowered size is announced once (`al-runner-v3-entries-cap-lowered`). No RSS reader
(no `/proc`): unmeasured forever, so 16 codeunit entries a request. Tests inject the readings: high and low readings, a heavy codeunit
after cheap ones, memory reused (no reading) and memory kept (read from the floor), a no-growth request near the floor (cheap), a peak
given back before the request ends (only the sampler sees it), the kill-pair batches, a small request judged in its 256-entry chunk;
each red-checked.

**Measured on the build** (`final4.*` against `master.*`: the same Contoso run on this branch at 94b89dc6, admitted at `--peak serve`,
and on master 0a6b7516 at 256 entries a request, which has R975, so both read its 11 page `OnAction` mutants no-coverage): cost 96 MiB
a test entry, about 42 test entries a request; daemon peak 5.67 GiB, whole tree 6.25 GiB (master: daemon 20.4, tree 20.8 GiB); all
20,790 verdicts and killing tests identical to master's; session 82 s (master 156 s).

**Not changed.** Admission's `--peak serve` stays 8, and R948's between-request bound. A single mutant group larger than the limits still
goes alone (one echo, every covering codeunit): a widely covered mutant can still make one large request. DO's daemon BASELINE (one
codeunit a request) is a different holder: LethAL's own process (see its own item).
