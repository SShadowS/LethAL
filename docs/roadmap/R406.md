**Seen 2026-10-02 by the orchestrator**, running `bun scripts/verify.ts` on the R-378 merge
(b4ad8a0a) while three lanes ran corpus captures and live gates. One test failed:
`scripts/snapshot-late-write.test.ts`, "R393 late snapshot write > (b) control, CI unset: the
wrong entry IS written under B's key". The marker read:

    A late call reached; CI=undefined
    A late toMatchSnapshot THREW: Snapshot matchers are not supported in concurrent tests

The control expects "A late toMatchSnapshot returned OK". Run alone, the file passed 3 of 3 times
straight after. So the late call from test A depends on timing: under load it can land while bun
treats the run as concurrent, and bun then refuses the snapshot matcher outright instead of
writing under B's key. The guard (case a) was not affected; only the control that shows the
defect exists can fail.

**To close.** Make the control independent of timing: for example, hold test B open on a promise
that A's late call releases, so A's write always lands inside B. Or accept either "returned OK
and wrote under B" or this named refusal as the control's outcome, stating why. Red-check that the
control still fails when the late write cannot happen.

**Closed 2026-10-02 (63677f0a), by the lethal-preproc lane.**
- **The cause.** Test B slept 700 ms under the same 200 ms `--timeout`, so B timed out ITSELF at about 400 ms, the moment A's late call fired at 400 ms. When B's timeout won, no test was current, and bun refused the matcher as "concurrent". When B's timeout came later than A's call, the write landed in B. When it came earlier still, the process exited before A's call.
- **Reproduced on demand** with a scratch copy of the fixture whose A sleep is a parameter, CI unset: at 411 to 414 ms, 2 of 10 runs threw `Snapshot matchers are not supported in concurrent tests`. At 414 ms and above, the process usually exited first, with no marker.
- **The fix, in the fixture only** (`scripts/fixtures/r393/late-write.fixture.ts`). B has its own 10 s timeout and waits on a promise that A's late call resolves in a `finally`, capped at 5 s. A sleeps 1000 ms. The late write always lands while B is the running test. The control's assertions are unchanged: nothing was widened, and `scripts/snapshot-late-write.test.ts` is not edited, so guard case (a) is unchanged too.
- **Measured.**
  - The fixed structure with A's late call at 400, 411 to 414, 420, 600 and 1500 ms: every run wrote under B's key.
- **Red-checks.**
  - A sleeping 50 ms, inside its timeout, so no late write can happen: all three cases fail.
  - B without its own timeout: all three cases fail, 3 of 3 runs. At 1000 ms that is deterministic, not a reopened race.
- **Under load.** The test file was run 20 times while `bun scripts/verify.ts` ran in parallel: 20 pass, 0 fail. The parallel verify passed too, 5295 / 7 / 0.
