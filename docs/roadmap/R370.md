**Found by R-214's pre-commitment (2026-09-30, ruling T1-f).** Some code wraps only PART of a
construct in `#if not CLEAN27`: a member's only header, a case label, or a call's first line.
Under `CLEAN27` the text that remains is not valid AL. alc rejects it (measured with an invented
probe of the same shape: `AL0496`, `AL0104`, `AL0198`). R-214's enumeration still keeps the sites
that start in active text, so a run under that set would plant mutants in a build that cannot
compile.

**Rule** (R-214's presence check): a file whose full twin (every directive and inactive line
blanked) has more ERROR/MISSING parse nodes than the original. It is excluded per file from the
presence join, stays in the byte-exact expected capture, and is counted.

**Measured.** dc.1 (`CLEAN27, CLEAN28`): 5 of 88 directive files,
`.dependencies/DC/Codeunit/CDCContiniaConfigMgt.Codeunit.al`, `.dependencies/DC/Codeunit/CDCPurchApprovalEMail.Codeunit.al`,
`.dependencies/DC/Page/CDCReqAppvlReasonCmt.Page.al`, `Modules/Approvals/Codeunits/CDCApprovalForwardSubscr.Codeunit.al`,
`Modules/Approvals/Codeunits/CDCApprovalManagement.Codeunit.al`. Every other corpus and set: 0.

**Out of R-214's scope.** Detecting an invalid build is a different check from choosing arms. A
product fix could refuse such a file by name (like `preproc-undecided`), or report the set as not
buildable before any run.

**Closed 2026-10-05 as a ruling: not found outside DC.** The R-364 census
(`/coord/handoff/R-364/measurement.md`, per `app.json` project: BaseApp's 203, CDO at 5f2a71d,
fixtures and examples, under `[]` and under each project's own symbols) found 0 unbuildable files in
every corpus and set. R-214's 5 files were in DC under `CLEAN27, CLEAN28`, which this census did
not measure. Reopen if a real run is asked for under a set that leaves a file unbuildable.
