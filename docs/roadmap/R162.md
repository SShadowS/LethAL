Replace a qualified enum or option value with a sibling member of the same declared type.

```al
SalesLine.Status := SalesLine.Status::Released;   // before
SalesLine.Status := SalesLine.Status::Open;       // after
```

**What weak test it catches.** A state-machine test that asserts the operation ran and never
asserts the resulting state. The high-value case is an INTERFACE-typed enum, where the member
decides which implementation codeunit dispatches, so the mutant catches a suite that never pins
implementation-specific behaviour. Nothing in the product can model a wrong branch of a polymorphic
dispatch today.

**Footprint, measured on `do-rel2/Cloud`:** 2,355 `qualified_enum_value` nodes, **zero claimed by
any operator**. By syntactic context: 762 in an argument list, 619 as a `case_branch` label, 268 as
an assignment right-hand side, 182 nested in an argument, 67 inside an `in` list literal, and 154
plus 89 inside comparisons (those statements already carry `negate-conditional`, so they are the
non-marginal share). The marginal surface is well over a thousand, two orders of magnitude above
R13's bar of 13.

**Why it should compile.** A sibling member of the same type is type-identical by construction.
Guards, all in `receiver.ts`'s safe direction where unresolvable means refuse: the enum,
`enumextension` or option field's table must resolve in the project symbol table, so base-app enums
are refused; the type needs at least two members; in a `case` label, pick a sibling not already used
as a label anywhere in that `case` statement, which avoids both a duplicate-label compile risk and
an equivalent relabel.

**One thing to probe before the guard is frozen:** what `alc` does with a duplicate `case` label.
That is an offline `/al-compile`, not a live run.

**False kill:** none intrinsic. A downstream `TestField(Status, Status::Open)` raising is the
production code's own guard, an honest kill, and R121's screen reporting it as a kill without an
assertion is correct behaviour rather than a hazard.

Proposed by the Fable subagent 2026-08-19; the footprint here is measured rather than its guess.
Next step is the R159 treatment: site census with the operator's own `targets()`, overlap check,
`alc` compile proof in both directions, then a pre-committed live arm.

**BUILT 2026-08-19. Offline complete, live NOT done.**

`lethal.swap-enum-member` (Tier 2, 1.0.0) replaces a qualified enum value with the NEXT member of the
same enum in declaration order, wrapping. Deterministic on purpose: the same source must always
yield the same mutant, or two runs are not comparable and history compares mutations that are not
the same mutation.

**The `alc` probe this row asked for was run first, and it changed a guard from caution into a
requirement.** A duplicated `case` label is a hard error:

```
error AL0402: Expression "R162 Status"::Open cannot be specified more than once in a 'case' statement.
```

So the operator walks siblings in declaration order and takes the first not already labelling
another arm of the same `case`; if all are taken it emits nothing. Without that guard a single swap
fails the whole project's compile after the expensive step.

**The headline 2,355 was a ceiling.** Measured on `do-rel2/Cloud`: 2,472 `qualified_enum_value`
nodes, **65 claimed**. 620 are `case` labels, of which 11 are claimed. The gap is the
project-declares-it guard: almost every enum a real app references is a BASE-APP enum whose members
this source-derived layer cannot see, and inventing them would emit a value that may not exist.

65 still clears R13's bar of 13.

**That collapse is now a pattern across three candidates**, and it is worth carrying forward:

| candidate | ceiling | honestly claimable |
| --- | ---: | ---: |
| [[R159]] arithmetic | 1,121 | 100 (120 after [[R160]]) |
| [[R165]] forward trigger flag | 394 | 49 |
| this row | 2,472 | 65 |

A node-kind census answers "how much of this shape exists", never "how much can this tool reason
about". For a source-derived layer looking at an app built on a platform it cannot see, the second
number is one to two orders of magnitude smaller. Any future row quoting a census figure should
quote both.

**Gate impact, measured:** `examples/gift-card` **+2**, and **zero** on `sandbox-data`,
`sandbox-app`, `sandbox-hang` and `sandbox-probes`. So `itest:tables`, `itest:bcdev`, `itest:envtool`
and `itest:hang` are structurally unaffected — the mirror of [[R163]], which moved the tables gate
and left the demo alone. Both demo mutants compile-proven offline with `alc`, 2/2.

**What remains.** Both demo mutants are predicted **survived**, because `PostEntry` writes the value
into `GiftCardEntry."Entry Type"` and changes nothing else, and the string `Entry Type` does not
appear anywhere in the demo suite. That is a second survivor class found rather than planted: a
ledger that records issue-versus-redemption which nothing checks. Written down in
`docs/superpowers/specs/2026-08-19-r162-swap-enum-member-precommitment.md`.

The run has not happened: every Cronus container was wiped to a clean BC, with no LethAL Control app
and no fixture apps published. This row stays open until the demo campaign is re-run and re-frozen.
