Replace a qualified enum or option value with a sibling member of the same declared type.

```al
SalesLine.Status := SalesLine.Status::Released;   // before
SalesLine.Status := SalesLine.Status::Open;       // after
```

**What weak test it catches.** A state-machine test that asserts the operation ran and never
asserts the resulting state. The high-value case is an INTERFACE-typed enum, where the member
decides which implementation codeunit dispatches, so the mutant catches a suite that never pins
implementation-specific behaviour. Nothing in the product can model a wrong branch of a polymorphic
dispatch today.

**Footprint, measured on `do-rel2/Cloud`:** 2,355 `qualified_enum_value` nodes, **zero claimed by
any operator**. By syntactic context: 762 in an argument list, 619 as a `case_branch` label, 268 as
an assignment right-hand side, 182 nested in an argument, 67 inside an `in` list literal, and 154
plus 89 inside comparisons (those statements already carry `negate-conditional`, so they are the
non-marginal share). The marginal surface is well over a thousand, two orders of magnitude above
R13's bar of 13.

**Why it should compile.** A sibling member of the same type is type-identical by construction.
Guards, all in `receiver.ts`'s safe direction where unresolvable means refuse: the enum,
`enumextension` or option field's table must resolve in the project symbol table, so base-app enums
are refused; the type needs at least two members; in a `case` label, pick a sibling not already used
as a label anywhere in that `case` statement, which avoids both a duplicate-label compile risk and
an equivalent relabel.

**One thing to probe before the guard is frozen:** what `alc` does with a duplicate `case` label.
That is an offline `/al-compile`, not a live run.

**False kill:** none intrinsic. A downstream `TestField(Status, Status::Open)` raising is the
production code's own guard, an honest kill, and R121's screen reporting it as a kill without an
assertion is correct behaviour rather than a hazard.
