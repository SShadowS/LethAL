**Found 2026-10-21** by the R-586 plan review (minor finding), checked by the lane in `ResultsStore.priorSurvivorKeys`
on master c8545c87.

**What.** `priorSurvivorKeys` reads the latest finished run's `backend`, but it uses it only for R557's al-runner
test-name checks. It never compares it with the session's backend. The only checks that separate a run of one
backend from a session of another are:
- the identity scheme;
- the coverage mode;
- the test-app identity: hash, `proven`, dependency fingerprint;
- the build symbols;
- R442's hidden files.

bcdev and al-runner share the coverage mode `none`. So a bcdev run's survivors are kept from an al-runner session (and
the other way round) only because the two backends compute the test-app identity differently: al-runner records its
dependency fingerprint as "not published", while bcdev takes it under the lease. Nothing states or tests that this
difference is what keeps them apart.

**Why it matters.** A survivor is evidence only on the backend that measured it: al-runner and bcdev differ in
known ways (R546, [[R553]]). If a future change made the two identities coincide, `--skip-known-survivors` would
skip mutants on one backend because the other one saw them survive. That is a false survive carried across
backends.

**Not a live defect today.** This is unmeasured. No session has been seen to lend across backends.

**To close.** Add an explicit same-backend check to the history read. [[R586]]'s planned `runMayLend` (backend and
`runner_build` first) does this when either side is `al-runner-v3`. Extend it to every backend pair, with a red test:
a bcdev `none` run lends nothing to an al-runner `none` session with the same test-app identity.

**Expect a red test when this closes.** `tests/r618-lend-order.test.ts`, "control: the same run with the mark lends
(R592's known gap ...)", pins today's behaviour: a marked al-runner run lends to a bcdev session. Closing this item
turns it red; update it to expect a refusal (added by R-618's build review, M-5).

**Closed by R-592b (2026-10-22).**
- **The check.** `backendBuildRefusal`, step 1 of `runMayLend`, now refuses ANY pair of different backends, not only
  pairs that include `al-runner-v3`.
  - The message for pairs without v3 is new: "a verdict is lent only within one backend (R592)".
  - Pairs that include v3 keep R586's text, which `itest:lend` asserts verbatim.
  - The warning codes do not change: `history-backend-build-changed` and `snapshot-backend-build-changed`.
  - With no session named (unit callers only; all three production sites pass one), only a v3 run is refused, as
    before.
- **The sites it closes.**
  - History (`--skip-known-survivors`) lent across bcdev and al-runner.
  - So did **baseline-snapshot reuse**: `findBaselineSnapshot` selects by batch hash and coverage mode, not by
    backend. A bcdev snapshot was reused by an al-runner session (R619's test "bcdev snapshot, v2 session: reused
    (R592's gap, unchanged)").
- **`--resume-run` of another backend could NOT carry before this change.** `resolveResume` throws on
  `row.backend !== backendName` before `runMayLend`. `--resume` searches only runs of its own backend
  (`findResumableRun`). That throw is now pinned for the bcdev and al-runner pair as well.
- **Tests:**
  - `r586-run-may-lend.test.ts`: both directions refused; the same backend lends.
  - `r618-lend-order.test.ts`: the R592 control now expects `backendBuildRefused` in both directions. RC4a's R557
    mark tests moved to an al-runner session, so step 2 stays reachable.
  - `r619-one-lend.test.ts`: history and snapshot refuse bcdev to v2; same-backend controls; the `--resume-run`
    pin.
  - Five tests were red before the fix.
  - Red checks: refusing only bcdev runs, refusing only al-runner runs, and dropping the different-backend
    condition. Each goes red, with 2, 4 and 40 failures (`/coord/handoff/R-592b/redcheck-*.log`).
- **Known limit (cost only, build review):** `priorSurvivorKeys` and `findBaselineSnapshot` take the NEWEST match
  and do not filter by backend; step 1 runs after that.
  - Example: run al-runner, then bcdev, then al-runner again. The third session finds the bcdev run or snapshot
    first and refuses it, so it re-runs its baseline or skips no survivor. An older al-runner match would have lent.
  - No wrong verdict, only time. v3 already behaved this way.
  - Fix if mixed-backend stores prove common: filter the two lookups by backend.
- **`itest:lend`:** unchanged, since every leg runs on one backend (pre-commitment
  `docs/superpowers/specs/2026-10-22-r592b-lend-precommitment.md`).
