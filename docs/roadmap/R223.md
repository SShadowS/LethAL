**Found while designing the autonomous issue orchestrator**
(`docs/superpowers/specs/2026-09-13-issue-orchestrator-design.md`), by an adversarial review from
gpt-5.6-sol, and verified here before it was believed.

Every env-gated integration test calls `process.exit(0)` on its skip path:

| itest | line |
|---|---|
| `packages/runner/itest/bcdev.itest.ts` | 49 |
| `packages/runner/itest/tables.itest.ts` | 53 |
| `packages/runner/itest/hang.itest.ts` | 65 |
| `packages/runner/itest/al-runner.itest.ts` | 48 |
| `packages/runner/itest/chunked.itest.ts` | 78 |
| `packages/runner/itest/envtool.itest.ts` | 132 |

So `bun run itest:tables` with `LETHAL_ITEST_TABLES` unset prints that it skipped and exits 0. To a
human reading the terminal that is unambiguous. To anything reading the exit code, a skipped gate
and a passed gate are the same value.

`scripts/compile-fixtures.ts` has the same shape twice over: `:87-89` exits 0 with the message
"SKIPPED, not passed" when `alc` cannot be found, and `:105` skips a project with no `.alpackages`
without incrementing the failure count.

## Why this is a correctness risk rather than a nit

It is this repo's signature bug in the one place it is least visible. `CLAUDE.md` names the shape:
"Empty-vs-empty 'matches' is this project's signature bug", and "Fail loudly on caller-contract
violations ... throw, never return a plausible empty default". A gate that reports success for
having done nothing is exactly that, and the message that makes it honest to a human is invisible
to a script.

Today the blast radius is small because the gates are invoked by hand, by someone reading the
output. It stops being small the moment anything reads the exit code: a CI job, a wrapper script,
a `&&` chain, or the orchestrator, whose merge criterion was originally written as "every required
leg exited 0" and would therefore have merged everything on a ladder that never reached Business
Central, on one misspelled environment variable.

## What closing it would take

A machine-readable completion receipt per leg is the version the orchestrator spec needs anyway:
leg name, candidate SHA, the sublegs run against their expected count, the artifact ids observed,
and an explicit status, so a skip is representable as neither pass nor failure. The caller then
requires the receipt rather than the exit code, and a required leg that skipped is an error at the
caller rather than a silent success.

The cheaper half, worth doing regardless: a distinct non-zero exit for "skipped" behind an opt-in
flag (`--require-env`), so an automated caller can demand the gate actually ran while an
interactive run keeps today's friendly skip. `compile-fixtures.ts` needs the same treatment plus a
positive inventory: the resolved `alc` path, the projects it expected, and zero skipped among the
ones the change affected.

## What landed, 2026-09-18

The seven live gates (bcdev, tables, chunked, hang, lease, stale-publish, al-runner) now write a
machine-readable receipt through `packages/runner/itest/gate-receipt.ts`, and a challenged skip
exits non-zero as well as writing a `skipped` receipt. Both halves, because there are two kinds of
caller: one reads the receipt, one reads `$?`, and before this the second learned `0` either way.

Nothing changes for a human. A receipt is written only when the caller sets all four of
`LETHAL_GATE_NONCE`, `LETHAL_GATE_SHA`, `LETHAL_GATE_GENERATION` and `LETHAL_GATE_RECEIPT`, and a
PARTIAL set throws rather than falling back, since falling back would hand the caller exactly the
exit-code-only result the receipt exists to replace.

The receipt reports `artifactsReported: false` rather than an empty map when a leg cannot attest
which artifacts the server is running. `{}` would read as "nothing was published", which is a
different claim and the one that hides R56.

## What landed second, the same day

`compile-fixtures.ts --inventory <out.json>` writes what was actually done: the resolved compiler,
and per project its version, its SOURCE HASH and whether it compiled. In that mode a missing `alc`
is an error rather than a friendly skip, because a caller that asked for an inventory and got exit
0 with no inventory has learned nothing. Without the flag the script behaves exactly as before.

The script reports and does not judge: which skipped project matters depends on what a change
touched, and the script does not know the diff.

## Why the source hash, and not the version

Measured on Cronus285 while building this: `LethAL Sandbox Data Tests` reports `1.0.0.17`, exactly
its `app.json` version. R56's shape is source changing WITHOUT a bump, so a version comparison
agrees with itself while describing different code. The hash moves whenever the source does.

A local build hash is no good either, because nothing the server reports is comparable to it: BC
reports a `PackageId`, a fresh GUID per publish, which says WHICH publish without saying what went
into it. So the join has to be RECORDED rather than derived. `scripts/agentflow/artifact-freshness.ts`
does that, with four answers: `fresh`, `stale` (R56), `unverified-publish`, `missing`/`unexpected`.

`unverified-publish` is the honest fourth answer and it BLOCKS. An app published by hand has no
ledger entry and the executor cannot vouch for it. Treating an unknown publish as fine would
reopen R56 through the exact door it came in: someone publishing the test app by hand as their own
workflow. Demonstrated live on Cronus285, whose fixture apps were published by hand during
container qualification and therefore classify as `unverified-publish` today.

## What is still open

1. The executor does not publish anything yet, so no ledger exists and every app on the agent
   containers is `unverified-publish`. The comparison is built and proven; the thing that populates
   its middle term is not.
2. `scripts/compile-fixtures.ts` still exits 0 in its NON-inventory mode when `alc` is missing.
   That is deliberate (a TypeScript-only contributor must not be blocked) and the inventory flag is
   the escape hatch for a caller that needs certainty, but it means the bare script is still not
   safe to read by exit code alone.

Load-bearing for [[R224]] and for anything that automates the gates.
