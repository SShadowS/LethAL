**Found 2026-10-21** by the second Opus delta review of [[R586]] (`/coord/handoff/R-586/review-build-delta2.md`, G5).

**What.** The update gate's worktree preparation (`gatePreparation` in `scripts/al-runner-v3-update.ts`) checks
the fixture symbol tar's sha256 (`FIXTURE_SYMBOLS_TAR_SHA256`) only when it EXTRACTS it, that is when the fixture
`.alpackages` folders are absent. Folders already present, from an older tar or copied by hand, are used without
any check.

**Effect.** None on a verdict measured so far: stale symbols give an alc failure (`infra-fail`) or M8's
`al-runner-v3-system-application-not-found` / version refusal, not a wrong verdict. It would matter only if the
Microsoft apps differed at the same System Application version.

**To close.** On extraction, write the tar's sha256 to a marker file beside the extracted folders, and on a later
run require that marker to equal `FIXTURE_SYMBOLS_TAR_SHA256` before using folders already there (otherwise
re-extract or refuse by name). Unit-test the preparation decision in both directions.

**Scope widened 2026-10-22 (orchestrator).** `itest:alrunner-v3` itself did not prepare the folders at all, so a
manual run in a fresh worktree failed on infrastructure before any fact was measured:

- R-637's first live run: legs C, S1 and N1 `INFRA-FAIL ... ENOENT ... scandir
  '/work/lethal-wt/r637/fixtures/sandbox-tests/.alpackages'` (`/coord/handoff/R-637/live/alrunner-v3.log`). It
  cost a live run.
- lethal-code's R-612 leg C, the same error in `/work/lethal-wt/r612` (`/coord/handoff/R-612/live/legC.log`;
  reason 1 of `docs/superpowers/specs/2026-10-22-r612-live-precommitment-addendum.md`).

So both callers now share ONE function, with the first daily run after this lands as a stated condition: it must
not refuse for good because folders extracted before R614 have no marker.

**Closed (8090734b, with the build review's fixes in 72203cfc).** `prepareFixtureSymbols` in
`packages/runner/itest/fixture-symbols.ts`, called by the update gate's `runGate` (replacing `gatePreparation`)
and at the start of the itest's `main()`:

- folders absent: the tar's sha256 must equal `FIXTURE_SYMBOLS_TAR_SHA256`; then ONLY the members under the two
  folders are extracted (no other fixture folder is written), and the pin is written to
  `.fixture-symbols.sha256` at the worktree root (gitignored);
- both folders present and that marker equals the pin: used as they are, the tar not read;
- both present and NO marker (the migration): re-verified against the tar, the file set and every file's sha256
  under the two folders. Equal: the marker is written and the run goes on. Any difference, a symlink included,
  refuses by name;
- a wrong marker or only one folder: refused by name, `al-runner-v3-gate-symbols-unverified`, naming the marker
  found, the sha expected and the one-time fix (remove both folders and the marker). With no tar to verify
  against, the fix named is to supply the pinned tar, or to write the marker by hand after checking the folders.
  Nothing is ever deleted automatically.

The update gate writes the outcome (`extracted`, `verified` or `marked`) to the update log as
`<time> <tag>: fixture .alpackages: <outcome>`, so the first cron after this lands should log `marked`. A future
re-pin of the tar refuses the gate worktree once; the pin's comment and the gate page name the fix.

The two folders are all the legs need: R-637's and R-639's live runs had only those two extracted and passed all
eight legs. The tar is read by a small ustar reader (regular files and directories only, the POSIX prefix read on
the POSIX magic only; any other member type, an absolute path, or a path that lands outside the worktree once
joined, backslashes included, throws), so no platform `tar` is needed and the 1.7 GB tar is streamed, never held
in memory. Checked offline on 2026-10-22, read-only: a scratch COPY of today's `/work/lethal-wt/al-runner-v3-gate`
folders came out `marked` in 3 s against the real tar. A full extraction to scratch by the first version of the
reader was identical (`diff -r`) to GNU tar's, apart from the marker. Tests:
`packages/runner/tests/fixture-symbols.test.ts` covers each outcome and refusal above, a nested subfolder, a
symlink inside a folder, an unsupported member type, an absolute and a climbing member path (`/` and `\`), the
POSIX-versus-GNU prefix, and both callers' wiring; the update test covers the log line. 21 single-revert red checks
in `/coord/handoff/R-614/red-unit/`.

Live: `itest:alrunner-v3` on 0e7ef884 in a worktree with NO fixture `.alpackages` printed
`fixture .alpackages extracted`, extracted only the two `GATE_ALPACKAGES` folders from the real pinned tar, and
passed all eight legs against pinned alpha.2; `git status` afterwards showed no change (the marker is gitignored)
(`/coord/handoff/R-614/live/alrunner-v3.log`). That also confirms the two folders are all the legs need.
Re-run on the merged head 524d48d7 (R-585 and R-639 merged in) with the folders and marker present: printed
