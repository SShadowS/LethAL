**Found 2026-10-08 by R-508's adversarial plan review (I2), by reading the code. Not verified live.** A false-kill
risk, narrowed but not closed by [[R508]].

**What.** R508 corrects a lease-lost batch in the store twice: once at the moment of loss (`LeaseSession`'s
`onLost`, called by `noteLeaseLost` after the latch) and once in the session's `finally` (`invalidateLostBatch`).
There is no SIGINT/SIGTERM handler, so Ctrl-C or a kill skips every `finally`. What is left is a verdict recorded
AFTER the loss note and BEFORE such a crash. Example: the heartbeat notes the loss while a `RunMutant` is in flight,
`onLost` rewrites the rows recorded so far, then the in-flight run answers a position-1 `timeout`, which is recorded
as `timeout-killed` with no further dispatch, and the process is killed before the `finally`. The run is unfinished
and that row is not `error`, so a `--resume` run with `--stop-hung-sessions` carries the kill (`carryableRow` refuses
`timeout-killed` without it). The R508 test "a verdict recorded after the loss note is corrected by the session's
finally" shows the row; only the `finally` corrects it. The more general residue is a `survived` recorded after the
note (R508 test 5's shape): it is carried into the resumed run and, once that run finishes, seeds
`--skip-known-survivors`, which hides a kill rather than inventing one.

`LostBatchNotStoredError`'s "do not --resume run N" is advice only: `--resume last` would still pick that run. In
practice a store that refused the correcting write is likely to refuse the resume's own writes too, but the table
below would make the refusal structural.

**Not a fix: a positive "batch completed" marker.** The store has no batch-completion transaction, and without
`maxGuardsPerBatch` the whole project is ONE batch, so every crash would leave the batch unmarked and `--resume`
would carry nothing. That breaks [[R47]] on every crash.

**Proposed fix: a negative record, written at the loss.**

- A new `lost_batches (run_id, batch_index, note)` table, created if absent. No migration of existing rows and no
  `IDENTITY_SCHEME` change.
- `onLost` inserts the row in the same synchronous write as today's `invalidateBatch`.
- Readers exclude a lost batch's rows whatever their verdict: `mutantVerdicts` (the reader behind
  `buildResumeIndex`; the exclusion belongs in the reader, not in `strandedKeys`), `findResumableRun`'s `EXISTS`
  and its sibling queries (`unfinishedRunUnderOtherScheme`, `unfinishedRunUnderOtherSymbols`,
  `unfinishedRunUnderOtherCoverageMode`), and `findBaselineSnapshot`.

**To close.** Reproduce offline first: R508's crash stand-in (a store that breaks when teardown starts) combined
with a verdict recorded after the note, then a resume that carries it. Then add the table and the reader
exclusions. Pin both directions (a lost batch's late verdict is not carried; a completed batch before it still is),
red-checked. Plan: `/coord/handoff/R-508/plan.md` §"Crash window".

**Fixed by R-512 (plan r3, `/coord/handoff/R-512/plan.md`).** The negative record as proposed, with one change:
readers do not EXCLUDE a lost batch's rows, they read them as `invalidateBatch` would have rewritten them.

- `lost_batches (run_id, batch_index, note)` is created if absent (no `migrate()` step, no `IDENTITY_SCHEME`
  change; an old store gains an empty table and reads as before). `ResultsStore.markBatchLost` inserts with
  `INSERT OR IGNORE`, so the first note wins. `onLost` calls it FIRST, before `invalidateBatch` and
  `dropBaselineSnapshot`; the session's `finally` (`invalidateLostBatch`) calls it again as a second chance.
- One SQL expression, `EFFECTIVE_VERDICT_SQL`, reads a lost batch's row as `error` unless it is `error` or
  `known-survivor` (`INVALIDATION_KEEPS_SQL`, the list `invalidateBatch` itself uses). `mutantVerdicts` returns
  such a row with the loss note and no killing fields; `findResumableRun` and its three siblings use it in their
  `EXISTS`, so a run whose only carryable rows are lost is not resumable and `--resume last` moves to an older run.
  `findBaselineSnapshot` skips a lost batch's snapshot even when `onLost`'s drop failed.
- Read as error rather than excluded, so a stranded row in a lost batch still reaches R53's `strandedKeys` (the
  hang is not re-run), and a colliding identity key with one row in the lost batch stays ambiguous.
- `verify` still reads the run's stored rows and can list a lost batch's `survived` row as a gap target. That is
  acceptable: verify re-measures every target.
