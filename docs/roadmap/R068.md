**A variable declared in a TRIGGER's own `var` section is never resolved, so Tier 2 refuses every site whose receiver is declared there.** `lookupVar` (`packages/builtin-tier2/src/receiver.ts`) resolves procedure locals, procedure parameters and object globals; `buildSymbolTable` indexes `procedure` members only, so a trigger's `var` section is invisible in EVERY object kind — table triggers, page triggers, `OnRun`, field `OnValidate`. Safe direction (rule 4 refuses; Tier-1 `void-method-call` still covers the site) and already stated in `lookupVar`'s doc comment as deliberate conservatism — but it is a real coverage loss, not a design choice, and trigger bodies are where a great deal of BC logic lives. Measured incidentally 2026-07-31: R30's fixture pageextension first declared its records inside `OnOpenPage` and generated four specs, **not one of them `remove-setrange`**; moving the same declarations to the object's `var` section made the site claimable. Sizing it on a real project has NOT been done — `scripts/probe-r30-pageext.ts` counts receivers declared in procedures and globals, and would need a trigger-scope arm added.

Once trigger vars resolve, the trigger-local `Helper` wins scope resolution outright — before the (kind, name) key is ever consulted — so the site claims identically whether or not R70 is regressed, and the gate stops detecting the class it was built for while still passing. **The fix is small and must land first:** change `page 79324 "Data Scope Probe"`'s `Helper` from `Record "Data Main"` to a NON-record type (e.g. `Integer`). Then under a regressed R70 the page's declaration makes the receiver resolve to a non-record and Tier 2 REFUSES — the mutant flips `remove-setrange` -> `void-method-call`, an observable that does not depend on R68 either way. Re-freeze `tables.baseline.json` with the usual old/new diff after that change. Found by checking the interaction before implementing, not by a gate — no gate would have reported it, which is the point.
