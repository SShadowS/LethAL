**`SessionConfig.emit` accepting a single subscriber, plus a separate `fanOutEmit` helper to combine several, is one layer of indirection more than the design needs.** `runSession` (`orchestrator.ts`) already fans events out to multiple listeners via `createEmitter([collector, ...])` internally; `cli.ts`'s `fanOutEmit` (`packages/runner/src/cli.ts`) exists ONLY to pre-combine the stderr progress renderer (Task 5) and the `--progress-out` NDJSON sink (Task 6) into the ONE subscriber slot `SessionConfig.emit` currently allows, then unwraps that combination again inside `runSession`. Widening `SessionConfig.emit` to `readonly EventSubscriber[]` would let `runSession` fan out to all of them directly and delete `fanOutEmit` (and its dedicated test suite, `cli.test.ts`'s `describe("fanOutEmit (Task 6 review round 1)")`) entirely — one fan-out implementation instead of two. Found during the whole-branch review of the event-stream branch (2026-08-05); not fixed there since it touches Task 5/6's already-landed, already-tested surface rather than Task 4's. Evidence: `packages/runner/src/cli.ts`'s `fanOutEmit`, `packages/runner/tests/cli.test.ts`'s `describe("fanOutEmit (Task 6 review round 1)")`.

---

**DONE 2026-08-08, and the row was right about all of it.** `SessionConfig.emit` is
`readonly EventSubscriber[]`, `runSession` spreads it straight into its existing
`createEmitter([...])`, and `cli.ts` passes `emitSubscribers` as the list it already had.
`fanOutEmit` and `cli.test.ts`'s `describe("fanOutEmit (Task 6 review round 1)")` are gone. One
fan-out implementation, as the row asked.

Two things worth recording that the row did not mention.

**`createEmitter` already had the isolation behaviour `fanOutEmit` reimplemented**, so this was a
deletion rather than a move: both catch a throwing subscriber, mark it broken once, and keep
delivering to its siblings. `fanOutEmit`'s stated reason for existing separately was avoiding a
SECOND `seq` stamp — real, and irrelevant once the subscribers go into the one canonical emitter
that stamps them.

**A deletion cannot be red-checked, so the feature it served got a test instead.** Nothing asserted
that `runSession` passes ALL of `cfg.emit` through: `events.test.ts` covers `createEmitter`'s
fan-out and isolation, and the callers each supplied one subscriber. A regression to
`[cfg.emit[0]]` would have been invisible. `orchestrator.test.ts` now drives a session with two
subscribers and asserts they received EQUAL SEQUENCES, plus that `seq` is a single 1..n run — a
length check alone would pass on two independently stamped copies. Red-checked by slicing the
spread to the first subscriber: that one test reddens, 186 pass / 1 fail, restored to 187 / 0.

Callers touched: one production call site (`cli.ts`) and six in `orchestrator.test.ts`, all of which
passed a `createEmitter(...)` result and now pass `[emit]`.
