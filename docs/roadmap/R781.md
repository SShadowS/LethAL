**Found by R-766's proof (2026-10-25, `/coord/handoff/R-766/proof/run1/`).** [[R766]]'s queue hands out whole
procedure scopes, so every mutant of one `procedureScopeOf` runs on one lane in manifest order. That is the ruling
that keeps the [[R197]] kill ledger, which orders a mutant's covering tests by the kills already made in its procedure,
exactly as at N = 1, so `killingTest` and verdicts cannot move with lane timing. On D1 (one CDO file) the 63 mutants
fall into few scopes: N = 4 started 3 daemons and gained nothing (93 s -> 92 s). The gift card spreads (15 s -> 4 s).

**Can a scope be split safely?** Only by changing what the ledger shows a mutant, and every option moves
`killingTest` (and, through the I4 rules, sometimes a verdict) away from N = 1 and bcdev:
- (a) a ledger SNAPSHOT frozen per scope at batch start: deterministic for every N >= 2, but not equal to N = 1;
- (b) a static test order (no ledger) under N > 1: deterministic, not equal to N = 1;
- (c) keep the ledger but run one scope's mutants on several lanes in manifest order, each waiting for its
  predecessors' kills before it orders its tests: equal to N = 1, but the waiting serialises the scope again.
So the safe answer is (c), which gains nothing, or a ruling that accepts (a)/(b)'s different `killingTest` for N > 1
(and a pre-commitment of every figure that moves).

**To decide.** Measure how real projects spread before choosing: the mutants-per-scope distribution (offline, from
the manifest) on the whole CDO Cloud app and on DC, and one live N = 1 vs N = 4 run on a larger CDO slice with many
procedures, within the heavy-job limits. If real projects have many scopes (the expectation), parallel already helps
them and scopes stay whole; this item then records the ceiling as a known limit for few-procedure projects.

**Measured 2026-10-25** (`/coord/handoff/R-781/`, LethAL's own planner grouped by `procedureScopeOf`; names and counts
only). Best case at N lanes = total / max(largest scope, total / N), equal cost per mutant:

| target | mutants | scopes | largest scope | top 3 | top 10 | bound N = 4 | bound N = 8 |
|---|---|---|---|---|---|---|---|
| D1 slice (one CDO file) | 63 | 4 | 46.0% | 93.7% | 100% | 2.17x | 2.17x |
| CDO Cloud, whole app | 36,601 | 3,419 | 0.83% | 2.34% | 5.81% | 4.00x | 8.00x |
| DC Cloud, whole app | 112,070 | 8,697 | 0.44% | 1.22% | 3.28% | 4.00x | 8.00x |

So whole apps lose nothing to scope affinity; only few-procedure slices like D1 hit the ceiling. A live pair on a
140-mutant CDO slice (two files, 23 scopes; al-runner 3.0.0-alpha.5+edge.20261024 (dcdf9e821), serve-entries) was
per-mutant IDENTICAL at N = 1 and N = 4 (`scripts/report-diff.ts`, 0 differences; 39 killed, 101 no-coverage) but
not faster (65 s vs 75 s wall): only 39 mutants needed live runs (about 23 s of a 62 s session), and four daemons'
warm-ups summed to 62 s against 7 s for one, with another heavy job on the box. Three other slices could not run at
either N (`al-runner-v3-entries-warmup-dirty`: their tests need unbuilt DotNet sidecars or read the Company table).

**Proposal.** Keep scopes whole: no split, no ledger-snapshot ruling (real apps have thousands of scopes). The real
limit for small runs is per-lane startup (each daemon compiles and warms the project): parallel pays only when the
live work is large next to N warm-ups. Close this item as a measured limit, and record in the `--workers` docs that
it helps large projects and slows small ones; a follow-up could start extra lanes only when the live work queued is
several warm-ups long (unmeasured).
