**Seen on master's Windows CI, run 40123793830, attempt 1 (a re-run passed).**
- Test: `runMany — R503: the watchdog's GetOperationStatus poll is bounded > P6: a slow poll that answers inside the
  bound is used (the bound is not the poll interval)` in `packages/runner/tests/run-mutant-many.test.ts`.
- Failure: `Expected: "timeout"`, `Received: "deadline-exceeded"`.

**Why.** P6 leans on real timers with thin margins:
- the second status poll answers after a 40 ms `setTimeout`, under a 200 ms poll bound;
- the run's budget is 400 ms (`requestCeilingMs`);
- the 408 that confirms the stop is released by a 5 ms `setTimeout` after `StopHungRunAt`, inside a 100 ms
  `stopGraceMs`.

A runner that stalls for about 100 ms between the stop and the release passes the hard cap
(`requestCeilingMs + stopGraceMs`), and the transport correctly reports `deadline-exceeded`.

**What P6 pins** (R503): a poll slower than the watchdog's poll INTERVAL (`watchdogPollMs: 5`) but inside the poll
BOUND is still used, and its answer drives the stop. Nothing in that needs tight margins.

**The cause, reproduced locally:**
- A 150 ms stall before the 408 still gives `timeout`, so the grace was NOT the margin that broke.
- A slow poll stalled to 250 ms gives `deadline-exceeded` in 502 ms, the CI failure exactly. The poll's real bound is
  `min(pollBoundMs, hard cap left)`. With a 200 ms bound and a 500 ms hard cap, a stalled poll is a failed poll, and
  the call runs out.

**The fix (test only).** The poll bound is now 2000 ms and `stopGraceMs` 2000 ms, so the hard cap clamps the bound
only after 2.4 s. A poll stalled to 250 ms and to 1000 ms both pass.
- **Not fully clock-free.** The transport reads one monotonic clock (R710) with no injection point, and P6's
  property is itself a real duration: a poll longer than the 5 ms interval. So a fake clock would need a transport
  change that this flake does not justify. The margin is now 25x the observed stall instead of 0.
- **Red check, the other direction:** with the transport bounding the poll by the INTERVAL (`pollMs`) instead of
  `pollBoundMs`, P6 fails (`deadline-exceeded`) with the new margins. So the test still catches the bug it exists
  for.
