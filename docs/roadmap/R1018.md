Found by coord task PR-06 (2026-11-15), after `current` moved to edge-5a58a0f16 at 07:57:56 UTC during a batch of PR-06 runs.
Related: [[R950]] (resolve once), [[R786]] (the warm-up fallback), [[R814]] (gated builds), [[R1013]].

**Code path.** `AlRunnerV3Backend`'s constructor resolves the configured binary once (`resolveV3Binary`, a realpath; R950). Every
spawn of that backend uses the resolved path, so within one backend the build is fixed: serve daemons and their restarts, one-shot
runs, the cross-check one-shots, and the .NET sidecar (`pinnedSidecar` beside the resolved binary). But `runFromCli`'s `attempt()`
(`cli.ts`) calls `build(...)` for each attempt. When the serve-entries default stops at the warm-up
(`AlRunnerV3ServeFallbackWarmupError`), the second attempt builds a NEW backend from the same config, and that resolves the link
again.

**Measured** (`/coord/handoff/PR-06/linktest/`; a private symlink, never `current`):
1. Avalara's config was given `alRunnerV3.path` = `<link>/al-runner`, with the link at edge-a184cfc79.
2. Once the run reached its baseline, the link was moved to edge-5a58a0f16 (08:41:54).
3. The store's runs then read:
   - run 1 (the serve attempt, abandoned at the warm-up) has runner_build edge-a184cfc79;
   - run 2 (the one-shot retry) has runner_build edge-5a58a0f16;
   - stderr prints `[lethal] al-runner:` once for each build.
4. The report names only 5a58a0f16, yet its `al-runner-v3-serve-default-fallback-warmup` caveat is the a184cfc79 warm-up's
   finding.

Nothing says the build changed.

**Why it matters.** `current` is a link the daily update moves (R723). A lane's run that falls back to one-shot across a move
changes build silently. The report then mixes one build's warm-up refusal with another build's verdicts. A pre-committed build
is not the one measured. The PR-06 runs were not affected: the ones queued across the move had not started.

**Fix shape.** Resolve the binary once per `lethal run`, before the first attempt, and hand the resolved path to every attempt;
or refuse the retry by name when the link now resolves elsewhere. Either way the retry's report must name the build its warm-up
ran on. A test: a fake link that moves between the attempts, with the second attempt's spawns asserted on the first resolved path.

**Fixed** by lethal-code in coord PR-12: the binary is resolved once per run, and every attempt and backend gets that path (fix
79dfbe47, review follow-up 51c9da08, master 09d4242a).
