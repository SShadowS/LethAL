**What.** Filed from R205 point 2 (R-205, 2026-10-05). In the R205 incident a mid-edit source file
was already broken when LethAL parsed it (a procedure's `end;` was missing). tree-sitter recovered
without an `ERROR` node, the instrumented batch failed to compile, bisection re-staged and failed
again, and every mutant of the batch was scored `error` with the note "deploy failed for a reason
that is not attributable to any SINGLE mutant — either environmental ... or MORE THAN ONE mutant
breaks the compile". Neither was the cause: the project itself did not compile.

**Why it matters.** R-205 pins the build to one source snapshot, so a later edit no longer reaches
the build. It does not help when the snapshot itself is broken: the run measures the broken text
and blames the environment. The message points the user at the wrong cause.

**Suggested change.** Compile the plain, unmutated snapshot once before batch 0 and, when alc
refuses it, stop with "your project does not compile: <alc output>". Checking `rootNode.hasError`
per file would not have caught this case, because the recovery had no `ERROR` node. R181 already
compiles a candidate build; this is the zero-mutant case of the same check, and it would also save
the bisection's second compile.

**Evidence.** R205's body (the staged artifact, the reflog and the `dryrun.txt` comparison).
