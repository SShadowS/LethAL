**What.** Filed from R205 point 2 (R-205, 2026-10-05). In the R205 incident a mid-edit source file
was already broken when LethAL parsed it (a procedure's `end;` was missing). tree-sitter recovered
without an `ERROR` node, the instrumented batch failed to compile, bisection re-staged and failed
again, and every mutant of the batch was scored `error` with the note "deploy failed for a reason
that is not attributable to any SINGLE mutant — either environmental ... or MORE THAN ONE mutant
breaks the compile". Neither was the cause: the project itself did not compile.

**Why it matters.** R-205 pins the build to one source snapshot, so a later edit no longer reaches
the build. It does not help when the snapshot itself is broken: the run measures the broken text
and blames the environment. The message points the user at the wrong cause.

**Suggested change.** Compile the plain, unmutated snapshot once before batch 0 and, when alc
refuses it, stop with "your project does not compile: <alc output>". Checking `rootNode.hasError`
per file would not have caught this case, because the recovery had no `ERROR` node. (Correction:
this row first said "R181 already compiles a candidate build". That pointer was wrong. R181 is an
operator ruling, and nothing compiled the unmutated source before this row landed.)

**Evidence.** R205's body (the staged artifact, the reflog and the `dryrun.txt` comparison).

**Landed (063683d5).** Not before batch 0, but lazily: at the session's first `AlcCompileError` on
the sequential deploy path, `checkPlainBuild` stages the unmutated target (`prepareBatchProject`
without `writeInstrumentedProject`) and compiles it through the new optional
`ExecutionBackend.compilePlainCheck` (bcdev only: same compiler, package cache and /define, no
Control staging, no publish). A healthy run pays nothing. If alc rejects that build too, the
session throws `UnmutatedBuildFailedError` ("alc rejected LethAL's staged copy of the unmutated
target, using this compiler and package cache", then alc's output), records no `error` row for the
batch, and stays unfinished, so `--resume` retries it and history ignores it. It does not say "your
project does not compile": staging stamps `app.json`, flattens paths and rebases resources, so
only the observation is claimed. If the plain build compiles, bisection runs as before. The outcome
is cached per session (`firstCallOnly`). `AlcCompileError` now keeps both alc streams, labelled
(a stderr warning used to hide a stdout error). Neither the version-conflict check nor the retry's
second check reads an `AlcCompileError` as a conflict (the retry's since 65e20ee8), so alc's own
output cannot start or abort a retry; a real publish conflict still retries once. A failed compile's
partial `.app` is removed best-effort (65e20ee8). Scope: the worker path is not covered, since bcdev refuses `workers > 1` and
al-runner has no plain check. Tests: `r461-unmutated-build.test.ts`, each red-checked.
