`lethal.flip-filter-literal` refuses a filter string in two structurally different ways, and only one
of them had ever been exercised against a real server.

1. **Character refusal**, cheap and early: `REFUSED_CHARACTERS` in
   `packages/builtin-tier2/src/filter-expression.ts` is `/[*?@()'&]/`, so the mini-parser declines
   the string outright on a wildcard (`*` or `?`), a case-insensitive marker (`@`), grouping parens,
   the AND combinator (`&`), or an inner quote (the `<>''` idiom, which is the commonest `<>` shape
   in real AL). Nothing is classified and no rule ever runs.
2. **Ladder exhaustion**, late: the string CLASSIFIES successfully and then matches no rule in the
   four-rule ladder. A closed range (`'%1..%2'`) is the worked example.

R134's fixture measured the second one, at arm H. The first was covered by one offline unit test and
by nothing else. The two fail differently when they break: a broken ladder-exhaustion refusal
splices a filter the ladder never validated and the fixture notices as an aggregate mismatch, while a
broken CHARACTER refusal hands BC a string the parser was never meant to reach, whose likely runtime
rejection scores `killed` with no assertion earning it and nothing tagging the mechanism (R86, R138).
That is the false-kill shape this project exists to catch, and on the `<>''` population it would be
the commonest one.

## What landed

**Arm I**, `Data Filter Ops.CountTaggedInBand`, plus its covering test
`Data Tests.NotBlankFilterCountsOnlyTaggedRows`. The `<>''` idiom was taken rather than the wildcard
fallback the row allowed: `alc` accepted the AL literal (`'<>'''''`) first time and BC accepted the
filter, so the higher-value character was available.

```al
Related.SetRange("Entry No.", LowBound, LowBound + 3);
Related.SetFilter("Main No.", '<>''''');
exit(Related.Count());
```

Scoped by Entry No. BAND rather than by "Main No.", which is forced: the filter's own target field is
"Main No.", so a "Main No." scope would make the not-blank filter redundant and the arm's assertion
would stop proving the filter ran at all. The band's upper bound is computed (`LowBound + 3`) so
Tier-1 `swap-call-arguments` refuses the site, arm H's reason.

**Measured before it was written.** `scripts/r141-filter-probe/` (published to Cronus283, unpublished
after) seeded the arm's exact data and returned:

```
MEASURED: NO THROW -- baseline=2 noSetFilter=3 noSetRange=3 filterAsBCReportsIt=<>''
```

So BC accepts the idiom, reads it as "not blank", and each collateral mutant changes the count. No
verdict in the pre-commitment rested on unchecked arithmetic — the same precaution
`scripts/r134-filter-probe/` took for arm D, where the spec's literal text would have broken the
arm's own baseline.

## What this still does not prove

Only ONE of the seven refused characters is measured live. `*`, `?`, `@`, `(`, `)` and `&` remain
offline-only. The inner quote was chosen because it is the highest-value one, not because the others
are covered; a wildcard arm would be the obvious next addition if that population ever matters
enough to pay a baseline re-record for.
