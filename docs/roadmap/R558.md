**Filed 2026-10-09 by the R-551 build** (plan section 10, item 2; review of the R-551 plan, "Recording
and retirement").

**What.** Since [[R551]], a one-shot al-runner session picks its test selector once, from a probe:
`--test X --test-exact X` when the build accepts the flag, or [[R488]]'s `--test X --exclude-test
<sibling>...` otherwise. The choice reaches only the `al-runner-test-selector` warning event (the
`--progress-out` NDJSON and emit hooks). Warnings are not folded into `SessionReport`, so a saved report
cannot say which selector produced its verdicts.

**Proposed.** An optional `executionContexts[].testSelector` (`"exact" | "substring-with-excludes"`,
absent on `--server` and on bcdev), added at the next schema ripple, so the ripple is paid once (see
CLAUDE.md, "Adding a `SessionReport` field ripples").

**Not urgent:** both paths are correct on every build measured, and the event already names the
choice per session.

## Done (R-558, 2026-10-09)

The plan is `docs/superpowers/plans/2026-10-09-r558-test-selector-in-report.md`, opus-reviewed.
- **The event:** `runSession` emits a structured `al-runner-test-selector` event beside R551's warning, which stays
  for the console line.
- **The fields:** the event is folded like [[R147]]'s `platformAppsDir` into
  `executionContexts[].testSelector` (`"exact"` or `"substring-with-excludes"`), plus `testSelectorReason` (the
  probe's reason) exactly on the latter.
- **Where they appear:** directly-measured al-runner contexts only. They are absent on bcdev, on `--server` (the
  probe is not-applicable there, which includes `itest:alrunner`'s cli-default leg), on carried verdicts, and on the
  zero-count entry of a run that scored nothing.
- **The `--resume` caveat:** a batch whose baseline was reused (`resume-baseline-reused`, R192) took its baseline
  from the earlier run, which may have used the other selector. The field states this session's own runs, like
  `platformAppsDir`.
- **The live gate:** `itest:alrunner` checks it per leg: present and valid on every one-shot leg, and absent on
  every `--server` leg.

**The committed sample reports were deliberately NOT regenerated** (orchestrator's ruling, 2026-10-09). The field is
optional and nested, so `REPORT_SCHEMA_VERSION` stays 3 under R157's rule, and every committed report still
validates. The samples are bcdev reports, where the field can never appear. This step of CLAUDE.md's ripple list
exists for REQUIRED fields; it was not missed.
