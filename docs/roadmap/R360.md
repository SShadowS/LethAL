**Found by the code lane in R358's review (2026-09-30).** `runFromCli` makes
`<tmp>/lethal-XXXXXX` per session: the instrumented copy of the project for every batch
(`instrumented/run-<id>-batch-<n>/`), every worker's build, and, for bcdev, the compiled `.app`
under `publish/`. It is never removed. R358 tried to remove it and had to revert: the orchestrator
records each batch's `appPath` and `instrumentedDir` in the store (`batch_artifacts`, C02-06), both
inside that folder, and `lethal verify` reads them back (`verify.ts` `installedOf`,
`named-mutants.ts` `loadInstalledArtifact`). Removing the folder made every verify refuse with
`local-copy-unreadable`, which breaks run, explain, write a test, verify. The test
`lethal run then lethal verify on one store (R358)` in `packages/runner/tests/cli.test.ts` pins
that the folder survives the run.

**Size.** On this machine on 2026-09-30, `lethal-XXXXXX` entries in the temp folder: 19,966,
171,982,829 bytes (mixed with unit-test folders of the same prefix from before R358). A real
project's copy is its full source per batch, so every run on a large app leaves tens of MB.

**To close.** Only the highest batch matters (`installedOf` refuses any other). Either move that
batch's `.app` and batch folder somewhere durable (for example beside the store,
`<db dir>/.lethal/artifacts/run-<id>/`) and update the store row's `app_path` and
`instrumented_dir` before removing the scratch folder, pruning older runs' copies; or adopt a
retention rule (keep the last N runs' folders). Keep the folder when the session throws, since
compile diagnostics name files in it (R358 review M1). The run-then-verify test above must stay
green, and gain a check that the scratch folder is gone.

**Measured for the R360 plan's I5 (2026-09-30, offline, scratchpad script, not committed).** A
bundle of all 9,620 `.al` files of `U:/Git/BC.History/BaseApp` (187.2 MB raw, 26.4 MB after
`gzip -6`, largest file 0.79 MB) plus a 100 MB random `.app` and a 4.4 MB manifest, written as one
row per file into a fresh WAL store, then read back file by file. Bun's own RSS with nothing loaded
was 210 MB.

| step | time | peak RSS | `.sqlite` | `-wal` |
|---|---|---|---|---|
| read, hash and gzip every file | 2.6 s | 499 MB | | |
| insert, one transaction | 0.6 s | 711 MB | 132.8 MB | 133.6 MB |
| read back, gunzip, re-hash | 0.4 s | 696 MB | | |
| `wal_checkpoint(TRUNCATE)` | | | 132.8 MB | 0 |
| second bundle, then prune the first | | | 265.5 MB | 4.1 MB, 0 after checkpoint |
| third bundle into the freed pages | | | 265.6 MB | 133.6 MB |

The WAL does not shrink by itself (SQLite reuses the file but never truncates it), so the store
checkpoints with `TRUNCATE` after a bundle write and after pruning. Pruned pages go to SQLite's
free list and the next bundle reuses them; LethAL does not `VACUUM`. What is kept is decided per
group, runs of one app on one server (`app_id`, `resource_key`): a finishing run leaves its group
about two bundles (its own, plus one of a newer run still going). A group that never repeats is
bounded by a second rule (review I-1): when an env-tool session deletes an environment it created,
every bundle stored under that environment's key is dropped at teardown, since nothing installed
there can be verified again. A kept (`--keep-env`) or quarantined environment, or one whose delete
failed, keeps its bundles. Bundles of a directly configured server whose name changes between runs
are not reclaimed by either rule. Limits chosen from this: `.app` 512 MB, one `.al` 16 MB
decompressed (20 times the largest BaseApp file), whole payload 1 GB decompressed (5 times
BaseApp). Each is checked while writing and, through zlib's `maxOutputLength`, while reading.

**Closed 2026-09-30 (09e0fab1 store, b5d3a531 orchestrator, 010a55e6 verify, 7f4fc16f cli,
6b7b6b56 docs), plan `docs/superpowers/plans/2026-09-30-R-360-run-scratch-retention.md` r2.** The
installed batch's files now live in the store (`installed_bundles`, one `installed_bundle_files`
row per `.al`), written at step 3d in the same transaction as the batch row, with a SHA-256 over
the instrumented payload that verify recomputes, so a changed byte of stored AL is refused
(`payload-differs`) instead of moving coverage to the wrong procedure. `runFromCli` owns the scratch
folder from `mkdtemp` on: it removes it after a clean report, and keeps and names it on any throw,
a quarantined report or a durable quarantine record for its tier. A finishing run prunes bundles in
its `(app_id, resource_key)` group, but never the group's most recently PUBLISHED bundle (the build
on the server), whichever run finishes last: older-published bundles of finished runs, of
unfinished runs that started before it, and of its own lower batches go (a publish also replaces
the same run's lower batch at once). Verify refuses a row written before R360 by name ("recorded
before R360"), with no path fallback, and a pruned one naming what replaced it. `--resume` has no
such refusal: no resume path reads the prior run's installed files (checked in `resolveResume`,
`replayCarriedBatch` and `findBaselineSnapshot`, run 002), and the end-of-run bundle check applies
only to batches the run itself published.
The run/verify agreement test now asserts the folder is gone before verify reads the store.

**Review fixes (2026-09-30).** I-1 above (teardown rule). A clean report can still name files in
the removed scratch folder: a bisected compile failure's note (an `error` verdict) carries `alc`'s
output, whose paths are in the batch dir, and the folder is removed after such a report (review
M-6; left as is, the note keeps the compiler's text). Also fixed: a payload at exactly the size
limit, the end-of-run check loading the whole bundle, refusal texts that claimed a server for runs
that recorded none, a length prefix in the digest, and a 5 s store busy timeout.
