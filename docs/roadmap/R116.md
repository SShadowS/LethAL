**A survivor can carry `executionProven: true` beside `guardEvidence: "not-observed"` — two of our own signals flatly contradicting each other — and nothing says so.** `executionProven` is derived from `attribution === "exact"`, i.e. coverage claims a test executed the mutated procedure. `not-observed` is the DECISIVE guard-evidence state: the run's own attestation that no guarded site executed at all, whose shipped interpretation says the mutant "belongs with `no-coverage`". Both can appear on the same survivor, and `lethal explain` emits them side by side without remarking on the conflict — on the one command whose stated job is saying what is proven and what is not. Measured: **zero** `not-observed` survivors across all six committed campaign reports, and no fixture builds the pair, so this is latent rather than live — which is precisely why it needs filing rather than discovering later on a customer's report. The design question, deliberately not settled inside a fix wave: should the projection STATE the contradiction (and if so, keyed on what — a new field, or a tool-condition, since an interpretation may exist only if it is keyed to an existing machine value), or should the disagreement be reconciled upstream where attribution and guard evidence are decided, so it can never reach a report? Note the second option is the stronger one if the two signals are genuinely never both right, and the first is correct if they can legitimately disagree and the reader needs to know. A fixture pinning that the pair CAN occur and that the projection currently does not reconcile it landed with subsystem B; this row is about what to do next. Filed 2026-08-06 from subsystem B's whole-branch review.

**The open question is answered, 2026-08-07, by reading what the two signals actually measure. They
are NOT contradictory, so option 2 — reconcile upstream so the pair can never reach a report — is
the WRONG one, and would destroy information.**

- `executionProven` is `attribution === "exact"`: a member-level coverage match, collected on the
  BASELINE run, saying a test executed the mutated **procedure**.
- `guardEvidence: "not-observed"` comes from the MUTANT run's attestation. `ObservedAny` is set
  inside `IsActive` (`ControlState.Codeunit.al`), the guard predicate the instrumented target calls
  **at each mutation site** — so `not-observed` means no guarded **statement** executed anywhere in
  the target during that mutant's covering runs.

Different granularity (procedure vs statement) and different runs (baseline vs mutant). A test can
enter a procedure and never reach one statement inside it — an untaken branch — and both readings
are then simultaneously correct. So the pair is not a contradiction; it is a distinct and MORE
actionable finding than either signal alone: *this test enters the procedure but never reaches this
line*. That calls for a new case covering the branch, not a stronger assertion in an existing test,
and those are different pieces of work.

**What is genuinely wrong is the shipped prose, not the data.**
`GUARD_EVIDENCE_INTERPRETATIONS["not-observed"]` says the mutant "belongs with `no-coverage`". That
is right when attribution is `object` or `all-green` and WRONG when it is `exact`: covered-but-
unreached is not uncovered, and telling a reader to file it with `no-coverage` throws away the one
thing that makes it actionable.

**What is left to decide, and it is the part that needs care rather than more measurement:** where a
pair-keyed interpretation may live. The admissibility rule (`explain.ts`) requires an interpretation
to be keyed to a machine value the report carries AND co-located in source with that value — and a
claim keyed on the CONJUNCTION of `coverageAttribution` and `guardObserved` has no single value to
sit beside. Either the rule gains an explicit notion of a pair-keyed interpretation, or the report
gains a derived field that names the state (and then the interpretation co-locates with that field,
which is the shape the rule already supports). Whichever is chosen also needs the fixture the row
notes does not exist, and an `EXPLAIN_SCHEMA_VERSION` bump.

Still latent, not live: zero `not-observed` survivors across all six committed campaign reports.

**Closed 2026-08-07. The "where does a pair-keyed interpretation live" question is answered by the
rule `explain.ts` already states, so no rule change was needed.**

That module's own text says: *"If a useful thing to say has no field to hang on, the fix is to add
the FIELD to the report first, as its own change with its own justification — never to let this
projection assert something free-floating."* A claim about a CONJUNCTION has no single value to
co-locate with, so the conjunction becomes a value. Shipped in `report.ts`, beside
`guardEvidenceOf`:

```ts
export type SurvivorReach = "covered-but-unreached" | "unreached-and-uncovered" | "not-decided";
export function survivorReachOf(attribution, guardEvidence): SurvivorReach
export const REACH_INTERPRETATIONS: Record<SurvivorReach, Interpretation>
```

`ExplainSurvivor` gains `reach` and `reachInterpretation`; the registry joins
`ADMISSIBLE_INTERPRETATIONS`, so the identity, leaf-path, provenance and basis-resolution checks all
cover it by construction. `EXPLAIN_SCHEMA_VERSION` **3 → 4**.

**The shipped prose was the actual bug, and it is fixed.** `GUARD_EVIDENCE_INTERPRETATIONS`'s
`not-observed` no longer ends "It belongs with `no-coverage`" — that is right for `object` and
`all-green` and WRONG for `exact`, and telling every reader to file it with `no-coverage` throws
away the one thing that makes the `exact` case actionable. It now points at `reach`, which decides.

**Row correction: the fixture the row says does not exist DID exist.** `explain.test.ts` already
built `survivorMutant("M0001", "exact", false)` and pinned that the projection emitted both signals
unreconciled — including an exact key-set assertion, which is why this change could not be made
silently. That test is now rewritten to pin the DECIDED behaviour, and its comment (which described
the pair as "a genuine contradiction in evidence... two measurements, two sessions, opposite answers
about the same mutant") is replaced, because that reading is the one this row overturned.

**Red-checked at both branches of the derivation, not at the function:**

- Removing the `attribution === "exact"` branch (so every `not-observed` is `unreached-and-uncovered`)
  reddens two tests.
- Removing the `guardEvidence !== "not-observed"` gate (so `observed`/`not-measured` get a verdict
  they cannot support) reddens the third.

**Still latent, and deliberately so:** zero `not-observed` survivors across all six committed
campaign reports, so every real report projects `reach: "not-decided"` for every survivor today.
This is the field that will be right the first time the pair does occur, rather than a reader
noticing two numbers and guessing.
