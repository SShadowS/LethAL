Found by coord PR-301 (lethal-preproc, 2026-11-21), from GitHub #52. Evidence: `/coord/handoff/PR-301/` (the code reading and
`result.md`). Related: [[R053]], [[R1064]], [[R1061]], [[R164]].

**What happened.** On #52 a missed hang ran to the 180,000 ms budget on a bcdev run with the stop off.
- The transport abandoned its request, the server could not confirm completion, and the tier was quarantined.
- 12 of 17 mutants never ran, and recovery took `clear-quarantine` plus `force-reset-lease`.
- With `--stop-hung-sessions` the same hang scores `timeout-killed`, as the reporter saw on an earlier build.

**Why nobody sees it coming.**
- The product default is off (R1064, owner ruling: the stop ends a session on the user's server, which needs the server
  owner's yes).
- Our servers run with it ON (the setup script writes `stopHungSessions: true`), so no gate exercises the default users
  get, except `itest:hang`'s OFF leg, which proves the quarantine.
- `hang-capable-sites-deployed` ("with --stop-hung-sessions off, such a mutant strands this tier") fires only for sites a
  plug-in operator tags. Built-in operators refuse hang sites instead and never tag one.

**Done in PR-301.**
- The hang screen catches #52's shape.
- The overrun quarantine note and record name the switch when the session ran without it.
- That helps after the fact, not before.

**Options (the owner's ruling).**
- (a) Keep it as it is.
- (b) Default on, with an opt-out. This contradicts R1064's reason.
- (c) **Recommended:** keep it off, but print one warning at the start of every bcdev mutant run without the stop, naming
  the switch and what a hang costs, and add a `lethal doctor` check. Gates run with the stop on, so no gate warning set
  moves. The ripple is one warning code and its `CAVEAT_INTERPRETATIONS` entry if it becomes a caveat.
