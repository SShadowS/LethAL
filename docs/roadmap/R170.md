**This row was filed on a false premise and the correction is the finding.**

As filed (2026-08-20, alongside [[R169]]) it claimed the fixtures follow "two different rules" for
placing the three injected objects, that `gift-card` used a safer pattern than the others, and that
the load-bearing fix was a check refusing selector ids outside the target's own declared `idRanges`.

Checked against the code rather than against the app.json files alone, all three claims are wrong:

- **The check already exists.** `validateSelectorIds` (`packages/schemata/src/id-ranges.ts`) refuses
  an id outside every declared range, refuses two ids that are equal, and refuses an id already
  declared by the target. It runs twice on the `lethal run` path, the first time before
  `resolveEnvToolSession` can provision a billed environment.
- **There is one rule, and it is implemented.** `pickSelectorIds` takes the highest declared range
  and counts DOWN from its top, with the stated reason: the injected objects are LethAL's, not the
  app's, and an app grows upward from the bottom of its range. `lethal init` calls it, so a
  first-time user gets a config that compiles on the first run.
- **All four fixtures match that rule**, including the two the row called inconsistent:

| fixture | highest declared range | rule picks | fixture uses |
| --- | --- | --- | --- |
| `sandbox-app` | 79000-79199 | 79199 / 79198 / 79197 | same |
| `sandbox-data` | 79300-79399 | 79399 / 79398 / 79397 | same |
| `sandbox-hang` | 79400-79449 | 79449 / 79448 / 79447 | same ids |
| `gift-card` | 90197-90199 | 90199 / 90198 / 90197 | same |

`gift-card` is not a different pattern. It declares a dedicated three-id range, which makes that
range the highest, so the same rule lands there. The digit patterns the original report noticed
(`x197-x199` twice, then `79447-79449`, then `90197-90199`) are a consequence of the rule, not
evidence against it.

**What was actually left, and is now done.** The rule lived only in a function doc comment. A user
pointing LethAL at their own app reads `examples/gift-card/README.md`, which could only say "this app
reserves 90197..90199" without naming the practice or mentioning that `lethal init` will choose for
them. Both READMEs now state it.

**One cosmetic residue, deliberately not changed.** `sandbox-hang` assigns the three ROLES in the
opposite order to `pickSelectorIds` (`selectorId: 79447` where the picker would put `79449`). The id
SET is identical and nothing reads the ordering, so renumbering a live gate's fixture to buy symmetry
is not a trade worth making. It is recorded here so the next reader does not re-file it.

**The lesson worth keeping.** The original row compared `app.json` files against each other and
inferred a convention from the numbers. The convention was a function two directories away. A row
that names a missing check should say where it looked for the existing one.
