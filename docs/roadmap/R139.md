LethAL publishes the mutation TARGET on every run and treats publishing the TEST app as the
operator's own workflow. That split is deliberate and documented. What is missing is the check that
makes the split safe.

Measured on 2026-08-13. The tables fixture grew by 11 new tests, both app versions were bumped, and
the target was republished by the run as always. The test app was never republished to the container,
which still held the previous two versions. The gate then reported:

```
expected exactly 1 baseline failure (the TestPage test), got 12
```

naming all 11 new tests plus the one permitted failure. Every downstream figure moved with it:
`killed=113 survived=24 noCoverage=55 baselineGreen=false untargetedTriggers=6`. Of 51 new mutants,
45 that were predicted `killed` came back `no-coverage`, because tests that fail at baseline are
dropped from the green set and mutants covered only by them are recorded `no-coverage` (R55). So a
stale test app silently converts a whole wave of real verdicts into non-findings, and the aggregate
still looks like a plausible result.

The refusal itself worked, and that is worth stating: the baseline assertion caught it rather than
letting the run be recorded. The gap is the DIAGNOSIS. Nothing in the output distinguishes "your test
app is stale" from "your tests are broken". Establishing which took a probe against the container,
replaying the runner's own baseline call, to surface the real message:

```
{"error":"expected exactly one method InsertRunTriggerSetsTheTriggerField, found 0"}
```

That message is conclusive and the runner already receives it. It just never reaches the operator in
a form that names the cause.

What this row asks for, cheapest first:

1. **Name the cause when the message says so.** `found 0` for a test the local source declares means
   the published test app does not contain that test. That is a mechanically detectable condition and
   deserves its own named caveat, the way the TestPage refusal is named, rather than being counted as
   an ordinary baseline failure.
2. **Compare identity, not version strings, before measuring.** The obvious check is to read the
   local test project's `app.json` version and ask the container what it has published. The better one
   is to compare the `PackageId` BC reports for the installed test app against the id of the locally
   built package: a version string is a thing humans forget to bump correctly, so it can match while
   the contents differ, whereas a `PackageId` mismatch is unambiguous and BC already tracks it. Either
   way it costs one read before baseline discovery starts and needs no new deployment step. A mismatch
   is not automatically an error, since an operator may deliberately measure against an older test
   app, but it is always worth printing.
3. Consider whether the doctor preflight should carry check 2, since it exists to report every
   refusal in one pass rather than one per slow retry (R109). Note its standing caveat: it does not
   check baseline test health today, so this would widen its remit.

**CHECK 1 LANDED 2026-08-14 (`16b4014`), and it refuses rather than annotating.** Reading the code
to implement it turned up why this row's own symptom kept recurring: the R31 detector was written
against `NO_RESULT_FOR_METHOD`, which only `bcdev_test_run` produces, while the tables gate runs its
baseline through the fenced RunMutant transport. The store shows what the transport actually recorded
for the missing tests, on both incidents, run 189 and run 195: `RunMutant returned 0 test lines,
expected exactly 1`, outcome `error`. The detector never fired on the path that hit the problem
either time.

What landed:

- The transport stops discarding the server's own `{"error": ...}` text. `RunOneMethod`
  (`RunMethod.Codeunit.al`) and `BuildRunError` (`ControlApi.Codeunit.al`) both answer in that shape
  with no `testResults` key, so a missing method, a DUPLICATE method, a lock timeout on the suite
  tables and a failed suite load all reach the client as the same zero test lines.
- `describeStaleTestApp` therefore matches the SERVER's wording, `, found 0`, which has exactly one
  producing AL code path, and not the client's line count, which has several. Matching the count
  would have produced a confident wrong cause on every transient, and the retry clearing the
  transient would make that wrong cause look confirmed.
- The session REFUSES. A test the server has never seen means the run is measuring a different suite
  from the one the source declares, unlike the R35 and R69 diagnoses, which annotate a test that
  could not run and let an otherwise honest run finish.

**Correcting what this row previously claimed about check 2.** It said the identity comparison
already exists, citing the `itest:envtool` run of 2026-08-13. The code says otherwise:
`env-tool-publisher.ts` learns "already published" by ATTEMPTING the publish and catching BC's
`duplicate package ID` rejection. That is a write-side skip, not a read. On the bcdev path LethAL
never publishes the test app at all, so there is nothing to be rejected, and a real pre-measurement
check needs a server READ (the control app over `NAV App Installed App`, or an MCP call) plus a local
expectation, which today is only `app.json`'s version string unless LethAL starts compiling the test
app it deliberately does not own. So check 2 is more expensive than this row claimed, and check 1
covers the measured symptom on its own.

**It happened a second time in the same plan, on 2026-08-14, which is the strongest argument for
fixing it.** The filter-literal wave (R134) grew the same fixture by seven tests, bumped the test
app to 1.0.0.11, and the container still held 1.0.0.10. The gate refused with
`expected exactly 1 baseline failure (the TestPage test), got 8`, naming all seven new tests, and
all 32 of the wave's new mutants came back `no-coverage` while the 192 pre-existing verdicts stayed
exactly right, so the aggregate again looked like a plausible measurement. Knowing the failure mode
from the first occurrence cut diagnosis from a container probe to one `Get-BcContainerAppInfo` call,
but it still cost a full gate run. A person who has read this row can spot it in a minute; the
product still cannot say it.

A second, related trap surfaced in that fix and belongs here: the test project's `.alpackages` held
a stale BUILD of the target's symbols at the SAME version string (`1.0.0.3`), predating the new
codeunit entirely. Recompiling the target into that cache was required before the test app would
compile. A version-string comparison would not have caught it, which is the second reason this row
prefers package identity over version strings.

The operator-facing rule that carried this row before check 1 landed is now enforced by the product:
**if more than the permitted baseline failures appear and the new tests are among them, check the
container's published test-app version before reading any other number in the report.** A run that
hits the measured shape no longer produces a number to misread.

## CHECK 2 LANDED 2026-08-14 (see commit below), and it compares TEST SETS, not version strings

The row asked for identity rather than a version string and left the cost open. Here is what was
measured and decided.

**The read: the dev endpoint's own `dev/packages`.** `GET
{server}:{port}/{instance}/dev/packages?publisher=&appName=&versionText=` returns the package BC
currently holds — measured against Cronus283, 21,103 bytes, byte-for-byte the app that was
published. It needs no new deployment step, no control-app change and no second credential source:
the same `server`/`serverInstance`/`tenant` and the same `BC_DEV_USER`/`BC_DEV_PASSWORD` the backend
already hands bc-dev-mcp. The three alternatives were rejected on cost or availability:

| candidate | why not |
| --- | --- |
| a control-app procedure over `NAV App Installed App` | costs an `extensions/lethal-control` version bump, a rebuild, a republish to every fixture container, and then every gate requires the new version |
| the Automation API's `extensions` endpoint | measured: `Authentication_InvalidCredentials` on this container with the credentials every other LethAL call uses |
| `bcdev_package_download` (the MCP tool) | writes the package into a project's `.alpackages` as a side effect and demands an `app.json` at that path; the same endpoint, with a footprint |

**The local expectation: the published package's own AL SOURCE, compared test-set to test-set.** The
row's worry about version strings is exactly right, and this run proved it again: the second incident
had a stale BUILD at an unchanged version string, which a version comparison calls healthy. The
package the dev endpoint returns carries `src/`, so the strong comparison is available WITHOUT LethAL
compiling the test app it deliberately does not own — parse the published source with the SAME parser
`discoverTests` uses locally (`testsInAlSource`, split out of discovery for exactly this) and compare
the declared test sets. A package-ID comparison, which the row floated, remains impossible for the
honest reason: there is no local package to have an ID.

**It reports, it does not refuse.** Check 1 owns the refusal, on the server's own words. A second
refusal on a DERIVED signal adds risk without adding safety, and an operator may deliberately measure
an older test app. The warning names every missing test and carries `STALE_TEST_APP_REMEDY`.

**Silence is a requirement.** Three exits are silent by design: a backend that cannot answer at all
(`al-runner` has nothing published; the env-tool path names no dev server and publishes the test app
itself), a test project with no readable `app.json`, and a healthy comparison. Only a genuine failed
READ warns, because a check that fails silently reads exactly like a check that passed.

Evidence, 2026-08-14:

- Healthy, live: published 1.0.0.12 / local 1.0.0.12, 52 published tests against 52 discovered,
  `missingTests: []`, warning **silent**.
- Red-check: one `[Test]` added to the LOCAL source only, versions left EQUAL. The check named
  `Data Tests.NotYetPublishedProbe` — the case a version comparison cannot see, which is the whole
  argument of this row's check-2 paragraph.
- Gates: `itest:tables` 187/31/10 unchanged and silent, `itest:bcdev` 3/10/3 unchanged and silent,
  `itest:alrunner` unchanged (the method is absent there, so the check never runs).
  `itest:envtool` could NOT be run: its environment reports `Stopped`, and LethAL refuses to start an
  environment it does not own. That gate's path is the `undefined` (not-applicable) exit by
  construction, so it is silent by design rather than by measurement.

## Check 3 (fold it into the doctor): RULED OUT, 2026-08-14

The doctor exists to report every refusal in ONE pass instead of one per slow retry (R109). Check 2
already runs before any deployment, on every session, and costs one HTTP GET — the round trip the row
wanted removed is removed. Putting the same read in the doctor would duplicate it, and it would widen
the doctor's remit from "can this run start" to "is the suite the one you think", which immediately
raises why it does not also check baseline greenness — the standing caveat the row itself names. If
the doctor ever grows suite-health checks as a deliberate feature, this belongs in that set; adding it
alone would be a remit change smuggled in as a convenience.
