---
id: "R139"
title: "A stale published TEST app is indistinguishable from genuinely failing tests, and costs a full gate run to diagnose"
section: "product-gaps"
status: "open — measured 2026-08-13 during the R136 trio's first gate run"
order: 405
---

LethAL publishes the mutation TARGET on every run and treats publishing the TEST app as the
operator's own workflow. That split is deliberate and documented. What is missing is the check that
makes the split safe.

Measured on 2026-08-13. The tables fixture grew by 11 new tests, both app versions were bumped, and
the target was republished by the run as always. The test app was never republished to the container,
which still held the previous two versions. The gate then reported:

```
expected exactly 1 baseline failure (the TestPage test), got 12
```

naming all 11 new tests plus the one permitted failure. Every downstream figure moved with it:
`killed=113 survived=24 noCoverage=55 baselineGreen=false untargetedTriggers=6`. Of 51 new mutants,
45 that were predicted `killed` came back `no-coverage`, because tests that fail at baseline are
dropped from the green set and mutants covered only by them are recorded `no-coverage` (R55). So a
stale test app silently converts a whole wave of real verdicts into non-findings, and the aggregate
still looks like a plausible result.

The refusal itself worked, and that is worth stating: the baseline assertion caught it rather than
letting the run be recorded. The gap is the DIAGNOSIS. Nothing in the output distinguishes "your test
app is stale" from "your tests are broken". Establishing which took a probe against the container,
replaying the runner's own baseline call, to surface the real message:

```
{"error":"expected exactly one method InsertRunTriggerSetsTheTriggerField, found 0"}
```

That message is conclusive and the runner already receives it. It just never reaches the operator in
a form that names the cause.

What this row asks for, cheapest first:

1. **Name the cause when the message says so.** `found 0` for a test the local source declares means
   the published test app does not contain that test. That is a mechanically detectable condition and
   deserves its own named caveat, the way the TestPage refusal is named, rather than being counted as
   an ordinary baseline failure.
2. **Compare versions before measuring.** The runner can read the local test project's `app.json`
   version and ask the container what it has published. A mismatch is not necessarily an error, since
   an operator may deliberately measure against an older test app, but it is always worth printing,
   and printing it costs one call.
3. Consider whether the doctor preflight should carry check 2, since it exists to report every
   refusal in one pass rather than one per slow retry (R109). Note its standing caveat: it does not
   check baseline test health today, so this would widen its remit.

Until this closes, the operator-facing rule is the one this run learned: **if more than the permitted
baseline failures appear and the new tests are among them, check the container's published test-app
version before reading any other number in the report.**
