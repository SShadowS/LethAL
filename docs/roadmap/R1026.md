Found by coord PR-14's `itest:alrunner-v3` (lethal-bugs, 2026-11-15, head 671e6190 on `current` edge-5a58a0f16;
`/coord/handoff/PR-14/v3gate.txt`). Related: [[R998]] (added those cases), [[R1010]] (the same cells now fail in the
untouched-handle grid), [[R1019]].

**What happened.** Every leg passes, but the warn fact `serve-keep-reasons` reads `diverged`: `recordref-not-open: MOVED fail
... The record is not open.` (x4) and `gettable-unassigned-variant: MOVED fail ... NavVariant variable not initialized.` R998
judged these five rows refusals only; on edge-5a58a0f16 al-runner runs them and fails them as BC would. The daily update gate
of 2026-11-15 read `matches` because it ran at a LethAL commit before R998's cases (4fcfaa92).

**Why it matters.** A plain trusted fail keeps the daemon anyway (the safe direction, no verdict risk), but the fact now warns on
every candidate, so a real move in another case hides behind it.

**To close.** R998's cases accept a plain trusted fail as R705's http and cascade cases do (the build fixed the refusal), with a
test; the next gate reads `matches`.

**Done (lethal-code, 2026-11-15).** In `packages/runner/src/al-runner-v3-contract.ts`, the four RecordRef cases and the GetTable
case accept a plain trusted fail, but only with BC's error as the build words it (`PLAIN_FAIL_TEXT`: "The record is not open.",
"Microsoft.Dynamics.Nav.Runtime.NavVariant variable not initialized."). The cascade case's `later` moved into the same table. Any
other plain-fail text is still a move, and FieldRef.Class (50681) still accepts only its refusal. A test covers all three, red-checked:
without the message pin, it and R705's "tolerance is narrow" test go red; without the case flag, it goes red.
