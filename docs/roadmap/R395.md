**Filed 2026-10-01 from R387.** R387 made `--server` the default transport of `lethal run --backend
al-runner`. The one-shot transport sends each test its own timeout (`AL_RUNNER_TEST_TIMEOUT_SEC`), so
a hung test is a runner-confirmed timeout and scores `timeout-killed`. The server has no per-test
filter and no per-test deadline: `AlRunnerBackend.ensureServerSuite` sends one `runTests` for the
whole suite under `max(timeoutMs, SERVER_SUITE_MIN_DEADLINE_MS)`, at least 10 minutes
(`packages/runner/src/al-runner-backend.ts`).

**What a hang becomes there, pinned offline.** `packages/runner/tests/cli-al-runner-defaults.test.ts`
("a daemon that never answers runTests ...") drives the default `buildBackend` path against a fake
daemon that never answers: the verdict is `outcome: "error"`, `operation: "pre-dispatch-rejected"`,
with `no summary line within 600000 ms`. So a hung mutant is UNMEASURED, never a kill, which is the
safe direction, but it costs the whole deadline and every test of that activation loses its verdict,
not only the hung one.

**What is not checked.** No live al-runner hang runs anywhere: R164 bars hang-capable sites from
scored gates, and no al-runner hang fixture exists. Whether the real daemon answers, recovers or must
be restarted after a hung `runTests` is unmeasured.

**What would close it:** a per-test deadline in the server protocol (upstream), or a client-side
deadline scaled to the suite plus a daemon restart on expiry, with a hang fixture outside the scored
gates to measure it. Until then it is a stated limit in README.md and
`docs/using-lethal-from-an-agent.md`.
