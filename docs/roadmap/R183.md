## What is wrong

`AlRunnerBackend.capabilities()` returns `authoritative: false`, and its doc comment justifies that
with, among other things:

> there is no BC service tier, so there are no transactions — `Commit()` and `Rollback()` are
> no-ops … (upstream `docs/limitations.md`)

**That sentence is measurably false on al-runner 2.7.0.0.** LethAL's own `remove-commit` operator
deletes a `Commit()` and asks whether any test notices. On the table fixture:

| procedure | bcdev | al-runner 2.7.0.0 |
| --- | --- | --- |
| `Data Commit Ops.CommitThenFail` | killed | **killed** |
| `Data Commit Ops.CommitThenRun` | survived | survived |
| `Data Commit Ops.CommitThenRunValueForm` | killed | **survived** |

If `Commit()` were a no-op, deleting it would change nothing and all three would survive. Instead
`CommitThenFail` is KILLED, by al-runner's own message:

```
NavNCLDialogException: expected the row committed before the error to survive it, but it is gone
```

Removing the `Commit()` made the committed row vanish when the error fired, which is BC's behaviour.
Error-rollback is modelled.

## Why the flag must NOT flip, and why this is still worth filing

`authoritative` stays `false`. `coverage: "none"` is unchanged, the other architectural limits stand,
and one of the three commit mutants really does diverge. Nothing here argues the backend is
authoritative.

**The problem is the same one [[R99]] already had to fix once.** That row found `authoritative: false`
resting on R7, discovered R7 was fixed on v2, and re-decided the flag on new grounds rather than
leaving it "correct by accident". The commit clause is now in exactly that state: it is quoted from
upstream's `docs/limitations.md` as current fact, upstream's doc is behind its own binary, and LethAL
copied it. A justification nobody re-measures is how the last one went stale.

## What the residual actually is, now that it has been measured

Narrower and more specific than "no transactions": only `CommitThenRunValueForm` diverges — [[R72]]'s
arm, `Codeunit.Run` with its **return value consumed**, which is the factor a 2x2x2 on Cronus281
measured as deciding BC's write-transaction refusal. The transaction boundary BC puts around
`Codeunit.Run` in that form is what al-runner does not reproduce.

That is a better sentence for the comment than the one there now, and it is one this repository
measured rather than inherited.

## Work

1. Rewrite the `capabilities()` justification to say what was measured: error-rollback IS modelled;
   the residual is `Codeunit.Run`'s value form, plus `coverage: "none"` and the limits no fixture
   here exercises.
2. Say plainly which claims are INHERITED from upstream docs and unverified by LethAL (permissions,
   company context, base-app data, parallel sessions). Today they read as though LethAL measured
   them; it did not, and it has no arm for any of them.
3. Consider a canary for the commit case, the way R7/R8 have one. The value is the same: this claim
   went stale silently, and a probe that re-measures per session would have said so.

Evidence: `docs/superpowers/specs/2026-08-28-alrunner-bc-parity-probe.md`, where both experiments
were pre-committed before running and this one refuted its own prediction.
