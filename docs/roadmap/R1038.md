`run.codeunit.json`; `bc-check-expected/number-sequence.expected.tsv`). Related: [[R1036]] (about 400 standing sightings under
isolation auto), [[R1037]] (family 6), [[R1031]].

**Why.** #8002's refusal ("an earlier test of this codeunit, <test>, changed number sequence <x> that existed before it: what the
rollback of TestIsolation = Function leaves of it is not measured") stands in about 400 sightings under LethAL's default isolation,
and 1,121 in all (R1036). It asks one question: does a rollback undo a NumberSequence change on BC?

**Built.** A BC-check app, invented and written by hand (two tests per cell and an install codeunit):
- app `51000000-0000-4000-8000-000000051007`, ids 51000-51040;
- `alc` 0 errors and 0 warnings against bc2's System symbols.

An install codeunit seeds eight sequences (seed 100, increment 1). The operations are Next (twice), Restart(500), Delete, Current
(the control) and Insert of a new sequence. Each comes in two variants:
- **SAME:** one codeunit, a changing test then a reading test. This is #8002's case.
- **SPLIT:** a changer codeunit, then a reader codeunit. Under BC's codeunit isolation a rollback falls between them, so this
  variant answers the question. It is also LethAL's BC path, one method per call.

**Measured on al-runner edge-5a58a0f16** (both isolation modes, `expected.tsv`):
- **SAME, isolation "test" (LethAL's mode):** the readers after Next, Restart and Delete are refused (#8002). The new Insert is
  undone per test (exists=No). The control reads 100.
- **SAME, isolation "codeunit":** every change carries to the next test (101, 500, No, Yes).
- **SPLIT, both modes:** every change is undone before the reader codeunit (100, 100, Yes, No). So al-runner treats a sequence
  change as transactional at a codeunit's end.

**Predicted for BC, inferred and not measured.** BC documents number sequences as not transactional, so the SPLIT readers would
read 101, 500, No and Yes. If so:
- al-runner's undo at a codeunit's end is a wrong answer, a new upstream issue;
- #8002's refusal is answerable, since BC keeps the change.

If BC undoes the changes as al-runner does, the refusal is only a missing pin.

**To close:** lethal-bugs' BC run of the app (its standing approval), then the measured answer on #8002, and a regression entry
with BC's answer (measured). If BC keeps the changes, a new issue for the undo at a codeunit's end.
