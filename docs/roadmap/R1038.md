**Why.** #8002's refusal ("an earlier test of this codeunit, <test>, changed number sequence <x> that existed before it: what the
rollback of TestIsolation = Function leaves of it is not measured") stands in about 400 sightings under LethAL's default isolation,
and 1,121 in all (R1036). It asks one question: does a rollback undo a NumberSequence change on BC?

**Built.** A BC-check app, invented and written by hand (two tests per cell, an install codeunit and a guard):
- app `51000000-0000-4000-8000-000000051007`, ids 51000-51040;
- 16 test codeunits holding 21 tests;
- `alc` 0 errors and 0 warnings against bc2's System symbols.

**How it is built.**
- **Install:** resets nine sequences (seed 100, increment 1) and removes the two "new" ones, so each run after a fresh install
  starts from the same state.
- **Operations:** Next (twice), Restart(500), Delete, Current (the control) and Insert of a new sequence.
- **The guard:** every changer also inserts a row into a guard table, and every reader reports whether that row is still there
  (`guardRow`) and the company. `guardRow=No` proves a rollback fell between change and read; `guardRow=Yes` makes the cell void.
- **Two variants per operation:**
  - **SAME:** one codeunit, a changing test then a reading test. This is #8002's case.
  - **SPLIT:** a changer codeunit, then a reader codeunit. Under BC's codeunit isolation (runner 130450) a rollback falls between
    them, so this variant answers the question. It is also LethAL's BC path, one method per call.

**Measured on al-runner edge-5a58a0f16** (both isolation modes, `expected.tsv`):
- **SAME, isolation "test" (LethAL's mode, guardRow=No):** the readers after Next, Restart and Delete are refused (#8002). The new
  Insert is undone per test (exists=No). The control reads 100.
- **SAME, isolation "codeunit" (guardRow=Yes):** every change carries to the next test (101, 500, No, Yes).
- **SPLIT, both modes (guardRow=No):** every change is undone before the reader codeunit (100, 100, Yes, No). So al-runner treats
  a sequence change as transactional: undone at a codeunit's end, and per test under "test".
- **Untouched (51021):** Current reads 100.

**Predicted for BC, inferred and not measured, per operation.** BC documents number sequences as not transactional. As I read it,
that covers the numbers `Next` hands out; Insert, Delete and Restart create, drop or alter a sequence, which BC may undo. So a
mixed result is plausible:
- **Next:** not 100 if kept (101 if the first Next returns the seed), 100 if undone.
- **Restart:** 500 if kept.
- **Delete:** No if kept.
- **Insert:** Yes if kept.

For each operation BC keeps, al-runner's undo is a wrong answer (a new upstream issue), and #8002's refusal is answerable. For each
it undoes, al-runner already gives BC's answer and only lacks the measurement.

**Measured on BC (lethal-bugs, 2026-11-15).** On bc2, BC 28.4 W1 (`/coord/handoff/PR-27/bc-run/result.md`): a fresh install, all
16 codeunits once in id order, through the dev endpoint's default runner (codeunit isolation). That runner gives no per-method start
times; its call runs the codeunits in the order given, and each changer is reported before its reader. The result is **mixed**:

| SPLIT operation | BC | al-runner (both modes) | guardRow | reading |
|---|---|---|---|---|
| Next | 101 | 100 | No | **BC keeps it, al-runner undoes it: a wrong answer, #8152** |
| Restart | 100 | 100 | No | both undo it |
| Delete | exists=Yes | Yes | No | both undo it |
| Insert (new) | exists=No | No | No | both undo it |
| Current (control) | 100 | 100 | No | equal |

- **Untouched:** reads 100 on both.
- **SAME cells:** guardRow=Yes on BC, so void for the question, as designed.
- **So:** the numbers `Next` hands out are not undone by a rollback on BC, as its documentation says, while Restart, Delete and
  Insert are.
- **For #8002:** its refusal of a test after a `Next` is answerable (the sequence keeps its advanced value). For the other three
  operations, al-runner already gives BC's answer.
