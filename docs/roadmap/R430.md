id: "R430"
title: "a test that hands a test-app mock codeunit to another app sits on verify's whole-source fallback"
section: "product-gaps"
status: "open, filed 2026-10-04"
order: 1151
---

**What.** `lethal verify` decides whether a test is old or new by a per-test digest (R-371). When a
test hands a test-app codeunit, or an Interface variable, straight to code in another app, the
test takes the whole-source digest (a hash of every `.al` file; "the fallback"). The reason is
that external code can run the codeunit's procedures, and the walk cannot see which. The result
is safe but coarse: an edit to any `.al` file, however unrelated, makes verify treat these tests
as new and re-run them.

**Evidence.** The R-389 probe (`/coord/handoff/R-389/r389-probe.ts`), run on CDO 5f2a71d on
2026-10-04, over its Test app (`/work/src/do-lethal/Test`, 1,287 tests): 6 tests are on the
fallback today, and the only cause is a test-app mock codeunit passed to another app's code (a
mock HTTP client handed to a `SetHttpClient`-style procedure of the other app). No other test is
on the fallback. Procedure and file names only are recorded here; the source is not quoted (public
repo). The orchestrator ruled on 2026-10-04 that this be filed.

**Why it matters.** Precision of verify, not safety. The fallback is the safe direction. The cost
is wasted re-runs on an unrelated edit, for tests that use mocks, which are often the slowest.

**What would close it.** Fold the mock codeunit's reach instead of falling back: every procedure
and trigger of the codeunit and everything they reach, as `foldImplementation` does today for an
enum's implementation codeunit (`packages/runner/src/testpage-scan.ts`). For an Interface
variable handed out, fold every test-app codeunit that implements the interface (through
`extends`), as R-389 plans for a Variant assigned from an interface.

**Depends on R389.** R389 builds the codeunit fold for a Variant (its plan,
`/coord/handoff/R-389/2026-10-04-R-389-variant-interface-reach.md`, open question 3). This item
reuses that fold and applies it to the direct case. Build it after R389's fold lands.

**Direction: this NARROWS the digest.** R389 only widens (the safe direction). This item moves
tests OFF the fallback, so fewer tests re-run. It must be measured to never drop a real
dependency: on CDO, digest every test before and after, and for each of the 6 tests prove, by
editing code the external code can reach through the mock and by editing code it cannot, that
the digest moves for the first and stays still for the second. Any dependency the fold misses is
a false "old" verdict, so a narrowing that cannot show this stays on the fallback.
