**Measured 2026-10-09 by R546** (`docs/measurements/2026-10-09-r546-alrunner-bc-agreement.md`). It closes
the UNMEASURED case in [[R121]]'s "A limitation this row did not record".

**What.** On one real slice (CDO `CDO Recipient Mgt.`, 51 kills by the same killing tests on both
backends, every verdict equal), `SessionReport.assertionScreen` differs by backend:
- bcdev: 3 of 51 kills flagged, `discrimination: "partial"`;
- al-runner: 51 of 51 flagged, `discrimination: "vacuous"`.

On al-runner every kill's failure text begins with an exception type (`NavNCLDialogException: ` on 48
kills, `NavCSideDuplicateKeyException: ` on 3: M0044, M0045, M0051), where on bcdev the test's own assertion text comes first, so the
prefix rule finds no assertion on any al-runner kill. The al-runner report then says the vacuity "is a
property of the suite's assertion style, not of the mutants", which is a WRONG diagnosis: the same
suite separates kills on bcdev. No verdict moves; the screen is advisory.

**To close.** Strip a leading exception-type prefix on the al-runner path before the rule reads the
text (R101(f) already names `NavNCLDialogException: <message>` as the al-runner shape), or at least
make the `vacuous` note name the backend as a possible cause when the runner is al-runner. Re-measure
on this slice: the al-runner screen should then flag the same 3 kills as bcdev (M0044, M0045, M0051).

## Fixed (R-553, 2026-10-09)

Plan `docs/superpowers/plans/2026-10-09-r553-r552-screen-prefix-and-control-staging.md`, predictions
`docs/superpowers/specs/2026-10-09-r553-r552-precommitment.md`, both committed before the build.

- **The strip.** `screenMessageOf` (`assertion-screen.ts`) is the text R121's rule now reads. On
  al-runner it is `killMessageOf` minus ONE leading `AL_RUNNER_EXCEPTION_PREFIX`
  (`^(?:[A-Za-z_]\w*\.)*[A-Za-z_]\w*Exception: `); on bcdev it is `killMessageOf`, unchanged, whatever
  the text starts with. `killMessageOf`, `looksLikeAssertionFailure` and `looksLikeRunnerRefusal` are
  byte-identical, so `scripts/r121-classify-eval.ts` prints the same output as master (checked byte
  for byte) and the 73-kill corpus test still pins 23 flagged, 6 of 6, 6/23. The stored
  `killingTestFailure` is never rewritten.
- **Keyed on identity.** `BackendCapabilities` gains an optional `kind` (`"bcdev"` or `"al-runner"`),
  set by `BcDevMcpBackend` and `AlRunnerBackend` themselves. The screen strips only when `kind` is
  `"al-runner"`: never on `authoritative` (an al-runner backend made authoritative one day still
  strips) and never on the text (a bcdev text can carry a .NET type name). `SessionReport.backend`
  now prefers `kind` too, falling back to the old inference for events recorded before it. A stream
  recorded before this change carries no `kind`, so replaying it does not strip; a new run does.
  `stream-v1.schema.json` gains the optional property; no `SessionReport` field, no `Caveat`.
- **The note.** A `vacuous` al-runner screen where at least one KILLED kill's text lacked the prefix
  gets `ASSERTION_SCREEN_VACUOUS_AL_RUNNER_NOTE`, which names the backend as a possible cause. A
  `timeout-killed` text does not count (its text is the runner's, not the suite's). When every killed
  text carried the prefix and the screen is still vacuous, the suite really has no `Assert.` text and
  the standard note stays.
- **Not done.** No count of stripped prefixes (it would ripple through events, the fold, the schemas
  and every sample report). A failed `asserterror` (`NavNCLAssertErrorException`) is still not an
  assertion on either backend.

**Offline evidence, shipped code.** Over R546's reports, `screenMessageOf` gives ar-A and ar-B 3 of

and `screenMessageOf === killMessageOf` on every bcdev mutant). Replaying `ar-A.events.ndjson`
