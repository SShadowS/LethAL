**Asked for directly**: "we might want to have an exclude path for folders or files you don't want
to mutate". There was no way to say it. `--only` is an ALLOW-list, so "mutate everything except the
upgrade code" had to be written as an enumeration of every other folder, which on a 553-file project
is not a list anyone maintains.

## Not the thing [[R174]] refused

R174 refused a Stryker-style `ignoreMethods`, and refused it on measurement: 0.38% of raw specs for
the safe pattern set, 1.70% for one that also swallowed 27 live `negate-guard` mutants, against
R13's 5% bar. That is a CALL-SITE ignore list keyed on method names, a new mechanism justified by
how many mutants it removes.

This is path-based scoping, the complement of a filter that already exists, and it is justified by a
caller being able to state their intent at all rather than by a mutant count. Different mechanism,
different argument, and R174's measurement says nothing about it.

## What it does

```text
lethal run --only "src/**" --exclude "src/Upgrade/**" --exclude "src/Generated/**"
```

- Repeatable; patterns union.
- **Subtractive, applied after `--only`**, so the two compose in the order people say them.
- Selects MUTANTS, not sources. An excluded file is still parsed into the project-wide semantic
  context, still compiled and still published, exactly as an `--only`-excluded file is. Excluding a
  file cannot change what a mutant elsewhere resolves to, and a test asserts that directly.

Measured on `fixtures/sandbox-data`: 28 files / 397 sites becomes 15 files / 114 sites under one
pattern.

## Two refusals, and the second is the one worth reading

**A pattern matching no file is refused**, and the reason is sharper than `--only`'s version of the
same rule. A typo'd `--only` selects FEWER files and the report says so; a typo'd `--exclude`
selects MORE, mutating the very files the caller said to leave alone while telling them it did not.
Silence there under-reports, silence here MISREPORTS.

**Excluding everything is refused** rather than reporting a null score, which reads as "nothing to
fix".

## The report had to know, or the flag would be a footgun

`SessionReport.only` exists because "a report that recorded the score but not the narrowing would be
indistinguishable from a full run at the same number". That argument applies harder here: an
exclusion is the narrowing a reader is LEAST likely to remember, because it is the one people set
once and stop thinking about. So `exclude: { patterns, excludedFileCount }` is recorded beside it,
it raises the same `narrowed` caveat, and it makes `reliability` say `narrowed` rather than `full`.

The file counts are kept APART (`excludedByOnly` against `excludedByExclude`) so a run using both
flags can say which flag dropped a file. A reader chasing a missing file needs to know which pattern
to edit.

## What the end-to-end check caught that the unit tests could not

The unit tests passed while `--exclude` did nothing in `--dry-run`, because they call
`generateMutationSet` directly and the dry-run path builds its own call. `printDryRun`'s own doc
comment says a dry run answering "for a wider scope than the one the real run will use" would be
worse than useless, and that is exactly what it did until the flag was threaded through. Worth
recording because the gap was invisible from the tests and obvious from one command.

## Follow-ups not done

- **No config-file key.** The CLI flag is the whole surface. Exclusions are durable per project and
  belong in `lethal.config.json` next to the other project settings; a caller retyping them on every
  invocation will eventually retype them wrong. Worth doing and deliberately not smuggled in here.
- **The counter's NAME.** `excludedByOnly` predates this and now sits beside `excludedByExclude`,
  which reads fine, but the event field it rides was named for one flag when there was one flag.
