**Filed 2026-11-05 from GitHub #46, coord task R-819.** Related: [[R658]].

**What broke.** Since R658, `report.ts` (three places), the console banner and the README told a user whose baseline test
timed out to raise `--baseline-timeout-ms`. The option existed only as `baselineTimeoutMs` in the session config, with no
way to set it. `run`'s strict argument table refused the flag, so the advice could not be followed.

**Fixed by adding the flag,** because the option is real and useful for a slow test: `--baseline-timeout-ms <n>`, a positive
integer, default 120000 (`BASELINE_TIMEOUT_DEFAULT`), on `run`. It is refused with `--dry-run`, which runs no baseline.

**The new risk the flag opens.** The default is safe: 120 s plus the 30 s stop grace is under a hosting gateway's 360 s. A
large value is not: a gateway can cut a hung baseline test's call before LethAL can send its stop (R658), and the run then
quarantines. So a run on bcdev warns `baseline-timeout-over-ceiling` when the timeout plus the grace passes the request
ceiling. It warns; it does not refuse, because a local server has no such gateway.

**Not changed.** `lethal verify` keeps the default, as it keeps the mutant floor's: it has neither flag. A changed timeout does
not change a run's fingerprint, the same as `--mutant-timeout-ms`, so raising it and using `--resume` works.

**Guards** (`r819-issues.test.ts`): every flag `report.ts` tells a user to raise is parsed for real, and the value is checked
at the session config, so a flag that parses and does nothing would fail.
