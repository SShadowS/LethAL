**What was tried.** RUST-01 spiked a native Rust parser (a napi-rs addon, tree-sitter 0.25.10 plus
tree-sitter-al 4.4.1, the same grammar inputs as the WASM path) as a faster replacement for
web-tree-sitter. The pre-commitment fixed a bar before any native timing was read: native median
parseMs (parse plus flatten plus transfer) had to be at most 50% of the WASM baseline's 19,094 ms,
that is at most 9,547 ms, over `U:/Git/BC.History/BaseApp` (9,620 files). Below the bar: stop, and
take R292's TypeScript route instead (release each parse tree once it is used, or a two-pass
census).

**Result: the bar failed, by a wide margin.** Three runs over the same BaseApp corpus gave parseMs
34,515 / 34,541 / 29,122, median **34,515 ms**, against the 9,547 ms bar. Native is about 1.8x
SLOWER than WASM, not 2x faster. Node count matched WASM exactly (31,135,464 on every run), and a
WASM re-run in the same session gave 19,207 ms, close to the 19,094 ms baseline, so the result is
not machine noise. Native peak memory was about 1.9 GB, well under WASM's range on this fixture,
but that did not offset the speed loss.

**Where the time went.** A Rust-only timing with no Node-API layer (`examples/split.rs`, same
corpus) showed tree-sitter's own parse alone taking 21,867 ms, already past WASM's whole 19,094 ms,
before 5,584 ms of flattening. No binding or transfer optimization could have closed that gap; the
parse itself was the slow part. The C grammar was built with MSVC's `cl /O2` through the `cc`
crate. clang was not installed and was never tried; that is the first thing to test if this route
is reopened.

**What did work.** The loader: `bun build --compile` needs a `require` written as a define-keyed
template (variant B) to embed the native `.node` file; one literal `require` per platform (variant
A) fails to build, since Bun treats every literal `require` of an absent file as a hard resolve
error whether or not the branch is taken. Native offsets and columns use UTF-16 code units, the
same convention web-tree-sitter reports, confirmed on a 38-node comparison with 0 differences.

**Kept for context, from the WASM baseline (median of 3, wall s / peak MB):** W1 bench-parse
BaseApp 19,094 ms / 1,148 MB; W2 census BaseApp whole aborts after about 21 s (R292, wasm heap
exhaustion); W3a census BaseApp/Source 161.03 s / 16,151 MB; W4 dry-run Base Application 414.33 s
/ 16,810 MB; W5 dry-run sandbox-data 0.36 s / 307 MB. W3a and W4 are the leading, still unattributed
candidates for an earlier 30 GB memory observation; W4 at 16,810 MB is the stronger lead. W6 (a
real run against Cronus28) never ran: the container's OData and API endpoints rejected the
fixture's credentials with a 401 `Authentication_InvalidCredentials`, and by the time that would
have been fixed the spike had already stopped on the speed bar, so W6 was moot.

**What was validated before the stop.** A whole-BaseApp identity capture (mutant sites, hashes and
identity keys, taken at the spec level since instrumentation itself refuses several corpora, see
R297, R298, R299) matched byte for byte between the WASM pipeline and a from-scratch capture: raw
1,775,337 / deployed 1,687,696 mutant specs, sha256
`a66a270e1530907e2b6c2b468b29f409fcd822b2ee92e02e6827bd083c59621b` of the listing. So the parser
swap itself was sound everywhere it was tested; the spike stopped on speed, not correctness.

**Disposition.** `packages/engine/native/` (the Rust crate) was never committed. It was moved to a
scratch directory for reference and removed from the worktree. Nothing to revert.

**Open decision for the owner.** Either try clang instead of MSVC for the grammar build and
re-measure, or drop the native route and take R292's TypeScript fix instead (release each parse
tree once it is used, or a two-pass census).
