**Found by R-297 Task 7 (2026-09-28)**, handed back unfiled by that task's report; filed here per
that hand-back. Distinct failure class from [[R292]] (widened alongside this filing): R292 is the
parser's web-tree-sitter WASM heap exhausting from retained trees; this is a SEPARATE limit hit only
once that one is bypassed.

**What happens.** With the RUST-01 native-parser capture overlay (a scratch copy that frees each
WASM tree after use instead of retaining every one), `bun cap-locate.ts` over whole
`U:/Git/BC.History/BaseApp` (9,620 source files) completes: 7,106 files located, 7,106 OK, 0 FAIL,
166.5 s wall, 14.7 GB peak. The next step, `bun cap-identity-keys.ts`, which calls
`writeInstrumentedProject`, dies 1,757.6 s in at 13.0 GB:

```
RangeError: Out of memory
    at writeInstrumentedProject (.../schemata/src/project.ts)   JSON.stringify of mutant-manifest.json
```

All 7,108 instrumented AL files (7,106 plus selector objects) were written before the throw; only
the ONE JSON string for `mutant-manifest.json`, built in memory by `JSON.stringify` over every
mutant's manifest row for the whole corpus at once, exhausts memory. RUST-01's own Task 0 report
records the same throw at an earlier commit (`71b8df1`, 2,067 s, 18,008 MB) and worked around it in
scratch with an NDJSON writer (one line per row, never one string for the whole manifest).

**Why it is not R292's mechanism.** R292 is a wasm-heap ceiling on RETAINED PARSE TREES, fixed by
freeing each tree once its facts are read (as the capture overlay already does, and as
`census-operator-sites.ts` does not, still). This throw happens with every tree already freed: it is
JavaScript's/Bun's limit on a single string's size (or the memory to build one), hit by
`JSON.stringify` materializing one manifest string for tens of thousands of mutants across 7,106
files in one call, not by anything to do with parsing.

**Why it matters.** Even after R292's parser-side fix lands, `lethal run`/`lethal campaign` still
cannot write a manifest for a project the size of whole BaseApp: the write step itself needs to hold
the whole serialized manifest in memory at once. Any real project approaching this file/mutant count
hits the same wall, independent of which parser produced the AST.

**What would close it.** Stream the manifest instead of building one string: write
`mutant-manifest.json` (or an NDJSON sibling, matching RUST-01's scratch workaround) incrementally,
one row (or one file's rows) at a time, rather than accumulating every row into one in-memory array
and calling `JSON.stringify` on the whole thing in `writeInstrumentedProject`. Re-run the whole-BaseApp
capture-overlay identity-keys step afterward to confirm it completes.

**Reproduce.** Needs the RUST-01 capture overlay (frees each WASM tree after use) or an equivalent
non-retaining parser; the product parser aborts first via [[R292]]'s mechanism, so this throw is
reached only past that. `bun cap-identity-keys.ts` over `U:/Git/BC.History/BaseApp` from a project
root with every source file the capture overlay locates.

**Closed by RUST-03 S4.1 (2026-09-29).** `writeManifestJson` (`054a9774`) streams the manifest row
by row, byte-identical to `JSON.stringify` for the three manifest fields, and removes any old manifest
before writing (`e1901ccc`). Measured in AMENDMENT 10 of
`docs/superpowers/specs/2026-09-28-rust-03-precommitment.md` (W9): the whole-BaseApp manifest is
written by the product writer in all 3 runs (a patch audit shows the writer byte-identical to product
code), median peak 9,969 MB under the 16,384 MB ceiling, and a streaming JSON parser reads each
1,512,104,535-byte file to the end with 1,687,722 rows equal to deployed. One limit of that
measurement: the harness turns off the reach-grain pass, so its rows carry no `reachGrain`.
