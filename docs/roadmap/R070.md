**The symbol table keys scope on the BARE object name, so a page named after its table silently overwrites the table's variables — and that naming is the standard BC convention.** `buildSymbolTable` (`packages/engine/src/semantic/symbol-table.ts`) calls `globals.set(ownerName, …)` / `procedures.set(ownerName, procs)` with `header.name`, so `table 50000 "CDO Setup"` and `page 50000 "CDO Setup"` share one key and whichever is parsed LAST wins wholesale. Reproduced 2026-07-31 with exactly that pair: `globalsOf("CDO Setup")` returns the PAGE's `Helper: Record Customer` and the table's own `Helper: Integer` is gone; `localsOf("CDO Setup","P")` likewise. **Measured frequency on Continia Document Output Cloud: 13 names shared across kinds, 12 of them page+table** — i.e. the ordinary "card page named after its table" convention, not an edge case. The consumer is `claimsRecordMethod`'s `lookupVar`, and the direction is the DANGEROUS one: a receiver that should be unresolvable (rule 4 refusal) inside the table can resolve through the page's declaration and be CLAIMED, and a receiver that resolves to a DIFFERENT table sends rule 3's shadowing guard at the wrong table. A wrong claim mislabels the mutation and, under §3.2 dedup precedence, deletes the correct Tier-1 mutant at that site. Verdicts themselves stay honestly measured, which is why this is a wrong-CLAIM finding rather than a wrong-verdict one. `objects` is unaffected (both entries are present), so `buildTypeTable`/`buildCallerIndex` do not have this defect. The fix is the one R30 just applied one namespace over — key scope by (kind, name) — and it must not change `resolveObject`, which is already kind-aware. No fixture has a cross-kind name collision, so all four frozen gates are blind to this and a fixture is part of the fix. Found while self-reviewing R30's kind-namespacing.
