---
id: "R279"
title: "GH-24's reach latch may emit a second `var` section when a procedure's var section holds only comments (unmeasured)"
section: "correctness-risks"
order: 979
status: "open"
---

**What.** The reach-marker instrumentation declares a procedure-local latch (`LethALReachLatch:
Boolean`, R246). The code that places that declaration in the schemata compile module looks for
the procedure's `var_section`, takes its `var_body`, and inserts the latch after the last child that
is not a comment. If a `var_body` exists but contains ONLY comments, there is no such child. The
code then falls into the "no var section" branch and writes `var LethALReachLatch: Boolean;` before
`begin`, which would be a second `var` section in the same procedure. The compile would then fail
for the whole artifact.

**Status: reasoned, not measured.** Two things are unknown. First, whether tree-sitter-al produces a
`var_body` for a `var` keyword followed only by comments. When there is no `var_body`, the code falls
back to the section itself and inserts after the `var` keyword, which is fine. Second, whether `alc`
accepts a `var` section with no declarations at all. Found by the fix-round re-review of R246's
latch (GH-24, 2026-09-26) and listed in the GH-24 submit note as a deferred minor, but not filed
until now.

**What would close it.** A schemata unit test that instruments a procedure whose `var` section holds
only a comment, checks the emitted source has exactly one `var`, and compiles it offline with `alc`.
If the case is reachable, anchor the insertion on the `var` keyword instead of the last declaration.

Evidence: the latch placement in `packages/schemata/src/compile.ts` (the `lastDecl` branch), and the
GH-24 submit note's deferred minors (`H:/lethal-coord/tasks/GH-24/submit-note-run001.md`).
