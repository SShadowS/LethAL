**Filed 2026-10-25 by lethal-preproc, from coord task R-790.** Related: [[R586]], [[R769]], [[R780]], [[R734]].

**What.** The v3 backend proves every batch with alc before al-runner runs it (R586 plan §3; R769: al-runner runs some AL
that alc rejects). On D1 at 6aa7700c (`/coord/handoff/final-timing/6aa7700c/timing.md`, D1 #2), deploy is 7.6 s, of
which the alc batch compile is 6.2 s. The baseline takes 2.6 s and the mutant loop 6.1 s, in a wall of 20.8 s. The
owner's idea: run alc at the same time as the tests, and throw the tests' results away if alc rejects. That could
save about 6 s on D1. The gift card's alc takes 0.7 s.

**Constraints found reading the code (2026-10-25).**
- **The error's path.** alc's rejection (`AlcCompileError`) must still come out of `deploy()`: the orchestrator's
  deploy step routes it to R734's redeploy and to bisection, which reads ONLY that error as "subset does not
  compile". If it came out of a later `run()`, it would be scored as a test failure instead.
- **Results are written at once.** The orchestrator writes each baseline and mutant result to the store, and emits
  its events, as soon as the backend returns it (`recordTestResult`, `recordBaselineSnapshot`, `recordMutant`).
  "No result committed before alc joins" therefore means either:
  - (A1) the backend runs work SPECULATIVELY inside `deploy()` while alc compiles, keeps the results private, and
    serves them after alc passes; or
  - (A2) the shared orchestrator buffers every write and event from the deploy to the join. That is the path bcdev
    uses too.
- **alc writes into the test dir.** With `features: ["TranslationFile"]`, real alc writes `Translations/<App>.g.xlf`
  during the compile (R780). An al-runner run that reads the test dir at the same time could read a half-written
  file, and the proof (read after the compile) would not describe what that run read. Any overlap must compile a
  COPY of the test dir, or prove that alc writes nothing there.

**To close.** The orchestrator rules on A1 or A2 (see the coord task). Then build it with red tests per direction,
pass the full v3 gate per mutant, and add a timing receipt from `scripts/v3-timing.ts`.

**Ruling (orchestrator, 2026-10-25): A1.** A2 is a shared-path redesign two days before the talk, so it is the
follow-up below.

**A1, built (lethal/r790).** In serve-entries mode, `deploy()` runs the baseline's one-shot calls
(`speculateBaseline`) while alc proves the batch. That is one call per suite codeunit, at the baseline's stop, with
coverage, exactly as `callCodeunit` makes them inside the baseline bracket. Their raw answers stay private.
- **(a) The error path is unchanged.** `deploy()` still waits for alc. On any alc failure it aborts the calls, waits
  for them, drops them and throws. That covers both `AlcCompileError` and `ArtifactPrepareError`.
  - alc compiles a COPY of the batch (`compileTargetCopy`, `alc-src/`). Its error text is mapped back to the batch's
    own path, with the same class (`errorAsIfIn`).
  - Whatever alc writes into the copy (for example `Translations/*.g.xlf`) is copied back into the batch, so v3 reads
    the bytes it read before R790.
- **(b) Bound to the proved bytes, used once.** The calls are kept only when one key, taken before AND after they
  ran, equals the same key built from the proof. The key covers the batch's `.al` hash, its app.json and its other
  files; the test dir's `.al` hash, other files and app.json; and `<deps>` with sha256. The real paths must match too.
  Each call is served once, inside the baseline bracket, on the lane whose folder is the proved batch, and only to a
  call with the same codeunit, stop and coverage flag. `checkBound` still runs before it is served. Any mismatch, any
  later deploy, or anything thrown later in `deploy()` leaves the baseline live.
- **Not kept, so those calls run live.** All of these ran beside alc's CPU:
  - a call that timed out, or has a timeout row;
  - a call whose spawn failed;
  - a call that exited with a code `callCodeunit` does not read as rows (a crash);
  - a call whose rows do not decode;
  - a call where twice its wall time or any row's duration reaches the mutant budget floor. A budget is
    max(2 x baseline duration, floor), so a kept call's duration can never move a budget. The default floor is
    180 s.
- **(c) No overlap with alc's writes.** The calls are joined BEFORE the test-app compile, the step that may write
  into the test dir (R780). The target compile writes into the copy. Its writes are copied into the batch only after
  it ends, possibly while the calls still run. That is safe only because of the keys: a copy-back changes the "after"
  key or the proof, and then nothing is served.
- **Option 4 (ruling, measured need).** On D1 the target compile writes `Translations/Continia Document Output.g.xlf`
  (4.5 MB) into the batch on EVERY compile. Without a cached copy, the calls always read a batch without it, so they
  are never served.
  - Measured: the file is byte-identical across runs. An strace of a whole D1 run on a157b2d34
    (`/coord/handoff/R-790/strace-d1c/`) shows al-runner opened 6600 `.al` files and no `.xlf`. Option 4 does not
    rely on that: the `.xlf` stays in the key, as in the proof.
  - alc's writes are cached under `<cacheDir>/alc-writes/<key>.json`. The key is the batch's app.json without its
    per-build `version` (the `.al` hash changes every run). At most 16 entries; any problem with an entry is a miss.
    No `.al` file, absolute path, drive, stream or `..` is accepted.
  - They are placed into the batch before the calls, only where the batch holds no such file.
  - After alc: equal bytes keep the placed file (so its mtime, and the keys, are unchanged); different bytes are
    copied over (not served); a placed file alc did not write is removed (not served).
  - A wrong or stale entry only loses the speed-up.
- **(d) Tests** (`al-runner-v3-entries.test.ts`, "R790"), each red with its guard removed:
  - alc passes: the baseline is served from the calls, equal to the sequential baseline;
  - served once;
  - alc rejects: the same `AlcCompileError` text and class, nothing kept;
  - alc cannot start: the same `ArtifactPrepareError`, nothing kept;
  - a byte changes during the calls: live;
  - an `.xlf` the test-app compile writes: live. This one caught that the first key serialised a Map as "{}";
  - a byte changes and changes back before the proof (the "after" check alone): live;
  - a timeout row: live;
  - another stop: not served;
  - alc's writes in the copy reach the batch;
  - a duration the floor would not cover: live;
  - option 4: a cached `.xlf` equal to alc's output is served on the warm run; a differing one is not, and the
    batch holds alc's bytes; a cached file alc does not write is removed, not served.
- **The v3 lane trace is unchanged.** A served call's argv equals the live call's, coverage file name included. The
  speculative calls each take a call number, so later calls' coverage file names shift; harmless.
- **Build reviews (opus, two):**
  - Review 1 found the Map-as-"{}" key, crashed or timed-out calls being kept, and the copy changing what v3 reads.
  - Review 2 found served durations moving budgets and crashed or garbage calls being kept.
  - Both were fixed, each with a test.
  - Not covered by a live leg: v3 now does start on a batch alc then rejects. Leg X (a) still sees 0 spawns,
    because its backend has no budget floor or suite.
- **The copy's cost on D1:** `cp -r` of the whole CDO Cloud project tree (larger than the staged batch) took 0.16 s,
  under the ruling's 0.3 s.

**A2, the follow-up (not built).** Let `deploy()` return before alc joins, run the baseline AND the mutant loop, and
buffer every store write and event until the join; discard and replay today's alc-error path if alc rejects.
- About 6 s off D1 (the alc batch compile overlapping the baseline and the loop), against A1's baseline-only overlap.
- It touches the shared orchestrator path bcdev uses (the deploy step, `recordTestResult`, `recordBaselineSnapshot`,
  `recordMutant`, the events), so it needs BC legs and its own plan review.
