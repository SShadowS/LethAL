**Filed 2026-10-05 from the R-442 plan** (R442: a header-refused file reserves no identity ordinals).
When R-307 refuses a file because its object header cannot be read (`no-header`), that file's mutants
reserve no ordinals, so a same-tuple twin in another file takes the ordinal the refused mutant would
have had. R-442 stops the STORE from carrying such keys (it records the refused file's loose tuples on
the run and drops matching rows when carrying). It does not cover equivalence MARKS.

A person marks a mutant equivalent by copying its `markKey` (shown by `explain`) into the project's
marks file. A mark written from a run that had a header refusal holds the twin's shifted key. Once the
refused file's header becomes readable, the refused file's own mutant takes that ordinal back, and the
mark now names it: the mutant is reported as reader-marked equivalent although nobody looked at it.
The marks file is the user's own, so the store-side fix cannot see or filter it.

**To close.** Make a mark written from such a run detectable: for example a per-mutant flag in the
report (and `explain`) saying its key may shift because a header refusal in the same run shares its
loose tuple, so the mark is refused or warned about when it is used. That is a `SessionReport` field,
with the full ripple CLAUDE.md lists. Pin it with the same Bad/Good sequence as R442, using a mark
instead of a recorded survivor.

**Closed (b6ca43aa, R-443; plan r2.1 and reviews in the coord handoff `R-443`).** Widened from
the header case to every renumbering, since a key alone cannot say which twin it was written for.
A mark now carries its proof, printed by `lethal explain` as each survivor's `mark`: `file`,
`numberingDigest` and `fileSingleton`. R-391's rule (`carryRecord`) is applied to marks in
`applyEquivalenceMarks`:
1. **Same numbering:** the mark's `numberingDigest` equals this run's. The digest
   (`numberingDigestOf`) hashes the numbering OUTPUT, every numbered site with its ordinal, in
   code-unit order. So equal digests mean equal ordinals, whatever the cause (an edit, `--only`,
   `--lines`, a header refusal, the host's collation, R475). The mark matches by key.
2. **A proven singleton:** otherwise, the mark says `fileSingleton: true` and this run has no twin
   of it in that file. The mark matches on (tuple, file). Explain writes `fileSingleton: true`
   only when the (file, tuple) is not one of the run's RECORDED twin sites, and neither its coarse
   tuple nor its file is in the run's `carryHidden` (a twin `--lines` dropped is in neither list
   of numbered sites, but it is in `carryHidden`).
3. **Otherwise** the mark is refused, listed in `readerMarkedEquivalent.refused` with its reason
   (`no-proof`, `no-run-facts`, `renumbered`, `twin-in-file`) and printed in the console. Its
   mutant stays a plain survivor. A key-only mark (every mark written before this) is refused
   `no-proof` (the orchestrator's ruling, option 2). A run without its own numbering facts refuses
   every mark (fail closed).

The report gains the run-level `numberingDigest`, `twinSites` and `carryHidden` (optional, so older
reports still validate), the store a nullable `runs.numbering_digest`, and explain goes to
`explainSchemaVersion` 12. The per-row `readerMark` joins on the matched row (batch and code), not
on the mark's key, which under rule 2 can belong to another row. `lethal verify` skipped a marked
survivor by key too; it now applies the same rule against the SOURCE run's recorded facts.
`fixtures/sandbox-harden/lethal.equivalent.json` is re-marked from a real run of the fixture, and
its unit test also applies the mark through rule 2 alone, so the gate does not depend on the
digest.

Tests are in `packages/runner/tests/r443-marks.test.ts` (each mark is the one explain prints,
pasted through the marks parser): the three original sequences (cross-file, same-file, header);
controls for rule 1, rule 2 and a legacy mark; `--only` both ways and the `--lines` same-file case;
a twin `--lines` dropped and then the marked twin deleted; the per-row join; absent facts; explain
reading the recorded facts; and a reversed file comparator, whose digest must change.

RED-CHECKED (revert, run, restore):
- key-only matching: the three sequences and all of B1 go red, each on the wrong twin;
- never rule 1: the unchanged-source same-file control goes red;
- `fileSingleton` ignored: same-file, header, `--lines` and B2 go red;
- the file ignored in rule 2: cross-file and "marked in full, applied under `--only`" go red (the
  header sequence does not: its mark is not a singleton, because the refusal hid its coarse tuple);
- the source hash as the digest: all three B1 tests go red;
- an input digest (no ordinal in the rows): the reversed-comparator test goes red;
- `fileSingleton` without `carryHidden`: the B2 sequence goes red on the unmarked twin;
- matched key and per-row join by the mark's key: the per-row test goes red (the other twin
  carries the mark).

Residuals, none a renumbering:
- the kind or rename collision R391 names: the tuple holds an object's name, not its kind, so a
  codeunit replaced by a same-named table in the same file can inherit a singleton's mark;
- a statement moved inside its file, or a flipped `#if` arm, inherits the mark of the singleton it
  replaces (R474's class). It is sharper for marks than for carries, because an equivalence reason
  is often about the context around the statement;
- a mark copied between projects matches under rule 2 the way a key-only mark matched before.
