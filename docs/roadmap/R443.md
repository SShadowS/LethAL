**Filed 2026-10-05 from the R-442 plan** (R442: a header-refused file reserves no identity ordinals).
When R-307 refuses a file because its object header cannot be read (`no-header`), that file's mutants
reserve no ordinals, so a same-tuple twin in another file takes the ordinal the refused mutant would
have had. R-442 stops the STORE from carrying such keys (it records the refused file's loose tuples on
the run and drops matching rows when carrying). It does not cover equivalence MARKS.

A person marks a mutant equivalent by copying its `markKey` (shown by `explain`) into the project's
marks file. A mark written from a run that had a header refusal holds the twin's shifted key. Once the
refused file's header becomes readable, the refused file's own mutant takes that ordinal back, and the
mark now names it: the mutant is reported as reader-marked equivalent although nobody looked at it.
The marks file is the user's own, so the store-side fix cannot see or filter it.

**To close.** Make a mark written from such a run detectable: for example a per-mutant flag in the
report (and `explain`) saying its key may shift because a header refusal in the same run shares its
loose tuple, so the mark is refused or warned about when it is used. That is a `SessionReport` field,
with the full ripple CLAUDE.md lists. Pin it with the same Bad/Good sequence as R442, using a mark
instead of a recorded survivor.
