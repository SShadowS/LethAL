**Filed 2026-10-22 by lethal-code**, from R-655's measurement (`/coord/handoff/R-655/measure.md`). Related:
[[R631]], [[R219]].

**What.** `prepareBatchProject` (orchestrator.ts) builds each batch project by copying the `.al` files and then
every other file of the target as a project resource ("nothing is guessed from an extension"). A target folder
that also holds LethAL's own config, such as the fixtures' gitignored `lethal.config.bc1.json` and
`lethal.config.bc3.json`, which carry the server login, has that file copied into every staged batch dir. Seen in
R-655: the v3 itest's staged `active/` trees under `/tmp/lethal-itest-v3-*/` hold copies of both. Nobody read them.

**Why it matters.** It is the user's own secret, copied into temp dirs that may outlive the run (itest scratch,
`--resume` state), and into whatever else reads the batch dir. Measured only for scratch dirs. Not measured:
whether alc packs such a file into the built `.app` (only `resourceFolders` should be packed), and whether any
copy reaches a report or the results store.

**To close.**
- Measure where the copies go: scratch dirs, snapshots, the `.app`, reports.
- Then either leave LethAL's own config files out of the resource copy, by exact name (`lethal.config*.json` and
  `.vscode/launch*.json`, which can hold the same login), or refuse a target folder that holds one, naming the
  file.
- A red test per direction.
- Never read the files' contents while measuring.

**Fixed (3424c3f0).** Measured in `/coord/handoff/R-668/measure.md`: alc packs a file into the `.app` only under a
covering `resourceFolders`, and then the login also lands in the results store's `installed_bundles` row.
- **By name.** `isProjectResource` (orchestrator.ts) drops `lethal.config.json` and `lethal.config.<x>.json` at any
  depth and in any case, so neither the batch copy nor the drift check sees them.
- **By identity.** The run's `--config` file is dropped by device and inode, whatever its name, case or path (a
  symlinked parent dir, a hard link). `runOutputPaths` also names it, so editing it mid-run is not a project change.
- **Warning.** When app.json's `resourceFolders` covers a dropped file, the run warns once per file
  (`lethal-config-resource`): a test that reads it as a resource fails at the baseline, and the user's own build
  still ships it, so take it out of `resourceFolders`. No refusal.
- `.vscode/launch*.json` and `.env` files were already left out by the dot rule (unchanged, pinned).
- Tests: `r668-lethal-config-out-of-batch.test.ts`, the R668 tests in `orchestrator.test.ts`, `compile-only.test.ts`
  and `cli-envtool.test.ts`. End to end with alc: `bun scripts/r668-batch-app-check.ts` (needs `LETHAL_ALC_DIR`).

**What stays behind from runs before this fix.** Only when a `resourceFolders` entry covered a config file, except
the last bullet:
- the latest `installed_bundles` row per group in `lethal.sqlite`, until a newer bundle of that group is published;
- pruned bundle rows, in SQLite's free pages after a prune (no `secure_delete`, no `VACUUM`);
- the resident app on the BC server, until the next publish replaces it;
- scratch dirs of failed or killed runs (`$TMP/lethal-*`, `$TMP/lethal-itest-v3-*`), which hold the copied file
  whether or not `resourceFolders` covered it.

**Advice.** Take the config file out of `resourceFolders`, as the warning says. Then rotate the password. Re-run once, so a clean bundle replaces the stored one and the server's app. Then
`VACUUM` the store. Delete leftover scratch dirs. No migration.
