title: "A carried `killed` lands on an unchanged statement whose surrounding code changed, because the identity key hashes only the statement's subtree"

**Found 2026-10-05 by the adversarial review of R-391's plan** (coord handoff `R-391`, plan r3/r4
reviews), pre-existing and outside R391's scope.

**What.** A mutant's identity key is its statement's subtree hash, object name, member, operator
and twin ordinal (`identityTupleOf`, `serializeKey`). Nothing in it covers the code AROUND the
statement. `--resume` (`carriedVerdictFor`) and `--skip-known-survivors` (`filterHistory`) carry a
recorded verdict onto any mutant with the same key, so after an edit that leaves the statement
itself untouched but changes its context, the old verdict carries.

**The false-kill sequence.** A statement `S` is mutated and recorded `killed` in run 1, which is
interrupted. The user inserts an `exit;` just before `S` (so `S` is now unreachable and its mutant
cannot be killed) and resumes. `S`'s subtree is unchanged, so its key is unchanged, and the
mutant carries `killed` with run 1's `killingTest` without being run. A survived verdict carries the
same way under `--skip-known-survivors` (a mutant that edited context now makes killable is skipped).

`carriedVerdictFor`'s doc comment says "a stale verdict can never attach to edited code"; that
holds for the statement's own text only.

**To close.** Since R391, a run records its generation-time source hash. A cheap tightening: when
the hash changed, carry only for files whose BYTES are unchanged (a per-file hash from the same
source snapshot), and say how many carries that refuses. Measure first how often a resume or a
history carry crosses an edited file in practice.
