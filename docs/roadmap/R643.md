**Filed 2026-10-22 by lethal-preproc during R-585** (orchestrator ruling: accept the cost now, fail closed; file the
cheaper variant, and build it only if resumes turn out to be frequent).

**What.** R-585 makes `carriedVerdictFor` never return a stored `no-coverage` ([[R621]]: a stored no-coverage can be
stale after a source edit between runs, which the resume does not refuse). As a side effect, R192's whole-batch
replay (`replayCarriedBatch`) no longer covers a fully scored batch that holds any no-coverage row. That batch now
takes the ordinary path: deploy, then the baseline (usually from a reused snapshot), then the carry rules.
- Before R-585: such a batch cost nothing on a resume.
- After R-585: one deploy per such batch per resume, estimated at about 40 s on a hosted server (from the R-585 plan;
  not timed live). On real projects most batches hold at least one no-coverage row.

**The cheaper variant (not built).** "Snapshot-confirmed whole carry": before deploying, look up the batch's
reusable baseline snapshot (same batch hash and test app, R192/R389 rules). If that snapshot's coverage leaves EVERY
stored no-coverage mutant of the batch uncovered, replay the batch whole as before, with no deploy. This trusts the
snapshot's coverage exactly as far as R192 already trusts its baseline. If any stored no-coverage mutant is covered
in the snapshot, deploy and re-derive as R-585 does.

**When to build it.** Only if resumes turn out to be frequent enough that the deploys cost more than the risk. Measure
first: count resumes per campaign and time the extra deploys live.

**To close.** Build the variant with a red test per direction: a batch whose snapshot confirms every stored
no-coverage replays whole without a deploy; a batch where the snapshot covers one of them is deployed and re-derived.
Or close by ruling if resumes stay rare.
