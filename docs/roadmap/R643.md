**Filed 2026-10-22 by lethal-preproc during R-585** (orchestrator ruling: accept the cost now, fail closed; file the
cheaper variant, and build it only if resumes turn out to be frequent). **Widened by R-646c** (the same ruling).

**What.** Since R-646c, `--resume` never records a batch from the resumed run without a deploy: R192's whole-batch
replay (`replayCarriedBatch`) is gone. Every fully scored batch takes the ordinary path: deploy, then the baseline
(from a reused snapshot when one matches, otherwise run again), then the carry rules in step 5b.
- R-585 ([[R621]]) had already sent every fully scored batch holding a no-coverage row down that path: a stored
  no-coverage can be stale after a source edit between runs, so it is re-derived.
- R-646c ([[R646]]) sent the rest: a carried survivor must be checked against the tests that cover it in THIS
  session, and the replay ran no baseline to check it against.
- **Cost per fully scored batch per resume:** about 40 s (a deploy, with a reused snapshot), or about 255 s (a deploy
  plus a fresh baseline at R192's measured scale: 40 s + 215 s for 407 tests). The fresh baseline is the usual case
  after a crash on a closed-world server, whose snapshots stay pending (R389, R601). Neither figure is timed live.
- **How many batches it hits, against master before R-646c** (`/coord/handoff/R-646c/allkill.out`, `census.out`,
  `reports.out`): batches that R-646c moved from the replay to a deploy (fully scored, no no-coverage row, no error
  row) are at most 3 of 16 in the committed real-campaign reports and at most 42 of 73 in the local test stores.
- **How often resumes happen:** 1 resume in 82 local runs; 2 of 12 committed reports, both single-batch and interrupted
  mid-batch (no fully scored batch to replay). R192's original measurement was 12 resumes in one hosted session.

**The cheaper variant (not built).** "Snapshot-confirmed whole carry": before deploying, look up the batch's reusable
baseline snapshot (`findBaselineSnapshot`, the same one the ordinary path would reuse). Replay the batch whole with no
deploy only when that snapshot confirms every row: each carried survivor ran against every test covering it there,
each carried kill is covered and not refused there, each stored no-coverage stays uncovered there. The design notes
and the review findings any build must answer are in `/coord/handoff/R-646c/plan.md` (r0 to r2) and
`/coord/handoff/R-646c/review-opus-plan.md`:
- B1: a kill is consistent only if the snapshot still covers it and does not refuse it.
- I2: the backend's coverage refusals are known only after a deploy (and depend on build symbols, which the snapshot key
  does not hold).
- I3: a crashed closed-world run's own snapshots are pending and never reused, so "no snapshot" is common; there the
  ordinary path runs a fresh baseline, which the variant must not skip.

**When to build it.** Only if resumes turn out to be frequent enough that the deploys cost more than the risk. Measure
first: count resumes per campaign and time the extra deploys live.

**To close.** Build the variant with a red test per direction (a confirmed batch replays without a deploy; each
unconfirmed case deploys), and a test that the variant and the ordinary path give the same verdicts per mutant on one
store. Or close by ruling if resumes stay rare.

**Closed by ruling (R-643, 2026-10-24), after a live measurement.** One `itest:lend` on bc1 at master bd240c67, every
log line timestamped (`/coord/handoff/R-643/gate-lend-bc1-timed.log`, `measure-r643.md`):
- R1 and R3, `--resume` runs that carry every mutant (15 carried, 0 grouped calls) and still deploy plus take a
  snapshot-reused baseline, take 3.8 s and 4.0 s per whole session.
- Sessions refused before any deploy (RN3, RN1d, RN2, RN4) take 0.7 to 0.8 s. So a skip saves at most about 3 s per
  fully carried batch on this fixture. A fresh run (L0, 15 grouped calls) takes 6.3 s.
- The 40 s and 255 s figures above stay untimed. A fresh baseline (I3) is a cost the variant must not skip anyway.
- Resumes stay rare (1 in 82 local runs), and I2 means "snapshot-confirmed" cannot be decided before the deploy it
  would skip without new state. So the variant would reopen R-646c's carry path for seconds.
