**Fixed 2026-10-23 by coord task R-435.** The covering loop (`runMutantsOnBackend`) now goes on past a v3 refusal
that follows a timeout. `AlRunnerV3Backend.run` flags such a row with `refusedAfterStop` (an internal
`TestVerdict` field, not a report field) only when a mutant is active and the call's FIRST not-run row is a
timeout that comes before the refused row. The loop keeps the first such refusal as pending and asks the next
covering test. If that test, or a later one, kills (and reproduces), the mutant is `killed` or `timeout-killed`
as usual. If nothing else decides it, the mutant ends `error` with cause `runner-refused` and the same note as
before, never `survived`. A pending `kill-not-reproduced` wins over it; a later error wins over it. A refused row
inside a reproduction or a confirm still ends the mutant. Why it is safe: the rows are cached per codeunit, so the
next test gets the row it would get were it first in the order. A timeout after an earlier non-timeout refusal is
not trusted: see [[R694]].
Tests: "R639: refusedAfterStop" in `al-runner-v3-backend.test.ts` and "R639: the covering loop" in
`orchestrator.test.ts`.

Original item:

**Filed 2026-10-22 by coord task R-637** (side finding S1 of the measure step). This is a cost only, not a
correctness problem.

**What.** A mutant makes test A of a codeunit hang. v3 stops A. Then v3 marks a later test B of the same codeunit
as not trusted: a `notRun` error row, "... an earlier test of this codeunit was refused while it ran (A: ...) ...
this failure is not trusted: ...". That happens when B reads state A could change. If B is the FIRST covering
test LethAL asks about, `AlRunnerV3Backend.run` scores it `error` (`runner-refused`), and that error ends the
mutant. LethAL never asks about A. A's timeout row would have been a confirmed timeout kill, through the R516
confirm and R577. So a detected mutant shows as `error`, and it costs a full stop (at least 180 s by default).

**Measured.** In the R-637 probe (`/coord/handoff/R-637/out/lethal-tests/`), 2 of 2 hang mutants were lost this way:
- the mutants are `lethal.empty-block` and `lethal.return-value` on `R637 Logic.Target`;
- LethAL orders the covering tests by name, so it asked about `AChecksClean` before `ZHangs`;
- the result was 0 killed, 0 timeout-killed and 2 errors.

The measurement is `/coord/handoff/R-637/measure.md` §1c and §3 (S1). It is rare in real suites, because R196 and
the rules after it refuse hang-capable sites. In the kept evidence it never happened, since no call had a timeout.

**To close.** Pre-commit a rule and red-check both directions. The rule: when a not-trusted row names a covering
sibling that timed out in the same call, judge the mutant by that sibling's timeout row, through the existing
position-1 timeout confirm and then R577, instead of ending on the error. Otherwise the mutant stays `error`. The
rows are already cached per call (`rowsByCodeunit`), so it needs no new v3 call. Then run `itest:alrunner-v3` with
every figure unchanged, or with moves that are pre-committed.
