**What.** Found by the opus review of R-872's plan, by reading `verify.ts`; not run. A new test passes fresh, fails under the mutant, passes the unmutated confirm, fails again under the mutant (so the kill is reproduced), then fails its unmutated rerun. Its `newTests` state is `flaky` and verify exits 5. But `results[].verdict` stays `killed` and `counts.killed` counts it: `measuredResultOf` and the results assembly never read the `newTests` state.

**Why it matters.** A reader, or an agent in #10's hardening loop, who reads the counts or the per-survivor verdict without the exit code takes a flaky test as a proven kill. Verify's whole point is a kill a later full run agrees with.

**To close.** A row's verdict is `killed` only when its killing test's state is `stable`; otherwise it reads `error` with a note naming the flaky test, and the count follows. A red test each way: a flaky killer reads `error`, a stable one `killed`. `itest:verify` and `itest:agreement` figures do not move if no gate test is flaky: confirm on the gates.
