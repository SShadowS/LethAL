`REPORT_SCHEMA_VERSION` has been `2` throughout, and the rule it follows (stated on
`EXPLAIN_SCHEMA_VERSION`, which the report copies) is that **additive fields do not require a bump**.
That rule is correct for a READER: a consumer that does not know a field is unaffected by it.

It is not correct for a VALIDATOR, and generating `schemas/report-v2.schema.json` from the type
made that visible. Two fields are REQUIRED by today's `SessionReport` and absent from reports written
earlier under the same version number:

- `declarativeSites` (added by R144)
- `preprocessorSymbols`

So `docs/campaign/2026-08-08-r85-swap-population/rung2.report.json` is a genuine, correct, `v2`
report that the published `v2` schema REJECTS. A consumer validating an archived report meets that
as a false rejection, and the schema is the thing that looks wrong.

**Why this is filed rather than fixed by loosening the schema.** Marking the two optional would make
the schema disagree with the type, which is the drift the generator exists to prevent, and would
also weaken it for the shape the tool actually writes today. The honest fix is one of:

1. **Bump on a required addition.** Narrow the rule: additive OPTIONAL fields are free, additive
   REQUIRED ones are not. Cheap to state, and it makes the version mean "this shape".
2. **Never add a required field**, only optional ones, and let the reader treat absence as the
   default. This is what most long-lived formats end up doing.
3. **Accept it and say so**, keeping the schema as "the shape this build writes" and telling
   consumers that archived reports may lack later-required fields — which is what the schema's own
   description currently does, and what the test pins.

(3) is where it stands today, deliberately, because (1) and (2) are decisions about the format's
future rather than bug fixes. `packages/runner/tests/schemas.test.ts` pins BOTH facts: a report
written by this build validates, and the older one fails with exactly those two paths. If someone
later loosens the schema, the second test reddens and the decision gets made on purpose.

Evidence: `schemas/report-v2.schema.json`, the two tests named above, and
`docs/campaign/2026-08-08-r85-swap-population/rung2.report.json`, which is the file that proves it.

---

**CLOSED 2026-08-19 by taking option (1), narrowed.**

The rule is now: **an added OPTIONAL field is free; an added REQUIRED field is a new shape and
bumps.** Written on `REPORT_SCHEMA_VERSION` itself, where the old wording lived.

**Not fixed by bumping v2 to v3.** That would relabel reports already written and archived as v2,
which is a worse lie than the one it corrects. v2 is recorded as having had two shapes, the schema
describes the shape this build writes, and the rule applies from here.

**Made executable, not written down.** `packages/runner/tests/schemas.test.ts` pins the root
`required` set of every published schema, per FILE rather than per version constant so a new surface
cannot be added without landing in the list. Adding a required field regenerates the schema, which
changes the set, which reddens with the decision named.

Red-checked: adding one required field to `SessionReport` and regenerating fails three tests, the
pin among them. Restored, 14 pass.

The two tests this row already relied on are untouched and still pin both halves: a report from this
build validates, and `rung2.report.json` fails on exactly `$.declarativeSites` and
`$.preprocessorSymbols`.
