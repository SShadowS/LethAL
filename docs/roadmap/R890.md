Found by coord task R-887 (BC.History round 3, BankDeposits, al-runner v3 edge-05d692e5e, demo data and sidecar). Evidence:
`/coord/handoff/R-887/direct/` (`bd-all.txt`, `bd-all-isotest.txt`, `bd-one-isotest.txt`, `bd-explain.txt`). Related: [[R857]] (the
same split between the two backends, for WorkDate), [[R886]] (where the symptoms were first seen), coord task R-882 (the same apps live
on BC).

**What.** LethAL's v3 backend always calls al-runner with `--isolation test` (`v3CallArgv`): the whole test codeunit runs in one
process, and each test's database changes are rolled back after it, but the codeunit's global variables live on. bcdev runs each
test method alone through runner 130450, so every test gets a fresh codeunit and its `Initialize` runs again. Microsoft's suites set
up shared data once per codeunit, behind an `IsInitialized` global (and usually a `Commit`). On v3, the first test sets it up; the
rollback then undoes the data but not the flag, so the later tests skip the setup and find it gone.

**Measured, BankDeposits' 75 tests, al-runner run directly with LethAL's own settings except the isolation:**

| isolation | passed | failed | not run |
|---|---|---|---|
| al-runner's default (codeunit) | 62 | 1 | 12 |
| `--isolation test` (what LethAL passes) | 32 | 6 | 37 |

The second row is exactly LethAL's baseline for this app. Only under it do two symptoms appear:
- 5 tests fail "Bank Deposit Nos. must have a value in Sales & Receivables Setup" (the setup the first test made, rolled back);
- 23 tests are refused, by cascade, with al-runner's "an earlier test of this codeunit ... changed an isolated storage key or a number
  sequence that existed before it: what the rollback of TestIsolation = Function leaves of it is not measured".

These were first taken for al-runner findings. They are LethAL's, and nothing goes upstream.

**A second app, ServiceDeclaration (61 tests, same setup, `/coord/handoff/R-887/direct/sd-*.txt`):** codeunit isolation 43 passed /
3 failed / 15 not run; `--isolation test` 5 / 36 / 20, of which 29 fail "The Service Declaration Setup does not exist" (none under
codeunit isolation). The same mechanism: the setup one test makes is rolled back for the next. The not-run rows in both modes are
mostly al-runner's permission refusal (aldevtools #7524), which is independent of this item.

**Not settled: which mode matches BC.** One of the five, run ALONE (`--test-exact`, `--run-selected-only`) under `--isolation test`,
still fails, now with "The following UI handlers were not executed: GeneralJournalBatchesPageHandler". Run alone under codeunit
isolation, it passes. So "run each test alone" (`--isolate-tests`, R857) is not shown to be the fix either. What BC does for these
tests, through bcdev's one-method runner, is not measured here.

**What it costs.** On BankDeposits, 30 of 75 baseline tests are lost on v3 (5 failed and 25 refused, set against the codeunit-isolation
run), and every mutant only they cover becomes `no-coverage`. Any suite with once-per-codeunit setup is exposed. That is the common
shape in Microsoft's test apps.

**To close.**
1. The live BC run of the same three apps (coord task R-882): per test, BankDeposits' baseline through bcdev, against the two v3
   modes above, and `--isolate-tests`. That decides which v3 mode matches BC.
2. Then make v3's default that mode, or refuse by name where none matches; pre-commit the moved v3 gate figures first.
3. Re-run BankDeposits on v3 and compare per test with the BC run.

**Landed (coord task R-890): `alRunnerV3.isolation: "method"`, opt-in.** Every test alone (as R857's `--isolate-tests`) under
al-runner's codeunit isolation, so a fresh codeunit per test, as BC's one-method runner. Both transports (`--isolation codeunit`
one-shot, `testIsolation: "codeunit"` serve). The default and every gate stay `"test"`, explicitly. The mode is in the run's lending
build (`isolation-method`) and in the resume fingerprint, so a run in one mode never lends to or resumes from the other.

**Measured against BC (R-882 on `bc5`; evidence `/coord/handoff/R-890/findings.md`, round 2).** BankDeposits cannot be measured on BC
(every test reaches a `TestPage`), so the BC side is the other two apps, with demo data and the sidecar on v3:

| app | v3 `test` agrees with BC | v3 `method` agrees with BC | what `method` still differs on |
|---|---|---|---|
| ServiceDeclaration (61 tests) | 9 | 34 | al-runner permission refusals 14, [[R895]] (GUI branch) 8, TestPage on BC 4, BC `NotSupportedException` 1 |
| PaymentPractices (36 tests) | 31 | 32 | [[R895]] 3, TestPage on BC 1 |

Per mutant: of R-882's 7 PaymentPractices mutants that v3 left alive and BC killed, `method` kills all 7 with BC's own killing tests;
`test` kills 2. Every difference `method` leaves has another named cause: this item's class is gone under it. Cost: +17% wall on
PaymentPractices' narrowed run; on the BankDeposits sample, median per mutant 19 s against 268 s (about 14x).

**Still open: the default** (step 2). `method` is what BC does, at a cost that depends on the suite. Switching moves v3 gate figures,
so it needs a pre-commitment and a ruling.
