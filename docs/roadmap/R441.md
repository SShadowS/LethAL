**Found 2026-10-05 by the post-merge gpt-6.1-sol review of R-385** (`/coord/reviews/R-385-001/sol-postmerge.md`).
R433 and R438 made `fetchApiRows` in `packages/runner/src/harness.ts` refuse an automation-API
request that names `extensions` without exactly one app-id filter, because the unfiltered list hung
BC 28.4 and took Cronus28 down. The check reads the path and query text after percent-decoding, but
it does not remove raw tab, CR or LF characters. A path such as `…/companies(<id>)/exten<TAB>sions`
with no filter passes the check; native `fetch`'s URL parser then strips the tab, so the server
receives `/extensions` with no `$filter`, the request that hangs BC.

Only code inside `harness.ts` can send it, because the source scan
(`scripts/automation-api-guard.test.ts`) exempts that file and reports the automation API text
anywhere else. No code sends it today.

**To close.** Apply the refusal to the URL `fetch` will actually send (build it with `new URL(...)`
and check its normalised path and query), in the one place the request is sent, rather than to the
raw text. One zero-fetch test with a tab, one with CR/LF, red-checked by checking the raw text again.

**Closed 2026-10-05 (R-441).** `fetchApiRows` now builds the URL with `new URL(...)`, runs the same
refusal on its normalised path and query (the `tenant` parameter excluded, since it comes from
config), and sends exactly that parsed URL, so what is checked is what is sent. The raw-text check
still runs first. A tab and CR/LF inside `extensions` are refused with zero fetches; with the new check
removed both go red. The allowed GUID URL and the companies calls are byte-identical to before.
