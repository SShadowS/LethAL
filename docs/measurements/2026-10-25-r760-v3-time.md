# R760: where al-runner-v3's time goes (measured 2026-10-25, lethal-preproc)

Coord task R-760, from an owner request. Measurement only: nothing was changed. The binary was al-runner
3.0.0-alpha.5+edge.20261024 (dcdf9e821), the pinned `current`, on master b39ee555. No BC server was used. Raw
evidence is in `/coord/handoff/R-760/` (scripts `run.sh`, `d1.sh` and `replay.sh`; per-run stdout, stderr, reports,
events, process logs, strace logs and replay outputs). One opus review checked every figure against the raw files,
and its corrections are applied here.

**Method.**
- Every process LethAL spawned was recorded two ways:
  - `strace -f -ttt -s 1024 -e trace=execve,exit_group`, for COUNTS and full argv only. Its timings are not used:
    under ptrace the .NET processes ran about 10 times slower (the gift-card session took 100 s traced, against 10 s
    untraced).
  - A `/proc` poller sampling every 25 ms, for timings at almost no overhead (`procpoll.ts`). It misses only
    processes shorter than 25 ms.
- One al-runner call was split with the binary's own `--timings`, replayed hot with LethAL's exact argv against a
  copy of the run's scratch. Caveat: the replay used al-runner's default cache (`~/.cache/al-runtime`), not the
  gate's `ALRUNNER_CACHE`, so its first replay was cold (24.96 s). The real run had no cold call: its first mutant
  call took 3.9 s.

**A caveat on absolute figures.** Today's D1 is 1.4-2.3 times slower than R-653's on the same slice, with a different
edge build (`/coord/handoff/R-653/live/final/results.md`):

| D1 | R-653 | today |
|---|---|---|
| one-shot | 462 s | 667 s |
| serve | 85 s | 193 s |
| serve mutant loop | 57 s | 151 s |
| `assertBound` per check | 0.16 s | 0.35 s |

`assertBound` is LethAL's own file hashing and it doubled too, so container or disk speed today is the likelier cause.
No other heavy job held a slot, but the machine's other load was not measured. Proportions are more trustworthy than
seconds.

## The answer
The tests themselves take milliseconds, as expected: **0.01 s for the gift card's 8 tests, 0.03 s for D1's 21 per
call.** The time goes to the NUMBER of cold one-shot al-runner calls times what each call does besides testing:
- recompiling the instrumented project;
- reading the dependency compile cache;
- writing coverage;

plus LethAL's own work between calls.

## D1 (the CDO slice, 63 mutants, 555 instrumented files, 17 dependency apps)

| | one-shot (default) | serve-entries |
|---|---|---|
| wall (itest leg) | 667.4 s | 192.7 s |
| LethAL's al-runner calls | 166 `test` calls with coverage (1 baseline + 165 in the mutant phase; median 3.34 s, total 564.5 s), plus the contract probe's 17 | 1 `serve` daemon (151.5 s), plus 18 `test` calls (11.4 s; they include the 3.55 s baseline and two 3.1 s hang probes) |
| alc (`dotnet`) | batch compile 12.7 s, test app 6.5 s, plus the probe's two (0.7 s and 0.9 s) | 16.3 s |
| verdicts vs bcdev | 51 / 12 / 0, 0 differences | 51 / 12 / 0, 0 differences |

**Where one-shot's 667.2 s goes:**
- 43.9 s before the first mutant call: the contract probe about 9.9 s, alc about 20.8 s, plus generate, deploy and
  the baseline;
- 564.5 s inside the 166 calls;
- 58.9 s in the gaps between consecutive mutant-phase calls (median 363 ms over 165 gaps).

The gaps match serve's measured `assertBound` cost (0.35 s per check), and the backend checks once per send.

**One hot D1 call** (`d1.*.err`, `--timings`): 3.73 s in all.
- Project compile: about 1.8 s (load 0.11, check workspace 0.28, check rest 0.16, lower 1.21, engine 0.05).
- Reading the 15-layer dependency compile cache: about 0.95 s ("hit, opened in 0.06 s", "reading the blocks
  0.90-0.94 s").
- Tests: 0.03 s.
- Coverage: about 0.8 s (28663 statements). Without `--coverage-json` the call is about 2.9 s (3.24 / 2.84 / 2.92).
- `--isolation codeunit` costs the same (3.75 / 3.50 / 3.64 s).

The project is NOT identical across calls: `activate()` writes a new selector `.al` for each mutant. So a whole-source
compile cache would miss on every mutant's first call.

**Why 166 calls for 63 mutants:** 1 baseline, plus one call per mutant (63), plus two per kill (2 × 51 = 102): the
unmutated confirm and R577's reproduction. Code: `al-runner-v3-backend.ts`, R577 `killsMustReproduce` and R653. So
61% of the calls are confirms and reproductions.

**Inside serve's mutant loop** (151.3 s, the gate's own split):
- coverage windows: 38.0 s;
- echo requests: 37.5 s (74);
- live runs: 37.4 s (51);
- `assertBound`: 31.1 s (90 checks, about 0.35 s each);
- warm-up and prefetch: 6.8 s.

**One-shot timeline** (poller, `poll1.procs.jsonl`):
- 0-0.3 s: bun start-up;
- 0.3-8.9 s: the contract probe (R586), about 8.6 s or 45% of the wall time. It is dominated by two deliberate 3 s
  `--test-timeout-secs` hang probes, and includes the probe's two alc compiles;
- then alc's batch and test-app compiles;
- then 118 coverage calls (1 baseline + 49 + 2 × 34) of 26-80 ms each.

**One hot gift-card call:** 0.08 s (compile 0.03 s, run 0.01 s). Without coverage it is 0.04 s.

## Ranked: where D1's one-shot 667 s goes
Shares of the 564.5 s inside the calls, scaled from the hot replay's proportions:

1. **Recompiling the instrumented project on every call:** about **270 s (≈ 41% of the wall)**.
2. **Reading the dependency compile cache on every call** (0.95 s): about **140 s (≈ 21%)**. serve keeps it
   resident.
3. **Coverage on every call:** about **120-135 s (≈ 19%)**.
4. **LethAL's own work between calls** (very likely `assertBound` re-hashing per send): **58.9 s (≈ 9%)**.
5. **alc proof compiles (#5602) at deploy:** batch 12.7 s + test app 6.5 s = **19.2 s (≈ 3%)**. The alc-per-batch
   hypothesis is refuted as a major cost.
6. **The contract probe:** about **10 s** on D1 (1.5%); on the gift card about 8.6 s, **45%** of its 19.2 s.
7. **The tests themselves:** about 0.03 s × 166 ≈ **5 s (< 1%)**.

The call COUNT multiplies 1-4: 102 of 166 calls are confirms and reproductions.

## The changes that would cut most (NOT built; for a ruling)
- **A. serve-entries as the campaign default.** It exists (R635/R652/R653), compiles and reads the dependency cache
  once per daemon, and measured 0 differences on D1 here and in R-653.
  - D1: 667 → 193 s (−71% today; R-653 measured −82%). Gift card: 19.2 → 12.8 s.
  - Blockers to name: R722 (upstream #5798, dotted test names refused under entries), and the MO and WR legs, which
    are one-shot by pre-commitment.
- **B. One-shot: answer the per-kill confirm and reproduction more cheaply,** for example both in one process, or the
  confirm from rows already held. About 51 × (3.4 s + 0.36 s gap) ≈ **190 s**. It touches R577's guarantee, so it
  needs a ruling and a review.
- **C. LethAL: cache `assertBound`'s file hashes by size and mtime between checks.** About **55 s** on one-shot and
  about 30 s on serve.
- **D. Upstream, for one-shot users:**
  - keep or memory-map the dependency cache cheaper (0.95 s per call);
  - compile the workspace per object, incrementally, so a one-file change (the selector) does not recompile all 555
    files.

  A whole-source cache would hit only on repeats (the confirms, about 102 calls, saving about 1.8 s each ≈ 185 s).
  Minimal invented repro (not filed): a test app and a 500-file target. Run `al-runner test --timings`, change ONE
  small file, and run again. The second run still reports a full compile (≈ 1.8 s) plus the dependency read (≈ 0.9 s),
  while the tests take ≈ 0.03 s.
- **Coverage cannot simply be dropped.** Every call needs raw coverage for the §6 Sleep-index check, whatever the
  coverage mode; the check reads coverage for passing rows under a mutant and for the baseline. Skipping it on the
  51 confirms (about 40 s) needs a code check first, because one-shot's `isBaselineCall()` also covers confirms.

Each figure above is from one or two runs on this container. They are not a gate.
