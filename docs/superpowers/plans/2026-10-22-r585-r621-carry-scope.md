## R585: history lends only from a run whose test set holds this session's

**Record.** Add a new column `runs.test_scope TEXT`: a JSON sorted array of the qualified test names
the session sends at baseline (`tests` after discovery, `--tests-only` and R-236c's refusals). Write it
in `createRun`. Migrate it as NULL on old rows. Read it in `getRun`. Copy it in `seedRunFrom`.

**Why names, not patterns.** Comparing glob sets is hard, so a pattern rule would have to be
"equal, or none on the source". Names catch every way a suite can narrow, not only `--tests-only`:
R403's test symbols and arm policy, discovery markers, refused tests. The compare is a subset check,
the same rule snapshot reuse already applies (R-236c). Size is about one name per test per run, which
is less than the `test_results` baseline rows a run already writes.

**Rule.** A run lends history only when every test this session sends is in the run's `test_scope`.
- Equal sets lend.
- A wider source set lends.
- Anything else is refused: a narrower set, a disjoint set, or NULL.
- Names are compared only after the test-app check passed, so they mean the same tests.

**Old runs (NULL): refuse.** A pre-fix run may be a `--tests-only` run, and the store cannot tell.
Reading NULL as "full suite" would lend exactly the false survivors this item is about. The cost is one
full re-run after the upgrade. That is the same choice R442 made for `carry_hidden` NULL.

**Where.** It is a history site check in `priorSurvivorKeys`' `siteChecks`, so it sits after
`runMayLend` step 1 and before steps 2 and 3. Inside the site checks the order becomes: scheme,
coverage mode, test app, **test scope** (new), symbols, carry_hidden, hidden files. A new
`on.testScopeChanged` hook leads to a warning with code `history-test-scope-changed`:
`[lethal] --skip-known-survivors: the latest finished run, run N, <did not run K of this session's
tests (e.g. A, B) | recorded no test scope (before R585)>; a survivor there may be killed by one of
them, so none is skipped: every mutant is executed (R585).`

**Other sites need no change.** `--resume` and `--resume-run` already refuse a scope change through
the fingerprint (proven). Snapshot reuse already checks a subset.

## R621: a stored no-coverage is never carried; it is always re-derived

**Rule.** `carriedVerdictFor` returns `undefined` for a stored `no-coverage`. This generalises R318's
`coverageArmNames` exception, which then goes away. The two paths then behave like this:
- Partial path (`scoreBatch`): a mutant uncovered now is still recorded fresh as no-coverage (step 5).
  A mutant covered now is RUN, not carried.
- Whole path: `batchCarriesEntirely` is false for a batch holding a stored no-coverage, so the batch
  takes the ordinary path: deploy, then baseline (or a reused snapshot), then the partial rules. So
  `replayCarriedBatch` never sees a no-coverage, and it needs no coverage of its own.
- The index (`CARRYABLE_VERDICTS`, `carryable` count, the `resume-reusing-run` text) stays unchanged.
  Removing `no-coverage` there would count those rows as 'error' rows in the warning, which is wrong.

**Result.** "Carry only when uncovered now" and "always re-derive" give the same verdict. When the
mutant is uncovered now, re-deriving is the carry, just not flagged `carried`. So the simplest rule
is exact.

**Cost (the trade-off to rule on).** R192's whole-batch skip is lost for every fully scored batch that
holds a no-coverage row. On real projects that is most batches.
- Today: such a batch costs nothing.
- After the fix: such a batch costs one deploy per resume (about 40 s hosted). The baseline is
  usually still saved, because the prior run's snapshot for the same batch hash and test app is
  reused.
- A batch with no no-coverage row still replays whole, as today.
- Upgrade, NOT in this item: "snapshot-confirmed whole carry". Before deploying, look up the batch's
  reusable snapshot. If its coverage leaves every stored no-coverage uncovered, replay the batch
  whole. That trusts the snapshot's coverage as far as R192 already trusts its baseline. It is worth
  doing only if the owner wants the deploy back. Ask, and file it if yes.
