# C02-09: Gap ids in `lethal explain` and `lethal verify`, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Revision 2 (2026-09-26),** after review round 1 (`H:/lethal-coord/reviews/C02-09-plan/review-r1.md`) and the owner's answers. All six questions are decided. The gap id now hashes the block's TEXT as well as its position, so a stale id fails as `unknown-gap`. No-coverage blocks are listed separately. Every gap names the artifact to verify it against. `unobservedBlock` is scoped to the recorded rows and withheld on runs that drop mutants inside a block. See "Review responses" at the end.

**Goal:** `lethal explain` groups survivors into gaps (one per innermost branch body) and gives each a gap id and an artifact id, and `lethal verify` accepts a gap id and expands it to that gap's survivors, so one call proves one gap closed.

**Architecture:** The gap id is a SITE property, computed once, when the manifest is written (`packages/schemata`), and carried to the report row like `procedureStartLine` (C02-01, `fd72825`). `explain` copies it and groups rows by it; `verify` reads it from the installed artifact's manifest and groups store rows by it. Both group through one shared pure function (`packages/runner/src/gaps.ts`), so the two commands cannot disagree about which survivors a gap holds.

**Tech Stack:** Bun + TypeScript, tree-sitter-al (engine), `node:crypto` sha256, bun:sqlite store, hand-written JSON Schemas under `schemas/`.

**Spec:** the owner's comment on issue #11, point 1 ("Group into gaps, not survivors ... Group by enclosing branch/block, and mark a block where *every* mutant survived as `unobserved-block`"), issue #16 requirement 3 ("Take gap ids as well as mutant ids ... so one call proves one gap closed"), and the owner's answers below. ## Decisions (all six decided, 2026-09-26)

### Q1: DECIDED. Grain: the innermost branch body. Id: file path + block position + block TEXT (owner)

- **Grain** (default kept): a mutant's gap is the innermost branch body that contains it: the `then` or `else` of an `if`, a `case` arm, a loop body, or else the procedure or trigger body. A mutant on an `if`'s CONDITION belongs to the block that holds the `if`, not to either branch, because the condition runs whether or not a branch is taken.
- **Id** (owner): the hash covers the relative file path, the block's start and end offsets, AND the block's source text. Any edit to the block's text gives a new id, so an id copied before the edit fails as `unknown-gap` rather than naming the edited block. An edit that only moves the block (text above it changes) also gives a new id, and so does a CRLF versus LF checkout (the offsets and the text both differ). Both are documented as limits, not fixed.

### Q2: DECIDED. Members are survivors only; no-coverage blocks are reported separately (owner)

A gap's members are its `survived` rows, the set `explain` lists as `survivors`. A block's no-coverage mutants are never gap members. `explain` lists them in a separate `noCoverageBlocks[]`, grouped by the same block, with no gap id (so nothing invites passing them to verify as a gap). `verify --survivors <gapId>` runs exactly the gap's survivors; a block with only no-coverage mutants has no gap, and its id refuses as `gap-has-no-survivor`.

### Q3: DECIDED. `--survivors` accepts gap ids, recognised by the `G` prefix (owner)

`--survivors G3f9a1c2b7d10,0/M0004`. No new flag, so no `FLAG_OWNERS`, help-section or ownership-test change.

### Q4: DECIDED. Two new refusal reasons; `VERIFY_SCHEMA_VERSION` 2; v1 kept as published (default kept)

`unknown-gap` and `gap-has-no-survivor` are added, so `VERIFY_REFUSALS` grows from 23 to 25. `schemas/README.md`'s rule (a value domain that changes in either direction bumps) then requires `VERIFY_SCHEMA_VERSION` 2 and a new `schemas/verify-v2.schema.json`; `verify-v1.schema.json` stays as published. Reusing `unknown-mutant` or `not-a-survivor` for gaps was rejected: it would change what those values mean, which the same rule says also bumps.

### Q5: DECIDED. #11 points 3 to 6 are not in this task (default kept)

C02-09 builds point 1 (grouping and `unobserved-block`) and #16 requirement 3. Points 3 (covering tests with `file:line`, ranked), 4 (a suggested fix kind per gap), 5 (mutant ranges marked inside the source span) and 6 (the exact verify command per gap) are filed as roadmap items in Task 9. Point 4 needs a ruling of its own: `explain.ts`'s admissibility rule says the projection never says what test to write, and `strengthen-assertion` / `new-case` / `new-test` are exactly that.

### Q6: DECIDED. `--top` caps `survivors` only; `gaps` and `noCoverageBlocks` are always complete (default kept)

A gap is small (ids and counts, no source text), and its point is to replace 151 rows with about 10. Because `--top` can drop every survivor row of a gap, each gap carries its own artifact provenance (see "What `explain` emits").

## Definitions (the contract this plan builds)

### What a gap is

- **Gap block.** For a mutant whose replaced node is `N`: walk from `N` up through its ancestors, `N` itself included. The gap block is the first node that is EITHER (a) in a branch slot, meaning its `<parent rawKind>.<field name>` is one of the pairs in engine's `SINGLE_STATEMENT_SLOTS` (`if_statement.then_branch`, `if_statement.else_branch`, `case_branch.body`, `while_statement.body`, `for_statement.body`, `foreach_statement.body`), whether it is a single statement or a `begin ... end` block; OR (b) a `repeat` body or a `case ... else` body (both wrap their statements in a `statement_block`, so they are not in `SINGLE_STATEMENT_SLOTS`; Task 1 reads the exact kinds off the parser); OR (c) the body block of a `procedure` or `trigger`. If none matches, the gap block is the outermost ancestor (the file's root). It is never absent.
- **Gap id.** `"G"` followed by the first 12 lowercase hex characters of `sha256(<file with every \ turned into /> + "\n" + <block startIndex> + "\n" + <block endIndex> + "\n" + <block source text>)`. Example: `G3f9a1c2b7d10`. `file` is the manifest's `file` (a path relative to the project, as the report prints it). The block text is the raw source slice `source.slice(startIndex, endIndex)`, never the clipped `originalText`.
- **Block lines.** `blockStartLine` and `blockEndLine`, 1-based, from the same `lineOfIndex` as `startLine` and `procedureStartLine`.
- **Members.** The gap's rows whose verdict is `survived` (Q2).
- **Counts.** Over every RECORDED row with that gap id: `survived`, `killed` (`killed` + `timeout-killed`), `noCoverage`, `other` (`error`, `known-survivor`).
- **`unobservedBlock`.** `true` exactly when every RECORDED row of the block survived: `killed === 0 && noCoverage === 0 && other === 0`. It speaks about the rows the run recorded, never about mutants the run did not generate. It is WITHHELD (absent, meaning "not decided") when the report carries the `operator-narrowed` or `line-narrowed` caveat, because those two drop mutants INSIDE a block, so a block can record one survivor while its killed neighbour was never run. It is kept under `narrowed` (`--only`/`--exclude` select whole files, so a block is wholly in or wholly out) and `tests-narrowed` (every mutant of the block is still recorded; that caveat already qualifies every verdict of the run). It is the #11 comment's `unobserved-block`, as a boolean rather than a new enum (see "Versions").
- **Batch.** Batches split at FILE granularity (`planArtifacts`, `orchestrator.ts`), so every row of a gap shares one `batchIndex`. `explain` refuses a report where they do not.

### Stability

| Question | Answer |
|---|---|
| Same report, two `explain` calls | Same ids. `explain` copies them from the report. |
| Two runs of the same source and config | Same ids. The hash reads only the file path, the block's offsets and its text. It does not read mutant ids, batch numbers, `--max-guards-per-batch`, `--only` or run order. |
| `--resume` | Same ids. A resumed run re-instruments, and a carried row is built from the resuming run's manifest entry (`o.mutant`), so it carries the current gap id. Verify refuses a carried member with the existing `carried` reason. |
| An edit to the block's text | New id. The old id refuses as `unknown-gap` against an artifact built from the edited source (owner, Q1). Against the SAME installed artifact the edit refuses first as `source-changed`. |
| An edit that only moves the block | New id, same reasons. A limit, documented. |
| CRLF vs LF checkout of the same commit | DIFFERENT ids (offsets and text differ). `startIndex` has the same limit. Documented, not fixed. |
| `\` vs `/` in `file` | Same id (normalised before hashing). |

### What `explain` emits (Task 5)

- `$.survivors[].gapId` (string, verbatim from the report row). Absent on a row from a report written before C02-09.
- `$.gaps[]`, present exactly when the report's rows carry gap ids; `[]` when they do and no row survived. Absent (never `[]`) on an older report, so "no gaps" and "not recorded" cannot be confused. One entry per gap id with at least one `survived` row:

```ts
export interface ExplainGap {
  readonly gapId: string;
  readonly batchIndex: number;
  readonly file: string;
  readonly blockStartLine: number;
  readonly blockEndLine: number;
  readonly codeunitName: string;
  readonly procedureName: string;
  readonly triggerName?: string;
  /** mutantCodes of the gap's `survived` rows, ordered by line then mutantCode. */
  readonly members: readonly string[];
  readonly survived: number;
  readonly killed: number;
  readonly noCoverage: number;
  readonly other: number;
  /** Every RECORDED row of the block survived. Absent on an operator- or line-narrowed run. */
  readonly unobservedBlock?: boolean;
  /** The artifact to pass to `lethal verify --artifact` for this gap. Exactly one of this and
   *  `artifactIdAbsent` is present. */
  readonly artifactId?: string;
  /** Why there is no artifact to verify this gap against. Same values as on a survivor. */
  readonly artifactIdAbsent?: ArtifactIdAbsence;
}
```

- **A gap's artifact.** `carried` when ANY member is a carried row (verify would refuse that member anyway, and the gap was not measured by one artifact). Otherwise the same lookup a survivor uses (`artifactOf`): the `artifacts[]` entry whose `batchIndex` equals the gap's, else `not-recorded` (no `artifacts` field) or `not-published` (no entry for that batch). Present whether or not `--top` kept any of the gap's survivor rows. This is where the gap recipe's `<artifactId>` comes from.
- `$.noCoverageBlocks[]` (Q2): present exactly when `gaps` is; one entry per block with at least one `no-coverage` row, fields `batchIndex`, `file`, `blockStartLine`, `blockEndLine`, `codeunitName`, `procedureName`, `triggerName?`, `members` (the no-coverage mutantCodes, same order rule). No gap id and no counts: it is a location list, not a verify input.
- Order of both lists: by `file`, then `blockStartLine`, then the block's gap id (used for ordering only). Total, so the same report gives the same order on any machine.

### What `verify` accepts and emits (Task 6)

- **Syntax.** A `--survivors` token matching `^G[0-9a-f]{12}$` is a gap id. The existing mutant id is `^(0|[1-9]\d*)/(M\d{4,})$`. The two cannot overlap (a gap id has no `/` and starts with `G`). Anything else stays `malformed-request`.
- **Expansion.** Against the SAME artifact verify already resolves (`--artifact`, the store's record, the installed batch), never another run: read that artifact's hash-checked manifest (`loadInstalledArtifact`), join each manifest entry's `gapId` to the store's `batchMutantRows` for that run and batch by `mutantCode`, group with `tallyGaps`, and replace each gap id by `<batchIndex>/<mutantCode>` for each member. The expanded list then goes through `resolveVerifySource` unchanged, so every existing per-id rule (carried, not-a-survivor, wrong-batch) still applies to each member.
- **Refusals** (all exit 6, all before any lease, all naming every offending id):
  - `unknown-gap`: no manifest entry of the installed artifact has that gap id. This covers a STALE id: the block's text changed (the owner's Q1 rule makes that a new id), the block moved, or the checkout's line endings differ. The detail says so, and adds that only the last batch of a run stays installed, so a gap from an earlier batch is unknown too.
  - `gap-has-no-survivor`: the block exists but none of its rows is `survived`; the detail gives its counts, and when `noCoverage > 0` says those mutants are in explain's `noCoverageBlocks` and can be named one by one. An empty expansion is never run and never reported as success.
  - `source-predates-verify` (existing): a gap id was named but the installed manifest has no gap ids (built before C02-09). Mutant ids still work against such an artifact.
  - `malformed-request` (existing): a mutant named both directly and through its gap, or the same gap id twice.
- **Collisions.** Two different blocks sharing a 12-hex id is prevented at the WRITER: `writeInstrumentedProject` throws when one id maps to two `(file, startIndex, endIndex)` triples in its manifest, and an integration test drives that call site (Task 2). A manifest verify reads is hash-checked against the store, so it is the writer's output. `explain` refuses a report where rows sharing a gap id disagree on `file`, `blockStartLine`, `blockEndLine` or `batchIndex`. It does NOT detect two different blocks on the SAME lines of one file that share an id, because the report carries block lines, not offsets; that case is caught only at the writer, which produced the report. The plan claims no more than that.
- **Output.** Every `results[]` entry gains `gapId` (string), copied from its manifest entry, whether it was named directly or through a gap. Absent only when the installed manifest predates C02-09.

### Versions

```ts
/** C02-09: bodies that are not SINGLE_STATEMENT_SLOTS because they wrap a statement_block. The
 *  pairs are read off the parser in tree-walks.test.ts, not guessed. */
const WRAPPED_BRANCH_BODIES: ReadonlySet<string> = new Set([/* the measured pairs */]);

/**
 * C02-09: the innermost branch body holding `node` (itself included): a branch or loop slot, a
 * wrapped repeat/case-else body, or a procedure's or trigger's body block. The file root when none
 * does. A gap groups the survivors of one such block. Never null.
 */
export function gapBlockOf(node: ALSyntaxNode): ALSyntaxNode {
  let n: ALSyntaxNode = node;
  for (;;) {
    const parent = n.parent;
    if (parent === null) return n;
    const slot = n.fieldName === null ? null : `${parent.rawKind}.${n.fieldName}`;
    if (slot !== null && (SINGLE_STATEMENT_SLOTS.has(slot) || WRAPPED_BRANCH_BODIES.has(slot))) return n;
    if (n.kind === ALNodeKind.block && (parent.kind === ALNodeKind.procedure || parent.kind === ALNodeKind.trigger)) return n;
    n = parent;
  }
}
```
