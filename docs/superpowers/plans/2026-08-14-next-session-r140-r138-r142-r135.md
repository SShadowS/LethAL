## How to work

Take the rows in the order given. Finish one completely, commit it, then start the next. Do not batch
them into one change and do not start a second row because the first got hard. If a row turns out to
be blocked, write what you learned into its `docs/roadmap/R<nnn>.md` file, commit that, and move on;
a measured blocker recorded on the row is a real result, an abandoned row is not.

You are running without a human in the loop, so the roadmap row plus its cited evidence IS the
approved scope. That licenses you to implement what the row asks for. It does not license you to
widen it: if you find yourself designing something the row does not name, stop, file a new row for it
and continue with what was asked.

Rules that are not negotiable, all of them learned the expensive way:

- **Build loop order:** `bun run typecheck`, then `rm -rf packages/*/dist`, then `bun test`. Skipping
  the dist wipe gives roughly 21 phantom failures from stale compiled `*.test.js`.
- **After touching any `.al` under `fixtures/`, run `bun run compile:fixtures`.** Nothing else
  compiles them, and a broken fixture leaves the live gate happily measuring the previously
  published build (R56).
- **TDD.** Write the failing test, watch it fail for the right reason, then implement. For any bug
  fix, red-check it: revert the specific fix, confirm the specific test goes red, restore, and report
  both outputs.
- **Live gates are the authority.** A differing verdict is a BLOCK, never "close enough": stop,
  report the mismatch verbatim, and do not reconcile it by editing the expectation.
- **No two live gates at once.** The lease and the op marker are machine-global, even across
  different containers.
- **Never pipe a live gate** through anything that can close the pipe early. Send it to a log file.
  The al-runner gate takes over ten minutes; run it in the background and wait for it rather than
  letting a foreground timeout kill it.
- **A baseline is re-recorded by DELETING it and re-running**, never by hand-editing it and never by
  setting an env var to bypass the edit guard. Back the file up outside the repo first, because
  `git checkout -- <path>` is blocked by a safety hook here.
- **Pre-commit per-mutant verdicts BEFORE any live run that changes a fixture or a report figure**,
  in `docs/superpowers/specs/`, committed. Never edit a pre-commitment after the run: a contradicted
  prediction is the finding.
- **Roadmap:** file a row the moment you discover something worth one. Edit `docs/roadmap/R<nnn>.md`,
  then run `bun scripts/roadmap-index.ts`. Never hand-edit `ROADMAP.md`.
- **No `file.ext:<line>` citations in docs** — `scripts/line-citations.test.ts` fails the build.
  Cite a greppable name instead.
- **This repo is public.** Run `bun scripts/redact-campaign-report.ts <report.json>` before committing
  any campaign report from a real project.

Operational notes worth minutes each:

- **Publishing the table fixture's test app** takes a specific sequence, learned twice on
  2026-08-14. `altool publishapp` alone fails, because the server compiles the test app against the
  INSTALLED target and the installed target is the previous run's instrumented build. What works:
  unpublish the instrumented target version (`UnPublish-BcContainerApp -name 'LethAL Sandbox Data'
  -version <the 1.0.<runId>.<batch> one> -unInstall -doNotSaveData -force`), publish the plain target
  build with `Publish-BcContainerApp -useDevEndpoint -syncMode ForceSync -install`, then publish the
  test app; if BC answers "no previous version was found" or "duplicate package ID", the package is
  already published and only needs `Sync-BcContainerApp -Mode ForceSync -Force` followed by
  `Install-BcContainerApp`. Recompile the target into the test project's `.alpackages` first — a
  stale build hides behind an unchanged version string.
- Since `91bf897` the runner READS the published test app before measuring and warns by name when it
  lacks a test the source declares, so a stale test app now costs seconds rather than a gate run.
- In shell heredocs use `python3`, not `python`: the `python` on this machine mangles backslash
  escapes inside heredoc bodies, which silently breaks string replacements.

## Row 1: R140, a false `survived` from fallback 2

`docs/roadmap/R140.md`. The highest-value row here, because it manufactures a defect report against
the user's tests rather than merely losing information.

Coverage attribution has two paths that disagree. The member-level path DECLINES when every covering
test is non-green: the mutant is recorded `no-coverage`, or `error` with a note naming the red test.
The trigger path does not. `coverageFilter`'s FALLBACK 2 (`packages/runner/src/selection.ts`) runs an
unplaceable table-trigger mutant against every green test, and whatever comes back is scored. When
the object's only covering test is the red one, the green set by construction excludes the only test
that could kill the mutant, so it comes back `survived` — reliably, and silently. Measured
2026-08-13: two mutants took that path and both had been pre-committed `killed`, correctly.

Do this:

1. Decide between the row's two options and write the decision down with its reasoning: FALLBACK 2
   DECLINES (recording `no-coverage` under the existing baseline-red caveat) versus FALLBACK 2 still
   scores but the verdict carries a caveat naming the condition. The row prefers declining; if you
   disagree after reading the code, say why on the row rather than silently doing the other one.
2. TDD it at the unit level. The seam is `coverageFilter` plus whatever `untargetedTriggerCount`
   already tallies — the tally exists, the verdicts it covers are what need treatment. Red-check the
   fix.
3. Make sure a reader can tell the two situations apart afterwards. A `survived` that was never
   killable must not read like an ordinary survivor anywhere in the report.
4. Live: run `itest:tables` and expect **no change at all** — 191/31/10, `untargetedTriggerCount` 0.
   That fixture takes fallback 2 for nobody, so the gate's job here is to prove the change is a
   no-op on healthy attribution, not to demonstrate the fix.
5. Do NOT make a second fixture test red to demonstrate the fixed behaviour live. The tables gate
   asserts exactly one permitted baseline failure BY NAME, and a second one would gut that assertion.
   If you want live evidence, propose it on the row as a follow-up with its cost.

Acceptance: unit tests that go red without the fix, the tables gate unchanged, and the row closed
with the decision recorded.

## Row 3: R142, conformance cases that never check for extras

`docs/roadmap/R142.md`. Cheapest of the four, entirely offline, no container. Good to do while a
container is busy or unavailable.

R137 gave `runConformance` a refusal contract for cases with an EMPTY `expectedSpecs`. A case with a
NON-empty expectation still only checks that the expected spec appeared, so an operator emitting the
expected spec plus an unwanted one passes.

Do this:

1. MEASURE first: run every operator's non-empty conformance cases with an exactness check and list
   the cases where produced exceeds expected. That measurement decides the cost of the row.
2. For each such case, classify it: golden under-specified (complete the expectation) versus operator
   emitting something it should not (that is a bug, and it gets its own test and red-check).
3. Then make the check permanent, and red-check the contract the way R137 did — deliberately emit an
   extra spec, confirm the harness goes red, restore.
4. If the measurement shows the exactness check would be dishonest for some case shape, record that
   on the row with the case named, rather than weakening the contract quietly.

Acceptance: `bun test` green across all operator packages, the deliberate break goes red, and the row
closes with the measured list.
