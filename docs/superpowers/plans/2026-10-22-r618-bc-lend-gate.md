## 1. What lends, in what order, and what a refusal says

### 1.0 A finding first: `runMayLend` has no production caller

`runMayLend` (store.ts) is called only by `tests/r586-run-may-lend.test.ts`. Each production site
copies its steps INLINE: it calls `backendBuildRefusal`, then `runLendsAlRunnerNames`, and puts its
own checks in between. R618's text ("put `runMayLend` in front of every place") describes the
intended order, not the call graph. Two consequences:
- A red check that breaks `runMayLend` reddens no live leg. Red checks must break
  `backendBuildRefusal` or `runLendsAlRunnerNames`, which every site calls.
- The order is not one function. It is four copies, so the gate checks the order at each site
  separately.

`backendBuildRefusal` refuses only when ONE side is `al-runner-v3`. A bcdev session gets
`lendingSession = { backend: "bcdev", runnerBuild: undefined }` (`runnerBuildOf` gives a build only
on v3). So in a bcdev session:
- a v3 run is refused at step 1;
- a v2 (`al-runner`) run passes step 1. If it carries the R557 mark, it LENDS (this is the known
  gap R592). If it has no mark, it is refused at step 2;
- "another `runner_build`" cannot be refused. A bcdev run with a `runner_build` passes step 1,
  because only v3 compares builds. A BC gate cannot exercise this. The al-runner-v3 legs own it.

### 1.1 History: `priorSurvivorKeys` under `--skip-known-survivors`

What it lends: the `survived` and `known-survivor` keys of the LATEST FINISHED run for the project
path (`ORDER BY id DESC LIMIT 1`, `finished_at IS NOT NULL`). Only that one run is consulted.
Matching mutants are recorded `known-survivor` and not executed (`filterHistory`, then
`carryRecord`, then `carryBarred`). A `no-coverage` or `killed` row is never lent here.

The order of checks. The first one that refuses returns no keys. Its warning is emitted only when
`skipKnownSurvivors` is on, once per session:

| # | check | warning code |
|---|---|---|
| 1 | `backendBuildRefusal` | `history-backend-build-changed` |
| 2 | identity scheme | `history-identity-scheme-changed` |
| 3 | coverage mode | `history-coverage-mode-changed` |
| 4 | test app: hash equal, `test_app_proven = 1`, deps equal. A pending (`|pending`) or revoked (`|closed-world:revoked`) hash fails here, because it never equals the session's hash | `history-test-app-changed` (the message prints the recorded hash WITH its suffix) |
| 5 | build symbols | `history-build-symbols-changed` |
| 6 | `carry_hidden` NULL | `history-carry-untrusted` |
| 7 | hidden files differ | `history-hidden-files-changed` |
| 8 | `runLendsAlRunnerNames` (R557 mark) | `history-al-runner-test-names` |
| 9 | R557 C1: renamed baseline errors (al-runner only) | `history-al-runner-test-names` |

So steps 1 and 2 of `runMayLend` are separated here by six other checks. To reach step 8, a v2 seed
must pass checks 2 to 7, which means it must have coverage mode `fenced`. A real v2 run has mode
`al-runner`, so a real one stops at check 3.

### 1.2 `--resume` (last)

`findResumableRun` uses SQL to find the newest run that matches all of these: same project, same
backend, same config fingerprint, same scheme, UNFINISHED, at least one carryable row (on v3 also
the same build). A run from another backend is simply NOT FOUND. The session then throws
"found no unfinished run ..." (or names a run under another scheme, coverage mode or symbol set).
It does not fall back to anything.

Then `resolveResume` (orchestrator.ts) runs these checks. A refusal is a THROW, not a warning:
1. `assertLends` (`backendBuildRefusal`). In a bcdev session this can never refuse, because the
   SQL already required the same backend.
2. `assertSameTestApp`, against the pre-lease proven hash. A pending or revoked run fails here:
   "`--resume: run N was measured against test app <hash|suffix>` ... `none of its verdicts is
   carried (R247, R495)`".
3. `assertSameBuildSymbols`.
4. `carryHidden` NULL.
5. R557. This one is a WARNING, not a throw: `runLendsAlRunnerNames`, or the renamed errors, give
   `resume-al-runner-test-names` and an empty carry (`resumedFrom.carryRefused`).
6. `buildResumeIndex`:
   - `CARRYABLE_VERDICTS` = killed, survived, timeout-killed, no-coverage, known-survivor;
   - `carryableRow` drops `timeout-killed` unless `stopHungSessions` is on;
   - R577 drops a kill without `killReproduced` when `killsMustReproduce` is on (al-runner only;
     the bcdev backend does not set it, so bcdev kills carry);
   - a colliding key is dropped (`ambiguousKeys`).
7. `withoutRefusedTests` (R-236c): `resume-testpage-rescored`.
8. `resume-reusing-run` (counts) and the `resume-resolved` event.

Later, in `runSession`:
- the hidden-files union check (throws);
- after the lease, R492/R496 (`TestAppRepublishedError`);
- per mutant, `carryRecord`, which can refuse a renumbered key with the warning
  `carry-refused-renumbered`;
- `carryDisabled`.

All of steps 1 to 4 happen BEFORE `createRun` and before the lease, so a refused resume holds no
lease op.

### 1.3 `--resume-run N`

The checks run in this order: the run exists; same project; **same backend (throws "verdicts are
not interchangeable across backends")**; `assertLends`; scheme; coverage mode; `assertSameTestApp`;
build symbols; config fingerprint ("scoped differently"); `carryHidden`. Then the same tail as
`--resume`.

So a v3 run in a bcdev session is refused by the backend-equality check, before
`backendBuildRefusal`. `--resume-run` does NOT require the run to be unfinished, so a FINISHED run
can be resumed and carried whole.

### 1.4 Baseline-snapshot reuse (R192)

This happens only when `resumeState !== undefined`, `allowReuse` is true, and the batch is NOT
carried whole. `batchCarriesEntirely` replays a batch whose mutants all carry, with no deploy, no
baseline and no lookup: the warning is `resume-batch-carried`.

`findBaselineSnapshot` selects the newest row from ANY run, by SQL:
- batch hash = key;
- snapshot hash = session hash;
- the owner run has the current scheme, the same coverage mode, `runs.test_app_hash =
  baseline_snapshots.test_app_hash` (the R496 join), `test_app_proven = 1`, the same deps, and is
  not `%|pending`;
- the snapshot is not in `suspect_snapshots` and not in `lost_batches`.

After that come these checks:
- `backendBuildRefusal` gives `snapshot-backend-build-changed`, and the baseline re-runs;
- `runLendsAlRunnerNames` gives `resume-al-runner-test-names`;
- the v2 renamed errors give `resume-al-runner-test-names`;
- the R-236c scope check.

If all pass, the warning is `resume-baseline-reused`, which names the run and batch. A refused
snapshot does NOT fall back to an older one: the baseline re-runs.

R-389's identity handling:
- A closed-world session records its run hash, and every snapshot it takes, as `<hash>|pending`.
  `confirmClosedWorld` strips the suffix after execution. A changed answer instead appends
  `|closed-world:revoked` to both (`revokeTestAppHash`).
- **sandbox-app is closed-world.** Its runs record `package:<sha>|closed-world:public+internal`,
  confirmed (r553, run 4).
- Because the key is the session's unsuffixed hash, a snapshot with a natural pending or revoked
  key is never found. The join excludes the case where the snapshot kept its key but the owner run
  is pending or revoked.
- `NOT LIKE '%|pending'` cannot be reached on its own: key equality plus the join already force the
  owner's hash to equal the session's. No live red check can isolate it.

## 2. Seeding a store offline

There is no shared test helper for this. `tests/r586-run-may-lend.test.ts` has a local
`finishedRun()`, but it uses invented values. The store's write API covers every seed. No raw-SQL
WRITE is needed:

| need | API |
|---|---|
| a run row with any backend, `runnerBuild`, coverage mode, hash (with a suffix), proven, deps, fingerprint, `carryHidden`, `generationSourceSha256`, `twinTuples`, `numberingDigest`, `dependencySourceSha256`, `alRunnerNames` | `createRun` (`appVersion` is required; any string will do) |
| its mutant rows | `recordMutant` |
| finished or not | `finishRun`, or leave it out |
| a snapshot | `recordBaselineSnapshot` |
| revoked | `revokeTestAppHash(id, REVOKED_SUFFIX)` (suffixes the run and its snapshots in one transaction) |
| pending | `createRun({ testAppHash: H + PENDING_SUFFIX, ... })`, with the snapshot under either key |
| drop a snapshot | `dropBaselineSnapshot` |

The plan: CLONE the real fill run A, changing ONE field per seed. Then every other check passes,
and a refusal can only come from the field that was changed.
- `getRun(A)` gives every `createRun` field except `appVersion`.
- `mutantVerdicts(A)` lacks `mutantCode`, `line` and `batchIndex`, so the helper READS
  `SELECT * FROM mutants WHERE run_id = ?` and writes each row back with `recordMutant`.
- The snapshot comes from a read of `baseline_snapshots` (batch hash), then `findBaselineSnapshot`
  (payload), then `recordBaselineSnapshot`.

This lives in a new itest-side helper, `packages/runner/itest/lend-seed.ts`
(`seedRunFrom(store, fromRunId, overrides)`). Its options:
- `backend`, `runnerBuild`, `coverageMode`, `hashSuffix`, `alRunnerNames`;
- `keepCodes` (a set of M-codes), or `rows: false`;
- `finished`;
- `snapshot: { key: "same" | "suffixed" }`;
- `revoke`.

It gets an offline unit test, `lend-seed.test.ts`, in `:memory:`, so it runs in CI:
- a clone with no override gives the same rows as its source in `getRun`, `mutantVerdicts`,
  `priorSurvivorKeys` and `findResumableRun`;
- each override changes ONLY its field;
- each seed gives the expected `priorSurvivorKeys` callback.

This is what stops a negative leg from passing because the seed was wrong in a second field.

Running a real al-runner or al-runner-v3 session into the same store would give a "natural"
other-backend run. This plan does not do that. Such a run's coverage mode is `al-runner`, so
history stops it at check 1 (v3) or check 3 (v2), and the snapshot lookup never finds it. It would
also add a dependency on the al-runner binary to a BC gate.

## 3. Interrupting a run so that `--resume` has something to carry

- **`--only` a subset, then resume the full set: IMPOSSIBLE by design.** `only`, `exclude`,
  `operators`, `lines`, `testsOnly` and `skipKnownSurvivors` are all in `sessionFingerprint`.
  `--resume` will not match ("a run scoped by different --only ... is deliberately not matched"),
  and `--resume-run` throws "scoped differently". The subset run is also finished, so `--resume`
  cannot find it anyway.
- **Stop after N mutants:** there is no such option (no `maxMutants`, no `stopAfter`, no
  `AbortSignal` in `SessionConfig`).
- **A crashed or killed run: refused on this fixture, by design.** A crash skips
  `confirmClosedWorld`, so the run keeps `<hash>|pending`. `--resume` then throws at
  `assertSameTestApp`, as R389 intends ("a run killed before this never supplies a verdict"). It
  also risks an orphaned lease op, so it is ruled out anyway. Per the code order, a QUARANTINED
  run does reach `confirmClosedWorld`, because the batch loop `break`s and the confirm block runs
  before the "never mark a quarantined run finished" block. So the R47 case stays resumable. That
  is read from the code, not measured.
- **Chosen: an offline interruption.** Clone the finished fill run A into an UNFINISHED run with a
  chosen subset of its rows and its confirmed identity. That is exactly what a run interrupted
  after its identity was confirmed looks like. It is deterministic, and it puts no BC op at risk.
  The crashed-run state itself (`|pending`) becomes the negative seed RN1.

## 5. Where the gate lives: a new `itest:lend`, not a leg of `itest:bcdev`

- `itest:bcdev` writes the fixture's PERSISTENT `fixtures/sandbox-app/lethal.sqlite`, and pins
  `groupedCalls` 15 and `warmKills` 0 on its sessions. A history leg (3 calls) or a resume leg
  (0 to 8 calls) in that file would need its own figures, and it would leave known-survivor and
  carried rows in the store that every later run in that worktree reads. Its frozen figures must
  not move.
- `itest:lend` uses a SCRATCH store (`mkdtemp`, like `bcdev-names` and `chunked`), the same
  fixture pair (already published on bc1 to bc3, so no new fixture and no new publish), the same
  config and launch-file handling (`config-path.ts`, `assertLaunchMatchesConfig`), and the same
  `SELECTOR_IDS`. It reads `bcdev.baseline.json` read-only. It writes no baseline file. Its
  expected tables are code constants in `gate-expected.ts` (`LEND_FIGURES`), taken from the
  pre-commitment.
- Cost: about 11 BC sessions plus 3 refusals before the lease, roughly 4 to 8 minutes. Section 6
  marks the cuts.

## 6. The gate's steps (exact order; the pre-commitment)

Notation:
- S is the scratch store. A is the fill run.
- H is A's recorded hash; it must be unsuffixed. D is A's deps.
- `clone(...)` is `seedRunFrom(S, A, ...)`.
- KEPT is {M0001, M0002, M0004, M0005, M0006, M0007, M0008, M0016, M0017}: 2 killed, 5 survived,
  2 no-coverage.
- RERUN is the other 10: M0003, M0009 to M0015, M0018, M0019.
- "frozen" means per mutant equal to `bcdev.baseline.json`: verdict, `killingTest`, and
  `mutatedTextSha256`.

Every leg also asserts these, unless the leg says otherwise:
- the leg's own run row records hash H, proven, and deps D (so a faithful clone WOULD have lent);
- no warning code outside the leg's expected set among `history-*`, `resume-*`, `snapshot-*` and
  `carry-refused-renumbered`.

### Positive half

1. **L0 fill.** Run A, with no flags. Expect:
   - frozen 3 / 12 / 4;
   - `groupedCalls` 15;
   - `getRun(A)`: `testAppProven` true, the hash does not end in `|pending` or `|revoked`;
   - exactly one snapshot for A, unsuffixed.
2. **L1 history.** Run B with `skipKnownSurvivors`. The latest finished run is A. Expect:
   - M0004 to M0015 are `known-survivor`;
   - M0001 to M0003 are killed by `OverBudgetDetected`;
   - M0016 to M0019 are no-coverage;
   - counts: killed 3, survived 0, noCoverage 4, knownSurvivors 12;
   - `groupedCalls` 3;
   - no `history-*` warning;
   - the known-survivor keys = A's survived keys = the 12 survivors in `bcdev.baseline.json`
     (matched by `mutatedTextSha256`);
   - B mapped (known-survivor -> survived) equals A per mutant.
3. **R1 resume-run of a finished run.** `resume: A`, with no skip flag (same fingerprint as A).
   Expect:
   - `resume-reusing-run` says 19 carryable;
   - `resume-batch-carried` for batch 0;
   - no `resume-baseline-reused`, and no deploy (no batch artifact for the run);
   - `groupedCalls` 0;
   - all 19 rows have `carried: true`, and are frozen per mutant (the killers kept);
   - `resumedFrom` = { runId: A, carriedMutants: 19, skippedStranded: 0 }, with no `carryRefused`.
4. **Seeds for R2** (all UNFINISHED, with NO mutant rows, so neither history nor `--resume` can
   see them):
   - SP1: run `H|pending` + snapshot `H|pending` (a natural crashed run);
   - SP2: run `H|pending` + snapshot H (the join only);
   - SP3: run H + snapshot H, then `revokeTestAppHash` (a natural revoke);
   - SP4: run `H|closed-world:revoked` + snapshot H (the join only).

   Then **K** = `clone(unfinished, keep KEPT)`, created LAST so it is the newest resumable run.
5. **R2 resume.** `resume: "last"`. Expect:
   - it resolves to K: `resume-reusing-run` says 9 carryable;
   - `resume-baseline-reused` names **run B, batch 0**. B is the newest real snapshot owner;

## 9. Risks

- **The latest finished run is the only history source.** If any run finishes between a seed and
  its leg (for example a concurrent session on the same store), the leg reads the wrong run. The
  scratch store is private to the gate, and legs run one after another.
- **Snapshot owner identity.** R2 expects run B, but L1, N0 to N5 and R2 itself all record
  snapshots. R2 must run BEFORE N0 to N5, as ordered above. The gate must compute "the newest
  real snapshot owner" from S and assert that it is B, not hard-code an id.
- **Clone fidelity.** A seed that differs in a second field passes its negative leg for the wrong
  reason. Defences: N0 live, `lend-seed.test.ts` offline, and the expected warning CODE per seed
  plus the seed id in its message (a wrong second field gives an earlier code).
- **Test-app drift between legs.** A republish of sandbox-tests mid-gate would make every negative
  pass as `history-test-app-changed`. Defence: each leg asserts that its own run row's identity is
  H and D, and N1 and N3 expect codes that a drift would replace.
- **The `--resume-run` of a finished run (R1)** depends on the fact that `--resume-run` does not
  require an unfinished run. That is true today, but undocumented. If it is ever restricted, R1
  goes red, which is the right signal. The R2/K path keeps covering the unfinished case.
- **Closed-world crashed runs are never resumable** (§3). This is by design, but it is a product
  limit worth one line in `docs/gates/lend.md`. It could be filed if the orchestrator thinks a real
  project will trip on it. The quarantine path stays resumable per the code order, which has not
  been measured.
- **Cost:** about 11 sessions. Possible cuts: N1o (RC3 then becomes unit-only), R3b, or folding N0
  into L1 (but then RC10 has no live leg).
- **Server proof:** proof is per server, so the gate is admitted on each of bc1, bc2 and bc3 by one
  passing run. Under a lease; no signal stop mid-run.
- **The order is not one function** (§1.0). A future site added without copying the inline order
  is invisible to this gate. Consider making the production sites call `runMayLend` (a separate
  item; out of scope).
