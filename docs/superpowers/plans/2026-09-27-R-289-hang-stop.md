## Review Focus

1. **A diagnostic test that hangs.** In `runManyOnce`, the fetch `catch` does `settle(); await watchdog;`, and `settle()` does not release a watchdog already awaiting `StopHungRunAt`. The existing `fakes` helper in `run-mutant-many.test.ts` answers `stopAt` synchronously and cannot reject its held `RunMutantMany` fetch, so Task 1 uses a purpose-built fake whose stop is released by hand AFTER the fetch rejects, and pins the order with trace events.
2. **Two clocks and a missing t0.** The gate, the sidecar and the server each have a clock. Every timeline row uses local epoch milliseconds (`Date.now()`, same host for gate and sidecar). Status polls record BOTH send and receive times, so the inferred loop start is a bracket, not a point. If no matching poll answers, t0 is "undecided" by pre-commitment.
3. **Probing the wrong server.** `repro/nst-wedges/common.ts` fixes `BC_URL` at import time and defaults to Cronus28. Task 4 and Task 5 build settings from an explicit container before any request, and refuse to start if the URL and the gate config disagree.
4. **A repro that runs the wrong loop.** `NST Repro03 API.StartLoop` hard-codes `Runner.SetTestMethod('LoopUntilBound')`. Task 5 passes the method through the API and the answer names the method that ran; a run whose answer does not match the requested arm is discarded.
5. **A trace that changes the run it observes.** An `appendFileSync` failure inside the watchdog must not reject the watchdog and leave the main request open. Task 1 preflights the destination and makes a write failure loud but bounded (Task 1 Step 3 test 3).

## What the code already shows (facts), and what is still hypothesis

Facts, read from the code:
- The third occurrence's message, `RunMutantMany connection failed after dispatch: TimeoutError: The operation timed out.`, comes from the fetch `catch` in `runManyOnce` (`packages/runner/src/run-mutant-transport.ts`, around line 909), on the branch where `controller.signal.aborted` is FALSE. So our own 330 s abort (`requestCeilingMs + stopGraceMs`) did not end THAT call. That branch leaves out `stopDetail()`, so the record does not say whether `StopHungRunAt` was sent, answered or refused.
- The watchdog's `getOperationStatus` and `stopHungRunAt` call `postAction` with no timeout.
- `TryRenew`, `TryGetOperationStatus` and `TryStopHungRunAt` (`extensions/lethal-control/src/ControlState.Codeunit.al`) each start with `Lease.LockTable()`. `TryStopHungRunAt` then also locks `LC Op Progress`, calls `StopSession` while holding both, and commits after.
- M0004's hang reaches no guard call per loop pass: `packages/schemata/src/components.ts` groups nested sites under the outermost procedure-body mutation, and `dispatch.ts` emits one flat branch per group, so M0004's branch is selected once and then runs a loop with `Advance()` deleted. The same holds for the line-145 `SpinUntil` deletion (review r1). Task 2 confirms this on the emitted AL.
- `packages/builtin-tier1/src/loop-hazard.ts` does not classify progress made through a call, which is both `CountUpTo` hangs.

Hypotheses (unmeasured):
- **H1, starvation:** the tight loop starves the NST; other sessions' calls, `$metadata` included, stop being answered from loop start, before any stop is sent.
- **H2, lock across the stop:** calls answer until `StopHungRunAt` runs; then calls that take the `LC Lease` lock (renew, status, stop) block behind the stopping session, while lock-free calls keep answering.
- **H3, StopSession wedges the NST:** all calls answer until AL executes `StopSession`, then all stop, `$metadata` included. The trace's `stop-sent` shows only that the CLIENT sent the request: a request queued at OData or behind a lock looks the same. So H3 needs either server-side evidence that AL entered `StopSession`, or a decisive plain-versus-locked comparison in Task 5. Without one of those it stays undecided.
- **H4:** the failure does not recur within the run cap.
- **HB, Bun timeout:** Bun's fetch has a default timeout below 330 s that raised the live `TimeoutError`. Task 1 measures Bun's behaviour offline. A matching elapsed time and error text on a live run SUPPORTS HB; it does not by itself prove which layer raised the live error.
- The four `RenewLease` `AbortError`s fit H1, H2 and H3 alike. They do not separate them.
