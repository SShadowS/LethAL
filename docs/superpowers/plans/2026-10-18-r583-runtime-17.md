`plan.r2.md` holds except as changed here. F-numbers refer to `adversary-r2.md`.

## §3 the net, redone (F1, F2, F3, F4)

**One-shot.** The markers `EMIT-ZERO`, `EMIT-EXCLUDED` and `PARTIAL-EMIT-DROP` are read only from that
invocation's own `res.stderr`. The JSON `compilationErrors` is read from that invocation's envelope.

**`--server`.** `readSummary` keeps `exitCode` and `compilationErrors`, and `ServerRunResult` gains the fields.
stderr is never used, because the daemon's buffer covers its whole life.

**Scope.** An entry counts only when it names the ACTIVE TARGET bundle: its `file` or module is the instrumented
target, or it names an object LethAL emitted or mutates, such as `MutationSelector`. An entry for the TEST app
(a safe `EMIT-EXCLUDED` of unreached test codeunits) keeps today's behaviour: absent rows become per-test
`error` (`pre-dispatch-rejected`). An entry whose module cannot be attributed counts as target, the safe side.

**Outcome.**
- On the baseline (`activate(null)`), a target-bundle entry makes the backend throw a typed error,
  `AlRunnerTargetCompileError`, which extends `Error` directly and names the message. The orchestrator turns it
  into a session refusal at the point where it already refuses a failed baseline, named in the build.
- On a mutant run, it turns every row into `error`, with the message attached. It is never killed and never
  survived.

**The existing door, stated in R583.** Today `--server` ignores `exitCode` and `compilationErrors`. So on 069cbf32
at runtime 13, the R387 default scored rows from a bundle al-runner had refused. That gives false SURVIVES, not
false kills, because the baseline and every mutant behaved the same.

**Measured expectation, added to the pre-commitment.** Zero target-bundle `compilationErrors` on every leg of
every al-runner gate, on both builds. Test-app entries, if any, are listed and must be unchanged.

## 1. The runtime move

  al-compile. 1.0.0.21 is taken by lethal/r389, which has its own AL changes and is waiting on the owner's Global
  republish. Two builds must never share a version: whichever lands second rebases its version above the other's,
  so R-389 would become 1.0.0.23 on runtime 17. R583 records this dependency.
  `MIN_CONTROL_VERSION` is raised to 1.0.0.21 only if a runtime-16 build must be refused. That is my default: no

## 2. Refuse below runtime 14.0 (al-runner resource selector)
- In `AlRunnerBackend`, the selector mode is decided ONCE, at `deploy()`, from the `active/app.json` that al-runner
  compiles. It is stored in a field that `activate()` reads (review r1 finding 4), and `selectorMode()` is never
  re-read.
- When the effective mode is resource and the runtime is below 14.0, compared as numeric major.minor, the backend
  THROWS a typed error by name: "runtime <X> is below 14.0, which the resource selector needs
  (NavApp.GetResourceAsText, AL0666); set app.json runtime ≥ 17.0 or alRunner.selectorMode static".
- An unparseable runtime is refused the same way, as fail closed.
- No runtime field means resource is kept, since al-runner compiles at its newest runtime. R583 records that this
  was measured on 069cbf32 only.
- `alRunnerAdvisory` no longer says `"resource" is faster` when the runtime is below 14.0. It says to raise the
  runtime instead (review r1 finding 7).
- The error class extends `Error` directly. The CLI reports it like the other configuration refusals.

## 3. The general net: refuse a run al-runner partly failed to compile
Measured (bisect.md "PARTIAL-EMIT-DROP"):
- PARTIAL-EMIT-DROP never fires for a diagnosed drop like AL0666. It catches BC's silent drop only.
- The runtime case shows as `EMIT-ZERO` or `EMIT-EXCLUDED` on stderr, and as non-empty `compilationErrors` with
  `exitCode` 3, in both the one-shot JSON and the `--server` summary. Tests still run and can PASS.

So the guard reads the envelope, not one marker:
- **Any al-runner answer carrying non-empty `compilationErrors`** gives no scorable row. This covers the one-shot
  envelope and the `--server` summary, and the case where tests are present.
- Every test row in such an answer is read as `error`, with the compile message attached by name. Today's R518
  timeout path keeps its own `compilationErrors`-absent condition.
- On the BASELINE run, such an answer refuses the session by name: a project al-runner did not fully compile
  cannot be measured.
- On a mutant run, the mutant reads `error`, never killed or survived, with the message.
- **The stderr markers `EMIT-ZERO`, `EMIT-EXCLUDED` and `PARTIAL-EMIT-DROP`** (matched by prefix, since only the
  prefix is documented) give the same outcome even when `compilationErrors` is empty. That keeps the net
  independent of the JSON field.
- The old build f06ee78c prints none of these for this case, because it ignored the runtime. R583 says so: the
  net is effective only on builds that diagnose.

# R-583 plan r1 (lethal-code): the resource selector needs runtime 14.0; fall back below it, and keep the gate testing it

Base: master 0254e6d2. Branch `lethal/r583`; R583 is filed there (0810551c). Bisect: `/coord/handoff/R-583/bisect.md`.

## Finding (measured)
- **The first bad upstream commit is f23b9b5f.** From that commit on, al-runner compiles at the app's own
  `runtime` from `app.json`. Before it, al-runner always compiled at the newest runtime.
- **The resource selector needs runtime 14.0.** `emitResourceSelector` (in `schemata`'s `selector.ts`) calls
  `NavApp.GetResourceAsText`, which needs runtime 14.0. `alc` itself gives `AL0666` on runtime 13.0. So the
  resource selector was only ever valid on runtime 14.0 or newer, and old al-runner accepted it only because it
  ignored `runtime`.
- **What the user saw.** On f23b9b5f and later, al-runner drops `MutationSelector.Codeunit`, and every test then
  fails with a misleading "active-mutant.txt not found".
- **So this is a LethAL assumption, not an upstream regression.** The standalone repro confirms al-runner's
  behaviour is correct.
- **Users are exposed too, not only the gate.** 18 of the 19 fixtures declare runtime 13.0. Since R387, the CLI
  default on al-runner is `--server` plus the resource selector, so any user app on runtime 13.0 or lower breaks
  on a current al-runner. One-shot runs with the resource selector fail the same way.

## Change
1. **Runtime check (`packages/runner/src/al-runner-backend.ts`, `installResourceSelector` and `selectorMode`).**
   - Read the target's `app.json` `runtime` once per session.
   - When it is BELOW 14.0, the backend uses the static selector instead, and emits a named warning,
     `al-runner-resource-selector-runtime`. The warning says the runtime found, that the resource selector
     needs 14.0 (`NavApp.GetResourceAsText`, AL0666), and that each mutant is now recompiled.
   - No runtime declared: al-runner then compiles at its default, the newest. Keep the resource selector.
   - A runtime that cannot be read or parsed: fall back to static, the safe side, with the same warning. Never
     guess.
   - The CLI default (`cli.ts`, `serverMode ? "resource" : "static"`) is unchanged; the backend decides per
     target. An explicit `"selectorMode": "resource"` in the config on a runtime below 14.0 also falls back,
     with the warning, rather than failing every test. The report states that the effective mode was static.
2. **Report.** The effective selector mode is recorded where the report already records the resource or static
   leg. The warning carries the reason.
3. **Gate (`packages/runner/itest/al-runner.itest.ts`).** With the fallback, the resource legs would quietly run
   static on the runtime-13.0 fixtures and stop testing R222's transport.
   - The gate copies each fixture pair it uses for a resource leg to its own temp folder, as it already does.
     In that copy alone, it sets `runtime` to `"14.0"` in both `app.json` files.
   - al-runner compiles from source, so no publish and no BC is involved, and the committed fixtures and the
     bcdev and tables gates are untouched.
   - The gate ASSERTS that each resource leg's effective mode is resource, not static. This is the
     anti-inertness check: a leg that silently fell back fails by name.
   - The one-shot and static legs keep the fixtures' own runtime 13.0. They are unaffected.
4. **Docs.** R583 gets the finding, the fix and a re-open condition: re-check if a later BC runtime moves
   `GetResourceAsText`. The CLAUDE.md itest paragraph and `docs/measurements/README.md`'s al-runner v2 section
   need a one-line note. That is the owner's file; I only propose the CLAUDE.md line, never edit it.

## Tests (each red-checked alone, full output read)
1. A runtime-13.0 manifest under `selectorMode: "resource"`: the backend installs the STATIC selector and emits
   the named warning. Red: drop the runtime check.
2. Runtime 14.0 and newer: the resource selector is installed. Red: compare with `<=` instead of `<`.
3. No `runtime` field: resource. Red: treat missing as below 14.0.
4. A runtime that cannot be parsed: static, with the warning. Red: treat an unparseable runtime as 14.0.
5. The gate's effective-mode assertion fails when a resource leg ran static. Red: run the leg on an unpatched
   fixture.

- `itest:alrunner` on BOTH builds:
  - the current pin f06ee78c, expected PASS with the frozen figures unchanged;
  - a scratch build of 069cbf32, expected PASS. That build failed before this change.
- After this lands, the daily update can move `current` to 069cbf32 or newer. That is the orchestrator's call,
  not this task's.
