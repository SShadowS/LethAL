# PR-215 measurement, design and pre-commitment: tests that reach Report.RunRequestPage on LethAL's BC path (R1135)

Coord PR-215 (lethal-code, 2026-11-19). Roadmap: R1135. Evidence: `/coord/handoff/PR-215/` (`size.ts`, `tests.tsv`,
`kills.tsv`, `projects.tsv`, and the smoke run in `smoke/`).

**Revised before any build** after the spec-adversary review (2026-11-19). The first version (master 839c5be3) misstated
today's verdict for such mutants (`no-coverage`; it is `error`), proposed a classification that R113 would turn into a new
caveat, would have named the wrong cause when only request-page tests are present, and took the parse count as evidence that DO
does not reach the call.

## 1. Measured: how many tests reach it, and how they read
- **The parse** (`size.ts`): PR-161's WorkDate sizing, adapted.
  - **What counts:** a test method reaches `RunRequestPage` when it, its `HandlerFunctions`, or same-codeunit helpers to depth 3
    call `.RunRequestPage` on `Report` or on a report variable.
  - **The smoke check:** an invented codeunit with a direct call, a call through a helper, a `Report.Run`, and a test with no
    call. The script found exactly the first two.
  - **Scope:** 86 projects (R-975's 83 BC.History projects, DO, DC) and 7,904 test methods.
- **Result: 26 test methods in 3 projects reach it by a direct call.**
  - `xl`: 20 tests, all refused at v3's stored baseline.
  - `bd`: 2 tests, counted twice because two stores carry the project.
  - `sub`: 2 tests, both passing at v3's baseline. 12 v3 kills rest on one of them.
  - `Report.Run`/`RunModal` reach 70 tests; recorded only.
- **The count is a floor, and DO does reach the call.** Library code, Base Application and the app under test are not
  followed. PR-133's H1 (`docs/superpowers/specs/2026-11-17-pr133-x2-restarts-precommitment.md`) recorded 6 v3 daemon closes
  in DO on a `Report.RunRequestPage` refusal reached through Base Application code. **The design below does not rest on the
  count:** it matches the failure text, so every test that hits the refusal is named, whatever the parse found.
- **How they read on bcdev** (PR-158's bcdev run of `sub` on bc3, `/coord/handoff/PR-158/runs/sub.bc3/`):
  - `DetailedCalculationReportUsesSubcontractorPricing` **fails at the baseline** with "The report request page cannot be used in
    background or server sessions.";
  - `TestSubcontrDispatchingList` is refused before it runs, as a possible TestPage (R-236c).

  That run was scoped to one other file, so it shows no mutant verdict for this test.

## 2. Today's handling, read from the code
- **A test that does not pass at the baseline is dropped from the green set** (`didNotPassAtBaseline`). Nothing in this item
  changes the green set.
- **A mutant left uncovered by the green tests but covered by such a test is recorded `error`, outside the score.** Its note
  comes from `unsupportedCoverageNote`, and for a request-page test it is the generic "unsupported test type: mutant covered
  only by test(s) that did not pass at baseline (...)".
  - A mutant the test reaches only after the refusal reads `no-coverage`, because the test stopped there.
  - **No false verdict comes from this item.**
- **What is wrong is the cause the run names:**
  - the test counts only as a baseline failure;
  - its mutants' notes say "unsupported test type";
  - no report block names the request page.

  The same family has a named class: `tests-testpage-unsupported` (R57/R58), widened by R909 to Linux BC's CLR shape.

## 3. The change (the smallest honest one; no new classification, caveat or field)
- **The matcher:** `describeRequestPageRefusal(failureText)` in `testpage-unsupported.ts`.
  - It matches BC's words "The report request page cannot be used in background or server sessions" in the failure's FIRST
    LINE only. Stack frames never match, as `TESTPAGE_REFUSAL_RE`'s guard ensures.
  - It returns a request-page diagnosis (`REQUEST_PAGE_DIAGNOSIS`, with BC's own words).
  - It becomes the third branch of `describeTestPageRefusal`, so both call sites pick it up:
    - the baseline emit, which classifies the test `tests-testpage-unsupported`;
    - `select`'s per-mutant map.
  - **The event stream and its schema stay as they are.**
- **The report** (`buildReport`) re-matches each listed test's baseline `failureMessage` to choose the block's `diagnosis`:

  | tests present | `diagnosis` |
  |---|---|
  | TestPage tests only | `TESTPAGE_DIAGNOSIS`, unchanged (byte-identical) |
  | request-page tests only | `REQUEST_PAGE_DIAGNOSIS` alone |
  | both | `TESTPAGE_DIAGNOSIS`, then one sentence naming the request-page tests (R1135) |

  - The banner's count line says "for opening a report request page", or "a TestPage or a report request page", only when one
    is present.
  - The caveat key and its interpretation are unchanged.
- **The per-mutant note** gets a request-page branch in `unsupportedCoverageNote`, after the TestPage branch. Its lead is
  "request page unsupported on this path: mutant covered by test(s) that open a report request page, which this session type
  cannot show", followed by `REQUEST_PAGE_DIAGNOSIS`.
- **Known limits:**
  - English BC only. The text was measured on BC 28.4 W1. A localized or reworded server falls back to the generic note, which
    is the safe direction (as with R66, R35 and R69).
  - `Report.Run(..., true)` in this session is not measured.
- **Not changed:**
  - verdicts, counts, `mutationScore`, the green set, R904's data-off stop;
  - every event;
  - every report with no request-page failure, byte for byte;
  - every gate: no fixture calls `RunRequestPage`.

## 4. Predictions
- **P1:** a baseline whose only failure carries the request-page text:
  - `testPageUnsupported.tests` names the test;
  - its `diagnosis` is `REQUEST_PAGE_DIAGNOSIS` and does NOT contain "TestPage";
  - the caveats include `tests-testpage-unsupported`.
- **P2:** a run with only a TestPage failure gives the same report as before, byte for byte (the existing goldens and snapshots
  unchanged). Both kinds present give the TestPage text plus the sentence.
- **P3:** a pass, a line-count answer, or the text only in a stack frame (not line one) is not classified.
- **P4:** a mutant covered only by a request-page test gets the request-page note lead and diagnosis.
- **Red checks in both directions:**
  - the matcher removed: P1 and P4 go red;
  - the line-one anchor or a guard removed: P3 goes red;
  - the request-page diagnosis used always: P2 goes red;
  - the note branch removed: P4 goes red.
- **Gates:** none move. VERIFY, and CI.

## Amendment 1 (2026-11-19, after the build and its opus review; not a prediction)
**Changed from the review:**
- **The report fold follows the orchestrator's precedence.** It names a test as request-page only when the Windows TestPage text
  is absent, so a failure that carries both is a TestPage refusal in the note and in the report alike. There is a test, and its
  red check passed.
- **The P3 test** claims only what the matcher decides (text, line one). A pass and a line-count answer are kept out by the
  orchestrator's existing guards (`didNotPassAtBaseline`, `isRunMutantLineCountMessage`), unchanged here.
- **Two stale comments are corrected:** `SessionReport.testPageUnsupported`, and the orchestrator's classification note.

**Left as they are, by design (byte identity for every run without the text):**
- `CAVEAT_INTERPRETATIONS["tests-testpage-unsupported"].meaning` keeps the TestPage text, and so does the banner's header
  ("TESTPAGE UNSUPPORTED ON THIS PATH:"). The block's own `diagnosis` and the banner's count line name the request page.
- **A mutant covered by a TestPage test and a request-page test** gets the TestPage note. The request-page tests are listed in
  it as tests that did not pass for another reason.
- **A resumed or lent run** names request-page tests only from batches recorded by this build. Carried verdicts keep their
  earlier generic note. No verdict or count differs either way.
- `itest/verify-scale.ts` treats any `tests-testpage-unsupported` as "a TestPage test was sent". No fixture reaches a request
  page, so this cannot happen today; it is recorded here.
