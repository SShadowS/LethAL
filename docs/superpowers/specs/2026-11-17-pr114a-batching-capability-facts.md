- **114b:** batching, gated on 114a's accessor, with every high and medium fix from the reviews.

Design and evidence: `/coord/handoff/PR-114/` (spec-draft.md draft 3, `carry-probe.ts`, `carry2-probe.ts`, `lane/`, `mem/`), and

## Why facts, and why a new kind
Batching rests on four facts about al-runner v3, each measured on edge-4ebfe7913 and each an upstream default that has moved
before (ADR-066 amendment 12, ADR-070 mid-migration):
1. In one plain request with several test codeunits, no state crosses codeunits through SingleInstance globals, a SingleInstance
   temp table, a library codeunit's globals, a real row or a bound manual subscriber.
2. An EXCLUDED test codeunit with an OnRun carries nothing.
3. An INCLUDED test codeunit with an OnRun reaches later codeunits, and they stream a duplicate row: the signature 114b's
   pre-decode check relies on.
4. The SingleInstance lane only hints (`orderHints`) without `strictOrder`, and re-runs (a second row) with it.

**A contract fact that does not read `matches` refuses the whole session** (`v3ContractRefusals`), which is far too strong here.
These facts only decide whether batching may switch on. So they are a NEW fact kind, `capability`:
- **In the gate** (`classifyLegC`), a capability fact must read `matches`, else gate-fail. A build that widens the carry or the
  lane is caught before it can become `current`.
- **In a session,** a capability fact never refuses. It only feeds the accessor.

## The facts (`al-runner-v3-contract.ts`; invented AL generated by the probe, no DotNet, no sidecar)
All run through serve with LethAL's batch body: no `test`, the complement in `excludeTests`, `testIsolation: "test"`, coverage and
per-test coverage, and none of `runSelectedOnly`, `strictOrder`, `testSuites`, `testRunner` or `testDriver`.
- **The four no-cross facts** (writer and reader codeunits, as `carry2-probe.ts`):
  - `batch-no-cross-singleinstance`: covers the SingleInstance counter and the SingleInstance temp table;
  - `batch-no-cross-library-global`;
  - `batch-no-cross-row`;
  - `batch-no-cross-subscriber`.

  Each reads `matches` when every reader row in the batch equals the reader alone.
- **`batch-onrun-excluded-no-carry`:** an OnRun writer EXCLUDED from the batch. The reader and a third codeunit equal their
  single answers (`carry-gate1.txt`).
- **`batch-onrun-included-duplicates`:** an OnRun writer INCLUDED. The later codeunits stream a second row with the same name (the
  carry's signature). It reads `matches` when the duplicate appears, so a build that carries silently fails it.
- **`batch-lane-hint-only`:** the lane app (`lane/lane2-probe.ts`), our body. The reader row is exactly `fail` "store is 0", with
  2 rows in all and a summary `orderHints` entry naming that test and the global.
- **`batch-lane-strict-reruns`:** the same with `strictOrder: true` (NOT our body). The reader is re-run: a second reader row
  that passes.

The facts run in their own scratch source folders, so no fact's codeunits reach another fact's requests. Leg C goes from 28
to 36 facts.

## The accessor (`al-runner-v3-pins.ts`, in the style of `sleepRuleRetiredFor`)
`baselineBatchingFor(contract, version, sha)` is true only when ALL of these hold:
- the build's pin carries `baselineBatching: true`;
- this session's probe reads all 8 capability facts as `matches`;
- `sleepRuleRetiredFor(...)` is true (the §6 gate of draft 3, M4).

It is computed once in `status()`, kept in a private field, given a getter, and printed in the session's details ("baseline
batching: allowed | off (<reason>)"). **No pin carries `baselineBatching` in 114a, so it is false on every build, and no code
batches.**

## The gate leg `DBM` (al-runner-v3.itest.ts; not in `V3_GATE_LEGS`, as DB and DBI are not)
- **The fixture:** `fixtures/sandbox-optin` and `-tests`: 4 test codeunits, no OnRun, and mutants in the target.
- **What it runs:** a session with `daemonBaseline: true`, and the same fixture with the one-shot baseline.
- **What it asserts:**
  - **per-mutant equality between the two sessions** (verdict, `killingTest`, notes), a self-relative check that needs no new
    frozen baseline file;
  - the daemon baseline was not dropped;
  - `requests === codeunits` (4);
  - the sample count equals `baselineSampleIds(4).length`;
  - `judgeDaemonBaseline("DBM", ...)` names every skip.
- **What 114b changes.** 114b turns batching on for this leg with a batch-size seam of 2, so the complement is never empty (draft
  3, M2). The request count then moves 4 -> 2, pre-committed there.

## Predictions (pre-committed)

- **Every other leg and pin is unchanged.** No session behaves differently, because the accessor is false everywhere. Sessions'
  contract probes take longer by the new facts' requests; the cache absorbs this after the first run (`probeCodeHash` changes, so
  every cached probe is re-run once).
- **DBM passes:** per-mutant identical, 4 requests for 4 codeunits.
- **Unit tests, each red when its rule is reverted:**
  - each fact's reading from fake answers, both ways (`matches` and not);
  - `classifyLegC` gate-fails a non-`matches` capability fact;
  - a session never refuses on one;
  - the accessor is false without the pin flag, false when any fact is not `matches`, false without §6, and true only with all
    three;
  - the fact count (36) and kinds;
  - DBM's leg list entries.
- **Docs:** the gate page (leg C's count and kinds, the DBM bullet, a History entry), docs/measurements/README.md's fact count,

## Addendum 1 (2026-11-17, after the first live run and the Opus build review, before the final gate)
- **Leg C's first live reading.** On edge-4ebfe7913, all 8 capability facts read `matches` (`/coord/handoff/PR-114/gate-observe.log`),
  and leg C passes in 28 s.
- **DBM's first run failed:** its selector ids lay outside `sandbox-optin`'s id range (77200-77249), so the instrumented app did
  not compile. They are now 77249/77248/77247.
- **DBM's figures, pre-committed here** from the observe run on the fixed ids (`/coord/handoff/PR-114/gate-dbm.log`): in both
  sessions, 15 killed, 3 survived and 104 no-coverage over 122 mutants, with 0 errors and 0 timeout-killed.
  - The daemon baseline: 4 codeunits, 4 requests, 2 served and compared samples, nothing dropped.
  - The warning sets: `dbm-oneshot` `[]`; `dbm-daemon` `["al-runner-v3-memory-guard", "al-runner-v3-serve-flagged-unknown"]`.

  DBM asserts these counts (`assertCounts`, from gate-expected.ts), so two equally uninformative sessions cannot pass.
- **Fixes from the review:**
  - a fact request that times out stops the probe's daemon and marks the remaining facts `unmeasurable`, so a late answer is
    never read as the next fact's (M1);
  - capability facts never make the probe uncacheable (M2);
  - `batch-onrun-included-duplicates` sends a non-empty `excludeTests`, as LethAL's body always does (L2);
  - DBM gets DBI's not-applicable path on a no-serve build (L3).
- **R164 on DBM, stated honestly.** Built-in operators refuse hang-capable sites (R196) and never tag them, so the
  `hangCapable` check guards only a future tagging operator. What keeps `sandbox-optin`'s loop sites off a server is that no test
  calls those procedures.
