## 2. Revised after the spec-adversary review (2026-11-19): the rules that are safe, and what they give on DO
The first version (master 024858b3) predicted 824 exact `no-coverage` on y2. The review showed that number rests on an unsafe
rule.
- **The flaw:** (b) used (i)'s object-to-method relation as if it listed every left-out method that can reach a mutant. It does
  not:
  - one hop only, and only through a company-writing helper;
  - no calls through target objects;
  - no event subscribers (`CDO Subscribers` holds 40).

  A red method's unknown coverage could then pass as "no coverage". For example, `CDO Upgrade Tag Definitions` is reachable
  from a red Folder test through `CDO Azure Blob Folder Upgrade`, and (i) relates it to the green `StaleExpiryUpgrade` only.

**The safe rules:**
- **(a) Covered by a left-out method** in the source's `coveringTests`: **unmeasured**, with the new cause
  `left-out-test-coverage`, naming the methods.
- **(b) `no-coverage` only when EVERY left-out method of this run passed at the source's baseline** (green = baseline outcome
  exactly `pass`, read from positive evidence: per-test outcomes in the report, or the source's events) **and the source row is
  an observation**:
  - its verdict is `no-coverage`, `survived`, `killed` or `timeout-killed`;
  - it is not `carried`, not in `unplaceableMutants`, and not R609-noted.

  (b) restores the verdict `record()` received before (i)'s rewrite. It never writes a hard-coded `no-coverage`, which matters
  under `coverage none`. Its note says "per al-runner v3 (not authoritative)".
- **(c) Anything else:** (i) unchanged.
- **The input checks:**
  - `confirm.ts`'s `assertSameScope` in full: flags (`preprocessorSymbols`), suite (`testsOnly`, `excludeTests`), and source;
  - a duplicate check on the join key;
  - a test-source sha256 that the report must carry, with older reports refused by name;
  - `--resume` refused, as confirm does;
  - a per-session reset of the source map, like `setLeftOutReach`.
- **The report ripple** (one change): the new `MutantErrorCause` `left-out-test-coverage`, per-test baseline outcomes or a
  passed list, and a run-level `coverageFrom` (input sha256, and the (a), (b), (c) counts). That is the full `SessionReport`
  ripple of CLAUDE.md, including regenerated sample reports.

**What the safe rules give on DO's y2:** 14 of 16 left-out methods were red, so **(b) = 0 and (c) = 1,346**. (a) catches the
59 mutants covered only by left-out methods, all of which (i) already marks. **On y2, (iii) changes no DO verdict.**

## 3. The decision gate, pre-committed
- **(iii) is built only if a real source makes it do something.** That means a v3 run of DO in which all 16 left-out methods
  pass at baseline, so (b) is non-zero.
- **y3** (when scored, about 14:30 CET): the 16 methods' baseline outcomes, and (a), (b), (c) under the safe rules, are
  measured and recorded here.
  - **If (b) > 0 on y3:** the build follows, with the predictions taken from y3 per mutant, and computed through PR-212's
    built `companyWriteMethods` (± the parser's difference, per object). The tests: (a), (b), (c), each refusal, P3's byte
    identity, and the fallback, each red-checked both ways.
  - **If (b) = 0 on y3 as well:** R1137 is recorded as measured (no effect on DO), and closed by a ruling, not built. The
    report ripple is not worth zero moved verdicts (owner principle 13). It is revisited when a project's source run passes
    its left-out tests.
- **v3 is not authoritative** (R586). Even with (b) > 0, its coverage of company-writing tests is v3's, and is labelled so.
