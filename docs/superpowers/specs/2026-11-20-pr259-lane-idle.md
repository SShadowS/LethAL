# PR-259 spec-light: where perf10c's ~890 s of lane idle went, and the lever (R1156)

lethal-preproc, 2026-11-20, offline (DO speed lever 4 of PR-251). Source: perf10c,
`/coord/handoff/PR-217/perf10c.run.events.ndjson` (3 lanes, mutants phase 16,457.5 s on the monotonic clock). Scripts and
outputs: `/coord/handoff/PR-259/` (`idle.py`, `gaps.py`, `split.py`, `hash-time.ts`, `hash-variants.ts` and their `.txt`).
Numbers and names only.

## 1. When the lanes were idle (overlap-clipped request intervals, the suspend excluded)
Busy = the union of each lane's serve requests `[atMs − wallMs, atMs]` (`atMs` is monotonic; the 3 requests that
spanned the 1,967 s suspend have their wall reduced by it). Idle = the phase minus busy: 2,664 lane-s (888 s of wall),
matching PR-251's corrected figure.

| where | lane-s | |
|---|---|---|
| start (lanes 1-2 wait for lane 0's 72 s warm-up: R785's lane gate sizes them from its peak) | 149 | memory admission |
| window boundaries (the gaps of 5 s or more) | 32 | one 9.3 s wait is the only one the TIMING line counts |
| the tail (after each lane's last request) | 1 | |
| **between consecutive requests, under 5 s each** | **2,482** | 10,047 gaps, median about 240 ms |

The between-request gap is the same whatever the request (kind, entries or tests); it grows by about 200 ms for each
other lane whose answer lands inside it. Split at the next request's `serve-request-sized` event, the time is all AFTER
it: answer -> sized 1 ms; sized -> send 94 ms (lane 0) and 264-270 ms (lanes 1-2) median.

## 2. Why: R652's per-send bound check
- `sendInFlight` runs `checkBound` -> `assertBound` before every send, outside the timed request wall: it re-reads and
  SHA-256s every `.al` file of the lane's instrumented tree (R767 made it synchronous).
- perf10c's own counter: `bound 2,380,997 ms over 10,050 checks` (one per send: 236 warm-ups + 6,482 prefetch + 3,332
  live), so **237 ms per check, 2,381 lane-s: 90% of all lane idle.**
- DO's instrumented tree: 591 `.al` files, 69 MB. Measured offline on CPUs 12-21 (`hash-variants.txt`): walk 2.9 ms,
  stat of every `.al` 1.3 ms, reading every `.al` 25.7 ms, read + SHA-256 (today) 67.5 ms, read + `Bun.hash` (wyhash)
  36.3 ms; `hashAlTree` as called today 84 ms median. In the run it costs about 2.8 times that (237 ms): the reads
  are synchronous, so three lanes' checks queue on the one JS thread beside three busy daemons.

## 3. What each lever saves (wall seconds per DO run like perf10c; all verdict-neutral)
| lever | saves | why |
|---|---|---|
| longest-first ordering of heavy codeunits | about 0 | the tail is 1 lane-s |
| work-stealing at the tail | about 0 | same |
| smaller tail windows | about 3 | window waits are 32 lane-s in all |
| lanes 1-2 start without waiting for lane 0's warm-up peak (R785 seeded from a measured peak) | up to about 50 | 149 lane-s; changes memory admission |
| **(A) bound check with a fast content hash** (every byte still read, every send) | **about 420** (300-500) | 237 -> about 110 ms per check if the in-run factor holds |
| (B) stat fast path (size, mtime, ctime, ino, git's racy-entry rule; full hash at each daemon start) | about 750 | 237 -> about 15 ms per check |

The orchestrator's three levers aim at the tail, which perf10c does not have: its idle is a fixed cost per send.

## 4. Proposal: (A) now; (B) only by a ruling
- **(A):** at proof time also record a bound fingerprint of `active/`'s `.al` files (path + `Bun.hash` per file, folded in
  sorted order), kept in memory beside `activeHashExceptSelector`; `assertBound` compares that instead of re-running
  `hashAlTree`. Every `.al` byte is still read before every send, so it still catches what today's check catches
  (added, removed or changed files, a same-size rewrite with the mtime restored); only the collision bound changes, from
  SHA-256 to 64 bits per file against accidental drift, which is all the guard is for (a user's or LethAL's own edit
  after the proof, R652). `hashAlTree`, the proof key, `boundKey` and every stored hash stay as they are. The other
  checks (`otherFilesDrift`, `app.json`, the selector, `lastActivated`) are unchanged: they cost under 5 ms.
- **(B)** is what R652 and R767 deliberately left out ("it changes what the guard trusts"). It saves about 330 s more,
  but a same-size rewrite with every stat field restored would pass unseen until the next daemon start. Owner's call;
  not proposed.
- **Verification (pre-committed for (A)):** unit tests: R767's four T22 cases pass unchanged against the new fingerprint
  (a same-size rewrite with the mtime restored, an `.al` added, removed, a test `.al` added), each red-checked (a constant
  fingerprint goes red); a path rename with equal bytes is caught. Live: the full v3 gate with 0 per-mutant differences;
  `boundMs/boundChecks` on a DO run (or PR-246's held combined run) read before and after, the claim being under 130 ms
  per check.
- **Not chosen:** hashing in a worker (a lane still waits for its own hash; only the cross-lane queue goes), and checking
  once per window (R652 moved to once per send on purpose).
