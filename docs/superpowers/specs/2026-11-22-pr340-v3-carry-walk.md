## Step 0b, before any build: do excluded codeunits run hidden? (review S1)
- **Why it matters:** R1094 showed that an ENTRY's `excludeTests` hides rows but still runs them. Whether a top-level batch
  `excludeTests` skips whole codeunits is not measured. If they run hidden, a DO walk runs the whole suite and times out.
- **The probe:** the carry fixture (§7) gets a third test codeunit, a CPU burner of about 2 s, that covers nothing. The
  seq batch is sent excluding it, with and without `runSelectedOnly: true`, and with the echo kept in.
- **The judgement:**
  - a burner that runs hidden shows as `testsMs` of 2 s or more on a request whose visible rows take milliseconds;
  - with `runSelectedOnly`, the walk must still kill M0009-M0011.
  - The body the build sends is the one that skips the burner and still kills.
  - **If no body does both, nothing is built, and this pre-commitment is amended.**
- **MEASURED (2026-11-22, `/coord/handoff/PR-340/probe/seq0b/`, main-ef9f6a222): excluded codeunits are SKIPPED.**
  - The burner (71772, a fixed 3,000,000 iterations) took 234 ms at baseline.
  - Every walk request that excluded it took 2.6-4.8 ms of `testsMs`, with and without `runSelectedOnly`.
  - Every walk still killed M0009-M0011 (fail with the mutant, pass with `none`, fail again).
  - The echo, kept in, read `LETHAL-ECHO:<mutant>`, then `LETHAL-ECHO:NONE`, then `LETHAL-ECHO:<mutant>`.
  - **So the build sends the batch body WITHOUT `runSelectedOnly`, the shape step 0 measured.**
  - **A first try used a clock-bounded loop.** It ended at once (1 ms): al-runner's clock does not advance inside a loop.
    That run is kept as `seq0b-clockburner/` and is not evidence.
  - **Still not tested:** the burner's id is above both 71770 and 71771, so an excluded codeunit sitting BETWEEN the
    writer and the reader is not tested. The gate page says so.

## 1. The variable: on every mutant-run v3 serve daemon, proven inert (the orchestrator's alternative)
- **LethAL sets `AL_STRICT_SEQUENTIAL=1` on EVERY mutant-run serve daemon it starts, in the child environment** (not
  inherited).
  - al-runner reads the variable's PRESENCE (`var_os(..).is_some()`, so even `0` turns it on).
  - LethAL therefore always sets it on these daemons, and tests check that it is present whatever the ambient value is.
- **The update gate's leg C (the contract probe) is EXCLUDED: its servers do not get the variable,** except the new
  `batch-sequential-carry` fact's own server, which sets it explicitly.
  - The variable is NOT added to `v3ChildEnv`, which leg C's servers also use. It goes in a separate helper used only
    where the backend starts a mutant-run daemon.
  - So `batch-lane-strict-reruns` and every other leg-C fact keep measuring what they measure today. Pre-committed: their
    readings do not move.
- **Read in al-runner's source** (5a58a0f16, the delta review): every use goes through
  `sequential_strict() = strict_order && strict_sequential`. Without `strictOrder` nothing changes.
- **Why not a second daemon:**
  - it would add about 2.5 GiB per lane, which no memory rule counts (R1176: 3.3 per lane at `--peak 22`);
  - it would cost a warm-up per lane.
- **The proof that the variable is inert outside `strictOrder` requests:**
  - step 0's 13 of 13;
  - the FULL v3 gate on the final head: 0 moves against every frozen baseline, D1, D1c and T included;
  - and every later al-runner update gate, whose LethAL-run legs carry the variable.
  - **Any move is a BLOCK, and the fallback is the second daemon,** with its memory counted.
- **The ordinary path's `strictOrder` stays absent,** as today.

## 2. When the walk runs (orchestrator)
- **Only on al-runner-v3.** On bcdev the session already carries state, and R1174 re-walks it there.
- **Only for a mutant scored `survived` whose PR-327 (a) label would be added,** judged over the FULL covering set
  (`fullCovering`, the PR-303 pruned path included).
- **Never on:** an unsafe session, a spent or signalled time budget, a dry run, `LETHAL_V3_CARRY_WALK=off`, or a build
  that is not carry-proven (§4).
- **On the lane that scored the mutant:** a lane-view method (`carryWalkOn(lane, ...)`), never forwarded to lane 0. A test
  covers 2 lanes.
- **The order is al-runner's own sequential walk** (BC's codeunit order), never the kill ledger. A walk kill never feeds
  the ledger (R1174's rule), which keeps it clear of PR-302's ledger effect.
  - The gate page records that bcdev's R1174 re-walk uses the no-ledger order. So a reader placed before its writer in
    one order and after it in the other can still disagree between backends.

## 3. What the backend sends, and when a walk kills
- **Three requests on the lane's daemon,** each batch-shaped with `strictOrder: true` and step 0b's body:
  - the kept codeunits: the mutant's covering codeunits;
  - **the ECHO included**, everything else excluded;
  - the activation goes through the lane's resource file, as a batch send does: (1) the mutant, (2) `none`, (3) the
    mutant again.
- **The guards, as today's batch sends:**
  - the bound check and artifact proofs run BEFORE the resource file is written;
  - the walked mutant id is checked against `proof.manifestIds` explicitly;
  - each send polls for a stop signal (`STOP_SIGNAL_POLL_MS`);
  - the resource file is restored afterwards, even after a throw;
  - the deadline is `v3CallDeadlineMs` over the kept codeunits.
- **KILLED by test T** only when ALL hold:
  - every one of the 3 answers holds EXACTLY the baseline tests of the kept codeunits plus the echo row (R198-style
    completeness);
  - the echo names the mutant, then `none`, then the mutant;
  - T is `fail` in (1), `pass` in (2) and `fail` in (3);
  - T is the first such test in the answer's order.
  - **This is R577's reproduction and R653's no-mutant confirm, in the carry lane.** A leak from one request into the
    next makes (2) fail, so it cannot kill.
- **WALKED, no kill:** all three answers are complete with correct echoes, and no test goes fail, pass, fail.
- **WALK FAILED:** anything else (the reason is named):
  - an error, refusal or timeout of any request;
  - an incomplete row set;
  - a wrong or missing echo;
  - zero rows;
  - a stop signal.
  - **A walk failure never moves a verdict.**
- **A timed-out walk** kills and replaces the lane's daemon, as any timed-out request does. It can never score
  `timeout-killed`.
- **A test red in (2)** (the lane's own baseline red) never kills.

## 4. Each build must prove the carry (review B3)
- **A new leg-C batch fact, `batch-sequential-carry`:** with `AL_STRICT_SEQUENTIAL=1`, a batch `strictOrder` request
  over an invented writer and reader pair must make the reader FAIL with the carried state.
- **AMENDMENT 1 (2026-11-22, found while building): the walk is allowed when THIS SESSION's contract probe reads
  `batch-sequential-carry` `matches`, and the build's own gate record (`.gated` or the manifest row) does not record it
  as anything else.**
  - A recorded `diverged` wins; a record WITHOUT the fact does not block.
  - **Why the change:** v2.1 also required the record to carry `matches`. But no existing build's record can carry the
    fact until this change merges, and the update gate re-runs. Under that rule the walk would stay off everywhere,
    including on the carry gate, whose pre-committed table could then never hold.
  - **What still guards B3:**
    - every session runs the probe (`status()`, or the R762 probe cache keyed by build);
    - a build that ignores the variable makes the probe read `diverged`, so the walk is off;
    - an unmeasured fact (an old cache without it) also turns it off;
    - and a walk can only kill on fail, pass, fail with correct echoes, so a broken build can at worst give "walked" or
      walk-failed. "Walked" needs the probe's `matches`, so it cannot come from a build that ignores the variable.
- **Otherwise:** walk-failed "build not carry-proven", with the label kept.

## 5. How it is scored
- **KILLED:**
  - verdict `killed`, with the killing test T, its failure from (1) and the reproduced failure from (3);
  - `failureNote` gains `[singleinstance-carry-killed] killed when the covering codeunits ran in one session, in order
    (al-runner's sequential lane, R1173)`;
  - the `[singleinstance-carry-unobservable]` label is NOT added.
- **WALKED:** `survived` stays, with `[singleinstance-carry-walked] survived with the covering codeunits run in one
  session, in order (R1173)` in place of the label.
- **WALK FAILED:** `survived` stays, with the label plus `[singleinstance-carry-walk-failed: <reason>]`.
- **The tags live in the existing free-text `failureNote` field,** as PR-327 (a)'s label does. No `Caveat`, no report
  field, no schema bump.
- **`LETHAL_V3_CARRY_WALK=off|on`** (default on; a bad value is refused by name) is folded into the config fingerprint,
  as PR-303 did for `LETHAL_V3_REACH_PRUNE`. A `--resume` across on and off is refused with the same message shape.

## 8. Tests (red-checked both ways; stateful fakes with call counters, never timing)
1. **fail, pass, fail** with complete rows and correct echoes gives `killed` by T with the tag. Reverting the scoring
   turns it red.
2. **fail, fail, fail** (red without the mutant) gives walked, not killed.
3. **fail, pass, PASS** (no reproduction) gives walked, not killed.
4. **The echo naming `none` where the mutant was expected, or missing** gives walk-failed.
5. **A kept codeunit's row missing in any answer** gives walk-failed.
6. **A refusal, a timeout or zero rows** each gives walk-failed, with the label kept and the reason named.
7. **A build with no `batch-sequential-carry` record, or this session reading it otherwise,** gives no walk and the note
   "build not carry-proven".
8. **Every mutant-run serve daemon's environment has `AL_STRICT_SEQUENTIAL` present,** whether the ambient value is set
   to 0, set to 1 or absent. Leg C's ordinary fact servers do NOT get it, and `batch-sequential-carry`'s server does.
   Red both ways.
9. **No walk for:** bcdev, an unlabelled survivor, a 1-codeunit set, an unsafe session, a spent budget, a killed mutant,
   or `off`. The call counter must be 0.
10. **With 2 lanes, the walk's sends go to the scoring lane's daemon and resource file only.**
11. **A carry kill never enters the kill ledger.**
12. **The resource file is restored after a throw.**
13. **`LETHAL_V3_CARRY_WALK` is in the fingerprint,** and a resume across values is refused.
