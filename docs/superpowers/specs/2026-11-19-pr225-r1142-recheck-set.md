## 2. The change (A)
- **The recheck's `tests`:** for each target, the covering tests whose main-pass outcome under that mutant was not
  `pass` (a withheld kill stores its distrusted failure as `error`: these are the candidate killers). Then add every
  main-baseline test of those tests' codeunits. Today's set is the covering tests and their codeunits.
- **The input** is a per-target list of not-pass covering tests, read from the main pass's own results (events or store),
  not the report.
- **Nothing else changes.**
  - Rules (a) to (e) are unchanged.
  - A killer outside the set has no recheck-baseline row, so rule (c) fails and the row stays `error`.
  - **A test a rule needs and the baseline did not run counts as not passed: unmeasured, never a kill.** (c) already
    says "not in the recheck baseline". (e) already counts "no result" as lost.
- **A target with no not-pass covering test** contributes no test. Its row stays `error`, because it can have no
  killer the rules accept.

## 6. Amendment 1 (2026-11-19, before any live run): found by the Opus build review, ruled by the orchestrator
**What the review found.** The nested recheck session executes ONLY the tests in the set: `keepOnlyTests` is the set.
So its killer is always in the set, and narrowing the set can change WHICH test kills first. Two parts of §2 and §3 are
therefore wrong.
- **A row can GAIN a kill.** Take a target with covering tests K1, which passed under the mutant in the main pass, and C,
  the distrusted failure.
  - Today the nested run may meet K1 first. K1 kills, then fails rule (e) or (b), so the row stays `error`.
  - Under A, K1 is not run. C kills alone, reproduces, passes alone at the recheck baseline, and its codeunit loses
    nothing, so the row becomes `killed`.
  - The kill ledger's test order can shift killers the same way.
- **A left-out killer never reaches rule (c),** so §2's "rule (c) fails" path cannot happen. And §3's "the 12 stay
  `error`" is not a per-mutant certainty: another candidate may kill some of them.

**The ruling** (the orchestrator, 2026-11-19). A gained row is a measured kill, not a false one. Its killer meets every
recheck rule: it failed under the mutant in the main pass (it is a candidate), the kill reproduces alone, it passes alone
at the recheck baseline, and its codeunit loses nothing. That is exactly the evidence the recheck exists to demand.
Running both sets to forbid gains would throw away the saving the owner approved.

**What replaces §2 and §3:**
- **Gains are allowed** when the new killer meets rules (a) to (e) in the narrowed run. **A gain whose killer fails any
  rule is a BLOCK.**
- **Losses are allowed** only as kept rows with their rule named. The kept note now says how many of the row's covering
  tests the recheck ran. The others passed under the mutant in the main pass, or the main pass never reached them, so
  they are unmeasured here (R1142). This replaces §2's rule (c) note, which could not fire.
- **§3's per-mutant prediction becomes a bound:** at most 12 of today's 409 recovered rows are lost (the named 12),
  every other recovered row keeps its killer, and gains are possible.
- **The live check compares all 516 targets per mutant,** kept ones included, not only today's 409. It lists every gained
  row with its killer and the rules it met, and every lost row with its kept note.
- **The result tells the owner in one line that A can also gain measured kills,** not only lose up to 12.
- **Also from the review:** `notPassTestsOf` now ignores rows run with no mutant active (`mutant_code` NULL: an unmutated
  kill confirm, a warm replay, a discovery confirm). Those rows are not outcomes under the mutant. This has its own red
  test.
