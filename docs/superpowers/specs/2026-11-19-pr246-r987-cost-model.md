## 0a. Amendment 1 (2026-11-19, the rulings, the cause read in code, and the offline replay; before any build)
- **RULED:** Q1 fix the model (price by recent real growth per entry; keep the 4 GiB bound and the RSS guards as the net);
  Q2 an offline replay first, then ONE full DO run against y3 per mutant, after PERF-10 and PR-235's resume.
- **The cause, read in code** (`noteEntryCost`, al-runner-v3-backend.ts): cost per test entry = `(peakRss − floorRss) /
  tests`, where the floor is the LOWEST start the daemon ever had. A kept daemon holds ~1 GiB over its floor (y3 lane 0:
  start p50 2.97 GiB), and that held memory is divided over every request's entries as if they had grown it; each call then
  keeps its HIGHEST such cost for the whole session ("never falls"). §1's "highest ever" was half of it; the floor is the
  other half.
- **The new model (pre-committed for the build):**
  - a reading's cost per test entry = `max(0, peakRss − startRss) / tests` (marginal growth, from the request's own start);
  - a call's price = the highest of its last K = 5 readings (recent, not all-time); unmeasured calls keep today's rule;
  - `groupsThatFit` and its caps are unchanged (4 GiB summed price, 256 entries, 16 unmeasured);
  - held memory stays bounded by the guards built for it: lane admission by peak (R948/R952), the recycle bound
    (`daemonMaxRssGb`, 6 GiB) between requests, the memory gate before each chunk;
  - the PR-88 cap-lowered line and the `serve-request-sized` event report the new price (the event keeps `floor` and
    `start`, so a later run can replay either model).
- **The offline replay** (`/coord/handoff/PR-246/replay.py`, `replay.txt`; y3's sized events in run order per lane; merges
  across units assume `LETHAL_V3_PACK_ENTRIES=256`):
  - the OLD model replayed: 5,052 -> 4,842 prefetch requests (the replay is within ~4% of what y3 actually did);
  - the NEW model: 5,052 -> **1,270** (K=5; K=1: 1,253, K=20: 1,349): ~2,320 s of fixed cost, **9.7% of the 23,928 s mutant
    phase**.
- **The full DO run (pre-committed; after PERF-10 and PR-235's resume, on a quiet box logged as such):**
  - same scope and config as y3, `--profile slim` (y3 predates PR-209's default operators), `--workers 3`,
    `LETHAL_V3_PACK_ENTRIES=256`, the new model;
  - **predicted:** prefetch requests 1,270 ± 15%; prefetch setup+baseline lane-seconds ≤ 35% of y3's 7,897; mutant phase
    at least 1,500 s below y3's 23,928 s;
  - **must hold:** every verdict equal to y3's per mutant on the full site key; any difference is first checked by a
    CONTROL run without the change on the same head (master has moved since y3: PR-225's recheck set, PR-227, PR-241), and
    only a difference the control does not show counts against the change; daemon peak per lane recorded, no lane over its
    admission, no recycle storm (recycles reported and compared with y3's).

## 0b. Amendment 2 (2026-11-19, the Opus build review, before any run): a held-memory reading may raise a price, never lower it
- **The hole:** marginal growth from the request's start reads LOW when the request reuses memory the daemon already holds
  (freed .NET memory is reused by whatever runs next). Five such readings could drive a call's price to ~0, and the next
  request (256 entries; across units under the pack knob) could grow far past anything seen. No guard foresees it: the
  recycle bound reads RSS only between requests, lane admission reads the session's highest absolute peak (never `costOf`),
  the memory gate checks usage before a chunk with no forecast, and `watchMemory` runs only for the baseline. The worst case
  is a cgroup OOM kill (32 GiB, shared). Verdicts are not at risk (a dead prefetch is dropped and re-run live; a dead live
  request scores `error`), but the full DO run would count the differences.
- **Pre-committed fix:** a reading from a daemon whose start is `RETAINED_SLACK_BYTES` (512 MiB) or more over its floor may
  RAISE a call's price (it is pushed when above the current price) but never LOWER it (otherwise dropped). Only near-floor
  readings, which reuse cannot distort, bring a price down. Red tests both ways (a high-start low reading is dropped; a
  high-start high reading raises the price; a near-floor low reading lowers it).
- **Replayed** (`replay.py` 'guarded', `replay2.txt`): 5,052 -> 1,287 prefetch requests (unguarded 1,270): still ~2,309 s,
  9.7%. §0a's predictions stand (1,270 ± 15% covers 1,287).
- **Also:** K = 5 pinned by a test that fails at K = 4 and K = 6 (importing `COST_READINGS_KEPT`); the stale "highest"
  comments in `al-runner-v3-entries.ts`, `events.ts` and `backend.ts` updated.
- **Known limit:** the replay and §2's tail read growth from the request's start too, so they share part of the blind spot
  the guard closes; the full DO run records daemon peak per lane and recycles against y3's.

## 1. Measured (y3, DO, 3 lanes, 5,052 prefetch requests)
- **The budget binds:** predicted cost / 4 GiB: p50 0.85, p90 1.65 (PR-241 amendment 4).
- **But real memory growth is ~30x smaller than predicted:** growth (sampledPeak − start) per prefetch request p50 0.11 GiB,
  p99 0.14, max 0.87; real/predicted p50 0.03, p90 0.10, p99 0.62, max 1.00. Per non-echo entry: p50 11.9 MB, p90 31.0,
  p99 98.5, max 148 MB.
- **Real daemon memory:** peak per lane max 3.62 / 3.41 / 3.29 GiB (sum of the three lanes' maxima 10.3 GiB) inside the
  container's 32 GiB (28 GiB after the 4 GiB reserve).
- **Why (from the code survey, to be confirmed by the build's first step):** R987 keeps each codeunit's HIGHEST cost ever
  measured (`noteEntryCost` / `costByCall`), so one heavy request (a first compile, a warm-up) inflates that codeunit's cost
  for the rest of the run. On a one-hour slice it has not yet inflated: PR-94's slice reads cost/budget p50 0.03, max 0.84
  (`sized-slice.py` on PR-241 arm A), which is why a slice cannot show this lever.

- **Tail risk:** real growth adds per entry (R987 measured it linear on Contoso), so the worst merged request grows by the

  reads RSS between requests and would recycle a daemon that ends a request above it.
- 3-lane DO windows declare `--peak 18` today; a larger per-request growth would need that declared peak re-measured.

## 3. Proposal
- **Fix the cost model, not just the number:** price a codeunit by its RECENT real growth per entry (e.g. the last request's
  `(sampledPeak − start) / entries`, or a p90 over its last k requests) instead of the highest ever; keep the 4 GiB budget
  as the bound on that honest estimate, and keep the R948/R952 guards (lane admission by peak, the recycle bound) as the
  safety net. Expected: close to the "none" row on DO (most requests well under 4 GiB of real growth), ~7-10% of the
  mutant phase together with `LETHAL_V3_PACK_ENTRIES` for cross-unit merges.
- **Alternative (smaller, no model change):** raise the budget to 8 GiB (4.7%, tail max 1.07 GiB).
- **Verification:** a slice cannot show it (§1). Options: (i) a full DO run A/B on a quiet box (two ~7 h runs), judged on
  requests and the per-request cost in the same run; or (ii) first an offline replay of y3's sized events through the new
  cost model to predict requests per lane exactly, then one full DO run with the change against y3 per mutant.
- **Must hold:** every verdict equal per mutant; daemon peak per lane recorded; no lane above its admission.
