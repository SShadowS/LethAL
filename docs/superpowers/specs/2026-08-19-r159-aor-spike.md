# R159 spike: is Arithmetic Operator Replacement worth building for AL?

Measured 2026-08-19. Instruments: `scripts/r159-aor-spike/` (`aor.ts` prototype operator,
`census.ts`, `compile-proof.ts`). Corpus: `do-rel2/Cloud`, 554 `.al` files. Compile proof:
`fixtures/sandbox-data` and `fixtures/sandbox-app`.

R159 filed AOR as the one absent operator with no recorded reason anywhere: `+`/`-` and `*` / `/` are
the most standard mutation in the literature, and `design.md` §4 does not list them in any tier
while no roadmap row refuses them. This spike is the measurement that turns that into a decision.
It answers three questions and deliberately does not answer the fourth.

## 1. How many sites survive a compile-safety guard?

AL overloads `+` heavily: Text concatenation, `Date + Duration`, `DateTime + Duration`, `Label`
formatting. Swapping any of those emits AL that `alc` rejects, and a rejection arrives as an
`AlcCompileError` on the whole project AFTER the expensive instrument-and-publish step. So the
prototype claims a site only when BOTH operands resolve to a numeric type (`Integer`, `Decimal`,
`BigInteger`, `Byte`), and refuses anything it cannot type.

| | count |
| --- | ---: |
| arithmetic nodes in procedure/trigger bodies | **1,121** |
| claimed (both operands provably numeric) | **100** |
| refused: an operand is provably NOT numeric | **844** |
| refused: an operand could not be typed at all | **170** |
| refused: operator outside the flip set (`div`, `mod`) | 7 |

Split of the claimed: **73 additive**, **27 multiplicative**.

**The headline is the refusal, not the claim.** 1,006 of the 1,121 tokens are `+`, and the refused
shapes are `Text + ?` 337, `Text + Text` 169, `Text + Text[2]` 157, `? + Text` 85, `Text + Label` 17.
In this app AL's `+` is overwhelmingly **string concatenation**, so the literature's most standard
operator applies to **8.9%** of the sites its name suggests. That is a fact about AL rather than
about this corpus's style, and it is the reason nobody should have ported AOR over on reputation.

The two refusal classes are counted separately on purpose, and the order of the checks matters:
"provably not numeric" is tested BEFORE "could not be typed", so `Text + <untypeable>` files as
settled rather than as open. Reporting it the other way round would inflate the apparent headroom of
a better type table by 337 sites on its own.

## 2. Does the guard actually work, in both directions?

`compile-proof.ts` applies each mutation one at a time to a real project and runs `alc`.

| project | positive pass (claimed sites must compile) | negative pass (refused sites must be rejected) |
| --- | --- | --- |
| `fixtures/sandbox-data` | **8/8 compile** | **4/4 rejected** |
| `fixtures/sandbox-app` | **3/3 compile** | 0/0, **vacuous**, that project has no non-numeric arithmetic |

Every negative is rejected with the same diagnostic, e.g.

```
error AL0175: Operator '-' cannot be applied to operands of type 'Text' and 'Text'
```

The negative pass is the load-bearing half. Without it, a guard that refused every site would score
a perfect positive pass, which is this repository's signature bug in its purest form: empty-vs-empty
reading as agreement. The script says VACUOUS out loud rather than printing `0/0` and letting it
read as evidence.

One incidental finding worth recording: `Level * 2` to `Level / 2` COMPILES on Integer operands, so
`/` yielding Decimal does not fail the assignment it feeds. The multiplicative hazard is a runtime
one, not a compile one.

## 3. Would it find anything the shipped operators do not?

R13's precedent bar for an operator on the existing emit path is **>= 13 MARGINAL sites**, where
marginal means sites no shipped operator already perturbs. It was calibrated on the smallest shipped
operator (`swap-modify-flag`, 13), and `IsolationLevelSwap` was refused under it at 11.

Overlap is measured at STATEMENT granularity, with `empty-block` counted separately rather than
folded in: every statement sits inside some `code_block`, so folding it in would report ~100%
overlap and prove only that a coarse operator exists. The question is whether a FINE-GRAINED mutant
already perturbs the same statement.

| | count |
| --- | ---: |
| claimed sites | 100 |
| statement already carries a fine-grained mutant | 39 (39.0%) |
| **statement carries no fine-grained mutant, marginal** | **61** |
| of those marginal: additive | **48** |
| of those marginal: multiplicative | **13** |

What covers the overlapping 39: `negate-conditional` 18, `conditional-boundary` 17, `return-value`
11, `void-method-call` 8, `remove-setrange` 1.

**Additive clears the bar by 3.7x (48 >= 13). Multiplicative lands exactly ON it (13 >= 13).**

## 4. What this spike did NOT measure

- **Kill behaviour.** Nothing here is a live run. Whether an existing suite kills an arithmetic
  mutant, and whether that kill discriminates, is unmeasured. `fixtures/sandbox-data` has 8 claimed
  sites and would be the arm; registering the spike operator would move the frozen `itest:tables`
  figures, so it was not done.
- **The 170 untypeable sites.** They are a limit of `packages/engine/src/semantic/types.ts`, not a
  property of the code, and they bound the claimed count from below. Filed as R160.
- **One corpus, one vendor.** A codebase doing more numeric work would shift every number here.

## Recommendation

**Build the additive half. Do not build the multiplicative half yet.**

Additive is 48 marginal sites, compile-proven in both directions, on the existing emit path, needing
no new activation mechanism. That is a straightforward operator by this project's own precedent.

Multiplicative sits exactly at the bar and carries a hazard additive does not: `x * y` to `x / y`
divides by zero whenever `y` is zero, which raises and scores a **kill that says nothing about the
test**, the R121 false-kill shape, and the same shape as arm E of the R82 swap fixture where a BC
length overflow killed a mutant under a test asserting nothing. Taking it needs a declared
`PlatformKillMechanism` and a screen decision first, exactly as `swap-modify-flag`'s `Insert` arm
needed `run-trigger-skipped-insert` (R138, narrowed by R143). Thirteen marginal sites is not worth
that on its own; it becomes worth it if R160 lifts the type table and the count grows.

Whatever is built needs the usual live arm with per-mutant verdicts PRE-COMMITTED before the run.

**One practical note for the conference demo:** `examples/gift-card` contains **zero** arithmetic
nodes, so an arithmetic operator could not be shown on the demo app without changing it. Worth
knowing before anyone plans a slide around it.
